# Archive Center GitHub Install/Update Contract

Archive Center has two different GitHub paths. They must not be mixed.

## 1. Normal User Path: GitHub Release Package

Normal users install and update from GitHub Releases, not from a raw source
checkout.

The release package contains:

- compiled backend binaries
- package launchers
- migrations
- prompts
- OS-specific runtime bootstrap scripts

This path is the default for Windows, Linux/Ubuntu, macOS, and Termux.

Normal-user fresh-install entrypoints:

- POSIX: `install.sh`
- Windows: `install-windows.ps1`

Their public commands are fixed in `docs/simple-fresh-install.md`. They require
no user-selected timeout, install directory, CPU, service mode, restart delay,
or start flag. They stop before network or file changes when the managed install
root already exists. They do not perform updates.

Internal Release helpers:

- POSIX: `scripts/install-github-release.sh`
- Windows: `scripts/install-github-release.ps1`

The fresh-install entrypoints call these internal helpers with the normal
defaults. Direct helper use and the separate update path remain advanced
interfaces rather than additional normal-user fresh-install methods. Both
helpers require a caller-selected external-operation timeout
(`AC_EXTERNAL_OPERATION_TIMEOUT_SECONDS`, `--external-operation-timeout-seconds`,
or `-ExternalOperationTimeoutSeconds`). They do not substitute a hidden network
deadline.

These helpers must:

1. read the latest GitHub Release
2. select the current OS package asset
3. download `SHA256SUMS*.txt`
4. download the selected package ZIP
5. verify SHA256
6. extract into a versioned install directory
7. keep runtime data in a stable install-level data directory
8. move the local `current` pointer to the verified package
9. create an install-level launcher that reads the persisted install-level data
   root before entering the current package
10. optionally start or register that install-level launcher

The package launcher is responsible for MariaDB, ChromaDB, migrations, and
`live/full_local` runtime env. A release-package install must not leave the
backend in `shadow/noop/core_lite/fallback`.

Release updates must not use the versioned package directory as the canonical
database location. The installer-owned data root is:

- POSIX/systemd: `$INSTALL_DIR/data` through `ARCHIVE_CENTER_DATA_DIR`
- Windows helper: `$InstallDir\data` through `ARCHIVE_CENTER_DATA_DIR`

The POSIX helper persists this path outside the versioned package and both
direct starts and systemd starts enter the current package through the same
install-level launcher. A package update or later process restart therefore
cannot silently switch MariaDB or ChromaDB back to a package-local `.runtime`.

If a previous release stored data under a package-local `.runtime`, the helper
may migrate that runtime into the stable data root only when the stable root has
not already been initialized. It must not overwrite an existing stable data
root during an update.

## 2. One-click Managed Update

This contract starts with the completed Archive Center 3.9.9 package. Archive
Center 3.9.0 and the intermediate 3.9.5 test package are not direct-update
sources and are not given a special compatibility path. They must make one
fresh 3.9.9 installation while preserving only user MariaDB data, ChromaDB
data, local settings, and secrets; their old backend, launcher, updater,
`.updates`, package manifest, and runtime binaries are discarded. After that
fresh installation is healthy and the preserved data has been verified, every
package under this contract must support later updates from the settings UI
with one click on `지금 업데이트`.

The normal update flow is fixed:

1. The plugin sends one `POST /update/apply` request. It does not choose a
   platform, CPU architecture, asset name, hash, or current version.
2. The running backend uses its own `GOOS` and `GOARCH` to select the release
   asset and reports the detected runtime identity.
3. The backend reads the latest GitHub Release, selects the matching package,
   downloads the release SHA256 list and package, verifies the package hash,
   and writes the pending update under the package-owned `.updates` directory.
4. The backend finishes and flushes the HTTP acknowledgement, then exits with
   code `75` only when it was started with
   `AC_UPDATE_APPLY_MODE=managed_launcher_exit_75`.
5. The already-running managed launcher sees exit code `75` and immediately
   enters the existing updater transaction. The user does not run another
   command, restart the package, or click another button.
6. The updater verifies the current updater binary, current managed manifest,
   candidate archive hash, candidate `package_version`, complete candidate
   manifest, migration contract, and every managed file fingerprint.
7. The updater adds and replaces candidate files and removes files that were
   managed by the old manifest but are absent from the candidate manifest.
   Runtime data, `.runtime`, `.updates`, local environment files, MariaDB data,
   Chroma data, and secrets are never managed package files.
8. The launcher applies every `migrations/*.sql` file in lexical order and then
   runs the schema binary's embedded rerunnable schema work.
9. The launcher starts the candidate and requires `/ready` plus an exact
   `/version` match before committing the update.
10. If schema application, startup, readiness, version verification, or commit
    fails, the updater restores managed package files only. It never rolls the
    database back. The restored backend must start successfully against the
    forward-migrated database and pass `/ready` plus its exact old version.

Runtime package selection:

| Running backend | Release package |
|---|---|
| `windows/amd64` | Windows x64 |
| `linux/amd64` | Linux x64, including Ubuntu x64 |
| `linux/arm64` | Linux arm64, including Ubuntu arm64 |
| `darwin/amd64` | macOS Intel |
| `darwin/arm64` | macOS Apple Silicon |
| `android/arm64` | Termux arm64 |

The 4.1.0 release publishes Windows x64 only. A native Windows arm64 backend may
identify itself correctly, but automatic update is not declared supported until
a matching, fully bundled Windows arm64 release asset is built and published.

Linux may additionally report the distribution ID from `/etc/os-release`, such
as `ubuntu`, but the package ABI remains Linux plus its CPU architecture. A
client-supplied platform that disagrees with the running backend is rejected.

Release packages must contain `PACKAGE_FILE_MANIFEST.json` with an exact
`package_version` and `PACKAGE_MIGRATION_UPDATE.json` with the complete
migration inventory. The inventory includes both SQL files and the
`mariadb-schema` binary because that binary owns embedded schema work. Database
changes must remain expand-first, rerunnable, and usable by the previous
backend. Database rollback is not part of the updater.

## 3. Operator Path: Git Source Checkout

Raw `git clone` is an operator/developer path. It does not by itself install
MariaDB, ChromaDB, package launchers, or system services.

A source checkout may be used to build packages, run tests, or prepare a
release. It must not be described as a normal full install unless a deploy
script has built and staged a package-shaped install root.

Required future operator helpers:

- source build/deploy script
- source update/deploy script
- `/ready` release gate after service restart

Until those helpers exist, the supported self-host install path is the GitHub
Release package helper.

## Required Ready Gate

After an install or update, the backend must pass the release gate:

```text
mode=live
store_mode=mariadb_authority
runtime_profile=full_local
vector_mode=local_native|bundled|local_proot
mariadb=configured
chromadb=configured
degraded=false
```

If `/ready` reports `shadow`, `noop`, `core_lite`, or `fallback` for a full
install, the install is not complete.
