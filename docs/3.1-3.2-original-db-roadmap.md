# Archive Center 3.1-3.2 원작 DB 강화 로드맵

상태: 원작 DB 전용 범위와 구현 순서 재정리  
최종 정리: 2026-07-18

## 1. 목표

원작 DB의 품질이 사용자의 자료 수집 능력에 좌우되는 문제를 줄인다. 사용자는
작품명과 판본, 허용할 출처 범위를 선택하는 것만으로 검증 가능한 원작 자료를
확보할 수 있어야 한다. 사용자가 합법적으로 보유한 자료를 직접 추가하는 경로도
동등하게 유지한다.

공용 팩, 자동 발견 자료와 사용자 자료는 한 원작 검색 기반에서 함께 사용할 수
있어야 하지만 소유권은 섞지 않는다. 같은 문서와 같은 사실은 반복 저장·주입하지
않고, 독립 출처가 같은 사실을 지지하면 출처와 근거를 합쳐 보존한다. 판본이나
범위가 다르거나 내용이 충돌하면 자동 병합하지 않는다.

## 2. 이번 로드맵의 경계

포함한다.

- 작품·판본·continuity 통합 식별과 제목·원제·번역명·별칭 검색
- Versioned Canon Pack의 검증, 설치, 조회, 비활성화, 제거와 rollback
- 사용자 비공개 원문과 Local Canon Overlay의 독립 보존
- 문서 hash, 출처 observation, 근거 locator와 fact provenance
- 문서·개체·사실의 중복 및 충돌 진단
- 합법적이고 허용된 출처를 대상으로 한 Source Discovery
- coverage saturation과 `insufficient_source_coverage`
- 승인된 공용 자료와 사용자 승인 overlay의 결합 검색 및 중복 없는 주입

포함하지 않는다.

- RisuAI Host Context, 로어북, 캐릭터 설명, 시나리오와 작가 노트 저장
- 장기 기억 admission, 기억 무결성 판정과 서사 교정
- 로어북 또는 캐릭터 봇 자동 생성
- 커뮤니티 유행·밈·말투 분석을 Canon으로 저장하는 기능
- 배포 권한 없는 원문 전체를 Canon Pack 또는 릴리스에 포함하는 기능
- 모델 추론이나 검색 답변을 출처 있는 사실로 자동 승격하는 기능

메인 장기 기억은 구현 대상이 아니다. 원작 DB 오류가 `/ready`, 메인 저장·삭제·
검색을 막지 않아야 하고 원작 검색은 독립된 예산과 주입 경계를 사용한다는 격리
계약만 검증한다.

## 3. 데이터 소유권

### 3.1 Canon Pack

재사용 가능한 작품별 승인 자료 패키지다. manifest, 작품·판본 식별, pack version,
호환 version, 출처 observation, 문서 checksum, 근거, 승인된 사실, conflict,
uncertainty와 coverage report를 가진다. 원문 전체는 배포 권한이 있을 때만 포함한다.

### 3.2 Private Full-Text Source Library

사용자가 합법적으로 보유하거나 직접 제공한 원문을 로컬에만 보존한다. Canon
Pack과 함께 배포하지 않는다. 원문에서 파생된 사실은 문서 hash와 locator로 근거를
추적한다.

### 3.3 Local Canon Overlay

사용자 자료에서 승인된 원작 사실을 저장한다. 공용 Pack row를 수정하지 않으며
pack update, remove와 rollback 뒤에도 보존한다. supplement, override, suppress와
conflict 관계는 명시적인 backend 계약으로만 적용한다.

### 3.4 Candidate Staging

Source Discovery와 모델 추출 결과를 승인 전 보관하는 격리 계층이다. candidate는
`pending`이며 실제 검색·주입 collection에 들어가지 않는다. 사용자에게는 개별
사실 전수 검수가 아니라 충돌, 불확실성, 판본 불일치와 근거 부족 같은 예외만
검토하도록 한다.

## 4. 변하지 않는 원칙

- MariaDB가 canonical truth이고 ChromaDB는 재구축 가능한 검색 index다.
- 정책, 식별, 중복 판정, 설치 transaction, 검색과 주입 계획은 Go backend가 맡는다.
- `Archive Center.js`는 RisuAI 관찰, transport, 실제 payload 적용과 UI만 맡는다.
- 고정 자료 수, 인물 수, 후보 수 또는 품질 점수로 완료를 판정하지 않는다.
- 같은 hash는 중복 blob으로 저장하지 않지만 독립 source observation은 잃지 않는다.
- 비슷한 문장은 범위와 의미가 검증되기 전에는 같은 fact로 병합하지 않는다.
- 공식 출처도 판본 차이와 상호 충돌을 보존한다.
- `.env`, DB, 사용자 원문, 채팅, secret과 Chroma data를 Git이나 배포물에 넣지 않는다.
- Pack 실패는 원작 DB 경고로 한정하며 Archive Center 시작과 메인 기능을 막지 않는다.

## 5. 완료된 기반

- 모델 검토는 `machine_recommended_*` pending recommendation만 만든다.
- `approved`와 `rejected`는 사용자 검토 API만 만들 수 있다.
- 기존 `critic_auto` 항목을 변경하지 않는 read-only preview가 있다.
- `canon-pack-manifest.v1`, `canon-identity-provenance-dedup.v1`,
  `canon-storage-and-migration-scope.v1`, `source-discovery-pipeline.v1` 계약이 있다.
- `POST /canon-packs/preview/v1`은 ZIP을 DB-write-free로 검증한다.
- `002_canon_pack_storage.sql` additive storage가 구현되었다.
- fresh install `001_schema.sql`과 기존 DB compatibility pass에 schema가 등록됐다.
- disposable MariaDB 11.4.12에서 신규 설치, 기존 row 보존, 재적용, FK와 CHECK를
  검증했다.
- updater v1은 schema 변경 package를 계속 거부한다. 전체 package migration은
  별도 release infrastructure 작업이며 이 로드맵에 포함하지 않는다.

이 항목들과 별도로 Local Canon Pack installer, lifecycle, overlay resolution,
logical-fact dedup, Registry, diagnostics와 bounded Source Discovery backend가 구현됐다.
실제 외부 provider와 최종 RisuAI 검색·주입 검증은 아직 남아 있다.

## 6. 수정된 구현 순서

### 단계 1. 계약 상태 정합성

- [x] storage 계약에 migration status와 live MariaDB 증거 반영
- [x] identity 계약에서 구현된 storage와 남은 runtime gap 분리
- [x] 원작 DB 로드맵에서 Host Context와 장기 기억 기능 제거
- [x] manifest, identity와 SQL column 사이의 설치 field mapping 확정

### 단계 2. Local Canon Pack 설치와 lifecycle

preview 결과를 재사용하되 install 직전에 같은 bytes와 hash를 다시 검증하여 TOCTOU를
막는다.

- [x] 동일 ZIP bytes 재검증과 archive·manifest SHA-256 기반 install 입력 계약
- [x] pack generation 단위 MariaDB transaction
- [x] pack list와 detail API
- [x] activate, deactivate, remove와 이전 generation rollback
- [x] 설치·제거 뒤 원작 전용 Chroma rebuild 또는 `pending_reindex` 상태 표시
- [x] authority 격리 회귀 테스트와 neutral fixture disposable MariaDB E2E

이 단계는 LLM 설정 없이 검증한다.

### 단계 3. Pack과 Local Overlay 결합

- [x] supplement, override, suppress와 conflict 결과 계약
- [x] pack row를 수정하지 않는 overlay write path
- [x] pack update, remove와 rollback 뒤 overlay 보존
- [ ] 같은 작품·판본의 여러 generation과 publisher 공존 정책
- [x] exact fact는 evidence union 후 한 번만 검색·주입
- [x] scope-distinct와 near-text fact는 자동 병합하지 않는 테스트

### 단계 4. 작품 검색과 로컬 Registry 조회

첫 구현은 원격 공용 Registry 운영이 아니라 설치 가능한 로컬 pack catalog다.

- [x] 제목, 원제, 번역명과 별칭 normalized lookup
- [x] work, edition과 continuity ambiguity 응답
- [x] source, version, coverage, conflict, uncertainty와 trust ViewModel
- [x] 호환되지 않거나 손상된 pack의 명시적 거부 사유

### 단계 5. Provenance와 coverage 연결

- [x] source observation, exact source bytes hash와 수집 시점 기록
- [x] fact마다 evidence locator와 pack/local/discovery origin 연결
- [x] 다중 출처, 독립성 미판정, conflict와 uncertain 진단
- [x] domain별 missing, partial, blocked와 query-relative coverage
- [x] MariaDB truth만으로 원작 전용 Chroma를 재구축하는 테스트

### 단계 6. Source Discovery 안전한 수집 기반

`source-discovery-pipeline.v1`의 text Canon core만 먼저 구현한다.

- [x] 허용 위키용 `source-profile.v1` parser strategy와 실행 코드 없는 profile 진단
- [x] DB-write-free fetch plan preview와 승인 domain policy
- [x] provider 기반 공식·라이선스·공개 출처 discovery와 access-policy gate
- [x] SSRF, redirect, MIME, size, timeout, login/cookie 제한이 있는 safe fetch
- [x] immutable response hash, 구조 section inventory와 격리 job ledger
- [x] 검색 결과, section candidate와 원문 미보존 기본값 분리

### 단계 7. 후보 추출, 중복·충돌과 종료

- [x] 근거 locator와 exact excerpt가 필수인 pending text candidate extraction
- [x] exact document/fact dedup과 provenance union
- [x] mirror, independent source, edition difference와 conflict 구분
- [x] 발견 후보를 이용한 pending dynamic query frontier 확장
- [x] 새 source·query의 의미 있는 coverage delta 기록
- [x] `insufficient_source_coverage`와 access-policy 종료
- [x] job ledger의 예외 중심 pending review payload
- [x] 근거 검증 batch admission
- [x] 승인 batch를 Source Discovery origin의 로컬 원작 DB 항목으로 생성

LLM은 구조화 추출과 후보 정리에 선택적으로 필요하다. 검색·수집·hash, 근거 저장,
중복 판정과 승인 경계는 LLM 없이 실행·검증 가능해야 한다. provider가 없으면 추출
job을 명시적으로 대기시키며 원작 DB나 메인 기능을 실패 처리하지 않는다.

### 단계 8. 실제 원작 검색·주입 검증

- [x] active 승인 Pack과 사용자 승인 overlay만 retrieval 대상이 됨
- [x] 동일 logical fact는 출처가 여러 개여도 한 번만 검색됨
- [ ] supplement mode는 현재 장면에 부족한 원작 사실만 사용함
- [ ] primary mode는 별도 Canon Base budget을 사용함
- [ ] spoiler, time, branch, edition과 knower hard filter가 유지됨
- [ ] 의미 없는 입력에는 원작 자료를 강제 주입하지 않음
- [x] 원작 DB 작업 전후 메인 chat/memory sentinel fingerprint가 유지됨

실제 RisuAI 통합 검증까지 끝나야 원작 DB 강화가 실사용 가능하다고 판정한다.

## 7. 품질 진단

단일 점수 대신 다음 결과를 따로 제공한다.

- 출처와 근거 위치 추적 가능성
- source hash와 locator 검증 상태
- 독립 출처 사이의 일치와 conflict
- exact duplicate, near duplicate와 scope-distinct 상태
- 핵심 개체, 사건과 관계의 연결 가능성
- edition과 continuity 식별 확실성
- 현재 질의에 필요한 범위 충족 여부
- 부족한 domain, 접근 불가 source와 미처리 section

## 8. 저작권과 보안

- 공용 Pack에 배포 권한 없는 원문 전체나 이를 대체할 상세 재구성을 넣지 않는다.
- 사용자 보유 원문은 로컬 비공개 자료로 취급하고 pack update와 export에서 제외한다.
- 로그인, 유료 자료, 우회 접근과 불법 공유 source를 자동 수집하지 않는다.
- session, cookie, token, 개인 채팅과 secret을 discovery job에 포함하지 않는다.
- 외부 문서의 지시문은 데이터이며 backend 제어 명령으로 실행하지 않는다.
- source license와 access 상태가 불명확하면 승인 자료로 승격하지 않는다.

## 9. 완료 판정

3.1 완료는 local Canon Pack 검증, 설치, 조회, 비활성화, 제거, rollback, overlay
보존과 중복 없는 검색을 neutral fixture와 disposable MariaDB에서 증명한 때다.

3.2 완료는 허용된 source discovery, safe snapshot, evidence candidate,
reconciliation, coverage 종료, 예외 검토, pack candidate 생성과 실제 원작
검색·주입을 검증한 때다.

문서, schema, preview 또는 mock test만으로 실사용 완료라 부르지 않는다.

## 10. 보류하거나 구현하지 않을 범위

- 모든 작품을 자동 완성한다는 보장
- 고정 인물·세력·문서 수 또는 고정 품질 점수
- 특정 작품이나 source site의 Go code 하드코딩
- 모델이 conflict의 승자를 자동 선택하는 기능
- public Registry 운영, publisher governance와 원격 서명 신뢰 체계
- updater v2 migration과 자동 rollback
- text Canon core 검증 전 image 분석 확장
- community 자료를 Canon 승인 근거로 자동 사용하는 기능
- Risu Host Context, 로어북, 장기 기억 무결성과 서사 교정

보류 항목은 별도 요구와 설계 승인이 있을 때 새로운 로드맵에서 다룬다.

## 12. 원작 DB 구현 기록

이 절은 이전 혼합 로드맵에서 원작 DB에 해당하는 완료 기록만 보존한다.

### 12.1 모델 자동 승인 차단

상태: 완료, 2026-07-18

- reference 추출의 기본 `auto_review`를 끄고 adapter 요청도 `false`를 명시했다.
- critic 결과는 `machine_recommended_*`인 pending recommendation으로만 기록한다.
- recommendation 직후 vector index를 만들지 않으며 사용자 검토 API만 승인 상태를
  만들 수 있다.
- production route 테스트와 `go test ./internal/httpapi -count=1`, JavaScript syntax
  검사를 통과했다.

관련 runtime은 `Archive Center.js`,
`go-service/internal/httpapi/group_reference_library.go`와 같은 package 테스트다.

### 12.2 기존 `critic_auto` read-only preview

상태: 완료, 2026-07-18  
계약: `reference_legacy_auto_review_preview.v1`

- 기존 `critic_auto` 항목만 진단하고 상태나 Chroma를 변경하지 않는다.
- review 분포와 `grounded`, `present_unverified`, `missing` 근거 상태를 표시한다.
- preview 전후 review와 audit mutation이 없음을 production route 테스트로 확인했다.

### 12.3 Canon Pack과 identity 계약

상태: 문서 계약 완료, importer/lifecycle 구현은 12.7 참조

- `docs/canon-pack-manifest-v1.md`
- `docs/canon-pack-manifest-v1.schema.json`
- `docs/canon-pack-manifest-v1.example.json`
- `docs/canon-identity-provenance-dedup-v1.md`

작품·판본 식별, provenance, exact hash, fact identity, evidence union, conflict와 Local
Overlay의 계약을 확정했다. importer는 구현됐지만 fact identity resolver와 overlay는
아직 없으므로 전체 실사용 완료가 아니다.

### 12.4 Canon Pack DB-write-free preview

상태: production API와 집중 테스트 완료, install은 12.7 참조  
API: `POST /canon-packs/preview/v1`

- ZIP path traversal, manifest/schema 불일치, 누락·추가 payload와 checksum 오류를
  거부한다.
- preview는 DB, reference item, filesystem과 main memory를 변경하지 않는다.
- unsigned local pack만 preview할 수 있으며 임의의 publisher trust를 부여하지 않는다.

관련 구현은 `go-service/internal/canonpack`과
`go-service/internal/httpapi/group_canon_pack_preview.go`에 있다.

### 12.5 Additive Canon storage와 live gate

상태: local disposable MariaDB 11.4.12 gate 통과, 원격 GitHub Actions 미실행

- `migrations/002_canon_pack_storage.sql`에 승인된 관계·lifecycle table을 추가했다.
- 같은 schema를 fresh install `001_schema.sql`과 `mariadb-schema` compatibility pass에
  등록했다.

### 12.7 Local Canon Pack 설치와 lifecycle

상태: Go backend 구현 및 local disposable MariaDB 11.4.10 검증 완료, 2026-07-18  
계약: `canon_pack_lifecycle.v1`

- `POST /canon-packs/install/v1`은 preview와 별개로 전달된 동일 ZIP bytes를 다시
  검증하고 archive SHA-256과 manifest SHA-256을 설치 기록에 결합한다.
- 설치는 MariaDB authority mode에서만 허용한다. shadow, fixture와 noop store는
  durable install을 주장할 수 없다.
- 승인된 manifest의 작품·판본·제목·출처 observation·근거 locator와 승인 content를
  한 transaction에서 설치한다. 원문 전체는 저장하지 않고 source metadata와 hash만
  저장한다.
- `GET /canon-packs/v1`, `GET /canon-packs/{install_id}/v1`과 lifecycle action
  `activate`, `deactivate`, `remove`, `rollback`을 추가했다.
- pack-owned reference row는 origin membership으로 install generation에 연결한다.
  승인 검색은 active generation의 row만 반환하고 legacy/local 승인 row는 유지한다.
- 동일 manifest item이 여러 continuity에 속할 때 origin ID가 충돌하지 않도록 실제
  target ID를 identity에 포함한다.
- RFC3339 `retrieved_at`은 MariaDB `DATETIME`에 쓰기 전에 backend에서 파싱한다.
  이 오류는 disposable MariaDB E2E에서 발견하고 수정했다.

설치 field mapping은 다음과 같다.

| Manifest field | MariaDB owner |
| --- | --- |
| `pack`, pack-level `review`, `trust`, `coverage_report` | `canon_pack_installs` |
| `work.stable_id`, `work.edition` | `reference_work_editions`와 기존 `reference_works` |
| original, translated, alias titles | `reference_work_titles` |
| `sources[]`와 document hash | `reference_source_observations`, metadata-only `reference_documents` |
| entities, locations, factions, settings | `reference_entities` |
| events | `reference_timeline_nodes` |
| relations와 claims | `reference_claims` |
| record evidence locator | `reference_item_evidence` |
| pack generation membership | `reference_item_origins` |

12.7 구현 시점에는 `conflicts`, `uncertainties`, logical fact identity, overlay resolver와
Chroma lifecycle 연결이 포함되지 않았다. 이 후속 구현과 검증은 12.8에 기록한다.

검증 증거:

- `go test ./internal/canonpack ./internal/store ./internal/httpapi -count=1`

### 12.8 원작 DB 강화 1~6 통합 구현

상태: backend 구현 및 local disposable MariaDB 검증 완료, 독립 실사용 검증 대기, 2026-07-18

- lifecycle 뒤 runtime embedding 설정이 있으면 원작 전용 Chroma를 재구축한다. 설정이나
  Chroma가 없으면 pack/overlay transaction은 성공하고 `pending_reindex`를 반환한다.
- `canon_fact_exact.v1` fingerprint와 logical fact를 설치 transaction에서 생성한다.
  작품·판본·continuity·적용 범위와 정규화 문장이 같은 fact는 claim row를 추가하지 않고
  origin과 evidence만 결합한다. punctuation, edition 또는 continuity가 다르면 병합하지
  않는다.
- `reference_overlay_rules`를 쓰는 Local Overlay API를 추가했다. 기존 사용자 승인
  reference item을 replacement로 사용할 수 있으며 공용 pack row는 수정하지 않는다.
- `GET /canon-registry/v1`은 원제·번역명·별칭 title row로 설치 pack을 찾고 work,
  edition, continuity, version, trust, coverage와 ambiguity를 반환한다.
- pack diagnostics는 source observation, document hash, evidence-bound item, 다중 출처,
  conflict, uncertainty, entity 연결성과 coverage를 단일 점수 없이 각각 반환한다.
  mirror/repost가 분류되지 않은 다중 출처는 독립 출처 일치로 승격하지 않고
  `unassessed`로 표시한다.
- `POST /source-discovery/preview/v1`은 DB-write-free fetch plan을 만든다.
  `POST /source-discovery/jobs/v1`은 versioned search provider 결과를 승인 domain
  policy와 대조하고, public HTTP(S) safe fetch, exact response hash, 구조 section,
  pending evidence candidate, dynamic query frontier와 coverage 종료를 격리 ledger에
  저장한다.
- Source Discovery search provider key와 LLM client metadata는 job JSON에 저장하지
  않는다. 원문 bytes 기본 retention은 `none`이고 bounded excerpt만 pending candidate로
  남는다.
- 모델 candidate는 실제 source URL, locator와 exact excerpt가 일치할 때만 staging에
  남으며 항상 `pending`, `admission_eligible=false`다.
- `source_discovery_jobs`는 reference·session·memory 테이블과 FK가 없는 additive
  staging table이다.

API:

- `GET /canon-registry/v1`
- `GET /canon-packs/{install_id}/diagnostics/v1`
- `POST|GET /canon-overlays/v1`
- `POST /source-discovery/preview/v1`
- `POST /source-discovery/jobs/v1`
- `GET /source-discovery/jobs/{job_id}/v1`

Source Discovery job의 외부 처리 구간은 요청당 90초로 제한한다. 검색 provider 응답은
1 MiB를 초과하면 거부하고, 개별 원문 응답은 2 MiB를 초과하면 거부한다. 이 제한은
자료 개수로 coverage 완료를 판정하는 기준이 아니라 단일 요청의 자원·보안 경계다.

검증:

- 같은 fact를 포함한 두 pack generation 설치 뒤 claim 1개, logical fact identity 1개,
  evidence 2개를 실제 MariaDB에서 확인했다.
- deactivate, remove, rollback과 suppress overlay가 승인 reference 검색에 반영됨을
  확인했다.
- Registry, diagnostics와 insufficient-coverage discovery ledger를 실제 MariaDB에서
  확인했다.
- 원작 작업 전후 `chat_logs`와 `memories` sentinel의 row count와 content hash가
  동일함을 확인했다.
- private/loopback/metadata URL, URL credential과 secret query 거부, HTML 구조 추출,
  근거 없는 모델 candidate 거부를 production 함수 테스트로 확인했다.

아직 완료로 표시하지 않는 범위는 전체 `source-profile.v1` parser profile, mirror와
repost 독립성 분류, round별 coverage delta, 자동 batch admission, pack candidate 생성,
실제 외부 search provider와 실제 RisuAI 원작 주입 E2E다.

### 12.32 보존 원문 통합 자동 분석

- 115개 원문을 사용자가 몇 개씩 반복 실행하는 흐름을 폐기했다. `부족한 자료 자동 보완`을 한 번 실행하면 Go 백엔드의 `source_discovery_corpus_analysis` 작업이 저장된 통합 section 대기열을 계속 처리한다.

- 후보는 계속 `pending`으로만 저장하며 자동 승인하지 않는다. 메인 장기 기억의 저장·검색·삭제·예산·주입 경로는 변경하지 않았다.

### 12.31 보존 원문별 평론가 정밀 분석

상태: 2026-07-19 Build 31 구현 및 자동 테스트 완료

- `원문 문서`의 각 행 오른쪽에 독립적인 `평론가 정밀 분석` 버튼을 둔다. 분석 이력이 있는 문서는 `평론가 다시 분석`으로 표시한다. 각 버튼은 해당 행의 `document_id`만 백엔드에 전달하므로 다른 원문을 한꺼번에 호출하지 않는다.

- 평론가 호출은 새 검색이나 재수집을 수행하지 않는다. 로컬 DB에 `raw_retention=full`로 보존된 원문을 다시 읽으며, 공통 평론가 LLM 설정을 그대로 사용한다.

  불필요한 discovery job을 DB에 남기지 않는다. 공통 검색 API 설정과 실제 backend 연결은
  12.11에 기록한다.
- 후보는 계속 `pending`으로 격리 저장되며 승인된 원작 검색이나 장기 기억에는 들어가지
  않는다.
- 결과 화면에서는 job state와 termination code 같은 backend 내부 값을 제거하고 후보 수와
  검토 대기 상태만 표시한다. 작품명 입력의 Enter 실행도 버튼과 같은 요청 경로를 사용한다.

### 12.11 운영체제 독립 외부 검색 API 연결

상태: 구현 후 사용자 설정 부담 때문에 12.13에서 제거, 2026-07-18

- 감독관 LLM 설정 화면과 같은 입력 패턴으로 `원작 자료 검색 API` 설정을 추가했다.
  Provider, API Key, Endpoint, Timeout을 저장하며 Windows와 Linux 모두 Go backend가 동일한
  외부 HTTPS API를 호출한다.
- 지원 provider는 Brave Search, Tavily와 기존 `source-search-request.v1` custom endpoint다.
  Brave/Tavily endpoint는 비워두면 공식 기본 endpoint를 사용한다.
- Brave/Tavily는 첫 실사용 단계에서 작품 identity 검색 1회만 호출한다. 화면의 단일 실행이
  탐색 영역 수만큼 숨은 과금 호출을 만들지 않게 한 운영 제한이며, coverage saturation을 위한
  후속 질의 반복 실행은 비용·중단 조건 UI가 마련되기 전까지 아직 구현하지 않는다.
- 검색 API는 LLM이 아니므로 model, temperature, reasoning preset·effort·budget을 받거나
  전송하지 않는다. 검색어 계획 LLM 설정은 별도 계약으로 분리한다.
- `/config/update` runtime 설정에 `sourceSearchProvider`, `sourceSearchApiKey`,
  `sourceSearchEndpoint`, `sourceSearchTimeout`을 추가했다. API key는 runtime trace, job JSON,
  provider diagnostics에 반환하지 않는다.
- 작품명만 입력한 자료 찾기는 쓰기 없는 preview에서 runtime provider 구성을 확인한 뒤,

  검색된 공개 URL의 SSRF·redirect·size·MIME 검증과 페이지 수집은 기존 Go access gate가
  담당한다.
- 검색 결과는 사용자가 고른 단일 출처 범위의 pending acquisition으로만 분류한다. 두 개
  이상의 출처 유형이 동시에 요청됐는데 domain 정책이 없으면 임의 분류하지 않고 거부한다.

### 12.12 검색 계획 LLM 분리

상태: 구현 후 별도 검색 API와의 이중 설정 문제 때문에 12.13의 단일 검색 LLM으로 통합,
2026-07-18

- 외부 검색 API 앞에 독립적인 `검색 계획 LLM`을 두었다. 이 LLM은 작품명과 허용 출처
  범위로 최초 검색어 한 개만 생성하며, 답변·원작 사실·별칭·URL을 생성하거나 승인하지
  않는다.
- 설정 UI는 Provider, API Key, Endpoint, Model, Timeout, Temperature, Reasoning Preset,
  Reasoning Effort, Reasoning Budget과 Max Completion Tokens를 제공한다. 기본값은
  temperature `0.1`, reasoning effort `none`, max completion tokens `512`다.
- `none`은 Archive Center가 provider reasoning effort/budget을 활성화하지 않는다는 뜻이다.
  모델 자체가 내부 추론을 강제하는 경우까지 비활성화할 수 있는지는 provider와 모델
  계약에 따른다.
- 계획 LLM이 미설정이거나 호출·JSON 파싱에 실패하면 `<작품명> identity` 검색어로
  결정적으로 복귀한다. 이 실패는 Source Discovery와 기존 Canon Pack 검색, ready,
  장기 기억 저장·검색·주입을 막지 않는다.
- 계획 결과는 외부 검색 API의 query로만 전달된다. 검색 결과 URL은 기존 public HTTPS와
  SSRF 검증을 통과해야 하고, 페이지에서 추출한 후보도 계속 `pending`,
  `admission_eligible=false`로 격리된다.
- `/config/update`에 `sourceSearchPlanner*` runtime 필드를 추가했으며 API key는 runtime
  trace나 job 결과에 노출하지 않는다.

검증:

- 미설정 시 결정적 fallback 검색어를 production planner 함수로 확인했다.
- OpenAI-compatible fixture를 production proxy 경로로 호출해 temperature `0.1` 전달과
  reasoning effort `none`일 때 OpenAI reasoning 필드 비전송을 확인했다.
- 외부 검색 API UI와 계획 LLM UI가 분리되어 검색 API 패널에 LLM 옵션이 나타나지 않는
  것을 JS smoke test로 확인한다.

### 12.13 별도 검색 API 제거와 네이티브 검색 LLM 통합

상태: backend·RisuAI UI·fixture 회귀 구현, 실제 provider live 검증 대기, 2026-07-18

- 사용자가 LLM API와 별도로 Brave/Tavily API key까지 발급·관리해야 하는 구조는 자료
  확보 부담 제거 목표와 충돌하므로 제거했다. `원작 자료 검색 API`와 `검색 계획 LLM`
  두 설정 화면을 하나의 `원작 자료 검색 LLM`으로 통합했다.
- 지원 provider는 공식 네이티브 웹 검색과 구조화 citation 계약을 확인한 OpenAI,
  Gemini와 Claude다. OpenRouter, Ollama, Copilot과 일반 Custom endpoint는 평범한 채팅
  호출이 된다는 이유만으로 웹 검색 지원으로 표시하지 않는다.
- OpenAI는 Responses API의 `web_search`, Gemini는 `googleSearch` grounding, Claude는
  Messages API의 `web_search_20250305` server tool을 사용한다. 별도 Brave/Tavily runtime
  key와 endpoint 계약은 제거했다.
- 모델의 일반 답변에 나타난 URL 문자열은 수집하지 않는다. OpenAI search action과
  URL citation, Gemini grounding chunk, Claude web search result와 citation에 들어 있는
  구조화 URL만 source candidate로 받는다.
- 구조화 URL도 곧바로 fact가 되지 않는다. 기존 public URL access gate로 다시 fetch하고
  exact hash·locator·excerpt가 연결된 candidate만 `pending`으로 저장한다.
- 검색 LLM이 없거나 선택한 provider가 네이티브 웹 검색 계약을 지원하지 않으면 작품명
  자동 검색을 실행하지 않는다. 사용자가 제공한 공개 URL 수집은 계속 독립적으로 동작한다.
- 이번 변경은 Source Discovery와 설정 UI에만 한정하며 장기 기억 저장·검색·주입 경로를
  변경하지 않는다.

### 12.15 검색 LLM 설정 이동과 작품 lifecycle 관리

상태: backend·RisuAI adapter·회귀 테스트 구현, 실제 RisuAI 화면 검토 대기,
2026-07-18

  `검색 설정` 작업 탭으로 이동했다. Provider, API Key, Endpoint, Model, Timeout,
  Temperature, Reasoning Preset·Effort·Budget과 Max Completion Tokens 계약은 유지한다.
- 검색 설정은 해당 탭의 전용 저장 버튼으로만 저장한다. 일반 설정 저장 버튼은 더 이상
  원작 검색 LLM DOM을 참조하지 않으므로 두 화면의 생명주기가 서로 얽히지 않는다.
- 생성된 작품을 선택하면 제목과 작품 유형을 수정하거나 작품 공간을 삭제할 수 있다.
  수정은 현재 `revision`을 요구하는 optimistic concurrency 계약을 사용해 다른 화면의
  변경을 조용히 덮어쓰지 않는다. 내부에 보존된 언어 값은 사용자에게 다시 요구하지 않고
  그대로 유지한다.
- 작품 삭제는 명시적 확인 뒤 backend `DELETE /reference-works/{work_id}`를 호출한다.
  현재 세션 연결이 있으면 `reference_work_in_use`, 설치된 Canon Pack이나 local overlay가
  참조하면 `reference_conflict`로 거부한다. UI가 연결이나 팩을 자동 제거하지 않는다.
- 삭제 성공 시 해당 작품의 원작 자료 상태만 화면에서 비운다. 장기 기억 DB, 채팅 기록,
  다른 작품, 사용자 개인 데이터는 삭제하거나 수정하지 않는다.
- 이 bounded UI slice의 `Archive Center.js` 증감은 직전 `3.2-canon-pack-ui.20260718-6`
  작업 상태 대비 `+47/-3`이다. 추가된 JavaScript는 DOM 렌더링, 사용자 확인·입력 수집과
  backend transport에 한정하며 revision·삭제 허용 정책은 Go backend가 소유한다.
- 후속 실사용 확인에서 검색 LLM의 Max Completion Tokens가 UI·설정 정규화·backend 동기화
  경계에서 `1024`로 잘리는 문제를 확인했다. 감독관·평론가와 같은 `1..128000` 계약으로
  세 경계를 통일했으며 기본값 `512`는 유지한다. 따라서 사용자가 지정한 `5000`도 저장되어
  Source Discovery runtime 설정으로 전달된다. 수정 빌드는
  `3.2-canon-pack-ui.20260718-8`이다.
- 검색 설정 내부의 전용 저장 버튼은 하단 전체 저장 버튼과 중복되어 제거했다. 전체 저장은
  검색 설정 화면이 열려 있을 때 `sourceSearchPlanner*` 입력을 읽고, 다른 작업 화면에서는
  기존 저장값을 보존한다.
- `현재 세션 연결`에서는 작품·이야기 흐름 선택기와 작품 수정·삭제 버튼을 반복 표시하지
  않는다. 앞선 원작 자료 화면에서 선택한 상태를 그대로 사용하고 `선택한 원작 DB` 이름만
  읽기 전용으로 표시한다.
- 작품 삭제 실패 안내는 backend transport 상태를 구분한다. `404/405`는 삭제 API가 없는
  이전 backend 패키지, `0`은 backend 연결 실패, `409`는 실제 세션·overlay·Canon Pack

  CASCADE` 대상이므로 그 자체를 의존성 충돌로 오인하지 않는다. 수정 빌드는
  `3.2-canon-pack-ui.20260718-9`이다.

### 12.20 후보 추출의 공통 평론가 설정 소유권 복구

상태: backend 구현 및 회귀 테스트 완료, 사용자 Ollama Cloud 실호출 재검증 대기

  때만 fallback으로 사용하던 잘못을 확인했다.
- 검색 에이전트는 URL 탐색만 담당한다. 수집된 본문의 인물·장소·사건·관계 후보 추출은

### 12.28 자동 수집 원문 보존과 원작 내부 정보 정리

- 동일 본문 SHA-256은 작품·이야기 흐름 안에서 한 문서로 저장하고, 서로 다른 원본·미러

### 12.29 Source Discovery 사용량 제어와 이어 분석

### 12.42 3.2 원작 DB 보조 범위 종료

상태: 2026-07-20 Build 41 기준 범위 종료

- 3.2의 원작 DB 보조 작업은 Build 41 상태에서 종료한다. 추가 Source Discovery 추출 튜닝, 원작 주입 E2E 확장, Canon Pack lifecycle 실사용 확장은 후속 필수 작업으로 잡지 않는다.
- 현재 구현은 원문 수집·로컬 보존, 근거 후보 생성, 중복·충돌 진단, 원문별 및 통합 분석, 원문 머리글 표시와 승인 자료의 독립 검색·주입 경계를 제공한다.
- 대규모 작품에서 자동 생성되는 개체의 양과 정밀도가 충분하지 않을 수 있다는 한계는 남아 있다. 이를 완전한 자동 원작 DB 구축으로 표시하지 않고 보조 기능으로만 취급한다.
- 일반 모드에서 원작 DB는 메인 장기 기억보다 우선하지 않는다. 명시적인 단독 모드가 아닌 경우 승인된 원작 자료도 현재 장면을 보완하는 별도 라인으로만 사용한다.
- pending, uncertain, 근거 없는 모델 생성 정보는 원작 사실로 자동 승격하거나 검색·주입하지 않는다. 원작 DB 오류와 자료 부족은 Archive Center 시작, ready, 채팅, 메인 장기 기억 저장·검색·삭제를 막지 않아야 한다.
- 이후 작업은 원작 DB 보조 기능을 더 확장하지 않고 별도 로드맵으로 이동한다.
