## 3. 3.5 이후 운영·배포 보완 이력

### 3.5 Windows 관리형 설치

- `9f28088`에서 Windows 패키지가 MariaDB와 ChromaDB 실행물을 ZIP에 동봉하지 않고,
  첫 실행 때 별도 사용자 runtime 경로에 설치하는 구조로 전환됐다.

  오인하던 경로를 수정했다.
- 현재 Windows full-local 설치는 다음 순서를 사용한다.
  1. 공식 MariaDB ZIP을 내려받고 SHA-256 검증
  2. 공식 CPython 설치 파일을 내려받고 SHA-256·Authenticode 검증
  3. 별도 virtual environment에 고정 버전 ChromaDB 설치
  4. `import chromadb`와 설치 버전 확인 뒤 실행
- `.env`, 사용자 MariaDB, Chroma persist data, API key, log와 cache는 패키지에 포함하지
  않는다.

### 3.6 Windows 표준 실행 프로필 교정

## 4. 3.6-B 구현 상세

### 4.1 새 저장 계약

fresh schema와 기존 DB용 additive migration에 다음 테이블을 추가했다.

| 테이블 | 책임 |
|---|---|
| `entity_identities` | 이름과 분리된 source-bound stable ID, namespace, kind, lifecycle, review, source revision |
| `entity_identity_surfaces` | 표시 이름·별명과 정확한 원문 위치·유효 turn·review 상태 |
| `entity_identity_links` | 추후 승인된 alias/split/merge/cross-namespace link; 자동 merge 용도가 아님 |
| `entity_identity_artifact_bindings` | 기존 entity/KG/character-state projection의 발생 위치를 stable ID에 병렬 연결 |
| `speaker_attributions` | Host role과 in-world speaker를 분리한 원문 span·confidence·review 상태 |

마이그레이션은 기존 row 삭제·reset·renumbering·이름 기반 backfill을 하지 않는다.
표시 이름과 `normalized_surface`에는 unique identity 제약을 두지 않았다.

### 4.2 stable ID 생성과 idempotency

- ID 입력은 `session + source revision + namespace + entity kind + source bucket + 원문 span`이다.
- 원문 span이 없는 legacy/unverified 후보만 artifact index를 보조 위치로 사용하며
  `needs_review`로 남긴다.
- 이름 문자열은 ID 입력으로 사용하지 않는다.
- 같은 원문 revision을 같은 위치에서 재처리하면 같은 ID와 idempotency key를 사용한다.
- 같은 이름이 두 번 나타나면 원문 byte span이 다르므로 다른 stable ID가 된다.
- Critic이 같은 원문의 entity 배열 순서를 바꾸어 반환해도 원문 위치가 같으면 ID가
  바뀌지 않는다.
- 과거/rescan/import처럼 Host source acceptance가 없는 경로는
  `legacy_unverified` source contract로 기록한다. Host-native source로 위장하지 않는다.
- active-final complete-turn은 3.3의 `source_acceptance_observation.v1` revision과
  logical turn/message/generation 관찰을 identity source context로 전달한다.

### 4.3 자동 병합 금지

- `canonicalCharacterName`의 편집거리 2 이하 fuzzy 선택을 제거했다.
- 기존에 `Marina`가 있어도 새 `Marino`를 `Marina`로 바꾸지 않는다.
- 기존 character state와 이름을 맞출 때는 공백·문장부호를 정규화한 전체 표시 이름이
  정확히 같은 경우만 재사용한다. 성·이름 suffix, 로마자 유사 표기, 등장 빈도와 배열
  순서는 병합 권한이 아니다.
- Critic의 `character_identity_accuracy`가 만드는 기존 name projection은 호환 목적으로
  남아 있다. 명시적 `same_entity=true`이고 같은 별칭이 서로 다른 canonical target을
  가리키지 않을 때만 그 기존 projection 안에서 사용할 수 있으며 stable ID를 자동
  merge하는 권한은 갖지 않는다.
- 같은 source turn에서 동일한 전체 이름이 여러 번 나오면 원문 span별 stable occurrence를
  분리하고, 그 표면으로 KG·상태를 연결할 때는 어느 한쪽을 선택하지 않고
  `session_unknown/needs_review`로 보존한다.
- entity가 제공한 별칭은 원문 span이 있더라도 동일인 확정 근거로 승격하지 않는다.
  표면과 근거 위치는 보존하되 `needs_review`이며, KG·상태·화자는 전체 이름 또는 별도의
  명시적 동일인 근거가 없으면 `session_unknown`으로 연결한다.
- 둘 이상의 entity가 공유하는 별칭은 owner별 source span을 임의 배분하지 않는다.
  extraction 배열 순서가 바뀌어도 같은 surface ID와 review 결과를 유지한다.
- 짧은 표면이 긴 전체 이름 안에 포함된 경우 독립 mention으로 세지 않는다. 화자 excerpt가
  긴 이름의 앞부분을 잘라 제출된 경우에도 합본 원문의 절대 byte span으로 다시 검사한다.
- session, Host setting, reference, user/OOC와 unknown namespace는 서로 다른 ID로
  저장한다.
- Host/reference namespace에 나온 이름은 session presence를 자동 획득하지 않고
  `unverified/needs_review`로 남는다.

이 판정은 현재 accepted source turn 안의 occurrence 안전장치다. 과거 turn의 occurrence를
읽어 session 전체 canonical root를 선택하거나 split/merge하는 reader·운영 API는 아직
구현하지 않았다.

### 4.4 기존 entity·KG·state 연결

- legacy `entities`, `kg_triples`, `character_states`를 즉시 삭제하거나 스키마 전체를
  재작성하지 않았다.
- 같은 source extraction 안에서 표면이 하나의 source-observed identity에만 대응할 때
  `entity_identity_artifact_bindings`에 stable pointer를 저장한다.
- 동명이인 때문에 후보가 여러 개면 해당 KG endpoint는 별도의 unknown occurrence에
  `needs_review`로 연결한다.
- KG의 일반 문자열 object처럼 현재 entity 후보가 전혀 없는 값은 억지로 identity로
  만들지 않는다.
- character delta만 존재하고 이름이 원문에 정확히 있으면 해당 source turn의 character
  identity occurrence를 새로 만들 수 있다.
- character delta의 이름이 원문에 없으면 identity와 binding 모두 `needs_review`이며,
  정상 근거로 승격하지 않는다.

### 4.5 speaker attribution

- Critic 출력 계약에 선택적 `speaker_attributions`를 추가했다.
- evidence excerpt가 현재 user/assistant 합본 원문에 정확히 존재할 때만 저장한다.
- 복수 화자 후보, unknown/tentative/ambiguous 표시, 또는 이름이 excerpt에서 직접
  확인되지 않는 경우 known character로 승격하지 않는다.
- 짧은 화자 표기가 다른 인물의 긴 전체 이름 안에 포함된 것뿐이면 직접 확인으로 보지
  않는다. excerpt가 긴 이름의 일부만 잘라낸 경우에도 원문 절대 span에서 중첩을 검사한다.
- 이 경우 source-bound unknown identity, `tentative|unknown`,
  `needs_review`, 정확한 byte span과 원문 excerpt를 보존한다.
- 같은 excerpt가 원문에 반복되면 각 attribution은 첫 문장에 겹쳐 쓰이지 않고 등장
  순서대로 서로 다른 byte span을 사용한다.

### 4.6 삭제·리롤·초기화

새 identity row가 삭제된 턴 뒤에 잔존하지 않도록 다음 MariaDB 경로에 FK 순서 삭제를
연결했다.

- turn rollback의 `DeleteEntities`
- canonical tail `ReplaceLogicalTurn`
- session 전체 삭제
- admin 전체 reset

source revision별 invalidation graph와 Chroma outbox 재생은 3.6-D 범위이므로 이번
packet에서 별도 fallback worker를 만들지 않았다.

### 4.7 HUD

추가했다. identity 판단이나 count 계산을 JavaScript에 넣지 않았다.

### 4.8 저장 모드 경계

- `mariadb_authority`는 identity extension을 권위 저장소에 직접 쓴다.
- `mariadb_shadow`는 MariaDB shadow lane에 쓰되, shadow 장애가 기존 주 저장 경로를
  실패시키지 않고 shadow failure ledger에 기록되도록 기존 dual-write 의미를 유지한다.
- `dual_shadow`의 양쪽 lane이 모두 no-op이면 identity 저장을 지원하는 것처럼 광고하지
  않으며 오류·저장 개수도 만들지 않는다.
- `mariadb_read_shadow`의 read-only wrapper는 선택적 identity writer를 구현하지 않으므로
  파생물 저장을 시도하지 않는다.

## 5. 3.6-C 구현 상세

### 5.1 원자 기억 저장 계약

기존 `memories`의 한 턴 aggregate row는 이번 작업에서 삭제하거나 대체하지 않았다. 대신
`precise_memory_units`를 additive projection으로 추가해 Critic이 이미 반환하는 자료를 다음
네 종류의 독립 row로 분리한다.

| kind | 입력 제안 | 저장 의미 |
|---|---|---|
| `event` | `narrative_events` | 실제 발생했다고 제안된 한 사건 |
| `state` | `state_claims` | 한 subject의 한 current state 주장 |
| `utterance` | `speaker_attributions` | 발언·생각·서술이 원문에 나타난 occurrence; 발언 내용의 진실과는 분리 |
| `observation` | `belief_updates` | 특정 인물이 믿거나 알고·의심·오해하는 owner-scoped 인식 |

각 row는 `precise_memory_unit.v1`, session·turn, active source revision·logical turn,
generation/content hash, 합본 원문의 exact byte span·excerpt, Direct Evidence ID, kind/subtype,
payload, entity pointer, truth/epistemic/authority, admission/review/visibility, confidence,
idempotency key와 lifecycle을 저장한다. 사용자 입력과 Assistant 출력이 하나의 문자열로
조립된 현재 경계는 `combined_turn_pair`로 기록하며, 모든 excerpt가 Assistant message에서
왔다고 잘못 표시하지 않는다.

### 5.2 source·근거 admission

- 3.3의 accepted current source context가 없으면 precise row를 쓰지 않는다.
- excerpt가 현재 합본 원문에 정확히 없거나 같은 excerpt가 여러 번 나와 위치를 하나로
  증명할 수 없으면 fail-closed한다. Critic이 유효한 exact span을 제공한 경우에만 그 위치를
  사용할 수 있다.
- 같은 턴의 `verified_direct` Direct Evidence ID가 없거나 stale·repair·tombstone·supersede
  상태면 쓰지 않는다.
- admission은 Direct Evidence 저장 뒤, 기존 narrative current-state 저장 전에 실행한다.
- idempotency key는 extraction 배열 index가 아니라 source revision, kind, exact span,
  정규화된 semantic payload와 role surface로 만든다. 같은 source의 재처리와 배열 순서
  변경은 row를 늘리지 않는다.

### 5.3 truth·authority 경계

- exact accepted source는 그 문구가 표시됐다는 occurrence를 증명할 뿐, 내용 전체를 객관
  세계 진실로 만들지 않는다.
- objective state/event만 `objective_world_state`를 받을 수 있다.
- `belief_updates`는 `subjective_episodic`, owner-scoped, 기본 `owner_private` observation이다.
- proposal·plan은 `support_hypothesis/proposed`, 추측·불확실성은
  `support_hypothesis/non_objective`, lie·deception은
  `subjective_episodic/speaker_claim`, OOC는 `ooc_meta`로 분리한다.
- 낮은 confidence의 objective 후보와 unresolved identity가 있는 objective 후보는
  `review_required/needs_review`로 낮추고 objective authority를 제거한다.
- world/session subject는 인물 ID가 없어도 exact 근거와 구조화된 scope를 통과하면 객관
  state가 될 수 있다.

### 5.4 identity 오염 차단

3.6-B의 same-turn source-observed identity가 정확히 하나이고 해당 surface가 unit의 exact
excerpt 안에 독립적으로 나타날 때만 actor·subject·affected·location·object·knower pointer를
저장한다.

- 공유 별칭, alias-only 표기, 동명이인, 일반명사 충돌, 근거 없는 이름과 복수 후보는 stable
  pointer를 얻지 못한다.
- actor·subject·speaker·knower가 unresolved이면 어느 후보도 선택하지 않고 review 상태로
  보존한다.
- event의 `participants`도 전부 unique하게 해소돼야 objective admission을 유지한다.
  성공하면 stable participant ID 목록을 deterministic payload에 기록하고, 하나라도
  모호하면 ID 목록을 만들지 않는다.
- 출력용 이름에 작품명·직책·내부 ID를 합성하지 않는다.

### 5.5 MariaDB·삭제·HUD

- fresh schema, `004_precise_memory_units.sql` additive migration,
  `mariadb-schema` compatibility pass를 같은 계약으로 맞췄다. `004`는 migration 실행 순서일
  뿐 roadmap packet 이름이 아니다.
- `mariadb_authority`와 실제 writer가 있는 dual-write lane만 precise write를 지원한다.
  no-op·read-only·비활성 writer는 지원한다고 광고하지 않는다.
- shadow-only 장애는 기존 migration shadow 의미처럼 failure ledger에 기록하되 주 경로
  오류로 위장하지 않고, 저장 수는 0으로 유지한다.
- rollback, canonical logical-turn replacement, session delete와 admin reset에서 precise
  row를 evidence·identity FK보다 먼저 제거한다.
- complete-turn 응답·persistence pipeline·derived total과 Go HUD ViewModel에
  `precise_memory_units_saved`/`정밀 기억` 수를 추가했다. JavaScript는 한국어·영어·일본어
  표시명만 가진다.

### 5.6 3.6-C에서 의도적으로 남긴 호환 경계

3.6-C packet은 source admission 기반까지만 구현했으며, 당시 다음 항목을 완료로 표시하지
않았다.

- 기존 aggregate `memories` writer 제거와 모든 producer의 공통 transaction cutover
- source edit/correction 이후 dependency graph·outbox·reprocess
- cross-turn canonical identity root와 reviewed split/merge
- precise row의 vector/index/recall 및 최종 주입
- 기존 사용자 DB의 clone migration·dry-run·rollback과 live RisuAI 검증

앞의 두 항목은 각각 3.6-E와 3.6-D, identity 운영과 기존 DB 전환은 3.6-E 이후, recall은
4.0, 실환경 누적 gate는 4.1의 책임이다.

## 6. 3.6-D 구현 상세

### 6.1 source revision과 동시성 fence

- `memory_source_revision.v1`은 accepted user/assistant 원문 쌍, logical turn, Host message와
  generation 관찰값, content hash, lifecycle을 MariaDB에 보존한다.
- RisuAI가 branch ID를 노출하지 않는 현재 complete-turn 계약에서는 branch를 추정하지 않고
  `branch_state=not_exposed`로 저장한다.
- active logical turn은 generated slot과
  `UNIQUE(chat_session_id, active_logical_turn_slot)`로 DB에서도 하나만 허용한다.
  애플리케이션의 `SELECT ... FOR UPDATE`만 믿지 않으며 동시 insert의 duplicate key는 source
  conflict로 반환한다.
- byte가 같은 assistant 출력이어도 Host generation/revision이 새로 관찰되면 이전 source를
  supersede하고 새 source generation으로 취급한다.

### 6.2 dependency와 무효화

- `memory_derivation_dependency.v1`은 precise memory child가 source revision과 어떤
  Direct Evidence parent에서 파생됐는지 versioned edge로 기록한다.
- canonical logical-turn replacement는 이전 source, dependency, precise row, 재처리 job,
  미완료 vector upsert를 한 MariaDB transaction에서 무효화하고 새 source revision과 raw
  turn을 함께 쓴다. replacement 전에 Chroma를 직접 삭제하지 않는다.
- rollback은 source invalidation/outbox transaction이 실패하면 canonical row 삭제 전에
  중단한다. 성공한 뒤의 Chroma 장애는 rollback을 `partial_error`로 되돌리지 않고 durable
  outbox의 retryable 상태로 남긴다.
- session delete는 active source뿐 아니라 과거 superseded/invalidated source까지 `deleted`
  처리한다. vector delete 작업은 보존하되 raw user/assistant, source message/generation,
  precise evidence/payload와 stale upsert document JSON은 즉시 비운다.

### 6.3 재처리 job

- critic 호출 실패와 critic 설정 누락은 accepted active source revision에
  `memory_reprocessing_job.v1`을 enqueue한다.
- idempotency key는 session, source revision, derivation, extractor, index version으로
  결정하므로 같은 실패를 다시 받아도 job이 늘어나지 않는다.
- pending/leased/retryable/permanent/completed/stale_rejected, lease owner/expiry, retry time,
  attempt와 last error를 보존하며 source가 inactive가 되면 claim/completion에서
  stale-reject한다.
- 3.6-D는 안전한 durable enqueue·claim·retry·stale fence까지 연결했고, 3.6-E에서 실제
  critic 재호출과 공통 admission transaction을 수행하는 worker가 이 queue를 소비한다.
- worker는 실행 중인 Go process의 runtime critic/embedding 설정만 읽으며 API key나 provider
  credential을 job 또는 outbox에 저장하지 않는다.

### 6.4 vector outbox

- `memory_vector_outbox.v1`은 operation key로 delete/upsert를 idempotent하게 저장하고 source
  active/inactive 조건, lease, retry와 permanent/stale 상태를 compare-at-commit한다.
- replacement·rollback·session delete는 알려진 legacy memory/evidence/world-rule ID와 precise
  document ID의 delete를 먼저 MariaDB에 기록한다. complete-turn, replacement, rollback은
  outbox를 제한된 수만큼 opportunistic하게 drain한다.
- provider upsert 뒤 source가 stale이면 보상 delete를 시도하며, durable invalidation 경로가
  최종 delete를 다시 보장한다.
- embedding이 없는 memory/evidence/precise upsert는 `needs_embedding`으로 남고, 3.6-E
  worker가 현재 runtime embedding 설정으로 vector를 만든 뒤 Chroma upsert를 수행한다.
  설정 누락과 일시 provider 실패는 searchable text를 잃지 않고 retryable 상태로 남는다.
- precise row를 실제 recall·최종 주입의 권위 source로 사용하는 전환은 여전히 4.0 범위다.

### 6.5 SQL 오류와 migration 경계

- job, outbox, dependency insert는 `INSERT IGNORE`를 쓰지 않는다. duplicate key `1062`만
  기존 idempotency identity를 다시 읽어 같은 작업인지 확인하고, FK·JSON·data 오류는 그대로
  실패시킨다.
- fresh schema, 독립 `005_memory_derivation_lifecycle.sql`, `mariadb-schema` compatibility
  statement를 같은 계약으로 맞췄다.
- `006_memory_admission_writer.sql`은 공통 writer admission marker와 확정 결과 JSON을
  `ADD COLUMN IF NOT EXISTS`로만 추가한다. 기존 numbered migration은 수정하지 않는다.
- updater는 새 번호의 additive migration, 함께 변경된 fresh schema와 서명·manifest로
  인증된 `mariadb-schema` 실행물만 허용한다. 과거 migration 수정, DROP·DELETE·UPDATE·
  INSERT·RENAME·MODIFY·CHANGE와 fresh schema 단독 변경은 적용 전에 거부한다.
- launcher는 package 적용 뒤 backend health commit 전에 `mariadb-schema`를 실행한다.
  schema 실행 또는 health check가 실패하면 package file set은 이전 세대로 복구된다.
  additive column은 DB에 남을 수 있지만 이전 binary가 무시할 수 있는 형태만 허용한다.
- 실제 사용자 DB에는 실행하지 않았다. disposable 3.5 clone 재적용·중단 복구와 실제
  package rollback 증거는 3.6-E release gate로 계속 남는다.

## 7. 3.6-E 구현 상세

### 7.1 공통 admission transaction

`memory_admission.v1`을 foreground complete-turn과 background worker가 공유하는 단일 Go
저장 경계로 추가했다. MariaDB transaction은 다음 순서로 동작한다.

1. 정확한 active source revision과 turn을 `FOR UPDATE`로 잠근다.
2. 같은 derivation/extractor/index version에 이미 확정된 결과가 있으면 첫 결과를 유지한다.
3. 호환 `memories` aggregate, 현재 turn의 critic Direct Evidence, precise memory unit,
   dependency edge와 vector outbox를 조정한다.
4. source revision에 admission version, result hash, 확정 extraction JSON과 시각을 기록한다.
5. 어느 단계든 실패하면 전체 transaction을 rollback한다.

확정 extraction JSON은 crash recovery를 위한 파생 결과이며 raw user/assistant와 별개다.
재실행은 새 critic 표본을 그대로 사용하지 않고 이 JSON을 모든 secondary projection보다
먼저 복원한다. 따라서 core commit 직후 process가 중단돼도 다음 worker가 처음 결과를
기준으로 identity·KG·상태 등 남은 projection을 이어서 만들 수 있다. session delete에서는
raw source와 함께 이 JSON도 비운다.

생산 `mariadb_authority`에서 accepted source가 있는데 공통 writer가 없거나 source가 없는
경우 legacy `SaveMemory`/`SaveEvidence`로 우회하지 않고 명시적 오류로 중단한다. lifecycle을
광고하지 않는 fixture·noop·구형 비권위 store의 기존 호환 경로만 남겼다.

### 7.2 durable worker와 producer 전환

- backend 시작 시 `mariadb_authority`이고 source/job/outbox/admission 계약을 모두 제공할
  때만 한 개의 Go worker loop를 시작한다.
- job은 저장된 accepted raw user/assistant를 runtime critic으로 다시 추출하고 foreground와
  같은 `saveCriticExtractionArtifacts` 및 공통 writer를 호출한다.
- critic 설정 누락, provider 오류와 저장 오류는 15초부터 최대 15분까지 지수 backoff로
  재시도한다. inactive source는 stale-reject한다.
- admin rescan과 Memory Explorer의 재분석은 lifecycle authority에서 직접 critic/writer를
  호출하지 않고 정확한 active source revision의 durable job을 enqueue한다.
- 외부 Hypa summary import는 accepted raw source를 증명할 수 없으므로 lifecycle authority에서
  명시적으로 거부한다. 이를 허용하려면 별도의 versioned external-source admission 계약이
  필요하며 legacy summary를 active source로 가장하지 않는다.

### 7.3 atomic 범위와 의도적으로 남긴 경계

한 SQL transaction에 묶인 범위는 compatibility memory, critic Direct Evidence, precise
memory, dependency, source admission marker와 vector outbox다. stable identity와 기존
subjective/KG/narrative/character projection은 각자의 source-bound idempotent writer를
계속 사용한다. 공통 core commit 뒤 secondary projection이 실패하면 job이 재시도되며,
저장된 첫 extraction으로 빈 부분을 보완한다.

기존 3.5 aggregate row를 이름이나 요약 문자열만 보고 새 source revision·stable identity로
자동 backfill하지 않는다. 기존 row는 호환 read 대상으로 보존하고, 새 accepted source부터
새 writer를 사용한다. 과거 turn의 재처리는 신뢰 가능한 raw user/assistant와 logical-turn
관찰을 source admission으로 먼저 확보한 경우에만 가능하다.

## 7A. 3.6-F 서사 가이드 균형 복구

### 7A.1 목적과 범위

이 packet은 새 plot planner나 장면 simulation을 추가하지 않는다. 기존 3.5 감독관이
기억 ID만 받고 실제 전달 문장을 읽지 못하면서 pacing·scene emphasis·callback·가역적
선택지까지 모두 금지하고, 긴 고정 source rule 때문에 호출 자체가 차단되는 문제를
수정한다.

Go는 support packet, lane eligibility, prompt/output contract, strength coverage, budget,
proposal normalization과 stable reason을 소유한다. JavaScript는 RisuAI 설정·관찰 전달,
backend plan 적용, HUD/UI 표시만 담당한다. DB schema, memory admission, critic 저장,
Chroma collection과 updater는 이번 packet에서 변경하지 않는다.

### 7A.2 구현 순서

1. 기존 guide OFF·current-input priority·private memory·unknown ref 거부 회귀를 먼저 고정한다.
2. 전달된 memory lineage의 안전 처리 `final_text`와 source ref만 supervisor support packet에
   연결한다.
3. fidelity와 expression eligibility/출력 lane을 분리한다.
4. visible guide의 source ID 반복과 첫 항목 전체-fit 호출 gate를 제거하고 item별 예산
   조립으로 바꾼다.
5. weak/medium/strong의 allowed role을 실제로 다르게 만들되 authority는 동일하게 유지한다.
6. JavaScript의 Auto mode 사전 판정과 사용되지 않는 active-path guidance 계산을 제거하고
   UI 설명을 backend 계약에 맞춘다.
7. 직전 완료 턴 `Input Context`와 선택형 입력 개선 LLM의 UI 명칭·제어 결합을 분리한다.
   전자는 일반 턴의 기본 연속성 앵커로 유지하고, 후자를 꺼도 서사 가이드 controls가
   비활성화되지 않게 한다.
8. focused Go 회귀, 전체 Go suite, `node --check "Archive Center.js"`, diff check와
   독립 validator review를 수행한다.
9. 실제 RisuAI에서 한국어 Auto, 기억 없는 초기 turn, protected memory, 각 strength,
   3,000자 기본 예산과 final displayed output을 확인한다.

### 7A.3 완료 기준

- supervisor payload의 모든 memory ref가 같은 packet의 실제 전달 문장 하나와 대응한다.
- raw private memory와 전달되지 않은 기억 후보가 supervisor prompt에 포함되지 않는다.
- current input만 있어도 expression lane이 `no_support`로 사라지지 않는다.
- fidelity/callback의 기억 사실은 delivered-memory ref 없이는 통과하지 않는다.
- weak/medium/strong은 서로 다른 coverage를 가지지만 모두 proposal-only다.
- 다수 Host ref가 source ID 문자열 반복으로 narrative budget을 소진하지 않는다.
- 한 guidance item의 초과가 뒤 항목을 자동 차단하지 않는다.
- JavaScript가 guide mode, role, budget이나 proposal 의미를 다시 계산하지 않는다.
- 선택형 입력 개선 LLM을 꺼도 직전 완료 턴 Input Context와 서사 가이드는 독립적으로
  동작한다.

### 평론가 JSON 안전 파싱과 Vertex/Gemini JSON 출력 정책

### MariaDB 기존 설치·업데이트 계정 권한 정합화

2026-07-29에 기존 설치의 MariaDB 내부 계정과 새 배포 DSN이 어긋나는 문제를 실제

부트스트랩을 사용했다.

격리한 MariaDB 11.4.10 데이터 디렉터리에 기존 비밀번호와 보존 확인용 row를 만든 뒤

`ERROR 1045 Access denied`, 기존 비밀번호와 보존 row 조회는 성공했다.

수정 내용:

- `go-service/cmd/mariadb-schema/main.go`의 기존 배포 바이너리에 opt-in
  `managed-bootstrap` 모드를 추가했다. 새 executable이나 DB migration은 만들지 않았다.
- 관리자 연결을 하나로 고정하고, 어떤 DDL보다 먼저 `SELECT @@datadir`를 실행해 현재
  포트의 데이터 디렉터리가 런처의 관리 디렉터리와 같은지 확인한다.
- 소유권이 확인된 경우에만 기존 계정을 삭제하지 않고 `CREATE USER IF NOT EXISTS`,
  `ALTER USER`, `GRANT` 순서로 `127.0.0.1`과 `localhost` 계정을 정합화한다.
- 정합화 직후 관리형 앱 DSN으로 실제 `Ping`에 성공해야 스키마 적용으로 진행한다.
- `managed_mariadb_admin_auth_failed`, `managed_mariadb_datadir_query_failed`,
  `managed_mariadb_datadir_mismatch`, `managed_mariadb_privilege_sync_failed`,
  `managed_mariadb_app_auth_failed`를 JSON report의 안정 오류 코드로 반환한다.
- Windows와 POSIX 런처의 직접 계정 SQL을 제거하고 같은 `mariadb-schema`
  production owner를 호출한다. 기존 `AC_MARIADB_DSN` 동작은 이번 범위에서 바꾸지 않았다.
- fresh-install smoke는 런처가 새 managed bootstrap과 expected datadir를 전달하고,
  예전 직접 `CREATE USER`/`GRANT` SQL이 되살아나지 않는지 검사한다.

## 12. 3.6 LLM Gateway provider와 service tier

2026-07-29에 LLM Gateway를 `custom` 별칭이 아닌 독립 generation provider
`llmgateway`로 추가했다.

- 메인/감독관과 평론가 설정에서 LLM Gateway를 직접 선택한다.
- endpoint 안내값은 공식 OpenAI 호환 주소
  `https://api.llmgateway.io/v1`이다. 기존 설정 계약에 따라 실제 endpoint
  값은 사용자가 저장해야 하며, provider 변경만으로 저장값을 몰래
  덮어쓰지 않는다.
- 각 역할은 `standard`, `flex`, `priority` service tier를 독립적으로
  선택한다.
- JavaScript는 선택 UI, 설정 저장, backend 전달만 담당한다.
- Go backend가 `llm_gateway_service_tier`를 검증하고 최종 요청의
  `service_tier`로 변환한다.
- `standard/default/auto`는 upstream `default`, `flex`와 `priority`는 같은
  값으로 전달한다.
- 미지원 tier의 upstream `unsupported_service_tier` 400 오류는 tier를
  제거한 재시도나 자동 강등 없이 그대로 실패 처리한다.
- typed tier와 `extra_body_json.service_tier`가 충돌하면 upstream 호출 전에
  설정 오류로 차단한다.
- trace에는 requested/applied/served tier를 기록하고 응답이 실제 tier를
  주지 않으면 `not_reported`로 남긴다.

공식 근거:

- https://docs.llmgateway.io/features/service-tiers

검증 상태:

| 검증 | 결과 |
|---|---|
| LLM Gateway 전용 URL과 OpenAI 호환 body | 자동 회귀 통과 |
| standard/flex/priority 변환 | 자동 회귀 통과 |
| invalid/conflict의 upstream 호출 전 차단 | 자동 회귀 통과 |
| `unsupported_service_tier` 자동 강등 방지 | 자동 회귀 통과 |
| main/supervisor/critic runtime config 전달 | 자동 회귀 통과 |
| bundled Node `Archive Center.js --check` | 통과 |

실제 외부 provider 호출도 수행하지 않았다.

## 13. 3.6 Anthropic Claude automatic prompt caching

2026-07-29에 direct Claude Messages API 요청에 Anthropic automatic prompt
caching의 역할별 typed 설정을 추가했다.

- UI 선택값은 `off`, `ephemeral_5m`, `ephemeral_1h`이며 기본값은 `off`다.
- Publisher와 Critic은 각각 독립 설정을 저장하고 Supervisor는 Publisher
  설정을 상속한다.
- JavaScript는 Claude 전용 행 표시, 설정 저장, backend 전달만 담당한다.
- Go backend가 `claude_prompt_cache_mode`를 검증하고 최종 Claude 요청의
  top-level `cache_control`로 변환한다.
- `ephemeral_5m`은 `{"type":"ephemeral"}`, `ephemeral_1h`은
  `{"type":"ephemeral","ttl":"1h"}`로 보낸다.
- typed 설정이 없거나 `off`이면 수동
  `extra_body_json.cache_control`을 보존한다.
- 이 수동 보존은 해당 필드를 명시적으로 보내는 backend caller 호환
  계약이다. Claude UI는 Vertex Extra Body JSON 설정을 노출하거나
  재사용하지 않으며, 일반 plugin 경로는 typed Claude 설정만 사용한다.
- typed/manual 값이 일치하면 허용하고, 충돌·잘못된 값·Claude가 아닌
  provider의 non-off 값은 upstream 호출 전에 차단한다.
- Anthropic 응답에 `usage`가 있을 때만 normalized response에 원본 usage를
  보존한다. trace에는 실제로 반환된
  `cache_creation_input_tokens`, `cache_read_input_tokens`,
  `usage.service_tier`만 기록한다.
- Anthropic 공식 요금 기준으로 5분 cache write는 기본 input의 `1.25x`,
  1시간 write는 `2x`, cache read/hit는 `0.1x`다. 두 Claude UI 행에 이
  비용 차이를 표시한다.

공식 근거:

- https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- https://platform.claude.com/docs/en/about-claude/pricing

검증 상태:

| 검증 | 결과 |
|---|---|
| off/5분/1시간 exact request mapping | 자동 회귀 통과 |
| manual 보존·typed/manual 일치·충돌 차단 | 자동 회귀 통과 |
| invalid/wrong-provider의 upstream 호출 전 차단 | 자동 회귀 통과 |
| Anthropic usage normalized response/trace 보존 | 자동 회귀 통과 |
| main/supervisor/critic runtime config 전달 | 자동 회귀 통과 |
| JS 설정·Claude 전용 UI·test connection 전달 | 자동 회귀 통과 |
| 실제 Anthropic 계정과 지원 모델 호출 | `live Anthropic call unverified` |

provider, HUD 재설계, retry 정책 변경은 이 작업 범위에 포함하지 않았다.
