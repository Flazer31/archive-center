# Archive Center 3.3-3.5 Source Integrity·RisuAI Host Context·출력 충실성 로드맵

상태: 3.3 기능 구현 범위는 종료했다. 3.3-A inventory는 `preparatory`, 3.3-B~F와 연계
운영 보정은 `implemented_unverified`다. 자동 회귀와 일부 실제 RisuAI 확인은 통과했으나
리롤 실패와 배포 환경 전체 확인 전이므로 release gate는 미완료다. 3.4-MEM-A~E는
`implemented_unverified`다. 실제 최종 입력에서 발견한 주입 밀도·관련성 차단 항목을 먼저
교정한 뒤 3.4-MEM-F 실제 RisuAI·성능 검증으로 진행한다.
범위: 3.2 원작 DB 이후부터 3.5 대형 마일스톤까지. source 분류·수명주기 기반은 3.3이
소유하고, 원자적 기억·관계·상태·회상은 3.6~4.0, 시뮬레이션 지원은 4.X가 소유한다.
목적: 실제 사용자 입력·시작 source·표시된 최종 출력의 경계를 먼저 고정하고, RisuAI가 현재
요청에 이미 조립한 캐릭터·시나리오·로어북·작가 노트를 effective Host Context로 관찰한다.
그 설정과 검증된 장기 기억에서 현재 응답이 반드시 이행할 항목을 짧은 실행 계약으로 만들어
실제 payload에 적용한다. RisuAI의 로어북 activation·recursive scan·token budget은 다시
구현하지 않는다. 동시에 Archive Center가 생성 전후에 추가하는 조회·직렬화·보조 LLM·저장
대기 시간을 계측하고 줄여, 기능이 늘어도 RisuAI의 본문 모델 호출 시작과 턴 완료가 불필요하게
늦어지지 않게 한다. 속도 개선은 source·기억·저장·삭제·원작 DB·RisuAI lifecycle 계약을
생략하는 방식으로 달성하지 않는다. 장기 기억의 추출·admission·검색·선별·주입 품질과
정확성이 성능보다 우선하며, 이 품질이 동일하거나 개선된 범위의 경량화만 채택한다.

### 0.1a 공식 RisuAI 적합성 기준

이 로드맵의 모든 구현은 `permanent-risu-host-backend-boundary.md`의
`Official RisuAI Conformance Baseline`을 필수 선행 조건으로 따른다. 작업 시작 전에 지원할
공식 RisuAI 버전의 문서와 upstream source/type에서 해당 hook, 메시지 필드, 역할, 호출 순서를
직접 확인하고, 확인한 commit 또는 tag·날짜·API/type 위치를 검증 기록에 남긴다.

- JavaScript는 공식 RisuAI가 실제로 노출한 입력 처리 관찰, 저장된 `Chat.message`,
  `beforeRequest` payload, streaming, 성공 응답과 최종 표시 사실만 전달한다.
- 입력 처리 시점·저장 시점·`beforeRequest` 시점·최종 표시 시점을 서로 같은 것으로 간주하지
  않는다. 앞선 시점의 값을 최종 요청이나 승인된 출력이라고 기록하지 않는다.
- 공식 RisuAI가 제공하지 않는 revision·generation·visibility·display 사실은
  `unobserved`/`not_exposed`로 두며 `false`, `true`, 문자열 비교나 임의 ID로 채우지 않는다.
- Go가 current input, request ownership, source authority, bootstrap, acceptance,
  generation/revision fence와 저장 결과를 결정한다. JavaScript는 이 정책을 선결정하지 않는다.
- release gate에는 공식 shape를 사용하는 production adapter 시험과 개인 대화·그룹 대화·빈 입력,
  streaming·성공·실패·리롤·편집·삭제·분기 중 해당 단계가 소유하는 실제 RisuAI lifecycle 검증을
  포함한다. fixture나 문법 검사만 통과한 상태는 `implemented_unverified`를 넘지 못한다.

공식 RisuAI의 구조나 호출 순서가 바뀌면 기존 adapter와 versioned observation contract를
수정한다. 이를 우회하는 별도 watcher, 병렬 저장 경로 또는 JavaScript 정책 fallback을 만들지 않는다.

### 0.4 현재 상태와 다음 작업

3.3-A 읽기 전용 조사에서 현재 production lineage를 확정했다. JavaScript가 `/prepare-turn`
뒤 `/supervisor`를 별도로 호출하고, supervisor proposal을 `/storylines/sync`와
`/world-rules/sync`의 `apply` mode로 전달해 canonical row를 직접 쓸 수 있던 경로가
재현됐다. 같은 결과의 current-turn overlay와 final-output 이후 `/complete-turn` admission은
서로 다른 경로임도 구분했다. 다만 실제 loaded artifact가 active source와 일치하지 않았고,
지원 기존 DB clone·RisuAI lifecycle·전체 stage 기준선은 아직 검증하지 못했으므로 3.3-A는
`preparatory`다.

3.3-B의 runtime containment는 `implemented_unverified`다. backend는 두 sync route의
`apply`를 안정적인 `supervisor_canonical_write_forbidden` 오류로 거부하고 실제 save를 하지
않으며, `dry_run` 후보 확인과 수동 PATCH·trust·delete는 유지한다. JavaScript의 두 자동
sync 함수와 호출부는 제거하되 current-turn overlay·payload guidance는 유지했다. source
검사, overlay runtime smoke, 관련 Go package와 전체 Go test는 통과했다. 그러나 기존 DB의
supervisor/cache-origin row를 provenance별로 식별·격리하는 clone upgrade와 실제 loaded
package의 row delta는 아직 검증되지 않았다. 이 두 증거 전에는 3.3-B를
`release_gate_verified`로 올리지 않는다. 다음 순서는 이 잔여 gate를 닫은 뒤 3.3-C의
versioned source/capability DTO로 넘어가는 것이다.

### 0.5 2026-07-21 3.3-A 판단과 3.3-B 작업 기록

#### 3.3-A 판단

- production JavaScript는 `/prepare-turn` 뒤 `/supervisor`를 별도 호출하고 있었다.
- supervisor 결과의 storyline과 world rule proposal은 current-turn overlay로 이번 payload에
  사용되는 경로와, sync route의 `apply` mode로 canonical row를 쓰는 경로가 함께 존재했다.
- `/complete-turn`이 final source를 다시 추출·admission하는 간접 경로는 위 직접 sync write와
  별개다. 이번 packet에서는 직접 write만 차단하고 간접 admission은 3.3-C~E의 source
  envelope·acceptance 작업 전까지 수정하지 않았다.
- 조사 결과는 3.3-B bounded slice를 정하는 근거로는 충분하지만 실제 loaded artifact 불일치,
  기존 DB clone과 전체 RisuAI lifecycle fixture 미검증 때문에 3.3-A 자체는 `preparatory`다.

#### 3.3-B에서 적용한 변경

- Go `POST /storylines/sync`와 `POST /world-rules/sync`는 supervisor proposal의 `apply`를
  HTTP 409와 `supervisor_canonical_write_forbidden`으로 거부하며 `SaveStoryline` 또는
  `SaveWorldRule`을 실행하지 않는다.
- 두 route의 `dry_run` 후보 parsing·normalization·count는 유지했다.
- storyline/world rule의 수동 PATCH·trust·delete 경로는 유지했다.
- `Archive Center.js`의 `postStorylineSync`, `postWorldRulesSync` 함수와 두 자동 호출부를
  제거했다. runtime JavaScript 변경량은 추가 0줄, 제거 62줄이다.
- current-turn storyline/world-rule overlay 생성·merge·payload guidance는 기존 출력 동작을
  보존하기 위해 유지했다. 이 조립 책임의 Go 이전은 3.4의 단일 `/prepare-turn` cutover
  소유이며 이번 packet에서 앞당기지 않았다.
- 차단된 storyline apply 경로에서만 사용되던 저장 변환·evidence 갱신 보조 함수도 제거했다.
- 안정적인 오류 code와 apply 차단, save count 0, dry-run, 수동 CRUD 보존, JavaScript 자동
  persistence 부재, same-turn overlay runtime 동작을 회귀 테스트로 고정했다.

#### 검증 증거

- active `Archive Center.js`의 Node syntax check 통과;
- 번들 Node를 실제 PATH에 포함한 same-turn overlay injection·freshness runtime smoke 통과;
- `go test ./... -count=1` 전체 통과;
- 별도 read-only 위험 검토에서 다른 direct-write P0/P1 우회가 발견되지 않음;
- 위험 검토에서 발견된 삭제된 sync 주석 의존 smoke-test 경계를 현재 overlay 함수 경계로
  교체하고, formatter dependency를 포함해 다시 runtime 검증함;
- `git diff --check` 통과. CRLF 변환 경고 외 whitespace 오류 없음.

#### 수정하지 않은 경계

- 메인 장기 기억의 추출·저장·검색·주입과 Chroma 경로;
- 원작 DB와 reference budget·검색·주입;
- RisuAI user input·복수 start·streaming·final·reroll·edit·delete·branch lifecycle;
- GigaTrans·ReKo·후처리 호환 경로;
- `/complete-turn`의 final source admission과 그 파생 저장;
- DB schema·기존 row migration·배포 package.

#### 남은 3.3-B release gate

1. 지원 대상 기존 DB clone에서 supervisor/director/cache/overlay-origin storyline·world-rule row를
   source와 provenance별로 inventory한다.
2. 기존 column과 source evidence만으로 해당 row의 canonical read 제외·격리가 가능한지
   먼저 검증한다. 불가능하다는 재현 증거 없이 schema·migration을 추가하지 않는다.
3. 격리 전후 row delta, 수동 승인 row 보존, restart·upgrade 뒤 격리 row 미부활을 검증한다.
4. active source와 일치하는 실제 loaded artifact에서 JavaScript 자동 sync call 0,
   supervisor-origin canonical write 0, 수동 CRUD 정상과 main-memory·원작 DB sentinel 보존을
   같은 evidence manifest로 연결한다.
5. 위 증거가 모두 통과하기 전에는 `implemented_unverified`를 유지하고 3.3-B 완료나 3.3-C
   production cutover를 선언하지 않는다.

## 1. 결론

3.3~3.5는 전체 로어북을 다른 DB로 복제하거나 RisuAI의 activation을 대체하는 구간이 아니다.
다음 세 결과를 하나의 source·전처리 경로로 완성한다.

1. 실제 사용자 입력·복수 start source·streaming/candidate·표시된 최종 출력·reroll·삭제·분기를
   versioned source envelope와 acceptance lifecycle로 구분한다.
2. 현재 RisuAI payload에 실제로 들어온 Host 설정과 관찰 불가능한 경계를 source·scope·span
   근거로 구분한다.
3. 이미 전달된 설정과 장기 기억을 근거로, 메인 생성 모델이 실제로 이행할 수 있는 짧고 명확한
   `response_execution_contract.v1`을 만들어 최종 payload에 적용한다.

3.3~3.5는 로어북 전용 API로 원문 목록을 읽지 않는다. `beforeRequest`에서 실제 생성 요청에
들어온 payload만 effective Host Context로 관찰한다. Host가 source 종류나 ID를 함께 노출하지
않으면 내용을 보고 로어북이라고 추측하지 않고 `host_source_kind=unknown`으로 둔다. 전체
로어북 DB·semantic retrieval·누락 보완은 이 로드맵에서 폐기한다.

감독관을 과거처럼 다음 사건과 결말을 정하는 강한 작가로 되돌리지 않는다. 반대로 모든
지시를 “가벼운 선택적 힌트”로 만들어 켜기와 끄기의 차이가 사라지는 상태도 허용하지
않는다. 강도는 사실 authority나 사용자 agency를 넓히는 값이 아니라, **근거가 있는 실행
의무를 얼마나 명시적으로 전달하고 검증할지**를 조절한다.

3.5 완료 시점에는 다음이 가능해야 한다.

- 가이드 OFF에서는 출력 개선용 계약이 실제 payload에 들어가지 않는다.
- 실제 사용자 입력만 current user source가 되고, start message·system prompt·streaming 초안·
  superseded/deleted output이 현재 입력이나 canonical final로 위장하지 않는다.
- 가이드 ON이며 적용할 근거가 있는 턴에서는 계약이 실제 payload에 들어가고, 목표한
  설정·연속성·현재 입력 반응이 출력에서 관찰된다.
- 같은 기능·자료·provider 조건에서 Archive Center가 본문 모델 호출 전에 만드는 대기와
  final 표시 뒤 턴 완료 대기가 기준선보다 가벼워지고, 긴 세션에서도 전체 과거 row와 대형
  proof payload를 매번 무제한 materialize하지 않는다.
- 적용할 근거가 없는 턴은 ON이어도 억지 차이를 만들지 않는다.
- 강한 가이드도 user/player 행동·감정·결정, 근거 없는 사건, 관계 변화나 전체 이야기
  종료를 강제하지 않는다.
- 감독관·Host Context 장애가 기존 기억 주입, 생성, 저장, 삭제와 `/ready`를 막지 않는다.

속도는 독립적인 품질 축이다. 단순히 endpoint가 성공했거나 평균 한 번이 빨라진 것으로 완료하지
않는다. 같은 source snapshot·설정·loaded artifact에서 cold/warm 실행과 분포를 비교하고, 빨라진
결과가 payload·최종 저장·삭제·reroll·분기·장기 기억·원작 DB의 의미를 바꾸지 않았음을 함께
증명해야 한다.

## 2. 현재 runtime에서 확인한 문제

이 절은 구현 완료가 아니라 현재 경로를 기준으로 한 policy debt 감사다.

### 2.1 OFF와 ON의 실행 경계가 불명확하다

`Archive Center.js`의 `runSupervisor`는 Archive Center가 활성화된 경우 guide mode가
`off`여도 `/supervisor` 호출 자체를 중단하지 않는다. `off`는 guide suffix를 비우지만 기본
supervisor system prompt는 계속 `book_author`와 `director` directive를 요구하고, 반환된
directive는 다시 본문 보조 블록 후보가 된다.

따라서 사용자가 끈 것이 “스타일 suffix”인지 “출력 개선 directive 적용”인지 분명하지 않고,
실제 출력에서는 OFF와 ON 모두 유사한 감독관 지시를 받을 수 있다.

### 2.2 약화 문구가 강도 차이를 상쇄한다

현재 `weak`은 가이드를 “거의 보이지 않게” 유지하라고 하고, standard·romantic·action 등
모드별 suffix는 강도와 관계없이 다시 “가벼운 선택적 스타일 힌트”라고 지시한다. strong을
선택해도 동일한 optional 문구가 실행 의무를 약하게 만들 수 있다.

또한 현재 `/supervisor` handler는 내부 `supervisor_input_pack`을 다시 만들 때 strength를
`weak`으로 전달하지만, 실제 LLM system suffix는 요청에서 넘어온 다른 strength 문구를 사용할
수 있다. 따라서 UI 설정, pack trace와 실제 호출 의미가 서로 다를 가능성도 함께 감사해야
한다.

이 문제를 prompt 문장만 더 강하게 바꾸는 방식으로 해결하지 않는다. strength가 어떤
필드를 생성하고 어떤 항목을 실제 payload의 `must_*` 계약으로 올리는지 Go contract로
정의한다.

### 2.3 감독관 블록이 기억 예산과 경쟁한다

현재 author/director 결과는 memory, storyline, world rule, character state 등과 함께 하나의
보조 조립 경로로 들어간다. 최종 예산·순서·중복에 따라 감독관 핵심이 잘리거나 많은 지원
텍스트에 묻힐 수 있다.

3.5에서는 장기 기억 예산을 줄이지 않는 `narrative_support_max_chars` lane을 사용한다. RisuAI가
이미 넣은 Host Context 원문은 재주입하지 않고 source observation으로만 추적하며, 그 원문에서
압축한 execution constraint의 block·hash·사용량만 별도로 표시한다.

### 2.4 고정 개수·단계·장르 문구가 정책에 섞여 있다

현재 formatter와 prompt에는 일부 배열 고정 절단, pressure 단계, 장르별 지시 문구와 beat
제한이 존재한다. 이 값들은 현재 구현의 관찰 대상이지 3.5 정책으로 계승할 기준이 아니다.

3.3~3.5에서는 작품·장르·인물·모델명, 고정 outcome 수, 고정 forbidden 수, 고정 pressure
score·단계, 턴당 사건 수와 고정 beat 수로 출력 개선 여부를 판정하지 않는다.

### 2.5 실제 효과 증거가 부족하다

directive 수신, block 포함과 LLM 호출 성공만으로 출력 개선을 증명할 수 없다. 같은 요청과
근거에서 OFF/ON이 각각 무엇을 전달했고, 출력이 어떤 의무를 이행했으며, 과잉 주도나
설정 위반이 어떻게 달라졌는지 연결된 evidence가 필요하다.

### 2.6 감독관 proposal이 현재 persistence로 직접 들어간다

현재 `Archive Center.js`는 supervisor 결과가 있으면 `postStorylineSync(..., "apply")`와
`postWorldRulesSync(...)`를 호출하고, backend의 `/storylines/sync`와 `/world-rules/sync`는
후보를 실제 저장할 수 있다. guide suffix를 비우거나 본문 guide block을 숨기는 것만으로는
감독관 proposal의 간접 적용과 저장을 끄지 못한다.

3.3의 첫 containment item에서 이 호출·overlay·maintenance 전체 lineage를 고정하고 supervisor
origin 직접 write를 backend에서 거부한 뒤 JavaScript의 자동 `apply` 호출을 제거한다. 최종 표시 출력에서 실제
발생한 사실도 3.6~4.0 메인 기억 owner의 일반 source·authority admission을 통과해야 한다.
교체되는 JavaScript apply 계산과 호출은 같은 bounded work item에서 제거하며 무기한 fallback을
남기지 않는다.

### 2.7 기능 누적이 생성 전후 blocking path를 무겁게 한다

2026-07-20 로컬 진단에서 `/prepare-turn`은 짧은 세션에서도 수백 ms를 사용했고, 더 긴
세션에서는 응답이 약 2.37 MB까지 커졌다. 해당 응답은 678개의 최상위 key를 포함했지만 현재
JavaScript 적용 경로가 직접 소비하는 key는 그 일부였다. `retrieval_units_ir`,
`raw_turn_span_metadata`와 여러 proof/contract surface가 production 요청마다 함께 직렬화되는
구조가 관찰되었다. 이 수치는 합격 threshold가 아니라 당시 loaded package의 병목 증거이며,
source folder 이름과 실제 `/version` build가 달랐으므로 release 성능 기준으로 재사용하지 않는다.

같은 경로에서 session memory·KG·evidence·chat log·storyline·world rule·character state 등을
무제한 list한 뒤 조립하고, Chroma health·embedding·search를 순차 실행하는 흐름이 확인되었다.
final 표시 뒤 `/complete-turn`도 critic 호출과 파생 artifact 저장·embedding·vector upsert를
동기 경로에서 수행한다. CPU·RAM 포화가 없어도 이 직렬 대기와 materialization은 세션이
길어질수록 호출 체감을 늦출 수 있다.

3.3~3.5는 이 문제를 다음 원칙으로 해결한다.

- 3.3은 실제 loaded artifact에서 stage별 시간·row·byte·호출 수와 결과 hash를 고정한다.
- 3.4는 `/prepare-turn`의 production 응답을 JS 적용과 UI 표시에 필요한 versioned projection으로
  줄이고, 저장소 조회는 의미상 필요한 범위에서 수행한다. 오래된 관련 기억을 단순 최근 N개로
  잘라내지 않는다.
- 3.5는 Archive Center가 소유하는 보조 LLM·vector·저장 경로의 중복 호출과 직렬 대기를 줄이고
  전체 호출 시작·완료 지연의 비퇴행을 입증한다.
- RisuAI 또는 외부 플러그인이 소유한 lifecycle·호출을 Archive Center의 속도 개선 명목으로
  제거·재정렬하지 않는다.
- 상시 health polling이나 UI 실시간 감시를 추가하지 않는다. 요청 자체에 필요한 상태 확인과
  사용자가 누른 진단, release 측정만 구분해 수행한다.

## 3. 영구 경계

### 3.1 소유권

- JavaScript는 실제 payload path·role·span·hash와 Host가 직접 노출한 ID·scope·revision 등,
  RisuAI에서만 관찰할 수 있는 사실과 최종 적용 위치만 전달한다. 노출되지 않은 activation이나
  source 종류를 추측하지 않는다.
- Go는 source authority, lifecycle, constraint 선별·압축, 중복, 예산, 강도 의미, 실행 계약 조립, 적용·유예
  reason과 안정적인 오류 상태를 소유한다.
- 감독관 LLM은 Go가 제공한 사실과 변경 envelope 안에서 동기·표현·전개 후보를 제안할 수
  있지만 truth, 관계, 지식, user agency와 thread closure authority를 만들지 못한다.
- 본문 모델은 raw user input을 다시 쓰지 않고, 별도 실행 계약을 참고해 최종 서술과 대사를
  생성한다.

### 3.2 자료 권한

권한은 다음 순서를 기본으로 하되 각 항목의 scope·branch·visibility를 함께 확인한다.

```text
신뢰된 host role/channel의 명시적 OOC·작가 지시·설정 정정
-> 현재 사용자 입력의 응답 의무와 명시적인 현재 세션 분기
-> 현재 세션에서 source로 확정된 변화
-> 현재 활성 RisuAI 캐릭터·시나리오·로어북·작가 노트
-> Local Canon Overlay
-> 승인된 원작 Canon Pack
-> 불확실한 검색·감독관 proposal
```

RisuAI 설정은 승인 원작 DB로 자동 병합하지 않는다. 세션에서 실제로 발생하지 않은
로어북 사실을 인물의 경험이나 관계 변화로 저장하지 않는다. OOC/meta 지시와 in-world
사실도 같은 row나 실행 의무로 섞지 않는다.

현재 사용자 입력은 이번 응답의 최우선 대상이지만 그 안의 모든 문장이 객관적 truth가 되는
것은 아니다. 신뢰된 host role/channel로 확인된 authorial correction, user/player의 행동·대사,
인물의 주장·거짓말·추측과 객관적 서술을 분리한다. 문자열 표식이나 특정 문구로 OOC 또는
truth authority를 판정하지 않는다.

### 3.3 메인 기능 보호

Host Context나 감독관이 실패하면 해당 lane을 `degraded` 또는 `failed`로 표시하고 원래
payload·장기 기억 경로를 계속 사용한다. 장애를 빈 성공이나 정상 지원으로 위장하지 않는다.
실패 격리는 출력 개선을 무호출·no-op·진단-only로 남겨도 된다는 뜻이 아니다.

경량화도 동일한 보호 경계를 따른다. runtime response key나 DB materialization을 줄이기 전에
실제 JS·UI·운영 진단 consumer와 payload/hash/row parity를 증명한다. final 표시 뒤 파생 작업을
비동기화하려면 raw turn/source가 먼저 durable하게 저장되고, 작업이 versioned·idempotent·
재시작 복구 가능한 영속 outbox를 통하며, 완료 전 상태가 UI와 `/ready` 계약에서 정직하게
구분되어야 한다. 이 조건을 충족하지 못하면 해당 write는 동기 경로에 남긴 채 batch·reuse로만
최적화한다. process-local queue나 무조건 성공 응답으로 저장 지연을 숨기지 않는다.

성능 packet은 RisuAI의 실제 user input 인식, 복수 start·streaming·reroll·edit·delete·branch,
input/beforeRequest/afterRequest hook 순서, GigaTrans·ReKo·후처리 payload와 표시 결과를 바꾸지
않는다. Archive Center의 시작·`/ready`·원문 저장·삭제·장기 기억·원작 DB도 동일한 sentinel로
보호한다. 이 항목 중 하나라도 달라지면 지연이 줄어도 성능 개선으로 채택하지 않는다.

특히 장기 기억은 단순 row 수나 응답 byte parity만으로 보호되지 않는다. 같은 source snapshot에서
사건·약속·비밀·관계·상태·시간·화자와 인물별 지식 경계의 추출 근거, admission 결과, 현재성,
old-but-relevant 회상, 중복·충돌 억제와 최종 주입 item을 항목별로 비교한다. 이전 기준선에서
정확히 찾아 주입하던 기억이 누락되거나, 잘못된 기억·오래된 상태·다른 인물의 지식이 추가되면
속도가 빨라져도 release를 차단한다. 단일 총점의 평균 향상으로 개별 정확성 퇴행을 상쇄하지
않는다.

### 3.4 3.5 종료선과 3.6~4.0 인계

3.3~3.5는 **공통 source 수명주기를 고정하고 외부·Host 설정을 현재 요청에 맞게 생성 전에
전달하는 계층**이다. source의 정체와 채택 상태는 판정하지만, 그 source에서 메인 장기 기억의
사실·관계·상태를 새로 판정하거나 기억 구조를 완성하지 않는다.

| 버전 | 이 문서가 소유하는 결과 | 이 문서가 소유하지 않는 결과 |
|---|---|---|
| 3.3 | `message_source_envelope.v1`, `session_bootstrap.v1`, `source_acceptance_lifecycle.v1`, 실제 payload Host observation, source capability, OFF/ON·payload trace와 supervisor write containment | 로어북 전용 API·전체 raw lore 저장·검색·activation 재구현, entity 합성·동일성 판정, 메인 기억 schema·truth admission·검색 정책 |
| 3.4 | actual Host Context의 권한·중복·constraint compile, source-linked entity/alias 후보, 짧은 실행 계약과 실제 payload 적용 | payload 밖 설정의 자동 발굴·주입, stable session entity 생성·merge/split, story clock·신체 상태·인물별 canonical 지식·관계 |
| 3.5 | 설정·현재 입력·entity reference 충실성, guide efficacy·agency·장애 격리 E2E | 장기 기억 완성, canonical entity admission, 캐릭터 profile 완성, 장면·세력 simulation |

3.5가 3.6~4.0에 넘기는 versioned 결과는
`message_source_envelope.v1`, `session_bootstrap.v1`, `source_acceptance_lifecycle.v1`,
`risu_host_context_snapshot.v1`, `host_context_support_plan.v1`,
`host_context_reference_evidence.v1`, `response_execution_contract.v1`,
`guidance_application_trace.v1`과 각 source ID·budget·상태다.
3.6~4.0은 이 결과를 다음 원칙으로 소비한다.

- Host Context를 다시 수집·분류하거나 같은 목적의 native attribution·중복 억제·supervisor를 병렬로
  만들지 않는다.
- 3.5는 현재 메인 기억에서 이미 검증된 source만 읽는다. 3.6~4.0에서 아직 구현되지 않은
  story time, knower, 관계나 profile을 추측해 임시 truth로 채우지 않는다.
- 3.6~4.0은 메인 기억의 admission·current/history·검색·주입·lifecycle을 소유하지만
  3.5의 native Host source 근거, guide strength, OFF parity와 독립 예산을 다시 판정하지 않는다.
- 3.6 `entity_identity.v1`은 `host_context_reference_evidence.v1`을 개체 생성·별칭·동일성 연결의
  보조 근거로 사용할 수 있다. 그러나 Host-only entity는 setting/reference-defined이며
  별도 active session source 없이는 등장·경험·사건·현재 상태·관계·knower row를 만들지 않는다.
- 후속 계약이 `response_execution_contract.v1`을 확장할 때에는 versioned composition을
  사용한다. 같은 의미의 두 payload block이나 두 예산 계산기를 만들지 않는다.
- 3.6~4.0과 4.X는 `PERF-*` stage·projection·durability·non-regression 계약을 그대로 소비한다.
  기억·시뮬레이션 기능을 추가하면서 전체 row materialization, 대형 proof 상시 반환, 보조 LLM
  무조건 호출이나 검증되지 않은 process-local write queue를 되살리지 않는다.
- 3.5 완료는 정밀 장기 기억 완료를 의미하지 않고, 4.0 완료도 3.5 출력 충실성 검증을
  대신하지 않는다. 각각의 requirement와 release evidence를 따로 유지한다.

3.6~4.0의 authoritative 범위와 단계는 `4.0-precision-long-term-memory-roadmap.md`가
소유한다. 4.0 이후 캐릭터 실행 카드·활성 인물·세계·세력 simulation은
`4.x-model-adaptive-rp-simulation-roadmap.md`의 별도 후속 범위다.

3.5의 출력 충실성은 **현재 입력과 실제로 전달된 effective Host Context·검증된 기억 constraint의 이행**을
판정한다. 근거에 명시된 화자·호칭·말투 규칙 위반이나 전달된 `already_realized` 사건의 단순
반복은 잡을 수 있지만, 다층 성격 해석·단일 특성 환원·예시 대사 복사 경향·과도한 친밀감·
장르별 서사 압력·활성 인물과 세계 simulation의 고급 의미 판정은 4.X의 owner다. 이 항목을
3.5 완료 조건으로 앞당겨 별도 character profile·simulation·critic을 만들지 않는다.

## 5. 전처리 계약

### 5.0 공통 요청·응답 경계

JavaScript가 Go에 보내는 것은 RisuAI에서 실제로 관찰한 사실뿐이다.

- session·chat·branch·request·generation과 실제 message index/role, raw current user input과
  start/bootstrap source의 위치·revision;
- streaming·display candidate·active final·superseded·deleted를 판정하는 데 필요한 Host 관찰;
- host item의 실제 payload span/hash와 Host가 직접 노출한 경우에만 ID·scope·revision;
- output guide의 사용자 설정 상태와 Host capability;
- raw current user input의 위치·hash·active revision, Host snapshot revision set, backend state
  revision과 guide-mode revision. 본문은 정책 판정용으로 다시 쓰지 않는다;
- 최종 payload 적용 결과와 final displayed output의 관찰 ID/hash.

JavaScript는 관찰할 수 없는 stable ID, authority, relevance, knowledge boundary, budget,
strength 의미 또는 persistence 결정을 추측하지 않는다. Go 응답은 최소한 다음을 한 번에
반환한다.

- response contract version과 required/optional capability;
- 요청에서 받은 revision set, response idempotency key와 payload 적용 전 다시 확인할
  expected active revision fence;
- lane별 `eligible`, `not_applicable`, `empty`, `deferred`, `degraded`, `failed`,
  `incompatible` 상태 및 안정적인 reason code;
- source-linked Host constraint item과 execution item의 ordered block, 완전한 text/hash와 예산 사용량;
- native overlap, suppression, compaction, deferral과 coverage gap;
- JS가 실제 payload에 적용할 위치와 적용하면 안 되는 항목;
- UI용 ViewModel과 trace correlation ID.

`not_applicable`과 `empty`는 정상적인 무주입 결과다. `degraded`, `failed`, `incompatible`을
빈 plan이나 성공으로 바꾸지 않는다. backend contract가 맞지 않으면 JS가 옛 selection·budget·
prompt assembly를 대신 실행하지 않고 해당 보조 lane만 제외하며 메인 payload를 보존한다.

- `not_applicable`: 설정상 OFF이거나 현재 request가 해당 lane의 적용 대상이 아님;
- `empty`: 적용 대상이며 검색·판정은 정상 완료했지만 관련 지원 item이 없음;
- `deferred`: 관련 item은 있으나 현재 request/budget/lifecycle에서 의도적으로 다음 처리로 유예;
- `degraded`: 일부 capability·source·provider·budget이 부족해 coverage가 불완전함;
- `failed`: 요청 처리나 검증이 실패해 신뢰 가능한 plan을 반환하지 못함;
- `incompatible`: contract/capability version이 맞지 않아 해당 lane을 적용할 수 없음;
- `stale_rejected/cancelled/superseded`: 결과 생성 뒤 active request fence가 바뀌어 적용하지 않음.

UI와 trace는 이 상태, reason, retryability, 영향 lane과 원 payload 보존 여부를 그대로 표시한다.
상태별 row/payload delta를 release test에서 분리하며 모두를 `ready`, `skipped` 또는 빈 성공으로
합치지 않는다.

응답이 도착하면 JS는 host에서만 확인 가능한 현재 request/generation/input/branch/Host revision과
guide-mode revision을 다시 관찰해 Go가 반환한 fence와 일치할 때만 payload에 적용한다. Go는
backend state revision과 idempotency를 검증한다. 그 사이 새 입력·reroll·delete·branch switch·
Host 수정·guide OFF가 발생했으면 `stale_rejected`, `cancelled` 또는 `superseded`로 끝내고 늦은
결과가 payload, adapter cache, trace current pointer나 canonical write를 바꾸지 못하게 한다.

요청·응답 계약을 추가하기 전에 기존 `/prepare-turn`, `/supervisor`, sync·overlay 경로 중
어느 owner를 교체하는지 기록한다. 새 병렬 endpoint·watcher·cache를 기본 해법으로 만들지
않고, 기존 owner를 고친 뒤 교체된 JavaScript 계산과 직접-write 호출을 같은 작업에서 제거한다.

3.4 cutover 뒤 RisuAI 생성 adapter가 호출하는 **생성 전 최종 planner**는 `/prepare-turn`
하나다. 이 endpoint는 canonical state에 쓰지 않는 read-only planning path다. Go는 그
요청 안에서 필요할 때만 supervisor LLM을 orchestration하고 proposal을 원래 source envelope로
검증해 `response_execution_contract.v1`에 합친다. proposal 원문을 별도 payload block으로
주입하지 않는다. 기존 `/supervisor` HTTP route가 운영·진단 또는 명시적 compatibility window에
남더라도 JS 생성 경로는 호출하지 않으며, 최종 budget·assembly·write owner가 될 수 없다.

final displayed output 뒤 raw source 보존과 기억 admission을 담당하는 complete-turn은 별도
post-display ingestion 경로다. 3.3~3.5에서는 기존 메인 저장 기능을 바꾸지 않되 supervisor
proposal을 저장 입력으로 보내지 않는다. 3.6부터 complete-turn·background·reprocess는 공통
Go admission transaction을 통과하며 `/prepare-turn`을 write endpoint로 재사용하지 않는다.

JS의 backend unreachable transport queue는 메모리에만 존재하며 이미 관찰한 동일 active
request packet의 재전송만 할
수 있다. 새 request·generation·branch·input/Host/guide revision이 관찰되면 이전 packet과
도착 결과를 폐기한다. queue의 실제 용량·시간·retry는 versioned operation setting과
backpressure로 관리하고 작품·모델·prompt 정책과 결합하지 않는다. guidance는 현재 payload에
적용할 시점을 놓치면 다음 턴에 재사용하지 않고 `failed/stale_rejected`로 끝낸다.
이 queue는 4.0의 persistent reprocessing job·MariaDB/Chroma outbox에 복제·승격되지 않으며,
양쪽 queue 사이에는 source revision fence 외의 순서·재시도 의존성이 없다. Go의 영속 queue도
live guidance request나 결과를 JS로 되돌려 보내는 통로로 사용할 수 없다.

### 5.1 `risu_host_context_snapshot.v1`

현재 요청의 `beforeRequest` payload에서 실제로 관찰된 Host context를 request-scoped source로
보존한다.

- payload message path·role·order와 exact span/hash;
- request·generation·session·branch fence;
- Host가 payload와 함께 직접 노출한 경우에만 source kind·ID·scope·revision·visibility;
- 신뢰된 Host role/channel이 선언한 OOC/meta/in-world 경계;
- 필드별 `observed`, `unavailable`, `not_exposed`, `degraded`와 관찰 근거.

Host가 source kind·stable ID·revision·activation을 노출하지 않으면 이를 prompt 문구, 위치,
keyword 또는 content hash로 추측하지 않는다. `risu_host_context_snapshot.v1`은 실제 payload의
request-scoped view이지 RisuAI 내부 로어북·캐릭터·모듈 DB의 mirror가 아니다. 선택된 actual
source span과 그 turn의 hash·scope만 execution trace와 `host_context_reference_evidence.v1`
근거로 남길 수 있으며, 과거 evidence를 현재 Host 설정으로 재사용하지 않는다.

### 5.2 `host_context_support_plan.v1`

Go는 raw user input, 관찰 가능한 직전 active-final output source, 현재 인물·장소·사건·관계·
thread와 actual payload에 실제 포함된 Host Context를 이용해 다음 집합을 계산한다. payload 밖의
로어북이나 설정 원문을 별도로 조회해 후보 풀에 추가하지 않는다.

`prior_response_source`는 `active_final`, `absent`, `unknown`을 구분하고
가능한 경우 session·branch·request·generation·message·revision·hash를 가진다. 첫 응답이거나
직전 final을 확인할 수 없으면 `absent/unknown`으로 남기며 start message, streaming chunk,
reroll 전 candidate 또는 오래된 cache를 직전 accepted output으로 대체하지 않는다. 3.3의
`source_acceptance_lifecycle.v1`이 확정한 active-final tuple만 사용하며 3.4·3.5와 3.6~4.0이
별도 acceptance 정책을 만들지 않는다.

복수 start message와 character greeting은 Host/bootstrap source로만 별도 전달한다. 내용이
assistant 형식이어도 `prior_response_source`나 `active_final`이 아니며 first/start-only 요청은
반드시 `prior_response_source=absent`다. 필요한 start source는 source/Host lane의 eligibility를
거쳐 사용할 수 있지만 직전 응답으로 위장해 recap·continuation guidance를 만들 수 없다.

- `native_present`: RisuAI가 이미 같은 목적으로 넣은 항목;
- `must_preserve`: 이번 응답에서도 유지해야 하는 native-present 설정;
- `response_relevant`: 현재 입력에 직접 답하는 데 필요한 설정;
- `knowledge_boundary`: 인물별 known/unknown/hidden/misinformed 경계;
- `session_divergence`: 원작이나 오래된 로어북보다 우선하는 현재 세션 변화;
- `conflict/unknown`: 자동 선택하면 안 되는 충돌·불확실성;
- `deferred`: 현재 요청의 native-present source지만 실행 constraint로 압축할 필요가 없는 항목.
- `eligibility`: 사용한 scene/entity/source 관계, 선택·유예·제외 reason과 coverage 상태.

항목 선택은 특정 단어 목록이나 고정 후보 수가 아니라 native source scope, entity·scene relation,
causal dependency와 현재 응답 의무로 결정한다. 관련 항목이 없으면 빈 plan은 정상 결과지만
source attribution·provider 실패와는 다른 상태로 보고한다.

`knowledge_boundary`, 관계·thread와 scene field는 현재 effective Host Context가 직접 명시했거나 현재 메인
기억 owner가 이미 검증해 제공한 값만 읽는 inherited optional field다. 3.6~4.0 계약이 아직
없거나 coverage가 부족하면 `unknown/unavailable/degraded`로 남기며 3.5가 모델 추론으로
보완하거나 canonical row를 만들지 않는다.

### 5.2a `host_context_reference_evidence.v1`

Go는 actual payload의 Host context에서 이번 실행 계약에 실제 사용한 span만 source-linked
evidence로 만든다. 최소 필드는 request·generation·session·branch fence, payload path·role·
order, exact span/hash, Host가 직접 제공한 source metadata와 `unknown` capability다. 원문 전체를
별도 Host DB로 복사하지 않는다.

entity mention·alias·setting assertion 후보를 만들 수는 있지만 특정 entity 종류 목록, 작품·
인물명, 고정 후보 수, similarity threshold 또는 embedding 점수로 identity를 확정하지 않는다.
source kind가 unknown이면 lore·character card·scenario라고 추측하지 않으며, 이름·별칭·LLM
confidence 하나만으로 Host/reference/session entity를 merge하지 않는다.

3.4의 `/prepare-turn`은 read-only다. 이 evidence는 실제 payload·execution trace의 일부이며 entity
import나 별도 Host registry write를 숨은 side effect로 실행하지 않는다. 안정 entity 생성·link·
rename·split·merge·retire는 3.6 `entity_identity.v1` admission이 원래 turn/effective-input source와
함께 판정한다. Host-only 근거는 setting/reference-defined 후보일 수 있지만 별도 active-final
session source 없이는 등장·경험·현재 상태·관계·knower를 만들지 않는다.

```text
Host payload evidence -X-> session occurrence / experienced event
Host payload evidence -X-> relationship current / body current
Host payload evidence -X-> character knows / turn realization
```

### 5.3 `response_execution_contract.v1`

메인 생성 모델에는 이미 존재하는 Host 원문을 다시 복제하거나 감독관 장문을 그대로 쏟지 않고 다음 실행 역할을
분리한 짧은 계약을 전달한다.

- `must_preserve`: 위치·상태·설정·지식·관계처럼 깨지면 안 되는 현재값;
- `must_respond`: 현재 사용자 입력에서 직접 반응해야 하는 행동·질문·정정;
- `must_account`: 이미 발동해 무시하면 인과가 끊기는 영향;
- `may_advance`: 근거와 user agency 안에서 선택 가능한 다음 변화;
- `hold_allowed`: 회복·대화·관찰·recap·agency 대기처럼 진행하지 않아도 되는 근거;
- `must_not_assert`: 근거 없는 사실, 비밀 누출, user/player 결정, 관계 급변과 과도한 closure;
- `source_refs`: 각 항목을 지지하는 기억·Host Context·원작·세션 source ID.

계약은 raw user input을 재작성하지 않는다. 실제 user message 인접 지원 block으로 넣되 역할과
권한을 명확히 표시하고, 원래 system·user 지시보다 높은 authority를 주장하지 않는다.
3.5 base에는 다층 character depth, trait-domain projection, `relationship_view`,
`voice_behavior_projection`, `world_execution_slice`, `thread_execution_view`를 넣지 않는다.
이 필드는 4.0 evidence와 4.X prerequisite가 준비된 뒤 같은 versioned 계약을 확장해 제공하며,
3.5가 유사 필드를 추론하거나 축약판을 미리 만들지 않는다.

### 5.4 `supervisor_scene_proposal.v2`

감독관 LLM은 `response_execution_contract.v1`을 읽고 다음만 보완한다.

- 현재 인물의 source-backed 동기와 표현상 주의점;
- `may_advance` 안에서 가능한 복수의 전개 후보;
- 캐릭터·말투·설정 fidelity를 잃기 쉬운 지점;
- 이미 실현된 outcome 반복과 단일 thread tunnel vision 방지.

감독관은 새 사실, 필수 사건, user/player 선택, 관계 transition, offscreen canonical event,
thread 해결과 작품 종료를 만들 수 없다. proposal을 채택하더라도 Go가 원래 envelope와 source
refs를 다시 확인한다.

채택은 본문 delivery 허용일 뿐 persistence admission이 아니다. supervisor 결과를
`/storylines/sync`, `/world-rules/sync` 또는 메인 기억 write에 직접 전달하지 않는다. 최종 표시
출력에서 proposal과 비슷한 사건이 발생했더라도 occurrence source와 3.6~4.0의 일반
authority·agency·scope admission을 별도로 검증한다.

3.3~3.5에서는 proposal 자체나 “나중에 3.6~4.0 admission을 받을 후보”를 persistence queue에
쌓지 않는다. 채택된 항목도 현재 request의 execution contract에서만 유효하고 request 종료와
함께 폐기된다. final displayed output의 raw chat/effective-input source 보존은 기존 메인 경로가
계속 담당하지만, proposal-origin metadata와 source refs를 제거해 일반 user/source 사실처럼
세탁해서는 안 된다.

3.3 containment에서 현재 final-output 저장·파생 owner와 table/column을 inventory하고,
supervisor-origin span이 storyline·world rule·memory·관계·thread의 canonical admission으로
이어지지 않음을 증명한다. 3.6 일반 admission 전에는 proposal에서 비롯된 의미 변화를 별도
canonical row로 쓰지 않는다. 기존 3.x 파생 경로가 final source를 처리하더라도 supervisor-origin
lineage를 보존해 direct authority를 거부하거나 proposal-only로 격리해야 한다. 실제 final span은
발생 관찰 근거일 뿐 제안 권한·인과·agency·관계 transition·closure 권한이 아니다.

이 계약은 3.5의 유일한 supervisor proposal base다. 4.X가 추가 동기·활성 인물·세계·진행
계획을 필요로 하면 같은 proposal owner와 호출 경로를 versioned extension으로 확장하고 두
번째 supervisor나 병렬 scene proposal writer를 만들지 않는다. 3.5 base는 current-input/lore
fidelity와 source envelope만 소유하고 4.X 고유 simulation field를 미리 계산하지 않는다.

### 5.5 `guidance_application_trace.v1`

다음을 같은 request ID에서 연결한다.

- guide eligibility와 근거;
- 사용자가 선택한 profile과 실제 적용 의미;
- Host Context·memory source IDs;
- 생성된 execution item과 supervisor proposal 구분;
- item별 full/compact/deferred/suppressed/trimmed 상태와 reason;
- narrative support budget과 실제 사용량;
- 최종 payload span/hash와 placement;
- 최종 출력에서의 이행·누락·위반;
- OFF/ON, 실패·timeout·malformed와 원 payload 보존 상태.
- request/generation/input/branch/Host/backend/guide-mode expected revision과 적용 시 관찰값,
  `applied/stale_rejected/cancelled/superseded/duplicate_ignored` 결과.

payload span/hash와 source 일치는 Go가 결정적으로 계산한다. 최종 출력의 의미상 이행·위반에
LLM 검토가 필요하면 결과는 별도 diagnostic evidence이며 본문 저장·삭제·장기 기억을 막거나
canonical truth를 만들지 못한다. 검토 실패도 이행 성공으로 처리하지 않는다.

### 5.6 로어북 reader 폐기와 Effective Context Compliance

3.3~3.5는 다음 경로를 구현하지 않는다.

- `getCurrentLorebookEntries()` 또는 lore 목적의 `getDatabase()` 호출;
- character/chat/module lore 원문 mirror와 별도 MariaDB registry;
- lore 전용 Chroma collection, semantic activation과 누락 lore 자동 주입;
- keyword·regex·decorator·항목 위치를 Archive Center가 다시 해석하는 RisuAI activation 복제;
- prompt 내용이나 hash로 lore item ID·종류·revision을 만들어내는 fallback.

이 폐기 결정의 이유는 RisuAI가 이미 keyword·constant와 자체 예산으로 로어북을 최종 요청에
조립하기 때문이다. Archive Center가 raw lore 전체를 다시 읽으면 같은 기능을 중복 구현하면서
비활성·조건 불충족·비밀·미래 정보를 조기에 노출할 수 있다. 공식
[`getCurrentLorebookEntries()` API](https://github.com/kwaroran/RisuAI/pull/1450)도 activation 전 raw
snapshot을 반환하므로 이를 현재 요청의 active truth로 사용할 수 없다.

대신 JavaScript는 `beforeRequest`가 전달한 실제 payload와 Host가 직접 제공한 metadata만
관찰한다. Go는 그 effective context에서 이번 응답이 이행해야 할 source-backed constraint를
선별·압축하고, 이미 존재하는 원문을 다시 주입하지 않는다. `beforeRequest`가 실제 최종 조립
payload를 제공하는지는 지원 RisuAI/PocketRisu 환경에서 먼저 live probe로 증명한다. 증명되지
않으면 `host_effective_context_unavailable`로 표시하고 로어북 reader fallback을 추가하지 않는다.

앞으로 raw lore reader를 되살리려면 단순한 품질 기대가 아니라 별도 사용자 요구, 재현된 결손,
RisuAI activation과 다른 결과를 내야 하는 이유, 비밀·조건·lifecycle 보호, 독립 예산과 제거
조건을 갖춘 새 change request와 사용자 승인이 필요하다. 현재 3.3~3.5 문서는 그 확장을
미리 준비하는 table·API·worker·cache를 만들지 않는다.

### 5.7 기존 supervisor-origin 자료의 provenance cutover

앞으로의 direct write만 막아서는 충분하지 않다. 3.3 containment는 지원 기존 DB에서
supervisor/director/cache/overlay가 자동 생성한 storyline·world-rule·guidance row와 direct
user/source-linked row를 가능한 provenance로 inventory한다.

- 직접 source admission을 증명할 수 없는 자동 proposal은 삭제하지 않고
  `legacy_proposal_unverified/proposal_only`로 격리한다. 일반 raw legacy row의
  `legacy_unverified`와 같은 namespace로 합치지 않는다;
- 격리 row는 Host constraint compile, execution contract, canonical state와 3.5 efficacy ground truth에
  사용하지 않는다;
- user가 직접 수정·승인했거나 source/evidence가 검증되는 row는 그 근거를 보존하고 일반
  authority 검증 대상으로 넘긴다;
- provenance를 구분할 수 없는 경우 canonical로 추정하지 않고 row별 coverage gap과 사용자
  검토 surface를 남긴다;
- migration/backfill은 resumable·idempotent하며 restart·reindex가 격리 row를 다시 활성화하지
  못하게 한다.

기존 column으로 이 상태와 read exclusion을 보장할 수 있는지 먼저 재현한다. 부족하면 additive
migration을 3.3 bounded item에 포함하되 새 평행 storyline/world-rule store를 만들지 않는다.
구버전 DB dry run, disposable clone의 중단·재개·재적용, direct-write 차단 후 DB row delta 0과
격리 row payload 부재가 3.3 release evidence다.

### 5.8 경량 production 실행 계약

경량화의 대상은 Archive Center가 추가한 blocking work다. 본문 provider 자체의 생성 시간,
RisuAI가 소유한 hook lifecycle, 외부 플러그인 호출은 같은 trace에서 구분해 관찰하되 Archive
Center가 임의로 생략하거나 순서를 바꾸지 않는다.

`/prepare-turn`은 같은 versioned plan에서 두 projection을 계산할 수 있지만 production 응답에는
다음만 전달한다.

- JS가 active revision fence를 검증하고 실제 payload에 적용하는 ordered block·text/hash·budget;
- UI가 현재 request의 lane 상태·reason·source summary·적용 여부를 표시하는 compact ViewModel;
- release·장애 분석을 원본 evidence와 연결하는 correlation ID와 contract/build version.

전체 retrieval IR, 반복된 raw span metadata, 내부 proof 사본과 JS가 소비하지 않는 중간 계약을
매 production 요청에 무조건 직렬화하지 않는다. 진단 근거를 삭제하는 것이 아니라 backend
trace·기존 진단 surface에 correlation으로 보존한다. compact projection cutover는 지원 JS·UI
consumer inventory, old/new response consumer test와 실제 payload hash parity를 한 packet에서
완료한다. 단순히 key가 커 보인다는 이유로 제거하지 않는다.

저장소 query는 현재 source fence·active state·예산·검색 목적에 필요한 row와 field를 backend에서
선별한다. 전체 row를 가져온 뒤 Go에서 자르는 현재 경로를 그대로 두고 JSON만 줄이는 것은
완료가 아니다. 반대로 최근 row나 고정 top-N만 읽어 오래된 약속·비밀·관계·사건을 놓치는 것도
허용하지 않는다. 기존 retrieval 결과와의 differential fixture, 장기 세션의 old-but-relevant
fixture와 coverage gap을 통해 query pushdown·projection의 의미 parity를 증명한다. 비교는
선택된 text만이 아니라 source/evidence ID, entity·knower, temporal current/history, conflict·
dedup reason, injection order와 budget 상태까지 포함한다. 기준선이 정확히 회상하던 item 하나를
잃고 평균 응답 시간만 개선된 결과는 실패다.

Archive Center 소유 보조 LLM은 Go planner가 source·guide mode·eligibility로 필요하다고 판정한
경우에만 실행한다. OFF, no-support, stale/superseded 요청에는 출력 guide 목적 호출이 없어야
한다. 조건은 작품·장르·모델명·prompt 문구나 고정 complexity 점수가 아니라 versioned source
계약과 실제 적용 항목의 존재로 결정한다. 별도 supervisor endpoint를 JS에서 병렬로 유지해
같은 일을 두 번 하지 않는다.

vector 경로는 같은 turn/source text의 embedding 재사용, 지원 backend의 batch operation과
불필요한 중복 health/read를 우선 줄인다. 캐시를 추가해야 한다면 source hash·embedding model/
collection revision이 key에 포함되고 stale invalidation·크기 제한·관찰 가능한 miss reason이
있어야 한다. 캐시 miss나 Chroma 장애를 빈 recall 성공으로 바꾸지 않는다.

`/complete-turn` 최적화 순서는 다음과 같다.

1. 동일 source의 중복 critic·embedding·upsert 여부를 측정한다.
2. 결과 의미가 같은 호출만 reuse·batch하고 row/vector parity를 확인한다.
3. raw turn/source와 사용자 삭제·reroll·branch fence를 먼저 durable하게 확정한다.
4. 직전 active-final 뒤 즉시 시작한 다음 `/prepare-turn`이 해당 source를 정확한 authority로
   읽을 수 있는 read-your-writes barrier를 증명한다. 파생 memory가 아직 pending이면 검증된 raw
   source-backed equivalent를 사용하거나 필요한 admission 완료를 기다리며, stale memory로
   정상 응답하지 않는다.
5. 파생 작업을 blocking path 밖으로 옮길 필요가 남은 경우에만 MariaDB 영속 outbox,
   idempotency, retry/backoff, restart recovery, delete/cancel ordering과 visible pending/degraded 상태를
   하나의 versioned 계약으로 구현한다.
6. outbox와 read barrier가 모두 준비되지 않은 release에서는 파생 저장을 버리지 않고 동기
   상태를 유지한다.

성능 trace 자체가 새로운 상시 부하가 되어서는 안 된다. 일반 production은 stage duration,
row/byte/call count와 correlation만 낮은 비용으로 기록하고, 큰 proof payload·상세 SQL/IR은
명시적 진단·release fixture에서만 수집한다. UI 상태 확인도 사용자 동작 기반이며 주기적인
health polling을 경량화 해법으로 추가하지 않는다.

## 6. 강도 계약

기존 UI의 `none/weak/medium/strong`을 유지하더라도 의미는 Go의 versioned profile로 다시
정의한다. profile은 모델 등급이나 장르별 prompt가 아니다.

이 profile은 **출력 guide만** 제어한다. RisuAI native Host Context는 Archive Center 설정과
무관하게 Host가 조립한 그대로 유지된다. raw-lore reader·보완 기능은 3.3~3.5에 존재하지 않는다.

### `none`

- 출력 개선용 execution contract와 supervisor proposal을 본문 payload에 넣지 않는다.
- supervisor가 다른 유지보수 목적 때문에 실행되더라도 그 결과를 출력 guide로 적용하지
  않는다.
- 장기 기억·원작·Host의 기존 native payload는 그대로 유지한다.

### `weak`

- 현재 입력 반응과 `must_preserve` 위반 위험이 실제로 있을 때만 짧게 개입한다.
- “거의 보이지 않게”라는 문체 지시가 아니라 필요한 constraint의 완전한 전달을 보장한다.
- 임의 진행 후보는 필수가 아니다.

### `medium`

- `must_preserve`, `must_respond`, `must_account`와 관련 `may_advance`를 명시한다.
- 단순 복기 대신 현재 입력에 대한 실질적 반응을 유도하되 결과 하나를 정답으로 강제하지
  않는다.

### `strong`

- 적용 대상 턴에서 필수 execution item을 모호한 optional prose로 약화하지 않는다.
- 허용된 envelope 안에서 캐릭터·설정·인과가 실제 출력에 드러나도록 명확한 계약을 제공한다.
- 사건 수, 전개 속도, 관계 단계나 결말을 고정하지 않으며 user/player agency를 침범하지
  않는다.

강도는 source authority, 비밀 visibility와 truth를 바꾸지 않는다. `strong`도 없는 근거를
만들 수 없고, `weak`도 확인된 필수 설정을 삭제할 수 없다.

## 7. 독립 예산과 payload 위치

| 예산 | 대상 |
|---|---|
| `max_injection_chars` | 기존 Archive Center 장기 기억·세션 정보 |
| `reference_injection_max_chars` | 보완·단독 공통 원작 자료 |
| `primary_canon_base_max_chars` | 단독 모드 전용 원작 기반 정보 |
| `narrative_support_max_chars` | response execution contract와 채택된 supervisor guidance |

RisuAI가 이미 payload에 넣은 native Host Context 원문은 Archive Center 주입 예산으로 다시 계산하거나
복제하지 않는다. 그 원문에서 압축한 실행 constraint만 `narrative_support_max_chars`를 사용한다.
폐기한 raw-lore index·보완 주입을 위해 `host_context_injection_max_chars`를 미리 예약하거나 기존
장기 기억 예산을 차용하지 않는다.

예산을 하나의 고정 비율로 나누지 않는다. Go가 item 완전성, 현재 relevance와 실제 전체
context 여유로 full/compact/deferred를 결정한다. narrative support가 잘리더라도 장기 기억
예산을 침범해 메우지 않으며, 필수 item 일부가 전달되지 못하면 빈 성공 대신
`guidance_degraded/coverage_gap`을 표시한다.

전체 provider context 상한을 넘을 때에는 raw current input과 기존 system 계약, RisuAI가 이미
조립한 Host Context와 메인 기억 delivery를 먼저 보존하고 Archive Center output guidance가
자기 lane 안에서 축약·유예된다.
한 lane의 잔여 예산을 다른 lane이 자동 차용하거나 동일 text를 두 lane에서 중복 계산하지
않는다. 최종 arbitration과 실제 block order·hash는 Go 하나가 소유한다.

UI는 `Assembled Auxiliary Context`, `Original Work Context`, `Risu Effective Host Context`와
`Output Guidance Context`를 구분한다. 실제 payload에 적용된 text만 Effective Input에서
확인할 수 있어야 한다.

### 3.3 — Source Integrity와 Host Context 관찰 기반

- `message_source_envelope.v1`, `session_bootstrap.v1`, `source_acceptance_lifecycle.v1`을 production
  route의 공통 source spine으로 연결하고 실제 user input·start/system/Host·model output을 분리;
- streaming·display candidate·active final·superseded·deleted와 edit·reroll·branch revision을
  표시 상태 근거로 판정하며 prompt 문자열이나 고정 turn 번호로 대체하지 않음;
- `risu_host_context_snapshot.v1` 계약과 host observation 범위 확정;
- 실제 RisuAI API capability matrix와 actual payload span attribution 범위를 확정;
- chat/character/module 전환·수정·비활성·삭제·복사·분기 뒤 native payload 관찰이 stale source를
  현재 설정으로 재사용하지 않는지 검증;
- Host context에서 entity를 언급하는 actual payload span을 관찰 가능한 source metadata에
  묶되 JS가 source kind·activation·entity kind·identity·merge를 계산하지 않음;
- 현재 supervisor ON/OFF·strength별 실제 호출·directive·payload 적용 경로 감사;
- `postStorylineSync`, `postWorldRulesSync`, supervisor overlay와 maintenance 전달의 직접·간접
  persistence lineage를 감사하고 backend의 supervisor-origin write 거부와 JavaScript 자동
  `apply` 호출 제거를 같은 첫 bounded item에서 완료;
- 지원 기존 DB의 supervisor/cache-origin row를 inventory·격리하고 canonical read·lore
  eligibility에서 제외하는 resumable provenance cutover;
- request/generation/input/branch/Host/backend/guide-mode revision fence와 stale·duplicate 응답 차단;
- `guidance_application_trace.v1`의 eligibility·span/hash·budget·skip/degraded surface 구현;
- OFF에서 출력 guide가 실제 payload에 적용되지 않는 parity gate;
- 현재 고정 count·pressure·장르 prompt·JavaScript policy debt 목록 고정;
- 실제 loaded artifact에서 RisuAI hook 관찰, `/prepare-turn`의 DB/vector/LLM/serialize, payload apply·
  본문 handoff, final 표시와 `/complete-turn`의 critic/write/vector를 분리한 blocking-stage baseline;
- stage별 cold/warm duration 분포, materialized row·response byte·외부 호출 수·payload/hash/row 결과를
  같은 source snapshot에 연결한 performance evidence manifest.

3.3 완료는 로어북 DB를 만들었다거나 supervisor 호출 성공을 표시했다는 뜻이 아니다. 실제
RisuAI observation, native attribution과 OFF parity가 production 경로에서 대조되어야 한다.

3.3의 bounded work item은 다음 순서를 지킨다.

1. current request→supervisor→payload→sync/write lineage를 production trace로 고정한다.
2. backend가 supervisor-origin canonical write를 거부하고 JavaScript 자동 `apply` 호출을
   제거하여 수동 사용자 CRUD와 분리한다.
3. 기존 자동 proposal row를 provenance별로 격리하고 cutover 재적용 parity를 증명한다.
4. source envelope·bootstrap·acceptance lifecycle과 host capability manifest를 포함한
   revision-fenced 공통 request/response DTO를 정의한다.
5. `beforeRequest` payload가 실제 조립된 요청인지 live probe하고, message path·role·span/hash와
   Host가 직접 노출한 metadata만 DTO로 전달한다. source 종류·activation이 없으면 unknown으로
   두며 로어북 reader·registry·Chroma·보완 주입 fallback을 만들지 않는다.
6. Go가 lane 상태와 ViewModel을 반환하고 JS는 관찰·전달·표시만 하게 한다.
7. OFF 경로의 payload hash parity, canonical DB row delta 0과 stale 응답 부재를 negative test로
   고정한다.
8. 교체할 나머지 JS policy 목록, 정확한 제거 owner와 3.4 cutover 조건을 남긴다.

### 3.4 — Active Host Context 전처리와 실행 계약

3.4에는 기존 Host Context 작업을 대체하지 않는 `3.4-MEM` 병행 작업군을 추가한다. 상세
범위·일곱 delivery class·초기 예산·병행 가능 구간·회귀 시험은
[`3.4-memory-delivery-budget-foundation.md`](3.4-memory-delivery-budget-foundation.md)가 소유한다.
Host Context constraint는 `narrative_support_max_chars`, 메인 기억은 `max_injection_chars`를
사용하며 두 예산은 서로 빌려 쓰지 않는다. 두 작업군의 조사·분류·fixture는 병행할 수 있지만
단일 `/prepare-turn` 최종 assembly·order·text/hash·budget cutover는 하나의 Go owner에서
통합한다.

- actual Host Context의 authority·span·중복·현재 응답 relevance 결합;
- actual Host source에서 request-scoped `host_context_reference_evidence.v1`의 entity·alias·identity-link 후보를 만들고
  payload와 3.6 handoff에 사용하되 `/prepare-turn`과 JS가 session entity를 쓰지 않음;
- `host_context_support_plan.v1`과 `response_execution_contract.v1`을 기존 `/prepare-turn`의 유일한
  versioned planner 안에 구현하며 두 번째 최종 planner를 만들지 않음;
- `narrative_support_max_chars`의 Go owner 확정. 이미 존재하는 Host 원문은 재주입하지 않음;
- raw user input을 보존한 채 인접 지원 block을 실제 payload에 적용;
- `supervisor_scene_proposal.v2`가 Go envelope 안에서만 제안하도록 변경;
- 3.3에서 차단한 supervisor proposal direct write가 다른 overlay·maintenance·compatibility
  경로로 우회되지 않는지 검증하고, 최종 occurrence도 3.6~4.0 일반 admission을 거쳐야만
  저장되도록 경계 확정;
- strength profile을 optional prompt 문구가 아닌 적용 역할·coverage 계약으로 전환;
- 적용할 자료가 없는 정상 skip과 검색·LLM·예산 실패 분리;
- `/prepare-turn`에서 JS apply와 UI에 필요한 compact production projection만 반환하고 대형
  retrieval/proof 중간값은 correlation 기반 진단으로 분리;
- session 전체 list 후 절단 대신 source/revision/relevance/active-state와 budget을 이용한 query
  projection을 적용하되 old-but-relevant 기억의 differential parity를 증명;
- OFF/no-support/stale 요청에서 Archive Center 출력 guide 목적 보조 LLM 호출이 0인지 검증.

3.4 완료는 schema나 shadow trace만으로 인정하지 않는다. native-present 설정에서 압축한
constraint가 ON payload에 실제 포함되고 OFF에는 guide block이 없으며, native Host Context
원문은 다시 주입되지 않아야 한다. actual payload에 없는 로어북 자료를 별도 source에서 찾아
자동 활성화해서도 안 된다.

3.4의 cutover는 backend plan 추가와 JavaScript 축소를 하나의 bounded item으로 묶는다.
compatibility window가 불가피하면 지원 backend version, 비교 대상, 사용자에게 보이는 상태,
owner와 제거 조건을 먼저 적고 기한 없는 fallback을 금지한다. supervisor proposal을 직접
저장하던 호출이 남아 있으면 `GUIDE-NO-DIRECT-WRITE`와 3.4를 완료로 표시하지 않는다.

### 3.5 — Host-grounded Output Fidelity 대형 마일스톤

- actual Host Context 관찰→native attribution→execution contract→실제 payload→final output 전체 E2E;
- actual Host source span의 entity·alias evidence가 설정상 이름·동일성·설명 이행에 실제 기여하고 수정·비활성·
  삭제·분기 뒤 stale binding이 사라지며 canonical session entity row가 부수 효과로 생기지
  않는 E2E;
- 로어북 위반, 현재 입력 미응답, 전달된 source의 화자·지식·관계 constraint 위반과 과잉
  주도 진단. 다층 캐릭터 해석·단일 특성 환원·대사 복사·친밀감·장르 압력은 4.X가 별도
  fixture·UI·완료 증거를 소유하며 3.5가 계산·표시하지 않음;
- eligible 턴의 OFF/weak/medium/strong 비교와 의미 없는 턴의 no-forced-difference 검증;
- 출력 guide ON에서 설정 이행과 첫 출력 채택이 개선되는지 라이브 비교;
- 강한 guide에서 user action 강제·불필요 escalation·단일 thread 집중·성급한 closure 비퇴행;
- 장애 주입, 기능 OFF, 삭제·리롤·분기·재시작과 기존 기억 저장·주입 회귀;
- 동일 source embedding과 vector upsert의 reuse·batch, 불필요한 중복 상태 확인 제거와
  `/complete-turn` blocking-stage 단축. 비동기 파생 처리는 durable source·영속 outbox·재시작
  복구·삭제/취소 순서·pending/degraded 표시가 함께 검증된 경우에만 허용;
- 짧은 세션과 장기 세션, cold/warm 실행에서 생성 전후 stage latency·response byte·DB row·외부
  call count 분포를 baseline과 비교하고 payload/hash/row·기억·원작 DB parity를 동시 검증;
- UI에서 Risu Effective Host Context와 Output Guidance의 source·예산·적용·위반 근거 표시.

3.5는 모든 requirement가 실제 production payload와 라이브 evidence에서 검증되기 전에는
완료로 표시하지 않는다. 일부 모델·장르·언어·happy path의 개선을 전체 완료로 보고하지
않는다.

3.5는 생성 후 자동 재작성·무한 리롤을 도입하는 버전이 아니다. 생성 후 검토는 설정 위반,
현재 입력 미응답, 지식 누출, agency·closure 위반과 guide 이행을 근거와 함께 진단한다. 기본
경로에서 본문을 임의 교체하거나 canonical state를 고치지 않으며, 고급 재작성과 모델 적응은
4.X의 별도 승인 범위다.

`no-forced-difference`는 생성 문장의 byte equality나 고정 품질 점수가 아니다. 같은 source
snapshot에서 guide eligibility가 비어 있으면 OFF와 ON의 **output-guidance item set·block
span·budget usage가 모두 비어 있고**, native Host Context·메인 기억·raw input block hash가 동일해야
한다는 deterministic payload 계약이다. 확률적 본문이 우연히 달라진 사실은 실패도 성공도
아니다.

라이브 비교는 production DB를 오염시키는 연속 reroll로 수행하지 않는다. 같은 source
snapshot·provider parameter와 가능한 경우 같은 seed를 사용한 격리 branch/replay에서 OFF와
각 profile의 첫 출력을 수집한다. seed가 없으면 반복 cohort와 실제 사용자 채택·리롤·위반
사유를 분리 보고하며 단일 고정 score·threshold로 합격을 만들지 않는다. 비교 출력과
review는 diagnostic evidence이며 canonical memory나 다음 요청 source로 되먹이지 않는다.

### 8.1 공통 work packet 규칙

버전 하나를 한 번에 구현하지 않는다. 아래 packet은 각각 독립적인 변경 목록·owner·테스트와
evidence manifest를 가진다. 선행 packet의 exit gate가 열리지 않으면 뒤 packet의 코드는
작성할 수 있어도 production cutover나 완료 선언을 하지 못한다.

각 packet은 최소한 다음을 기록한다.

- 바꾸는 production 함수·route·table/column·JS 호출부와 바꾸지 않는 경계;
- entry fixture와 현재 실패/성공 baseline, 예상 behavior delta;
- 양성·음성·mutation/metamorphic·lifecycle·fault fixture 중 해당되는 실제 조합;
- 신규 backend owner와 같은 packet에서 제거할 기존 JS/병렬 owner;
- 기존 사용자 DB clone/upgrade와 기능 OFF·provider 없음·backend 장애의 비퇴행 결과;
- 실제 loaded artifact hash, request/row/payload correlation과 남은 open risk;
- `preparatory`, `implemented_unverified`, `release_gate_verified` 중 정확한 상태.

#### 3.3-C 구현 증거 — 2026-07-21

상태는 `implemented_unverified`다. source tree의 production `/prepare-turn` 연결과 전체 Go/Node
회귀 테스트는 통과했지만, 실제 loaded artifact·RisuAI live hook·3.3-D/E lifecycle fence와
3.3-F OFF payload parity는 아직 이 packet의 검증 증거가 아니다.

- 요청 계약: `message_source_observation.v1`과 `host_source_capabilities.v1`. JavaScript는
  session/request/message index/observed role/payload path와 명시적으로 버전화한 raw-input 관찰
  hash만 전달한다. chat/branch/generation/revision/displayed-output/Host source ID·scope·revision은
  transport field로 존재하지만 Host가 제공하지 않으면 생략하며 Go도 추론하지 않는다.
- production 연결: `onBeforeRequest`가 하나의 orchestration request ID를 `/prepare-turn` 호출 전에
  만들고 `tryPrepareTurn` request body에 두 observation DTO를 전달한다. Go의
  `handlePrepareTurn`은 generated legacy DTO를 수정하지 않는 확장 request로 decode하고, 정상
  response와 migration-source-lock response 모두에 `prepare_source_projection.v1`을 반환한다.
- Go owner: required capability는 `message_position`, `message_role`, `request_correlation`, `session_identity`,

  contract compatibility, 정규화와 lane status/reason은 Go만 계산한다.
- stable status/reason: `eligible/source_observation_eligible`,
  `not_applicable/source_observation_not_applicable`, `empty/source_observation_empty`,
  `deferred/source_observation_deferred`,
  `degraded/source_observation_optional_capability_missing`,
  `failed/source_observation_malformed` 또는 validation-specific stable reason,
  `incompatible/source_observation_contract_missing|source_observation_contract_incompatible|source_observation_required_capability_missing`.

- 격리: source lane의 `degraded`, `failed`, `incompatible`는 legacy main prepare payload를 막거나
  `ok/ready/skipped/empty`로 바꾸지 않는다. JavaScript는 `source_contract`를 bundle/runtime detail에
  그대로 전달하고 별도 source authority·selection·budget·prompt fallback을 만들지 않는다.
- 테스트 증거: supported/unsupported version, required/optional capability 누락,

- 미구현 경계: actual user input·복수 bootstrap 판정은 3.3-D, streaming/candidate/active-final,

#### 3.3-D 구현 증거 — 2026-07-21

상태는 `implemented_unverified`다. 실제 사용자 입력과 시작 메시지 판단을 Go가 소유하도록
`/prepare-turn`을 판단 단계와 본 처리 단계로 나눴다. JavaScript가 prompt 문구를 보고 실제
입력을 정하거나 시작 메시지를 사건 기억으로 승격하지 않는다.

- JavaScript는 input hook의 실제 문자열, 공식 active chat의 메시지 역할·위치·노출 ID,
  `beforeRequest`가 받은 payload 경로와 hash, RisuAI가 노출한 첫 인사·대체 인사·선택 index만
  관찰해 전달한다. input hook은 중간 관찰로 표시하며 최종 전송 payload나 원문 source라고
  과장하지 않는다.
- Go `current_input_decision`은 현재 active chat의 실제 user와 input-hook 관찰을 hash·위치·역할로
  대조한다. system/preset scaffold가 payload에서 user role처럼 직렬화되어도 실제 current user를
  덮어쓰지 못한다. 관찰이 없거나 모순되면 입력을 추측하지 않고 store read·기억 주입을 시작하지 않는다.
- `session_bootstrap.v1`은 같은 본문의 시작 메시지가 여러 개여도 Host message index 경계를
  보존한다. RisuAI가 선택 index를 노출한 경우에만 첫 인사 또는 대체 인사를 선택하며, 잘못된
  index는 다른 인사를 추측하지 않고 `unverified`로 남긴다.
- 시작 메시지는 Host/bootstrap source로만 보존한다. prior assistant response, 확정 사건,
  canonical write 근거가 아니며 의미 있는 실제 user 입력 전에는 memory read와 injection을 허용하지 않는다.
- production route의 판단-only 호출에서 DB·Chroma write 0을 확인하고, 전체 호출에서는 Go가
  승인한 실제 입력만 검색·조립으로 넘긴다. 동일 문구의 복수 시작 메시지 보존, scaffold 오인 방지,
  malformed input-hook 격리, 미검증 입력의 store read 0, 번들 Node runtime 관찰을 회귀로 고정했다.

#### 3.3-E 구현 증거 — 2026-07-21

상태는 `implemented_unverified`다. source tree의 계약·production 연결·자동 회귀 테스트는
완료했지만, 실제 loaded package에서 스트리밍·리롤·편집·삭제·분기 전체를 재현한 release
evidence는 3.3-G 전까지 완료로 간주하지 않는다.

- 공식 Host 기준: 2026-07-21 확인한 공식 RisuAI upstream commit
  `4f0568ec2be7f93e575d0ed88949de3c3082931b`의 `Chat`, `Message`,
  `MessageGenerationInfo`, request/streaming/reroll/edit/delete 구현을 기준으로 삼았다.

  `Message.chatId`, `Message.time`, `Message.generationInfo.generationId`만 관찰한다.
  공식 message revision은 없으므로 `revision_state=not_exposed_by_risuai`로 전달하며 revision을
  Host 값인 것처럼 만들지 않는다.
- adapter 계약: `source_acceptance_observation.v1`은 현재 활성 chat의 메시지 위치, 실제 역할,

- Go owner: `source_acceptance_lifecycle.v1`이 active chat의 현재 메시지, streaming 여부,
  전송된 저장 본문 hash, generation/message identity를 검증하고 backend revision을 계산한다.
  streaming, 비활성 위치, 본문 불일치, rollback 이후 관찰과 이미 superseded된 revision은
  canonical DB·derived artifact·vector write 전에 거부한다. active-chat backfill의 과거 메시지는
  기존 명시적 backfill metadata가 있는 경우에만 현재 branch의 관찰된 메시지로 허용한다.
- 늦은 작업 fence: 새 revision 승인 또는 기존 `/rollback/{turn_index}` 삭제가 진행 중인 이전
  `/complete-turn` worker context를 취소한다. critic 뒤에도 current revision을 다시 비교하므로
  늦은 extractor·embedding·vector 결과가 최신 결과를 계속 덮어쓰지 못한다. 삭제 무효화는
  기존 rollback 경로에 결합되며 새 watcher나 별도 저장 경로를 만들지 않는다.
- 재시도와 idempotency: candidate/streaming 거부는 complete-turn 완료 cache에 기록하지 않는다.

  보존된다.

  adapter는 새 계약을 필수로 보내며, 거부·보조 기능 장애는 사용자에게 표시된 본문을 바꾸거나
  메인 응답을 막지 않는다. 메인 기억 schema, 원작 DB, 감독관 입력·출력 경계와 기존
  삭제·리롤 저장 경로는 새 병렬 구현으로 교체하지 않았다.
- 자동 증거: streaming 쓰기 0, active final 승인, Host revision 미노출 보존, backfill 범위,
  reroll/delete fence, stale queue 폐기, 후보 거부 idempotency cache 비오염, 새 revision의 이전 worker
  취소를 단위 테스트로 고정했다. 기존 complete-turn/rollback 묶음, JS route smoke와 번들 Node
  문법 검사를 함께 통과시킨다.

#### 3.3-E 실제 RisuAI 피드백 재수정 — 2026-07-22

초기 구현은 `source_acceptance_not_current_active_tail`을 과도하게 반환해 일반 생성과 PocketRisu
리롤 모두 원문은 대기 상태에 놓이고 파생 자료는 큐에서 늦게 생성되는 문제가 있었다. 실제
RisuAI를 기준으로 반복 재현한 뒤 다음 경계를 보정했다.

- active final은 단순히 배열의 마지막 원소인지로 판정하지 않는다. 현재 user 기준점 뒤의 실제
  assistant이며, 뒤에 turn이 아닌 Host metadata가 있는 경우에도 현재 논리 턴의 assistant tail로
  인정한다. 그 뒤에 새 user/assistant turn이 있으면 이전 응답은 여전히 거부한다.
- native `afterRequest` 직후 active chat 반영이 아직 끝나지 않았으면 candidate를 확정 저장하지
  않고 실제 active assistant 확인을 기다린다. 확인 뒤 queue payload의 assistant 본문과 source
  observation을 화면의 현재 final로 다시 구성해 원문과 파생 처리가 같은 결과를 사용하게 한다.
- 사용자가 DB의 마지막 턴을 지우고 같은 turn index에서 새 응답을 만들거나 리롤해도, 새
  generation/revision이 active final이면 기존 번호의 최신 결과로 교체한다. 삭제 fence보다 오래된
  worker는 계속 막고, 새 generation까지 영구 차단하지 않는다.
- queue 복원 때 credential을 저장 payload에 복제하지 않는다. 현재 runtime 설정을 다시 결합하고
  source observation·logical user anchor는 보존한다.
- 일반 생성, assistant 뒤 비턴 metadata, 연속 리롤, active Host final로 queue 재구성, persisted
  queue 복원, 이전 worker 지연 완료를 자동 회귀로 고정했다. 실제 확인에서는 원문·요약·개체 생성,
  연속 리롤 교체와 새로고침 뒤 중복 턴 부재가 확인됐다.

#### 3.3 구현 종료·3.4 인계 — 2026-07-22

3.3의 기능 구현은 `implemented_unverified`로 닫고 3.4로 넘어간다. 실제 RisuAI에서 일반 생성,

확인했다. 리롤 생성 실패 때 기존 확정 응답 유지와 배포 환경 전체 회귀는 자동 시험 근거만
있으므로 release gate 완료로 표기하지 않는다. 전용 Host 신호가 없는 수동 출력 편집 감시는
위 절의 후속 보류 결정을 유지한다.

종료 범위에는 supervisor canonical 직접 쓰기 차단, source/capability DTO, 실제 사용자 입력과
복수 시작 메시지의 Go 판정, active-final acceptance와 revision fence, PocketRisu형 동일 논리 턴

raw 선저장·파생 재시도, Ollama loopback, Table Read 제거, Build 42/43 경계 수정도 포함한다.
JavaScript 경량화 측면에서는 supervisor 자동 sync 62줄과 사용하지 않는 Table Read 경로를
제거했고, 수동 편집을 위한 반복 watcher나 버튼 감시를 추가하지 않았다.

3.4 진입 직전에 적용한 임시 전체 주입 예산 보정도 다음과 같이 고정한다.

- 자동 예산 단계는 추정 토큰 `4,500 → 9,000 → 13,500 → 18,000`, 문자 기준

- Go가 이미 제목을 포함해 반환하는 `[Persona Recollection]`과
  `[Character Private Recollection]`에는 JavaScript가 같은 제목을 다시 붙이지 않는다.
- 이 보정은 3.4의 일곱 자료 종류별 예산을 구현한 것이 아니다. 3.4-D/E에서 Go 단일 계획으로
  교체할 임시 전체 상한이며, RisuAI 관찰·전달만 담당하는 JavaScript에 분류 정책을 추가하지 않는다.
- 번들 Node 구문 검사, 관련 Go 시험, 전체 `go test ./... -count=1`, `git diff --check`를 통과했고
  실제 한 턴에서 추가 예산 반영과 제목 1회 출력을 확인했다.

### 8.5 현재 production debt와 제거 owner

이 표는 새 기능 목록이 아니라 3.3 baseline에서 실제 호출 여부를 재현하고 해당 release에
제거·축소할 owner를 고정하는 inventory다. line number가 아니라 함수·route와 behavior test로
추적한다.

| 현재 owner | debt | bounded 제거·대체 gate |
|---|---|---|
| `Archive Center.js/runSupervisor` + `POST /supervisor` | guide OFF에도 별도 supervisor 호출·결과 경로가 남을 수 있음 | 3.3 OFF no-op/row-delta gate, 3.4에서 생성 adapter는 단일 `/prepare-turn`만 호출 |
| `Archive Center.js/postStorylineSync`, `postWorldRulesSync`와 호출부 | supervisor proposal을 `apply` mode로 canonical 후보에 전달 | 3.3 첫 containment에서 자동 호출·호출 전용 계산 제거, backend supervisor-origin write 거부; 수동 CRUD는 보존 |
| `go-service/internal/httpapi/group_proxy.go` | supervisor pack strength를 `weak`으로 고정해 UI·trace·실제 호출 의미가 갈릴 수 있음 | 3.4 Go versioned strength profile 하나로 대체하고 literal 제거 mutation test |

숨기면 제거로 인정하지 않는다.

## 9. 필수 검증 시나리오

- guide OFF에서 supervisor가 별도 유지보수 호출을 하더라도 output directive가 payload에
  들어가지 않는 경우;
- guide ON이지만 관련 설정·기억·진행 의무가 없어 OFF와 출력 차이를 강제하지 않는 경우;
- first/start-only·복수 start message·prior assistant 부재, reroll 직후·edit/delete·branch switch와
  표시되지 않은 candidate에서 prior active-final을 창작하거나 stale output으로 대체하지 않는 경우;
- assistant 형식의 start message도 `prior_response_source=absent`를 유지하고 별도 bootstrap/Host
  source로만 eligibility를 받는 경우;
- actual payload에 이미 있는 Host 설정에서 실행 constraint를 만들되 같은 원문을 다시 주입하지
  않는 경우;
- Host가 source 종류·ID·activation을 노출하지 않으면 prompt 문구·위치·hash로 lore라고
  분류하지 않고 `unknown`을 유지하는 경우;
- 지원 Host의 `beforeRequest`가 최종 조립 context를 제공하지 않는다면
  `host_effective_context_unavailable`을 표시하고 lore API·전체 DB fallback 없이 메인
  생성·저장·삭제·장기 기억이 계속되는 경우;
- production route가 `getCurrentLorebookEntries`, lore 목적 `getDatabase`, Host registry·Chroma
  write를 호출하지 않는 경우;
- 선택된 Host setting의 이름·별칭·설명이 `host_context_reference_evidence.v1`과 payload에서
  정확한 source span을 유지하고 3.6 identity handoff에 사용 가능한 경우;
- 같은 surface/alias가 Host setting, session entity와 원작 reference entity에 동시에 있어도
  namespace를 유지하고 이름·vector·LLM confidence만으로 자동 merge하지 않는 경우;
- Host context가 과거 사건·관계·신체 상태·비밀 지식을 서술해도 reference assertion과 entity 후보만
  생기고 session event·relationship current·body current·knower·turn realization row delta는
  모두 0인 경우;
- 이후 별도 active-final session source에서 실제 mention/occurrence가 생기면 Host evidence는
  보조 identity 근거로만 쓰이고 occurrence는 새 session source를 root로 admission되는 경우;
- 사용자가 Host setting과 다른 현재 세션 분기를 명시해 세션 변화가 우선하는 경우;
- request·branch·payload revision 변경과 restart 뒤 과거 Host evidence가
  현재 설정으로 재사용되지 않고 독립 session 근거가 있는 entity는 보존되는 경우;
- NPC만 아는 비밀을 다른 인물이 알지 못하도록 knowledge boundary를 전달하는 경우;
- weak도 필수 continuity constraint를 누락하지 않고 strong도 user/player 결정을 강제하지
  않는 경우;
- 조용한 대화가 정당하지만 기존 위협·의무를 삭제하지 않아야 하는 경우;
- source-backed 갈등·거절·배신·관계 변화가 안전 명목으로 무색해지면 안 되는 경우;
- 감독관 proposal의 사건·관계·결말이 final output을 경유해 canonical truth로 세탁되지
  않는 경우;
- final displayed output 저장 뒤에도 supervisor-origin span·source refs가 보존되고 3.6 일반
  admission 전 파생 storyline·world rule·memory·relation·thread write가 생기지 않는 경우;
- guide strength와 관계없이 supervisor 결과 자체가 storyline·world rule·memory에 직접
  `apply`되지 않고 일반 admission 전에는 write count가 증가하지 않는 경우;
- 생성 adapter가 `/prepare-turn`과 `/supervisor`를 두 최종 planner로 함께 호출하지 않고,
  채택된 proposal item이 검증된 execution contract 안에 한 번만 나타나는 경우;
- 미채택·요청 종료 supervisor proposal이 임시 DB·queue·다음 턴 cache에 남지 않는 경우;
- 느린 request A 뒤 request B, reroll·delete·branch switch·Host revision 변경·guide OFF가
  발생했을 때 A 결과가 payload·cache·write를 바꾸지 않고 stale 상태로 남는 경우;
- 같은 guidance 응답이 재시도·중복 도착해도 한 번만 적용되고 현재 trace를 덮지 않는 경우;
- backend timeout/unreachable 중 active request fence가 끝나면 transport packet을 다음 턴에
  재사용하지 않고, queue overflow·retry 실패가 JS policy fallback이나 정상 skip으로 바뀌지
  않는 경우;
- JS volatile transport queue의 packet이 Go reprocess/outbox에 들어가지 않고, Go 영속 job도
  live guidance 결과를 JS에 재적용하지 않는 경우;
- 구버전 supervisor-only storyline·world-rule·director cache가 upgrade 뒤 payload나 canonical
  source가 되지 않으며 검증 가능한 user/source-linked row는 보존되는 경우;
- 예산 부족 시 일부 guide가 조용히 사라지지 않고 coverage gap으로 남는 경우;
- `narrative_support_max_chars`를 최대로 올려도 `max_injection_chars`가 줄거나 두 lane이 자동
  차용하지 않고, provider 상한에서는 각 lane 내부 축약·유예와 누락 범위가 보고되는 경우;
- Host Context·supervisor 실패에도 기존 기억 주입과 본문 생성·저장·삭제가 계속되는 경우;
- 특정 작품명·장르명·인물명·문구·고정 점수·개수·turn 조건을 제거하거나 바꿔도 계약이
  동일하게 작동하는 mutation fixture.
- actual Host source의 entity 언급 수·노출 metadata·alias 분포를 바꿔도 고정 top-N·type whitelist·similarity
  threshold가 silent omission이나 merge 권한으로 작동하지 않고 coverage가 입력 evidence와
  일치하는 property fixture.
- 같은 source snapshot의 full diagnostic plan과 compact production projection에서 JS 적용
  text/order/hash/budget, UI lane 상태·reason과 DB row delta가 일치하고 production 응답에
  JS/UI 미소비 대형 IR·raw proof 사본이 포함되지 않는 경우;
- 실제 장기 세션 분포를 대표하는 짧은·중간·긴 snapshot에서 total historical row가 늘어도
  `/prepare-turn` materialized row와 response byte가 무제한 비례 증가하지 않으며, 오래된 관련
  약속·비밀·사건은 계속 검색되는 경우;
- guide OFF/no-support/stale 요청에서 Archive Center 출력 guide 목적 LLM call·payload item·write가
  모두 0이고, 필요한 eligible 요청의 호출을 속도 명목으로 생략하지 않는 경우;
- 동일 source text의 embedding·upsert batch/reuse 전후 recall 결과·collection revision·MariaDB
  evidence와 오류 분류가 일치하는 경우;
- `/complete-turn` 도중 process 종료·재시작·provider timeout·Chroma 장애·delete/reroll/branch가
  발생해도 raw final source가 유실되지 않고 파생 row/vector가 중복·부활하지 않는 경우;
- final 표시 직후 다음 user turn이 시작되어도 직전 active-final의 사건·약속·상태 변화와
  인물별 지식 경계가 파생 작업 pending 때문에 누락되거나 이전 상태로 회귀하지 않는 경우;
- 경량화 전에는 정확히 회상되던 오래된 기억, 날짜·상태·관계·비밀·화자 귀속이 경량화 뒤에도
  동일 source/evidence와 authority로 검색·주입되고 거짓 양성이나 다른 인물의 지식 누출이
  늘지 않는 경우;
- UI를 열어 두어도 상태 확인을 위한 주기적 health polling이 생기지 않고 사용자 동작 또는 실제
  request에 필요한 확인만 수행되는 경우;
- 같은 loaded artifact와 snapshot에서 cold/warm stage 분포를 비교하며 한 번의 최솟값이나
  고정 ms threshold로 성능 완료를 선언하지 않는 경우.

| `/prepare-turn` 응답·DB 조회가 세션과 함께 무제한 증가 | `3.3-PERF`, `3.4-PERF` stage/row/byte baseline과 old-but-relevant differential fixture | total history 증가에 production materialization이 무제한 비례하거나 compact/full의 plan·payload·UI·row parity가 깨짐 |
| 속도를 위해 필요한 기억·호출·저장을 조용히 생략 | `3.4-PERF`, `3.5-PERF` eligibility·payload/hash/row/vector parity와 fault/restart fixture | eligible item·raw/final source·canonical row가 사라지거나 failed/pending을 success/ready로 표시함 |
| final 뒤 파생 작업이 중복되거나 재시작에서 유실 | `3.5-PERF` complete-turn idempotency·outbox·delete/reroll/branch fixture | 같은 source의 중복 row/vector, 삭제된 source의 부활, 복구 불가 pending 또는 process-local queue 유실이 발생함 |
| 경량화 뒤 장기 기억 정확도·회상 품질이 낮아짐 | `3.4-PERF`, `3.5-PERF` 항목별 extraction→admission→retrieval→injection differential과 old-but-relevant/knower/time fixture | 이전에 정확했던 item 누락, 거짓·stale 상태·잘못된 entity/knower 증가 또는 평균 점수로 개별 퇴행을 숨김 |
| 직전 턴 파생 작업이 끝나기 전에 다음 턴이 시작 | `3.5-PERF` immediate-next-turn read-your-writes·restart fixture | active-final source가 다음 prepare에서 누락되거나 stale snapshot을 ready/complete로 제공함 |
| 성능 관측 자체가 상시 부하를 만듦 | `3.3-PERF`, `3.5-PERF` idle/UI-open call trace | 사용자 동작과 request가 없는데 health/diagnostic polling 또는 대형 proof 직렬화가 반복됨 |

이 matrix에서 탐지할 수 있는 결함을 라이브 사용자 보고 이후에 처음 발견하면 해당 packet의
fixture 또는 release gate 누락으로 기록한다. 사용자의 주관적 품질 피드백은 별도로 존중하되,
재현 가능한 source·lifecycle·upgrade·package 오류와 섞어 “모델 편차”로 처리하지 않는다.

## 10. 평가와 완료 증거

단일 총점이나 단순 텍스트 차이로 출력 개선을 판정하지 않는다. 적어도 다음을 분리한다.

- current input에 대한 실질적 반응 누락;
- 로어북·세계 규칙·세션 분기 위반;
- 전달된 source에 대한 인물별 지식 누출과 명시적 화자·호칭·말투 constraint 위반;
- 전달된 `already_realized` source의 단순 복기·재연;
- source-backed 갈등·대가·관계 변화를 보수적으로 누락한 경우;
- 근거 없는 escalation·관계 변화·user/player 행동 강제;
- 한 thread 해결을 전체 이야기 종료로 확대;
- 첫 출력 채택, 리롤, 삭제와 사용자 피드백;
- 입력·감독 출력·본문 출력 비용과 지연;
- 생성 전 `/prepare-turn`의 DB query·materialization, vector health/embed/search, 보조 LLM,
  serialize/transfer/parse, payload apply와 본문 handoff 지연;
- final 표시 뒤 `/complete-turn`의 critic, raw/canonical write, embedding, vector upsert와 완료 지연;
- stage별 cold/warm p50·p95와 tail sample, materialized row·response byte·외부 call 수. 이는 관찰
  통계이며 작품·모델별 고정 합격 score로 사용하지 않음;
- guide가 필요했던 eligible 턴의 호출·적용·실패·skip 정확성;
- 메인 장기 기억과 원작 DB의 저장·검색·주입 비퇴행.

완료 evidence에는 다음이 필요하다.

- source commit, build/package와 실제 loaded artifact hash;
- actual Host payload span/hash와 직접 노출된 source metadata→`host_context_support_plan.v1`→execution item lineage;
- guide profile, eligibility, item hash와 actual payload span/hash;
- final displayed output에서 item별 이행·누락·위반 correlation;
- OFF/ON same-input 비교와 no-relevant-support 대조;
- negative/mutation, timeout·malformed·budget·rollback·delete fixture;
- 실제 RisuAI·MariaDB·Chroma 경로와 지원 OFF 비퇴행;
- 동일 snapshot의 baseline/optimized stage distribution과 response/query projection 차이,
  old-but-relevant retrieval·payload/hash/row/vector parity;
- 경량화 전후 memory extraction·source/evidence·admission·dedup/conflict·current/history·entity/
  knower·retrieval·최종 injection의 item-level differential과 각 변경 reason;
- 비동기 파생 경로가 있으면 durable raw source, outbox idempotency·restart/retry/backoff·delete/
  cancel ordering, immediate-next-turn read barrier, pending/degraded UI와 최종 row/vector 수렴 evidence;
- requirement별 `open/blocked/preparatory/implemented_unverified/release_gate_verified` 상태.

## 11. 하드코딩·축소 구현 금지

다음을 production 정책이나 완료 대체물로 추가하지 않는다.

- 특정 작품·장르·인물·세력·모델명과 예시 출력 문구;
- 고정 required outcome·forbidden move·storyline·character·thread 수;
- pressure·quality·risk·similarity의 전역 고정 점수와 threshold;
- 턴당 사건 수, beat 수, 전개 cadence와 ending phrase detector;
- prompt 문구나 언어별 키워드만으로 guide eligibility·장면 유형·성공을 판정;
- JavaScript의 별도 strength·budget·selection·prompt assembly 정책;
- OFF에서도 directive를 주입하면서 suffix만 제거하는 명목상 비활성;
- 모든 턴을 단순·safe·hold로 판정하거나 모든 guide를 optional prose로 약화;
- 경고·trace·shadow만 만들고 실제 payload 적용을 출력 개선 완료로 보고;
- 테스트 통과용 canned response, 빈 성공과 provider 실패의 정상화;
- 특정 장비에서만 맞는 고정 ms·row·payload-size threshold를 보편적 성능 완료 조건으로 사용;
- 필수 기억 검색·보조 호출·raw/canonical 저장·vector upsert를 조용히 생략하거나 success를 먼저
  반환해 지연만 낮추는 구현;
- 평균 지연이나 단일 품질 총점이 좋아졌다는 이유로 개별 기억의 누락·거짓 양성·stale 상태·
  entity/knower 오류·시간 역전을 허용하는 구현;
- 최근 N·고정 top-N·고정 후보 수로 materialization을 줄이고 오래된 관련 기억 누락을 허용;
- 상시 health polling, 무제한 cache·process-local write queue와 진단 proof의 production 상시 반환.

작업은 bounded slice로 나눌 수 있지만 3.5 목표를 “현재보다 약간 나아진 감독관”으로
축소하지 않는다. 완료 목표는 **필요한 턴에서는 체감 가능한 근거 기반 출력 개선을 만들고,
필요하지 않은 턴과 user agency에는 불필요하게 개입하지 않는 전처리 계약**이다.

## 3.4-MEM-D/E 진행 기록 — 2026-07-22

`3.4-MEM-D`와 `3.4-MEM-E`는 `implemented_unverified` 상태다. Go `/prepare-turn`이 사건·최근 기억, 인물 객관 상태, 인물별 주관 기억·관계, 물건·장소·세계 상태, 비밀·정체 보호, 미해결 목표, 직접 근거를 별도 예산으로 선택한다. 비밀 보호 지침은 실제 기억 목록에서 분리되며, Go가 `memory_delivery_plan.v1`의 최종 순서·내용·예산을 확정한다. JavaScript는 RisuAI 전달과 설정 저장, 분리된 미리보기 표시만 담당한다.

세부 기본값, 남은 공간 차용 규칙, 0 값 처리, 실제 RisuAI 검증 조건은 `3.4-memory-delivery-budget-foundation.md` 9절을 기준으로 한다. 실제 RisuAI 한 턴에서 분리 표시와 최종 payload를 확인하기 전에는 완료로 올리지 않는다.

## 3.4-MEM-F 진입 전 차단 항목 — 2026-07-22

분리된 최종 입력을 실제 장기 세션 자료로 확인한 결과, 예산 분류는 동작하지만 전달 내용의
밀도와 현재 장면 관련성은 아직 release gate를 통과하지 못했다. 상세 근거와 통과 조건은
`3.4-memory-delivery-budget-foundation.md` 10절이 소유한다.

- 예산을 채움 목표로 사용하지 않고 관련 자료가 부족하면 남겨 둔다.
- episode의 동일한 `memory`·`key_event`, 직접 근거의 같은 문장, 상태·세계 규칙의 이중 표현을
  최종 전달 전에 제거한다.
- `Input Context`는 오래된 직접 근거보다 직전 장면과 현재 인물·행동을 먼저 보존한다.
- 자료 종류 사이 중복을 제거하되 직접 근거, 객관 상태, 사건, 주관 해석, 비밀 보호의 권한과
  의미를 서로 섞지 않는다.
- 같은 turn·인물·사건 계보·비밀 종류의 후보 독점을 막고, 빈 구조와 현재 장면에 무관한 자료를
  주입하지 않는다.
- 비밀 보호 문구는 압축하되 공개 제한과 지식 범위는 약화하지 않는다.
- 실제 사용량·차용량·미사용량·보류량을 UI와 backend trace에서 같은 값으로 표시한다.

이 교정은 MEM-D/E의 Go 소유 선택·조립을 바로잡는 작업이며 새 JavaScript 정책, 별도 watcher,
별도 기억 저장소 또는 추가 LLM 요약 경로를 만들지 않는다. 교정 후 단위·통합 시험과 실제
RisuAI 최종 입력을 다시 확인한 뒤에만 MEM-F의 200·300턴, 재시작, 리롤·삭제·분기, 벡터 장애
검증을 시작한다. 따라서 현재 3.4는 완료 상태가 아니다.

1차 교정은 `implemented_unverified`로 구현됐다. episode 요약·핵심 사건 중복, 오래된 직접
근거가 `Input Context`를 선점하는 문제, 객관 자료 종류 사이의 동일 사실 중복, 빈 구조 자료,
관련성 provenance 없는 남은 항목의 무조건 차용을 제거했다. Host 보호 봉투를 제외한 실제 전달
가능량으로 자료별 예약을 다시 맞추며 설정 예약량과 실제 예약량을 trace에서 구분한다.

이 상태는 실제 RisuAI 재검증 전이므로 차단 항목 완료가 아니다. 다음 실제 입력에서는 직전
장면 보존, 중복 횟수, 자료별 `used/unused/deferred/deduplicated`, 비밀 보호 유지, 기존 원문·요약·
개체 생성 비퇴행을 확인한다. 그 결과에서 남는 의미상 중복만 재현 근거로 후속 교정한다.

실제 재검증에서 설정 화면의 `자동 주입 예산` 요약이 턴에 적용된 Go 상한과 다른 별도
JavaScript 추정값을 표시하는 것도 확인했다. 해당 요약 UI와 전용 갱신·번역·스타일 코드는
제거하고 추가 예산 설정 자체는 유지한다. 실제 적용 결과의 권위는 `/prepare-turn`의
`memory_delivery_plan.v1` 자료별 예약량·사용량 trace다.

## 3.4 장면 관련성 기반 미사용 예산 유지 — 2026-07-22

`implemented_unverified`. 예산이 남았다는 이유로 무관한 기억과 상태를 채우던 동작을 Go `/prepare-turn`에서 중단했다.

- 검색문은 실제 사용자 입력과 바로 전 assistant 출력 중심으로 제한한다.
- 벡터로 검증되었거나 현재 장면의 구조화된 인물·장소·물건과 직접 연결되거나, 복수의 실제 내용 근거가 맞는 기억만 선택한다.
- 현재 검색문이 있는 동안 무관한 최신 기억으로 빈 자료 예산을 채우지 않는다. `top_k`는 이후 통합에서 벡터 기억 검색에만 한정한다.
- 관계 그래프, 진행 줄거리, 인물 상태, 미해결 목표, 오래된 사건 묶음에도 같은 장면 연결 기준을 적용한다.
- 사건 묶음, 세계 규칙, 최신 확정 상태도 현재 장면 관련성을 통과해야 한다. 최신이라는 이유만으로 무조건 유지하지 않는다.
- 남은 자료별 예산은 비워 두며 다른 자료가 자동 차용하지 않는다.
- JavaScript에는 선택 정책을 추가하지 않았고 RisuAI 관찰·전달·적용 경계를 유지했다.

자동 테스트는 통과했지만 실제 RisuAI의 다음 최종 입력에서 자료별 `used/unused`, `*_irrelevant_dropped`, 관련 사건 보존, 무관 인물·관계 제거를 확인하기 전에는 MEM-F 완료로 올리지 않는다.

## 3.4 과거 입력 권한 차단과 관계 단위 선별 — 2026-07-22

`implemented_unverified`. 바로 전 논리 턴은 `Input Context`가 한 번만 전달하고, 과거 채팅 원문을 `Latest Direct Evidence`나 실제 사건 자료에 다시 복사하지 않도록 Go 조립 경로를 단일화했다. raw fallback 응답 형식은 진단 호환용으로 남기되 최종 전달문에서는 제외한다. 따라서 예전 사용자 문장이 새 사용자 입력처럼 다시 작동하는 경로를 제거한다.

관계 자료는 현재 인물 이름 하나만 맞는다는 이유로 그 인물의 모든 과거 관계를 전달하지 않는다. 관계 양쪽 인물이 현재 장면에 있거나 한쪽 인물과 관계·사건 근거가 함께 일치해야 하며, 관계 그래프와 인물 상태 내부 관계 목록에 같은 원칙을 적용한다. 제거 수와 단일 끝점 탈락 수는 trace에 남긴다.

이 변경은 Go의 읽기·선택·조립에만 적용한다. RisuAI JavaScript 관찰 계약, 원문 및 파생 자료 저장, canonical DB, vector 쓰기, complete-turn, 삭제·리롤·분기는 변경하지 않는다. 실제 RisuAI 최종 입력에서 과거 입력 유출 0, 직전 턴 중복 0, 무관 관계 제거와 현재 관계 보존을 확인하기 전에는 MEM-F 완료로 올리지 않는다.

## 3.4 생성 전 최종 입력 일치성 보강 — 2026-07-22

`implemented_unverified`. RisuAI Host 관찰의 message index를 기준으로 현재 사용자 메시지 직전의 완료된 논리 턴만 `Input Context`에 넣는다. 상태·관계·기억·resume 자료는 각 Go 전용 전달 영역을 사용하며 JavaScript가 별도 후보를 합치지 않는다.

JavaScript는 실제 request payload를 반환하기 직전에 message 배열 지문, 조립 입력 지문, 주입 구성 요소 포함 여부를 기록한다. 생성 후 저장과 대시보드 표시는 이 전송 직전 기록과 일치할 때만 실제 최종 입력으로 인정한다. 따라서 현재 입력의 재삽입, 생성된 assistant 출력의 사전 입력 오표시, 오래된 관계의 `Input Context` 우회, 미리보기와 실제 요청의 불일치를 같은 경계에서 차단한다.

적용만 JavaScript가 소유하며, provider 전송 이후 상태나 노출되지 않은 source metadata는
추정하지 않는다.

- Go `/prepare-turn`은 `payload_application_plan.v1`에서 원작 자료, 장기 기억, 서사 안내의
  순서와 정확한 문자열, 각 문자 예산, 사용량, SHA-256 해시를 확정한다. 사용자 입력은 별도
  보존 영역으로 기록하며 재작성하거나 그 예산을 다른 영역에 빌려주지 않는다.
- `guidance_application_trace.v1`은 서사 안내의 독립 `narrative_support_max_chars`, 적용·보류·
  잘림·실패 건수, 항목별 근거 ref와 해시, 최종 문자열 해시, 감독관 호출 상태를 반환한다.
  항목 중간 절단과 장기 기억·원작·직접 근거 예산 차용은 금지한다.
- 감독관 LLM 호출은 같은 `/prepare-turn` 실행 안에서만 수행한다. 안내가 `없음`, 실행 계약이
  준비되지 않음, provider 미설정인 경우 호출하지 않거나 보류하며 메인 RisuAI 요청과 기존 기억
  전달은 계속한다. 실패도 `failed_open`으로 기록하고 원문·기억 경로를 막지 않는다.
- 2026-07-23 첫 구현은 JavaScript의 기존 최종 조립·예산·Input Context 경로를 한꺼번에
  제거하면서 이전 검색·우선순위·연속성·예산 보호 판단까지 함께 삭제했다. 문자 인코딩 손상도
  발생했으므로 이 삭제는 취소했다. 손상된 한국어·일본어 문구를 복원하고 기존 함수와 대체
  경로를 되살린 뒤 JavaScript 경로 회귀와 전체 Go 시험을 다시 통과시켰다.
- Go의 `payload_application_plan.v1`, `guidance_application_trace.v1`,
  `memory_budget_resolution.v1` 준비 코드는 남아 있지만, 기존 JavaScript 조립 경로가 복원된
  현재 상태에서는 최종 단일 owner 전환이 완료됐다고 보지 않는다. 다음 구현은 기존 판단을
  Go에 하나씩 옮기고 동등성 시험을 통과한 경로만 제거해야 한다.
- 자동 기억 상한 계산도 Go `memory_budget_resolution.v1`으로 이동했다. JavaScript는 RisuAI에서
  실제 관찰한 현재 토큰 값·출처와 사용자가 정한 기본/추가 상한만 전달한다.
- 설정 화면에는 서사 안내 전용 상한을 별도로 두고, 편집 확인 화면은 장기 기억, 원작 자료,
  Output Guidance Context를 분리한다. 서사 안내에는 실제 적용량과 할당량, 적용·보류·잘림·실패,
  감독관 상태를 Go trace와 같은 값으로 표시한다.

취소 복구 후 자동 시험은 통과했지만 실제 RisuAI 한 턴의 최종 message 배열은 아직 확인하지
않았다. 따라서 3.4-D/E는 완료·`implemented_unverified`·`release_gate_verified` 어느
상태로도 승격하지 않는다.
