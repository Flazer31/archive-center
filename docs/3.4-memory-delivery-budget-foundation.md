## 1. 결정

기존 3.4의 주 목표인 actual RisuAI Host Context 전처리, source-backed constraint compile,
`response_execution_contract.v1`, 단일 `/prepare-turn` cutover와
`narrative_support_max_chars`는 그대로 유지한다.

이번에 재현된 메인 기억 검색·주입 결함은 기존 3.4를 대체하지 않고 `3.4-MEM` 작업군으로
같은 release에 추가한다. 이유는 다음과 같다.

- 결함은 현재 3.0 사용자의 실제 주입 결과를 손상시키므로 3.9까지 방치할 수 없다.
- 그러나 메인 기억의 canonical truth, 원자적 기억, stable entity, story time, body state,
  knower, 관계와 완성형 `memory_recall_plan.v2`는 계속 3.6~3.9가 소유한다.
- 3.4-MEM은 현재 저장 구조를 대상으로 한 전달 계층 교정이며 새 canonical table, 별도
  watcher, 병렬 저장 경로 또는 임시 truth를 만들지 않는다.
- 3.4-MEM에서 만든 분류·예산·trace 계약은 3.9가 일반화하거나 교체할 수 있어야 하며,
  3.9와 경쟁하는 두 번째 최종 planner가 되어서는 안 된다.

현재 작업 트리에 존재할 수 있는 부분 구현·시험 코드는 이 문서의 승인이나 구현 완료
증거가 아니다. 문서가 확정되기 전에는 해당 코드를 더 확장하거나 완료로 표시하지 않는다.

## 2. 확인된 결함

현재 경로는 서로 다른 memory row를 벡터 상위 결과로 선택한 뒤 실제 주입 시 동일하거나
거의 동일한 보호 지침으로 바꾼다. 원문 요약 기준 중복 제거가 먼저 실행되므로 변환 후
중복이 남고, 보호 지침이 `top_k`를 소비해 실제 사건·최근 기억을 밀어낸다.

실제 재현 예시는 다음과 같다.

```text
[Memory]
[vector_relevant, turn 11] POV-scoped identity continuity: ...
[vector_relevant, turn 9]  POV-scoped identity continuity: ...
[vector_relevant, turn 2]  Protected continuity guard: ...
```

이 결과의 실패 판정은 다음과 같다.

- 같은 인물·같은 정체 종류의 최종 보호 지침이 두 번 전달됨;
- `of the most suffering character`처럼 실제 인물이 아닌 값이 current POV 권한으로 사용됨;
- 보호 지침이 실제 사건 기억처럼 `[Memory]`와 `vector_relevant` 자리를 사용함;
- 보호 지침으로 제거된 자리를 관련 사건·최근 기억이 다시 채우지 못함;
- DB에는 정상 기억이 있어도 실제 payload에는 보호 문구만 남음.

## 3. 3.4-MEM 필수 결과

1. 최종 전달 문구로 변환한 뒤 다시 중복 제거한다.
2. stable하게 확인 가능한 동일 인물·동일 비밀/정체 종류의 보호 지침은 한 번만 전달한다.
3. 별칭은 확인된 same-entity 근거가 있을 때만 같은 인물로 묶고, 모호한 별칭은 자동 병합하지
   않는다.
4. 보호 후보가 벡터 상위 결과를 독점하지 않도록 bounded candidate pool에서 중복 coverage를
   접고 MariaDB의 실제 row를 다시 확인한다.
5. 보호 지침이 빠진 메인 기억 자리는 현재 recall need에 관련된 사건 기억으로 채우고, 부족할
   때 최근 기억을 사용한다. 숫자를 채우기 위해 무관한 기억을 넣지는 않는다.
6. 보호 지침과 실제 기억은 별도 block·선택 수·문자 사용량·포함/탈락 사유를 가진다.
7. `POV`, `시점`, `관점`이라는 입력 문구나 비인물 값을 권한으로 사용하지 않는다. 보호 기억의
   POV/knower 판정은 공식 RisuAI 관찰과 backend가 확인한 실제 인물 identity만 사용한다.
8. 유효한 POV가 없으면 POV-scoped 지침을 만들지 않는다. 현재 입력·최근 대화·검증된 현재
   상태에도 관련 인물이 없으면 일반 보호 지침도 주입하지 않는다.
9. JavaScript는 RisuAI 관찰·전달·적용만 담당하고 분류·검색·중복 제거·예산·최종 문구는 Go가
   소유한다.
10. 저장된 원문, canonical DB, vector lifecycle, 삭제·리롤·편집·분기·재시도 동작은 바꾸지
    않는다.

## 4. 메인 기억 내부의 일곱 예산 종류

메인 기억 `max_injection_chars` 내부를 다음 일곱 delivery class로 구분한다.

| delivery class | 현재 자료의 예 | 초기 기준 몫 |
|---|---|---:|
| 사건·최근 기억 | atomic/legacy memory, recent chat, 필요한 episode·chapter·arc·saga 회상 | 3,500자 |
| 인물의 객관 상태 | 신체·부상·건강·외형·위치·현재 행동 상태 | 2,500자 |
| 인물별 주관 기억·관계 | 인물별 기억, 인식, 감정, 관계 current/history | 3,000자 |
| 물건·장소·세계 상태 | 물건 소유·위치·파손, 장소 상태, 적용 중인 세계 상태 | 2,500자 |
| 비밀·정체 보호 | 공개 범위, knower/POV 경계, 별칭·정체 continuity guard | 1,200자 |
| 미해결 목표 | 약속, 의무, 목표, 진행 중 사건과 unresolved thread | 1,800자 |
| 직접 근거 | 정확한 발언·날짜·장소·사건 확인용 source excerpt | 3,500자 |

초기 합계는 18,000자이며 long-session 자동 profile의 초기 calibration 기준이다. 다음 원칙을
함께 적용한다.

- 위 숫자는 반드시 채우는 최소량이나 고정 비율이 아니라 eligible 자료가 있을 때의 기본
  몫이다.
- 사용자가 더 작은 `max_injection_chars`를 명시하면 그 전체 상한이 우선하며 Go가 coverage와
  누락 사유를 보존해 조정한다.
- 자료가 없는 class는 0자를 사용한다.
- 남은 몫은 같은 메인 기억 예산 안에서 uncovered recall need가 있는 다른 class가 빌릴 수
  있다. 메인 기억과 `narrative_support_max_chars`, 원작 DB 예산 사이의 차용은 금지한다.
- 기본 합계보다 더 필요한 경우 메인 기억 전체 최대 24,000자를 초기 상한 후보로 사용하되,
  RisuAI payload의 실제 남은 공간과 사용자 설정을 넘지 않는다.
- 동일 root evidence가 여러 class에 나타나면 delivery purpose가 같은 복제 문장은 합치고,
  서로 다른 필수 역할은 source ID를 공유한 별도 compact item으로 추적한다.
- 한 class가 많다는 이유로 다른 eligible class를 조용히 0자로 만들지 않는다. 완전히 전달하지
  못하면 `deferred` 또는 `coverage_gap`과 누락 class/source를 반환한다.
- block 또는 item 중간 문자열 절단은 금지한다.

200~300턴은 저장·검색 범위를 뜻하며 주입량을 턴 수에 비례해 늘리는 근거가 아니다. 전체
history가 증가해도 현재 request의 recall need와 관련된 item만 위 예산으로 전달한다.

### 4.1 3.4 전 임시 전체 상한 보정

3.4의 일곱 delivery class를 Go가 최종 소유하기 전까지 기존 단일 주입기는 추정 토큰 기준
`4,500 → 9,000 → 13,500 → 18,000` 단계, 문자 기준
`9,000 → 18,000 → 27,000 → 36,000 chars` 단계를 사용한다. 사용자가 지정한 추가 문자
예산은 화면 표시와 JavaScript 최종 조립에만 더하지 않고 `/prepare-turn`의
`max_injection_chars`에도 포함한다. 그렇지 않으면 Go가 기본 상한에서 후보 자료를 먼저 잘라
추가 예산을 실제로 사용할 수 없다. 자동 상한과 추가 상한의 합계는 최대 51,000자다.

Go가 반환한 `[Persona Recollection]`과 `[Character Private Recollection]` 블록에는 이미 제목이
포함되어 있으므로 RisuAI 적용 단계에서 제목을 다시 붙이지 않는다. 이 임시 단일 상한과
JavaScript 계산은 3.4-D/E의 Go 최종 plan 전환 시 제거 대상이며, 일곱 class 예산을 대신하지
않는다.

## 5. 기존 3.4와의 병행 여부

병행은 일부만 허용한다.

| 작업 | 병행 여부 | 이유 |
|---|---|---|
| 3.4-A actual Host source authority와 3.4-MEM 재현 fixture·현재 자료 mapping | 가능 | 읽는 source와 결과 계약을 각각 고정하며 canonical write가 없음 |
| 3.4-B constraint compiler와 3.4-MEM 보호/실제 기억 분류 함수 | 가능 | Host constraint와 main-memory delivery는 서로 다른 예산 lane |
| 3.4-C supervisor proposal envelope와 3.4-MEM 검색 다양성·중복 coverage | 가능 | provider proposal과 MariaDB/Chroma recall 책임이 분리됨 |
| 3.4-D 단일 `/prepare-turn` planner와 3.4-MEM 최종 block 조립 | 동시 수정 금지 | 같은 production owner, order, text, hash와 payload를 변경함 |
| 3.4-E narrative 예산과 3.4-MEM 일곱 class allocator | 계약은 병행, cutover는 통합 | 예산은 독립이지만 provider 전체 상한과 UI trace를 한 Go plan이 최종 결정해야 함 |
| 3.4-PERF/F와 3.4-MEM 성능·lifecycle gate | 최종 통합 | 같은 loaded artifact와 실제 payload 기준으로 함께 검증해야 함 |

권장 실행 순서는 다음과 같다.

1. Host 작업과 MEM 작업의 fixture·DTO·source/budget 경계를 각각 확정한다.
2. 3.4-MEM의 중복 보호 문구, 비인물 POV, alias 독점, 실제 기억 보충을 production 함수의
   단위·통합 시험으로 고정한다.
3. 기존 3.4-A~C와 3.4-MEM-A~C는 서로 다른 owner에서 진행할 수 있다.
4. 3.4-D/E 진입 전에 하나의 Go `/prepare-turn` plan schema와 block order를 합의한다.
5. 최종 assembly·budget·hash·compact projection은 한 작업자가 한 경로에서 통합하고 교체된
   JavaScript 계산을 같은 cutover에서 제거한다.
6. 실제 RisuAI payload와 UI trace, 기존 저장·삭제·리롤·분기·원작 DB sentinel을 함께 검증한다.

### 6.1 3.4-MEM-A 구현 기록 — 2026-07-22

`/prepare-turn`의 실제 조립 경로가 `injection_pack.memory_delivery_lineage`에
`memory_delivery_lineage.v1`을 반환한다. 각 항목은 MariaDB `memories` 행 ID와 turn,
선택 lane·순위·점수, Chroma hit 여부, 보호 문구 변환 여부, 최종 문구와 문자 수,
실제 기억 칸 또는 보호 지침 칸 소비 여부, 전달·중복 제거 상태를 연결한다. 보호 범위 중복으로
최종 변환 전에 빠진 행과 최종 문구 변환 후 빠진 행도 원본 행 ID와 탈락 사유를 남긴다.

production `/prepare-turn` 통합 fixture는 turn 11/9의 동일 정체 보호 기억, 서로 다른 세 종류의
비밀 보호 기억, 실제 사건 기억 한 건을 Chroma 순위로 반환한다. 같은 정체의 turn 9는 중복으로
빠지고, 최종 다섯 줄이 보호 지침 네 줄과 실제 사건 한 줄로 구성되는 현재 실패 기준선을
`protected_guard_dominant`와 `protected_guard_dominates_final_memory_lines`로 검출한다. 이 시험은
문제를 정상 동작으로 승인하는 것이 아니라 MEM-B/C가 해결해야 할 결함을 실행 가능한 증거로
고정한다.

MEM-A는 JavaScript, 저장 자료, 벡터 쓰기, 기억 선택 정책을 새로 바꾸지 않는다. 실제 RisuAI에서
trace를 확인하기 전 상태는 `implemented_unverified`이며, 보호 지침 분리·실제 기억 보충·일곱
예산 분류는 각각 MEM-B~E의 완료 증거가 필요하다.

### 6.2 3.4-MEM-B 구현 기록 — 2026-07-22

Go 기억 조립기가 보호 기억을 최종 문구로 만들기 전에 `보호 분류 + 확인된 인물 + 비밀 종류`로
범위를 묶는다. 같은 인물의 같은 비밀 종류가 여러 turn과 여러 벡터 결과에 반복되어도 최종
주입에서는 한 줄만 사용한다. 한 memory row에 이미 처리한 비밀 종류와 새 비밀 종류가 함께
있으면 기존 종류를 다시 쓰지 않고 새 종류만 별도 보호 범위로 전달한다.

중복 제거 때문에 비밀 보호가 약해지지 않도록 다음을 함께 적용했다.

- 같은 보호 범위의 모든 `disclosure_policy`와 `reveal_policy`를 합집합으로 보존한다. 하나를
  임의로 선택하거나 더 약한 정책으로 덮어쓰지 않는다.
- `known_by`와 `suspected_by`는 이름 중복을 제거한 합집합 개수로 전달한다. 비밀 내용과 해당
  인물 이름 목록 자체는 최종 보호 문구에 노출하지 않는다.
- 모든 비밀 보호 문구에는 현재 장면의 명시적 근거 없이 공개·고백·무관한 인물의 발견으로
  처리하지 말라는 공통 금지문을 유지한다.
- `same_entity=true`와 하나로 확정되는 canonical identity 근거가 있을 때만 별칭을 같은 인물로
  합친다. 같은 별칭이 서로 다른 둘 이상의 canonical 인물에 연결되면 source row별 보호 범위를
  유지하고 자동 병합하지 않는다.
- 인물 근거가 없는 보호 정보는 원문을 버리지 않는다. 같은 전역 비밀 종류의 일반 보호
  지침으로 합치되 모든 제한과 지식 범위를 보존한다.
- lineage는 최종 `protected_coverage_key`, 병합된 원본 memory row ID와 개수를 반환한다.
  원본 `secret_summary`나 보호된 사건 문장은 lineage와 최종 `[Memory]`에 넣지 않는다.

production 조립 시험은 같은 Mina `hidden_plan` 세 행을 한 줄로 합치면서 서로 다른 공개 제한과
지식 범위를 모두 유지하고, 같은 행의 `surveillance`는 별도 한 줄로 유지하며, 네 개의 비밀
원문이 하나도 노출되지 않는 것을 검증한다. 별칭 `Shade`가 Alice와 Bob 양쪽에 연결된 fixture는
두 `hidden_plan`을 합치지 않고 각각 보호하며, full memory set에서 확인한 alias ambiguity가
bounded vector 후보에서도 유지되는 것을 검증한다. 기존 POV 가명 동일성 문구와 MEM-A lineage,
비인물 POV 차단, 보호 후보 다양성 시험도 함께 통과했다.

MEM-B는 JavaScript, canonical DB, Chroma write, complete-turn, 삭제·리롤·분기 경로를 변경하지
않는다. JavaScript 변경량은 추가 0줄·삭제 0줄이다. 실제 RisuAI 최종 입력에서 중복 감소와 비밀
비노출을 확인하기 전 상태는 `implemented_unverified`다. 보호 지침을 `[Memory]`와 분리하는 작업은
MEM-E, 보호 후보가 차지한 자리를 실제 사건·최근 기억으로 채우는 완성 작업은 MEM-C가 소유한다.

### 6.3 3.4-MEM-C 구현 기록 — 2026-07-22

Go `/prepare-turn` 기억 선택기는 요청된 실제 기억 수와 보호 지침 수를 별도로 계산한다. ChromaDB
검색은 요청 수의 세 배까지만 후보를 읽는 bounded oversampling을 유지하고, 같은 보호 범위는
MEM-B coverage로 접는다. 벡터 후보에 실제 기억이 부족하면 MariaDB canonical memory 전체에서
현재 입력과 겹치는 관련 기억을 먼저 선택하고, 남은 실제 기억 자리만 최신 turn 순서의 최근
기억으로 채운다. 보호 후보는 이 실제 기억 목표를 소비하지 않으며, 실제 기억 목표를 채운 뒤
더 오래된 행을 숫자 맞추기 용도로 추가하지 않는다.

선택 trace에는 다음 값이 추가됐다.

- `actual_memory_target`, `actual_memory_vector_selected`;
- `actual_memory_relevant_refill_selected`, `actual_memory_deep_refill_selected`,
  `actual_memory_recent_refill_selected`;
- `actual_memory_refill_selected`, `actual_memory_refill_gap`;
- `protected_candidates_consume_actual_memory_target=false`;
- bounded vector 후보 한도와 MariaDB 보충 정책.

production 조립 시험은 벡터 상위 후보가 같은 Gloria/Lia 보호 정체 여덟 행으로만 구성된 상태를
재현한다. 최종 입력에는 병합된 보호 지침 한 줄을 유지하면서, 벡터 결과에 없던 MariaDB 관련
사건 한 건과 가장 최근 기억 두 건을 실제 기억 목표 세 칸에 채운다. 목표 뒤의 오래된 무관 기억은
들어가지 않으며, 기존 MEM-B의 정책 합집합·모호한 별칭 비병합·비밀 원문 비노출 시험도 함께
통과한다.

MEM-C는 JavaScript, canonical DB, Chroma write, complete-turn, 삭제·리롤·분기 경로를 변경하지
않는다. JavaScript 변경량은 추가 0줄·삭제 0줄이다. 최근 기억은 키워드가 겹치지 않더라도 관련
기억 뒤에 사용하는 명시적 fallback이며, 목표 개수 이상으로 임의 확장하지 않는다. 실제 RisuAI
최종 입력과 장기 세션에서 관련 사건·최근 기억 보충을 확인하기 전 상태는
`implemented_unverified`다. 일곱 delivery class별 문자 예산과 누락 사유는 MEM-D가 소유한다.

상태: `implemented_unverified` (단위 시험 완료, 실제 RisuAI 최종 입력 확인 전)

`/prepare-turn`은 `memory_delivery_plan.v1`을 만들고 다음 일곱 자료 종류의 최종 선택 순서와 문자 예산을 Go에서 확정한다.

|---:|---:|---:|---:|---:|---:|---:|---:|
| 9,000 | 1,600 | 1,150 | 1,400 | 1,150 | 1,200 | 850 | 1,650 |
| 18,000 | 3,500 | 2,500 | 3,000 | 2,500 | 1,200 | 1,800 | 3,500 |
| 27,000 | 5,250 | 3,750 | 4,500 | 3,750 | 1,800 | 2,700 | 5,250 |
| 36,000 | 7,000 | 5,000 | 6,000 | 5,000 | 2,400 | 3,600 | 7,000 |

전체 상한 안에서 최대 512자는 현재 사용자 입력 우선 지침, 기본 연속성 규칙, 보조 기능 실패 경고를 위한 Host 보호 봉투로 예약한다. 일곱 자료 묶음은 나머지 범위 안에서만 선택되므로 JavaScript 적용 단계에서 마지막 자료 묶음이 뒤늦게 잘리는 일을 피한다.

9,000과 18,000 사이처럼 중간 상한은 가까운 기준표를 전체 상한에 비례해 조정한다. 전체 상한에서 Host 보호 봉투를 뺀 실제 전달 가능량에 맞춰 일곱 예약값을 다시 비례 조정하므로 뒤쪽 자료가 봉투 크기만큼 일방적으로 잘리지 않는다. 현재 item 계약에는 차용할 개별 항목의 관련성 근거가 없으므로 남은 공간 차용은 사용하지 않는다. 관련성 provenance가 계약에 추가되기 전까지 `borrowing_policy=disabled_without_item_relevance_provenance`, `borrowed_chars=0`을 반환한다. 관련 자료가 부족하면 공간을 비워 두며, 예산을 채우기 위해 오래된 자료를 추가하지 않는다. 문장 중간 절단은 하지 않으며 들어가지 못한 항목 수를 `deferred_count`로 남긴다. 사용자 직접 설정에서 0은 기능 끄기가 아니라 해당 자료의 자동 예약값 사용을 뜻한다.

비밀 보호 문구는 실제 기억 목록과 분리되어 `protected_memory_text`와 `Protected Memory Guidance` 묶음으로 전달된다. 실제 기억은 `event_recent`에만 들어가며 보호 문구가 실제 사건 기억의 자리를 소비하지 않는다. 보호 내용 원문은 노출하지 않고 기존 안전 문구만 전달한다.

`Archive Center.js`는 일곱 예산을 저장해 `/prepare-turn`으로 전달하고, Go가 반환한 `memory_delivery_plan.v1.final_text`를 적용한다. 예전 백엔드와의 호환을 위한 기존 조립 함수는 남아 있지만 새 계획이 있으면 예산과 순서를 다시 판단하지 않는다. 최종 입력 미리보기는 한 개의 `Assembled Auxiliary Context` 대신 일곱 자료 묶음을 사용량/예약량과 함께 따로 표시한다.

고급 설정에는 자동/직접 설정 선택과 일곱 문자 예산 입력란을 추가했다. 이 설정은 기억·보조 자료의 전달 예산만 다루며 원작 자료 예산, 서사 지원 예산, 저장·벡터 수명주기에는 영향을 주지 않는다.

## 10. MEM-F 진입 전 주입 밀도·관련성 교정 항목 — 2026-07-22

실제 RisuAI 최종 입력에서 일곱 자료 예산의 분리와 표시 자체는 확인됐지만, 예산 안에 들어가는
자료의 밀도와 현재 장면 관련성에는 다음 문제가 남았다. 이 항목들은 새 기억 체계가 아니라
MEM-D/E의 선택·조립 결과를 바로잡는 차단 항목이다. 이를 고치고 같은 최종 입력에서 확인하기
전에는 MEM-F의 200·300턴 및 lifecycle 최종 검증으로 넘어가지 않는다.

### 10.1 확인된 문제

1. 사건 묶음에서 같은 내용이 `memory`와 `key_event`로 연달아 출력된다. 제공된 입력에서는
   여러 episode가 `memory: A; key_event=memory: A` 형태로 정확히 두 번 전달됐다.
2. 현재 장면과 관련성이 낮은 오래된 사건이 남은 예산을 채운다. 큰 예산이 최대 허용량이 아니라
   채워야 할 목표처럼 작동해, 현재 인물·행동과 무관한 과거 사건이 들어온다.
3. `Input Context`가 현재 장면보다 오래된 직접 근거를 먼저 채운다. 제한된 공간이 과거 호패,
   시험, 초기 인물 관계로 소진되어 직전 장면과 현재 등장인물이 빠질 수 있다.
4. 비밀 보호는 실제 기억과 분리됐지만, 종류만 다른 일반 보호 문구가 반복되어 현재 장면에
   필요한 보호 범위보다 많은 공간을 사용한다.
5. 직접 근거 안에서 같은 문장이 원문형과 source 표기형으로 반복되고, 현재 장면에 필요하지
   않은 오래된 사용자 입력도 함께 전달된다.
6. 주관 기억·관계에는 비밀 보호 묶음과 같은 의미가 다시 나오고, 매 턴 같은 설명문과 빈 관계
   구조가 반복된다.
7. 인물 객관 상태와 물건·장소·세계 상태에는 현재 장면에 없는 인물, 빈 필드, 같은 규칙의 JSON
   표현과 문장 표현이 함께 들어간다.
8. 현재 최종 중복 제거는 자료 종류 안에서만 이루어진다. 서로 다른 자료 종류가 같은 사실을
   다른 형식으로 출력하면 최종 payload에는 둘 다 남는다.

### 10.2 반드시 손볼 동작

- **예산은 상한이지 채움 목표가 아니다.** 각 자료의 관련 후보가 기준에 못 미치면 남은 예산을
  사용하지 않는다. 높은 관련성의 자료가 많은 장면에서는 상한까지 사용할 수 있지만, 공간이
  남았다는 이유만으로 오래된 자료를 추가하지 않는다.
- **episode 내부 중복을 제거한다.** 요약문과 핵심 사건이 같거나 한쪽이 다른 쪽을 그대로
  포함하면 한 번만 전달한다. 출처와 turn 범위는 trace에 보존한다.
- **현재 장면을 먼저 고정한다.** `Input Context`는 직전 장면, 현재 입력과 직접 연결된 인물·행동,
  현재 상태를 먼저 담고, 오래된 직접 근거·episode·persona는 별도 한도 안에서만 추가한다.
  전체 문자열을 앞에서부터 잘라 현재 장면이 사라지게 하지 않는다.
- **최종 표현 기준으로 자료 종류 사이 중복도 제거한다.** 우선순위는 직접 근거, 현재의 객관
  상태, 사건 요약 순으로 둔다. 단, 인물의 주관적 해석을 객관적 사실과 합치거나 비밀 보호를
  일반 사건으로 합치지 않는다.
- **후보 다양성을 제한한다.** 같은 turn, 같은 인물, 같은 사건 계보, 같은 비밀 종류의 유사
  항목이 한 자료 예산을 독점하지 못하게 한다.
- **비밀 보호를 압축하되 약화하지 않는다.** 공통 공개 금지는 한 번만 두고, 현재 장면과 관련된
  인물·비밀 범위만 짧게 추가한다. 공개 제한, `known_by`, `suspected_by`, same-entity 확정 조건은
  합집합으로 보존하며 비밀 원문은 노출하지 않는다.
- **구조화 자료를 간결한 사실로 표현한다.** 빈 객체·빈 배열·중복 필드·동일 규칙의 JSON/문장
  이중 출력을 제거한다. 현재 장면에 없는 인물과 관계는 관련 근거가 있을 때만 전달한다.
- **예산 표시를 실제 사용과 일치시킨다.** 자료별 예약량, 다른 자료가 빌린 양, 실제 사용량,
  관련성 부족으로 사용하지 않은 양, 보류 수를 구분한다. 메인 기억, `Input Context`, 원작 자료,
  RisuAI 자체 프롬프트·대화 이력은 서로 다른 항목으로 계산한다.

이 판단과 최종 조립은 Go `/prepare-turn`이 소유한다. `Archive Center.js`에 작품명, 모델명,
인물명, 버튼 문구 또는 별도 선택·요약 정책을 추가하지 않는다. 토큰 절약만을 위한 별도 LLM
요약 호출도 추가하지 않는다. 해당 호출은 지연과 실패 지점을 늘리고 원문 근거를 흐릴 수 있다.

### 10.3 통과 조건

- `memory`와 같은 `key_event`가 최종 입력에서 한 번만 나타난다.
- 현재 장면의 인물·행동이 `Input Context`에 먼저 남고, 오래된 자료가 이를 밀어내지 않는다.
- 관련 후보가 적은 장면은 예약 예산보다 짧게 끝나며, 무관한 과거 자료로 빈자리를 채우지 않는다.
- 현재 장면과 직접 연결된 오래된 기억은 turn이 오래됐다는 이유만으로 빠지지 않는다.
- 같은 사실이 직접 근거·상태·사건에 걸쳐 있어도 필요한 최종 표현은 한 번이며 source lineage는
  trace에서 확인할 수 있다.
- 주관 기억은 객관 상태로 승격되지 않고, 비밀 보호는 압축 뒤에도 공개 범위와 지식 보유자 경계를
  그대로 지킨다.
- 현재 장면과 무관한 인물, 빈 관계 객체, 중복된 세계 규칙은 주입 0이다.
- 일곱 자료의 실제 사용량 합계와 최종 텍스트 길이가 일치하고, 차용·미사용·보류 이유가 UI와
  backend trace에서 같다.
- 기존 저장·벡터·삭제·리롤·분기·원작 DB와 RisuAI 원문은 변경되지 않는다.
- 위 항목의 단위·통합 시험과 실제 RisuAI 최종 입력 확인 뒤에만 MEM-F의 장기 세션·재시작·장애
  검증을 시작한다.

### 10.4 구현 책임 위치

수정 범위는 다음 기존 owner 안으로 제한한다. 줄 번호는 바뀔 수 있으므로 함수와 동작으로
추적한다.

| owner | 손볼 책임 |
|---|---|
| `go-service/internal/httpapi/prepare_turn_assembly.go`의 episode 조립과 `episodeDenseAnchorPreview` | 같은 episode 요약·핵심 사건의 겹침 제거 |
| `go-service/internal/httpapi/prepare_turn_assembly.go`의 `buildInputContextText` | 직전 장면 우선순위와 내부 자료별 한도, 오래된 직접 근거의 선점 방지 |
| `go-service/internal/httpapi/prepare_turn_memory_budget.go` | 관련성 기준을 통과한 후보만 차용, 자료 종류 사이 최종 중복 제거, 사용·차용·미사용 trace |
| `go-service/internal/httpapi/prepare_turn_recall.go` | 같은 turn·인물·사건 계보·비밀 종류의 후보 독점 제한과 관련 후보 부족 처리 |
| `go-service/internal/httpapi/prepare_turn_memory.go` 및 기존 상태 조립 함수 | 보호 지침의 안전한 압축, 빈 구조 제거, 현재 장면과 무관한 상태의 compact 표현 |

JavaScript는 Go 결과의 전달·적용·표시만 담당한다. 이 교정으로 `Archive Center.js`에 검색,
관련성 판정, 중복 제거 또는 예산 차용 정책을 추가하지 않는다.

### 10.5 1차 교정 구현 기록 — 2026-07-22

상태: `implemented_unverified` (Go 자동 회귀 완료, 실제 RisuAI 최종 입력 재확인 전)

- episode 요약과 `key_event`가 같거나 요약이 핵심 사건 문구를 이미 포함하면 핵심 사건을 다시

  맥락 전체가 빈 값이 되지 않도록 제한 안에서 보존한다.
- 직접 근거·사건·인물 객관 상태·세계 상태 사이에서 최종 사실 문구가 같은 경우 먼저 선택된
  권위 높은 한 건만 전달한다. 주관 기억·관계, 비밀 보호, 미해결 목표는 의미가 달라 이 범용
  중복 제거 대상에서 제외한다.
- 상태와 세계 자료의 빈 객체·빈 배열·빈 문자열은 제거한다. `false`와 `0`은 실제 상태일 수
  있으므로 보존한다.
- Host 보호 봉투를 제외한 실제 전달 가능량에 맞춰 자료별 예약량을 비례 조정한다. 개별 항목의
  관련성 provenance가 없는 현재 남은 항목은 다른 자료의 빈 예산을 빌려 넣지 않는다.
- class trace에 설정 예약량, 실제 예약량, 실제 사용량, 미사용량, 중복 제거 수, 보류 수를
  구분해 남긴다.
- 설정 화면의 옛 `자동 주입 예산` 요약은 실제 `/prepare-turn`에 전달된 값이 아니라 별도
  JavaScript runtime 추정값을 사용했다. 실제 턴이 11,500자 상한을 사용한 상태에서도 화면은
  8,500자로 표시할 수 있어 제거했다. 추가 기억 예산 설정과 실제 요청 계산은 유지하며, 결과
  확인은 Go가 반환한 자료별 설정 예약량·실제 예약량·사용량을 기준으로 한다.

이번 1차 교정은 JavaScript를 변경하지 않았으며 저장·벡터·complete-turn·삭제·리롤·분기·원작
DB 경로를 변경하지 않았다. 보호 문구의 장면별 추가 압축과 구조적으로 다른 문장 사이의 의미상
중복 제거는 실제 새 최종 입력을 확인한 뒤 근거가 있을 때만 진행한다. 이름이나 작품 문구를
하드코딩한 추측 삭제는 적용하지 않는다.

### 10.6 관련성 없는 자료의 예산 소진 방지 — 2026-07-22

상태: `implemented_unverified` (Go 전체 자동 테스트 통과, 실제 RisuAI 최종 입력 재확인 전)

- 기억 검색문은 현재 사용자 입력, 실제로 확인된 현재 시점 인물, 바로 전 assistant 출력만 사용한다. `top_k`만큼 과거 채팅을 검색문에 붙이지 않는다.
- 현재 검색문이 있으면 단어 하나만 우연히 겹친 기억을 관련 기억으로 인정하지 않는다. 저장된 인물·장소·물건 식별자가 현재 장면과 직접 맞거나, 서로 다른 실제 내용 단어가 함께 맞을 때만 MariaDB 보충 기억으로 선택한다.
- 벡터 검색에서 검증된 기억과 위 근거가 있는 MariaDB 기억만 실제 기억 예산을 쓴다. 부족한 수량을 관련성 0인 최신 기억으로 채우지 않으며 남은 예산은 사용하지 않는다.
- 선택된 관련 기억과 최신 직접 근거는 이후 자료의 장면 연결 기준으로만 사용한다. 입력이 장소만 가리키는 경우에도 그 장소와 연결된 인물 상태와 미해결 목표를 유지할 수 있다.
- 관계 그래프, 진행 줄거리, 인물 상태, 미해결 목표는 현재 입력·직전 출력·선택된 관련 기억·최신 직접 근거와 연결되는 항목만 전달한다.
- 사건 묶음은 가장 최신 묶음 하나를 장기 연속성 기준점으로 유지한다. 더 오래된 사건 묶음은 현재 장면과 연결 근거가 있을 때만 전달한다.
- 모든 장면에 적용되는 세계 규칙과 최신 확정 상태는 단순 단어 불일치만으로 제거하지 않는다. 관련성 필터가 세계 규칙의 효력을 약화시키거나 현재 진실을 과거 값으로 되돌려서는 안 된다.
- Go trace는 `lexical_rejected_candidate_count`, `query_present_recent_fill_disabled`, 자료별 `*_irrelevant_dropped`, `actual_memory_refill_gap`을 남긴다. 빈 공간은 오류가 아니라 무관 자료를 넣지 않은 결과다.

회귀 테스트는 무관한 최신 기억이 빈 자리를 채우지 않는 경우, 현재 입력과 바로 전 assistant 출력만 검색문에 들어가는 경우, 관련 사건·관계·인물·목표는 남고 무관 항목은 제거되는 경우, 최신 사건 묶음 기준점은 유지되는 경우를 포함한다.

### 10.7 과거 사용자 입력의 재명령 방지와 관계 선별 강화 — 2026-07-22

상태: `implemented_unverified` (Go 관련 자동 테스트 통과, 실제 RisuAI 최종 입력 재확인 전)

- 과거 채팅 원문은 직접 근거나 실제 사건 자료에 다시 넣지 않는다. 바로 전 논리 턴의 사용자·assistant 원문은 작은 `Input Context`가 한 번만 소유하며, 더 오래된 사용자 문장은 기억·근거로 승인되지 않는 한 현재 요청에 재전달하지 않는다. 기존 raw fallback 응답은 진단 호환용으로만 남고 Go 최종 전달문에서는 제외한다.
- `Latest Direct Evidence`는 저장된 직접 근거와 현재 연속성 교정 자료만 사용한다. `Recent Raw Turn`을 복사해 과거 사용자 지시가 현재 요청과 같은 권한을 얻는 경로를 제거했다.
- 관계 그래프는 현재 인물 이름 한쪽만 맞는 것으로는 선택하지 않는다. 관계 양쪽 인물이 모두 현재 장면에 있거나, 한쪽 인물과 관계·사건 근거가 함께 맞을 때만 전달한다.
- 인물 상태 안의 관계 목록도 같은 기준으로 항목별 선별한다. 현재 인물의 모든 과거 관계를 한꺼번에 전달하지 않는다.
- Go trace는 `historical_chat_authority_policy`, `recent_raw_turn_delivery`, `raw_chat_fallback_delivery`, `kg_single_endpoint_only_dropped`, `character_relationship_irrelevant_dropped`을 남긴다.
- 원문 저장, canonical DB, vector 쓰기, complete-turn, 삭제·리롤·분기와 JavaScript Host 관찰 계약은 변경하지 않는다.

실제 RisuAI 확인에서는 직전 논리 턴이 `Input Context`에 한 번만 보이는지, 그보다 오래된 사용자 지시가 최종 입력에 없는지, 현재 장면과 무관한 과거 관계가 빠지고 현재 상대·사건과 연결된 관계는 남는지를 함께 확인한다.

## 12. 생성 전 입력 소유권과 실제 전송 검증 — 2026-07-22

상태: `implemented_unverified` (자동 회귀 통과 후 실제 RisuAI 재확인 필요).

- `Input Context`는 RisuAI가 관찰한 현재 사용자 메시지 위치보다 앞에 있는 가장 가까운 완료된 사용자/assistant 한 쌍만 담는다. 현재 사용자 입력과 생성 뒤 assistant 출력은 들어갈 수 없다.
- Host 관찰이 존재하지만 앞선 완료 턴이 없으면 비어 있는 상태를 그대로 사용한다. DB의 최신 행으로 되돌아가 현재 턴이나 리롤 결과를 재생하지 않는다.
- active state, canonical state, 직접 근거, episode, resume pack, persona 및 NPC private recollection은 각 전용 전달 영역만 사용하며 `Input Context`를 우회 통로로 쓰지 않는다.
- JavaScript는 Go가 반환한 `input_context_text`를 그대로 적용한다. backend plan이 있는 경우 로컬 entity/KG/scene 후보를 다시 더하지 않는다.
- 전송 직전에 실제 outbound message 배열과 조립된 입력의 지문을 고정하고, 주입할 각 구성 요소가 실제 payload에 포함됐는지 확인한다.
- 생성 완료 뒤 대시보드 저장·표시는 전송 직전 지문과 다시 조립한 값이 일치할 때만 허용한다. 불일치하면 생성된 assistant 출력이나 사후 변경값을 ‘생성 전 최종 입력’으로 표시·저장하지 않는다.
- 프롬프트 파일은 변경하지 않는다. 이 문제는 critic/supervisor 지시문이 아니라 입력 선택·전달·관찰 계약의 문제다.

실제 RisuAI에서는 현재 입력이 `Input Context`에 반복되지 않는지, 직전 완료 턴만 한 번 표시되는지, 무관한 과거 관계가 사라지는지, 대시보드 표시가 실제 outbound payload 검증을 통과하는지를 확인한다.
## 11. 조회·선별·전달 책임 통합 기록 — 2026-07-23

MEM-F 진입 전 교정으로 다음 경계를 production 코드에 고정했다.

1. `memory_delivery_plan.v1`의 자료별 문자 예산이 실제 전달량의 유일한 최종 책임자다. 후보 처리 상한은 DB/메모리 안전장치일 뿐 전달 quota가 아니다.
2. `top_k`는 벡터 기억 검색에만 사용한다. 비벡터 자료와 주관 기억 읽기, 최근 원문, 사건 요약, 계층 요약에는 독립 후보 안전 상한을 사용한다.
3. NPC 비공개 기억과 주인공·플레이어 기억을 역할 태그로 분리한다. 명시적 주인공 역할은 과거 태그에 `npc_private` 문자열이 남아 있어도 NPC 영역으로 변환하지 않는다.
4. 현재 입력에서 확인된 NPC마다 최적 기억 한 건을 선택하고 전체 두 건 제한을 제거한다. 직접 확인된 NPC가 있으면 그 집합 밖의 주관 기억은 선택하지 않는다.
5. 세션 주인 색인 뒤 확인된 여러 주인의 기억을 `OwnerEntityKeys` 한 번의 조회로 가져온다. 인물별 네 정렬 조회와 뒤따르는 전체 최신 조회는 제거한다.
6. 메인 기억 검색 결과는 세계·인물·관계·근거 검색문을 확장하지 않는다. 다른 자료 영역은 현재 사용자 입력과 바로 전 assistant 출력으로만 관련성을 판단한다.
7. 직접 근거, 세계 규칙, canonical 상태, 사건 요약은 현재 장면 관련성이 있을 때만 전달 후보가 된다. 최신 행·최신 사건이라는 이유의 무조건 통과는 제거한다.
8. 자료별 예산이 남아도 무관 후보를 끌어오거나 다른 영역의 잔여 항목을 차용하지 않는다.

자동 검증은 전체 Go 시험을 통과했다. 실제 RisuAI payload, 장기 200·300턴, 재시작·리롤·삭제·분기, 벡터 장애 검증 전 상태는 계속 `implemented_unverified`다. 이번 교정은 Go 읽기·선별·조립과 그 시험·문서만 변경했으며 JavaScript 증감은 `0/0`줄이다.
