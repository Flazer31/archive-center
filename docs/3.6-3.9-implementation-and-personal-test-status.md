# Archive Center 3.6–3.9 구현·문서·개인 테스트 상태 장부

상태: `3.9-A~F source_implemented / 3.9.0 release packages built /
Windows managed runtime verified / POSIX real-device verification pending`

기준일: 2026-08-01

> 2026-08-22 기준 Pre-4.0.0 단계 0–9, UI·세계선·기억·공급자·복구·시험 패키지의
> 최신 종합 기록은
> [`archive-center-pre-4.0.0-work-ledger-2026-08-22.md`](archive-center-pre-4.0.0-work-ledger-2026-08-22.md)에서
> 이어서 관리한다. 이 문서의 3.6–3.9 당시 판정은 과거 기준선으로 보존한다.

이 문서는 3.6부터 3.9까지의 설계 문서와 현재 production source를 대조해 다음 네 상태를
구분한다.

1. 문서에 적혀 있고 현재 source에도 구현된 항목
2. source에는 구현됐지만 기존 문서의 상태나 설명에 반영되지 않았던 항목
3. 문서에는 목표로 적혀 있으나 아직 구현·검증이 끝나지 않은 항목
4. source·자동 회귀까지만 확인됐고 실제 RisuAI·MariaDB·Chroma에서 검증해야 하는 항목

`release_ready=true`는 패키지에 필요한 관리 파일이 갖춰졌다는 build manifest 판정이다.
이 값만으로 3.9 기능의 loaded/live release gate가 통과한 것은 아니다.

주요 자동 회귀 파일은 `relationship_state_test.go`, `habit_evidence_test.go`,
`character_profile_voice_test.go`, `prepare_turn_character_memory_test.go`,
`publisher_plan_test.go`다.

## 4. source에는 있었지만 기존 상태 문서에 충분히 적히지 않았던 항목

### 주관 기억 생성 계약

- 매 턴·매 인물 1개를 강제하지 않는다. 최신 accepted turn에 별개의 source-grounded 관점
  내용이 있을 때만 생성 후보가 된다.
- 제3자 서술이나 객관 사건만 있는 턴은 0개가 정상이다. 인물 목록을 채우기 위한 기억을
  발명하지 않는다.
- protagonist와 NPC, explicit public과 owner-private 의미를 분리하고, 보호 기억은 exact
  evidence와 reveal policy가 없으면 저장하지 않는다.
- Critic이 유효한 빈 배열을 반환한 경우 `zero_unclassified_no_candidate` trace를 남긴다.
  현재 계약만으로는 “정말 후보가 없었음”과 “모델이 후보를 놓침”을 완전히 구분할 수
  없으므로 개인 테스트에서 원문과 trace를 함께 확인해야 한다.

### 장기 세션과 숫자 cap 제거

- persona capsule과 주관 기억 후보를 `200개` 같은 임의 개수로 미리 잘라내지 않는다.
- candidate read·recollection·character delivery는 적격 항목을 먼저 보존하고 최종 관련성,
  privacy/lifecycle, 중복 제거와 문자 예산에서 전달량을 결정한다.
- 1,205개 persona memory fixture가 오래된 기억까지 capsule에 보존되는 회귀를 갖는다.
  이 수는 제품 상한이 아니라 “작은 고정 cap이 없어야 한다”는 음성군이다.
- `count_cap=nil`, `candidate_count_cap=nil`은 무제한 prompt를 뜻하지 않는다. 최종 payload는
  사용자 K와 lane별 문자 예산을 계속 지킨다.

### 말투와 Publisher

- 말투는 과거 문장을 재사용하는 저장소가 아니라 source-backed 원리의 projection이다.
  상대·상태·장면에 따른 직접성, 완곡성, 회피, 호칭, 문장 길이와 행동 경향을 표현한다.
- 말투 projection은 장면·감정·사건을 강제하지 않으며 canonical truth나 relationship write
  권한이 없다.
- `proposal_0`은 Publisher plan을 만들지 못했거나 만들 필요가 없는 정상적인 0-plan 상태다.
  base memory·direct evidence·secret guard는 계속 전달된다.
- Publisher는 실제 main payload에 전달되지 않은 character-memory ref를 근거로 쓸 수 없다.
- 2026-08-02 재검증에서 자동 회귀와 prompt가 3.6-F의 표현 reviewer coverage를 여전히
  고정해 3.9-F 문서 계약보다 좁게 동작하는 불일치를 확인했다. 기존 Go 경로에서
  accepted previous completed turn을 continuity-only support로 연결하고, weak의 응답 초점·
  must-account·continuity·인물/관계 표현, medium의 pacing·scene emphasis, strong의 가역적
  장면 초점이 단일 guidance block으로 이어지도록 정정했다.
- Supervisor LLM이 정상 실행됐지만 적용 항목이 0개인 경우는 `proposal_0`으로 남기되 호출
  stage를 `succeeded`로 기록한다. provider 미호출을 뜻하는 `skipped`와 혼동하지 않는다.

## 5. 문서에는 적혀 있지만 아직 완료되지 않은 항목

### 3.6~3.8 누적 live gate

- 실제 사용자 DB의 clone migration·dry-run·rollback과 cross-turn identity review/split/merge
- 실제 RisuAI의 streaming·reroll·edit·delete·copy/move/branch lifecycle 전 조합
- real MariaDB transaction과 Chroma endpoint의 stale write·재시작·복구
- 실제 OpenAI·Vertex/Gemini·Claude provider의 typed failure와 품질 비교

### 3.9-G

- correction, entity merge/split, reroll, edit, delete, branch 이후 relation/profile/voice와
  Publisher input이 같은 accepted source revision으로 국소 재구축되는 end-to-end 증거
- stale plan·old generation·삭제된 source의 재사용 0
- 이 packet은 4.1 전체 transaction/outbox/OS lifecycle을 대신하지 않는다.

### 3.9-H

- 실제 RisuAI payload와 displayed final에서 single guidance lane과 source ref 일치
- 기억 OFF, Publisher OFF, strength 변화, provider 장애와 explicit redirection 비교
- 장기 RP에서 first-output 채택률, 리롤 사유, 지연·비용과 관계·말투 품질 관찰
- 사용자 배포 artifact의 hash와 source/build manifest 연결

## 7. 설치 후 검증 순서

1. 기존 `.runtime`과 중요한 사용자 DB는 평소 방식으로 백업한다. 패키지가 이를 초기화하도록
   두지 않는다.
2. 압축을 푼 폴더에서 `01_start_archive_center_windows.bat`를 실행한다.
3. 콘솔에서 MariaDB·ChromaDB 준비와 Go backend ready를 확인한 뒤
   `02_smoke_test_windows.bat`를 실행한다.
4. 같은 폴더의 `Archive Center.js`를 RisuAI에 등록하고 Bridge URL을 확인한다.
5. 기존 장기 세션과 분리된 개인 테스트 chat에서 아래 시나리오를 먼저 재현한다.
6. 오류가 없으면 실제 장기 RP로 이어서 누적 품질을 관찰한다. 특정 턴 수 하나를 합격
   기준으로 삼지 않고 누락·오염·stale 재사용·지연 추세를 기록한다.

- RisuAI plugin build ID와 backend `/version`, `/ready`
- 해당 turn의 원문, accepted/reroll/edit/delete 상태와 source revision

- 오류 코드, 재현 순서, 첫 출력 채택 또는 리롤 이유, 체감 지연

## 8. 다음 단계 판정

개인 테스트에서 source/knower/privacy 오염, stale 재사용, main 응답 차단 또는 데이터 손상이
재현되면 3.9 사용자 배포를 중단하고 먼저 수정한다. blocker가 없고 패키지 설치·기동,
주관 기억·관계·profile·말투·Publisher의 핵심 시나리오가 실제 artifact에서 확인되면 3.9
사용자 배포 후보를 만든다. 이후 버그·피드백을 수집하고 수정한 뒤 4.0 recall·delivery로
넘어간다.
