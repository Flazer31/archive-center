### 0.1 사용자 확정 목적과 의미 보존

- 이 문서의 중심 소유권은 **정밀 장기 기억**이다. 3.9의 기존 bounded Basic Publisher는
  오류 안정화까지만 유지하고, 1.0의 `book_author + director` 체감 복구는 4.0이 소유한다.
  이 Publisher는 관계·profile과
  기억의 truth·importance·검색 순위를 다시 쓰지 않으며 세부 계약은
  [`3.9-character-memory-basic-publisher-roadmap.md`](3.9-character-memory-basic-publisher-roadmap.md)를
  따른다.
- 기억을 근거로 대규모 활성 인물·장면 흐름·세계·세력·thread와 모델 적응형 감독을 계산하는
  고급 RP 지원은 4.6~5.0의 별도 목적이다. 장기 기억 중심이라는 이유로 그 목적을
  삭제·축소·폐기로 재해석하지 않는다.
- 4.0의 선택·보류·전달 사유와 4.1의 realization·thread lifecycle은 무엇이 기억됐고 실제로
  발생·해결·보류·포기됐는지를 설명하는 비구속 상태다. 이를 “이번 응답에서 진행하라”,
  “이 인물을 등장시켜라”, “이 사건을 아직 해결하지 마라”, “장면을 정적으로 유지하라” 같은
  서사 실행 명령으로 조립하지 않는다.
- 4.1은 관련 기억을 선택하고 무관·중복 기억을 제외할 수 있지만, 어떤 thread를 이야기의
  전면에 둘지, 어떤 합법적 전개를 택할지, 장면의 속도·사건 수·결말을 정하지 않는다.
- 이미 발생한 결과와 아직 남아 있는 결과, 해결·보류·포기·재개 상태를 정확히 보존하는 것은
  서사 강제가 아니라 과거 사건의 재연·부활·전체 종결 오판을 막는 장기 기억 책임이다.

이 절은 3.6~4.1의 기억 용어가 4.6~5.0의 실행 지원 의미로 확대되는 것을 막는 우선 해석
기준이다. 3.9의 기존 bounded proposal과 4.0 `publisher_plan.v2`도 이 경계를 넘지 않는다.

### 0.2 공식 RisuAI 적합성 상속

3.6~4.1의 모든 작업은 `permanent-risu-host-backend-boundary.md`의
`Official RisuAI Conformance Baseline`과 3.3 source spine을 그대로 상속한다. 구현 전에 지원할
공식 RisuAI 버전의 문서와 upstream source/type에서 메시지 구조와 input·request·streaming·
response·display·reroll·edit·delete·branch 순서를 확인하고, commit 또는 tag·날짜·확인한
hook/type을 release evidence에 기록한다.

- 4.1은 RisuAI source를 다시 수집하거나 임의 필드·문구·DOM 모양으로 보완하지 않는다.
  3.3이 공식 host shape에서 관찰하고 Go가 승인한 source envelope와 lifecycle만 소비한다.
- 공식 RisuAI가 노출하지 않은 revision·generation·display·visibility는
  `unobserved`/`not_exposed`로 유지한다. 이를 `false`, `true`, 생성한 번호 또는 내용 hash만으로
  확정해 memory admission·삭제·리롤·관계·상태 판정을 수행하지 않는다.
- JavaScript는 공식 RisuAI 관찰과 backend 결과 적용만 담당한다. 기억 원자화, truth·identity·
  story time·knowledge·relation·recall·저장·복구 정책은 Go가 소유한다.
- 공식 shape 기반 production adapter 시험과 실제 RisuAI의 저장·리롤·편집·삭제·분기·재시작
  lifecycle 증거가 없으면 전체 Go 시험이 통과해도 4.1을 `release_gate_verified`로 표시하지 않는다.

RisuAI upstream 변경은 기존 adapter와 3.3 observation contract의 versioned 변경으로 먼저
흡수한다. 4.1 기억 계층에 별도 host parser, watcher, 추정 revision 또는 병렬 저장 경로를 추가하지 않는다.

## 1. 결정

Archive Center 3.6~4.1 누적 구간의 중심 목표를 **정밀 장기 기억**으로 확정한다.

4.1은 기억의 양을 무조건 늘리는 버전이 아니다. 정상 저장된 대화의 원문을 잃지
않고, 그 원문에서 파생된 사건·상태·발언·인물별 인식을 근거와 함께 보존하며,
현재 장면에서 필요한 기억만 정확하게 회수하는 버전이다.

```text
원문 보존
-> 근거 있는 원자적 기억
-> 이야기 시간과 인물별 인식 연결
-> MariaDB hard filter
-> 복합 검색과 회상 계획
-> Go backend 최종 주입 계획
-> RisuAI payload 적용
```

기존에 논의한 캐릭터 출력 감독, 다중 인물 시뮬레이션, 응답 재작성과 멀티에이전트
품질 보조는 4.1 메인 기억의 소유물이 아니다. 이들은 4.1 기억을 읽는 후속
소비자가 될 수 있지만 기억의 사실성, 중요도, admission이나 검색 순위를 바꾸지
않는다.

이 문서는 `_archive/future-reference`의 Step 26~28과
`_archive/reference/character-modules`의 장기 기억 요구를 현재 Go/MariaDB/ChromaDB

## 2. 원작 DB와 3.3-3.5 선행 기능의 영구 경계

### 2.1 3.1-3.2 원작 DB

현재 3.1-3.2의 원작 DB 작업과 4.1 메인 장기 기억은 별도 작업이다.

| 구분 | 메인 장기 기억 4.1 | 원작 DB 3.1-3.2 |
| --- | --- | --- |
| 대상 | 실제 세션에서 일어난 일과 인물의 기억 | 외부 작품의 승인된 Canon 참고 자료 |
| canonical truth | MariaDB의 세션 원문·근거·파생 상태 | 별도 `reference_*` 및 Canon Pack storage |
| vector index | 메인 기억 Chroma collection | 원작 전용 Chroma collection |
| 예산 | 메인 기억 예산 `max_injection_chars` | 독립 원작 예산 계약 |
| 실패 영향 | 메인 저장·검색·주입 상태로 보고 | 메인 시작·ready·저장·장기 기억을 막지 않음 |
| 쓰기 경계 | 원작 row를 수정하지 않음 | 메인 기억 row를 수정하지 않음 |

원작 사실은 세션에서 실제로 발생한 사건이 아니다. 원작 자료가 검색되었다는 이유로
메인 기억, 인물의 경험, 습관 또는 관계 변화로 자동 승격하지 않는다. 세션에서 해당
사실이 실제로 언급되거나 사건에 사용된 경우에도 메인 기억은 그 세션 원문을 직접
근거로 삼고, 원작 자료는 별도 provenance로만 연결한다.

원작 DB가 비활성·빈 상태·degraded·failed여도 4.1 메인 기억은 정상 작동해야 한다.
3.1-3.2 작업 중에는 기존 메인 기억 sentinel이 변하지 않는지 계속 감시한다.

### 2.2 3.3-3.5 Host Context·출력 충실성

`3.1-3.5-consolidated-release.md`는 3.1~3.5의 공통 source integrity와 RisuAI Host Context, 현재
장면에 필요한 설정을 읽고, 생성 전 `response_execution_contract.v1`로 실제 payload에
적용하는 선행 기능을 소유한다. 4.1은 이 기능을 장기 기억 저장·검색 owner로 흡수하지 않는다.

- 3.5 전처리는 4.1이 admission한 기억과 source ID를 읽을 수 있지만 중요도·truth·관계·
  thread lifecycle을 다시 계산하거나 canonical row를 직접 쓸 수 없다.
- 요청 단위 명사 언급·개체·관계 주장·Direct Evidence 연결은 3.5 결과가 아니다. 4.1은
  stable identity·관계 lifecycle·정밀 recall을 제공하되, 이들을 하나의 관계 graph와 UI로
  묶는 4.6 기능을 선행 구현하거나 임시 projection으로 대체하지 않는다.
- `narrative_support_max_chars`는 메인 기억 `max_injection_chars`를 줄이거나 대신할 수 없다.
  RisuAI가 이미 payload에 넣은 native Host Context 원문은 별도 Archive Center 주입 예산으로 중복 계산하지
  않는다. 3.3~3.5에는 raw-lore reader·보완 lane이 존재하지 않는다.
- 4.1의 memory delivery가 바뀌어도 3.5 guide OFF parity, 실제 payload span/hash와 장애
  격리 계약을 보존해야 한다.
- 감독관 proposal과 final displayed occurrence는 4.1 admission 없이 기억·관계·사건·종료
  authority가 되지 않는다.

### 2.3 3.6~4.1 정밀 장기 기억의 버전 소유권

3.5까지의 source integrity·Host Context·출력 전처리와 3.6부터의 메인 장기 기억 작업을 같은 기능으로 묶지
않는다. 3.6~4.1은 이 문서의 단계 0~7을 다음 release 단위로 수행한다.

|---|---|---|
| 3.6 | 3.3 source spine을 소비하는 stable entity/speaker identity, 원자적 기억과 truth/authority admission, migration·reprocess 기반 | 단계 0~1 중 메인 기억 범위 |
| 3.7 | 3.5–3.6 현장 오류의 전체 안정화: final-output 확정, queue/idempotency, critic/provider, session migration·binding, Windows Chroma·MariaDB·updater와 HUD 사실성 | 3.7 감사 계획의 P0~P2 |

각 버전은 preparatory 상태와 production 검증 상태를 구분하고, 4.1은 단계 0~7 전체의
release evidence가 연결된 경우에만 완료다.

소유권 경계는 다음과 같다.

- 3.3~3.5는 공통 source envelope·acceptance lifecycle, actual Host Context의 source evidence와
  출력 guide를 소유하고 전체 raw lore 저장·검색이나 메인 기억 row를 쓰지 않는다.
- 3.6~4.1은 세션 원문에서 파생되는 memory admission·state·관계·profile·recall·delivery를

- 3.6의 stable `entity_identity.v1`과 4.0의 `memory_recall_plan.v2`는 4.6 관계 graph가

  두 번째 planner나 관계 UI를 먼저 만들지 않는다.
- 4.1 memory delivery는 `max_injection_chars` 안에서만 작동한다. 출력 guide의
  `narrative_support_max_chars`를 빌리거나 그 예산을 대신 계산하지 않는다.
- 3.4의 메인 기억 전달·분류 예산 정본은
  [`3.1-3.5-consolidated-release.md`](3.1-3.5-consolidated-release.md)에 통합됐으며

  body/relationship current-history와 완성형 coverage planner의 권위는 이 문서의 3.6~4.0가
  계속 소유한다. 3.4 임시 분류가 truth·admission·검색 completeness를 선결정하지 않는다.
- 4.1 이후의 대규모 활성 인물 선택, 캐릭터 실행 카드, 세계·세력 simulation과 모델 능력
  적응형 고급 감독은 4.6~5.0 후속 소비자이며 3.6~4.1 완료 범위가 아니다.

## 3. 이 문서에서 말하는 완벽한 기억

완벽은 모델이 모든 모호한 문장을 정답으로 해석하거나 모든 세부사항을 매번
프롬프트에 넣는다는 뜻이 아니다. 다음 불변 조건을 목표로 한다.

1. **원문 보존**: 정상 완료·저장된 턴은 정확한 role, message, turn과 hash로
   추적할 수 있다.
2. **근거 결합**: 파생 기억은 원문 turn·message ID·excerpt·hash로 돌아갈 수 있다.
3. **정직한 불확실성**: 근거가 없거나 시간이 모호하면 추측한 사실이나 날짜를 만들지
   않는다.
4. **관점 분리**: DB가 아는 사실과 특정 인물이 아는 사실을 구분한다.
5. **가역 상태**: 정정·변경·오해 해소 뒤에도 이전 상태의 역사와 변경 근거를 보존한다.
6. **필요 시 회상**: 평상시에는 관련 기억만 주입하고, 직접적인 과거 질문 또는 현재
   장면의 entity·time·relationship·continuity에서 recall need가 생기면 오래된 원문
   근거까지 단계적으로 탐색한다.
7. **생명주기 정합성**: 삭제·롤백·복사·이동·재색인 뒤 무효한 기억이나 vector가
   다시 나타나지 않는다. 관련 기존 코드 변경이 필요하면 별도 재현과 승인을 받는
   bounded item으로 분리한다.
8. **오류 비은폐**: 기억 없음, 새 기억 없음, 추출 실패, provider 없음과 검색 장애를
   서로 다른 안정적인 상태로 보고한다.

### 3.1 목표 축소 금지

4.1의 완벽한 정밀 기억 목표는 일부 중요 사건, 일부 기억 종류, 일부 언어, 일부
profile 또는 소수 예시 fixture만 처리하는 MVP로 축소할 수 없다. 저장·회수·관점·시간·
생명주기·주입 계약은 하나의 완료 범위다.

모든 세부사항을 매번 주입하지 않는다는 원칙은 근거 있는 세부 기억의 보존, 색인 또는
필요 시 회수를 생략할 권한이 아니다. 주입 선택성은 capture와 recall coverage를 축소할
수 없다.

단계, slice, preparatory schema, DTO, trace surface, shadow 비교 또는 일부 fixture 구현은
4.1 완료가 아니다. 이 문서의 필수 범위를 보류·제외하거나 후속 버전으로 이동하려면
다음을 제시하고 사용자의 명시적 승인을 받아 이 문서를 먼저 변경해야 한다.

- 원래 요구와 제외하려는 정확한 범위;
- 제외되는 실제 RP 사례;
- 데이터·회상·호환성 위험;
- 대안과 임시 owner;
- 다시 포함할 조건과 제거 기한.

작업을 여러 bounded item으로 나누는 것은 실행 순서만 분리한다. 원래 요구를 완료
범위에서 삭제하지 않는다.

이 문서에서 말하는 안전·보수성은 근거 없는 사실 승격, 비밀 누출, 잘못된 branch 적용과
메인 기능 장애 전파를 막는다는 뜻이다. 다음과 같은 의미 축소나 무기능화를 뜻하지 않는다.

- 명시적 source가 지지하는 사실을 구현이 어렵다는 이유로 hypothesis·`unknown`·
  `needs_review`에 영구 정체시키는 것;
- 중요하다고 미리 분류한 사건만 저장하고 생활 세부·정확한 발언·관계 맥락을 버리는 것;
- false positive를 피한다는 이유로 capture·admission·recall을 no-op 또는 진단-only로 만드는 것;
- 불확실한 일부 필드 때문에 같은 source에서 확정 가능한 다른 필드까지 전부 폐기하는 것;
- 관계·감정·상태 변화를 보수적으로 동결하여 명시적 단일 사건이 지지하는 큰 변화까지 막는 것;
- 비용·schema·provider·OS·일정 문제를 requirement 제외나 후속 이동의 근거로 사용하는 것.

근거가 불충분하면 확정 범위만 제한하고, 확인된 의미·원문·대안·불확실한 경계를 함께
보존한다. 가장 적게 주장하는 표현을 선택하더라도 source가 지지하는 의미까지 지워서는 안
된다. 과잉 승격과 과잉 억제, 잘못된 기억과 회수 가능한 기억의 누락은 대칭적인 실패다.

요구 문구에 둘 이상의 해석이 있고 그 선택이 범위·품질·사용자 체감을 바꾼다면 기존의
넓은 요구와 실제 RP 사례를 유지한 채 결정 항목으로 올린다. 구현자가 임의로 가장 작거나
가장 쉬운 해석을 채택할 수 없으며, 범위를 바꾸려면 12.5의 사용자 승인 절차를 따른다.

#### 3.1.1 최소 개선·안전 명목의 완료 위장 금지

작업 단위를 작게 나누는 것은 허용하지만 목표를 “현재 코드를 적게 바꾸는 수준”으로 다시
정의할 수는 없다. 다음 방식은 구현 완료로 인정하지 않는다.

- 가장 쉬운 기억 종류·언어·profile·happy path만 고친 뒤 전체 정밀 기억이 개선됐다고 보고;
- 실제 저장·회수·주입 대신 schema·prompt·경고·trace·진단 화면만 추가;
- 기존 기능 보호를 이유로 필요한 Go owner 연결을 생략하고 no-op·shadow-only 상태를 영구화;
- 오류 가능성을 줄인다는 이유로 known positive까지 저장·회수하지 않는 최소 행동을 선택;
- 현재 fixture의 고유 이름·문구·점수·개수·turn·예외 분기로 증상만 통과;
- 구현하지 못한 범위를 `optional`, `unknown`, `safe`, `degraded` 또는 후속 개선으로 바꿔 완료 집계.

bounded implementation은 증거에 따라 `preparatory`, `implemented_unverified` 또는
`blocked`로 정확히 보고하고 남은 requirement·owner·검증 gate를 그대로
유지해야 한다. “가장 적게 바꾸기”가 아니라 **확정된 목표 전체를 훼손하지 않으면서 현재
단계가 책임지는 범위를 완전하게 구현하기**가 최소 변경 원칙이다.

### 3.2 Requirement ledger

모든 구현 item은 다음 연결을 유지한다.

```text
사용자 원래 요구
-> requirement ID
-> 불변 조건
-> production owner
-> positive/negative/metamorphic fixture
-> 실환경 수용 게이트
-> completion evidence
```

최소 requirement ID는 다음과 같다.

| ID | 불변 조건 |
| --- | --- |
| `PM-RAW` | 정상 저장된 실제 원문과 final accepted output을 손실하지 않음 |
| `PM-SOURCE-IDENTITY` | session·chat·branch·request·generation·message·revision과 raw hash를 source envelope에서 분리하고 host observation보다 강한 ID를 추측하지 않음 |
| `PM-BOOTSTRAP` | 0턴의 복수 start message를 순서·role·개별 source로 보존하되 첫 사용자 입력과 무관하면 기억·원작 주입을 강제하지 않음 |
| `PM-ACCEPTANCE-LIFECYCLE` | streaming·candidate·active final·superseded·deleted generation을 구분하고 현재 활성 표시 출력만 canonical admission source가 될 수 있음 |
| `PM-ATOMIC` | 서로 다른 사건·관점·시간·비밀을 한 단위에 섞지 않음 |
| `PM-ENTITY-IDENTITY` | 이름 문자열이 아니라 stable entity/speaker ID와 alias·scope·split/merge lineage로 인물·화자를 연결 |
| `PM-HOST-CONTEXT-BINDING` | 3.5 `host_context_reference_evidence.v1`을 개체 존재·이름·별칭·설정 설명과 동일성 판단에 사용할 때 actual payload source span을 유지하고 Host setting, 원작 reference와 session entity namespace를 분리하며 Host-only identity에 등장·경험·현재 상태 권한을 부여하지 않음 |
| `PM-TIME` | story time, turn, branch와 현실 audit time을 분리 |
| `PM-PERSPECTIVE` | 인물별 known/unknown/believed/misunderstood/revealed 분리 |
| `PM-UTTERANCE` | 사용자 발언·청자·반응·정정이 정확한 source와 연결됨 |
| `PM-CHARACTER` | 성격·관계·말투·상태를 근거와 변화 이력으로 유지 |
| `PM-PROFILE-BOUNDARY` | 실제 user/OOC profile, player character와 NPC profile을 식별·저장·검색·전달 전 단계에서 분리 |
| `PM-CHAR-PROFILE` | stable baseline, current snapshot과 dynamic digest가 같은 evidence spine에서 파생되고 profile이 truth floor가 되지 않음 |
| `PM-TRAIT-SEMANTICS` | 능력·관심·직업·외형·지위·감정 같은 서로 다른 특성 영역을 분리하고, source evidence 없는 영역 간 성격·말투·행동 파생을 허용하지 않음 |
| `PM-RELATION-LIFECYCLE` | 관계를 방향·영역·근거·반례·상황·공개 범위별 current/history와 transition lineage로 유지하고 상호성·영속성·다른 관계 영역을 자동 파생하지 않음 |
| `PM-TURN-REALIZATION` | final displayed output에서 실제 실현된 사건·결과와 단순 언급·회상·요약을 분리하고 같은 root evidence가 새 사건이나 독립 근거로 증폭되지 않음 |
| `PM-THREAD-LIFECYCLE` | 복수의 미해결 thread를 source·branch·의존성·남은 결과·closure scope별 current/history로 보존하고 한 thread 해결을 sibling·parent·arc·saga·session 전체 종결로 확대하지 않음 |
| `PM-BODY` | 여성 인물의 주기·임신·출산·산후를 포함한 신체 상태를 근거·story time·공개 범위·변경 이력과 함께 유지 |
| `PM-CANDIDATE` | extractor·critic·agent 출력은 source-linked proposal이며 backend admission 없이 canonical write 불가 |
| `PM-AUTHORITY-ADMISSION` | source occurrence·발화·주장·객관 사실·인물별 인식·causal/agency/closure 권한을 분리하여 semantic proposal과 Go commit 검증을 연결 |
| `PM-DELIVERY` | 저장·검색·전달을 분리하고 Go가 item별 전달 상태·사유·coverage gap을 최종 소유 |
| `PM-MUNDANE` | 식사·날씨·복장·소지품·감각 같은 생활 세부를 필요 시 회수 |
| `PM-RECALL` | 구조화 기억이 부족하면 관련 원문까지 근거 기반으로 확장 검색 |
| `PM-LIFECYCLE` | reroll·삭제·rollback·copy·move·reindex 뒤 유령 기억 없음 |
| `PM-INVALIDATION` | source revision과 모든 파생 row·projection·vector의 dependency를 추적해 edit/delete/reroll 뒤 재투영하고 no-resurrection을 보장 |
| `PM-REPROCESS` | provider 부재·추출 실패 source를 원문 손실 없이 deferred queue로 보존하고 동일 source/version에 대해 멱등 재처리 |
| `PM-MIGRATION` | 기존 사용자 DB를 삭제·초기화하지 않고 resumable·idempotent backfill하며 근거가 부족한 row를 `legacy_unverified`로 정직하게 격리 |
| `PM-CONCURRENCY` | source revision barrier, stale worker rejection, transaction/outbox와 crash-safe resume로 반쪽 turn과 늦은 결과 덮어쓰기 방지 |
| `PM-CONTRACT-COMPAT` | 3.5 Host 계약·JS adapter·Go와 4.1 DB/index contract version을 협상하고 불일치 시 JS 정책 fallback 없이 정확한 lane 상태를 반환 |
| `PM-RAW-RECALL-COVERAGE` | exact/lexical·entity·structured·semantic raw route를 독립 추적하고 구조 기억이 부족할 때 오래된 원문까지 근거 기반으로 확장 |
| `PM-BUDGET` | Go가 동적 예산과 완전한 item/block 경계를 소유 |
| `PM-BOUNDARY` | 원작 DB·OOC/meta·후속 서사 보조와 truth/budget/failure 분리 |
| `PM-NO-HARDCODING` | 작품·문구·모델·점수·개수·비율·turn 정책 하드코딩 없음 |
| `PM-INTENT-FIDELITY` | 안전·보수성·불확실성·단계 구현을 이유로 명시된 기억 범위와 사용자 의도를 축소·공백화·진단-only로 바꾸지 않음 |
| `PM-EVIDENCE` | 모든 완료 주장이 production·실환경 증거로 추적됨 |

새 작업이 위 ID를 더 작은 의미로 재정의할 수 없다. 미구현 requirement는 문서에서
삭제하지 않고 `open`, `blocked` 또는 `implemented_unverified`로 남긴다.

## 4. 현재 재사용할 기반

새로운 평행 기억 DB를 먼저 만들지 않는다. 1차 구현은 현재 구조를 다음과 같이
재사용한다.

| 현재 구조 | 4.1에서의 역할 |
| --- | --- |
| `chat_logs` | 저장된 user/assistant 원문과 실제 턴 근거 |
| `effective_input_logs` | 당시 실제 user input과 input provenance |
| `memories` | 검색 가능한 원자적 기억 단위 |
| `direct_evidence_records` | excerpt, turn, message ID, hash와 archive lineage |
| `kg_triples` | 인물·장소·물건·사건 사이의 명시적 관계와 유효 범위 |
| `character_events` | 인물에게 일어난 변경·행동 이력 |
| `character_states` | 인물의 현재 외형·성격·상태·관계·말투 snapshot |
| `protagonist_entity_memories` | 인물별 주관적 기억, 비밀과 reveal policy |
| `pending_threads` | 약속·갈등·미해결 문제와 해결 이력 |

| `status_change_events` | 상태 변경 이력과 story-clock observation |

| physical/entity condition extraction | critic 결과의 owner·evidence·label을 확인한 뒤 `archive_canonical` status effect를 직접 저장하는 partial 기반; persisted proposal/review 단계는 없음 |
| `psychology_branches` | 근거 기반 습관·성향 가설을 위한 support-only 후보 |
| episode/chapter/arc/saga | 세부 기억을 대체하지 않는 상위 계층 요약 |

MariaDB가 계속 canonical truth이며 ChromaDB는 후보 selector다. Chroma 결과는 MariaDB
row로 hydration한 뒤 유효성, 관점, 시간과 archive 상태를 다시 검사한다.

### 4.1 현재 구현된 진입 기반과 남은 공백

- 3.3~3.5 production에는 `message_source_envelope.v1`, `session_bootstrap.v1`,
  `source_acceptance_lifecycle.v1`, `host_context_reference_evidence.v1`이 구현돼 있다.
  3.6은 이 계약의 active source ID·revision·branch·acceptance를 소비하며
  `chat_logs`, `effective_input_logs` 또는 evidence 문구에서 lifecycle을 다시 추정하지 않는다.
- `chat_logs`와 `effective_input_logs`의 기본 row는 여전히 turn·role·content 중심이다.
  따라서 3.6-A는 실제 production route의 source FK·transaction·기존 row 적용 범위를
  inventory해야 한다. 계약 이름이 존재한다는 사실만으로 legacy DB가 모두 backfill됐거나
  모든 final displayed lifecycle이 검증됐다고 간주하지 않는다.
- 0턴의 여러 start message를 개별 source로 보존하는 bootstrap 계약은 구현됐지만, 3.6
  atomic admission과 기존 DB migration에서 각 start source가 섞이지 않고 같은 active
  lifecycle을 따르는지는 production evidence로 닫아야 한다.
- 메인 기억의 `entities`, `character_events`, `character_states` 등은 이름 문자열 기반 연결이
  남아 있어 동명이인·별명·개명·복수 화자·서술자와 user/OOC 주체를 안정적으로 분리하는
  entity/speaker lifecycle이 부족하다. 원작 DB의 `reference_entities.entity_id`는 별도 namespace라
  메인 세션 entity ID를 대신하지 않는다.
- 현재 `entities`는 stable source ID·namespace·branch·field-level provenance·revision/tombstone과
  rename/split/merge lineage가 없어 lore-derived 이름·별칭·description을 안전하게 연결하거나
  철회할 수 없다. 3.5 lore 후보를 이 table에 직접 넣거나 `reference_entities`와 자동 병합하면
  설정상 존재와 세션 등장, 원작 Canon과 사용자 Host 설정이 뒤섞인다.
- 기존 row를 새 정밀 계약으로 올리는 migration/backfill, provider 실패 source의 deferred
  재처리, source edit/delete/reroll이 파생물 전체를 무효화하는 dependency registry와 동시성
  barrier가 아직 하나의 production 계약으로 연결되지 않았다.

- Critic은 중요한 변화 위주로 추출하므로 평범한 식사·날씨·작은 행동은 원문에만
  남을 수 있다.
- 한 턴의 여러 독립 사실이 하나의 요약 row에 섞이면 공개 사실과 비밀을 서로 다른
  관점으로 필터하기 어렵다.
- 이야기 속 날짜, 상대 시간, 현실 저장 시각과 turn 범위가 하나의 authority 계약으로
  통합되어 있지 않다.
- 단일 행동과 반복 습관, 상황 한정 행동과 안정된 성격을 구분하는 근거 누적 계약이
  부족하다.
- 현재 physical/entity condition 추출과 `status_effects` 저장 기반은 있지만, 인물별 신체
  baseline/current/history, 동일 상태의 dedup·회복·악화·해제 supersession, story-clock
  기반 만료 소비와 `/prepare-turn`의 보장된 신체 상태 회상은 완성되지 않았다.
- 현재 condition 경로는 별도 persisted proposal/review를 거치지 않고 critic extraction을
  `archive_canonical` effect로 직접 저장한다. 5.9의 proposal/challenge/backend admission은
  기존 구현 설명이 아니라 4.1에서 교체·보강할 미구현 계약이다.
- 여성 인물의 생리 주기, 임신 가능성·추정·확정·배제, 임신 단계, 출산과 산후 회복을
  generic health JSON 하나로 축소하지 않는 전용 의미 계약이 없다.
- RP 인물의 stable baseline, current snapshot과 dynamic digest를 같은 evidence spine에서
  파생하는 profile 계약이 없고, 실제 사용자 OOC profile과 player character/NPC profile의
  영구 경계도 더 명확히 해야 한다.
- 현재 profile에는 능력·관심·직업·외형·사회적 지위·안정적 성격·현재 감정·말투의
  의미 영역과 허용되는 영향 범위를 분리하는 계약이 없다. 한 속성을 근거 없이 다른
  영역의 행동으로 확장하거나 전형적 캐릭터상으로 치환하지 못하게 하는 evidence와
  counter-evidence 경계가 필요하다.
- 방향성 관계 snapshot과 관계 사건은 존재하지만, 신뢰·애정·친밀감·애착·의존·복종·
  동의처럼 의미가 다른 관계 영역의 current/history, 전이 근거, 반례와 rupture/recovery를
  하나의 lifecycle로 검증하는 계약이 없다. 사용자 입력, 일방 감정, 친절·도움·접촉·
  직무상 명령 이행이 상대 인물의 상호 감정이나 영구 관계 변화로 승격될 위험이 있다.
- final output, atomic event, summary와 profile digest가 같은 root evidence에서 파생됐는지
  표시하지 않으면, 다음 턴 회상에서 이미 실현된 사건과 그 요약이 동시에 전달되어
  모델이 사건을 다시 서술·발생시키고 그 paraphrase가 새 근거처럼 누적되는 반복 고리가
  생길 수 있다.
- `pending_threads`, `storylines`와 episode/chapter/arc/saga summary 사이에 atomic thread truth,
  derived aggregate와 closure authority의 owner 경계가 없다. request에서 선택된 한 thread를
  전체 active set으로 오인하거나 local resolution을 sibling·parent·arc·saga·session 전체
  종결로 확대하고, background·dormant thread의 남은 결과를 조용히 잃을 위험이 있다.
- Step 26의 active user profiling, Step 27의 native-context-aware delivery와 Step 28의
  visual/QH/QHM은 progress 문서상 완료 항목이 없고 활성 runtime·Git 이력에도 해당 계약이
  없다. 비슷한 persona, hard-floor, critic 기능을 해당 Step의 구현 증거로 사용하지 않는다.
- 인물 비공개 기억 선택에서 단순 이름 언급이 knowledge/POV 권한을 대신하지 않는지
  선행 감사가 필요하다.
- user message 안의 `POV`, `시점`, `관점` 같은 문구를 접근 권한의 authority로
  사용하지 않는지 감사해야 한다. 관점 권한은 신뢰할 수 있는 host observation과
  backend session state에서만 얻어야 한다.
- tombstone·superseded·validity 필터가 모든 evidence와 retrieval 경로에 동일하게
  적용되는지 보장되지 않는다.
- exact excerpt가 원문에 존재한다는 사실은 그 문장이 말해졌다는 근거일 뿐, 그 내용이
  객관적 진실이라는 자동 승인 근거가 아니다. scope가 불명확한 claim을 objective로
  기본 승격하지 않는다.
- 비슷한 문장을 고정 유사도 하나로 합치면 다른 시간·관점·상태의 기억이 손실될 수
  있다.
- 긴 세션에서 전체 row를 읽은 뒤 메모리에서 선별하는 경로는 성능 한계가 생길 수
  있다.
- 최종 주입 예산과 후단 절단에 JavaScript 소유권이 남아 있다. 4.1 완료 시에는 Go가
  item과 block 경계를 보존한 최종 계획을 소유해야 한다.
- 현재 `001_schema.sql`에는 일부 상위 요약 table의 중복 선언이 있으므로 4.1 migration
  전에 fresh install 결과와 실제 적용 정의를 감사해야 한다. 정리는 별도 preparatory
  item이며 새 기억 기능과 한 번에 섞지 않는다.

## 5. 논리 데이터 계약

아래 계약은 먼저 기존 JSON, evidence, status와 audit 구조 위에 정의한다. 실제 부하나
무결성 실패로 기존 구조가 부족하다고 재현된 뒤에만 additive column 또는 table을
승인한다.

### 5.A `message_source_envelope.v1`

상세 정의는 이 문서가 보존하지만 production 구현·release owner는 3.3이다. 3.6은 active
envelope를 메인 admission의 source FK로 소비하며 별도 source classifier를 만들지 않는다.

모든 raw user/assistant/system/start source는 파생 기억보다 먼저 다음 identity와 원문을 가진다.

- backend source ID와 contract version;
- host에서 실제 관찰된 session·chat·branch·request·generation·message ID와 message index;
- role/channel, raw content, normalized 없이 계산한 content hash와 관찰 시각;
- revision, predecessor/supersedes relation과 host lifecycle observation;
- streaming 여부, final display confirmation, 삭제·reroll·edit 관찰;
- source origin(`user_input`, `assistant_output`, `start_message`, `host_context`, `ooc/meta`)과
  capability provenance;
- 원문 role과 in-world speaker attribution을 분리한 span reference.

JavaScript는 host가 노출한 값과 실제 표시·삭제 관찰만 전달한다. host ID가 없으면 Go가
scope가 제한된 backend ID를 만들 수 있지만 이를 host-native ID로 표시하지 않고 collision,
replacement와 removal condition을 trace에 남긴다. content hash만으로 다른 branch·message·
speaker를 합치지 않는다. raw source 저장과 active lifecycle 확정은 파생 추출 성공에 의존하지
않는다.

### 5.B `session_bootstrap.v1`

상세 정의는 이 문서가 보존하지만 production 구현·release owner는 3.3이다.

0턴에 여러 start message가 있으면 host order, role, source envelope와 scope를 유지한 개별
source로 보존한다. 전체 start message를 하나의 발화·사건·화자·요약으로 합치지 않는다.

- start source 자체는 자동으로 실제 발생 사건, 인물별 기억, 관계 변화나 원작 사실이 아니다;
- 첫 user input에서 현재 응답에 필요한 start source만 retrieval candidate가 될 수 있다;
- 첫 input이 의미 없거나 start source와 연결할 근거가 없으면 원문만 보존하고
  `no_new_memory/not_applicable`로 진행한다;
- 첫 input을 특정 문구·길이·언어로 분류하지 않고 host lifecycle, 참조 대상, scene/entity와
  semantic evidence로 eligibility를 판정한다;
- chat 복사·이동·분기에서는 start source identity와 새 session lineage를 모두 보존하고 원래
  session의 canonical event를 복제하지 않는다.

start source는 role이나 문장 형식과 무관하게 `active_final` 또는 3.4
`prior_response_source`가 아니다. first/start-only 요청의 prior response는 `absent`이며, start
source는 bootstrap/Host lane에서만 현재 입력과의 관련성을 검증받는다. 이를 직전 assistant
응답으로 대체해 recap·continuation·memory admission을 만들지 않는다.

이 계약은 이전에 보류한 0턴 요약·개체 자동 생성의 우회 구현이 아니다. 3.3에서 source
보존과 first-turn eligibility만 먼저 확정하고, 3.6의 의미상 memory admission은 일반
5.9·7장 경로를 그대로 사용한다.

### 5.C `entity_identity.v1`과 speaker attribution

메인 세션 entity는 표시 이름과 분리된 stable backend ID를 가진다. 최소 의미는 다음과 같다.

- session/global 범위, entity kind와 user/OOC·player character·NPC·group·unknown namespace;
- identity namespace와 presence authority: session-observed, Host setting/reference-defined,
  원작 reference cross-link를 구분하고 같은 표시 이름이어도 자동 병합하지 않음;
- canonical display label과 source-linked alias/호칭의 유효 시간·scope;
- create, alias-add/remove, rename, tentative-link, split, merge, retire와 tombstone lineage;
- 원본 role, narrator, quoted speaker, 복수 speaker span과 attribution confidence/review state;
- 원작 reference entity와의 optional cross-reference. 이 연결은 namespace 병합이나 세션 truth
  승격이 아니다.

이름 일치, 별명 유사도 또는 모델의 단일 추측만으로 entity를 merge하지 않는다. ambiguous
speaker는 `unknown/tentative`로 보존하되 원문 자체는 잃지 않는다. split/merge는 과거 source를
다시 쓰지 않고 mapping revision과 영향을 받는 projection/index의 rebuild를 발생시킨다.

3.6 admission은 3.5 `host_context_reference_evidence.v1`의 exact payload source span·관찰 가능한 Host metadata·scope·branch와
entity/alias/link 후보를 실제 identity context로 소비한다. 가능한 결정은 최소
`reference_created`, `linked`, `tentative`, `needs_review`, `rejected`, `superseded`를 구분하고
identity evidence refs, mapping/binding revision과 idempotency key를 가진다. lore source가
명시한 설정상 entity는 안정 ID로 생성할 수 있지만 `session_presence=unobserved`,
`occurrence_authority=none`과 동등한 상태를 유지한다.

실제 active session source에서 entity가 언급·등장하면 lore evidence는 이름·별칭·종류·설명과
동일성 판정의 강한 보조 근거가 될 수 있다. 그러나 session mention/occurrence의 root evidence를
대체하지 않고, lore claim만으로 event, relationship/body current, knower, turn realization을
만들지 않는다. Host setting identity, session identity와 원작 `reference_entities.entity_id`는
명시적 binding으로 연결할 수 있지만 ID를 재사용하거나 row를 서로의 namespace로 이동시키지
않는다.

lore revision·비활성·삭제는 해당 binding·alias/assertion의 source dependency를 invalidation한다.
독립 session evidence가 있는 identity는 보존하며 Host-only binding만 retire/tombstone한다.
rename·동명이인·shared alias는 자동 overwrite가 아니라 tentative-link·split/merge proposal과
mapping revision을 거쳐야 한다. vector similarity는 후보 검색일 뿐 identity admission 권한이
아니다.

### 5.D `source_acceptance_lifecycle.v1`

상세 정의는 이 문서가 보존하지만 production 구현·release owner는 3.3이다. 3.6 이후의
admission·reprocess·recall은 이 active/superseded/deleted 판정을 소비할 뿐 재판정하지 않는다.

`accepted`는 사용자의 품질 만족을 의미하지 않는다. Archive Center에서 canonical admission에
사용할 수 있는 **현재 활성 final displayed generation**을 뜻한다. 최소 상태는
`observed`, `streaming`, `display_candidate`, `active_final`, `superseded`, `deleted`,
`invalidated`를 구분한다.

- streaming·중간 chunk·표시되지 않은 candidate는 raw audit 외 canonical memory source가 아니다;
- JS가 final displayed message ID/hash와 host lifecycle을 확인하면 Go가 branch/revision barrier를
  검사한 뒤 `active_final`을 결정한다;
- reroll은 이전 active final을 `superseded`, 삭제는 `deleted`, edit는 새 source revision과
  predecessor를 만든다;
- 늦게 도착한 extractor·critic·vector 결과는 source revision이 더 이상 active하지 않으면
  canonical commit할 수 없다;
- host가 명시적 accept 이벤트를 제공하지 않으면 그 사실을 capability로 남기고 final display
  관찰과 현재 branch 상태만으로 정의한다. 지연 시간이나 “다음 턴 도착”을 accept의 고정
  휴리스틱으로 사용하지 않는다.

### 5.E `memory_derivation_dependency.v1`

모든 atomic memory, evidence edge, current projection, summary/profile/thread projection과 vector
item은 root source ID·revision, derivation contract/extractor/index version과 parent IDs를 가진다.
edit·delete·reroll·branch retirement·entity split/merge가 발생하면 Go lifecycle owner가 영향
집합을 계산해 다음 순서로 처리한다.

영향 집합은 직접 child만이 아니라 source/message ancestry와 derivation graph의 transitive
descendant, 무효 source·state·relation·thread를 읽어 생성된 후속 turn realization·current
projection·summary/profile·index까지 포함한다. 후속 source 자체가 여전히 active여도 전제가
바뀌면 자동 삭제하지 않고 stale dependency로 격리해 재심사·재투영하며, 그 전에는 current
truth나 모델 payload로 전달하지 않는다.

1. 새 admission을 revision barrier로 차단한다.
2. canonical truth transaction에서 tombstone/supersession과 current projection 재계산을
   기록한다.
3. idempotent outbox로 vector delete/upsert와 파생 rebuild를 수행한다.
4. 완료 전 candidate·recall·delivery는 이전 active revision을 새 truth로 노출하지 않는다.

삭제된 source를 background replay, 재색인, crash restart 또는 stale cache가 되살리면
`PM-INVALIDATION` 실패다. 파생물을 찾기 위해 JSON 전수 scan이 필요한 상태가 실제 부하·
무결성 gate를 만족하지 못하면 필요한 normalized index/migration은 4.1 필수 범위다.

### 5.F `memory_reprocessing_job.v1`

`deferred_no_provider`, `extract_failed`와 contract upgrade 대상 source는 원문과 source revision을
유지한 bounded job으로 재처리한다. job은 source ID/revision, derivation contract·extractor·
embedding/index version, attempt 결과와 retryability를 가진다. Go가 queue selection, lease,
backoff, stale 검사와 commit을 소유하며 JavaScript timer/watcher가 재처리 정책을 갖지 않는다.

이 backend queue와 MariaDB/Chroma outbox는 영속 source/derivation 작업만 처리한다. 3.5 JS
adapter의 process-local active-request transport queue와 ID·status namespace·retention을 공유하지
않고, live guidance request/result를 보관하거나 다음 payload에 돌려주는 fallback으로 사용하지
않는다. 양쪽은 commit 시 source revision fence만 비교하며 서로의 전달 순서를 보장하지 않는다.

동일 source/version의 재실행은 같은 canonical 결과 또는 명시적 supersession으로 수렴해야
한다. provider가 복구돼도 삭제·superseded source는 재처리하지 않고, 부분 성공을 전체 완료로
보고하지 않는다. no-provider 경로에서도 raw 저장·검색 가능한 최소 lexical identity와
향후 replay eligibility는 보존한다.

### 5.G `memory_contract_capabilities.v1`

3.5의 `risu_host_context_snapshot.v1`, JS adapter와 Go API는 지원 contract version과
capability를 교환한다. Go는 required capability 누락을 stable error,
retryability와 영향 lane으로 반환한다. 불일치가 Host Context 또는 정밀 기억의 일부를 막더라도
메인 시작·raw 저장·기존 장기 기억을 가능한 범위에서 보존하고, 검증되지 않은 새 파생 write는
중단한다.

JS는 이전 budget·turn·selection·prompt assembly를 fallback으로 되살리지 않는다. 호환 창이
필요하면 최소 backend version, bounded dual-read 필요성, 단일 canonical writer, atomic cutover,
migration owner, telemetry와 제거 조건을 versioned contract에 명시한다. silent dual-write와
무기한 silent downgrade는 허용하지 않는다.

### 5.1 `precise_memory_unit.v1`

한 기억 단위는 한 사건, 한 상태 주장, 한 발언, 한 인식 또는 한 약속만 표현한다.

필수 의미 필드:

- record ID와 contract version;
- session, branch와 source turn range;
- source message IDs, exact excerpt와 source hash;
- `event`, `state`, `utterance`, `observation`, `promise`, `secret`,
  `preference_evidence`, `habit_evidence`, `correction`, `other_evidence_bound`를 포함하는
  최소 상위 kind와 versioned subtype;
- actor, affected entity, location, object와 관계 key;
- objective, owner-scoped, hearsay, inferred, misunderstood 중 epistemic mode;
- knowledge holder, visibility와 reveal condition;
- story-time observation과 precision;
- active, superseded, retracted, tombstoned 등 lifecycle;
- contradiction/supersession lineage;
- 언어와 alias metadata.

한 row에 공개 사실과 비밀, 서로 다른 knowledge holder, 서로 다른 시간 범위를 섞지
않는다. 모델 요약문을 원문 인용으로 표시하지 않는다.

### 5.2 `story_clock.v1`

이야기 시간은 다음을 구분한다.

- 원문에 명시된 절대 날짜와 시간;
- daypart, 계절과 같이 일부만 알려진 시간;
- 이전 사건에 대한 상대 시간;
- 시작과 끝만 제한된 범위;
- flashback, 회상, 계획과 실제 발생;
- branch별 시간;
- 알 수 없음.

상대 시간은 근거가 되는 기존 clock anchor가 있을 때만 계산한다. `어제`, `다음 날`,
`몇 달 전`을 server `created_at` 기준으로 바꾸지 않는다. `unknown`을 임의의 정확한
날짜로 승격하지 않는다.

### 5.3 `perspective_memory.v1`

사건마다 다음을 분리할 수 있어야 한다.

```text
objective event
├─ 직접 목격함
├─ 전달받음
├─ 추론함
├─ 오해함
├─ 아직 모름
└─ 알고 있지만 숨김
```

현재 입력에 인물 이름이 있다는 사실은 그 인물의 비밀을 공개할 권한이 아니다.
knowledge holder, current POV, current scene participation과 reveal state는 MariaDB에서
랭킹 전에 hard filter한다. current POV는 신뢰된 host observation과 backend state만
authority로 사용한다. 신뢰된 관점이 없으면 비공개 원문은 fail-closed하며, user가 입력한
관점 관련 문구로 권한을 넓히지 않는다.

### 5.4 `habit_evidence.v1`

습관과 성격은 사실이 아니라 처음에는 support-only 가설이다.

```text
한 번의 행동 -> 관찰
관련 행동의 반복 -> 경향 후보
서로 다른 상황의 근거와 명시적 발언 -> 습관 또는 성향 후보 강화
반례 또는 상황 의존성 -> 조건부 해석, 약화 또는 dormant
사용자 정정 -> 이전 해석을 보존한 채 supersede
```

고정 횟수, 고정 점수나 특정 인물 수를 코드에 넣지 않는다. policy version이 근거의
독립성, 시간 분산, 명시적 자기 진술, 반례와 상황 의존성을 함께 평가한다. 같은 evidence
재처리는 가중치를 다시 올리지 않는 idempotent 계약이어야 한다.

성격은 `차갑다`, `기계적이다` 같은 단일 형용사로 축약하지 않는다. 관심 분야,
의사결정 방식, 감정 표현, 상대별 태도와 스트레스 상황의 차이를 근거별로 유지한다.
말투 예문은 문맥 없이 다시 주입하지 않고 어휘·호칭·문장 리듬·금기와 상대별 변화로
추상화하여, 생성 모델이 예시 대사를 그대로 복사하지 않게 한다.

### 5.5 과거 사용자 발언 연결

원문 발언을 별도 table에 복제하지 않는다. `chat_logs`와 `effective_input_logs`를
authority로 두고 파생 기억은 다음 pointer만 가진다.

- 누가 말했는지;
- 누가 직접 들었거나 나중에 전달받았는지;
- 정확한 source turn/message/hash;
- 발언 당시 위치·상황·감정;
- 약속, 갈등, 관계 또는 후속 행동과의 연결;
- 인물별 해석과 오해;
- 정정·철회 또는 reveal 상태.

### 5.6 저장 authority와 객관적 진실의 분리

MariaDB가 canonical storage라는 말은 MariaDB 안의 모든 row가 객관적 세계 진실이라는
뜻이 아니다. 모든 기억은 `authority_class`와 `epistemic_mode`를 가져야 한다.

| authority class | 의미 | 객관 상태 쓰기 |
| --- | --- | --- |
| `objective_world_state` | 근거와 scope를 통과한 실제 사건·현재 상태 | 허용 |
| `subjective_episodic` | 특정 인물이 기억·믿음·오해하는 내용 | 금지 |
| `derived_semantic` | 사건에서 재구성한 성격·관계·말투 profile | 금지 |
| `support_hypothesis` | 습관·감정·의도·미스터리·offscreen 추정 | 금지 |
| `derived_summary` | episode/chapter/arc/saga navigation 요약 | 금지 |
| `ooc_meta` | 사용자 설정·작가 지시·UI 제어·안전 경계 | in-world 쓰기 금지 |

`subjective_episodic`, `derived_semantic`, `support_hypothesis`와
`derived_summary`는 objective/current-state block에 들어가거나 객관 사실을 supersede할
수 없다. 해당 owner의 행동·내적 반응을 지원하는 별도 lane에서만 사용한다. 관점이
불명확하면 fail-closed한다.

상위 요약은 세부 기억을 대체하지 않는다. 충돌 시 atomic evidence와 원문이 우선하며,
가능하면 요약만 주입하지 않고 관련 atomic row 또는 source excerpt까지 확장한다.

authority와 semantic interpretation은 다음 세 층으로 분리한다.

1. host/source observation: 어떤 role·message·generation·span이 실제 활성 source인지 확정;
2. semantic proposal: 발화·서술·거짓말·추측·사건·상태·knower·시간·인과를 source span에
   묶어 제안. LLM을 쓸 수 있지만 proposal-only다;
3. Go admission: active revision, source authority, entity/speaker, branch, visibility, state slot,
   conflict·duplicate·agency·closure envelope와 idempotency를 검증해 commit/review/reject 결정.

`deterministic backend admission`은 Go가 원문 의미를 고정 키워드로 대신 추출한다는 뜻이
아니다. 동일한 source-bound proposal과 canonical state에는 동일한 구조·authority 판정이
적용된다는 뜻이다. semantic model이 없거나 실패하면 raw source와 deferred 상태를 보존하고
불완전한 키워드 추출을 canonical truth로 승격하지 않는다. 반대로 provider 부재를 이유로
raw 저장·exact/lexical recall·향후 재처리까지 no-op으로 만들지 않는다.

final displayed output은 그 span이 표시됐다는 occurrence authority를 제공한다. 그 안의 인물
주장, 거짓말, 계획, 관계 감정과 사건 서술이 객관 사실인지, 누가 알게 됐는지, 제안된 사건의
causal permission·user agency·thread closure scope가 허용됐는지는 각각 별도 admission한다.

### 5.7 `character_profile.v1`과 profile 영구 경계

profile은 하나의 인물 설명문이나 truth blob이 아니다. 같은 evidence spine에서 다음
read surface를 서로 다른 권한으로 파생한다.

- identity와 비교적 안정적인 baseline;
- 최신 근거를 반영한 current snapshot;
- 최근 변화와 의미 있는 상호작용을 압축한 dynamic continuity digest;
- attribute observation과 그것을 바꾼 event pointer;
- 방향성 관계, 목표·믿음·지식, 습관·성격·말투 evidence와 반례;
- 명시적 unknown, conflict와 최신 meaningful interaction anchor.

attribute observation은 최소한 원래 의미 영역, 적용 범위, source evidence, 반례,
상황별 예외와 현재 유효성을 보존한다. `capability`, `interest`, `occupation`, `appearance`,
`social_role`, `stable_personality`, `current_emotion`, `voice_behavior`처럼 서로 다른 영역은
하나의 generic trait 문자열로 합치지 않는다. 한 영역의 특성이 다른 영역에 영향을 줄
수 있다는 사실도 source-linked observation이나 승인된 설정이 있을 때만 profile에
포함한다.

특히 능력이 강함, 특정 분야에 관심이 있음, 높은 지위를 가짐 또는 특정 외형을 가졌다는
정보만으로 냉정함·거만함·사회성 부족·감정 억제·특정 말버릇 같은 사회적·정서적·언어적
행동을 자동 파생하지 않는다. 이 예시는 production 키워드 목록이 아니라 영역 간 무근거
추론을 금지하는 설명이다. 실제 저장 계약은 특정 형용사 목록 대신 다음을 근거별로
관리한다.

- `supported_expression`: 해당 특성이 실제로 드러난 행동과 적용 상황;
- `unsupported_entailment`: 자료가 지지하지 않아 자동으로 따라오면 안 되는 해석;
- `counter_evidence`: 반대 행동이나 단일 해석을 깨는 실제 장면;
- `relationship_variant`: 상대와 권력·친밀도에 따른 표현 차이;
- `state_modulation`: 감정·피로·부상·위협 같은 현재 상태에 따른 일시적 변화.

`unsupported_entailment`는 모델이 만든 부정 목록을 canonical truth로 즉시 저장하는
필드가 아니다. source evidence, 사용자 명시 설정, 반복 관찰과 반례에서 backend가
admission한 해석 경계다. 자료가 없다는 사실은 반대 성격의 확정 근거도 아니다.

baseline, snapshot과 digest는 원문·atomic event를 대체하는 canonical truth가 아니다.
attribute와 factual event를 분리하며, attribute 변경은 source-linked event나 correction 없이
발생할 수 없다. topic continuity와 entity/event cue route를 분리할 수 있지만 특정 단어,
rare-word 목록, clue score, 고정 route 수나 per-field top-k를 정책으로 사용하지 않는다.

subject namespace는 최소한 다음을 분리한다.

| namespace | 의미 | 4.1 쓰기 경계 |
| --- | --- | --- |
| `user_interaction_profile` | 실제 사용자의 명시적 OOC 선호·안전 설정 | opt-in 근거만 허용; 추론형 cross-session profiling은 후속 작업 |
| `rp_character_profile` | player character와 NPC의 in-world identity·상태·성격·관계 | 세션 원문과 in-world evidence만 사용 |

캐릭터의 1인칭 발언, narrator/player 지식, 같은 이름 또는 사용자가 연기한 행동을 실제
사용자의 현실 profile로 변환하지 않는다. 반대로 실제 사용자의 OOC 선호를 캐릭터의
취향·기억·동의로 만들지 않는다. 두 namespace는 storage type, retrieval route, lifecycle,
export/delete 의미와 delivery label을 공유된 이름 문자열로 합치지 않는다.

#### 5.7.1 `relationship_state.v1`

관계는 하나의 전역 호감도나 단계 숫자가 아니라 방향성과 의미 영역을 가진 evidence-bound
current/history projection이다. 첫 구현은 별도 관계별 table을 늘리기보다 기존 관계 state,
event, evidence와 profile 구조에서 다음 의미를 재구축한다.

- `source_character_id -> target_character_id` 방향, session과 branch;
- 확장 가능한 relation domain과 그 영역에 한정된 current state·uncertainty;
- source turn/message/hash, event IDs, counter-evidence와 story-time validity;
- 공개 태도, 실제 내적 태도, knower/visibility와 authority/epistemic mode;
- 적용 context, 권력·의무·경계와 상대별 예외;
- previous/current/proposed transition과 causal event refs;
- correction, supersession, rupture, recovery와 reconciliation lineage;
- 반대 방향 edge는 reciprocity 값이 아니라 독립 reference.

한 relation domain의 evidence가 다른 domain으로 자동 전파되지 않는다. 신뢰는 애정·연애·
성적 끌림·친밀감·복종·동의와 같지 않고, 명령 수행은 authority·의무·두려움·전술 판단과
stable obedience를 구분한다. 사용자나 player character가 원하는 관계, 보인 감정 또는
입력했다는 사실도 상대 인물의 감정 근거가 아니다.

친절·도움·동행·접촉·명령 수행 같은 interaction은 우선 그 행동이 실제로 발생했다는
atomic event다. 해당 사건이 관계를 바꿨다는 source-linked evidence가 없다면 durable
relationship transition이 아니다. 반대로 단 한 사건이어도 final source나 승인 설정·세계
규칙이 큰 관계 변화를 명시적으로 지지하면 고정 횟수나 점수 없이 admission할 수 있다.
핵심은 점진성 강제가 아니라 변화의 방향·영역·크기·지속 범위를 직접 지지하는 근거다.

신체 접촉 사건, 그 접촉에 대한 각 인물의 해석, consent scope와 관계 상태는 서로 다른
unit이다. 과거 동의나 한 번의 친밀 행동은 현재·미래의 지속 동의, 독점 관계, 사랑 또는
상호 감정을 자동 생성하지 않는다. `interaction_boundary.v1`의 거절·철회·범위는 관계
projection보다 독립적이며 항상 우선한다.

모델·critic·agent가 제안한 관계 변화가 기존 evidence와 transition scope를 벗어나면 final
output 원문은 보존하되 current relationship projection을 덮지 않고 `needs_review` 또는
conflict로 남긴다. relation domain별 별도 score, 고정 단계 ladder와 접촉 keyword 표는
이 계약의 구현이 아니다.

### 5.8 `character_body_state.v1`

인물의 신체 상태는 RP 연속성의 필수 기억이다. 이 계약은 부상·질병만이 아니라 여성
인물의 생리 주기, 임신 가능성·추정·확정·배제, 임신 단계, 출산과 산후 회복을 명시적
coverage로 포함한다. 여성이라는 이유만으로 해당 상태를 추론하지 않지만, 설정과 서사
근거가 있는 상태를 generic profile이나 중요하지 않은 세부사항으로 축소하지 않는다.

각 unit은 전체 인물 JSON이 아니라 하나의 상태 주장, 관찰 또는 전이를 표현하고 다음을
가진다.

- fictional character subject ID, session과 branch;
- 신체 baseline 또는 상태 subtype과 affected area;
- onset, observation, phase/change, treatment, recovery/clear와 story-clock precision;
- source turn/message/hash, exact evidence와 extraction source;
- `canonical_in_fiction`, `derived_estimate`, `pending/needs_review`를 구분하는 authority;
- 객관 상태와 별개인 knower, POV visibility, reveal state와 sensitivity;
- current/historical lifecycle, supersession·recovery·clear·recurrence lineage;
- 행동·이동·감각에 미치는 effect와 근거 있는 constraint.

가능성·주기 추정은 확정 사실과 다른 authority lane이다. 성적 사건, 고정 주기 계산,
turn 수, server time, 모델 confidence 또는 agent 합의만으로 임신·비임신, 정확한 주기 날짜,
회복 완료나 의료적 상태를 확정하지 않는다. 명시적 story-time anchor가 없으면
`unknown`을 보존한다. RP continuity estimate를 현실 의료 진단이나 조언으로 표현하지
않는다.

snapshot은 현재 read surface이고 immutable delta/event가 근거다. 회복·해제는 이전 row를
삭제하지 않고 supersede하며, 재발·악화는 원래 onset과 새 evidence를 lineage로 연결한다.
expiry는 history 삭제가 아니라 current eligibility 변경이다. reroll·branch·rollback으로
폐기된 신체 상태가 다른 timeline이나 현재 snapshot에 부활해서는 안 된다.

이 계약은 fictional character 상태만 다룬다. RP 내용, 캐릭터 설정 또는 생식 서사를
근거로 실제 사용자의 성별, 임신, 생리 주기, 건강·질병·성적 상태를 추론·저장하지 않는다.

### 5.9 `memory_candidate_review.v1`

보조 extractor, critic, verifier와 Step 28 QHM형 agent는 canonical writer가 아니다. 다음
경로는 다중모델 사용 여부와 무관하게 동일하다.

```text
source packet capture
-> source/scope/identity/branch validation
-> evidence-bound candidate proposal
-> duplicate/conflict/stale/poison challenge
-> deterministic backend admission decision
-> canonical write 또는 review/reject 상태
```

높은 confidence, `commit_ready` 같은 agent verdict, 다수결, 같은 결론의 반복 또는 한
모델 내부 역할 합의는 write 권한이나 독립 근거가 아니다. 같은 evidence packet을 읽은
여러 agent의 동의도 하나의 근거를 여러 번 센 것으로 취급하지 않는다. source reference,
subject identity, branch/time scope, authority, knower/visibility, conflict와 사용자 정정을
Go admission owner가 다시 검증해야 한다.

agent가 없거나 실패해도 기존 원문 보존과 deterministic admission이 깨지지 않아야 한다.
visual artifact, OCR/vision 결과와 generated guidance는 proposal-only이며 source text 없이
memory 또는 body state의 write evidence가 될 수 없다.

### 5.10 `turn_realization.v1`

이 계약은 새 canonical 장면 DB가 아니라 기존 raw turn, atomic event/state, relation,
knowledge와 `pending_threads`에서 파생하는 source-linked realization projection이다. 목적은
이번 final output에서 실제로 발생·변경·해결된 것과 과거의 단순 언급·회상·재해석을
구분하여 다음 턴에서 같은 사건이 재연·증폭되지 않게 하는 것이다.

- final displayed message ID/hash, accepted generation, session·branch·revision;
- 현재 user input source와 새 요구·계속·정정·철회·질문·recap·reflection 등 semantic delta;
- output discourse function과 그 근거 span;
- 실제 실현된 event/outcome과 state·knowledge·decision·relationship·thread transition IDs;
- 과거 event의 mention, recollection, reinterpretation과 다른 POV의 새 reaction IDs;
- causal parent, 새 consequence와 아직 실현되지 않은 consequence reference;
- 새 사건 없이도 완결된 응답이면 source-linked no-new-realization reason;
- raw, atomic memory, summary와 profile projection이 공유하는 root evidence ID.

discourse function과 realization type은 versioned enum일 수 있지만 prompt 키워드로 결정하지
않는다. extractor는 source-bound proposal만 만들고 Go가 final output, current input,
branch, state slot과 thread transition을 검증한다.

이미 실현된 사건을 recap한 출력은 기존 event의 mention/recollection이며 새 objective
event가 아니다. summary를 다시 풀어쓴 문장도 같은 root evidence를 공유하며 독립 evidence,
importance, habit 또는 relationship strength를 증가시키지 않는다. lexical 표현이 달라도
같은 outcome이면 새 progression 근거가 아니고, 표현이 비슷해도 새 결정·지식·반응·결과가
있으면 별도 realization일 수 있다.

recap, reflection, OOC, 정적 감정 장면과 사용자 agency를 기다리는 턴은 raw를 보존하면서
`no_new_memory`가 될 수 있다. 매 턴 새 사건을 강제하지 않는다. 해결된 thread는 historical
transition으로 보존하되 active unresolved-consequence set에서 제거하고, 명시적 회상·다른 POV 반응은
과거 사건 자체를 다시 발생시키지 않는 별도 subjective/discourse unit으로 허용한다.

final displayed output은 어떤 문장과 사건이 표시됐다는 occurrence evidence다. 감독관·critic·
summary가 먼저 제안한 습격·배신·폭로·해결·종결이 출력에 포함됐다는 사실만으로 그 사건의
원인, 허용 범위나 closure authority까지 정당화되지는 않는다. Go admission은 current input,
사전 state·world rule·actor goal과 `narrative_thread_lifecycle.v1`의 causal precondition·agency
owner·resolution scope를 별도로 검증한다.

### 5.11 `narrative_thread_lifecycle.v1`

이 계약은 새 plot DB나 tension score가 아니라 기존 `pending_threads`, event, direct evidence,
`turn_realization.v1`과 hierarchy summary에서 thread current/history를 재구축하는 논리 계약이다.
`pending_threads`를 atomic owner 후보로 먼저 감사하고 `storylines`와 episode/chapter/arc/saga는
thread ID를 참조하는 derived aggregate·navigation projection으로 제한한다.

각 thread는 최소한 다음 의미를 가진다.

- stable thread ID와 revision, session·branch, source turn/message/hash와 evidence IDs;
- owner·participants, knower·visibility와 적용 가능한 continuity;
- 아직 남은 질문·목표 충돌·의무·위협·조건·결과와 story-clock condition;
- lifecycle current/history와 source-linked created/advanced/held/resolved/transformed/reopened/
  withdrawn transition;
- predecessor/successor, parent·dependency·conflict·causal refs와 남은 consequence의 이관;
- transition이 영향을 주는 정확한 thread IDs, `resolution_scope`, closure authority와 evidence;
- 명시적 user/host authorial 종료 신호와 in-world 사건 해결의 authority 분리.

`foreground`, `background`, `not_selected` 같은 attention role은 4.6~5.0의 request-scoped delivery
결과이며 canonical lifecycle이 아니다. 선택되지 않았거나 예산 때문에 전달되지 않은 thread를
paused·dormant·resolved·suppressed로 변경하지 않는다. dormant는 resolved가 아니며 reactivation
condition과 남은 consequence를 유지한다.

한 thread의 해결은 sibling·parent·episode·chapter·arc·saga·session을 자동 종료하지 않는다.
단일 사건이 여러 thread를 실제로 해결할 수는 있지만 각 target thread와의 direct causal/
resolution mapping이 필요하다. 상위 container가 닫혀도 unresolved child는 resolved로 세탁하지
않고 carried·dormant 또는 source-linked successor transition으로 보존한다. 검색 결과에 미해결
thread가 없거나 bounded query가 일부만 반환했다는 사실은 작품 종료 authority가 아니다.

recap·mention은 reopen 근거가 아니다. 새 원인·모순·사용자 정정처럼 source-linked change가
있을 때만 이전 resolution과 새 revision을 연결한다. transformed transition은 successor ID와
이전 consequence의 보존·해소·이관 결과를 모두 가진다. 4.1은 어떤 thread를 이번 장면의
주 plot으로 삼거나 다음 사건을 선택하지 않으며, pace와 attention은 4.6~5.0이 read-only로 계산한다.

## 6. AI RP 장기 기억 필수 coverage

다음 matrix 전체가 4.1 필수 범위다. 하나의 generic `event`나 `state` JSON에 모두 넣었다는
이유만으로 충족되지 않는다. 각 행은 atomic row 또는 source-indexed deep recall 중
적어도 하나로 production 경로에서 회수 가능해야 하며, 조용히 누락할 수 없다.

`precise_memory_unit.v1`의 kind는 폐쇄 목록이 아니라 최소 상위 class와 versioned subtype
계약이다. 아직 분류하지 못한 근거 있는 세부사항은 `other_evidence_bound` 또는
`needs_review`로 보존한다. 지원하지 않는 종류를 버리거나 임의의 중요 사건으로 합치는
것은 금지한다.

| 영역 | 필수 기억 | 저장·회상·주입 불변 조건 |
| --- | --- | --- |
| 사건 | 행동, 선택, 결과, 원인과 후속 영향 | 시간적 선후와 인과를 구분하고 참여자·근거를 연결 |
| 정확한 발언 | 사용자·인물의 발언, 약속, 철회, 거짓말, 정정 | final message ID/hash를 authority로 사용하고 paraphrase를 quote로 표시하지 않음 |
| identity | 동일 인물, alias, 개명, 대명사, 언어별 표기 | 동명이인 merge 금지, alias의 유효 시기와 화자 범위를 보존 |
| cover identity | 변장, 비밀 역할·혈통·소속, surface identity | objective identity와 인물별로 알고 있는 identity를 분리 |
| 신체 baseline | 나이대, 체형, 특징과 영구·일시적 변형 | 현재값과 변경 history를 분리하고 과거 외형이 현재를 덮지 않음 |
| 신체 상태 | 부상, 질병, 통증, 피로, 취기, 치료와 회복 | onset·effect·clear lineage를 보존하고 임의 회복 기간을 만들지 않음 |
| 여성 인물의 생식·주기 상태 | 생리 주기 anchor·phase estimate, 임신 가능성·추정·확정·배제, 임신 단계, 출산·산후와 명시된 관련 사건 | 여성이라는 이유나 성적 사건만으로 생성하지 않고, estimate와 canonical-in-fiction을 분리하며 story-time anchor 없는 자동 진행 금지 |
| 위치·이동 | 현재 위치, 출발·도착·이동 중, 경로, 동행자 | 거주지·회상 속 장소·현재 위치를 혼동하지 않음 |
| 공간 상태 | 방·문·잠금·파손·거리·접근성·장면 내 배치 | scene/time 범위를 가지며 오래된 공간 상태를 현재에 적용하지 않음 |
| 이야기 시간 | 날짜, 상대 시간, 순서, 지속시간, time skip | story clock anchor가 없으면 exact time으로 승격하지 않음 |
| 환경 | 날씨, 온도, 조명과 지역·장면 조건 | location/time scope 없이 전역 세계 상태로 저장하지 않음 |
| 감각 세부 | 냄새, 소리, 촉감, 맛, 시각적 단서, 작은 몸짓 | observer와 sensory channel을 기록하고 다른 인물에게 자동 공유하지 않음 |
| 식사·생활 | 먹은 것, 마신 것, 수면, 제안·거절·함께한 사람 | 제안을 섭취로 오인하지 않고 일반 턴 상시 주입 대신 필요 시 회수 |
| 소지품 | 소유, 보관, 위치, 획득, 전달, 분실, 소비, 변형 | owner와 holder를 분리하고 소비·전달된 물건을 부활시키지 않음 |
| 수량·자원 | 수량, 잔량, 비용, 거리, 측정값과 단위 | exact·approximate·unknown을 분리하고 stale 값을 현재 계산에 사용하지 않음 |
| 복장·장신구 | 착용 시작·제거, 현재 복장과 장면 한정 외형 | 영구 외형으로 승격하거나 flashback 복장을 현재에 적용하지 않음 |
| 능력·제약 | 기술, 능력, 약점, 학습, 상실, 일시적 사용 불가 | 한 번의 성공을 영구 능력으로 만들지 않고 known-by 범위를 보존 |
| 감정 | 현재 감정, 숨긴 감정, trigger, 해소와 상대별 태도 | 단기 감정을 고정 성격으로 승격하지 않고 공개 범위를 분리 |
| 목표·의도 | proposed, accepted, active, abandoned, completed 계획 | 계획을 발생 사건으로 저장하지 않고 owner·visibility·유효 범위를 보존 |
| 성격 | 가치, 판단 방식, 관심, 두려움, 방어·대처와 반례 | 단일 형용사나 한 행동으로 평면화하지 않고 evidence로 재구축하며 능력·관심·직업·외형에서 사회적 성격이나 말투를 무근거 파생하지 않음 |
| 습관·선호 | 루틴, 좋아함·싫어함, 상황 의존성과 반례 | 단일 관찰을 습관으로 만들지 않고 polarity·대상·시간 범위를 분리 |
| 말투·호칭 | speaker→addressee별 호칭, 존대, 어휘, 리듬, 언어 전환 | 예시 대사를 일반 상황에 복사하지 않고 원리와 상대별 변화를 저장 |
| 관계 방향 | 호감, 신뢰, 두려움, 존중, 질투, 원망과 확장 가능한 관계 영역 | `A -> B`와 `B -> A`를 별도 current/history로 보존하고 한 영역을 애정·친밀감·복종·동의에 자동 전파하지 않음 |
| 관계 사건·전이 | 첫 만남, 배신, 화해, 관계 변화와 계기 | interaction 사건과 관계 해석을 분리하고 previous/current/proposed·counterevidence·rupture/recovery lineage를 보존 |
| 신체 접촉·친밀 행동 | 접촉 actor/target, 행동, consent scope, 관찰자와 각 인물의 해석 | 발생 행동을 관계·사랑·상호성·지속 동의로 자동 승격하지 않고 explicit transition evidence가 있으면 별도 admission |
| 의무·권한 | 약속, 계약, 빚, 허가, 금지, 명령, 지휘계통 | 당사자·authority·조건·만료·이행·철회를 보존 |
| 동의·경계 | 동의, 거절, 철회, 개인 금기, 안전 신호 | 침묵·과거 동의·서사 추론으로 생성하지 않고 철회가 우선 |

| 세계 규칙 | 마법·기술·사회 규범, 예외와 적용 범위 | prompt 지시를 세계 사실로 저장하지 않고 version/evidence를 유지 |
| 목격·지식 | 누가 무엇을 직접 봄·들음·전달받음 | 이름 언급을 목격이나 knowledge 권한으로 사용하지 않음 |
| 소문·오해 | speaker, 전달 chain, 추론, 신뢰도, 해소 | 소문이 발화됐다는 사건과 소문 내용의 객관적 진실을 분리 |
| 비밀·reveal | known/suspected/misinformed/unknown/revealed 집합 | 한 인물에게 공개된 사실을 전역 공개로 만들지 않음 |
| offscreen event | 실제 발생, 보고됨, 추정됨, 아직 미확인 | 현장 참여자와 보고받은 인물을 분리하고 추정을 objective로 승격하지 않음 |
| unresolved thread | 미스터리, 과업, debt, 약속, 목표 충돌·위협의 생성·진행·hold·해결·변형·재개 | stable ID·branch·남은 consequence·dependency·transition lineage를 보존하고 attention 제외를 lifecycle 변경으로 사용하지 않음 |

| 부정·부재 | 하지 않음, 없음, 아직 아님, never, unknown | 부정문을 긍정 사건으로 추출하지 않고 부정의 범위를 보존 |

| copy·move | session provenance, source lock, vector generation | 두 session의 truth를 섞지 않고 lifecycle parity를 유지 |
| 사용자 반응 | 사용자 발언에 대한 실제 최종 assistant/인물 반응 | final displayed output만 authority로 사용하고 폐기 반응을 제외 |
| turn realization | 실제 실현된 사건·결과, mention·recall·reinterpretation, input delta와 discourse function | 이미 실현된 outcome·summary를 새 사건·독립 evidence로 증폭하지 않고 새 사건 없는 완결 응답과 실제 새 변화를 구분 |
| OOC·meta | 설정, 작가 노트, UI 제어, 시스템·개발자 지시 | 신뢰된 host role/channel metadata로 분리하고 in-world memory/KG 쓰기 금지 |
| 사용자 상호작용 선호 | 명시적 opt-in RP 선호와 안전 설정 | 캐릭터 취향·세션 사건과 분리하고 자동 cross-session profile 생성 금지 |
| 다국어 | 원문 quote, 번역·요약 언어, alias와 호칭 변형 | 번역문을 exact quote로 저장하지 않고 언어 변경에도 동일 entity를 회수 |
| 사용자 정정 | 수정 대상, authority, scope와 immutable lineage | 정정 전 row를 삭제하지 않되 active truth로 다시 선택하지 않음 |

### 6.1 RP 전용 공통 envelope

모든 RP 기억 lane은 다음 공통 의미를 가져야 한다.

- `authority_class`와 `epistemic_mode`;
- session, branch, source turn/message/hash;
- subject, owner, participants와 directional relation;
- story clock, validity와 lifecycle revision;
- evidence IDs와 supersession/correction lineage;
- visibility, knower, reveal와 OOC/in-world scope;
- fictional character/user-interaction subject namespace, profile kind와 sensitivity;
- 저장은 되었지만 주입할 수 없는 상태와 그 이유.

### 6.2 Consent와 OOC/meta

동의와 경계는 일반 성격·선호 memory로 저장하지 않는다. `interaction_boundary.v1`은
actor, counterpart, action/scope, allow/refuse/withdrawn/unknown, source message/hash와
validity를 표현해야 한다. 침묵, 과거 동의, 캐릭터의 거짓말이나 모델 추론으로 현재
동의를 만들 수 없다.

OOC/meta는 문자열 `[OOC]` 탐지로 분류하지 않는다. RisuAI가 제공하는 신뢰된 role,
channel과 lifecycle observation을 JavaScript가 최소 관측값으로 전달하고, backend가
versioned request-class 계약으로 분리한다. OOC는 in-world utterance, event, KG, character
memory 또는 world rule로 승격할 수 없다.

### 6.3 JSON 재사용과 normalized migration 결정

기존 JSON은 설명, excerpt, 표시 metadata와 파생 세부 정보에만 우선 재사용한다. 다음
조건을 모두 만족해야 한다.

- session, owner, authority와 current state hard-filter key가 row에 정규화되어 있음;
- write 시 전체 JSON schema를 검증함;
- uniqueness, FK, one-of, revocation과 branch isolation을 JSON 내용에 의존하지 않음;
- rollback/delete/migration이 JSON 전수 scan 없이 대상 row를 찾음;
- many-to-many knower/evidence/participant 관계를 숨기지 않음.

secret visibility, consent, branch, owner, canonicality, temporal validity, supersession 또는
검색·삭제·rollback의 필수 predicate가 JSON 안에서만 표현된다면 normalized migration은
4.1 내부 필수 작업이다. schema 필요성을 이유로 기능을 보류하거나 후속 버전으로 넘길
수 없다.

논리 계약은 문서나 JSON blob만 추가했다고 구현된 것이 아니다. 각 release 진입 전에 다음
물리 mapping과 production query plan을 결정한다.

| 계약 | 반드시 보장할 물리 성질 | 기존 구조가 증명하지 못할 때 |
|---|---|---|
| source/acceptance/bootstrap | message·generation·branch·revision uniqueness, active-final 교체, start source order | additive source/lifecycle schema와 기존 raw backfill |
| entity/speaker | stable ID, namespace, alias validity, split/merge와 source span FK | session entity/alias/attribution mapping을 normalized migration |
| atomic memory/authority | 한 unit·knower·time/scope 경계, source FK, active/superseded uniqueness | 기존 `memories`를 보존한 atomic child mapping 또는 검증된 normalized 대체 |
| body/relation/profile | current key, immutable history, direction/domain/visibility와 rebuild source | JSON 전수 scan을 없애는 key/index 또는 normalized current/history mapping |
| derivation/outbox | transitive dependency lookup, source revision compare, idempotent vector operation | dependency edge/index와 transactional outbox mapping |

모든 table에 같은 column을 기계적으로 추가하거나 기존 JSON을 전부 폐기하는 것이 목표는
아니다. 위 무결성·조회·migration fixture를 가장 단순하게 만족하는 기존 owner 수리 또는
정규화를 선택하고, 실제 DDL은 fresh/upgrade/reapply·rollback/no-resurrection evidence와 함께
승인한다.

### 6.4 실제 사용자와 RP 인물의 민감정보 경계

`user_interaction_profile`, player character와 NPC는 동일 이름·1인칭·display role을
공유하더라도 별도 subject identity다. 실제 사용자의 OOC 선호와 안전 설정은 명시적
opt-in evidence만 허용하며, RP 속 캐릭터의 발언·행동·신체 상태를 사용자의 현실 profile로
승격하지 않는다.

여성 RP 인물의 임신·주기·산후·질병 같은 민감 상태는 저장 필요성과 공개 권한을
분리한다. MariaDB의 subject, branch, validity, knower, POV, reveal와 sensitivity hard
filter를 ranking, Chroma, agent review, trace와 visual rendering보다 먼저 적용한다. 관련성,
모델 confidence, 서사적 유용성 또는 압축 이득은 공개 범위를 넓힐 수 없다.

| P1 | quiet/recap/회복 장면에서 갈등을 강제하거나 반대로 기존 위협·의무를 삭제 | `intentional_hold`를 허용하되 source-linked constraint·consequence·reactivation condition은 lifecycle에 남음 |
| P1 | resolved thread의 recap을 reopen으로 저장하거나 transformed successor의 미해결 결과를 소실 | recap은 mention이고 reopen/transform은 새 source·previous revision·successor·consequence carry를 요구 |

각 guard를 제거하거나 반전하면 대응 회귀 테스트가 실패해야 한다.

## 7. Admission과 상태 전이

기억 추출 결과는 최소한 다음 상태를 구분한다.

- `admitted`: 근거와 scope 검증을 통과한 파생 기억;
- `no_new_memory`: 정상 처리됐지만 새로 장기 보존할 파생 기억이 없음;
- `needs_review`: 근거는 있으나 시간·인물·충돌이 불확실함;
- `extract_failed`: provider 또는 출력 계약 실패;
- `deferred_no_provider`: 추출 provider가 없어 원문만 보존함.

`no_new_memory`와 실패를 summary fallback으로 채워 성공 처리하지 않는다. 원문은
정상 보존하되 파생 기억을 만들지 않는다. 재추출은 같은 source hash와 contract version에
대해 idempotent해야 한다.

excerpt grounding과 truth admission도 분리한다. exact excerpt 검증은 원문에 그 표현이
존재함만 보장한다. 서술자의 객관적 사실, 인물의 발언, 거짓말, 추측과 오해는 서로 다른
epistemic mode로 admission한다. scope를 확정할 수 없으면 `needs_review` 또는 unknown으로
남기고 objective로 승격하지 않는다.

중복과 충돌은 분리한다.

1. 같은 message/hash/excerpt의 재처리는 exact duplicate다.
2. 의미가 비슷한 기억은 자동 중복이 아니라 후보 관계다.
3. subject, kind, branch, temporal scope, perspective와 state slot이 일치할 때만 기존
   기억의 재확인 또는 변경 후보가 될 수 있다.
4. 정정·철회·상태 변경은 과거 row를 삭제하지 않고 lineage로 연결한다.
5. conflict 판단을 특정 언어의 부정어 목록이나 고정 문구에 의존하지 않는다.

candidate review는 canonical admission을 대체하지 않는다. extractor·critic·agent별 결과는
각각 source packet, 사용한 authority lane, conflict/dedup reference와 review reason을
가진 proposal로만 저장한다. Go backend는 다음을 독립적으로 재검증한다.

- source turn/message/hash가 실제 final accepted branch에 존재하는지;
- subject identity와 user/RP character namespace가 맞는지;
- story time, branch, validity와 lifecycle이 모순되지 않는지;
- authority, epistemic mode, knower/visibility와 sensitivity가 허용되는지;
- 같은 evidence 재처리, semantic near-duplicate, conflict, stale와 poison 여부;
- 사용자 정정이나 더 높은 권한의 direct evidence가 있는지.

relationship transition은 위 공통 admission에 더해 direction, relation domain, previous
state, causal event, magnitude·permanence scope, counter-evidence와 consent boundary를
검증한다. interaction 발생 자체나 user/player 입력은 상대 인물의 감정 transition 근거가
아니다. 단일 source라도 변화를 직접 지지하면 허용할 수 있고, 다수 interaction이라도
관계 해석 근거가 없으면 durable state로 승격하지 않는다.

thread transition은 stable thread ID, previous revision, source event/outcome, branch, lifecycle
transition kind, affected thread IDs, resolution scope와 outstanding consequence의 보존·해소·
successor 이관을 검증한다. final output·summary·supervisor report의 “끝남” 표현만으로 sibling,
parent 또는 episode/chapter/arc/saga/session closure를 만들지 않는다. 아직 가능한 사건은
realized outcome이 아니며, player가 결정해야 할 선택은 agency owner가 허용하지 않는 한
resolved transition으로 admission하지 않는다.

검토 결과는 최소 `admitted`, `proposal_only/needs_review`, `reject_duplicate`,
`reject_conflict`, `reject_unsourced`와 실행 실패를 구분할 수 있어야 한다. 이 enum은 상태
계약이며 agent가 반환한 같은 이름을 그대로 신뢰하지 않는다. agent/provider 실패 또는
빈 출력은 `no_new_memory`, `admitted`나 성공한 review로 변환하지 않는다.

### 7.1 Hot, complete-turn, background와 replay 경로 분리

- `/prepare-turn` hot path는 생성 전 유일한 read-only planner다. admitted/current revision을
  읽어 recall과 delivery를 수행하며 raw source, profile, graph, summary, body 또는 다른
  canonical state를 쓰지 않는다;
- complete-turn path는 final 표시 뒤의 별도 ingestion owner다. final accepted source와 hash를
  먼저 보존한 뒤 `turn_realization.v1`의
  realized/mention/recollection, input delta와 thread transition proposal을 검증하고 candidate
  생성, deterministic admission과 canonical transaction을 수행한다. 생성 전
  `ENDPOINT-SINGLE-PLANNER`는 이 post-display write owner를 없애거나 `/prepare-turn`에 합친다는
  뜻이 아니다;
- background path는 summary/profile/graph/invalidation proposal, stale/conflict 검사와
  index maintenance를 수행할 수 있지만 common admission transaction 없이 canonical row를
  쓰거나 live current state를 overwrite하지 않는다;
- replay/evaluation path는 live write와 분리하며, 명시적 maintenance/rebuild contract 없이
  과거 fixture·agent 결과를 production session에 commit하지 않는다.

경로가 다르다는 이유로 authority가 달라지지 않는다. 동일 source packet의 background
재처리는 새 독립 evidence가 아니며 complete-turn과 같은 idempotency, branch, visibility와
lineage gate를 통과해야 한다.

summary, profile과 graph는 admitted atomic row와 realization projection 뒤에 파생한다.
파생물은 root evidence ID를 유지하며 raw/event/summary/profile이 같은 delivery purpose로
동시에 선택되면 lineage cluster 안에서 coalesce한다. summary의 재서술은 새 event, 새
관계 transition이나 새 evidence가 될 수 없다.

### 7.2 기존 사용자 DB migration과 backfill

3.6 진입 전에 fresh schema만이 아니라 지원 대상 기존 DB에서 다음 inventory를 만든다.

- raw chat/effective-input row가 제공하는 session·turn·role·content·timestamp와 누락 identity;
- 기존 `entities`의 name·alias·type·turn과 누락된 source·namespace·branch·mapping lineage;
- evidence/memory/state/relation/thread row의 source pointer, lifecycle과 중복 상태;
- Chroma item이 가리키는 MariaDB row, collection/index/embedding contract version;
- 기존 delete·rollback·copy·move·branch 동작과 orphan·stale projection.

migration은 additive, resumable, idempotent하며 사용자의 기존 raw·canonical row를 삭제·초기화·
재번호화하지 않는다. backfill job은 migration version, cursor, source fingerprint, 처리 결과와
재시작 지점을 기록한다. 같은 DB에 재실행해도 source/evidence count와 current projection이
증폭되지 않아야 한다.

기존 row에 message/generation/branch/speaker/acceptance 근거가 없으면 합리적으로 보이는 값을
창작하지 않는다. raw 원문과 기존 lineage는 보존하고 정밀 보장이 불가능한 범위는
`legacy_unverified`와 field-level coverage gap으로 표시한다. 다만 확인 가능한 session·turn·role·
hash·existing source pointer는 backfill하고, 한 필드의 불확실성을 이유로 전체 row를 버리지
않는다. `legacy_unverified`는 영구 무시 상태가 아니라 exact/lexical recall, 사용자 정정과
후속 source 연결을 허용하는 명시적 제한 상태다.

3.3 provenance cutover가 식별한 supervisor/director/cache-origin row는 일반 raw legacy와
합치지 않고 `legacy_proposal_unverified/proposal_only` 격리를 그대로 계승한다. direct
user/source admission이 별도로 증명되기 전에는 exact/lexical recall, semantic recall,
execution/lore ground truth와 canonical projection에서 제외한다. final output에 비슷한 문장이
나타났거나 사용자 정정 candidate가 생겼다는 이유만으로 proposal provenance를 제거하지 않는다.

기존 `entities` row에 source·namespace·branch·speaker/subject 근거가 없으면 같은 이름의 lore,
원작 reference 또는 새 session identity에 자동 연결하지 않는다. 확인 가능한 기존 session
lineage는 보존하고 나머지는 `legacy_unverified` identity coverage로 남긴다. 사용자 정정이나
새 source-linked evidence가 생기면 일반 tentative-link/admission으로 연결하며 migration이
stable ID·merge·first occurrence를 창작하지 않는다.

이 제한 상태의 exact/lexical 결과는 audit, 사용자 정정과 backfill candidate 생성에는 사용할
수 있다. 모델 payload delivery는 current branch, active acceptance, visibility와 subject/speaker
scope를 현재 authoritative source로 재구성한 경우에만 허용한다. 하나라도 확인할 수 없으면
fail-closed exclusion과 field-level coverage gap을 반환하며 semantic similarity나 오래된 summary로
누락 scope를 채우지 않는다.

schema/index 전환은 dual-read가 필요한지 먼저 결정하고, 필요하면 지원 version, write owner,
fingerprint parity, cutover와 제거 조건을 고정한다. silent dual-write, JS migration, 매 시작마다
전체 DB 재스캔은 금지한다. 실제 사용자 DB 사본의 read-only dry run, disposable clone 적용,
중단·재개·재적용과 이전 버전 read 여부를 증거로 남긴다.

### 7.3 동시성, stale 결과와 crash recovery

모든 complete-turn/background/reprocess 작업은 시작 시 읽은 source revision set과 contract
version을 commit 조건으로 가진다. Go commit owner는 transaction 직전에 active branch,
source acceptance lifecycle, entity mapping revision과 tombstone을 다시 비교한다.

- 조건이 달라진 worker 결과는 `stale_rejected` 또는 새 revision 대상 재처리로 보내고 현재
  canonical row를 덮어쓰지 않는다;
- delete·reroll·edit tombstone은 늦은 extraction, summary/profile rebuild와 vector upsert보다
  우선한다;
- 한 session의 서로 다른 source는 병렬 처리할 수 있으나 같은 state slot·entity mapping·
  thread transition의 충돌은 expected revision 또는 명시적 merge proposal로 직렬화한다;
- MariaDB canonical transaction이 먼저 authority를 가지며 Chroma는 idempotent outbox event를
  소비한다. vector 성공만으로 canonical success를 만들지 않는다;
- lease 만료·provider timeout·process crash 후 재개는 동일 idempotency key를 사용하며 부분
  write를 새 evidence로 세지 않는다;
- queue backlog, oldest age, retryable/permanent failure, stale rejection과 source coverage를
  stable operation state로 노출한다.

고정 worker 수·retry 횟수·timeout으로 품질 완료를 판정하지 않는다. 운용 기본값은 설정과
환경 한계일 뿐 memory coverage를 조용히 절단할 권한이 아니며, backpressure로 지연되면
`deferred/backlogged`와 누락 범위를 보고한다.

## 8. `memory_recall_plan.v2`

검색은 다음 순서를 지킨다.

1. 현재 session과 허용된 branch 범위 확정;
2. 삭제·tombstone·superseded·시간 validity·근거 상태 hard filter;
3. POV, knower, visibility와 secret reveal hard filter;
4. entity/alias, 관계, 시간 범위와 구조화된 recall need로 후보 범위 축소;
5. Chroma semantic 후보를 MariaDB row로 hydration;
6. lexical, entity/KG, temporal proximity, recency, salience와 current-state
   relevance를 복합 평가;
7. 부족한 coverage에 대해서만 episode/chapter/arc/saga 또는 원문 심층 회상으로
   단계적 확장;
8. 선택·탈락 사유와 provenance를 trace에 기록.

현재 상태와 derived profile은 별도 route다. active body state와 current character state를
먼저 source-linked current/history row로 확인하고, stable baseline·dynamic digest·habit/
speech profile은 support-only route로 사용한다. topic continuity와 entity/event cue는
structured observation에서 도출하며 언어별 keyword·rare-word heuristic이나 고정 clue
score로 route를 선택하지 않는다. compiled profile만으로 coverage가 충분하다고 가정하지
않고 필요한 atomic row와 source excerpt까지 확장한다.

thread recall은 전체 eligible set, request에서 선택된 ID, 관련 있지만 deferred된 ID와
retrieval completeness를 구분한다. 4.1은 `selected/deferred/not_selected` 기억 전달 상태만
소유하고 `foreground/background` 서사 attention을 계산하지 않는다. 어떤 전달 상태도
`open/dormant/resolved` lifecycle을 변경하지 않는다. bounded query의 completeness를 증명하지
못하면 `potentially_truncated/coverage_gap`으로 남기며 검색되지 않은 thread를 resolved 또는
“다른 이야기 없음”으로 해석하지 않는다.

벡터 유사도 하나를 진실 점수로 사용하지 않는다. `top_k`를 채우기 위해 무관한 기억을
강제로 넣지 않으며 관련 기억이 없다는 결과를 정상으로 허용한다.

### 8.1 원문 심층 회상

원문 심층 회상은 모든 턴에서 전체 chat log를 넣는 기능이 아니다. 현재 요청에 과거
발언·날짜·장소·사건·물건을 확인할 recall need가 있고 구조화 기억만으로 coverage가
부족할 때만 실행한다.

검색 결과는 원문 전체가 아니라 필요한 excerpt와 앞뒤의 제한된 문맥, source pointer를
반환한다. 회상된 원문이 새 canonical 기억이 되려면 일반 admission을 다시 통과해야 한다.

긴 세션에서 전체 row를 읽는 방식이 병목으로 재현되면 먼저 기존 column과 index를
사용한 MariaDB 범위 조회를 구현하고, 그것으로 부족하다는 증거가 있을 때만 새 index
구조를 승인한다.

원문 route는 하나의 vector 검색으로 축소하지 않는다.

- exact/hash와 source/message ID route: 직접 인용·특정 발화·정정·reroll lineage;
- lexical route: 이름·별명·사물·장소·날짜와 rare phrase. 언어별 고정 질문 문구가 아니라
  structured cue와 indexed text를 사용;
- entity/relation/time/thread route: stable ID와 story-clock·knowledge·dependency hard filter;
- semantic route: 표현이 달라진 관련 원문 후보. similarity는 후보 신호이며 truth·merge·
  acceptance threshold가 아니다;
- neighborhood route: 선택된 source의 앞뒤 message, 같은 사건·발화·reaction의 bounded context.

planner는 route별 searched range, 단순 candidate count가 아닌 expected coverage, selected source,
hard-filter exclusion, unavailable index와 expansion stop reason을 추적한다. 특정 route가 비어도
다른 route를 실행하지 않은 채 `no_memory`로 결론내리지 않는다. 모든 route 결과는 MariaDB의
active source revision과 visibility를 재검증하고, raw context와 그 summary/profile이 같은
delivery purpose로 중복되면 root evidence cluster에서 합친다.

extractor·embedding·chunker·alias/entity mapping 또는 index contract가 바뀌면 영향 source와
vector version을 식별해 resumable rebuild를 실행한다. rebuild 중 old/new index의 coverage와
cutover fingerprint를 비교하고, rebuild 실패를 검색 결과 없음으로 위장하지 않는다.

## 9. `memory_injection_plan.v2`와 예산

저장량과 주입량을 분리한다. 세부 기억을 많이 보존하더라도 현재 장면에 관련된 항목만
주입한다.

Go backend가 다음을 최종 결정한다.

- ordered block과 item IDs;
- 각 item의 provenance와 inclusion reason;
- 각 item의 비구속적 memory delivery purpose와 root evidence lineage: current constraint,
  direct support evidence, already-realized reference, unresolved-state reference,
  historical reference 또는 no-new-realization record;
- 각 item의 `delivered_full`, `delivered_compact`, `suppressed_with_reason`, `deferred` 또는
  integrity-preserving override 상태와 reason;
- 제외·중복·지연 reason과 coverage gap;
- block별 사용 문자와 전체 사용량;
- 안전한 block/item 경계 압축과 절단;
- 최종 text와 hash.

thread item은 stable ID·revision, lifecycle, memory delivery state, outstanding consequence,
resolution scope/carry state와 eligible/deferred provenance를 함께 가진다. 하나의 selected
thread만 기억 블록에 전달하더라도 다른 관련 thread의 lifecycle을 바꾸지 않으며, closure
scope가 없는 요약을 결말 지시로 조립하지 않는다. 이 정보는 상태 설명이지 해당 thread를
진행·유예·종결하라는 지시가 아니다.

위 delivery state는 저장·검색 lifecycle과 분리된다. prompt에서 억제되거나 축약된 row를
삭제, tombstone 또는 retrieval disable로 바꾸지 않으며 explorer/trace에서 source와 사유를
검사할 수 있어야 한다. current body constraint, direct evidence, 사용자 정정, active
consent/boundary, unresolved obligation, secret/POV protection과 integrity warning은 native
overlap이나 prompt economy만으로 조용히 누락할 수 없다. 보존 여부는 고정 hard-floor
목록이 아니라 authority, visibility, current effect와 uncovered requirement를 읽은 resolved
backend policy가 결정한다.

JavaScript가 관찰할 수 있는 RisuAI recent chat, persona, bot card, lorebook, native memory와
decorator capability는 최소 observation으로 backend에 전달할 수 있다. native overlap은
low-authority support text의 중복 delivery를 줄이는 근거일 뿐 canonical truth나 저장을
비활성화하는 근거가 아니다. capability가 unknown이면 Go가 suppression을 추정하지 않는
보수적 plan과 명시적 reason을 반환한다. backend가 응답하지 않을 때 JavaScript는 같은
request/revision에 대해 이미 검증된 versioned plan 외의 local delivery policy를 계산하지
않고 원 payload를 보존하며 degraded/error를 표시한다.

JavaScript는 RisuAI lifecycle을 관찰하고 이 계획을 실제 payload에 적용한 뒤 적용 결과만
보고한다. 정책, ranking, budget 계산이나 후단 문자열 절단을 새로 추가하지 않는다.

4.1 정밀 기억은 기존 메인 장기 기억 예산 안에서 작동한다. 고정 lane 비율을 코드에
넣지 않고 current input, structured recall need, active entities, unresolved promise와 coverage에
따라 동적으로 배분한다. 메인 기억 예산을 원작 DB나 후속 서사 생성 보조가 빌려 쓰지
않는다.

우선순위 계약은 다음과 같다.

```text
현재 user input
-> 현재 상태와 직접 근거
-> 관련 원자적 장기 기억
-> 필요한 상위 계층 회상
-> 별도 예산의 원작 참고 자료
-> 후속 선택 기능인 서사 생성 보조
```

Step 28 visual sidecar는 4.1 delivery 계약의 구현 조건이 아니다. 향후 opt-in 실험을 하더라도
current input, direct evidence, canonical/current body state, correction, protection과 integrity
warning을 visual-only로 전달하지 않는다. visual packet은 source IDs, authority lane, fallback
text reference, renderer version, content hash, privacy scope와 invalidation identity를 가진
optional artifact일 뿐 memory source, vector source나 write evidence가 아니다.

## 10. 정책 하드코딩 금지 계약

값을 상수 이름, 설정 기본값, prompt, 정규식 또는 모델별 분기로 옮기는 것만으로는
하드코딩을 제거한 것이 아니다. 검색·선택·승격·시간·관점·예산·완료 결과를 바꾸는
고정값은 위치와 관계없이 policy hardcoding으로 취급한다.

### 10.1 금지 대상

- 고정 작품명, 인물명, 세력명, 플러그인명과 RP template;
- 고정 인물·후보·관계·memory lane 개수와 이를 성공 조건으로 사용하는 cap;
- 유사도·중요도·confidence·감정·성격의 전역 고정 cutoff;
- 고정 lane 비율, 문자 floor/cap과 turn 수 기반 계층 전환;
- `POV`, `기억`, `회상` 같은 prompt 문구나 언어별 단어 목록을 이용한 request,
  recall, secret, 관점과 성공 여부 분류;
- 모델 이름·정규식으로 memory policy나 출력 의미를 변경하는 분기;
- 능력·관심·직업·외형·지위·성별 같은 한 특성 영역을 고정표나 prompt 문구로 성격·감정·
  사회 행동·말투에 직접 연결하는 archetype mapping;
- 전역 호감도·친밀도 score, 고정 관계 단계 ladder, 접촉·친절·명령 keyword나 player/user
  우대 prior로 신뢰·애정·복종·동의·상호성을 승격하는 mapping;
- n-gram·문장 유사도 cutoff, 고정 novelty score, 허용 반복 횟수 또는 턴당 최소 사건 수로
  recap·progression·scene stagnation을 판정하는 정책;
- 장르명·모델명·특정 문구로 긴장·암울함·일상성·작품 종료를 분류하는 detector와 prompt;
- tension score·목표 곡선·고정 escalation cadence·turn-age·고정 thread 수·round-robin으로
  attention, fade, reopen 또는 closure를 결정하는 정책;
- selected/foreground thread의 해결을 sibling·parent·arc·saga·session 전체 종료로 바꾸는
  mapping, `all_story_complete` 추론 flag와 ending phrase detector;
- 시스템 시각, 고정 날짜, 고정 turn 또는 임의 carry-forward로 story time을 생성;
- 고정 신체 위험 keyword, 성별·이름 추론, 고정 생리 주기·임신 확률·임신 단계·회복 기간,
  신체 상태 우선순위와 prompt 행동 금지문;
- `qh_2/qh_4/qh_6/qh_8` 같은 이름을 필수 agent 수·외부 호출 수·독립 검증 수·품질
  등급이나 canonical admission 조건으로 해석;
- 빈 결과·provider 장애·예산 초과를 자료 생성 fallback으로 채우거나 `ready`로 위장;
- 테스트를 통과시키기 위한 고정 score, 고정 순위, 고정 출력 또는 무조건 성공 처리.

유사도와 중요도는 ranking signal일 뿐 단독 eligibility나 truth threshold가 될 수 없다.
score cutoff가 정말 필요하면 provider/API-family와 embedding space에 대해 실제 검증한
calibration artifact에서 요청별로 도출하고 `calibration_id`, `parameter_source`와 적용
이유를 trace에 남긴다. 임의 기본 calibration은 성공으로 처리하지 않는다.

후보·인물·lane 수는 현재 hard filter 통과 결과와 설정된 전체 자원 상한 안에서
동적으로 결정한다. 외부 자원 상한 때문에 잘린 경우 `truncated` 또는 `degraded`와 누락
coverage를 반환하며 품질 완료로 해석하지 않는다.

bounded query가 row/page/candidate/`top_k`/turn/window 상한에 도달하면 exhaustion 또는
coverage completeness를 production evidence로 증명하기 전까지 `potentially_truncated`로
취급한다. pagination·coverage escalation 없이 이를 `search_empty`, complete coverage 또는
품질 성공으로 보고하면 release blocker다.

모든 policy 함수는 resolved policy 객체를 입력받고 결과에 최소한 다음을 남긴다.

- `policy_version`;
- `parameter_source`와 `budget_source`;
- provider capability/calibration identity;
- inclusion/exclusion/drop reason;
- truncation과 uncovered requirement;
- 동일 입력·동일 MariaDB revision의 결정 hash.

필수 policy input이 없으면 숨은 기본값으로 결정하지 않고 명시적 degraded/error 상태를
반환한다.

### 10.2 허용 가능한 상수

다음은 기능 정책이 아니라 protocol·보안·저장 불변식일 때만 허용한다.

- contract version, enum, HTTP status와 RFC 형식;
- DB column/index 길이, FK, CHECK와 one-of cardinality;
- SSRF, request body size, redirect, timeout과 외부 호출 횟수 같은 보안·자원 상한;
- 사용자가 명시한 전체 문자/token/시간 예산;
- 선언된 provider/API-family의 endpoint와 request/response 형식.

자원 상한에 걸린 결과는 성공이나 관련 없음이 아니라 제한 상태로 보고해야 한다.
`0`, `1` 같은 값도 결과 정책을 결정한다면 자동으로 허용하지 않는다. 테스트 fixture의
숫자와 이름은 production policy가 아니어야 하며 기대값은 fixture의 source·branch·scope·
lifecycle에서 계산한다.

- 언어·인물명·작품명·모델 ID를 바꿔도 구조화 observation이 같으면 결정이 같아야 한다.
- 무관 후보를 추가하거나 입력 순서를 바꿔도 hard-filter 대상과 필수 recall이 변하지
  않아야 한다.
- score의 허용된 단조 변환이나 provider calibration 교체가 truth/visibility를 바꾸지
  않아야 한다.
- 후보·인물 수가 늘어도 숨은 cap 때문에 관련 항목이 조용히 사라지지 않아야 한다.
- turn/date를 임계점 주변에서 바꿨다는 이유만으로 회상 lane이 갑자기 바뀌지 않아야 한다.
- source-linked transition 없이 quiet turn이 기존 `15/20` 경계를 지나도 consequence/thread/
  psychology 상태가 expiry·dormant로 바뀌지 않아야 하며 schema 기본값을 바꿔도 같은 source
  lifecycle 결정은 같아야 한다.
- 기존 DB의 quiet-turn 기본값을 migration한 뒤에도 active consequence와 thread가 소실되거나
  재색인·restart에서 다시 dormant 처리되지 않아야 한다.
- 빈 결과, provider 장애와 예산 초과가 `ready` 또는 `no_new_memory`가 되지 않아야 한다.
- AST/literal audit는 보조 guard로 사용할 수 있지만 production 동작 검증을 대체하지
  않는다. 승인된 protocol constant allowlist 밖의 policy literal은 검토 실패로 처리한다.

### 10.5 보관·외부 자료 clean-room 경계

Step 26~28과 `character-modules`는 요구사항, 실패 사례와 평가 관점의 출처다. 외부 논문,
블로그, repository와 예제의 code, helper/function 이름, prompt wording, JSON/schema,
operation vocabulary, score formula, renderer asset와 benchmark fixture를 production 계약으로
직접 복사하지 않는다. 복사가 필요하면 origin, exact version, license, NOTICE/attribution과
현재 license compatibility를 먼저 기록한다. 논문·블로그 공개는 코드 license가 아니다.

identifier 변경, 번역, field reorder, 기계적 paraphrase 또는 구조를 따라 다시 쓰는 것은
clean-room 독자 구현으로 간주하지 않는다. 이런 derivative에는 원본과 같은 file-level
origin/version/license/NOTICE 검토가 필요하며 provenance나 사용 권한이 불명확하면
production, fixture와 generated artifact에서 사용할 수 없다.

YASNOTE hidden save block, 모델 tag 즉시 write, UI/regex state, 관계 점수와 신체 상태
가이드의 `BODY_RISK_KEYWORDS`, 고정 delivery priority, JavaScript local canonical fallback은
설계 원리가 아니라 제외해야 할 historical pattern이다. `참조 내역.md`의 Beta 0.8
Python/SQLite 구현 판정은 조사 provenance일 뿐 현재 3.0/4.1 production evidence가 아니다.

### 11.0a 버전 내부 work packet과 누적 품질 게이트

아래 packet은 버전 번호를 늘리기 위한 목록이 아니라 한 변경이 여러 실패 원인을 동시에

|---|---|---|
| `3.6-A` | 기존 schema·저장/추출/reprocess route와 3.3 source spine의 integration inventory | 지원 DB clone과 실제 production route에서 source FK·transaction·vector write·speaker 공백·migration 위험이 requirement별로 재현됨 |
| `3.6-B` | `entity_identity.v1`·speaker attribution·namespace 격리 | 동명이인·별명·복수 화자·Host-only/reference/session entity가 근거 없이 merge되지 않고 ambiguous attribution은 raw source와 review 상태를 유지함 |
| `3.6-C` | `precise_memory_unit.v1`과 truth/authority admission | 한 턴의 독립 사건·상태·발언·인식이 atomic row와 exact source pointer로 분리되고 거짓말·추측·OOC·proposal이 objective truth로 자동 승격되지 않음 |
| `3.6-D` | source dependency·idempotency·reprocess·migration | edit/correction/source revision이 파생물을 재구축하고 retry·replay가 중복 importance·event·관계·profile을 만들지 않으며 migration이 중단·재개 가능함 |
| `3.6-E` | admission owner cutover와 release integration | complete-turn/background/reprocess가 공통 Go admission transaction을 사용하고 JS·옛 병렬 writer가 제거되며 기존 DB upgrade·no-provider·crash fixture가 통과함 |
| `3.6-F` | 기존 3.5 source-backed 출력 가이드의 균형 복구 | 감독관이 실제 전달된 안전 처리 기억 문장과 exact ref를 함께 읽고, 기억 충실도와 선택형 표현 지원을 분리하며, 3,000자 기본 예산에서 중복 ID 때문에 호출이 차단되지 않고 어떤 강도에서도 story truth·사용자 행동·관계 변화·사건 종결 권한을 얻지 않음 |

##### 3.6-B 동명이인·공유 별칭·크로스오버 보완 게이트

`3.6-B`는 이름 문자열을 stable identity로 사용하는 것을 끝내는 단계다. 현재의 source-bound
identity occurrence 저장만으로는 session 전체에서 같은 인물을 재사용하는 canonical root나
동명이인 후보 판정이 완성됐다고 보지 않는다. 특히 기존 이름 기반 projection의 suffix·분리
표기·로마자 alias 일치는 stable identity의 merge 권한이 될 수 없다.

다음 사례를 각각 독립 fixture로 고정한다.

- `박한얼`과 `김한얼`은 서로 다른 session entity이며 `한얼`은 두 인물이 공유하는
  `alias_conflict`다.
- 서로 다른 원작의 `호시노 아이`와 `하야사카 아이`는 서로 다른 reference entity와 session
  entity이며 `아이`는 공유 별칭이다.
- `아이가 웃었다`의 `아이`처럼 동일 문자열이 일반명사로도 쓰일 때는 이름 문자열 일치만으로
  entity mention을 만들지 않는다.
- 서로 다른 작품·판본·continuity에 완전히 같은 전체 이름이 있어도 `stable_work_id`,
  `edition_id`, `continuity_id`, reference/session namespace가 다르면 자동 merge하지 않는다.
- 하나의 reference entity가 평행세계·회귀 전후·AU 등 복수 session incarnation으로 등장하면
  reference binding은 공유할 수 있어도 session entity ID는 분리한다.
- 사용자/OOC, player character, NPC, Host setting과 reference entity가 같은 표시 이름을
  공유해도 subject identity를 분리한다.

판정과 저장의 필수 결과는 다음과 같다.

1. 정확한 전체 이름과 source span은 긴 표기 우선으로 후보를 찾되, 작품명·직책·내부 ID를
   출력용 이름에 합성하지 않는다.
2. 공유 별칭·동명이인·일반명사 충돌에서 단일 후보를 증명할 근거가 없으면
   `unknown/tentative/needs_review` mention으로 보존하고 임의의 기존 인물을 선택하지 않는다.
3. 모호한 mention은 character state, 관계, 감정, 소지품, 비밀의 knower, 사건 참여자,
   speaker attribution과 atomic memory subject를 어느 후보에도 권위 있게 쓰지 못한다.
4. Host 작가 노트·lore와 원작 reference는 후보 및 binding evidence가 될 수 있지만 session
   등장·현재 상태·사건의 root evidence를 대신하지 않는다.
5. 이후 active source에서 전체 이름·화자·청자·명시적 정정처럼 충분한 근거가 생기면 mapping
   revision과 dependency reprocess로 이전 tentative mention을 연결한다. 원문 occurrence ID를
   다시 쓰거나 과거 row를 이름 기준으로 덮어쓰지 않는다.
6. vector similarity, 이름 길이·suffix, 등장 빈도, 최근성 또는 모델 confidence만으로
   동명이인 중 한 명을 선택하지 않는다.

검증은 단계별로 누적한다.

- `3.6-B`: 후보 발견, alias conflict, namespace와 session incarnation 분리, ambiguous raw
  mention 보존을 production identity owner에서 증명한다.
- `3.6-C`: unresolved identity가 atomic fact·state·relationship·knower·speaker row로
  승격되지 않는 must-not-admit 검증을 통과해야 한다.
- `3.6-D`: 뒤늦은 명시적 근거·사용자 정정·source edit가 mapping revision과 파생물 재처리를
  일으키고 잘못 연결된 row/vector가 남지 않아야 한다.
- `3.6-E`: 공통 admission owner와 worker를 먼저 전환하되, cross-turn review/split/merge와
  기존 DB migration을 dry-run·clone·rollback으로 검증한 뒤에만 3.6 전체 release gate를
  완료한다.
- `3.8`~`3.9`: 상태·관점·비밀·관계·profile이 이름 문자열이 아니라 확정 stable ID를
  소비하는지 검증한다.
- `4.0`: shared alias 질의에서 잘못된 인물의 기억을 주입하지 않고, 확정된 인물의 기억만
  actual payload에 전달되는지 must-recall/must-not-recall 쌍으로 검증한다.
- `4.1`: 실제 RisuAI 크로스오버 세션에서 reroll·delete·branch·restart·reindex 후에도
  identity merge, 기억 오염 또는 tombstoned mapping 부활이 없는지 live gate로 닫는다.

이 게이트가 문서·단위 테스트에만 존재하면 `release_gate_verified`가 아니다. `3.6-B`가
완료되지 않은 상태에서 `3.6-C` 이후 준비 작업은 할 수 있지만, unresolved identity를 이름
문자열로 대신 연결하거나 3.6·후속 버전 완료를 선언할 수 없다.

현재 구현 상태(2026-07-28):

- `3.6-A`: `source_characterized`. production owner·row 공백과 위험 특성 테스트를 고정했다.
- `3.6-B`: `same-turn homonym safety source_implemented / cross-turn identity and live
  migration gates pending`. additive identity schema, production saver, namespace 격리,
  exact full-name 판정, 동명이인 occurrence 분리, 공유 별칭·alias-only 일반명사 연결의
  `session_unknown/needs_review` 격리, 중첩·잘린 화자 excerpt 차단, rollback 경로와 자동
  회귀는 구현됐다. 별칭 표면은 원문 위치가 있어도 동일인 확정 권한으로 사용하지 않는다.
  cross-turn canonical root, reviewed split/merge와 identity-aware 과거 occurrence read는 아직
  완료되지 않았다.
- `3.6-C`: `source_implemented / existing DB migration and live release gates pending`.
  `precise_memory_unit.v1` additive schema와 production saver가 accepted current source,
  exact span, verified Direct Evidence를 통과한 event·state·utterance·observation을 독립
  row로 저장한다. 같은 턴의 unique source-observed stable ID만 actor·subject·speaker·knower
  pointer가 될 수 있고 공유 별칭·동명이인·모호한 participant는 review/non-objective로
  격리된다. belief·proposal·lie·deception·speculation·uncertain·OOC는 objective world
  authority를 얻지 않는다. production aggregate `memories` writer와 공통 재처리 executor는
  3.6-E에서 전환했으며 cross-turn canonical identity와 precise recall은 아직 전환하지 않았다.
- `3.6-D`: `lifecycle source_implemented / consumed by the 3.6-E worker, live gates pending`.
  accepted raw source revision, active logical-turn DB uniqueness, precise dependency
  edge, replacement·rollback·session invalidation, durable reprocessing job과 revision-fenced
  vector outbox를 production Go 경로에 연결했다. critic 실패·설정 누락은 같은 source/version
  key로 중복 없이 job에 남고, rollback은 source invalidation 실패 시 canonical delete 전에
  멈추며 Chroma 장애는 retryable outbox로 남긴다. session delete는 outbox delete identity를
  보존하면서 과거 raw/precise/upsert payload를 비운다.
- `3.6-E`: `common admission and worker source_implemented / disposable DB, package, and
  live release gates pending`. foreground complete-turn과 durable worker가
  `memory_admission.v1` Go transaction을 공유한다. transaction은 active source fence 아래
  compatibility memory, critic Direct Evidence, precise memory, dependency, admission marker와
  vector outbox를 함께 commit한다. 첫 extraction JSON을 source revision에 보존해 crash 뒤
  secondary projection도 같은 결과로 이어서 처리한다. admin rescan과 Explorer 재분석은
  direct writer 대신 durable job을 enqueue하며, `needs_embedding` outbox는 runtime embedding
  설정으로 materialize한다. production lifecycle authority의 legacy memory/evidence 병렬
  writer는 차단했다. updater는 immutable historical migration을 유지하면서 새 번호의
  `ADD COLUMN IF NOT EXISTS` migration과 동반 fresh schema만 허용한다.
- 3.6-E core transaction 밖의 identity/KG/state writer는 확정 extraction 기반 idempotent
  재시도로 복구하며, 모든 projection이 한 SQL transaction인 것은 아니다. 기존 3.5 summary를
  source/identity로 추측 backfill하지 않고 accepted raw source가 있는 turn만 재처리한다.
- disposable MariaDB clone의 3.5→3.6 upgrade/rollback, live RisuAI 동명이인·복수 화자·
  reroll, 지원 OS 3.6 package 증거가 없으므로 `release_gate_verified`나 3.6 완료로
  표시하지 않는다.
- schema-aware updater의 source·자동 회귀는 구현됐지만 실제 3.5 설치 package, disposable
  DB clone, schema/health fault recovery와 지원 OS별 증거는 미완료 gate다.
- 파일·테스트·커밋별 증거는
  [`3.1-3.6-e-implementation-ledger.md`](3.1-3.6-e-implementation-ledger.md)에 기록한다.

##### 3.6-F source-backed 서사 가이드 균형 복구

`3.6-F`는 3.6 메인 장기 기억의 소유 범위를 장면 simulation이나 plot planner로 확대하는
작업이 아니다. 3.5의 기존 `response_execution_contract.v1`과 출력 guide가 기억 충실도
검사만 남기고 선택형 표현 지원까지 차단한 문제를 3.6의 source·visibility·authority
경계 안에서 복구하는 호환 작업이다.

현재 source에서 확인된 문제는 다음과 같다.

1. 감독관 LLM은 전달 기억의 `source_ref` 목록은 받지만 해당 ref와 실제 전달 문장의
   대응을 받지 못한다.
2. 장기 기억 ref가 없으면 현재 사용자 입력과 현재 장면만으로 가능한 표현 지원까지
   `no_support`로 처리한다.
3. `must_preserve`와 `must_not_assert`가 동일 ref를 실제 주입 문장에 반복해 Host system
   ref 수에 따라 안내문이 커지고, 첫 고정 항목이 예산을 넘으면 감독관 호출 전체가
   `deferred_insufficient_narrative_budget`로 차단된다.
4. prompt·요청·result metadata·fallback·최종 주입에서 같은 강제 방지 문구를 반복한다.
5. `medium`과 `strong`의 backend coverage가 같고 UI의 pacing 지원 설명과 실제 계약이
   어긋난다.
6. JavaScript와 Go가 `auto` guide mode를 각각 판정하며, active prepare 경로의
   `narrative_stance`, `auto_advance_trigger`, `persistent_guidance` 일부는 실제 감독관
   payload에 의미 있게 소비되지 않는다.
7. 설정 UI의 `pluginMainApplyMode`를 `입력 보조 컨텍스트`라고 표시해, 항상 적용하는
   직전 완료 턴 `Input Context`와 선택형 입력 개선 LLM을 같은 기능처럼 보이게 한다.
   또한 이 선택형 LLM을 끄면 서사 가이드 강도와 stance까지 비활성화해 서로 독립인
   실행 경로를 잘못 결합한다.

구현 순서는 다음으로 고정한다.

1. 기존 source 계약과 guide OFF parity를 회귀로 고정하고, 기억 없음·전달 기억 있음·
   protected memory·다수 Host ref·각 strength를 known-broken fixture로 추가한다.
2. Go가 메인 모델에 실제 전달하기로 확정한 문장만
   `{source_ref, bounded_text, visibility/knowledge boundary}`로 감독관 support packet에
   연결한다. raw private memory, DB 원문, 전달되지 않은 후보는 넣지 않는다.
3. 기억 사실의 모순·누락·비밀 경계를 다루는 `fidelity` lane과, 현재 입력을 근거로
   분위기·표현·pacing·scene emphasis를 선택적으로 제안하는 `expression` lane을 분리한다.
   callback처럼 과거 사실을 언급하는 항목은 delivered-memory ref를 필수로 한다.
4. strength는 권한이 아니라 허용 coverage만 바꾼다. `weak`도 현재 입력만으로 낮은 영향의
   표현 지원이 가능해야 하며, `medium`은 pacing·scene emphasis·callback을, `strong`은
   추가로 가역적 선택지를 허용할 수 있다. 어느 강도도 사용자 행동, 새 사실·감정·지식,
   관계 변화, 사건 종결, scene jump 또는 canonical write를 요구할 수 없다.
5. 실제 출력 guide에서 source ID 반복을 제거하고 structured trace에만 보존한다. 고정
   안전 경계와 LLM proposal은 lane별로 예산을 조립하며, 한 항목의 초과가 뒤의 짧은
   항목이나 감독관 호출 전체를 차단하지 않게 한다.
6. `auto` mode policy는 Go만 소유한다. JavaScript는 공식 Host observation과 사용자의
   `auto` 설정을 전달하고 backend plan을 그대로 적용·표시한다. 사용되지 않는 adapter
   계산과 오래된 UI 설명은 같은 work item에서 제거한다.
7. 직전 완료 턴 `Input Context`는 일반 턴의 기본 연속성 앵커로 유지한다. 첫 턴처럼
   이전 완료 턴이 없는 경우에는 켜진 상태에서 빈 결과가 정상이다. 선택형
   `pluginMainApplyMode`는 `입력 개선 LLM`으로 명확히 표시하고 서사 가이드 controls와
   분리한다.
8. Go 회귀, JavaScript syntax, source diff 검증 뒤 실제 RisuAI에서 한국어 입력,
   protected memory, 기억 없는 초기 turn, weak/medium/strong, 3,000자 예산과 final displayed
   output을 확인한다.

최소 안전 경계는 유지한다.

- 현재 사용자 입력이 항상 최우선이다.
- 감독관 결과는 `proposal_only`, `truth_authority=false`, `would_write=false`다.
- 사실을 언급하는 항목은 실제 전달 문장과 exact source ref가 함께 뒷받침해야 한다.
- 전달되지 않은 private memory와 hidden knowledge는 prompt·trace·HUD에 노출하지 않는다.
- 사용자/주인공 행동, 관계 변화, 사건 종결, 비가역 결과와 canonical write를 감독관이
  결정하지 않는다.
- supervisor/provider 실패는 본문 생성을 막지 않고 정직한 fail-open 상태로 남는다.

완료 증거는 source 테스트만으로 닫지 않는다. 자동 회귀는 support packet의 본문/ref
정합성, role별 ref policy, strength coverage, item별 예산 조립, guide OFF parity와
JavaScript 정책 제거를 증명해야 한다. 실제 RisuAI와 실제 모델에서 “조언을 무시하거나
다른 합법적 전개를 선택할 수 있음”, 비밀 비노출, 사용자 행동 비강제와 HUD 상태가
확인되기 전 상태는 `source_implemented / live guide quality gate pending`이다.

##### 3.8-A 구현 기록 — `story_clock.v1`과 시간 불확실성

- Critic은 `story_clock.v1` proposal에서 절대 시각, daypart·계절의 부분 시각,

  턴의 exact·active direct evidence가 모두 확인된 경우에만 canonical

### 3.5 이관 gate — 2026-07-26

3.5의 종료선은 Output Fidelity `3.5-A/B/C`와 플로팅 작업 HUD `3.5-E`로 고정한다. 요청 단위 명사 언급·개체·관계
주장·Direct Evidence 연결과 관계 UI는 4.1 이관 gate가 아니라 4.6이 소유한다. 아래의
기존 agency·장애·성능·release 책임만 삭제하거나 완료 처리하지 않고 4.1 gate로 이관하며,
이관 항목은 3.5 완료를 막지 않지만 4.1 완료에는 release-blocking이다.
현재 `/prepare-turn`·`/complete-turn` 요청을 표시하는 작은 비차단 플로팅 HUD는 3.5-E가
소유한다. 4.1은 같은 ViewModel을 영속 background job, 재시작 복구와 cold-start 전체 진행으로
확장할 뿐 3.5 UI를 병렬로 다시 만들지 않는다.

| 이전 3.5 책임 | 4.1 이관 위치 | 4.1에서 닫아야 하는 증거 |
|---|---|---|
| 과거 `3.5-D`였던 agency·closure·권한 adversarial | `3.8-C/D`, `3.9-A`, `4.1-G` | wrong-knower·비밀 누출·일방 관계의 상호성 승격·사용자 행동/감정 강제·국소 사건의 전체 thread closure 확대가 source/관계/lifecycle 계약에서 차단되고 정상 진행을 일률적으로 억제하지 않음 |
| `3.5-E`에서 제외한 영속 background job·장애 격리·메인 회귀 | `4.1-B/D/F/G` | provider/backend/Host 장애와 restart·upgrade에서 ready·생성·저장·삭제·메인 기억·원작 DB가 보존되고, 영속 작업 상태가 3.5 플로팅 HUD의 ViewModel 계약을 확장해 같은 correlation/revision을 표시함 |

| 기존 `3.5-F` 격리 live cohort·release manifest | `4.1-G` | loaded package와 실제 RisuAI/MariaDB/Chroma에서 source→recall→payload→final→admission 계보, 사용자 채택·리롤 사유, OS·upgrade·fault evidence가 전체 requirement에 연결됨 |

이관은 서사 simulation을 4.1에 넣는 결정이 아니다. 기억·source·guide에서 보장할 수 있는
권한·비밀·관계·closure 근거와 장애·성능·lifecycle만 4.1 gate가 소유한다. 활성 인물 선택,
장면 진행, 장르 압력과 모델 적응형 표현은 계속 4.6~5.0의 read-only 소비 범위다.

### 직전 확정 턴 파생 기억 비동기화 — 4.0-F / 4.1-B·D·F·G 후속 작업

상태는 `future design`이다. 3.5 release에 비동기 호출만 덧붙이거나 JavaScript
fire-and-forget queue로 먼저 구현하지 않는다. 이 작업은 `4.0-F`가 foreground/background
지연과 provider 자원 경합을 측정하고, `4.1-B`가 영속 작업·transaction·재시작 복구를,
`4.1-D/F/G`가 final lifecycle, 장기 session과 실제 package의 live evidence를 닫을 때 수행한다. 리롤·삭제·편집
시 source의 의미는 새로 만들지 않고 `4.1-A`의 logical turn lifecycle을 소비한다.

#### 현재 동작과 문제

- RisuAI의 final assistant 출력이 관찰된 뒤 JavaScript `onAfterRequest`가
  `/complete-turn`의 전체 응답을 기다린다.
- Go `/complete-turn`은 raw user/assistant를 먼저 내구 저장한 뒤 같은 HTTP 요청 안에서
  평론가 LLM, 파생 기억 저장, embedding/vector와 후속 검사를 순차 실행한다.
- 현재 Go는 평론가 호출 뒤 source acceptance revision을 다시 확인하여 이미 superseded된
  generation의 파생 저장을 거부할 수 있다. 그러나 긴 평론가 호출 동안 Host가 새 리롤을
  아직 보고하지 못하면 `afterRequest` 완료와 리롤 관찰이 함께 늦어질 수 있다.
- 평론가가 30초 이상 걸리는 환경에서는 assistant 본문이 화면에 보이더라도 Host hook,
  HUD terminal 상태, 다음 조작의 체감 완료가 늦어질 수 있다. 긴 시간 자체가 기억 오염의
  원인은 아니지만 stale 작업이 살아 있는 경합 구간을 넓힌다.

#### 선택할 기본 실행 모델

현재 턴 `T`의 본문 생성과 `T`의 완성형 기억 추출을 동시에 실행하지 않는다. `T`의
assistant 본문이 존재하기 전에는 사건·관계·상태·요약의 source가 완성되지 않았기 때문이다.
대신 다음 모델을 기본 후보로 측정한다.

1. `T`의 active final을 실제 Host 관찰로 확정한다.
2. `T`의 raw user/assistant와 source identity를 짧은 동기 경계에서 먼저 내구 저장한다.
3. 동일 transaction/outbox 경계에서 `T`의 파생 처리 작업을 영속 등록한다.
4. raw와 작업 등록이 확인되면 `onAfterRequest`를 반환한다.
5. Go worker가 평론가 LLM, 응답 검사, 파생 기억 admission, embedding/vector를 수행한다.
6. 각 canonical/vector commit 직전에 logical turn·generation/revision·final content hash가
   여전히 active인지 비교한다.
7. 사용자가 다음 턴 `T+1`을 시작하면 메인 본문 생성과 직전 확정 턴 `T`의 파생 처리는
   provider 자원과 일관성 조건이 허용하는 경우에만 병렬로 진행한다.

이 구조의 목적은 기억 처리를 항상 한 턴 늦추는 것이 아니다. 사용자가 답변을 읽는 동안
끝나면 같은 턴 직후 완료되고, 다음 요청까지 남아 있을 때만 `T+1` foreground와 겹칠 수 있다.

#### 다음 턴 일관성과 read barrier

- `T+1`의 실제 RisuAI payload가 직전 raw user/assistant를 이미 포함하면, `T`의 파생 기억이
  아직 pending이어도 같은 내용을 다시 만들기 위해 메인 생성을 전역 대기시키지 않는다.
- 직전 raw가 Host payload에 없거나, branch/cut/context 제한 때문에 `T+1`의 필수 기억을
  다른 경로에서 얻을 수 없다면 해당 source에만 좁은 read barrier를 적용한다.
- read barrier는 전체 queue 완료나 고정 30초 대기가 아니다. 필요한 logical turn/source의
  raw fallback 또는 해당 파생 작업의 commit 여부만 확인한다.
- 아직 admission되지 않은 평론가 proposal을 canonical memory처럼 주입하지 않는다. raw
  fallback은 원문 source로 표시하고, 파생 결과와 같은 권한을 부여하지 않는다.
- 메인 LLM에게 본문과 함께 기억용 JSON·숨은 metadata를 출력하도록 요구하지 않는다.
  RisuAI 본문 생성과 Archive Center의 기억 admission을 결합하면 모델별 형식 오류,
  metadata 노출, 리롤 후보별 폐기와 provider 종속성이 커진다.

#### 리롤·삭제·편집 안전성

- 하나의 user 입력과 그 assistant 후보들은 동일 logical turn에 속하며, 현재 화면에 확정된
  결과 하나만 `active_final`이다.
- 리롤 candidate가 생성되는 동안에는 직전 확정 결과를 유지한다. 새 candidate를 raw나
  canonical memory source로 먼저 승격하지 않는다.
- 새 final이 확정되면 이전 generation 작업을 `superseded`로 바꾸고 provider 취소를
  best-effort로 요청한다. 취소 성공 여부와 무관하게 compare-at-commit fence가 늦게 도착한
  평론가·embedding 결과의 write를 차단해야 한다.
- 이전 final의 파생 row/vector가 이미 commit되었다면 새 결과를 append하지 않고 source
  dependency를 따라 원자적으로 교체·무효화·재색인한다.
- 삭제·편집·branch 이동도 버튼명이나 DOM 문구가 아니라 Host가 노출한 session/chat/branch,
  logical turn, message index/ID, generation/revision과 final display 상태로 판정한다.

#### provider 동시성 정책

- 메인 RisuAI 생성은 항상 foreground 우선이다. background 평론가가 메인 생성의 연결,
  첫 토큰 또는 전체 응답을 늦추면 병렬화를 성공으로 세지 않는다.
- cloud provider는 계정·gateway별 rate limit, 동시 요청 수, 429/timeout과 실제 latency를
  기준으로 background 동시성을 제한한다.
- 동일 gateway가 요청을 직렬화하거나 동일 계정 quota를 공유하면 background를 pause하거나
  메인 생성 뒤로 미룬다.
- Ollama와 같은 단일 로컬 GPU/CPU runtime은 두 모델 호출이 VRAM·메모리 대역폭을 나눠
  메인 응답을 크게 늦출 수 있으므로 기본 병렬 대상으로 가정하지 않는다.
- provider 이름별 하드코딩 대신 측정된 capability·설정·오류 상태를 Go scheduler 입력으로
  사용한다. session별 파생 작업은 중복 실행하지 않고 global/provider별 bounded concurrency를
  가진다.

#### 영속 작업과 HUD

- 작업 queue의 canonical owner는 Go와 MariaDB/outbox다. JavaScript process-local 배열,
  브라우저 timer, DOM watcher 또는 HUD polling을 복구 근거로 사용하지 않는다.
- backend restart 뒤 pending 작업은 같은 idempotency key와 source fence로 재개한다.
- raw 저장 성공/평론가 실패, 평론가 성공/DB 실패, DB 성공/vector 실패를 서로 다른 상태로
  보존하고 재시도 범위를 분리한다.
- 3.5 HUD의 기존 단계·시간·reason ViewModel을 확장하여 `raw 저장 완료`,
  `파생 처리 대기`, `foreground 때문에 보류`, `평론가 진행`, `vector 진행`,
  `리롤로 무효화`, `재시작 후 재개`를 같은 correlation/source identity로 표시한다.
- HUD를 닫거나 사용하지 않아도 queue 의미, scheduling, 재시도와 완료 결과가 달라지지 않는다.

#### 구현 순서

1. 현재 동기 경로에서 final 표시, `onAfterRequest` 반환, raw 저장, 평론가, 파생 DB,
   embedding/vector와 다음 턴 시작 시각을 분리 측정한다.
2. raw 저장과 파생 작업 등록을 하나의 내구 경계로 만들고 기존 동기 writer와 중복되지 않게
   owner를 전환한다.
3. 영속 worker에 source acceptance compare-at-commit, idempotency, restart resume와
   단계별 retry를 연결한다.
4. 리롤·삭제·편집·branch의 supersede/replace와 stale worker 차단을 production Host
   observation으로 검증한다.
5. `T+1` payload의 직전 raw 포함 여부를 확인하고 필요한 source에만 read barrier를 연결한다.
6. provider별 foreground 우선 scheduler를 적용하고 cloud shared quota와 local runtime
   경합을 따로 측정한다.
7. 장기 session·restart·provider timeout·DB/vector fault와 실제 RisuAI package에서
   non-regression evidence를 연결한다.

#### 완료 증거

- final 표시와 raw 내구 저장은 평론가·embedding 지연에 묶이지 않고 각각 측정된다.
- foreground 첫 토큰·전체 응답 시간이 background 비활성 baseline보다 악화되면 원인과
  provider 상태가 보고되며 병렬화를 강행하지 않는다.
- 리롤·삭제·편집·branch·restart에서 stale worker canonical/vector write가 0이다.
- 한 logical turn의 active final과 파생 set이 하나뿐이며 append형 중복이 없다.
- raw 성공 뒤 critic/provider 실패에서도 원문 유실이 0이고 재시작 뒤 pending 작업이 복구된다.
- `T+1`에서 직전 턴의 필수 내용 누락이 0이며, 이를 위해 모든 다음 턴을 평론가 완료까지
  대기시키지 않는다.
- 동일 turn의 중복 평론가·embedding·upsert가 0이고 retry는 실패한 단계부터 이어진다.
- HUD의 단계·시간·보류·무효화 reason이 실제 worker/outbox 상태와 일치한다.

#### 중단 조건과 금지 사항

- 실제 Host generation/revision/final-display를 신뢰성 있게 관찰할 수 없으면 리롤 안전
  비동기화를 시작하지 않는다.
- raw 저장과 영속 작업 등록의 crash-safe 경계를 만들기 전에는 `onAfterRequest`의 await만
  제거하지 않는다.
- provider 병렬 실행이 메인 응답을 느리게 하면 background를 pause/serialize하며 별도
  모델명 예외를 추가하지 않는다.
- 다음 턴이 직전 raw와 pending 상태를 모두 읽지 못하면 한 턴 지연을 기본값으로 강제하지
  않고 좁은 read barrier부터 완성한다.
- streaming/candidate, 평론가 report 자체와 미검증 metadata를 final source 또는 canonical
  memory로 저장하지 않는다.

예측 가능한 오류를 라이브 사용자에게 떠넘기지 않기 위해 unit test만으로 packet을 닫지 않는다.
source/lifecycle packet에는 최소한 실제 Host hook, 기존 DB clone, restart와 stale-result test가,
저장 packet에는 transaction·idempotency·migration test가, retrieval/delivery packet에는
must-recall/must-not-recall·actual payload parity가 필요하다. 사용자 피드백은 모델별 체감과
장기 사용 품질을 보완하지만 기본 기능 오류의 대체 검증이 아니다.

각 3.6~4.1 packet은 `3.1-3.5-consolidated-release.md`의 추가 검증·후속 인계와 이 문서의
lifecycle 결함 방지 기준을
상속하고 다음 항목을 추가한다.

- source가 맞지만 entity/speaker/time/knower/subject가 틀린 오류는 typed FK·hard filter와
  must-not-recall fixture로 release 전에 차단한다;
- 저장 성공·vector 실패, vector 성공·DB rollback과 stale worker는 crash/fault injection에서
  no-half-state로 증명한다;
- migration·reindex·entity remap 뒤 row/vector/projection set과 hash를 재대조하며 단순 row count
  또는 `/ready`만으로 성공을 판단하지 않는다;
- 정확도·latency·DB/index 증가·예산을 따로 보고하고 단일 총점이나 고정 합격 점수로 결함을
  숨기지 않는다;
- 실제 package·OS·기존 DB에서 처음 재현되는 기본 기능 오류는 해당 packet의 release evidence
  결손으로 되돌려 기록하고 후속 버전의 임시 fallback으로 덮지 않는다.

- 지원 기존 DB에 7.2 migration/backfill을 적용하고 deferred source를 5.F job으로 재처리한다.
- source→derived dependency와 revision compare-at-commit을 연결해 stale 결과를 거부한다.

게이트: 주입 가능한 모든 파생 기억이 정확한 source pointer를 가져야 한다. annotated
expected units와 실제 MariaDB 복수 row를 종류별로 대조하고, 공개/비밀/인물별 인식/

같은 root evidence의 raw/event/summary/profile 재처리가 새 event, importance, 습관·성격 또는
관계 강화를 만들면 실패한다.
감독관 proposal이 final displayed output에 포함됐다는 occurrence만으로 causal permission,
agency owner 또는 thread resolution·상위 closure authority를 획득해도 실패한다.
복수 start message가 한 사건으로 합쳐지거나, 표시되지 않은 generation·reroll 전 답변·삭제된
source·stale worker가 canonical row를 만들거나, 기존 DB의 누락 ID를 창작해 precise로 승격해도
실패한다.
같은 이름의 Host setting·session·원작 reference identity가 자동 merge되거나, Host-only entity가
session first-seen·사건·관계·신체 상태·인물별 지식·turn realization을 만들거나, lore
revision/delete 뒤 binding·alias·vector가 재등장해도 실패한다. 반대로 명시적 active lore의
known-positive entity/alias evidence가 안전을 이유로 영구 `unknown`에만 머물고 실제

게이트: 모호한 시간을 임의 날짜로 확정하지 않고, 오래된 상태가 최신 상태로 다시

근거 없는 장면 전환이 상태를 지우거나 reroll/rollback의 폐기 상태를 부활시키면 실패한다.

### 단계 3. 인물별 인식·비밀·발언 연결

- 객관 사실, 소문, 오해와 숨김을 분리한다.
- 관계 방향, consent/boundary와 OOC/meta scope를 같은 authority/hard-filter 계약에
  연결한다.
- 관계 interaction은 방향·상대·domain·visibility·consent와 source를 보존하되 durable
  current/history·transition projection은 단계 4의 `relationship_state.v1` owner가 계산한다.

게이트: 허용되지 않은 관점에서 비밀이나 잘못된 knower 기억이 하나라도 주입되면
실패한다. 권한 없는 원문은 candidate ID, trace, backend packet에도 나타나면 안 된다.
OOC/meta가 in-world event·KG·character memory를 만들거나 동의 철회 이전 상태가 활성화돼도
실패한다.
user/player 입력·일방 감정·친절·접촉·명령 수행만으로 상대 인물의 신뢰·애정·친밀감·
복종·동의·상호성이 생성되거나, 명시적 단일 source가 지지하는 큰 관계 변화를 고정 횟수
미달이라는 이유로 거부해도 실패한다.

### 단계 4. Character profile과 습관·성격·말투 증거 누적

- `relationship_state.v1`의 방향·domain별 current/history, interaction event, transition,
  counter-evidence와 rupture/recovery lineage를 연결한다.
- `habit_evidence.v1`을 support-only psychology branch에 연결한다.
- 중복 evidence, 반례, 상황 의존성과 사용자 정정을 처리한다.
- 말투는 복사 가능한 예문보다 대화 원리와 상대별 변화를 저장한다.
- `character_profile.v1`의 stable baseline, current snapshot과 dynamic digest를 동일 evidence
  spine에 연결하고 attribute observation과 factual event를 분리한다.
- 특성의 의미 영역, `supported_expression`, `unsupported_entailment`, counter-evidence,
  relationship variant와 state modulation을 같은 evidence spine에서 파생한다. 관심·능력·
  직업·외형·지위가 성격·감정·말투를 자동 결정하지 못하게 한다.
- 실제 user/OOC profile과 player character/NPC profile의 subject namespace, retrieval와
  delivery를 분리한다. 추론형 cross-session user profiling은 이 단계의 완료 조건이 아니다.

게이트: 단일 행동이 자동으로 습관이 되지 않고, 같은 evidence 재처리가 성향을 강화하지
않으며, 반례가 보존되어야 한다. compiled profile이 atomic truth를 overwrite하거나 캐릭터
발언·행동·신체 상태가 실제 user profile row를 만들면 실패한다. 한 특성 영역의 fixture가
근거 없는 다른 영역의 성격·말투·사회 행동을 생성하거나, 반례와 관계별 예외를 제거한
단일 전형으로 compile되면 실패한다. 관계 current/history가 방향·domain·counter-evidence·
consent와 source transition 없이 생성되거나 3.8의 interaction observation을 durable 관계로
그대로 승격해도 실패한다.

### 단계 5. 정밀 회상 planner

- hard filter 뒤 복합 retrieval과 coverage 기반 escalation을 구현한다.
- 과거를 직접 묻는 요청뿐 아니라 현재 장면의 entity·time·relationship·unresolved
  continuity에서 구조적으로 도출한 recall need에도 원문 심층 회상을 사용할 수 있다.
  prompt 문구 목록으로 trigger하지 않는다.
- 모든 선택과 탈락 reason을 trace에 남긴다.
- active body/current-state route와 support-only character-profile route를 분리하고,
  structured topic/entity/event cue에서 recall need를 도출한다.
- recent accepted realization, already-realized outcomes, thread 전체 eligible set과 selected/
  deferred memory delivery state, lifecycle·outstanding consequence와 동일 root evidence cluster를 retrieval
  결과에 표시한다.

게이트: 기억 종류·언어·거리·branch·관점별 fixture에서 expected source와 scope로부터
도출한 must-recall/must-not-recall 결과를 만족해야 한다. provenance 누락, secret/
wrong-knower/wrong-branch/stale 주입, 무관 입력 false injection, logical duplicate와
lifecycle resurrection은 허용하지 않는다. 종류별 결과와 macro 결과를 모두 보고하며,
임의의 단일 고정 종합 점수나 현재 구현 snapshot으로 완료를 판정하지 않는다.
이미 실현된 outcome이 새 unrealized consequence로 전달되거나 recap·다른 POV 반응이 새 objective
event로 admission되면 실패한다.
selected 하나만 반환하는 mutation, unresolved sibling·ancestor 누락, bounded result를 전체
coverage로 오인하거나 local resolution을 상위 closure로 확대하는 경로도 실패해야 한다.

### 단계 6. Go 최종 주입 계획과 item별 delivery governance

- Go가 최종 block, 순서, 압축, 예산과 text/hash를 소유한다.
- 같은 bounded item에서 교체된 JavaScript 계산을 제거한다.
- block 또는 secret guard 중간 절단을 금지한다.
- item별 full/compact/suppressed/deferred 상태, reason, native-overlap observation, integrity
  override와 coverage gap을 Go plan에 포함한다.
- item별 current constraint, direct support evidence, already-realized reference,
  unresolved-state reference, historical reference와 no-new-realization record를 포함하고 같은
  root evidence를 목적별로 coalesce한다.
- thread별 eligible/selected/deferred memory delivery state, outstanding consequence와
  resolution scope/carry state를 plan에 포함하고 전달 선택이 canonical lifecycle을 바꾸지
  않게 한다. 이 상태를 서사 attention·진행·유예·종결 명령으로 변환하지 않는다.
- native capability가 unknown이거나 backend가 실패해도 JavaScript가 body/profile selection,
  suppression, budget 또는 prompt assembly를 대신 계산하지 않는다.
- 동일 source, eligible candidate, authority와 총 문자/token 예산에서 기존 delivery,
  selective delivery와 native-overlap-aware delivery를 비교하는 same-token replay를 실행한다.

게이트: 모든 profile과 동적 예산 fixture에서 초과가 없어야 하고, 계획 hash와 실제
RisuAI payload 적용 결과를 대조할 수 있어야 한다. wrong-knower secret/body state,
direct correction, current body constraint와 unresolved obligation의 false suppression이
하나라도 있거나 억제된 row·reason이 trace에서 사라지면 실패한다. same-token 비교에서
must-recall/must-not-recall, false suppression, duplicate retention과 coverage omission을
각각 보고하지 않으면 Step 27 delivery adoption을 verified로 표시할 수 없다.
recent raw output과 그 summary/profile digest가 같은 목적의 서술형 block으로 중복 전달되어
복기 고리를 만들거나, no-new-realization 기록이 다음 턴의 정체 또는 새 사건을 강제하면 실패한다.
관련 thread가 누락 reason 없이 사라지거나 selected thread의 resolution이 sibling·ancestor·session
종료 지시로 전달돼도 실패한다.

### 단계 7. 생명주기와 실환경 검증

- 실제 MariaDB·Chroma에서 reindex, provider 장애, vector rebuild와 장기 세션을 검증한다.
- 삭제·롤백·복사·이동은 기존 계약을 우선 검증하고, 수정이 필요하면 별도 승인된
  bounded item으로 분리한다.
- 별도 bounded item은 실행 순서만 분리한다. 삭제·롤백·복사·이동·재색인 parity는 4.1
  필수 완료 범위이며 사용자가 문서 범위를 변경하지 않는 한 후속 버전으로 미룰 수 없다.
- MariaDB 삭제, current-state 복구, audit와 vector delete/rebuild 각 경계에 fault injection을
  의무화한다. 반쪽 상태가 확인되면 revision/transaction barrier와 멱등 재개 가능한
  vector outbox 같은 원자성 계약을 별도 설계한다.
- 정상 turn admission도 `chat/effective input -> evidence -> atomic memory -> current
  projection -> audit/outbox -> Chroma upsert` 각 경계에 fault injection을 실행한다. 각
  실패점에서 restart와 동일 complete-turn replay를 수행하고, 이전 revision 유지 또는
  멱등한 완전 재개 중 하나만 외부에 보여야 한다.
- shadow 전환이 필요하면 backend version gate, owner와 제거 조건을 명시한다.

게이트: Chroma 장애가 MariaDB truth를 훼손하지 않고 degraded 상태를 표시하며, 무효화된
기억이 검색·주입·재색인·restart로 복귀하지 않아야 한다. fault injection 어느 지점에서도
외부에서 반쪽 canonical state를 관측할 수 없어야 하며 재호출과 crash recovery가
idempotent해야 한다. 원문만 있고 파생 상태가 영구 누락되거나, current projection만
갱신되고 evidence/audit/vector가 빠진 반쪽 turn도 허용하지 않는다.

## 12. 완료 판정

4.1은 다음 조건을 모두 실제 production 경로에서 증명한 뒤 완료로 판정한다.

- 정상 저장된 원문과 effective input이 turn/message/hash로 추적된다.
- 주입되는 모든 파생 기억에 검증 가능한 source pointer가 있다.
- 모델 paraphrase를 exact quote로 표시하지 않는다.
- secret, wrong-knower, wrong-branch, tombstoned, superseded 기억이 주입되지 않는다.
- story time이 unknown이면 임의로 advance하거나 exact date를 만들지 않는다.
- 동일 evidence 재처리가 중복 기억이나 습관 강화를 만들지 않는다.
- 사용자 정정, 반례와 이전 상태가 lineage로 보존된다.
- 여성 인물의 주기·임신·출산·산후를 포함한 신체 상태가 source·story time·authority·
  knower·visibility·recovery/clear lineage로 추적되고 관련 장면에서 회수된다.
- 실제 user/OOC profile과 RP character profile이 storage, candidate, vector와 delivery에서
  섞이지 않는다.
- RP character의 stable baseline, current snapshot과 dynamic digest가 동일 source evidence,
  counterevidence와 projection revision에서 재구축되고, 세 surface의 내용·lineage parity를
  대조할 수 있다. generated profile prose는 rebuild source나 truth floor가 아니다.
- 방향·domain별 관계 current/history와 transition이 source·counterevidence·story time·
  consent scope·rupture/recovery lineage로 재구축되고 user/player 입력이나 interaction
  발생만으로 reciprocity·애정·친밀감·복종·영속성이 자동 생성되지 않는다.
- final displayed output의 realized event/outcome, mention/recollection, input delta와 thread
  transition이 같은 root evidence로 추적되고 이미 실현된 사건·summary가 새 사건이나
  독립 evidence로 증폭되지 않는다.
- 모든 unresolved thread가 동일 lifecycle 유지, source-linked resolve 또는 successor transform
  중 하나로 보존되고 attention 제외·예산 유예가 lifecycle transition을 만들지 않는다.
- local resolution이 sibling·parent·episode/chapter/arc/saga/session으로 전파되지 않으며,
  직접 authority가 여러 target을 지지하는 경우에만 scope별 closure가 허용된다.
- final output의 occurrence evidence와 사전 causal/agency/resolution authority가 분리되어
  supervisor-origin 사건·종결이 표시됐다는 이유만으로 canonical truth가 되지 않는다.
- agent/model/visual 결과가 backend evidence admission 없이 canonical memory를 쓰지 않는다.
- 명시적인 과거 회상 fixture가 기대 원문 근거를 찾는다.
- 무관하거나 의미 없는 입력에는 기억을 억지로 채우지 않는다.
- 관련 기억이 없는 상태와 추출·provider·Chroma 장애가 구분된다.
- 최종 injection이 메인 예산과 item/block 경계를 지킨다.
- item별 delivery 상태·reason·coverage gap이 backend plan과 실제 payload에서 대조된다.
- 동일 예산의 기존/selective/native-overlap-aware delivery replay가 must-recall,
  must-not-recall, false suppression, duplicate와 omission을 분리 보고하고 regression 없이
  통과한다.
- 명시적 source 사실이 과잉 보수 때문에 `unknown`·`needs_review`·진단-only에 정체되지 않고,
  불확실한 일부 unit과 확정 가능한 unit이 분리 admission된다.
- false admission뿐 아니라 false suppression·false omission·관계와 상태의 부당한 동결도
  requirement별 negative/mutation fixture에서 검출된다.
- `PM-INTENT-FIDELITY`를 포함한 모든 requirement가 원래 사용자 요구·production owner·실제
  payload evidence로 추적되며, 안전·비용·단계 구현이 범위 축소 근거로 사용되지 않는다.
- 원작 DB 비활성·빈 상태·장애가 메인 기억을 막거나 변경하지 않는다.
- edit·삭제·reroll·rollback·copy·move·branch와 재색인 뒤 lifecycle parity가 유지된다.
- 고정 작품명, 인물·세력 수, 고정 정책 점수와 prompt 문구 하드코딩이 없다.
- production 분기를 제거하거나 반전하면 실패하는 회귀 테스트가 있다.
- 실제 MariaDB·Chroma·RisuAI payload E2E와 장기 soak를 통과한다.
- 최종 보고에 JavaScript 추가·삭제 줄 수와 남은 adapter-side business logic을 기록한다.

문서, schema, fixture 또는 source 문자열 검사만 통과한 상태는 완료가 아니다. 실사용
품질은 live test 피드백으로 계속 평가하지만 live 피드백을 이유로 위 불변 조건을
완화하지 않는다.

### 12.1 증거 등급

| 등급 | 허용 표현 | 필요한 증거 |
| --- | --- | --- |
| 문서·schema·DTO·scaffold | `preparatory` | 계약과 미연결 production owner를 명시 |
| unit·fixture | `implemented_unverified` | production 함수/route 호출과 negative test |
| disposable MariaDB | `storage_verified` | 실제 migration·CRUD·idempotency·schema 증거 |
| 실제 Chroma endpoint | `retrieval_verified` | hydration, hard filter, eligible/vector ID 대조 |
| 실제 RisuAI hook/payload | `integration_verified` | host observation→plan hash→payload hash→display correlation |
| 합의한 장기 soak·lifecycle | `release_gate_verified` | restart·reroll·rollback·reindex·장애 주입 전후 fingerprint |

`release_gate_verified` 전에는 “4.1 완료”라고 표현하지 않는다. 실제 RisuAI 또는 필수
외부 환경을 사용할 수 없으면 증거를 합성 결과로 대체하지 않고 해당 단계는 `blocked`로
남긴다.

### 12.2 완료 증거로 인정하지 않는 방식

| 금지 방식 | 금지 이유 | 반드시 필요한 대체 증거 |
| --- | --- | --- |
| 테스트용 복제 구현 | production owner를 실행하지 않음 | production symbol 또는 실제 HTTP route 호출; guard 제거·반전 시 실패 |
| 항상 성공 stub/no-op | orchestration 우회 | 외부 경계 stub만 허용하고 호출을 기록하며 예상 밖 입력에서 실패 |
| source-string 검사 | 문자열 존재는 동작 증거가 아님 | 실제 입력, response, DB row, trace와 부작용 검증 |

| DTO·trace·shadow만 추가 | production 연결이 없는 preparatory slice | 실제 owner 연결, DB 부작용, negative test와 실환경 gate |

### 12.3 Completion evidence manifest

모든 phase 완료 보고는 다음을 제출한다.

- commit/build ID와 contract/policy version;
- MariaDB, ChromaDB, RisuAI와 provider의 version·실행 mode;
- migration ID·checksum·적용 전후 schema version;
- 실행한 정확한 명령, exit code와 passed/failed/skipped 수;
- 테스트가 호출한 production API 또는 symbol;
- 허용한 mock/stub 목록과 각 외부 경계;
- known-broken 동작에서 실패하는 negative/mutation evidence;
- DB before/after row fingerprint와 lifecycle revision;
- character body-state current/history·recovery/clear lineage fingerprint와 story-clock revision;
- user/OOC·RP character profile namespace, consent/lifecycle revision과 projection rebuild evidence;
- direction·domain별 relationship current/history, transition event, counterevidence,
  consent boundary와 rupture/recovery lineage fingerprint;
- turn realization의 final message/input delta/realized·mentioned outcome/root evidence/thread
  transition fingerprint;
- thread ID/revision, previous transition, source outcome, branch, outstanding consequence,
  predecessor/successor, closure scope/authority와 sibling·ancestor 불변 diff;
- eligible/selected/deferred attention→payload span→final output→thread transition E2E와
  thread-conservation fingerprint;
- MariaDB eligible ID와 Chroma ID의 누락·orphan 대조;
- candidate review decision, source packet hash와 실제 Go admission/commit ID correlation;
- item별 delivery state/reason/native observation provenance와 coverage gap 목록;
- backend injection plan hash와 실제 RisuAI payload/display hash 대조;
- 실제 RisuAI에 import·실행한 `.risup`/decoded/generated artifact의 content hash, active
  source commit과 재현 가능한 build command; 테스트한 source와 loaded artifact의
  hash/provenance가 다르면 integration evidence 무효;
- 장애 주입별 stable code, retryability와 저장·검색 부작용;
- requirement별 `open/blocked/implemented_unverified/verified` 상태;
- 원래 사용자 요구, 채택한 해석, 거부한 축소 해석과 의미가 달라지는 미확정 결정;
- false positive와 false negative, false suppression·omission을 함께 대조한 결과;
- 남은 policy hardcoding과 승인된 protocol constant;
- 사용한 외부 code·prompt·schema·asset가 있다면 exact origin/version/license/NOTICE manifest;
- source adoption ledger에서 `direct/structural/follow-up/history-only`로 분류한 항목과 실제
  구현 연결 상태;
- JavaScript 추가·삭제 줄 수와 남은 adapter-side business logic;
- 미검증·차단·후속 항목과 사용자가 승인한 범위 변경.

증거가 없거나 required test가 skip되면 `complete`가 아니라 `blocked` 또는
`implemented_unverified`다.

### 12.4 상태 위장 방지

다음 상태를 서로 대체할 수 없다.

- `no_new_memory`: 추출이 정상 완료됐지만 admission 대상이 없음;
- `deferred_no_provider`: provider가 없어 추출하지 않음;
- `extract_failed`: provider 호출 또는 출력 계약 실패;
- `candidate_review_failed`: extractor/critic/agent review가 실패해 admission을 완료하지 못함;
- `search_empty`: 검색은 정상 완료됐지만 eligible 후보가 없음;
- `search_failed`: 검색 실행 자체가 실패함;
- `vector_degraded`: MariaDB truth는 유지되지만 vector 기능을 사용할 수 없음;
- `truncated`: 자원 상한 때문에 eligible coverage 일부가 잘림;
- `potentially_truncated`: bounded query가 상한에 도달했고 exhaustion·coverage completeness를
  아직 증명하지 못함;
- `delivery_degraded`: capability·budget·backend 경계 때문에 선택 전달 계약 일부를 검증하지
  못했으며 누락 coverage와 원 payload 보존 상태를 함께 보고함;
- `blocked`: 필수 환경·결정·evidence가 없어 다음 gate에 진입할 수 없음.

전체 서비스 `/ready`가 정상이어도 개별 memory operation의 failed/degraded/truncated
상태는 그대로 노출한다.

### 12.5 Change control

- requirement를 완화·제외하려면 3.1의 change request와 사용자 명시적 승인이 필요하다.
- 새 bounded slice가 승인돼도 원래 미완료 requirement는 open 항목으로 유지한다.
- support profile, provider, 언어, branch 또는 lifecycle 종류를 줄여 테스트하려면 축소된
  검증 범위를 먼저 공개하며 전체 완료로 보고하지 않는다.
- legacy 동작이나 기존 green test는 새 4.1 불변 조건을 약화하는 근거가 아니다.
- 안전·보수성·불확실성은 unsupported claim의 authority를 제한하는 규칙이지, source가
  지지하는 기능·기억 종류·관계 변화·회상 경로를 제거하는 change request가 아니다.
- `unknown`, `needs_review`, `degraded` 비율이 높다는 이유만으로 안전하다고 평가하지 않는다.
  known positive가 실제 admission·recall·payload에 도달하지 못하면 미완료다.
- 사용자가 승인하지 않은 “MVP 완료”, “사실상 완료”, “핵심 완료” 표현으로 범위를
  축소하지 않는다.
- 구현 중 새 schema가 필요하다는 사실은 범위 제외 사유가 아니다. 필요한 migration을
  4.1 requirement로 유지한다.
- 남은 결정을 무기한 대기로 둘 수 없다. 각 결정에는 owner, 결정 단계, 합격 evidence와
  다음 단계 차단 조건을 둔다.

## 13. 후속 서사 지원과 4.1 외 독립 트랙

4.1 정밀 기억이 완료된 뒤 캐릭터 해석, 말투 유지, 대형 시뮬레이션 감독과 저성능
생성 모델 보조가 이 기억을 read-only로 소비할 수 있다.

후속 서사 지원은 다음을 할 수 없다.

- support-only 해석을 canonical memory로 자동 승격;
- 기억 importance나 retrieval score를 임의 수정;
- 인물의 비밀 scope를 넓힘;
- 예시 대사를 그대로 강제 주입;
- 원작 사실을 세션에서 발생한 사건으로 변경;
- 메인 기억 예산을 우회.

4.1이 3.5 전처리와 4.6~5.0에 제공하는 read-only evidence export는 다음으로 제한한다.

- active `message_source_envelope.v1`과 stable entity/speaker IDs;
- story clock, body/current state, perspective/knowledge와 relation current/history;
- character profile의 evidence·counterevidence·relationship variant. 실행용 캐릭터 해석문은 아님;
- `turn_realization.v1`, `narrative_thread_lifecycle.v1`, atomic source와 raw recall pointer;
- contract/index revision, coverage, unknown/degraded와 visibility hard-filter 결과.

4.1은 이 export에서 활성 인물, 다음 사건, 장르 압력, guide strength, 모델 profile, scene
proposal이나 본문 재작성 여부를 선택하지 않는다. 소비자는 source ID와 revision을 유지하며
canonical row를 다시 쓰지 않는다. 3.5가 먼저 배포된 환경에서는 capability negotiation으로
없는 4.1 field를 unknown으로 두고, 4.1 배포 뒤 같은 계약을 확장해 읽는다.

`turn_realization.v1`과 thread export는 read-only projection이다. 4.6~5.0이 attention·표현·진행
후보를 계산하더라도 realized/mentioned/recollected, lifecycle, closure authority를 재분류하거나
write-back할 수 없다. 4.6~5.0이 OFF여도 4.1 recall은 unresolved thread와 의존성을 자체 delivery
정책으로 전달하며, 4.6~5.0 attention이 없다는 이유로 thread를 숨기거나 dormant/resolved로
바꾸지 않는다.

별도 서사 지원 예산이 필요하면 실제 요구와 context 비용을 재현한 뒤 새로운 versioned
계약으로 승인한다. 4.1 문서만으로 그 예산이나 멀티에이전트 호출을 자동 추가하지 않는다.

다음은 4.1 계약과 경계를 공유하지만 4.1 완료 조건은 아닌 독립 후속 트랙이다.

- Step 26의 inferred cross-session active user profiling, compiled user projection과
  opt-out/export/delete/retention UI;
- Step 28 QH의 입력 개선·출력 repair와 multi-model debate/fanout;
- QHM의 실제 multi-model orchestration, provider routing과 비용/latency profile;
- visual context sidecar, renderer/cache와 provider-specific image attachment.

4.1에는 QHM에서 가져온 proposal→challenge→backend admission 불변식만 포함한다. 다중
agent가 없어도 admission은 완전해야 하며 `qh_2/qh_4/qh_6/qh_8` 같은 이름을 호출 수나
품질 완료 등급으로 고정하지 않는다. visual은 text canonical과 text fallback을 대체하거나
memory/body-state의 source, Chroma index source, write evidence 또는 4.1 완료 증거가 될 수
없다.

## 14. 검토 합의와 남은 결정

독립 구조 검토, 데이터·검색 검토와 위험 검토의 공통 결론은 다음과 같다.

- 원작 DB가 아니라 메인 기억 구조를 정밀화한다.
- 신규 table보다 기존 schema와 production path 감사를 먼저 한다.
- 기억을 원자화하여 공개 사실과 비밀, 서로 다른 관점·시간을 섞지 않는다.
- MariaDB hard filter를 ranking과 Chroma보다 먼저 적용한다.
- 원문은 authority로 보존하고 파생 기억은 pointer와 짧은 excerpt를 사용한다.
- 습관과 성격은 support-only 증거 누적으로 관리한다.
- RP character profile은 stable baseline, current snapshot과 dynamic digest를 동일 evidence
  spine에서 파생하며 실제 user/OOC profile과 분리한다.
- 관계는 방향·domain·interaction·transition·counterevidence와 consent boundary를 분리하고
  사용자 입력이나 접촉을 상대 인물의 감정·상호성·영속성으로 자동 승격하지 않는다.
- final output의 realized outcome, mention/recollection, input delta와 thread transition을
  같은 root evidence에서 추적해 summary/profile 재주입이 사건 재연을 강화하지 않게 한다.
- 여성 인물의 주기·임신·출산·산후를 포함한 신체 상태는 4.1 필수 coverage이며 현재
  condition/effect 기반을 폐기하지 않고 body current/history·lineage·recall로 확장한다.
- extractor·critic·agent는 proposal/review만 만들고 Go admission owner만 canonical write를
  결정한다.
- 저장량과 주입량을 분리하고 Go가 최종 예산을 소유한다.
- Step 27의 item별 delivery 상태·reason·native overlap 관찰은 4.1 injection 계약에
  흡수하고 visual/QH의 실제 multi-model runtime은 후속 트랙으로 둔다.
- 원작 DB, 메인 기억과 후속 서사 지원의 오류·예산·쓰기 경계를 분리한다.

구현 전 결정은 owner·단계·evidence를 다음과 같이 고정한다.

| 결정 | owner | 결정 마감 | 합격 evidence |
| --- | --- | --- | --- |
| 기존 `memories`의 복수 atomic row 호환성 | Go store/admission | 단계 1 진입 전 | 실제 MariaDB write/read/idempotency와 migration 판단 |
| tombstone·supersession·archive filter 누락 경로 | Go store/recall planner | 단계 1·5 진입 전 | production route inventory와 guard 제거 negative test |
| story-clock authority와 branch/flashback 규칙 | Go narrative state | 단계 2 진입 전 | property/metamorphic test와 authoritative source mapping |
| `character_body_state.v1` normalized key와 JSON 경계 | Go store/narrative state | 단계 2 진입 전 | 기존 condition/effect 이행, current/history·lineage·expiry production CRUD |
| 주기·임신·출산·산후 authority와 visibility | Go admission/recall | 단계 2·3 진입 전 | fact/estimate/unknown, wrong-knower, time-skip와 rollback adversarial fixture |
| knower/POV hard filter | Go recall planner | 단계 3 진입 전 | adversarial secret test와 fail-closed trace |
| `character_profile.v1` materialization과 rebuild | Go store/profile projection | 단계 4 진입 전 | evidence/counterevidence/revision에서 동일 projection 재구축 |
| `relationship_state.v1` normalized key와 기존 relation/event 재사용 경계 | Go store/admission/profile projection | 단계 3·4 진입 전 | 방향·domain별 current/history/transition·counterevidence·consent·rollback parity |
| `narrative_thread_lifecycle.v1`의 atomic owner와 기존 `pending_threads`·`storylines`·hierarchy projection 경계 | Go store/admission/recall | 단계 1·5 진입 전 | thread conservation, closure locality, transform/reopen·branch rollback과 hierarchy carry E2E |
| `turn_realization.v1` projection과 기존 raw/event/thread 재사용 경계 | Go complete-turn/admission | 단계 1·5 진입 전 | final output/input delta/realized·mentioned outcome/root evidence/thread transition E2E |
| user/OOC와 RP character profile 경계 | Go admission/profile scope | 단계 4 진입 전 | opt-in, wrong-subject, session/branch와 delete/retire negative fixture |
| 긴 세션 전체 read와 필요한 index | Go store/query planner | 단계 5 진입 전 | 합의한 부하에서 query plan·latency·coverage 보고 |
| RisuAI native capability observation 범위 | JS host observation + Go delivery | 단계 6 진입 전 | observed/manual/unknown provenance와 false-suppression replay |
| candidate review profile과 provider budget | Go admission/orchestration | 단계 1 및 완료 전 | no-agent parity, unsourced/conflict rejection과 actual commit correlation |
| JavaScript 최종 budget 제거 response contract | Go prepare-turn | 단계 6 진입 전 | backend packet/hash 계약과 adapter 적용 test |
| lifecycle 원자성·복구 | Go store/lifecycle | 단계 7 및 완료 전 | fault injection, crash recovery와 vector parity |

마감 단계에서 결정·evidence가 없으면 이후 단계는 `blocked`다. 별도 bounded item은 실행
순서일 뿐 4.1 완료 범위 제외가 아니다.

이 문서는 4.1의 방향과 검증 순서를 확정하는 계획이다. 현재 3.1-3.2 원작 DB 작업,
메인 런타임, schema, JavaScript, Go code를 변경하지 않는다.

### 검토 도구와 하위 모델 사용 기록

2026-07-19~20 통합·재검토에서는 관리형 동일 계열 독립 agent에 runtime 경계, 데이터·검색,
버전 구조, hardcoding·source 세탁과 교차 문서 침범을 나눠 맡겼다. 요청한 `kimi_coder`,
`glm_subcoder`, `deepseek_validator` 전용 collaboration role은 현재 환경에서 모두 `agent type is
currently not available`로 거부되어 사용한 것처럼 표시하지 않았다.

대신 로컬 Ollama API에 실제 등록된 `kimi-k2.7-code:cloud`, `glm-5.2:cloud`,
`deepseek-v4-pro:cloud`를 사용했다. KiMi는 3.3~3.5의 단일 planner·Host persistence·직접 write와
JS debt를, GLM은 3.6~4.1의 source/entity/lifecycle·migration·recall·동시성을, DeepSeek는 세
문서 전체의 경계 우회와 실패 모드를 반대검증했다. 모델에는 관련 문서 packet만 read-only로
전달했고 workspace write 권한이나 production tool을 주지 않았다. 이 출력은 완료 증거가 아닌
review input이며, Codex가 활성 문서와 실제 runtime owner debt를 대조해 최종 요구·게이트로
통합했다.

2026-07-20 lorebook-assisted entity 추가 검토에서는 동일 계열 architecture/risk agent와
KiMi·GLM에 3.3~3.5 후보/근거와 3.6 stable identity admission 경계를 따로 검토시켰다. 고정
fingerprint threshold, 고정 entity taxonomy, content hash를 stable identity로 쓰는 제안은
hardcoding·collision·authority 위험 때문에 채택하지 않았다. 대신 source-linked
`host_context_reference_evidence.v1`, namespace 분리, setting/reference-defined identity의 실제 생성과
session occurrence 무권한 계약을 통합했다. 수정 뒤 DeepSeek의 10개 항목 반대검증은 모두
`RESOLVED`, 문서 계약 기준 `PASS`였다.

## 15. 보관 자료 통합·채택 ledger

이 문서는 아래 자료의 장기 기억 요구를 단일 4.1 계약으로 재구성한다. `직접 흡수`는
원문의 구현·prompt·schema를 복사한다는 뜻이 아니라 requirement와 불변 조건을 본 문서의
local vocabulary로 다시 정의했다는 뜻이다. 어떤 원본 파일도 삭제·이동하지 않는다.

`primary_class`는 `direct`, `structural`, `follow-up`, `history-only` 중 하나만 사용한다.

secondary disposition을 기록한다.

## 16. 연구 근거와 RP 관점 확인

이 로드맵은 특정 논문의 고정 score나 구현을 복사하지 않는다. 다음 primary research가
공통으로 지적한 장기 기억·RP 실패 범주를 Archive Center의 기존 계약과 대조하는 데만
사용했다.

- [LongMemEval](https://arxiv.org/abs/2410.10813): 정보 추출, multi-session reasoning,
  temporal reasoning, knowledge update와 근거 없을 때의 abstention을 별도 능력으로
  평가한다. 4.1의 admission·시간·정정·정직한 empty 계약에 반영한다.
- [LoCoMo](https://arxiv.org/abs/2402.17753): 장기 대화에서 persona와 temporal event
  graph, causal/temporal reasoning, source turn 연결의 중요성을 보여준다. 4.1의 사건
  graph·story clock·source pointer와 장기 RP fixture에 반영한다.
- [Generative Agents](https://arxiv.org/abs/2304.03442): 경험 기록, 상위 reflection과
  동적 retrieval을 분리한다. Archive Center에서는 raw/atomic memory를 상위 요약이
  대체하지 않는 원칙으로 사용한다.
- [MemoryBank](https://arxiv.org/abs/2305.10250): 지속적 기억 update와 과거 상호작용을
  이용한 사용자 이해를 다룬다. Archive Center는 raw truth를 삭제하는 인간형 망각을
  채택하지 않고 active recall priority와 historical preservation을 분리한다.
- [InCharacter](https://aclanthology.org/2024.acl-long.102/): character fidelity가 지식과
  언어 습관만이 아니라 성격, 관심, 동기, 정서와 대인관계를 포함함을 평가한다. 6장의
  평면적 성격 해석 방지와 관계·감정·목표 coverage에 반영한다.
- [Memory-Driven Role-Playing](https://aclanthology.org/2026.findings-acl.1175/): RP memory를
  anchoring, selecting, bounding과 enacting으로 나누어 본다. 4.1에서는 source anchoring,
  relevance selection, 관점·시간 bounding과 실제 payload 적용 검증으로 대응한다.

논문 수치나 등장인물 수는 production 정책·완료 점수로 사용하지 않는다. 로드맵의 합격
조건은 Archive Center requirement ledger, neutral fixture, production owner와 실제
MariaDB·Chroma·RisuAI evidence에서만 나온다.
