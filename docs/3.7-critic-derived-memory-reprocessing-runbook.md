# Archive Center 3.7 — Critic 파생 기억 오염 복구 절차

상태: `source procedure defined / destructive bulk cleanup not authorized`

이 절차는 Critic JSON 오류나 과거 parser 결함으로 잘못 생성된 기억·직접 근거·관계·상태를
원문을 보존한 채 다시 처리하기 위한 운영 순서다. 사용자 raw chat, effective input,
`.env`, MariaDB data directory 또는 Chroma persist directory를 패키지 파일로 덮어쓰거나
일괄 삭제하지 않는다.

## 1. 적용 조건

다음 증거가 같은 session·turn에 연결될 때만 실행한다.

- `critic_extract_failed`, `CRITIC_JSON_PARSE_FAILED`,
  `CRITIC_SCHEMA_INVALID` 또는 잘못 생성된 protected memory
- canonical raw user/assistant chat이 모두 남아 있음
- 현재 active `source_revision`을 식별할 수 있음
- 대상 turn과 잘못된 파생 row를 구체적으로 열거할 수 있음

단순히 AI 답변의 문체가 마음에 들지 않는다는 이유로 전체 세션을 재처리하지 않는다.

## 2. 실행 전 고정

1. Archive Center 쓰기와 background worker를 중지한다.
2. MariaDB와 ChromaDB를 동일 시점으로 백업한다.
3. session ID, logical turn, active source revision, raw user/assistant content hash,
   기존 Critic pipeline version을 기록한다.
4. Memory Explorer·감사 기록에서 대상 turn의 memory, direct evidence, KG,
   world rule/state, subjective/protected memory, vector 문서를 inventory한다.
5. raw chat과 effective input이 없거나 active revision을 확정하지 못하면 중단한다.

## 3. Dry run

1. `/admin/rescan`의 dry-run 또는 탐색 화면에서 대상 session과 turn만 선택한다.
2. 현재 active revision이 아닌 job, 이미 superseded된 turn과 user-only tail이 후보에
   포함되지 않는지 확인한다.
3. configured Critic provider, timeout, JSON response policy와 embedding/Chroma 상태를
   확인한다.
4. 예상 job 수, 대상 turn 수와 vector delete/upsert 예상량을 저장한다.
5. dry-run 결과가 session 전체나 알 수 없는 revision을 포함하면 실행하지 않는다.

## 4. 오염 항목 격리

기존 오염은 새 재스캔 결과에서 빠졌다는 이유만으로 항상 자동 삭제할 수 없다.
특히 protected subjective memory는 안전 정책상 추측으로 일괄 삭제하지 않는다.

1. Memory Explorer에서 원문과 모순되거나 evidence·owner·reveal policy가 없는 항목만
   개별 ID로 검토한다.
2. 지원되는 UI/API가 있는 memory·subjective memory는 exact ID 단위의 감사 가능한
   삭제를 사용한다.
3. 관계·state·rule 등 여러 lane에 퍼진 항목은 임의 SQL로 일부만 삭제하지 않는다.
   source replacement/invalidation으로 같은 revision의 파생물 전체를 stale 처리할 수
   있는지 먼저 확인한다.
4. exact source 범위로 안전하게 무효화할 수 없는 secondary row가 남으면 자동 복구를
   완료로 표시하지 않고 `operator_review_required`로 보류한다.

## 5. 재처리 실행

1. UI의 `failedQueueMaxAttempts`가 backend runtime config에 동기화됐는지 먼저
   확인한다. 이 값이 없거나 유효하지 않으면 worker는 숨겨진 기본값을 사용하지 않고
   `CRITIC_RETRY_LIMIT_UNCONFIGURED`로 terminal 처리한다.
2. 대상 active revision만 `critic_pipeline.v2` 재처리 대상으로 넣는다.
3. 동일 idempotency job이 이미 있으면 일반 rescan은
   `reprocessing_job_already_exists`로 건너뛰어야 한다. 이를 성공·완료로 세면 안 된다.
4. 기존 committed 파생 결과를 다시 만들기로 검토·승인한 turn에만
   `force_derived_rebuild`를 명시한다. 응답의 `reopened`가 대상 수와 같고
   `memory_reprocessing_reopened` 감사 기록이 있는지 확인한다. 이 작업은 exact active
   source의 admission snapshot과 job만 다시 열며 raw user/assistant와 기존 secondary
   row는 삭제하지 않는다. active lease나 stale source는 재개하면 안 된다.
5. 실제 worker queue 이름이 `memory_reprocessing_jobs`인지 확인한다.
   `maintenance_audit_recorded`는 실행 큐가 아니다.
6. worker가 같은 source revision의 canonical raw user/assistant를 읽는지 확인한다.
7. Critic 결과가 schema 검사를 통과하고 protected 후보 quarantine trace를 남기는지
   확인한다.
8. reroll·delete가 발생하면 해당 job은 `CRITIC_RESULT_SUPERSEDED`,
   `stale_rejected`로 끝나야 하며 결과를 저장해서는 안 된다.
9. retryable 오류는 UI에서 지정한 최대 횟수 미만에서만 재예약되어야 한다.
   한도 도달 후에는 `CRITIC_RETRY_LIMIT_REACHED`로 끝나야 한다.
10. common admission과 revision-fenced secondary writer가 완료된 뒤에만 job을
   completed로 본다.

## 6. Vector 복구

1. inactive/superseded source의 vector delete outbox를 먼저 처리한다.
2. 새 active 파생 memory, direct evidence와 world rule의 embedding upsert를 처리한다.
3. Chroma readback에서 session, source table, source row ID와 source revision이 새
   canonical row와 일치하는지 확인한다.
4. `vector_not_configured` 상태에서는 파생 row 복구와 vector 복구를 같은 성공으로
   표시하지 않는다. Chroma를 연결한 뒤 reindex를 별도로 완료한다.

## 7. 완료 판정

다음 항목을 모두 확인한다.

- raw user/assistant chat과 effective input 보존
- active source revision 하나만 존재
- Critic failure가 있으면 code, stage, retryable, HTTP status와 bounded raw preview 확인
- worker failure 감사에 job ID, source revision, turn, attempt가 함께 기록됨
- malformed protected 후보가 저장·주입되지 않고 quarantine됨
- duplicate job은 성공으로 집계되지 않으며 force rebuild는 `reopened`로 별도 확인됨
- stale job과 늦게 도착한 결과가 terminal discard됨
- maintenance audit count와 실제 worker queue depth가 분리됨
- 대상 turn의 memory/evidence/KG/rule/state 수와 근거가 원문에 맞음
- vector delete/upsert와 readback 완료
- 같은 절차를 다시 실행해도 중복 row가 생기지 않음

하나라도 충족하지 못하면 `partial_recovery` 또는 `operator_review_required`로 남기고
서비스 재개 전에 원본 백업을 유지한다.

## 8. 금지 사항

- raw chat이나 전체 session을 먼저 삭제
- MariaDB data directory, Chroma persist directory 또는 사용자 `.env`를 새 패키지로 덮기
- backup 없이 직접 SQL bulk delete
- old source revision의 completed job을 active로 되돌리기
- `maintenance_audit_recorded`를 실제 재처리 완료로 해석
- `raw:ok`만 보고 derived/vector까지 복구됐다고 판정
