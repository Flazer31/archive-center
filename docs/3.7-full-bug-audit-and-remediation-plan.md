# Archive Center 3.7 — 3.5–3.6 전체 버그 감사 및 해결 계획

상태: **3.7-A/C/F source 완료 / 3.7-B/D/E 부분 완료 / pre-G source closure와 패키지 계보 정리 필요 / loaded-artifact·RisuAI 검증 전**

작성일: 2026-07-30 KST

감사 기준 커밋: `d167f82` (`fix: enable Windows 3.6 managed vector runtime`)

감사 대상 빌드 표기: `3.6.0-dev / 3.6-precision-memory.20260729-3`

대상 소스: `Archive Center.js`, `go-service`, Windows 관리형 패키지와 업데이트 경로

구현 목표 버전: **3.7**

배포 판정: **아래 차단 조건이 닫히기 전까지 3.7 실 배포 금지**

현재 판정:

- 3.7-A/C/F의 production source와 자동 회귀는 현재 HEAD `94c1c20`까지 연결됐다.
- 3.7-B의 host finality, pending/failed 분리, typed retry·replacement 주 경로는
  구현됐지만, failed `complete_turn` dedupe key가 아직 type/session/turn만 사용한다.
  같은 turn의 다른 idempotency/generation 실패를 구분하지 못할 수 있고 queue
  overflow도 오래된 항목을 명시적 terminal/admission 상태 없이 제거한다.
- 3.7-D는 전체 session manifest와 무삭제 차단을 구현했지만, 50개 manifest 항목 중
  executor가 구현된 것은 8개다. 전체 executor와 parity 계산기는 완성되지 않았으며
  현재 session migration은 부분 실행되지 않고 target mutation 전에 fail-closed한다.
- 3.7-E의 새 workflow·queue card는 typed Go fact를 사용하지만 기존 dashboard의
  legacy runtime-state card는 아직 detail 문자열 regex와 status 정규화를 사용한다.
- 플러그인과 Go 기본 버전은 `3.7.0-dev`지만 Windows/POSIX package builder와 env
  예시의 기본 표기는 아직 `3.6.0-dev`다. 3.7-G artifact를 만들기 전에 동기화한다.
- package file hash는 생성되지만 source commit → build command → package manifest →
  loaded artifact hash 연결은 아직 없다. 3.7-G의 첫 진입 작업으로 닫는다.
- 실제 RisuAI, 신규·기존 Windows 설치, packaged MariaDB/Chroma, 실제 provider와
  updater health commit/rollback은 아직 검증하지 않았다.

버전 이동 원칙:

- 이미 구현된 3.6-A~F와 3.6 소스 이력은 3.6으로 유지한다.
- 이 문서의 전체 안정화 작업을 새 3.7로 삽입한다.
- 기존 미래 계획은 `3.7→3.8`, `3.8→3.9`, `3.9→4.0`,
  `4.0→4.1`로 한 단계 이동한다.

이 문서는 여러 사용자가 보고한 다음 현상을 하나도 누락하지 않고 다시 분류하기
위해 작성했다.

- `waiting for RisuAI active chat confirmation`이 끝나지 않는 현상
- DeepSeek에서 멈추고 GLM에서는 정상인 현상
- 700ms, 800ms, 8초, 90초, 12초 등 UI와 무관한 고정 시간
- 실패 큐가 30분 이상 남고 시도 횟수가 수십·수백 회가 되는 현상
- `LOGICAL_TURN_REPLACE_FAILED`
- `complete-turn verify_unavailable`, `raw_chat_log_verify_unavailable`
- `CRITIC_LLM_FAILED`, `critic_extract_failed`, JSON 생성·해석 실패
- 평론가가 만든 기억이 주입되지 않거나 보호 기억이 과도하게 생기는 현상
- `maintenance_enqueued`, `drift_detected`, `repair_replay`,
  `session_normalize`, `admin_reindex` 로그가 실제 무엇을 뜻하는지 불명확한 문제
- 새 세션에서도 반복되는 `vector_not_configured`
- Windows ChromaDB 설치·기동·연결 불일치
- MariaDB 기존 설치·업데이트 환경의 권한 문제
- 3.0에서 3.5로 올라갈 때 updater가 `status`를 반환하지 않는 현상
- Memory Explorer의 턴 수와 현재 RisuAI 턴 수가 다른 현상
- 세션 이관, 캐릭터 인덱스 변경, pin, 수동 attach의 불안정성
- 서사 가이드가 예산 부족으로 계속 빠지는 현상
- 입력 조립 투명성에 실제 전달값이 아닌 후보값이 표시되는 현상
- OOC, 삭제, 리롤, 중복 감지 HUD의 상태와 닫기 규칙
- prefill이 실제 사용자 입력으로 오인된다는 제보와 반복 서사 제보

## 1. 판정 원칙

이 문서의 상태 표기는 다음과 같다.

| 판정 | 의미 |

| 구현됨·실환경 미검증 | 수정 소스와 회귀 테스트는 있으나 실제 RisuAI, MariaDB, ChromaDB 또는 공급자 호출 증거가 없다. |

계속 유지한다.

## 2. 결론

보고된 현상은 하나의 원인도 아니고, 전부 서로 무관한 오류도 아니다. 크게 네 개의
원인군으로 묶인다.

1. **최종 출력 확정과 저장 상태 머신 결함**
   - `afterRequest` 이후 JavaScript가 시간을 재며 RisuAI 채팅을 반복 조회한다.
   - 후보 출력 확정, 저장, 재시도 큐가 서로 분리되지 않았다.
   - DeepSeek의 느리거나 변동이 긴 스트리밍은 이 결함을 더 쉽게 드러낼 뿐,
     모델 자체가 근본 원인은 아니다.

2. **파생 기억 LLM과 상태 표기 결함**
   - 공급자 오류, 빈 응답, JSON 부재, JSON 문법 오류가 모두
     `CRITIC_LLM_FAILED` 하나로 합쳐진다.
   - 저장은 성공했는데 선택적 read-back만 실패한 경우도 경고로 보인다.
   - 실제 worker가 없는데 audit 기록을 `maintenance_enqueued`라고 표시한다.

3. **세션·이관·Vector·업데이트 계약 결함**
   - 현 세션 이관은 전체 session-scoped 테이블을 복사하지 않으면서 원본 cleanup을
     허용한다. 이는 P0 데이터 손실 위험이다.
   - 세션 pin은 캐릭터/채팅 인덱스 기반이며 저장 실패가 상위로 전달되지 않는다.
   - Windows 관리형 ChromaDB는 현재 소스에서 보완됐지만 기존 3.5 사용자 및 실제
     업데이터 경로는 아직 실환경 검증되지 않았다.

4. **진단 UI의 사실성 결함**
   - 후보(pre-budget), 선택(selected), 실제 전달(delivered)이 섞여 보인다.
   - 같은 `경고` 색상에 정보성 상태와 실제 장애가 함께 나타난다.
   - 일부 updater UI 경로에는 현재도 정의되지 않은 `$` 호출이 남아 있다.

따라서 `timeout만 늘리기`, `DeepSeek만 예외 처리하기`, `실패 큐 횟수만 더 늘리기`,
`JSON repair를 더 공격적으로 만들기`는 해결책이 아니다.

### 4.2 올바른 목표 상태

1. native `afterRequest`는 `assistant_candidate_observed`를 backend에 보낸다.
2. JavaScript는 공식 RisuAI signal 또는 공식 DOM mutation으로만 다시 깨어난다.
3. 깨어난 시점에 active chat의 session/role/message index/content를 관측해 보낸다.
4. Go가 candidate를 `pending`, `accepted`, `replaced`, `deleted`, `superseded`로 전이한다.
5. 확인 전 candidate는 **실패 큐가 아니라 pending observation**이다.
6. 공급자 응답 속도는 finality 의미를 바꾸지 않는다.
7. PR #1442 계열 API가 공식 merge되면 version/capability detection으로 사용한다.
8. 지원되지 않는 RisuAI에서는 관측하지 못한 값을 추측하지 않고
   `not_exposed` 또는 `unobserved`로 보낸다.

### 4.3 3.7-A trace 좌표 기준선

같은 이름을 서로 다른 의미로 사용하지 않도록 현재 좌표를 다음과 같이 고정한다.

| 정식 이름 | producer → consumer | scope·durability | 3.7-A 판정 |
|---|---|---|---|
| orchestration request correlation ID | JS prepare 관측 → Go prepare/HUD lineage | 단일 main request, host 관측값; 공식 Risu request ID 아님 | complete에서는 source-to-final lineage가 만들어진 경우에만 보존된다. 조건부 상관은 3.7-B 차단 항목이다. |
| complete-turn idempotency key | JS final content/generation hash → Go complete idempotency ledger | complete 요청 재전송 단위, durable 처리 키 | orchestration correlation ID와 alias하면 안 된다. JS의 `client_meta.request_id`는 현재 이 값을 다시 담는다. |
| HTTP trace request ID | Go `trace.go` helper | 단일 HTTP 요청용 의도, 현재 production 호출 없음 | 연결된 trace로 간주하지 않고 `unwired` 기준선으로 남긴다. |
| chat session ID | RisuAI active chat 관측 → Go routing/prepare/complete/store | 대화 세션 단위, canonical store key | 요청 SID와 backend가 resolve한 canonical SID를 구분해 표시해야 한다. |
| resolved turn index | Go routing/complete canonical tail | 세션 안의 숫자 턴, 저장된 chat tail에 따라 재결정 가능 | durable `logical_turn_id`와 별개다. |
| logical turn ID | Go accepted user anchor hash → source acceptance/derived fence | 논리 사용자 턴 단위, durable | HUD의 숫자 `logical_turn`과 alias하면 안 된다. |
| host generation ID | RisuAI message 관측 → source acceptance | 선택적 host 관측값, nullable | 미노출이면 `unobserved`; 모델명·시간으로 추정하지 않는다. |
| HUD workflow attempt | Go in-memory workflow ledger | `(session, resolved turn)` 진행 표시, 재시작 시 비영속 | JS transport queue `attempts`와 alias하면 안 된다. |
| transport queue attempts | JS durable failed queue | backend 전송 재시도 횟수 | pending final confirmation에는 사용하지 않는 것이 3.7-C 목표다. |
| source revision | Go accepted session/turn/generation/message/content hash → store/derived fence | canonical source revision, durable | HUD long-poll `revision`과 alias하면 안 된다. |
| HUD ViewModel revision | Go in-memory workflow status revision | long-poll 변경 감지용, 비영속 | source revision이 아니다. |
| migration ID | MariaDB migration row → reindex/lock/rollback/cleanup | whole-session migration 단위, durable | turn/request/source revision을 억지로 결합하지 않는다. |

공식 RisuAI request ID는 현재 노출되지 않으므로
`official_risu_request_id_not_exposed` 상태를 유지한다. 3.7-A에서는 관측되지 않은

## 5. 최종 출력·실패 큐 상세

### 5.1 감사 기준선의 최대 시도 횟수 우회 경로 — 3.7-B 이전

아래는 `d167f82`에서 재현한 과거 경로다. 현재 3.7-B source는 pending
confirmation을 실패 큐에서 분리하고 모든 transport 재시도 경로에 유한 상한을
적용한다.

감사 기준선의 `drainFailedQueue`는 item의 `attempts`를 증가시킨 뒤
다음 경우 곧바로 `stillFailed`에 넣고 `continue`한다.

- queued complete-turn의 source observation을 갱신하지 못함
- request status가 `processing`
- request status가 `completed`이지만 `success != true`

최대 시도 횟수 검사는 이보다 아래에 있으므로 위 경로에는 도달하지 않는다.
따라서 `att=36`, `att=223`과 같은 장기 잔존이 가능하다.

### 5.2 실패 큐의 목표 분리

| 상태 | attempts 증가 | 자동 재시도 | HUD |
|---|---:|---:|---|
| `pending_confirmation` | 아니오 | host signal 때만 재평가 | 정보 |
| `backend_processing` | 아니오 | status event/long poll | 진행 |
| `retryable_transport_failure` | 예 | 사용자 retry 설정 이내 | 경고 |
| `retryable_critic_failure` | backend job 소유 | worker policy 이내 | 경고 |
| `terminal_source_rejection` | 아니오 | 없음 | 정보 또는 경고 |
| `terminal_contract_failure` | 아니오 | 없음 | 오류 |
| `completed` | 아니오 | 없음 | 성공 |
| `superseded_or_deleted` | 아니오 | 없음 | 알림 |

JavaScript 로컬 queue에는 backend-unreachable transport item만 남겨야 한다.
canonical turn, source acceptance, critic retry는 Go의 durable state로 이동해야 한다.

### 5.3 DeepSeek와 GLM 차이

DeepSeek의 긴 reasoning/streaming 또는 결과의 후반 변화는 8초 quiet와 stable poll을
자주 리셋할 수 있다. GLM의 결과가 더 빨리 안정되면 같은 잘못된 경로가 통과할 수
있다. 이 차이는 재현 조건이지 root cause가 아니다.

따라서 다음 구현은 금지한다.

- `if model contains deepseek`
- DeepSeek 전용 180초 timeout
- provider별 안정 poll 횟수
- 특정 output 문구를 최종성 신호로 사용

## 6. `LOGICAL_TURN_REPLACE_FAILED`

실패 위치는
[group_turn_complete.go](../go-service/internal/httpapi/group_turn_complete.go#L147)의
logical turn replacement다. 현재 HUD에는 모든 하위 오류가
`LOGICAL_TURN_REPLACE_FAILED`로 합쳐지고 HTTP 500 body에만 원래 오류가 붙는다.

[mariadb_logical_turn_replace.go](../go-service/internal/store/mariadb_logical_turn_replace.go#L12)는
다음만 허용한다.

- 요청 turn이 현재 canonical tail
- RisuAI가 기존 assistant를 지운 직후라 tail이 정확히 하나 비어 있는 경우

과거 turn 또는 gap은 거부한다. 그 외에도 다음 하위 오류가 가능하다.

- source revision mismatch
- MariaDB 권한 부족
- FK 또는 transaction 실패
- session routing mismatch
- 실제 canonical tail과 요청 turn 불일치

사용자 screenshot만으로 이 중 하나를 확정할 수 없다. 반드시 500 응답 body와
`request_id`, `sid`, `requested_turn`, `latest_tail`, source revision을 함께 받아야 한다.

목표 stable error:

- `LOGICAL_TURN_NOT_CURRENT_TAIL`
- `LOGICAL_TURN_REVISION_CONFLICT`
- `LOGICAL_TURN_SESSION_MISMATCH`
- `LOGICAL_TURN_DB_PERMISSION_DENIED`
- `LOGICAL_TURN_FK_CONFLICT`
- `LOGICAL_TURN_TRANSACTION_FAILED`

tail/revision/session mismatch는 반복 재시도로 해결되지 않으므로 terminal이다.
DB transport/temporary transaction만 제한적으로 retryable이어야 한다.

## 7. 저장 성공과 read-back 실패를 구분

다음 응답은 저장 실패가 아니다.

```text
raw:ok
derived:ok
complete-turn verify_unavailable
raw_chat_log_verify_unavailable
```

[Archive Center.js](../Archive%20Center.js#L6199)는 canonical read-back timeout을
사용자 설정과 무관하게 최대 2500ms로 자른다. 원격 Tailscale, 모바일, 느린 DB에서는
쓰기 성공 후 이 선택적 검증만 실패할 수 있다.

목표 표기:

- `raw:ok` → Raw Save 성공
- `derived:ok` → Derived Save 성공
- `verify_unavailable` → `정보: 저장 응답은 성공, 선택적 read-back 미확인`
- read-back에서 실제 불일치 → `경고: write/read mismatch`

complete-turn 응답을 write authority로 유지하고 read-back 실패 때문에 이미 성공한
턴을 실패 큐에 다시 넣지 않는다.

## 8. 평론가 LLM과 JSON

### 8.1 현재 3.6에서 이미 달라진 부분

[turn_extraction_critic.go](../go-service/internal/httpapi/turn_extraction_critic.go#L701)는
현재 raw JSON candidate를 먼저 파싱하고, 실패한 경우에만 제한된 repair를 적용한다.
과거처럼 먼저 전체 텍스트의 따옴표를 무조건 바꾸는 경로는 아니다.

[proxy_provider.go](../go-service/internal/httpapi/proxy_provider.go#L329)는
critic/extraction JSON 요청에만 Gemini/Vertex
`generationConfig.responseMimeType=application/json`을 요구한다. 일반 서사 호출에는
이 정책을 강제하지 않는 회귀 테스트가 있다.

이 변경은 이전 3.5의 `invalid character ... after array element`,
`critic_json_missing` 문제에 직접 대응한다.

### 8.2 아직 남은 결함

[group_turn_complete.go](../go-service/internal/httpapi/group_turn_complete.go#L537)는
다음을 모두 `CRITIC_LLM_FAILED`로 표시한다.

- upstream HTTP/auth/quota 오류
- timeout
- content 추출 결과 없음
- JSON object 없음
- brace/bracket mismatch
- JSON parse 실패
- normalized schema 불일치

parser 실패 시 `trace.raw_preview`는 이미 보존된다. 이 trace를 사용하지 않고
모델이 잘못했다고 결론 내리면 안 된다.

목표 error 분류:

| 단계 | stable code | retryable |
|---|---|---:|
| 공급자 HTTP/auth/quota | `CRITIC_UPSTREAM_FAILED` | 상태별 |
| 요청 timeout | `CRITIC_TIMEOUT` | 예 |
| content 없음 | `CRITIC_EMPTY_CONTENT` | 제한적으로 예 |
| JSON object 없음 | `CRITIC_JSON_MISSING` | 예 |
| JSON syntax | `CRITIC_JSON_PARSE_FAILED` | 예 |
| schema 검증 | `CRITIC_SCHEMA_INVALID` | 입력에 따라 |
| stale revision | `CRITIC_RESULT_SUPERSEDED` | 아니오 |

### 8.3 OpenAI 형식에서는 되고 Vertex 형식에서는 안 된 경우

이는 같은 모델이라도 다음 adapter 차이로 생길 수 있다.

- response candidate/content 추출 위치
- tool/structured response shape
- streaming chunk 합성
- JSON MIME 및 기존 `extra_body_json` 충돌
- finish reason과 빈 content 처리

필수 fixture는 “정상 JSON”, “markdown fence JSON”, “빈 content”, “truncated JSON”,
“provider error body”, “streamed candidate”의 공급자별 raw response다.

### 8.4 재처리 안전성

raw user/assistant chat을 먼저 canonical하게 저장한다. critic 실패는 raw를 되돌리지
않고 derived retry job을 만든다. retry 결과가 도착했을 때 source revision이 바뀌었으면
저장하지 않고 superseded 처리한다.

## 9. 보호 기억과 기억 오염

[prepare_turn_memory.go](../go-service/internal/httpapi/prepare_turn_memory.go#L205)는
`protected_secrets`와 `character_identity_accuracy`만 보호 guard 입력으로 읽는다.
[turn_extraction_critic.go](../go-service/internal/httpapi/turn_extraction_critic.go#L1081)의
`belief_updates`는 별도 필드다. 따라서 `belief_updates`가 직접 guard를 만들었다는
인과관계는 현재 소스에서 확인되지 않는다.

다만
[protectedSecretRequiresGuard](../go-service/internal/httpapi/prepare_turn_memory.go#L766)는
policy가 비어 있으면 fail-closed로 guard를 활성화한다. 안전 원칙 자체는 맞지만,
LLM이 owner/policy/evidence가 없는 protected item을 많이 만들면 guard가 과도해질 수
있다.

해결 방향은 보호를 끄는 것이 아니다.

1. owner, subject, policy, evidence가 부족한 protected item은
   `protected_policy_missing` quarantine으로 보낸다.
2. quarantine item은 public memory에도 private guard에도 주입하지 않는다.
3. 같은 secret identity + owner의 guard는 한 번만 렌더링한다.
4. guard lane에 독립 예산과 최대 item 수를 둔다.
5. trace에 source field, policy, defaulted 여부, evidence를 남긴다.

필수 인과 회귀:

- `belief_updates`만 존재 → guard 0
- 같은 fixture에 valid `protected_secrets` 추가 → guard 1
- policy/owner/evidence 누락 protected item → quarantine 1, guard 0

### 9.1 이미 오염된 파생 기억 복구

1. raw chat과 effective input을 authority로 고정
2. 해당 source revision에서 생성된 derived row를 stale 처리
3. 현재 parser/schema로 재추출
4. malformed protected item quarantine
5. memory/evidence/KG/rule/status를 새 revision으로 rebuild
6. vector outbox 재생
7. 이전 derived/vector를 supersede

원본 raw chat을 삭제하거나 사용자 DB를 새 패키지에 포함해서 해결하면 안 된다.

## 10. maintenance와 audit 로그 해석

[group_turn_complete.go](../go-service/internal/httpapi/group_turn_complete.go#L1606)는
명시적으로 `worker_enabled=false`, `queue_mode=audit_shadow`라고 기록하면서도
`QueueDepth=1`, `Enqueued=true`, `maintenance_enqueued` audit event를 만든다.
실제로 실행 가능한 worker queue에 넣은 것이 아니다.

목표 응답:

```json
{
  "maintenance_enqueued": false,
  "maintenance_audit_recorded": true,
  "maintenance_queue_depth": 0,
  "maintenance_queue_mode": "audit_only"
}
```

사용자에게 제공된 로그는 다음처럼 읽어야 한다.

| 로그 | 의미 |
|---|---|
| `source_acceptance active final turn N` | turn N 출력이 active final source로 받아들여짐 |
| `source_acceptance replacement complete turn N` | 같은 logical turn의 새 출력으로 교체 완료 |
| `effective_input_saved` | 실제 입력 조립 결과 저장 |
| `critic_ingest_trace` | critic 결과 처리 trace 저장 |
| `critic_extract_failed` | raw는 보존됐지만 derived 추출 실패 |
| `maintenance_enqueued` | 현 소스에서는 실제 worker queue가 아니라 audit shadow |
| `drift_detected ... shadow handoff` | 실제 수리 완료가 아니라 후속 점검 audit |
| `repair_replay restored 2 chat log roles` | user/assistant raw 역할 2개를 canonical log에 복구 |
| `session_normalize` | 세션 정규화 관리 작업 |
| `admin_reindex` | vector 재색인 관리 작업 요청 |

같은 turn의 `critic_extract_failed`가 여러 번 보이면 첫 실행, queue retry, repair/reindex
재처리를 구분할 `attempt_id`와 `source_revision`이 필요하다.

### 12.4 즉시 조치

**전체 manifest migration이 완성되기 전까지
`/sessions/migrate-cleanup-source`의 실제 cleanup을 fail-closed한다.**
dry-run은 허용해도 confirm cleanup은 차단한다.

#### 2026-07-29 3.7-A 적용 기록

- cleanup 응답 계약을 `sc-mig-cleanup.v2`로 올렸다.
- dry-run은 source/target ID, migration ID, row/vector count를 읽기 전용으로
  반환하되 `session_cleanup_manifest_verification_required` blocker와
  `ready_for_cleanup=false`를 반드시 반환한다.
- confirm 요청도 같은 blocker로 끝나며 MariaDB cleanup과 Chroma
  `DeleteSession`을 호출하지 않는다.
- HTTP handler를 우회해 store cleanup을 직접 호출해도
  `ErrSessionMigrationCleanupManifestUnverified`로 실패한다.
- 기존 부분 삭제 helper는 제거했다. 전체 manifest가 완성되기 전까지 별도
  compatibility cleanup 경로를 두지 않는다.

자동 회귀에서는 dry-run/confirm/store 직접 호출의 무삭제와 기존 Go package 회귀를
확인했다. 이는 실제 MariaDB/ChromaDB가 연결된 live migration 증거는 아니다.
46개 전체 manifest, count/hash/FK/vector parity와 durable saga는 후속 migration
packet의 배포 차단 조건으로 남는다.

전체 구현은 모든 session table을 다음 중 정확히 하나로 분류해야 한다.

- `copy`
- `retain_audit`
- `regenerate`
- `delete_after_verified`

source count/hash, target count/hash, row map, FK remap, vector expected ID parity가 모두
맞아야 `copy_verified → vector_verified → source_locked`로 진행한다.
MariaDB와 Chroma 외부 작업은 durable saga로 복구 가능해야 한다.

- 일부 파일만 교체된 mixed package가 아닌지
- DB/schema update가 완료됐는지
- 이전 backend로 안전하게 rollback 가능한지

필수 updater fixture:

- 3.0.0 clean package
- 3.0.1 package
- 3.5.0 package
- status가 없는 legacy stdout
- pending state 없음
- apply 도중 중단
- backend health 실패
- 신규 Chroma runtime 필요
- 기존 MariaDB schema additive upgrade

업데이트는 코드 전체 교체와 additive DB schema, managed dependency 설치를 지원해야

## 20. 3.7 해결 순서

### 3.7-A — 기준선과 위험 차단

1. 현재 request/session/turn/generation/revision/migration 좌표의 producer,
   consumer, durability와 nullable 여부를 고정한다.
2. 같은 `request_id`, `revision`, `attempt` 표기가 서로 다른 의미를 공유하는
   지점을 별도 이름과 scope로 기록한다.
3. 전체 manifest parity 없이 가능한 session source cleanup을 HTTP와 store 양쪽에서
   fail-closed한다.
4. 이후 packet이 증명해야 할 재현 fixture와 release-blocking gate를 고정한다.

3.7-A는 finality·queue·critic·전체 migration을 한 번에 고치는 단계가 아니다.
현재 확인된 비가역 손실 경로를 먼저 닫고, 다음 수정이 비교할 수 있는 기준선을
만드는 preparatory safety slice다.

### 3.7-B — 출력 확정과 큐 정상화

1. finality watcher의 고정 시간 정책과 synthetic `onAfterRequest` 재진입 제거
2. pending confirmation을 실패 큐에서 분리
3. 모든 queue 상태에 terminal/retryable 계약과 최대 횟수 적용
4. logical replacement 하위 오류 typed 분류
5. 저장 성공과 optional verification 실패 분리

#### 처리한 사용자 피드백

3.7-B는 다음 보고를 직접 대상으로 삼았다.

- DeepSeek에서는 `waiting for RisuAI active chat confirmation`과
  `bridgeFetch OK /turn-workflow/status`가 반복되고 GLM에서는 정상 완료되던 현상
- 감시 시작 700ms, 조회 800ms, 출력 변화 후 8초, 강제 종료 90초,
  late-native 12초처럼 UI 설정과 무관한 고정 시간이 finality를 결정하던 문제
- `synthetic_afterRequest`가 native hook과 같은 저장 경로에 다시 들어가 중복 후보와
  대기를 만들던 문제
- pending confirmation이 `complete_turn` 실패 큐로 섞여 시도 횟수가
  30회 이상 증가하고 cold start 뒤에도 `deferred`로 남던 문제
- 리롤에서 `LOGICAL_TURN_REPLACE_FAILED` 하나만 보여 권한·revision·deadlock·commit
  결과 불명을 구분하지 못하고 같은 raw를 다시 보낼 위험
- `raw:ok`, `derived:ok`인데 `verify_unavailable` 때문에 전체 저장 실패처럼 보이던 문제

이 단계는 평론가 JSON 내용 자체를 고치는 작업이 아니다. host의 최종 출력 확정,
raw complete-turn exactly-once, pending/failed queue와 저장 결과의 사실성을 교정한
것이다. Critic/provider·파생 기억 문제는 3.7-C가 소유한다.

#### 구현된 계약

- `beforeRequest`에서 현재 character index, chat index, host chat ID,
  message count와 orchestration request correlation을 관측한다.
- native `afterRequest`는 응답 후보만 전달한다. 저장을 재귀 호출하거나
  그 hook 자체를 RisuAI commit 신호로 간주하지 않는다.
- RisuAI host mutation은 조회를 깨우는 신호일 뿐이다. 최종 확정은 공식 chat
  read API에서 같은 character/chat/host chat 좌표, 예상 message count와
  정확한 assistant slot, `isStreaming=false`, 후보 본문 일치가 모두 확인된
  때에만 성립한다. 새 출력은 기존 tail 다음 slot, 같은 길이 reroll은 기존
  assistant slot의 본문 또는 generation 변화로 구분한다.
- 700ms 시작 지연, 800ms polling, 3/4회 안정 횟수, 8초 quiet window,
  90초 강제 종료, 12초 late-native grace와 synthetic `onAfterRequest` 재진입은
  finality 경로에서 제거했다. promoted assistant sync에 남아 있던 별도 8초
  rollback grace도 제거했으며, exact active-chat confirmation 자체를 근거로
  확정 상태를 기록한다.
- host 확인 대기는 실패 큐와 분리된 `pending final confirmation` lane에 둔다.
  실행 closure는 메모리에만 두되 credential-free complete-turn payload,
  required observation key와 idempotency key는 별도 pluginStorage에 먼저
  영속한다. transport/backend 실패 queue에 넣거나 retry attempt를 올리지
  않는다.
- pending 항목은 session이 아니라 host request 또는 complete-turn
  idempotency key로 식별한다. 같은 session의 겹친 request를 하나의 mutable
  전역값으로 합치지 않으며, 새 후보가 이전 request를 대체하면 이전 후보를
  `superseded`로 끝낸다.
- host read를 기다리는 동안 후보가 교체되었는지 continuation 직전에 다시
  확인한다. drain 중 들어온 mutation wake는 후속 drain으로 넘겨 lost wake를
  막고, 동일 observation 재시도는 새 observation이 확인되기 전에는 진행하지
  않는다. accepted context의 duplicate hook은 저장을 다시 시작하지 않는다.
- exact host final이 확인된 continuation은 request-local orchestration,
  effective-input, pending context snapshot과 in-flight fence로 한 번만 실행한다.
- plugin reload 때 별도 pending 저장소를 복원하고 동일 idempotency key가
  실패 큐에도 남아 있으면 pending lane을 우선하여 정확히 한 곳에 둔다.
  복원 payload는 RisuAI active final을 다시 관측한 뒤에만 재개하며, 저장소에는
  critic/embedding 비밀값을 넣지 않는다. 실제 POST 직전에는 현재 UI runtime
  provider 설정을 다시 붙이고 다음 영속화에서는 다시 제거한다.
- `persistentSet`은 pluginStorage 쓰기 실패를 성공으로 삼키지 않는다.
  failed queue 저장 성공이 확인되기 전에는 pending 원본을 삭제하지 않으며,
  pending 저장소는 UI에 보이는 queue capacity를 넘는 새 항목을 조용히
  축출하지 않고 admission 실패로 반환한다.
- failed queue는 실제 transport/backend retryable 실패만 센다. 최대 횟수는
  숨은 상수나 LLM 재시도 값이 아니라 UI에 노출된 `실패 큐 최대 시도 횟수`
  설정을 사용한다. `retryable`, `terminal`, `superseded`를 분리하고
  `terminal`·`superseded`는 재큐잉하지 않는다. backend의
  `status=error`도 `retryable=false` 또는 `queue_action=discard`이면 terminal로
  처리한다.
- complete-turn idempotency ledger는 server-side payload fingerprint를 함께
  보관한다. fingerprint는 raw/source뿐 아니라 context, improvement trace,
  output language, request type, client metadata까지 포함한 complete-turn
  semantic payload 전체를 대상으로 한다. 같은 key와 다른 payload 충돌은
  `idempotency_key_conflict`, `retryable=false`, `queue_action=discard`로 반환한다.
- `commit_state=unknown`과 request-context가 끊긴 처리 결과는 raw 재실행이
  안전하다고 증명될 때까지 terminal reconciliation 상태로 ledger에 고정한다.
  진행 중 owner 수는 bounded capacity로 제한하며, owner가 뒤늦게 실제 결과를
  반환하면 같은 entry의 provisional unknown 응답을 실제 응답으로 교체한다.
- source acceptance는 idempotent write closure 안에서 한 번만 실행한다.
  같은 accepted final의 중복 POST가 acceptance ledger와 raw save를 다시
  진행하지 않는다.
- logical replacement 오류는 `code`, `stage`, `retryable`,
  `commit_state`, `raw_committed`를 가진 typed error로 반환한다. revision/tail,
  권한, 중복, FK constraint, lock wait/deadlock, commit outcome unknown을
  구분한다. raw replacement commit 뒤의
  reference/narrative cleanup 실패는 `status=partial`, `save_ok=true`,
  `reconciliation_required=true`, `queue_action=discard`로 반환하여 raw를
  재전송하지 않는다.
- request-status도 `save_ok`, `raw_committed`, `commit_state`,
  `derived_retry_required`, `reconciliation_required`를 보존한다. polling
  경로가 partial success를 단순 `ok`로 축약하지 않는다.
- `raw saved + derived retry required`는 critic 실패뿐 아니라 일반
  derived/audit persistence 실패에서도 complete-turn 전체 실패가 아니다.
  응답은 `status=partial`, `save_ok=true`, `raw_committed=true`,
  `derived_retry_required=true`로 raw와 파생 상태를 분리한다. backend가 파생
  재처리·reconciliation을 소유하며 JavaScript failed queue에는 raw save
  재시도 항목을 남기지 않는다.
- `verify_unavailable`과 `raw_chat_log_verify_unavailable`은 optional read-back
  증거 부재다. `save_ok=true`를 실패나 경고 저장 상태로 뒤집지 않는다.

### 3.7-C — Critic과 파생 기억 복구

#### 처리한 사용자 피드백

3.7-C는 다음 현상에 대응한다.

- `CRITIC_LLM_FAILED` 하나만 보여 provider 호출 실패, timeout, 빈 응답,
  JSON 누락·문법 오류와 schema 오류를 구분할 수 없던 문제
- OpenAI 형식에서는 정상인데 Vertex/Gemini 형식에서는 실패하거나
  `invalid character ... after array element`, `critic_json_missing`이 반복되던 문제
- raw 원문은 저장됐지만 평론가 파생 기억이 생성되지 않고 실패 큐만 늘어나던 문제
- retryable Critic 작업이 15분 backoff에 도달한 뒤에도 최대 횟수 없이 영구 반복되어
  호출 비용과 실패 큐가 계속 누적될 수 있던 문제
- 평론가가 잘못 만든 비밀·NPC 주관 기억이 protected memory로 승격되어 이후 입력에
  과도한 guard를 붙일 수 있던 문제
- 리롤·삭제 뒤 이전 source revision의 늦은 평론가 결과가 identity, surface,
  speaker 또는 파생 기억으로 남을 수 있던 경합
- `maintenance_enqueued`, `queue_depth=1`, `drift_detected`가 실제 worker 작업처럼
  보이지만 실제로는 audit shadow였던 표시 문제

#### 구현된 계약

1. Critic 실패를 구조화했다.
   - `CRITIC_PROVIDER_TIMEOUT`
   - `CRITIC_PROVIDER_CANCELED`
   - `CRITIC_PROVIDER_CALL_FAILED`
   - `CRITIC_PROVIDER_HTTP_ERROR`
   - `CRITIC_EMPTY_RESPONSE`
   - `CRITIC_CONFIG_INVALID`
   - `CRITIC_REQUEST_BUILD_FAILED`
   - `CRITIC_JSON_MISSING`
   - `CRITIC_JSON_PARSE_FAILED`
   - `CRITIC_SCHEMA_INVALID`
   - configuration/input 오류도 각각 별도 코드로 유지한다.
   각 오류는 `stage`, `retryable`, 가능한 경우 `http_status`를 가진다.
2. 실제 upstream HTTP 오류와 호출 전 configuration/request-build 오류를 분리한다.
   Claude·Gemini·Vertex의 빈 2xx 응답도 가짜 502로 바꾸지 않고 실제 상태와
   `CRITIC_EMPTY_RESPONSE`를 보존한다.
3. provider·parse·schema 실패 trace에 provider, model, HTTP status와 길이가 제한된
   `raw_preview`를 보존한다. configured API key뿐 아니라 Authorization/Bearer,
   API key, password와 access/refresh token 값 전체를 제거한다. complete-turn 감사
   기록과 durable reprocessing worker가 같은 분류기를 사용하며, worker 감사에는
   job ID, source revision, turn, attempt도 함께 남긴다.
4. JSON object가 비어 있거나 알려진 extraction payload가 없거나 주요 필드 자료형이
   잘못되면 normalization 전에 schema 오류로 중단한다.
5. protected secret, protected/NPC subjective memory와 protected identity 후보는
   owner·본문·명시적 reveal policy·현재 source에 정확히 존재하는 evidence를 모두
   만족해야 한다. evidence가 원문에 존재하더라도 보호 기억의 주장과 핵심 anchor가
   연결되지 않으면 격리한다. 하나라도 없으면 저장·주입하지 않고 quarantine reason
   count만 trace에 남긴다. subjective memory 저장 직전에도 같은 fail-closed 검사를
   다시 한다.
6. durable critic job은 exact `source_revision`에 연결된다. 실행 중 reroll·삭제가
   확인되면 provider/save context를 취소하고 결과를
   `CRITIC_RESULT_SUPERSEDED`, `stale_rejected`, terminal로 끝낸다.
7. identity, identity surface, artifact binding과 speaker attribution의
   accepted-source MariaDB 쓰기는 active source row를 `FOR UPDATE`로 잠근 같은
   transaction 안에서 검사하고 저장한다. foreground 재확인만으로 남던 TOCTOU를
   store 경계에서 닫는다.
8. 실제 durable worker queue는 `memory_reprocessing_jobs` 하나로 표시한다.
   maintenance handoff는 `maintenance_audit_recorded=true`,
   `maintenance_enqueued=false`, `queue_depth=0`, `queue_mode=none`,
   `audit_mode=plan_only`로 기록한다.
9. durable Critic retry의 최대 횟수는 새 고정값을 만들지 않고 UI의 기존
   `failedQueueMaxAttempts`를 backend 설정으로 전달해 1~11 범위에서 사용한다.
   설정이 전달되지 않았거나 유효하지 않으면 `CRITIC_RETRY_LIMIT_UNCONFIGURED`,
   한도에 도달하면 `CRITIC_RETRY_LIMIT_REACHED`로 terminal 처리한다.
10. Critic pipeline을 `critic_pipeline.v2`로 올려 새 결과가 이전 파서 결과와 같은
   idempotency 세대로 오인되지 않게 했다.
11. rescan의 duplicate enqueue는 더 이상 성공으로 집계하지 않는다. 명시적
   `force_derived_rebuild`에서만 exact active source와 기존 job을 transaction으로
   잠그고 admission snapshot/job을 다시 연다. raw source와 기존 secondary row는
   보존하며, `reopened` 응답과 `memory_reprocessing_reopened` 감사를 남긴다.

기존 오염 데이터의 운영 절차는
[`3.7-critic-derived-memory-reprocessing-runbook.md`](3.7-critic-derived-memory-reprocessing-runbook.md)에
분리했다. raw chat과 effective input은 삭제하지 않으며, 재스캔만으로 이미 남아 있는
모든 잘못된 secondary row가 자동 제거된다고 주장하지 않는다.

### 3.7-D — 세션·DB·Vector·업데이터

#### 처리한 사용자 피드백

3.7-D는 다음 현상과 위험에 대응한다.

- 일부 session table만 복사한 뒤 원본 cleanup이 가능해 다른 세션의 기억·관계·상태가
  유실될 수 있던 문제
- character/chat index 이동, copy/fork, reload 뒤 서로 다른 채팅이 같은 SID로
  묶이거나 pin 저장 실패가 성공처럼 보일 수 있던 문제
- Windows에서 ChromaDB가 설치되었어도 endpoint와 실제 upsert/readback이 확인되지
  않아 매 턴 `vector_not_configured`가 반복되던 문제
- 기존 MariaDB 계정이 연결은 되지만 CRUD 또는 DDL 권한이 부족해 저장·migration
  단계에서 뒤늦게 실패하던 문제
- 3.0/3.5 updater가 `status` 없는 응답, 섞인 stdout/stderr, 불명확한 recovery
  runner 또는 변경된 migration을 만나 mixed package 방지로 기동을 중단하던 문제
- updater 파일명을 바꾸어 검사를 우회하면 기동은 되지만 pending transaction의
  주체와 data root가 검증되지 않던 운영상 우회

#### 구현된 계약

1. `session-migration.manifest.v1`은 `001_schema.sql`의 session-content table을
   전수 검사해 직접 table 46개와 간접 child 4개를 분류한다.
   `session_fork_lineage.copied_from_session_id`처럼 보조 SID column도 별도 의미를
   기록한다. migration ledger, lock, route binding은 content manifest에서 제외한
   metadata로 명시한다.
2. table별 copy/retain-audit/regenerate/delete-after-verified 정책과 구현 여부를
   기록한다. 현재 executor가 다루지 못하는 항목이 남아 있으므로
   `session_migration_manifest_parity_unverified`,
   `source_target_count_hash_unverified`, `row_map_fk_remap_unverified`,
   `vector_expected_id_parity_unverified`를 release blocker로 반환한다.
3. count/hash, row-map/FK와 vector expected-ID parity를 저장하는 ledger,
   recoverable saga step, durable route binding table을 fresh schema와 additive
   `007_session_migration_manifest_and_route_binding.sql`에 함께 추가했다.
   manifest executor와 parity가 완성되기 전에는 source lock과 cleanup을 계속
   fail-closed로 막고, reindex도 `vector_verified_manifest_blocked`에서 끝낸다.
4. 공식 host에서 관측한 stable `character.chaId`와 opaque `chat.id`의 조합을
   backend durable binding의 unique identity로 사용한다. 전체 ID 조합을 비교하며
   MariaDB serializable transaction 안에서 exact readback을 확인한 canonical SID만
   반환한다. locked source는 검증된 target으로 redirect한다.
5. JavaScript pin key와 record는 v3로 통일했다. 구 index 기반 v1 pin은
   `legacy_promotion` 입력으로만 사용한다. stable identity가 관측된 경우 backend
   binding readback 또는 local pin exact readback이 실패하면 cache 갱신, `/turns`
   저장 요청과 retry queue 진입을 모두 중단한다. 수동 attach/migration UI도
   acknowledgement가 없으면 성공을 표시하지 않는다.
6. Windows dependency probe는 명시적 `-Execute`가 있을 때만 고유 임시
   collection/table을 만든다. Chroma는 production store로
   `Upsert → Get → QueryExact → Count → Delete → Count(0) → ResetAll`을 검사한다.
   Chroma v2가 collection ID DELETE에 성공을 반환하면서 실제 collection을 남기는
   동작을 실환경에서 재현해 name DELETE와 GET 404 사후검증으로 수정했다.
   DELETE 자체가 404여도 named GET으로 실제 부재를 확인하며, fallback DELETE가
   404인데 collection이 남아 있으면 성공으로 처리하지 않는다.
7. MariaDB application account probe는 non-root local TCP 계정만 허용하고 입력
   DSN으로부터 `127.0.0.1`과 `localhost` 두 target을 만든다. 각 target에서
   `PING → CREATE → INSERT/SELECT → UPDATE/readback → DELETE → ALTER → DROP`을
   schema 적용 전에 수행해 권한 부족 환경을 부분 schema 변경보다 먼저 차단한다.
   DSN과 password는 report에 넣지 않으며 권한 오류는
   `DB_PERMISSION_DENIED`와 stage/operation으로 반환한다.
8. Windows updater IPC는 stdout/stderr를 분리하고 contract, action, action별
   status, exit code와 failure code를 정확히 검사한다. update state는 preserved
   runner path와 SHA-256을 묶어 recovery 때 가장 최신 파일을 추측하지 않는다.
   committed state 뒤 같은 pending marker가 남은 crash window는 재적용하지 않고
   idempotent cleanup한다.
9. migration inventory가 달라지는 package는
   `archive-center.package-migration-update.v1` 계약이 필요하다. 이 계약은 package
   manifest가 인증하며 source version별 정확한 기존 migration size/hash와 target
   inventory를 비교한다. 검토되지 않은 임의 SQL을 문자열 규칙으로 자동 승인하지
   않는다.
10. 3.0.0·3.0.1·3.5.0 Windows update package에는 별도
    `archive-center.external-update-bridge.v1` compatibility bridge를 제공한다.
    bridge는 자체 script·updater·선택한 update ZIP의 SHA-256과 실제 공개 package의
    migration fingerprint를 검사한 뒤 새 updater를 보존 runner로 먼저 실행한다.
    3.0.0·3.0.1에서만 필요한 11개 obsolete managed path는 source fingerprint
    계약에 정확히 열거된 경우에만 transaction journal로 제거하며 rollback 때
    원본 바이트를 복원한다. 임의 경로 삭제 API는 열지 않는다. bridge 성공은
    `applied_pending_health`이며 launcher health commit 전에는 완료로 표시하지 않는다.
11. Windows launcher와 external installer는 package 폴더가 아닌
    `ARCHIVE_CENTER_DATA_DIR` 또는 `%LOCALAPPDATA%\ArchiveCenter\data`를 stable data
    root로 사용한다. legacy data import는 source를 지우지 않고 count/hash 검증과
    resumable marker를 사용한다. MariaDB port/process 또는 기본·설정된 local
    Chroma endpoint가 살아 있으면 raw data directory copy를 거부한다.
    Chroma guard는 `127.0.0.1`과 `::1`, 설정된 local endpoint를 해당 IP 주소군으로
    직접 검사한다. source를 고유 staging directory에 복사·검증한 뒤 같은
    volume에서 destination으로 promote하며, 성공 marker는 promote가 끝난 뒤에만
    기록한다.

### 3.7-E — HUD와 대시보드 사실성

#### 처리한 사용자 피드백

3.7-E는 다음 현상과 오해에 직접 대응한다.

- `waiting for RisuAI active chat confirmation`이 실패 큐와 같은 경고로 보이고,
  30분 전 또는 다른 세션의 실패 항목이 현재 턴 문제처럼 나타나던 현상
- `raw:ok`, `derived:ok`, `vector_not_configured`, `critic_extract_failed`처럼
  서로 다른 저장 lane의 상태가 하나의 성공·경고 문구로 뭉쳐지던 현상
- HUD에 6/12 같은 단계만 보여 실제 Host 관찰, backend 처리, payload 전달,
  원문 저장, 파생 기억과 Vector 중 어디에서 멈췄는지 알기 어려웠던 현상
- 현재 Host turn과 backend turn이 다르거나 Dry Run이 과거 turn을 보아도
  불일치를 한 화면에서 확인할 수 없던 현상
- OOC·삭제·리롤·정확한 중복 재전송 같은 정상적인 운영 이벤트까지 경고로
  보이거나, OOC 표시를 JavaScript가 backend 응답처럼 자체 조립하던 문제
- warning/error 창이 카드 바깥 또는 카드 본문 클릭으로 닫혀 원인을 읽기
  어려웠던 문제

#### 구현된 계약

1. HUD 계약을 `turn_workflow_hud.v2`로 올리고 다음 typed fact를 추가했다.
   각 fact는 `owner`, `scope`, `status`, `disposition`, `reason_code`,
   `severity`, 선택적 `count`를 가진다.
   - `host_observation`
   - `backend_processing`
   - `context_selection`
   - `payload_delivery`
   - `finality`
   - `raw_persistence`
   - `derived_memory`
   - `vector_index`
2. disposition은 `eligible`, `selected`, `delivered`, `deferred`, `dropped`만
   허용한다. 잘못된 값은 성공처럼 표시하지 않고 `deferred`와 typed reason으로
   정규화한다.
3. prepare 단계에서 RisuAI source observation, backend context selection과
   Host payload 적용 대기를 분리한다. complete 단계에서는
   `source_to_final_lineage_observation`이 `archive_center_before_request_return`에서
   `applied` 또는 `empty`였을 때만 payload를 `delivered`로 표시한다.
   active-final acceptance와 payload 전달을 같은 사실로 합치지 않는다.
4. complete-turn의 실제 persistence pipeline 결과를 raw, derived, Vector fact에
   각각 연결한다. 저장 수와 `ok`, `empty`, `queued`, `skipped`,
   `vector_not_configured`, `error`를 유지하며, Vector 실패가 raw 저장 성공을
   실패로 바꾸지 않는다.
5. 전체 severity는 `normal`, `notice`, `warning`, `error` 네 단계다.
   정상·알림은 카드 또는 X로 닫을 수 있고 warning·error는 backend가
   `dismissal_policy=x_only`로 반환한다. JavaScript는 이 계약을 그대로 렌더링하며
   자체적으로 severity나 닫기 정책을 재판정하지 않는다.
6. 성공한 backend/finality fact는 다른 lane의 Vector 경고를 상속하지 않는다.
   전체 카드는 Vector 경고를 유지하되 개별 backend/finality fact는 성공으로
   남는다. 반대로 `awaiting_risu_host_final`의 일시적인 notice는 정상 완료 뒤
   남지 않으며, 실제 deferred/dropped fact의 notice·warning은 유지한다.
7. 기존 OOC 판정 결과만 `turn_workflow_notice_observation.v1`로 Go에 전달한다.
   endpoint는 정확한 OOC observation만 허용하며, title·severity·dismissal과
   `turn_workflow_hud.v2` 응답은 Go가 만든다. JavaScript의 가짜 backend-shaped
   OOC ViewModel 조립은 제거했다. HUD 표시 설정을 꺼도 대시보드용 backend
   observation은 기록하되 화면에는 띄우지 않으며, transport 실패는 OOC 입력
   취소나 본문 응답을 실패시키지 않고 fail-open한다. 별도 5초 고정 제한 없이
   기존 사용자 요청 timeout 설정을 그대로 사용한다.
8. 삭제 성공은 notice, 삭제 동기화 부분 실패는 error, reroll 교체 성공은
   notice로 표시한다. 정확히 같은 중복 replay는 notice로, 내용 충돌 중복은
   warning으로 구분한다. 이 operation notice도 Go ledger에 기록해 대시보드가
   같은 사실을 읽을 수 있다.
9. `host_turn`, `backend_turn`, `turn_alignment`를 추가해 `aligned`,
   `host_ahead`, `backend_ahead`, `unobserved`를 reason과 함께 표시한다.
   HUD는 불일치일 때 `Host N / Backend M`을 함께 보여준다.
10. 대시보드를 `dashboard.viewmodel.v2`로 올리고 현재 session의 최신 Go workflow
    snapshot을 읽어 typed fact card를 만든다. 새 workflow card는 번역 문구를
    정규식으로 분석해 상태를 추측하지 않는다.
11. queue observation은 `transport_retry`, `pending_confirmation`,
    `maintenance`로 분리하고 `current_request`, `current_session_history`,
    `other_session`, `unknown` scope를 부여한다. request ID가 서로 다르면 같은
    session·logical turn이어도 과거 queue로 분류한다. 전체 실패 큐 depth만 있고
    correlation이 없으면 현재 경고가 아니라 `Historical Queue / unknown` notice다.
12. JavaScript는 RisuAI hook·session/message 관찰, 최소 queue correlation
    metadata 전송, DOM 렌더링만 담당한다. queue payload 본문과 API key는
    대시보드 요청에 넣지 않는다. 새 watcher, finality timer 또는 별도 상태
    캐시는 추가하지 않았다.
13. 대시보드 요청에 exact current workflow request ID가 있으면 같은 session의
    더 최신 operation notice로 바꾸지 않는다. exact ID가 없을 때만 session
    최신 snapshot을 사용하므로 현재 요청과 직전 삭제·중복 알림이 섞이지 않는다.
14. maintenance queue 항목은 enqueue 응답에 실제로 들어 있던 session,
    request ID, logical turn만 사용한다. correlation이 없는 maintenance audit를
    현재 요청으로 합성하지 않으며, maintenance audit 저장 실패도 derived memory
    저장 실패로 바꾸지 않는다.
15. OOC와 rollback operation request ID를 session·turn·operation source로
    결정적으로 만들고 Go ledger에서 같은 ID·같은 notice를 idempotent하게
    재사용한다. 같은 Host hook이나 transport 재시도가 operation card를 여러 개
    만들지 않는다.
16. rollback HUD의 raw, derived, Vector fact는 실제 `deletions` 결과에서 만든다.
    source invalidation 단계에서 중단되면 세 lane과 finality를 `blocked/error`로
    표시하고, 정상 삭제·부분 실패·Vector 비설정·durable outbox 재시도를 각각
    `deleted`, `partial_error`, `skipped`, `queued`로 구분한다. Vector outbox의
    permanent 실패는 재시도 가능으로 쓰지 않고 canonical 삭제 성공과 Vector
    영구 실패를 분리해 top-level delete sync `partial_error`로 올린다.
17. reroll로 superseded된 기존 workflow는 `accepted`로 남기지 않고 finality를
    `invalidated/dropped`로 갱신한다. 새 active-final과 이전 revision의 성공
    표시가 동시에 current truth처럼 보이지 않는다.

- 동일 session·동일 turn의 과거 request ID가 current queue로 승격되지 않는
  대시보드 회귀: 통과
- exact current workflow ID가 더 최신인 같은-session operation으로 치환되지 않는
  대시보드 회귀: 통과
- maintenance provenance 미확인 항목의 historical 분류와 maintenance audit 실패가
  derived persistence 실패로 승격되지 않는 회귀: 통과
- rollback 성공·source invalidation 차단·Vector outbox 재시도의 typed lane
  상태와 결정적 operation ID 회귀: 통과
- Vector outbox permanent 실패의 canonical/Vector 분리, top-level
  `partial_error`, error·X-only HUD 회귀: 통과
- JavaScript marker 회귀: 로컬 fake OOC ViewModel 부재와 typed endpoint 사용 통과

이는 source-level·fixture 검증이다. 실제 RisuAI/PocketRisu에서 streaming,
긴 reasoning, OOC, 삭제, reroll, duplicate, plugin reload를 수행한
loaded-artifact/mobile 검증은 아직 하지 않았다. warning/error X-only 동작도
실기기 확인 전에는 source 계약 통과로만 기록한다. 또한 기존 dashboard의
legacy runtime-state card에는 과거 문자열 정규화가 남아 있지만, 3.7-E의 새
workflow·queue 상태에는 사용하지 않는다.

### 3.7-F — 기억 전달과 서사 가이드 피드백

#### 처리한 사용자 피드백

3.7-F는 새 장기 기억 schema나 plot Director를 만드는 단계가 아니다. 현재
production prepare-turn 경로에서 이미 확인된 다음 불일치와 품질 저하를 닫는다.

- `compactPrepareTurnLine`이 전달받은 길이 제한을 적용하지 않아 compact trace가
  설정한 상한보다 길어지던 문제
- 설정의 `topK`가 backend에서는 Vector 후보 검색 상한인데 HUD·대시보드에서는
  최종 기억 총수처럼 보이던 문제
- Supervisor의 깨진 JSON, 올바른 빈 제안, 지원하지 않는 제안이 모두 정상 빈
  제안처럼 보이던 문제
- `romance`, `battle`, `kiss` 같은 영어 단어로 `auto` 장르를 판정해 입력 언어와
  표현에 따라 서사 모드가 달라지던 문제
- 서사 모드를 JavaScript 설정 화면에서 고를 수 없고 저장값을 다시 `auto`로
  덮어 실제 backend 동작과 UI가 달랐던 문제
- Go가 최종 선택·제외한 기억과 이유가 HUD에 연결되지 않아 “몇 개가 왜
  전달되었는지” 확인할 수 없던 문제
- Persona·hierarchy가 현재 요청과 무관해도 빈 수를 채우거나, 주관 기억이
  owner당 한 건으로 영구 차단되어 관련된 후속 기억도 사용할 수 없던 문제

#### 구현된 기억 전달 계약

1. 기존 `top_k`는 `vector_memory_search_limit_only`로 고정했다. protected guard를
   Vector 결과 수에 포함시켜 실제 관련 기억 후보를 밀어내지 않으며, 설정·HUD도
   이를 “Vector 후보”로 표시한다.
2. 별도 선택 설정 `core_objective_memory_max_items`와
   `core_objective_memory_delivery.v1`을 추가했다. 이 값은 relevance, entity
   coverage와 우선순위가 더 높은 직접 근거 lane과의 교차 중복 제거가 끝난
   객관적 사건 요약에만 최종 최대 상한으로 적용한다. 직접 근거로 이미 전달된
   중복 항목은 K를 소비하지 않으며, 문자 예산에 들어가지 못한 항목도 K를
   소비하지 않아 뒤의 서로 다른 관련 항목이 시도될 수 있다. 요청에서 필드가
   없으면 기존 item-count 동작을 유지한다.
3. 직접 근거, protected secret guard, 주관·관계 기억, 인물·세계·필수 상태,
   미해결 목표와 hierarchy support는 핵심 객관 기억 K를 소비하지 않는다.
   이는 무제한 주입을 뜻하지 않는다. 모든 lane은 기존 provenance,
   source lifecycle, visibility·privacy, 중복 제거, lane 문자 예산과 전체
   `max_injection_chars`를 계속 통과해야 한다.
4. 최종 lineage는 `eligible_distinct_count`, `candidate_count`,
   `delivered_count`, `deferred_by_limit_count`,
   `deferred_by_budget_count`, `missing_to_limit`, `gap_reason`을 분리한다.
   관련 기억이 K보다 적을 때 무관 기억을 채우지 않으며 `garbage_fill=false`,
   `top_k_reinterpreted=false`를 명시한다.
5. 최종 예산 조립 후 lineage의 delivered/deferred와 issue code를 다시
   계산한다. protected guard가 객관 기억보다 많다는 이유만으로 과거
   `protected_guard_dominates_final_memory_lines` 경고를 남기지 않고, 실제 객관
   기억이 완전히 전달되지 않은 경우에만 `actual_memory_absent`를 유지한다.
6. Persona는 현재 사용자 요청과 직전 accepted assistant 장면에 기억 내용,
   evidence 또는 owner가 아닌 semantic tag가 실제로 겹치는 항목만 선택한다.
   `owner_*`, `raw_owner_*`, visibility·source·reveal policy 같은 저장용 구조
   tag나 owner 이름 일치만으로 무관한 Persona 기억을 통과시키지 않고,
   내용 관련성을 통과한 뒤의 owner 일치는 정렬 가중치로만 사용한다. 한국어
   같은 비 ASCII 조사·활용이 붙은 표기도 보수적인 prefix 겹침으로 확인하되,
   단순 장기 세션이나 profile이라는 이유로 채우지 않는다.
7. hierarchy는 현재 요청과 관련된 가장 좁은 chapter→arc→saga 한 단계만
   선택한다. 장기 세션, 일반적인 “계속”, profile mode 같은 우회 조건으로
   무관한 상위 요약을 넣지 않는다.
8. 주관 기억은 privacy와 현재 입력 또는 관찰된 현재 장면의 owner scope를 먼저
   통과한 뒤, 각 기억의 text·evidence·tag가 현재 relevance context와 실제로
   겹치는지를 별도로 확인한다. owner 이름만 나온 경우 그 owner의 무관한 기억을
   전부 넣지 않는다. 이후 1차로 서로 다른 owner를 한 건씩 coverage하고, 남은
   문자 예산에서 같은 owner의 관련 비중복 항목을 추가한다. owner당 한 건이라는
   영구 hard cap과 수 채우기는 제거했다.

#### 구현된 서사 가이드 의미

1. `auto`는 본문 영어 키워드로 장르를 추정하지 않고 `standard`로 해석한다.
   `romantic`, `action`, `mature_*`는 사용자가 설정 UI에서 명시적으로 고른
   경우에만 적용된다. JavaScript는 선택값을 저장·전달하고 Go가 실제 모드와
   정책을 소유한다.
2. `none`은 Supervisor 호출과 output guidance만 0으로 만든다. 장기 기억,
   직접 근거, 비밀 보호, 상태와 continuity 주입은 계속 동작한다.
3. `weak`는 source-backed `response_focus`와 `must_account`,
   `medium`은 추가로 `may_advance` 또는 `hold_allowed`,
   `strong`은 추가로 `arc_anchor`와 `preferred_frontier`를 제안할 수 있다.
   이 이름들은 모두 선택형 표현 guidance이며 canonical 전이나 자동 scene
   transition 명령이 아니다.
4. 모든 강도에서 `truth_authority=false`, `canonical_write=false`,
   `force_progress=false`이며 사용자 행동, 새 진실, 관계 변화와 미해결 사건
   종결 권한을 차단한다. `strong`도 진행을 강제하지 않는다.
5. 새 complication을 생성하는 runtime 경로는 추가하지 않았다.
   `proactive_complication_default=off`,
   `proactive_complication_requires_opt_in=true`,
   `strong_implies_proactive=false`로 계약을 고정했다. 실제 생성 기능이 필요한
   경우 별도 명시적 opt-in, source constraint와 revision fence가 있는 후속
   계약 없이는 열지 않는다.
6. Supervisor JSON parse 실패는 `malformed_failed_open`, proposal envelope,
   list, item 또는 item 내부 `text`·`kind`·`source_refs` 타입이 계약과 다른
   응답은 `supervisor_schema_invalid`, 문법·schema상 올바른 빈 proposal은
   `valid_empty`, 허용하지 않는 kind·field만 있는 응답은
   `unsupported_rejected`, provider 실패는
   `supervisor_provider_failed_open`으로 분리한다. malformed 원문이나 stale
   제안은 prompt·trace·HUD에 재사용하지 않으며 본문 요청은 fail-open한다.
7. `compactPrepareTurnLine`은 공백 정규화 뒤 양수 길이 상한을 실제 적용하고,
   UTF-8 rune 경계를 보존하며 가능한 경우 단어 경계에서 자른다.

#### HUD·설정 연결과 비밀 경계

- Go `turn_workflow_memory_selection.v1` ViewModel이 Vector 후보 상한, 핵심 기억
  계약, lane별 eligible/selected/deferred/deduplicated 수, 최종 item disposition과
  typed reason, 제외 이유별 수를 제공한다.
- HUD는 Go ViewModel을 렌더링만 한다. delivered non-protected 항목에는 제한된
  preview를 표시할 수 있지만 protected text, 전달되지 않은 후보 text,
  `deferred_fact_keys`는 응답 ViewModel에서 제거한다.
- 설정 UI는 `핵심 연관 기억 최대 수`와 실제 `서사 가이드 모드`를 저장하고
  prepare-turn 요청에 전달한다. 강도가 `none`일 때만 모드 선택을 비활성화하며,
  저장값을 임의로 `auto`로 되돌리지 않는다.
- compact 응답의 검색 수, Supervisor 상태·실제 승인 지시 존재 여부와 호출 수는
  Go `prepare_turn.compact_orchestration.v1`이 계산한다. provider 실패를 설명하기
  위한 text 없는 trace item은 실제 directive로 세지 않는다. JavaScript는 이
  projection을 복사·표시할 뿐 기억 수나 Supervisor 상태를 다시 계산하지 않는다.
- plugin과 backend 기본 버전은 모두 `3.7.0-dev`로 맞추고, `guide_mode`의 frozen
  DTO/OpenAPI enum도 실제 UI·Go 계약인 `auto/off/standard/romantic/action/
  mature_soft/mature_direct`와 동기화했다.
- `Archive Center.js`에 추가된 동작은 RisuAI 설정 관찰·transport·DOM·현지화와
  Go trace 표시뿐이다. 기억 선택, K 적용, Supervisor 분류와 authority 판단은
  Go에 남는다.

#### 검증 상태와 남은 gate

- `go test ./internal/httpapi -count=1`: 통과
- bundled Node를 `ARCHIVE_CENTER_NODE_BINARY`로 지정한
  `go test ./cmd/js-route-variant-smoke -count=1`: 통과
- bundled Node `Archive Center.js --check`: 통과
- bundled Node와 로컬 Go cache를 지정한 `go test ./... -count=1`: 전체 통과
- compact 한글·emoji·단어 경계, 언어별 auto mode parity, malformed/empty/
  schema-invalid/unsupported Supervisor, provider 실패의 directive 오표시 방지,
  strength별 권한 차단, 교차 lane 중복 뒤 핵심 K와 support exemption,
  owner metadata-only Persona 차단, hierarchy·subjective relevance,
  HUD private text 비노출 회귀: 통과

이는 **source implementation과 자동 fixture 증거**다. 실제 loaded
`Archive Center.js`와 backend를 RisuAI에서 연결해 설정 저장·reload, 한국어
장면, protected memory, K 미달·초과, weak/medium/strong, malformed 실제 provider
응답과 HUD 표시를 확인하지 않았다. 따라서 상태는
`source_implemented / loaded-artifact guide-quality gate pending`이며 4.0의
정밀 recall·injection 완료나 proactive Director 완료로 표시하지 않는다.

### 3.7-G — 통합·실환경 검증과 배포

3.7-G는 A~F의 정책을 다시 설계하는 단계가 아니다. 현재 source를 실제 배포
artifact에 고정하고 Host·DB·Vector·updater·provider에서 같은 계약이 작동하는지
증명하는 단계다. source 시험 성공을 loaded artifact 성공으로 바꾸어 쓰지 않는다.

#### G-0 — 진입 전 정리

1. failed `complete_turn` queue key에 idempotency key와 필요한
   generation/source revision fence를 포함하고, duplicate와 overflow를 조용히
   버리지 않고 typed admission·terminal 상태로 남긴다.
2. Windows/POSIX package builder, `.env.example`, Windows env 예시와 운영 문서의
   기본 버전을 plugin·Go와 같은 `3.7.0-dev`로 동기화한다.
3. package manifest에 source commit, dirty state, 재현 가능한 build command,
   package version과 파일 manifest SHA-256을 기록한다.
4. loaded plugin build ID, backend `/version`, package manifest와 ZIP SHA-256을
   같은 evidence record에 연결한다.
5. 전체 session migration을 3.7 제공 기능으로 열지, 안전 비활성으로 배포할지
   확정한다.
   - 제공한다면 50개 manifest executor와 count/hash/FK/vector expected-ID parity를
     먼저 완성한다.
   - 비활성으로 배포한다면 UI/API가 unavailable을 명시하고 source cleanup과 target
     mutation이 계속 fail-closed인지 fault test로 증명한다.
6. legacy dashboard runtime-state 문자열 정규화는 3.7 typed 전환 범위가 아님을
   명시하거나, 전체 대시보드 사실성을 3.7 요구로 유지한다면 Go typed fact로
   전환한다.
7. proactive complication은 3.7에서 실제 기능이 아니라
   `default=off / explicit opt-in contract required`인 미래 경계로 고정한다.

#### G-1 — 자동·통합·fault 시험

- 전체 Go와 production JavaScript adapter 회귀
- migration manifest·binding·pin·cleanup fail-closed와 선택한 migration 제공 범위
- Critic 401/429/5xx, timeout, empty, malformed, schema-invalid, stale revision
- pending confirmation, transport retry, backend processing, terminal,
  superseded와 reload 복구
- MariaDB transaction·권한·중단 복구와 Chroma endpoint·outbox·readback 장애
- updater apply/status/commit/rollback, 중단 재개, tamper와 mixed-package 차단

#### G-2 — 실제 RisuAI lifecycle

- non-streaming과 streaming
- 긴 reasoning
- 번역/inlay가 있는 응답
- reroll·assistant delete·edit·branch·copy/fork·`/cut`
- plugin unload/reload와 backend restart
- desktop과 지원하는 mobile/remote 환경

각 lifecycle에서 Host candidate, accepted final, raw save는 정확히 한 번이어야 한다.
pending confirmation은 transport attempts를 소비하지 않아야 하며 reroll·delete된
revision의 늦은 결과는 저장·주입되지 않아야 한다.

현재 공식 RisuAI에 post-commit output listener가 없는 지원 버전에서는
`afterRequest`와 공식 mutation observation 경로를 검증한다. 지원 Host 버전이
달라졌다면 pinned upstream commit과 capability 표를 먼저 갱신한다.

#### G-3 — 실제 provider 비교

- 같은 prompt·설정·Host lifecycle에서 최소 두 개 이상의 실제 provider를 비교한다.
- 특정 모델명을 예외 처리하지 않고 streaming shape, reasoning 길이와 응답 지연이
  finality 의미를 바꾸지 않는지 확인한다.
- provider 호출은 사용자 자격 증명·비용·외부 전송이 필요한 실험이므로 실행 전에
  대상 provider와 비용 범위를 명시한다.

#### G-4 — Windows 신규 설치와 기존 설치 업데이트

- 빈 사용자 data root에서 관리형 MariaDB·Python·Chroma 설치와 재기동
- Python만 있음, Python은 있으나 chromadb 없음, 잘못된 Chroma 버전
- 3.5 기존 설치의 DB·Vector data 보존 upgrade
- `127.0.0.1`·`localhost` MariaDB CRUD·DDL
- packaged launcher의 Chroma endpoint·upsert·exact readback·cleanup
- compatibility bridge 뒤 `/ready`·`/version` 확인과 health commit
- health 실패·중단·tamper에서 byte-for-byte rollback과 data root 보존

#### G-5 — 품질·지연·비용 측정

동일 fixture와 설정으로 다음을 raw evidence와 함께 기록한다.

- 첫 출력 candidate 중 accepted final로 채택된 비율
- pending confirmation 발생률과 해소 신호
- reroll·delete·edit 후 stale 결과 폐기율과 잘못된 저장 0건
- main response, Host final 확인, raw save, Critic, derived, Vector 단계별 지연
- main·Supervisor·Critic 호출 수, token 또는 provider가 제공하는 비용
- 최종 기억 eligible/selected/delivered/deferred/dropped 수와 품질 표본

#### G 종료 조건

- source commit과 loaded artifact hash가 하나의 evidence manifest로 연결됨
- G-1~G-5의 필수 matrix에 `passed`, `failed`, `blocked`, `not_applicable` 중 하나가
  기록되고 미기록 항목이 없음
- release-blocking 실패가 0

## 23. 사용자 지원 답변 기준

### `waiting for RisuAI active chat confirmation`

> 현재 출력 후보는 들어왔지만 Archive Center가 RisuAI active chat의 최종 출력과
> 연결하지 못한 상태입니다. 모델 자체 오류로 단정하지 않습니다. 디버그에서
> request ID, session ID, logical turn, active chat user/assistant 수,
> complete-turn request status와 실패 큐 item 한 건을 확인해야 합니다.

### `raw:ok derived:ok verify_unavailable`

> 원문과 파생 자료 저장은 성공했습니다. 마지막 문구는 선택적 read-back을 시간 안에
> 확인하지 못했다는 뜻이며 저장 실패와 다릅니다.

### `CRITIC_LLM_FAILED`

> 3.7-C source에서는 공급자 호출·timeout·HTTP 오류·빈 응답·JSON 누락·문법 오류와
> schema 오류를 별도 `CRITIC_*` 코드로 표시합니다. `stage`, `retryable`,
> 가능한 경우 `http_status`와 비밀값이 제거된 `raw_preview`를 함께 확인합니다.
> 배포된 plugin/backend가 3.7-C 이전이면 여전히 `CRITIC_LLM_FAILED` 하나로 보일 수
> 있으므로 loaded artifact의 build ID를 먼저 확인합니다. 원문 저장 성공 여부는
> 계속 별도로 봅니다.

### `vector_not_configured`

> 과거 세션의 오류가 아니라 현재 실행 중인 backend에 Chroma endpoint가 연결되지
> 않았다는 서버 공통 상태입니다. MariaDB raw/derived 저장과 Vector upsert는 별개입니다.

### `LOGICAL_TURN_REPLACE_FAILED`

> 3.7-B source에서는 `code`, `stage`, `retryable`, `commit_state`,
> `raw_committed`로 하위 오류를 구분합니다. 권한·revision·중복·constraint·lock
> wait/deadlock·commit 결과 불명과 post-commit reconciliation 실패에 따라
> 재시도 여부가 달라집니다. 배포본이 구형 generic 코드만 반환하면 반복 재시도 전에
> HTTP 응답과 backend latest tail을 확인합니다.
