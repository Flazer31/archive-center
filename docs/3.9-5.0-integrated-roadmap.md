연극처럼 장면을 검토·연기·재구성하고 최종문 하나를 반환한다. 연동 전처리가 선택된
요청에서는 Archive Center 출판사를 자동으로 호출하지 않으며, 연동하지 않은 요청에서는
Archive Center의 기본 기억·출판사 기능을 그대로 유지한다.

## 전체 목적

3.9~5.0은 서로 다른 기억·출판·시뮬레이션 backend를 병렬로 새로 만드는 계획이
아니다.

1. 3.9~4.0은 정확한 기억·관계·상태를 찾고 전달하며 수정·리롤·장애 뒤에도
   거짓 기억을 부활시키지 않는 기반을 한 번에 완성한다.
2. 4.1~4.2 후보는 그 기반을 사용자가 탐색·정리·감사하는 운영 표면을 보강한다.
3. 4.3은 Archive 기억과 RisuAI 로어북·캐릭터·페르소나를 역할별 문맥으로 조립한다.
   감독관·나레이터에는 전체 배경 이야기와 공개 기억을, 연기자에는 같은 배경 이야기와
   해당 인물의 주관 기억을 할당한다.
4. 4.4는 별도 플러그인이 전처리를 맡는 요청의 소유권을 확정하고 Archive Center 출판사를
   자동 비활성화해 전처리 경로를 하나로 만든다. 4.5는 메인 모델의 1차 출력 이후 역할 AI
   협업과 최종문 합성, 후처리된 displayed-final 인식·저장 lifecycle을 완성한다.
5. 4.6~4.8은 검증된 기억을 read-only 실행 카드와 관계·세계·thread 지원으로
   투영한다.
6. 4.9는 4.0 출판사의 동일 owner와 단일 guidance 경로를 고급 다단계 검토로
   확장한다.
7. 5.0은 실제 표시 출력이 기억·관계·세계·사용자 방향을 지켰는지 진단하고
   실사용 release evidence를 닫는다.

목표는 **1.0의 관련 기억 회수·행동화·장면 집중 장점**을 가져오되, 3.6/3.7의
출처·시점·branch·권한·비밀·fail-open 경계를 약화시키지 않는 것이다.

## 전 버전 공통 불변식

### 영구 Host/backend 경계

- Go가 source admission, truth·authority, ranking, selection, memory delivery,
  prompt assembly, budget, lifecycle, orchestration과 ViewModel을 소유한다.
- `Archive Center.js`는 RisuAI 관측, backend 호출, 실제 payload 적용과 UI 표시만
  담당한다.
- 관계·검색·출판·시뮬레이션을 JavaScript의 병렬 backend나 fallback으로 만들지
  않는다.
- 뒤 버전은 앞 버전의 canonical owner를 복제하지 않고 versioned input을
  read-only로 소비한다.

### 기억과 검색

- MariaDB의 accepted source와 versioned canonical row가 권위 원장이다.
- Vector, graph, similarity, activation, 선택 횟수와 응답 유사도는 검색 신호일
  뿐 truth·importance·관계·삭제 권한이 아니다.
- vector `topK`는 후보 상한이고, 사용자-facing 핵심 기억 수는
  `core_objective_memory_max_items`와 실제 delivered K가 소유한다.
- 적격 기억이 부족하면 적게 전달하고 gap reason을 남긴다. 무관한 기억,
  raw chat, stale cache와 wrong-knower 자료로 K를 채우지 않는다.
- 핵심 객관 기억, continuity, direct evidence, subjective memory, 관계·profile,
  reference와 secret guard는 별도 lane과 예산을 유지한다.

### 출판사와 창작 자유

- `none`은 출판사 OFF이지 기억 지원 OFF가 아니다. 핵심 기억, 직접 근거,
  주관 기억, 상태·관계와 secret guard는 계속 유지한다.
- `none`, `base_only`, `proposal_0`에서는 Publisher 호출·plan·main guidance가 0이다.
- weak 이상도 `truth_authority=false`, `canonical_write=false`다.
- 4.0의 서사 강도 `none/weak/medium/strong/extreme/maximum`, 모델 입력 표현
  `compact/standard/explicit`과 4.9 호출 깊이 `directed/reviewed/deep`은 서로 다른 축이다.
- 현재 사용자 입력과 명시적 방향 전환이 이전 focus·arc·storyline보다 우선한다.
- focus는 response 또는 현재 scene 범위의 짧은 lease다. 자동 갱신, persistent
  plot lock과 과거 이야기의 강제 부활을 금지한다.

### 실패와 완료 증거

- LLM, Critic, embedding, reranker, vector와 graph가 없어도 exact·lexical recall,
  accepted state, 핵심 K와 메인 응답이 작동해야 한다.
- 선택 기능 장애는 후보·가시성·권한·K·예산을 넓히지 않는다.
- stale/default/partial plan과 이전 성공 결과를 현재 fallback으로 재사용하지 않는다.
- source test, schema, fixture와 package 존재를 loaded RisuAI·DB·Vector·실사용
  증거로 바꾸어 말하지 않는다.

## 3.9 — 관계·캐릭터 기억과 출판사 오류 안정화

### 3.9 목적

3.9는 “누구와 어떤 관계인가”, “어떤 행동이 반복됐는가”, “그 인물이 평소와
현재 어떻게 다른가”, “상대별로 어떤 말투와 태도를 보이는가”를 source-linked
기억으로 만든다. 기존 Go Publisher는 현재 bounded response hint 계약을 유지하고
provider-neutral 요청·응답과 stable failure가 오류 없이 작동하는 데서 3.9 범위를 끝낸다.
1.0의 `book_author + director` 역할과 coherent narrative-plan block은 4.0이 소유한다.

### 3.9 구현 packet

| packet | 책임 |
|---|---|
| `3.9-A` | 방향·domain별 `relationship_state.v1` current/history |
| `3.9-B` | `habit_evidence.v1`, 반복·반례·상황·상대 |
| `3.9-C` | stable/current/dynamic `character_profile.v1` |
| `3.9-D` | trait-domain과 `voice_behavior_projection.v1` |
| `3.9-E` | 관계·profile 기억 전달과 Publisher support projection |
| `3.9-F` | 기존 Go Publisher의 bounded hint와 provider 오류 안정화 |
| `3.9-G` | correction·entity merge/split·reroll/delete·branch 국소 rebuild |
| `3.9-H` | 실제 RisuAI 장기 RP 품질·비용·redirection gate |

### 3.9 완료 기준

- 관계를 한 score로 평탄화하거나 user/player를 자동 우대하지 않는다.
- 한 번의 행동을 습관·성격·말투로 승격하지 않는다.
- 현재 감정이 stable profile을 덮지 않고 관계별 태도와 반례가 남는다.
- 예시 대사를 복사하지 않고 말투·행동 원리를 source ref로 재현한다.
- Publisher는 정확히 한 typed guidance block만 만들며 기억 K와 별도 예산을 쓴다.
- Publisher 실패 시 base memory와 main response가 계속되고 stale plan은 0이다.

## 4.0 — 정밀 기억·출판·수명주기 완성

### 4.0 목적

4.0은 기억 개수를 무조건 늘리는 버전이 아니다. 현재 요청이 요구하는 사건·발언·
상태·관계·주관 기억을 exact·lexical·vector·source-backed neighborhood에서 찾고,
coverage와 예산을 적용한 최종 K를 실제 payload까지 전달한다. 같은 delivery lineage를
사용해 기존 단일 Publisher owner를 1.0 방향의 `book_author + director`와 한 개의 coherent
narrative-plan block으로 복구한다. 여기에 기존 4.1의 수정·삭제·리롤·분기·재구축·재시작과
실환경 release gate를 합쳐, 만든 기억이 전체 수명주기에서 stale로 부활하지 않는 것까지
4.0 완료 범위로 닫는다.

### 4.0 구현 packet

| packet | 책임 |
|---|---|
| `4.0-A` | authority·scope·branch·knower·time hard filter |
| `4.0-B` | exact·lexical·vector·relation/thread-neighborhood retrieval |
| `4.0-C` | requirement·coverage-aware `memory_recall_plan.v1` |
| `4.0-D` | semantic/source dedupe와 hierarchy zoom |
| `4.0-E` | 기존 `memory_delivery_plan.v1`·`payload_application_plan.v1`을 바꾸지 않는 `publisher_plan.v2` 교체, `book_author + director` 단일 호출·단일 block, 6단계 strength·3종 format |
| `4.0-F` | provider-neutral Publisher 실환경 응답·실패 관측, provider/Chroma 장애·기존 DB·장기 session 성능 gate |
| `4.0-G` | 선택형 lorebook `search_only`→`reference_assist`; 최초·수동·범위 변경 snapshot, 별도 read-only 저장·검색·예산, native/기억 확정 중복만 최종 표시 생략, 기억+참조 동시 소실 0 |
| `4.0-H` | edit/delete/reroll/copy/move/branch lifecycle matrix |
| `4.0-I` | transaction·outbox·concurrency·crash recovery |
| `4.0-J` | dependency-aware invalidation·reindex·rebuild |
| `4.0-K` | Publisher·displayed-final·Critic lifecycle |
| `4.0-L` | 지원 OS·package·update·rollback |
| `4.0-M` | 장기 session soak·부하·fault |
| `4.0-N` | requirement→source→test→artifact→loaded/live closure |

`4.0-E`는 출판사 전용 작업이다. 새 `memory_injection_plan.v2`를 만들지 않고 A~D가 확정한
기억 검색·선택·중복 정리·예산·최종 전달문을 그대로 소비한다. 세부 순서는
`E-1` 역할 계약 → `E-2` delivered 입력 연결 → `E-3` 단일 호출 → `E-4` provider 응답
정규화와 엄격한 현재 schema 검증 → `E-5` 단일 본문 계획 block → `E-6` 강도 → `E-7`
표현 형식 → `E-8` 회귀 검증이다. 1.0의 `book_author + director`, current-input 우선,
quiet-scene 보존과 기억의 행동·subtext 표현은 복구한다. 1.0의 기본 directive fallback,
잘린 JSON 수리, 누락값 자동 채움, legacy schema 변환, auto-advance·persistent suffix와
Publisher의 세계·storyline canonical write는 복구하지 않는다.

`E-1` 역할·출력 계약은 문서 기준으로 확정했다. 제공자 출력은
`supervisor_scene_proposal.publisher_plan` 안에 `publisher_plan.v2` 하나만 두고,
`book_author`의 `current_arc/narrative_goal/next_beats/guardrails`와 `director`의
`scene_mandate/required_outcomes/forbidden_moves/pressure_level` 여덟 필드를 모두 명시한다.
지원이 없으면 `null` 또는 빈 배열을 직접 반환하며 누락값 보충, v1 변환, 기본 directive,
canonical write는 허용하지 않는다. 2026-08-12 소스·자동 회귀 기준으로 `E-2~E-5`를 입력부터
본문 block까지 한 번에 연결했고, 기존 v1 출력 owner를 병렬 경로 없이 v2로 교체했다.
`E-6`은 `none/weak/medium/strong/extreme/maximum` 여섯 단계를 연결했다. 모든 활성 강도는
같은 근거·같은 승인 항목·같은 `book_author + director` 계약을 사용하며 현재 응답 지시의
명시성만 바꾼다. 고정 개수 채우기, 사실 권한 확대, 사용자 행동 강제와 장면 압력 자동 상승은 없다.
`E-7`은 사용자가 선택한 `compact/standard/explicit`을 승인 이후의 기존 단일 Go renderer에
연결했다. 세 형식은 같은 항목 text·순서·source ref와 단일 block을 유지하며 역할·필드 표식만
바꾼다. 형식은 Publisher LLM 입력·호출 횟수·strength·pressure·최종 예산을 바꾸지 않는다.

`E-8`은 새 기능이 아니라 E-1~E-7의 source 회귀 마감이다. 단일 provider 호출과 단일 guidance
block, current input 우선, quiet pressure 유지, 실패 시 fabricated·이전 plan 0, 연속된 같은
세션 요청에서 stale plan 재사용 0, raw·deferred private memory의 provider·guidance 노출 0을
production owner 경로에서 검증한다. loaded artifact와 실제 provider·RisuAI/PocketRisu 검증은
이 source 회귀와 별도 증거로 남긴다.

`E-2`는 소스와 자동 회귀 기준으로 완료했다. `supervisor_support_packet.v2`는 현재 사용자 입력
원문 전체와 accepted previous completed turn을 유지하고, 기존 `memory_delivery_plan.v1`에서
최종 예산 적용 뒤 실제 본문에 전달된 기억·인물·관계·상태·세계·thread 표현만 출판사 입력으로
연결한다. 보류·미전달 후보, raw private memory, 전체 과거 채팅은 포함하지 않으며 새 검색·선택·
예산·fallback 경로도 추가하지 않았다. 이 입력은 E-4의 승인 목록과 E-5 단일 block으로
연결되며, loaded/live/provider 검증은 소스·자동 회귀와 별도다.

`E-3`는 소스와 자동 회귀 기준으로 완료했다. 출판사 provider 요청은 정상·거절·실패 모두
논리 턴당 최대 한 번이며 공용 LLM 재시도 설정을 사용하지 않는다. `book_author`와 `director`를
위한 별도 호출, 두 번째 Publisher, JavaScript 호출은 없다. E-4의 `publisher_plan.v2` 판정과
E-5 본문 계획 block은 같은 bounded cutover에서 기존 owner를 교체했으며, 병렬 v1·fallback·
shadow 경로를 추가하지 않았다.

E-4의 확정 검증 기준은 “계약 외곽은 plan 전체 단위, 역할·필드·내용은 독립 단위”다.
`supervisor_scene_proposal.publisher_plan` 객체나 정확한 contract version이 없거나 두 역할이 모두
해석 불가할 때만 전체 `publisher_schema_invalid`다. 한 역할·필드의 누락과 타입 오류, 빈 text,
잘못된 ref·pressure level은 해당 영역만, 알 수 없는 추가 필드는 그 필드만 거부하고 다른 정상
항목을 유지해 `partial`로 공개한다. Go는 누락값을 채우지 않는다. v2 외곽은 정상이나 승인 항목이
없고 완전한 명시적 빈 plan도 아니면 `publisher_plan_no_valid_items`이며 정상 빈 plan으로 가장하지 않는다. 문자열 content,
배열 text part, `choice.text`만 공통 텍스트로 정규화하고 전체 code fence 하나 외 JSON 추출·수리,
구형 wrapper·v1 변환, 자동 재호출, 이전 plan 재사용은 허용하지 않는다. E-2 기억과 메인 본문은
실패와 무관하게 계속되며 E-4 validator는 E-5 renderer와 동시에 기존 v1 owner를 교체한다.
`partial`은 거부 단일값을 `null`로 수리한 provider plan이 아니라 역할·필드·원래 순서·검증된
text/ref만 가진 Go 내부 승인 목록이며 E-5는 그 목록만 소비한다. 허용 ref는 실제 text가 든
`supervisor_support_packet.v2` 항목으로만 만들고 text 없는 native/system ref를 추가하지 않는다.
배열형 content 조립은 E-4가 empty 판정보다 먼저 처리하며 실제 provider 확인은 F가 담당한다.
E-4·E-5는 2026-08-12 소스와 자동 회귀 기준 완료다. loaded artifact, 실제 provider,
RisuAI·PocketRisu 실사용은 이 판정에 포함하지 않는다.

### 4.0 전체 작업 순서

1. `4.0-A~D`: 기억 자격 판정, 여러 검색 방식, 회상 계획, 안전한 중복 정리와 범위 확대;
2. `4.0-E~G`: 1.0 방향 출판사 복구, provider-neutral 안정화, 선택형 lorebook;
3. `4.0-H~K`: 수정·삭제·리롤, 동시 처리·중단 복구, 재색인, displayed-final·Critic 수명주기;
4. `4.0-L~N`: OS·설치·업데이트·rollback, 장기 부하와 비분기 core 실환경 closure;
5. `4.0-BR-A~E`: Host 근거, branch topology와 고정 membership, SQL/Vector 격리,
   branch별 current-state projection;
6. `4.0-BR-F`: 같은 branch snapshot에서 결정적인 Go ViewModel을 만들고 분기 기능 gate를
   통과. 이 단계 전에는 UI를 전면 교체하지 않음;
7. `4.0-BR-G`: 검증된 분기 자료를 기준으로 세계선 탐색을 포함한 Archive Center UI 전체를
   반응형으로 다시 구현;
8. `4.0-BR-H`: RisuAI·PocketRisu, 데스크톱·터치 기기, MariaDB·Chroma, package까지 최종
   검증하고 4.0 종료.

세계선 UI는 한 포인터 drag pan, 두 포인터 중심 pinch 확대·축소, mouse wheel zoom,
현재 branch 복귀·전체 맞춤 버튼을 제공한다. drag로 node를 재배치하지 않으며, canvas 밖의
일반 스크롤을 막지 않는다. 분기 의미, semantic zoom 집약과 상세 자료는 Go ViewModel이
결정하고 JavaScript는 Host 관찰, 렌더링과 실제 화면 gesture만 담당한다.

### 4.0 완료 기준

- candidate→eligible→selected→rendered→delivered가 같은 exact item ref로 이어진다.
- K=10이고 적격 기억과 예산이 충분하면 관련 핵심 기억 10개가 실제 전달된다.
- 구조화 저장본은 source·time·branch·knower·visibility를 보존하고, 본문에는
  의미를 보존한 짧은 전달 표현을 사용한다.
- recent·continuity·historical coverage가 한쪽 독식을 막되 고정 quota filler를
  만들지 않는다.
- actor·anchor·부정·시간·owner 누락을 검사하고 잘못된 summary를 raw 덩어리로
  대체하지 않는다.
- Publisher가 사용한 support ref가 실제 payload에 없으면 해당 guidance를 적용하지
  않는다.
- `book_author + director`가 한 번 호출되고 출판사 계획 block이 실제 payload에 정확히 하나만 들어간다.
- `none~maximum` strength와 `compact/standard/explicit` format은 독립이며 provider·모델명으로 의미를 바꾸지 않는다.
- lorebook 선택 기능은 native activation을 추측하지 않고 핵심 기억·정사·관계 DB로
  자동 합치지 않는다.
- mutation batch는 all-or-zero이며 stale worker가 current revision으로 승격되지 않는다.
- edit·delete·reroll·branch 뒤 old memory·relation·profile·plan·vector·cache·HUD
  재노출이 0이다.
- MariaDB에서 Chroma/graph/search projection을 결정적으로 재구축할 수 있다.
- 실제 displayed final 하나만 complete-turn과 Critic admission에 들어간다.
- final을 관찰하지 못하면 응답은 보존하되 canonical mutation은 deferred/read-only다.
- 지원 OS의 fresh install·update·fault·backup·rollback에서 사용자 설정과 DB를
  보존한다.

## 4.1~4.2 배정 후보와 4.3~4.5 확정 연동 계획

이 절은 외부 예제 분석과 기존 문서에 부분적으로 남은 운영 기능을 버전 공백에
배치하는 제안이다. 4.0의 안전 기능을 뒤로 미루지 않고, 4.6 이후의 simulation
owner를 앞당기지 않는 범위만 다룬다.

### 4.1 후보 — 기억 Locator·계층 탐색

참조 관점: HAYAKU의 짧은 연속성 전달, Living Canon의 locator형 회상 색인,
OMNINODE의 계층 탐색.

- 한 subject·claim·question 단위의 source pointer와 found/not-found trace;
- query/scope/source revision/branch/knower/visibility/expiry가 맞을 때만 재사용;
- negative trace를 “사실이 없음”으로 승격하지 않음;
- hierarchy zoom과 source lineage를 Go ViewModel으로 탐색;
- canonical fact 복제, 새 상시 agent memory와 전체 대화 사본 색인 금지.

4.1은 4.0의 ranking·K·injection owner를 바꾸지 않는다.

### 4.2 후보 — 기억 정리·격리·검토·되돌리기

참조 관점: WygLoreLeaf의 quarantine·undo, OMNINODE의 merge review.

- exact duplicate와 idempotent replay는 자동 no-op;
- cross-source·entity·time·knower·privacy semantic merge는 proposal과 명시적 review;
- keep/remove source, 영향받는 relation·summary·visibility·projection과 undo 범위 표시;
- 원 source를 재작성하지 않고 mapping/revision/rebuild lineage 유지;
- 낮은 조회수·오래됨·activation만으로 자동 prune 금지;
- dependent undo가 불가능하면 부분 복구 대신 영향 graph와 선행 undo 보고.

4.2는 4.0의 transaction·rollback을 대체하지 않는다. 4.0에서 무결성 기반을 먼저
완료하고 4.2는 위험 정리 작업의 사용자 검토 표면만 추가한다.

### 4.3 — 역할별 이야기 문맥·주관 기억 강화

4.3은 모든 역할 AI에 같은 기억을 복제하지 않고, Archive Center 기억과 RisuAI가 실제로
제공한 로어북·캐릭터·페르소나 정보를 역할에 맞게 조립한다.

- 감독관·나레이터에 현재 arc·chapter·episode·scene·미해결 thread, 세계 상태와 공개된
  인물·관계 기억을 포함한 배경 이야기 전달;
- 연기자에는 같은 배경 이야기와 자신이 경험하거나 들은 사건, 해석·오해·의심,
  관계·감정 원인·목표 등 해당 인물의 주관 기억 전달;
- RisuAI 캐릭터·페르소나·활성 로어북은 공식 Host가 관찰해 전달한 범위만 사용하고,
  Archive Center가 로어북 발동 엔진을 다시 만들거나 활성 상태를 추측하지 않음;
- objective truth와 subjective belief, 공개 배경과 인물 private memory의 분리;
- 다른 인물의 private memory·미공개 계획·모르는 정보의 교차 할당 금지;
- 내부 entity ID는 routing에만 사용하고 AI 입력에는 이름·역할·자연어 기억 전달;
- 전체 raw chat을 역할 수만큼 복제하지 않는 계층형 story context;
- session·branch·turn·generation·revision·request fence와 역할별 assignment lineage;
- 역할 AI의 발언·토론·제안의 canonical memory 직접 저장 금지.

상세 정본은
[`4.3-character-subjective-memory-story-context-roadmap.md`](4.3-character-subjective-memory-story-context-roadmap.md)다.

### 4.4 — 별도 플러그인 연동 전처리와 단일 소유권

4.4는 현재 Recomposer로 부르는 별도 플러그인이 단독형을 유지하면서도 Archive Center와
연동될 수 있게 한다. 이름, 역할명과 packet 이름은 개발 중 바뀔 수 있다. 확정하는 것은
연동 모드에서 플러그인이 전처리 전체를 맡고 Archive Center 출판사와 중복 실행되지 않는다는
방향이다.

- 단독 모드에서는 RisuAI가 실제로 제공한 채팅·로어북·캐릭터·페르소나 정보로 전처리;
- Archive Center 연동 모드에서는 4.3의 배경 이야기·공개 기억·인물별 주관 기억을 추가;
- 역할별 모델·endpoint·추론 강도·호출 여부는 별도 플러그인 설정이 소유;
- 연동 전처리가 현재 요청을 맡는 순간 Archive Center Publisher 호출과 direct guidance를
  자동으로 0회 처리하고, base 기억 검색·비밀 경계·상태 전달은 유지;
- 플러그인 연동을 사용하지 않는 요청에서만 Archive Center Publisher가 기존 설정대로 동작;
- 같은 요청에 Archive Publisher 전처리와 별도 플러그인 전처리가 함께 들어가는 경우 0;
- 1차 출력 전체와 request/source lineage를 후처리 역할 입력에 연결;
- stale·wrong-turn·wrong-branch context·draft 소비 0;
- provider × role별 전송 자료·제외 항목·호출·비용·실패 단계 공개.

### 4.5 — 역할 AI 연극형 후처리·최종문과 displayed-final lifecycle

4.5는 RisuAI 메인 모델의 1차 출력 뒤에 여러 역할 AI가 붙어 실제 연극을 만들듯 장면을
검토·연기·재구성하고 최종문 하나를 합성하는 과정과 memory admission을 닫는다.

- 감독관은 배경 이야기·공개 기억·장면 목표와 제약을 바탕으로 전체 진행을 점검;
- 나레이터는 배경 이야기·세계·시간·장소·공개 기억을 바탕으로 서술 연속성을 점검;
- 연기자 1·2·N은 배경 이야기와 자신에게 할당된 주관 기억·관계·감정·목표를 바탕으로
  해당 인물처럼 반응하고 대사·행동 후보를 제시;
- 역할의 정확한 이름·수·대화 순서·합성 구조는 구현 중 바뀔 수 있으나 역할별 정보 격리와
  다중 AI 협업이라는 방향은 유지;
- 각 역할은 자신에게 허용된 기억과 공유 가능한 역할 발언만 사용;
- 협업 결과는 복수 전개 후보와 인물별 반응을 제공하되 사용자 행동·정답 줄거리 강제 금지;
- 최종 합성 전 perspective·비밀·관계·세계 연속성을 검증하고 최종문 하나만 RisuAI에 표시;
- 공식 Host lifecycle에서 후처리 중간 초안과 표시 최종문을 구분하고, 후처리가 끝난 실제
  displayed final만 complete-turn·Critic·memory admission에 정확히 한 번 제출;
- 스트리밍·리롤·삭제·재생성에서도 1차 출력이나 중간 역할 발언이 원문으로 잘못 저장되거나
  평론가가 중복 호출되는 경우 0;
- turn coordinates, 1차 출력 식별값, 최종 출력 식별값과 terminal state를 가진 final receipt;
- 별도 플러그인 미사용 시 Archive Center base 기억·Publisher·본문 생성·저장·HUD 비퇴행;
- provider/role별 latency·cost·실패 단계와 raw private text 없는 실행 trace.

4.5는 4.9 고급 출판사의 역할 수나 감독 depth를 미리 구현하지 않는다. 4.9는
4.4~4.5의 동일 owner·handoff·fallback·finality 계약을 read-only로 확장해
`Recall Auditor→Director→Reviewer` plan을 전달하며, 두 번째 bridge나 guidance
경로를 만들지 않는다.

## 4.6 — 기반 계약·관계 graph·탐색 UI

- 3.5 Host Context와 4.0 memory read model을 소비해
  `simulation_snapshot.v1`, `narrative_execution_brief.v1` 경계를 확정한다.
- 인물·물건·장소·사건·개념과 source-backed relation assertion을 projection한다.
- 언급 후보, tentative link와 canonical node·relation assertion을 구분한다.
- source·시점·branch·knower·privacy·충돌·미확정 상태를 Go ViewModel UI에서
  탐색한다.
- 4.0 retrieval graph-neighborhood와 4.6 관계 graph/UI를 서로 대체하지 않는다.
- UI mutation은 canonical admission·revision·audit API를 우회하지 않는다.

4.6 기능 OFF에서는 3.5 Host Context와 4.0 memory payload·저장 결과가 그대로여야 한다.

## 4.7 — 인물·관계 실행 카드

- `character_execution_card.v1`을 구현한다.
- 3.9가 정본인 `voice_behavior_projection.v1`을 read-only로 소비한다.
- 인물별 지식·오해·비밀·목적·감정 원인·agency와 관계 방향·domain을 분리한다.
- `truth_status`, `assertion_kind`, `knowledge_path`, `epistemic_state`를 섞지 않는다.
- stable/current/dynamic profile, 관계별 태도와 evidence-bound change envelope를
  장면 카드에 투영한다.
- user/player 자동 우대, 자동 reciprocity, cross-domain 승격과 예시 대사 복사를
  차단한다.

3.9 관계 계약과 4.0 rollback parity가 실제 경로에서 검증되기 전에는 4.7을 완료로
표시하지 않는다.

## 4.8 — 세계·세력·thread 시뮬레이션

- `world_execution_slice.v1`에서 규칙·세력·자원·시간·공간·인과와 actor/faction의
  독립 목표·수단·발동 조건·대가를 선택한다.
- current input delta와 already-realized outcome을 분리해 replay와 summary echo를
  막는다.
- 모든 eligible thread의 selected/related/deferred 이유와 hold를 남긴다.
- foreground는 response/scene 범위의 짧은 focus lease다.
- 한 thread 해결을 sibling·parent·arc·session·작품 전체 closure로 확대하지 않는다.
- 사용자가 방향을 바꾸면 이전 thread를 강제로 되살리지 않는다.
- offscreen 변화는 bounded hypothesis이며 accepted depiction과 source path가 생기기
  전에는 canonical write하지 않는다.

## 4.9 — 모델 적응형 고급 출판사

- 4.0 Publisher의 endpoint·owner·strength·format·failure와 단일 guidance block을
  versioned extension으로 확장한다.
- `scene_guidance_proposal.v1`과 `model_capability_profile.v1`을 확정한다.
- 모델명 대신 관찰 가능한 구조화 성능·입력 한도·실패·비용 신호로 표현의 압축·
  명시성·호출 깊이를 조절한다.
- `none`은 base support를 유지하면서 Publisher 호출·plan·guidance를 0으로 둔다.
- `reviewed`는 Director plan을 필수 Reviewer가 승인·축소·거절한다.
- `deep`은 고정 eligible set에서 Recall Auditor→Director→필수 Reviewer를 실행한다.
- 각 역할은 새 기억·ref·visibility·예산·권한을 추가할 수 없다.
- Reviewer 실패·미실행·timeout·malformed·독립성 실패는
  `base_only`·`proposal_0`이며 Director 단독안을 적용하지 않는다.
- 같은 모델 재사용은 호출별 역할·입력·출력·source refs를 분리해 기록하되
  독립 검토 성공으로 과장하지 않는다.

## 5.0 — 출력 충실도와 실사용 release closure

- 3.5의 Host source→constraint→payload→displayed final evidence와 기존 HUD를
  소비한다.
- 4.9 `scene_guidance_proposal.v1`을 변경하지 않고 사전 plan으로만 읽는다.
- `output_fidelity_report.v1`은 먼저 diagnostic-only로 구현한다.
- 인물 혼동, 지식 누출, 관계 급변, 자동 상호성, replay, stagnation, thread tunnel
  vision, closure 누출, 문장 복사와 세계 규칙 위반을 검출한다.
- 사후 진단이 memory·relation·thread를 직접 수정하지 못하게 admission을 재검증한다.
- 안전한 Host draft 교체와 bounded 1회 repair/re-proof가 증명되기 전에는 자동
  수선을 활성화하지 않는다.
- 별도 플러그인은 5.0의 필수 의존성이 아니다. 다만 4.4 연동 전처리가 현재 요청을
  소유하면 Archive Center 출판사는 그 요청에서 자동 OFF가 되어야 한다.
- 능력 profile별 지원 OFF/ON 맹검, 첫 출력 채택률·리롤·비용·지연·설정 이행과
  관계·thread E2E correlation을 측정한다.
- 지원 OS별 시작·저장·업데이트·삭제와 실제 장기 session release evidence를 닫는다.

## 버전 간 의존 흐름

```text
3.8 time/state/perspective
  -> 3.9 relation/profile/voice + bounded Publisher error stability
  -> 4.0 composite recall + final injection + book_author/director Publisher
         + lifecycle/rebuild/live recovery
  -> [4.1~4.2 후보: 탐색 -> 정리]
  -> 4.3 role-specific story context + subjective memory
  -> 4.4 standalone/integrated preprocessor + Archive Publisher auto-OFF
  -> 4.5 supervisor/narrator/actor post-processing + displayed-final lifecycle
  -> 4.6 graph/execution foundation
  -> 4.7 character/relationship execution
  -> 4.8 world/faction/thread execution
  -> 4.9 adaptive advanced Publisher
  -> 5.0 output fidelity + live release closure
```

뒤 단계의 기능이 구현돼도 앞 단계 완료를 대신하지 않는다. 특히:

- 4.6 graph UI는 4.0 recall·lifecycle과 4.3 주관 기억을 완료시킨 증거가 아니다.
- 4.9 Reviewer는 memory truth·관계 admission과 5.0 output audit를 소유하지 않는다.
- 5.0 진단은 잘못된 3.9~4.8 입력을 사후 prompt로 고치는 대체 경로가 아니다.

## 공통 release 중단 조건

다음 중 하나라도 발생하면 해당 버전과 의존 후속 버전의 완료 선언을 중단한다.

- source·time·branch·generation·revision·knower·visibility·privacy 약화;
- vector·graph·모델 proposal·출력 유사도의 canonical authority 승격;
- 무관한 기억으로 K 또는 coverage를 채움;
- Publisher·Reviewer·Critic·private simulation 결과를 memory source로 저장;
- 같은 요청에 recall planner, Publisher owner 또는 guidance block이 둘 이상 존재;
- `none`이 기억·직접 근거·주관 기억·상태·secret guard까지 끔;
- redirection 뒤 이전 storyline·focus·plan을 재사용;
- mutation partial apply, rollback 뒤 stale projection 재노출;
- JavaScript가 ranking·selection·budget·lifecycle·orchestration을 계산;
- 선택적 LLM·embedding·graph·별도 플러그인 장애가 base memory를 막거나 이미 표시 가능한
  메인 응답을 유실시킴;
- source·fixture·문서 증거만으로 loaded/live release 완료 선언.

## 별도 후속과 비범위

- 독립형 원작 DB/DLC 분리와 연동은
  [`standalone-dlc-separation-roadmap.md`](standalone-dlc-separation-roadmap.md)가
  소유하며 현재 버전 미배정이다.
- Recomposer는 현재 문서상의 가칭일 뿐 확정 이름이 아니다. 이름·역할명·packet 이름은
  변경할 수 있지만 단독형 플러그인, Archive Center 연동형 전처리, RisuAI 로어북·캐릭터·
  페르소나와 Archive 기억의 역할별 배분, 1차 출력 기반 감독관·나레이터·연기자 협업과
  최종문 합성이라는 방향은 유지한다. 연동 전처리를 쓰는 요청에서는 Archive Center
  출판사를 자동 OFF하고, 플러그인을 쓰지 않는 사용자는 Archive Center 출판사를 그대로
  사용할 수 있어야 한다.
- 전체 RisuAI lorebook activation engine 대체, 전체 module mirror와 JavaScript
  backend는 이 로드맵의 목적이 아니다.
- 기억의 이미지·도표 변환과 proactive autonomous simulation은 별도 opt-in 연구이며
  5.0 기본 완료 조건이 아니다.

## 다음 결정

4.1~4.2를 확정하려면 각 후보에 대해 다음을 별도로 승인해야 한다.

1. 사용자 가치가 독립 release를 만들 만큼 충분한가;
2. 4.0 정본 owner를 중복하지 않는가;
3. 4.6 이후 simulation 기능을 앞당기지 않는가;
4. 새 backend contract·UI·DB migration이 실제 재현 요구로 필요한가;
5. 비활성 상태에서 앞 버전 payload·저장·HUD 결과가 같은가;
6. source test와 loaded/live evidence를 어디까지 release gate로 요구하는가.

승인 전까지 확정 구현 순서는 3.9→4.0→4.3→4.4→4.5→4.6→4.7→4.8→4.9→5.0이며,
4.1~4.2 후보는 계획 검토 상태로만 유지한다.
