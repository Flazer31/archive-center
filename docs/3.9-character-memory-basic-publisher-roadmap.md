# Archive Center 3.9 캐릭터 기억·출판사 안정화 로드맵

상태: `3.9-A~F source_implemented / automated regression verified / 3.9-G~H pending`.
Windows 개인 테스트 package는 생성됐지만 loaded RisuAI·real MariaDB·real Chroma와
장기 RP 품질 증거는 아직 수집 전이다. 구현·문서·개인 테스트 현황은

대상: 관계·습관·캐릭터 profile, 관계·인물별 기억 전달, 현재 bounded Publisher의
provider-neutral 오류 안정화

  [`3.6-4.1-precision-long-term-memory-roadmap.md`](3.6-4.1-precision-long-term-memory-roadmap.md)가

## 0. 결정

Archive Center를 장기 기억 저장소로만 제한하지 않는다. 3.9는 3.8까지 축적한
시간·상태·인물별 인식과 3.9의 관계·습관·profile을 현재 bounded Publisher가 이번 응답의
행동·말투·관계 태도와 장면 초점에 사용할 수 있게 한다. 다만 3.9에서는 현재 hint 계약을
`book_author + director`로 확대하지 않고, 재현된 provider 요청·응답·표시 오류를 수정하는
데서 출판사 범위를 끝낸다.

3.9가 유지할 기억 전달 체감은 다음과 같다.

- 사용자 설정 K 안에서 현재 요청과 직접 관련된 짧은 핵심 기억;
- 직전 확정 응답·현재 장면의 별도 continuity;
- 인물별 주관 기억과 관계·상태·profile의 분리;
- 본문 모델에 직접 전달되는 짧은 기억과 Publisher가 검토하는 제한 보조 표면의 분리;
- 기억을 설명문으로 반복하지 않고 행동·대사·subtext·pacing에 반영하는 bounded hint;
- 현재 응답과 장면 범위의 제한된 방향 유지.

1.0의 `book_author.current_arc/narrative_goal/next_beats/guardrails`와
`director.scene_mandate/required_outcomes/forbidden_moves/pressure_level`, 하나의 coherent
narrative-plan block과 서사 가이드 강도별 지휘는 4.0으로 이관한다.

다음 1.0 동작은 복원하지 않는다.

- 장기 storyline lock과 persistent beat queue;
- 사용자가 다른 이야기로 이동했는데 이전 arc로 강제 복귀;
- 사용자/player character의 행동·감정·대사 결정;
- 근거 없는 새 사건·갈등·관계 변화·폭로·화해·엔딩 생성;
- Publisher plan, 모델 합의 또는 검색 적중을 canonical truth로 사용.

## 1. 선행조건과 비퇴행 하한선

3.9는 다음 3.8 결과를 소비하며 다시 구현하지 않는다.

- `story_clock.v1`의 exact·partial·relative·unknown과 scene scope;
- current/history와 validity interval이 있는 신체·위치·소지·감정 상태;
- `perspective_memory.v1`의 known/suspected/unknown/misinformed/hidden/revealed;
- speaker·listener·owner·knower·visibility·privacy;
- correction·reveal·retract·reroll·delete·branch 뒤 source revision 재구축.

다음 3.7 결과도 그대로 유지한다.

- vector 후보 상한과 `core_objective_memory_delivery.v1`의 사용자-facing K 분리;
- 한 문장 compact memory와 UTF-8 rune·가능한 단어 경계;
- `none`에서 Supervisor/output guidance만 0이고 기억·직접 근거·비밀 guard는 유지;
- weak/medium/strong의 typed authority 차이;
- malformed/schema-invalid/valid-empty/unsupported/provider failure 구분;
- Go ViewModel이 소유하는 eligible/selected/deferred/deduplicated/delivered trace.

3.9는 위 의미를 넓히거나 다른 JavaScript fallback으로 복제하지 않는다.

## 2. 영구 소유권

- Go는 관계·습관·profile admission, Publisher input selection, support eligibility,
  prompt assembly, 예산, plan 검증, stale fence와 trace를 소유한다.
- `Archive Center.js`는 공식 RisuAI 관찰, backend 요청, backend가 만든 완전한 block의 실제
  payload 적용, displayed-final 관찰과 UI 렌더링만 담당한다.
- Publisher LLM은 response-shaping proposal만 만들며
  `truth_authority=false`, `canonical_write=false`,
  `relationship_authority=false`, `closure_authority=false`다.
- Critic은 final displayed output에서 다음-turn 기억 후보를 추출하는 별도 역할이며 현재
  Publisher plan을 소급 수정하지 않는다.
- 3.9는 두 번째 검색 DB, 두 번째 prompt assembler, 별도 JavaScript Director와 병렬
  Publisher owner를 추가하지 않는다.

## 3. 관계·습관·profile 계약

### 3.1 관계

`relationship_state.v1`은 최소한 다음 축을 분리한다.

- subject와 object의 방향;
- trust, boundary, attachment, rivalry, duty, fear, respect 등 domain;
- outward/inner 또는 public/private 표현;
- current와 history;
- change source, counterevidence와 uncertainty;
- reciprocity와 consent;
- temporary/contextual/stable 범위;
- branch, generation, revision과 validity interval.

한쪽의 친절·접촉·복종·구조·고백을 상호 관계 변화로 자동 복사하지 않는다. player/user를
무조건 우대하거나 하나의 호감도 score로 모든 domain을 평탄화하지 않는다.

### 3.2 습관

`habit_evidence.v1`은 반복 scope, source occurrence, 예외, 반례, 최근성, 상황과 상대를
보존한다. 한 번의 행동이나 모델이 만든 요약을 습관으로 승격하지 않고 고정 횟수 threshold만
통과했다는 이유로 영속 특성으로 만들지 않는다.

### 3.3 캐릭터 profile

`character_profile.v1`은 다음을 분리한다.

- stable: 장기 가치·욕구·두려움·모순과 source-backed 성향;
- current: 현재 감정·부상·피로·단기 목표와 장면 상태;
- dynamic: 관계·사건·상황에 따라 달라지는 표현;
- relationship-specific: 상대별 태도·경계·말투 변화;
- counterevidence와 아직 확정할 수 없는 영역.

직업·능력·외형·관심사·지위를 성격·도덕성·감정·말투로 무단 확장하지 않는다.

### 3.4 말투·행동 projection

`voice_behavior_projection.v1`은 예시 대사를 복사하지 않고 상대·상태·장면별 표현 원리,
문장 길이·완곡성·직접성·회피·호칭·행동 경향과 금지 추론을 source ref에 연결한다.

## 4. 기억 전달 표면

3.9는 기억을 하나의 무순서 덩어리로 합치지 않는다.

| 표면 | 내용 | 기본 수신자 |
|---|---|---|
| 핵심 객관 기억 K | 현재 요청과 직접 관련된 한 문장 사건 기억 | 본문 모델·Publisher |
| 직전 continuity | 직전 accepted assistant output과 아직 유효한 인과 | 본문 모델·Publisher |
| time/state | 현재 시각·장면 scope·위치·신체·소지·상태 | 본문 모델·Publisher |
| subjective/perspective | 현재 role이 알거나 의심·오해하는 내용 | 허가된 role·Publisher |
| relationship/profile | 현재 등장인물·상대에 관련된 관계·습관·profile·voice projection | 본문 모델·Publisher |
| world/reference/secret guard | 현재 적용되는 규칙·원작 근거·비밀·must-not-assert | 본문 모델·Publisher |
| Publisher support | 위 검사를 통과했지만 직접 K와 별도인 제한 보조 item | Publisher |

K가 10이고 적격 기억과 예산이 충분하면 관련 핵심 기억 10개를 전달한다. 적격 기억이
부족하거나 privacy·source·lifecycle·중복·예산 검사를 통과하지 못하면 무관한 기억으로
수를 채우지 않고 shortfall reason을 표시한다.

Publisher support는 검색 탈락 후보, raw private text, stale/superseded item과 현재
branch 밖 자료를 포함할 수 없다. Publisher가 support-only item을 실제 plan 근거로
선택하면 본문 모델의 기존 ref를 재사용하거나 예산 안에서 짧은 `guidance_support`로 함께
전달한다. 근거를 본문에 전달할 수 없으면 해당 지시도 폐기한다.

3.9는 relation/profile lane의 wrong-entity·wrong-counterpart·wrong-knower·stale projection을
차단하지만 전체 메모리의 exact·lexical·vector 복합 retrieval과 coverage completeness를
선결정하지 않는다. 그것은 4.0이 소유한다.

## 5. 현재 bounded Publisher 안정화

### 5.1 실행 흐름

```text
current input
  + core memory K
  + accepted previous continuity
  + time/state/perspective
  + relationship/habit/profile/voice
  + world/reference/secret/agency guard
  -> Go bounded Publisher input
  -> 기존 Publisher/Supervisor 경로 1회
  -> Go schema·ref·authority·budget·lifecycle 검증
  -> 단 하나의 output guidance block
  -> RisuAI main model
```

3.9에서는 별도 Recall Auditor와 필수 Reviewer를 호출하지 않는다. 기존 Publisher owner와
endpoint를 유지하고 provider별 요청 option은 기존 adapter에서만 변환한다. 문자열 content,
배열형 text content part와 `choice.text` 등 지원 provider의 정상 응답을 공통 text로 해석하며,
빈 content·malformed·schema-invalid·HTTP 오류·timeout은 구분된 실패로 표시한다. 자동 retry,
기본 directive fallback, provider별 병렬 출판사 경로와 `book_author + director` 역할 확대는
3.9에 추가하지 않는다.

### 5.2 허용 plan

기본 Publisher는 다음 response-scoped 항목만 제안할 수 있다.

- `response_focus_refs`;
- `must_account_refs`;
- `continuity_anchor_ref`;
- 현재 관계·profile에 맞는 `character_expression_refs`;
- `relationship_expression_refs`;
- `world_guard_refs`;
- `must_not_refs`;
- medium 이상에서 Go가 미리 승인한 `may_advance` 하나 또는 `hold_allowed`;
- strong에서 current user turn이 계속 선택한 thread의 response/scene 범위
  `preferred_frontier_ref`와 표현상 `ending_edge`.

plan은 source ref가 없는 자유문 새 사건을 만들 수 없다. `ending_edge`는 이번 응답을
자연스럽게 끊는 표현 힌트이며 thread·arc·session·작품 closure가 아니다.

### 5.3 강도

| strength | Publisher 동작 | 금지 |
|---|---|---|
| `none` | Publisher 호출·plan·guidance 0 | 기억·직접 근거·비밀 guard를 함께 끄기 |
| `weak` | response focus, must-account, continuity와 인물 표현 | 새 beat·관계 변화·장면 이동 |
| `medium` | weak + 승인된 may-advance 또는 hold, pacing·callback | envelope 확대·parked story 자동 복귀 |
| `strong` | medium + 사용자가 계속 선택한 thread의 짧은 scene focus | persistent plot lock·새 complication·자동 closure |

명시적 redirection은 같은 요청에서 이전 focus·frontier·arc 의존 plan을 해제한다. 침묵,
짧은 반응, 빈 입력과 단순 비반대는 이전 storyline 유지 동의가 아니다.

### 5.4 실패

- Publisher 없음·skip·timeout·provider failure·malformed·schema-invalid이면 base memory와
  constraint만 사용한다.
- 이전 성공 plan, default guidance prose, 부분 plan과 더 넓은 support set을 fallback으로
  사용하지 않는다.
- Publisher 실패는 기억 검색·주입, main generation, complete-turn과 저장을 막지 않는다.
- 실패 뒤 strength·visibility·eligible support·K·문자 예산이 넓어지지 않는다.

## 8. 출시 중단 조건

다음 중 하나라도 발생하면 3.9 출시를 중단한다.

- 3.8 time/state/perspective의 source·knower·privacy 의미 약화;
- Publisher 기능 때문에 핵심 기억 K나 메인 기억 문자 예산 감소;
- 관계·profile·Publisher proposal의 canonical truth·relationship write 승격;
- 같은 turn에 기존 output guidance와 새 Publisher block이 중복 적용;
- JavaScript가 relation/profile 선택, strength, plan 또는 budget을 계산;
- `none`이 base memory·direct evidence·secret guard까지 비활성화;
- Publisher failure가 main response를 막거나 이전 plan을 재사용;
- 사용자 redirection보다 과거 storyline·momentum을 우선;
- 실제 RisuAI payload와 displayed output 증거 없이 완료 선언.

## 9. 다음 버전으로의 인계

3.9는 4.0에 stable entity·time·knower·relation·profile metadata와 Publisher가 실제 사용한
ref lineage, 현재 단일 owner·endpoint·strength·failure 계약을 제공한다. 4.0은 이를 이용해
복합 retrieval과 coverage를 개선하고 `publisher_plan.v2`의 `book_author + director`
일관된 서사 계획으로 확장한다.

3.9 bounded Publisher는 4.0 역할 복구 전에도 오류 없이 독립적으로 작동해야 한다. 4.0
cutover 뒤에는 같은 owner가 새 계약을 사용하며 두 계획 경로를 동시에 적용하지 않는다.
후속 계층은 이 경로를 병렬 복제하지 않고 versioned extension으로만 확장한다.
