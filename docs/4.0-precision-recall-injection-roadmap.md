상태: `planned` — 3.9 release gate 이후 구현

대상: 복합 기억 검색, coverage-aware recall, 핵심 기억 K, 최종 injection plan과 delivery
lineage, 1.0 방향의 provider-neutral `book_author + director` 출판사 복구,
고정 분기 기억 범위와 2차원 세계선 UI, edit/delete/reroll/branch/rebuild, 장애 복구와
실환경 release closure

정본 관계:

- 3.9 관계·profile과 현재 bounded Publisher의 오류 안정화는
  [`3.9-character-memory-basic-publisher-roadmap.md`](3.9-character-memory-basic-publisher-roadmap.md)가
  소유한다.
- 4.0의 검색·선택·최종 주입, item별 전달 증명, 기존 단일 Publisher owner의
  `book_author + director` 역할 복구와 그 결과의 전체 수명주기·복구·실환경 검증은
  이 문서가 함께 소유한다.
- 기억 Locator·계층 탐색은 4.1, 검토형 정리·되돌리기는 4.2가 소유한다.
- Archive 기억과 RisuAI 로어북·캐릭터·페르소나의 역할별 문맥 및 인물별 주관 기억 강화는
  4.3, 이름 미확정 별도 플러그인의 연동 전처리·Archive Publisher 자동 OFF·감독관·
  나레이터·연기자 후처리와 최종문 lifecycle은 4.4~4.5가 소유한다.
- 분기 topology와 활성 조상 경로를 표시하는 세계선 UI는 4.0이 소유한다. 관계·개체의

- 인물·세계·thread simulation은 4.7~4.8이며, 4.9는 4.0 출판사
  위에 Recall Auditor·Director·Reviewer 다단계 검토를 확장한다.
  [`4.6-5.0-model-adaptive-rp-publishing-roadmap.md`](4.6-5.0-model-adaptive-rp-publishing-roadmap.md)가

## 0. 결정

4.0은 기억 개수를 무조건 늘리는 버전이 아니다. 현재 질문에 필요한 사건·발언·상태·관계·
주관 기억을 source·time·entity·knower·branch·revision과 함께 찾고, 사용자-facing 핵심
기억 K와 별도 지원 lane을 정확한 예산 안에서 최종 payload로 조립하는 버전이다.

기존에 4.1로 분리했던 수명주기·복구·실환경 gate는 4.0 후반부로 합친다. 따라서 4.0은
기억을 잘 찾고 주입하는 데서 끝나지 않는다. 그 결과가 수정·삭제·리롤·분기·재시작,
DB/Vector 장애, 재색인과 패키지 업데이트 뒤에도 같은 accepted source를 가리킨다는 것까지
증명해야 완료된다.

### 0.1 4.0 내부 실행 분할

분기·세계선은 4.0에서 빼서 별도 후속 버전으로 미룰 기능이 아니다. 최종적으로 어느 기억을
볼 수 있는지 결정하는 4.0 정확성 계약에 속한다. 다만 기존 기억·출판 구현과 한 번에 섞지
않는다. 먼저 단일 활성 session 기준의 기억·출판·수명주기 owner를 완성하고, 그 owner를
바꾸지 않은 채 분기 범위를 마지막에 연결한다.

| 작업선 | 범위 | 구현 순서 |
|---|---|---|
| 4.0 핵심 기억·출판 | requirement, 검색, 선택, 최종 주입, Publisher, 비분기 lifecycle·복구·실환경 core gate | `4.0-A~N`을 먼저 작은 packet별로 검증 |
| 4.0 분기·세계선 | host 분기 발견, 고정 source membership, branch projection, SQL/Vector 격리, ViewModel, 무한 캔버스 UI | core gate 뒤 `4.0-BR-A~H`를 데이터 계약부터 UI 순서로 검증 |

두 작업선은 병렬 구현하지 않는다. 핵심 검색 owner가 확정된 뒤 분기 가시성 필터를 그 owner에
연결하고, SQL·Vector 격리가 증명된 뒤에만 세계선 UI를 붙인다. UI부터 만들거나 기존 검색과
별도의 분기 검색기를 만들지 않는다. 4.0 공개 완료는 두 작업선의 출시 중단 조건이 모두 닫힌
때에만 선언한다.

### 0.2 전체 구현 순서

| 순서 | 작업 묶음 | 완료 기준 |
|---:|---|---|
| 1 | 3.9 기준선과 4.0 입력·출력 계약 고정 | 현재 정상 턴·평론가·Publisher·저장·리롤·삭제 기준선과 변경 금지 범위 기록 |

각 순서는 앞 단계의 owner와 회귀가 고정된 뒤에만 시작한다. 11~14번을 앞당기지 않으며,
세계선 UI는 4.0에서 마지막으로 구현하는 사용자 기능이다. 15번은 새 기능 구현이 아니라
전체 산출물·실환경 증거를 묶는 최종 관문이다.

3.7-F의 `core_objective_memory_delivery.v1` 의미와 UI를 다시 만들지 않는다.

- vector `topK`는 후보 검색 상한이다.
- `core_objective_memory_max_items`는 최종 핵심 객관 기억 K다.
- K가 10이고 적격 기억·예산이 충분하면 관련 핵심 기억 10개를 전달한다.
- 적격 기억이 부족하면 무관한 item으로 채우지 않고 coverage gap을 표시한다.

4.0은 현재의 조각난 response hint를 최종형으로 고정하지 않는다. 기존 단일 Publisher
owner와 호출 경로를 유지하면서 1.0의 `book_author + director` 역할과 일관된 서사 계획
block을 복구한다. recall 결과와 delivery lineage는 Publisher와 본문 모델이 공유하며,
강압성은 별도 기능이나 provider 분기가 아니라 4.0의
`none/weak/medium/strong/extreme/maximum` 서사 가이드 강도로 조절한다.

3.9 개인 테스트에서 관찰된 다음 항목은 입력·기억·본문 전달을 중단시키지 않는 비치명
정밀도 문제로 분류하며 3.9 출시 중단 조건으로 삼지 않는다.

- 같은 인물쌍의 상세형·축약형 `relationship_state`가 한 payload에 함께 전달되는 중복은
  `4.0-D`에서 정리한다.
- Publisher continuity 안내가 현재 accepted scene보다 이전 단계로 되돌아가는 문제는
  `4.0-E`에서 현재 scene/time 좌표와 최종 guidance를 대조해 막는다.

## 1. 소유권과 비범위

- Go는 query requirement, hard filter, retrieval fanout, hydration, dedupe, coverage,
  selection, compression, budget과 최종 block assembly를 소유한다.
- MariaDB는 canonical source·memory authority이고 Chroma는 재구축 가능한 후보 index다.
- JavaScript는 RisuAI observation과 Go가 만든 injection plan의 실제 payload 적용만 담당한다.
- similarity, graph edge, selected/delivered/co-fired/response-similar 상태는 truth,
  importance, merge, relation, closure와 canonical write 권한이 아니다.
- 4.0은 분기 topology용 세계선 UI는 구현하지만 전체 관계·개체 의미 graph UI, semantic merge
  자동화, 캐릭터 simulation, Publisher 다층 호출과 원작 DB 독립화는 구현하지 않는다.

## 2. Query requirement

Go는 current input과 accepted state에서 질문별 requirement를 만든다.

- 사건·원인·결과;
- 특정 발언·약속·물건·장소·날짜;
- 현재와 과거 상태;
- 인물별 known/suspected/misinformed/hidden;
- 특정 상대와 domain의 관계;
- 습관·profile·말투 근거;
- unresolved thread와 이미 실현된 outcome;
- 현재 장면 continuity와 explicit reentry;
- 원작·Host Context·로어북 reference가 필요한 차원.

짧은 입력, 의미 없는 입력과 재개 요청도 무조건 넓은 최근 기록을 넣지 않는다. current
input에 명시 신호가 부족하면 직전 accepted scene, 현재 인물·상태와 open obligation 안에서
bounded continuity query를 만들고 부족함을 추적한다.

## 3. 검색 파이프라인

```text
current request requirement
  -> MariaDB hard filter
  -> exact ID·source·quote·date lookup
  -> lexical/full-text
  -> vector candidate
  -> source-backed relation·thread neighborhood
  -> Go hydration
  -> lifecycle·privacy·knower·authority validation
  -> semantic/source dedupe
  -> coverage-aware selection
  -> memory_delivery_plan.v1
  -> payload_application_plan.v1
```

### 3.1 Hard filter

후보 검색 전에 다음이 current scope와 일치해야 한다.

- session과 Host chat binding;
- branch, logical/source turn, generation과 revision;
- active-final/source acceptance와 tombstone/superseded 상태;
- entity와 speaker identity;
- story time, scene scope와 validity interval;
- knower·visibility·privacy·reveal ceiling;
- objective/belief/proposal/uncertain authority;
- source hash와 dependency generation.

필수 좌표가 unknown이면 더 넓은 후보로 완화하지 않고 해당 dimension을
`unavailable/degraded`로 보고한다.

### 3.2 검색 lane

1. exact source/ID/quote/date/entity;
2. lexical/full-text;
3. vector semantic 후보;
4. 기존 source-backed relation·thread edge의 bounded neighborhood;
5. hierarchy zoom;
6. 선택적으로 승인된 reference provider.

embedding 또는 Chroma가 없어도 exact·lexical·recent accepted continuity는 작동해야 한다.
vector/graph 장애는 후보 폭만 줄이고 truth·privacy·K·예산을 넓히지 않는다.

### 3.3 중복

동일 source occurrence, 동일 atomic meaning과 한 항목의 raw/summary/derived 표현은 의미
중복으로 합치되 source provenance를 잃지 않는다. 서로 다른 인물·knower·time·branch의
유사 문장을 같은 사실로 병합하지 않는다.

같은 방향의 인물쌍과 domain을 가리키는 관계 상태의 상세형·축약형 projection은 한 delivery
group으로 묶고, 현재 scope에서 가장 구체적인 표현 하나만 전달하되 retained source refs는
보존한다.

## 4. `memory_recall_plan.v1`

plan은 최소한 다음을 구분한다.

- requirement와 query seed;
- eligible·selected·deferred·excluded item;
- source/ref, memory kind와 delivery class;
- entity·time·knower·visibility·authority·lifecycle;
- retrieval lane과 score가 아닌 selection reason;
- dedupe group과 retained source refs;
- coverage dimension과 gap reason;
- requested K, eligible K, selected K와 delivered K;
- lane별 문자·item 예산;
- degraded dependency와 fallback owner;
- plan ID/hash, request/branch/generation/revision fence.

selected는 delivered가 아니다. 최종 compaction·예산·payload 적용 뒤 실제 delivered item과
hash를 다시 확정한다.

## 5. 기존 최종 전달 계약 유지

4.0-E는 새 `memory_injection_plan.v2`를 만들지 않는다. 현재 Go가 소유하는
`memory_delivery_plan.v1`과 `payload_application_plan.v1`을 그대로 사용한다. 4.0-A~D에서
확정한 검색·선택·중복 정리·예산·최종 전달문을 출판사 작업 때문에 다시 계산하거나 다른
계약으로 우회하지 않는다.

- Publisher 입력은 본문 모델에 실제 전달되는 기억과 같은 delivery lineage에서 만든다.
- Publisher 결과는 기존 output-guidance 소유자가 허용한 위치에 정확히 한 block만 추가한다.
- Publisher용 지원 자료가 핵심 객관 기억 K, 직접 근거, 주관 기억, 상태와 비밀 경계의
  선택·순서·문자 예산을 바꾸지 않는다.
- JavaScript는 Go가 만든 `payload_application_plan.v1`을 실제 RisuAI payload에 적용할 뿐,
  출판사 계획을 재조립하거나 강도·형식을 다시 계산하지 않는다.
- 기존 전달 계약 자체를 바꿔야 하는 재현된 결함이 나중에 발견되면 Publisher E와 분리된
  별도 작업으로 승인한다.

## 6. 1.0 출판사 역할 복구와 최종 전달

### 6.1 단일 owner와 역할 계약

4.0은 별도 출판사나 두 번째 guidance 경로를 만들지 않고 현재 Go Publisher owner를
`publisher_plan.v2`로 교체한다. 기존 내부 호환 envelope `supervisor_scene_proposal`은
유지할 수 있지만 실제 plan은 다음 두 역할을 하나의 호출과 하나의 검증 단계에서 반환한다.

- `book_author`: `current_arc`, `narrative_goal`, `next_beats`, `guardrails`;
- `director`: `scene_mandate`, `required_outcomes`, `forbidden_moves`, `pressure_level`.

#### 6.1.1 `publisher_plan.v2` 제공자 출력 계약

`E-1`은 다음 JSON을 출판사 LLM이 반환해야 하는 유일한 역할 출력 계약으로 확정한다.
E-1 계약 확정 당시에는 v1 호출·파서·본문 전달 경로를 v2로 부분 활성화하지 않았다. v2를 옆에
붙이는 shadow·fallback·legacy 변환 경로도 만들지 않았다. 이후 `E-2~E-5`가 입력, 단일 호출,
검증과 본문 block을 모두 연결한 뒤 기존 owner를 한 번에 교체했다.

```json
{
  "supervisor_scene_proposal": {
    "publisher_plan": {
      "contract_version": "publisher_plan.v2",
      "book_author": {
        "current_arc": null,
        "narrative_goal": null,
        "next_beats": [],
        "guardrails": []
      },
      "director": {
        "scene_mandate": null,
        "required_outcomes": [],
        "forbidden_moves": [],
        "pressure_level": null
      }
    }
  }
}
```

`current_arc`, `narrative_goal`, `scene_mandate`는 `null` 또는 다음
`source_linked_text` 하나다. `next_beats`, `guardrails`, `required_outcomes`,
`forbidden_moves`는 같은 항목의 배열이다.

```json
{
  "text": "short response-scoped guidance",
  "source_refs": ["exact allowed source ref"]
}
```

`pressure_level`은 `null` 또는 다음 구조다. 이 값은 장면 압력의 표현 방식이며 서사 강도
설정이 아니다.

```json
{
  "level": "quiet|low|medium|high",
  "text": "how pressure should be expressed in this response",
  "source_refs": ["exact allowed source ref"]
}
```

계약 규칙은 다음과 같다.

- 여덟 역할 필드는 모두 존재해야 한다. 지원이 없으면 단일값은 `null`, 배열은 `[]`를
  출판사가 직접 반환하며 Go가 누락값을 채우지 않는다.
- 값이 존재하는 모든 항목은 공백이 아닌 `text`와 하나 이상의 정확한 `source_refs`를
  가져야 한다. ref는 `E-2`가 허용한 현재 입력 또는 실제 delivered 자료의 ref를 그대로
  복사하며 이름·본문·유사도로 새 ref를 만들지 않는다.
- `current_arc`는 현재 응답을 이해하기 위한 가까운 arc framing이지 storyline 정본 갱신이
  아니다. `narrative_goal`은 이번 응답이 향할 가까운 목적이며 결말이나 사용자 행동을
  확정하지 않는다.
- `next_beats`는 되돌릴 수 있는 후보이고 의무 전개가 아니다. `guardrails`는 원문·현재
  장면·인물 지식·관계·세계 규칙을 어기지 않기 위한 표현 경계다.
- `scene_mandate`는 이번 응답에서 무엇을 보여줄지 정하지만 어떤 사건이 실제로 일어났다고
  선언하지 않는다. `required_outcomes`는 이번 응답에 드러나야 할 관찰 가능한 표현·정보
  반영이며 관계 변화, 사건 해결이나 새 사실의 발생을 뜻하지 않는다.
- `forbidden_moves`는 현재 응답의 금지 표현·진행이고 canonical 차단 규칙을 새로 쓰지
  않는다. `pressure_level`은 긴장 표현의 정도일 뿐 강제 진전, 갈등 격화나 장면 이동 권한이
  아니다.
- 제공자 출력에는 `status`, `authority`, `truth_authority`, `would_write`, `reason_code`를
  넣지 않는다. 이 값은 E-4의 strict 검증 뒤 Go가 소유한다. 검증된 plan의 authority는
  `response_scoped_proposal_only`, `truth_authority=false`, `would_write=false`로 고정한다.
- 두 역할 모두 사용자·주인공 행동 결정, 새 사실·감정·지식 생성, 관계 변화 확정, 미해결
  사건 종료, 장면 이동, 세계·storyline·memory canonical write 권한이 없다.
- `supervisor_scene_proposal.publisher_plan`이 객체가 아니거나 계약 버전이 정확한
  `publisher_plan.v2`가 아니면 plan 전체를 `publisher_schema_invalid`로 거부한다.
- `book_author`와 `director`가 모두 없거나 객체가 아니어서 어느 역할도 읽을 수 없을 때도
  `publisher_schema_invalid`다. 한 역할만 정상이라면 잘못된 역할만 거부하고 정상 역할을 계속
  검증한다.
- 여덟 역할 필드는 제공자 계약상 모두 존재해야 하지만, 한 필드의 누락이나 기본 container 타입
  오류 때문에 다른 정상 필드까지 폐기하지 않는다. 해당 필드만 거부하며 Go가 누락값을
  `null`·`[]`로 채우지 않는다.
- 개별 `source_linked_text` 또는 배열 항목의 text·ref·level이 잘못된 경우에도 그 항목만 거부하고
  다른 정상 항목을 유지한다. 알 수 없는 추가 필드는 사용하지 않고 경로만 trace에 기록한다.
  이는 값을 고치거나 구형 형식을 변환하는 fallback이 아니며, 거부한 단일값을 `null`로 바꾸어
  제공자 출력 전체가 정상인 것처럼 가장하지 않는다.
- JSON 수리, 기본 directive, 누락값 보충, v1 hint 변환, 잘린 JSON 복구는 하지 않는다.
- 배열 개수, 글자 수와 beat 수를 E-1에서 고정 상수로 정하지 않는다. 실제 포함 범위는 E-4의
  승인 결과와 기존 최종 예산 owner가 결정한다. E-6 strength와 E-7 format은 승인 항목을
  추가·삭제·축약하지 않으며 관련 항목을 채우기 위한 filler도 만들지 않는다.

여기서 `director`는 4.0의 단일 호출 안에 있는 장면 지휘 필드다. 4.9의 별도
Director·Reviewer 단계와 같은 추가 LLM 호출을 뜻하지 않는다. 4.9는 이 계약을 교체하거나
병렬 구현하지 않고 명시적으로 선택된 다단계 검토만 같은 owner에 확장한다.

현재 런타임의 `publisher_plan.v1`과 조각난 `supervisor_scene_proposal`을 유지한 채 옆에
두 번째 v2 경로를 붙이지 않는다. E 작업에서 기존 owner를 한 번에 교체하고, 같은 요청에
Publisher 호출·plan·본문 guidance block이 각각 하나를 넘지 않게 한다.

|---|---|---|
| `E-1` | `publisher_plan.v2` 역할·필드·권한 계약 | `book_author`와 `director`가 response-scoped proposal 하나에 존재하고 canonical write 0 |
| `E-2` | 출판사 입력 연결 | 현재 입력 전체, accepted continuity, 실제 delivered 기억·인물·관계·상태·세계·thread만 사용하고 미전달 후보·raw private memory·전체 과거 채팅 0 |
| `E-3` | 단일 호출 | 두 역할을 한 요청에서 생성하며 retry·두 번째 Publisher·JavaScript 호출 0 |
| `E-4` | 응답 정규화·검증 | 지원 provider의 text container를 공통 텍스트로 정규화한 뒤 Publisher 전용 strict parser로 현재 schema만 승인하고 JSON 수리·기본값 채움·legacy schema 변환·숨은 성공 0 |

| `E-7` | 입력 표현 형식 | `compact/standard/explicit`이 강도와 독립적으로 같은 plan 의미를 표현 |
| `E-8` | source 회귀 | 호출·block 중복 0, current input 우선, 조용한 장면 강제 진행 0, 비밀 원문 노출 0, 실패 시 fabricated guidance 0, reroll/delete stale plan 0, JS 정책 증가 0 |

#### 6.1.2.1 E-4 응답 정규화·검증 계약

E-4의 `strict`는 사소한 항목 오류 하나로 정상 계획 전체를 버린다는 뜻이 아니다. 제공자 응답,
JSON과 v2 계약 외곽에는 엄격하고, 그 안의 역할·필드·개별 계획 항목은 서로 독립적으로 검증한다.

처리 순서는 다음 하나뿐이다.

1. **제공자 container 정규화**
   - 첫 번째 choice만 읽으며 문자열 `message.content`를 그대로 사용한다. 추가 choice를 합치거나
     다른 choice에서 성공값을 찾지 않고 개수만 trace에 남긴다.
   - `message.content`가 배열이면 각 part의 문자열 `text`만 원래 순서대로, 새 문자를 끼우지 않고
     연결한다.
   - 첫 번째 choice의 message에서 텍스트를 얻지 못했을 때만 같은 choice의 문자열 `choice.text`를
     사용한다. `message.content`가 없거나 `null`, 지원되는 문자열·배열이지만 비어 있는 경우에만
     이 대체 읽기를 허용하며, 지원하지 않는 타입이 들어온 경우에는 `choice.text`로 우회하지 않는다.
   - 생각·도구 등 text가 없는 part는 내용으로 추측하지 않고 건너뛰되 개수만 trace에 남긴다.
   - 지원하지 않는 container 타입은 `publisher_response_container_invalid`, 텍스트가 전혀 없으면
     `publisher_llm_empty_content`다.
2. **단일 JSON 객체 확인**
   - 전체 응답을 감싼 JSON code fence 하나만 제거할 수 있다.
   - 설명문 속 `{...}`만 뽑지 않고, 앞뒤 문장·두 번째 객체·trailing token을 허용하지 않는다.
   - JSON을 그대로 한 번 읽으며 실패하면 `publisher_json_malformed`다. 따옴표·괄호·잘린 JSON을
     수리하지 않는다.
   - 같은 객체 안의 중복 key는 마지막 값으로 덮어쓰지 않고 `publisher_json_malformed`로 거부한다.
3. **계약 외곽 확인**
   - `supervisor_scene_proposal.publisher_plan` 객체와 정확한 `publisher_plan.v2` 계약 버전을
     확인한다. 이 외곽이 없거나 틀리면 plan 전체가 `publisher_schema_invalid`다.
   - `book_author`와 `director`가 모두 읽을 수 없는 경우도 전체 schema 오류다. 한 역할만 정상인
     경우에는 정상 역할을 유지하고 결과를 `partial` 또는 `publisher_plan_no_valid_items`로
     분류한다.
   - v1 hint, `directive` wrapper, 예전 필드명은 변환하지 않는다.
4. **역할 필드와 개별 항목 확인**
   - 여덟 역할 필드의 존재와 기본 타입을 각각 확인한다. 누락되거나 타입이 틀린 필드는 그 필드만
     거부하고 값을 채우지 않는다.
   - 각 항목은 공백이 아닌 문자열 `text`와 하나 이상의 문자열 `source_refs`를 가져야 한다.
   - ref 전체가 E-2의 정확한 허용 목록에 있어야 하며 하나라도 틀리면 해당 항목 전체를 거부한다.
     이름·본문·유사도로 ref를 보정하지 않는다.
   - `pressure_level.level`은 `quiet/low/medium/high`만 허용한다.
   - 잘못된 배열 항목이나 단일값 항목은 각각 독립적으로 거부하며 다른 정상 항목은 유지한다.
     거부 경로와 사유만 기록하고 원문 text나 비공개 자료는 오류 응답에 복사하지 않는다.
   - 허용 ref 목록은 `supervisor_support_packet.v2`에서 실제 text와 함께 존재하는 현재 입력,
     accepted recent context, delivered memory·character memory·context 항목으로만 만든다.
     `response_execution_contract.source_refs.all`이나 text가 제공되지 않은 `native_system` ref를
     목록에 추가하지 않는다.
5. **검증 결과 분류**
   - `ready`: 두 역할과 여덟 필드가 모두 존재하고 타입이 맞으며 모든 사용 항목이 유효함.
   - `valid_empty`: 두 역할과 여덟 필드가 모두 정상이며 출판사가 직접 모든 단일값을 `null`,
     배열을 `[]`로 반환함.
   - `partial`: v2 외곽은 정상이고 하나 이상의 유효 항목이 있지만 한 역할·필드·항목 또는 추가
     필드를 거부함.
   - `publisher_plan_no_valid_items`: v2 외곽은 읽을 수 있지만 완전한 명시적 빈 plan도 아니고
     승인된 항목도 없음. 이를 `valid_empty`나 성공으로 바꾸지 않는다.
   - container·empty·JSON·schema 실패는 각각 위 stable code를 유지한다.

모든 실패와 `partial`에서 메인 본문 요청과 E-2의 기억 전달은 계속된다. 출판사 계획만 적용하지
않거나 승인된 항목만 E-5에 넘긴다. 자동 재호출, 이전 성공 plan 재사용, 기본 plan 생성,
provider별 Publisher 분기, 별도 JavaScript 검증은 없다. 배열 개수·문자 수·beat 수를 E-4에서
고정하지 않으며 최종 출력 예산은 기존 Go owner가 담당한다. E-5는 승인 목록을 단일 block으로
컴파일하고 E-6·E-7은 각각 지시 명시성과 표현 구조만 결정한다.

`partial` 결과는 거부된 단일값을 `null`로 덮어쓴 새 provider plan을 만들지 않는다. E-4는
검증된 항목마다 역할, 필드, 원래 배열 순서, text, 승인된 source ref와 pressure level만 담은
Go 내부 승인 목록을 만든다. 거부 목록에는 역할·필드·배열 위치와 안정적인 사유 code만 남기며
text는 넣지 않는다. E-5는 raw provider map이나 거부 항목을 다시 읽지 않고 이 승인 목록만
컴파일한다. 따라서 부분 승인은 값을 수리한 것이 아니고, 유효성이 독립적으로 확인된 항목만
전달한 결과다.

거부 사유 code는 최소한 `role_missing`, `role_type_invalid`, `field_missing`,
`field_type_invalid`, `item_type_invalid`, `text_empty`, `source_refs_missing`,
`source_ref_invalid`, `pressure_level_invalid`, `unknown_field`를 구분한다. trace에는 container 종류,
choice·text part 수, 승인·거부 수와 거부 경로·code만 기록하며 provider 원문과 항목 text는 넣지
않는다. 이 trace는 current request 진단값이며 canonical DB write가 아니다.

E-4는 strength에 따라 어떤 역할 필드를 표시할지, 항목을 몇 개 사용할지, 최종 문장을 얼마나
길게 만들지를 결정하지 않는다. 유효성만 판정하며 E-5 단일 renderer가 승인 순서를 보존하고,
E-6 strength와 E-7 format은 그 승인 목록을 변경하지 않는다. 최종 예산은 기존 Go owner가 담당한다.

E-4 validator의 활성화는 E-5 renderer와 같은 변경에서 수행했다. v1 parser를 유지한 채
옆에 실행 가능한 v2 parser를 추가하거나, v2 실패 시 v1으로 되돌아가는 경로는 만들지 않았다.

E-4 구현 회귀는 다음 판정표를 그대로 증명해야 한다.

| 제공자 응답 | E-4 결과 | E-5로 전달되는 것 |
|---|---|---|
| 문자열 content의 완전한 v2 JSON | `ready` | 검증된 전체 항목 |
| 배열 content의 여러 text part에 나뉜 완전한 v2 JSON | `ready` | 원래 순서로 연결·검증된 전체 항목 |
| message에 text가 없고 `choice.text`에만 완전한 v2 JSON이 있음 | `ready` | 검증된 전체 항목 |
| 지원하지 않는 content container | `publisher_response_container_invalid` | 없음 |
| 정규화 뒤 빈 문자열 | `publisher_llm_empty_content` | 없음 |
| JSON 하나를 감싼 code fence | 내용에 따른 `ready/valid_empty/partial` | 검증 결과에 따른 항목 |
| 설명문과 JSON 혼합, JSON 두 개, trailing token, 잘린 JSON | `publisher_json_malformed` | 없음 |
| plan 객체 누락·계약 버전 불일치·두 역할 모두 해석 불가 | `publisher_schema_invalid` | 없음 |
| 한 역할 또는 역할 필드가 누락·타입 오류이고 다른 유효 항목이 있음 | `partial` | 유효 항목만 |
| v2 외곽은 정상이나 누락·타입 오류·잘못된 항목뿐이고 승인 항목이 없음 | `publisher_plan_no_valid_items` | 없음 |
| 유효 항목과 잘못된 항목이 함께 있음 | `partial` | 유효 항목만 |
| 비어 있지 않은 항목이 모두 잘못됨 | `publisher_plan_no_valid_items` | 없음 |
| 모든 단일값을 `null`, 배열을 `[]`로 명시함 | `valid_empty` | 빈 plan |
| 알 수 없는 추가 필드와 정상 항목이 함께 있음 | `partial` | 추가 필드를 제외한 정상 항목 |
| 알려진 여덟 필드는 모두 비어 있고 알 수 없는 필드만 있음 | `publisher_plan_no_valid_items` | 없음 |

각 행은 출판사 요청 횟수 1회, JSON 수리 0회, v1 변환 0회, 이전 plan 재사용 0회,
기본 plan 생성 0회를 함께 검증한다. `partial` 회귀는 거부된 항목의 text·비공개 원문을 trace와
오류 응답에 싣지 않고, 승인된 항목의 정확한 E-2 ref와 순서가 그대로 유지되는지도 확인한다.

E-4·E-5 교체에서 제거하거나 바꾼 지점은 다음과 같다.

- 공용 `chatCompletionText`와 OpenAI 계열의 empty-content 판정은 현재 배열형 content를 읽지
  못한다. E-4의 container 정규화가 empty 판정보다 먼저 실행되도록 기존 추출 owner를 고친다.
- 현재 `parseJSONFromLLMContent`는 Critic을 위해 객체 부분 추출, 잘린 JSON 닫기와 여러 수리를
  수행한다. 이 공용 함수를 엄격하게 바꾸지 않고, Publisher 호출 지점만 수리 없는 전용 판정을
  사용한다. Critic 파서 동작은 E-4에서 변경하지 않는다.
- 현재 malformed·schema 실패가 `zeroPublisherPlan`을 생성하는 v1 경로는 v2 실패에 재사용하지
  않는다. v2 실패에는 plan과 승인 목록이 없고 typed failure만 남는다.
  guide disabled·입력 부족·미설정처럼 LLM을 호출하지 않은 경우도 만들어낸 빈 v2 plan 대신
  호출하지 않았다는 기존 상태만 남긴다.
- `prompts/supervisor_system.txt`, 파일을 읽지 못했을 때의 builtin prompt와 `required_output`을
  같은 `publisher_plan.v2` 계약으로 교체해 prompt와 parser가 다른 중간 상태를 만들지 않았다.
- `/supervisor` 응답 판정, prepare-turn 상태 switch, HUD fact와 renderer를 E-4의
  `ready/valid_empty/partial` 및 각 실패 code와 E-5 승인 목록 소비로 같은 변경에서 교체했다.

HUD와 workflow 판정은 출판사 결과와 턴 전체 결과를 분리한다. `ready`는 정상 전달,
`partial`은 승인 항목 전달과 거부 개수 알림, `valid_empty`는 정상 빈 계획이다.
`publisher_plan_no_valid_items`와 container·empty·JSON·schema 오류는 출판사 단계의 명시적
경고이지만 원문 저장·기억 전달·메인 본문 요청·턴 완료를 실패로 뒤집지 않는다.

`E-2`는 2026-08-12 현재 소스와 자동 회귀 기준으로 완료했다. Go의
`supervisor_support_packet.v2`가 현재 사용자 입력 원문 전체, accepted previous completed turn,
그리고 `memory_delivery_plan.v1`의 최종 예산 적용 뒤 실제 본문에 남은 표현만 출판사 입력으로
연결한다. 기존 delivered memory·character memory와 같은 문구는 정확한 문구 단위로만 중복을
제거하며 의미 추론으로 합치지 않는다. selected-but-deferred 후보, 미전달 후보, raw private
memory, 전체 과거 채팅은 포함하지 않는다. 이 단계는 새 검색·선택·예산·fallback을 만들지 않았고,
E-4·E-5 cutover에서 `publisher_plan.v2` 입력으로 연결됐다. loaded artifact·실제 provider·
RisuAI/PocketRisu 실사용 확인은 별도 검증 대상이다.

`E-3`도 2026-08-12 현재 소스와 자동 회귀 기준으로 완료했다. 정상 턴은 기존
`runSupervisorLLM` owner에서 출판사 provider 요청을 정확히 한 번만 수행한다. 공용 LLM 재시도
설정이 남아 있어도 출판사 요청에는 적용하지 않으며, 추론 매개변수 거절·HTTP 오류·timeout을
다른 매개변수로 재전송하지 않고 한 번의 명시적 실패로 반환한다. 별도 `book_author` 호출,
별도 `director` 호출, 두 번째 Publisher와 JavaScript 출판사 호출은 추가하지 않았다.

`E-4`와 `E-5`는 2026-08-12 소스·자동 회귀 기준으로 같은 bounded cutover에서 완료했다.
Publisher 전용 응답 정규화와 수리 없는 현재-schema 판정이 유효한 역할·필드·항목만 승인하고,
E-5는 그 승인 목록만 하나의 본문 계획 block으로 컴파일한다. v1 fallback, shadow 변환,
이전 plan 재사용, 기본 plan 생성, 자동 재호출은 없다. 항목 하나의 오류는 정상 형제 항목을
공백으로 만들지 않으며, Publisher 실패는 메인 본문·원문 저장·기억 처리를 실패로 뒤집지 않는다.

`E-1`부터 `E-8`까지는 출판사 전용 작업이다. 4.0-A~D의 기억 후보·검색·선택·중복 정리,
평론가, 원문 저장, 턴 번호, 삭제·리롤, 설치·업데이트와 종료 경로는 이 묶음에서 변경하지 않는다.

현재 Go 소유권·delivery lineage·비밀 경계 위에 복구하고, 1.0에서 오류를 숨기거나 임의 지시를
만들던 부분은 가져오지 않는다.

#### 6.1.4 현재 런타임과 E의 정확한 차이

현재 소스에서 확인된 기준선과 E의 변경점은 다음과 같다.

- 현재 prompt와 parser는 `book_author + director`의 `publisher_plan.v2`를 사용한다.
  평면적인 v1 hint 배열과 v1 변환 경로는 Publisher 실행 owner에 남기지 않았다.
- 현재 저장·전달 계약은 `publisher_plan.v2`, `memory_delivery_plan.v1`,
  `payload_application_plan.v1`이다. E는 첫 번째만 v2로 바꾸고 뒤의 두 계약은 유지했다.
- 현재 support packet은 current input, accepted recent context, 실제 delivered memory와
  delivered character memory를 이미 구분한다. E-2는 이 owner를 확장해 실제 전달된 상태·세계·
  thread·hierarchy 표현을 연결하며 전체 과거 채팅이나 미전달 후보를 새로 넣지 않는다.
- 현재 강도 정규화와 Publisher 입력은 `none/weak/medium/strong/extreme/maximum`을 모두
  같은 사실 권한 안에서 구분한다. 강도는 지시의 명시성만 바꾸며 승인 항목·기억 예산·항목 수는 바꾸지 않는다.
- 출판사 호출은 공용 retry budget과 Critic용 JSON repair parser를 사용하지 않는다. Publisher
  호출 지점만 수리 없는 판정을 사용하며 Critic parser의 동작은 바꾸지 않았다.
- `message.content` 문자열·배열형 text part와 제한된 `choice.text`를 Publisher 전용 owner가
  empty 판정보다 먼저 정규화한다. F는 실제 provider별 응답을 검증한다.

즉 E는 이름만 바꾼 기능이 아니라 기존 v1 hint 경로를 1.0 역할 구조의 v2 계획으로 교체했다.
E-1~E-8은 소스·자동 회귀 기준 완료이며, loaded artifact·실제 provider·RisuAI/PocketRisu
실환경 검증은 남아 있다. E-8은 같은 백엔드·세션의 연속 요청에서 직전 Publisher plan을
재사용하지 않는지, raw·deferred private memory가 provider 요청과 최종 guidance에 노출되지
않는지까지 production owner 경로로 고정한다. 이 검증은 새 fallback·retry·cache·기본 plan을
추가하지 않으며 E-1~E-7의 호출·승인·단일 block·강도·표현 형식 계약을 변경하지 않는다.

### 6.2 기억과 근거 입력

4.0 출판사는 다음 입력만 사용한다.

- 현재 사용자 입력 전체;
- accepted current scene/time과 직전 완료 턴의 continuity;
- `memory_recall_plan.v1`에서 적격 판정을 받고 본문 모델에도 실제 전달되는 기억·직접 근거;
- 실제 전달되는 인물 상태·목표·말투, 관계·주관 기억, 세계 상태·세계 규칙;
- 현재 요청과 연결되어 실제 선택된 active storyline·open thread와 hierarchy summary;
- 본문 전달 가능성이 증명된 bounded `guidance_support`;
- 보호 기억은 비밀 원문이 아니라 본문 모델에도 보이는 렌더링된 guard 표현.

미전달 후보, raw private memory, stale/superseded item과 다른 branch의 자료는 포함하지 않는다.
각 factual premise는 실제 delivered source ref와 연결하고, 출판사 계획 자체는
`truth_authority=false`, `canonical_write=false`인 response-shaping proposal로 유지한다.

### 6.3 서사 가이드 강도

1.0의 역할 분리는 `weak` 이상에서 공통으로 사용하되 강압적인 지시는 높은 강도에만 둔다.

| strength | `book_author + director` 사용 범위 | 금지 |
|---|---|---|
| `none` | Publisher 호출·plan·guidance 0 | 기억·직접 근거·비밀 guard를 함께 끄기 |
| `weak` | 현재 arc와 가까운 목표, 부드러운 scene mandate, continuity·행동·subtext 중심 표현 | 필수 beat 강제, 사용자 행동 결정, 높은 pressure |
| `medium` | weak보다 목표·다음 beat 후보·guardrail·required outcome을 균형 있게 명시 | 단일 정답 전개, 관계 변화·closure 확정, 고정 개수 채우기 |
| `strong` | medium + 더 명시적인 우선순위, forbidden move, 높은 장면 pressure와 응답 ending edge | canonical truth 생성, 사용자 행동·감정·대사 강제, arc/session/작품 종결 |
| `extreme` | strong + 이번 응답의 우선순위와 필수 반영 순서를 명시하고 장면 목표를 더 직접적으로 지휘 | 하나의 줄거리만 허용, 사용자 선택지 제거, 새 사건·압력의 무근거 생성 |
| `maximum` | extreme + 현재 응답 안에서 따라야 할 ordered execution brief와 완료 확인 항목을 가장 명시적으로 제공 | response 범위를 넘는 지속 명령, 자동 carry·plot lock, 관계·사건·엔딩 확정 |

강도는 사실 권한을 넓히지 않는다. `maximum`도 current input·accepted scene과 delivered
support 안에서 표현의 명시성과 장면 지휘 강도만 높인다. 사용자의 현재 방향 전환은 모든
이전 arc·beat보다 우선하며, 낮은 강도에서는 비강제 후보와 자연스러운 표현을 우선한다.

### 6.4 모델 입력 표현 profile

작은 파라미터 모델에 필요한 명시성과 출판사의 서사 지휘 강도는 서로 다른 축이다.

| guidance format | 목적 | 강도에 미치는 영향 |
|---|---|---|
| `compact` | 큰 문맥과 복합 지시를 안정적으로 처리하는 모델에 짧은 계획 전달 | 없음 |
| `standard` | 기본 구조와 필드명을 유지한 균형형 계획 전달 | 없음 |
| `explicit` | 작은 모델을 위해 역할·우선순위·순서·금지를 더 구체적인 고정 구조로 전달 | 없음 |

`explicit`은 `weak`을 `strong`으로 올리지 않고, `compact`도 `maximum`의 지휘 강도를
약화하지 않는다. `explicit`의 역할·필드·순서 표시는 E-4가 승인한 역할·필드·원래 순서를
보이기 쉽게 표시할 뿐 새 우선순위를 만들지 않는다. 세 format은 항목 text·순서·source ref를
그대로 유지한다. 4.0에서는 사용자가 선택한 format 또는 검증된 기존 설정만 사용하고 모델명,
provider명, 알려지지 않은 parameter 수를 추측해 자동 선택하지 않는다. 4.9의
`model_capability_profile.v1`이 실제 관찰 근거를 갖춘 뒤에만 format 자동 선택을 확장할 수 있다.

4.9의 `directed/reviewed/deep`은 LLM 호출·검토 깊이이며 `compact/standard/explicit` 표현
profile이나 `none~maximum` 서사 강도와 별도 축으로 유지한다.

### 6.5 Provider 공통 요청·응답

핵심 출판사 prompt·parser·validator·renderer에는 provider명이나 모델명을 하드코딩하지 않는다.
OpenAI 호환 endpoint, LLM Gateway, Ollama 호환 endpoint와 그 밖의 지원 provider는 같은
`publisher_plan.v2` 역할 계약을 사용한다. endpoint·reasoning·max-completion 같은 차이는
기존 provider adapter에서만 해당 provider가 지원하는 형태로 변환한다.

공통 응답 정규화는 최소한 다음을 같은 텍스트 입력으로 처리한다.

- 문자열 `message.content`;
- 배열형 content part의 `text`;
- `choice.text`;
- JSON code fence를 제거한 뒤의 단일 JSON 객체.

빈 content·malformed JSON·schema-invalid·HTTP 오류·timeout은 구분된 stable failure로
표시한다. 자동 retry, 1.0 기본 directive fallback, 이전 성공 plan 재사용과 provider별
별도 출판사 경로는 만들지 않으며, 잘린 JSON 수리·누락 필드 기본값 채움·legacy schema
변환도 하지 않는다. 출판사 실패와 별개로 본문 요청은 계속한다.

### 6.6 단일 본문 계획 block

현재의 여러 `[Optional Publisher ...]` 조각은 하나의 일관된 출판사 계획 block으로
교체한다. block에는 현재 arc, 가까운 목표, 다음 beat 후보, 장면 mandate, 필수 결과,
guardrail·forbidden move와 pressure를 중복 없이 전달한다.

이 block은 기존 `payload_application_plan.v1`의 output-guidance owner를 통해 하나만 전달한다.
현재 typed memory lane의 순서·예산·text를 평탄화하거나 다시 검색하지 않고, Go가 최종
본문 계획 text와 순서를 확정하며 JavaScript는 실제 payload에 적용만 한다.

Publisher continuity가 accepted current scene/time보다 앞선 단계로 회귀하면 명시적
flashback·reentry가 없는 한 해당 계획을 defer한다. recall 성공만으로 새 사건·관계 변화·
closure를 확정하지 않으며 기억은 인용문 반복보다 행동·subtext·장면 반응으로 표현한다.

### 6.7 턴 간 계획 연속성 경계

4.0의 최초 cutover는 request-scoped 계획을 먼저 검증한다. 이전 arc·beat·required outcome을
다음 턴에 carry하는 기능은 별도 table·last-known cache로 먼저 만들지 않는다. carry가 필요하면
기존 서사 상태 owner의 재사용 가능성을 확인하고 이 문서 8장의
edit/delete/reroll/branch lifecycle과 같은 revision fence를 통과할 수 있는 계약으로만
활성화한다.

## 7. 4.0-G — 선택형 RisuAI 로어북 참조

상태: `source_implemented_regression_verified_live_gate_pending`

4.0-G는 더 이상 로드맵 승인 대기 후보가 아니라, 사용자가 명시적으로 켜는 4.0 독립
packet이다. 2026-08-12 현재 G-1~G-6의 source 구현과 자동 회귀는 통과했으며 G-7의 실제
loaded RisuAI/PocketRisu·MariaDB·패키지 검증은 남아 있다. 선택적 semantic 후보 확장은
아직 구현하지 않았고 exact/key/lexical 경로만 활성이다. 이 절의 계약이 과거 검토
문서의 `candidate_requires_*` 또는 4.1 이관 표현과 충돌하면 이 절을 우선한다.

목표는 RisuAI 로어북을 Archive Center 기억으로 복제하는 것이 아니다. RisuAI가 원본 작성,
native 발동과 기본 주입을 계속 소유하고, Archive Center는 동의를 받은 현재 범위의 항목을
별도 읽기 전용 참조 자료로 보존해 **필요할 때만** 검색한다.

### 7.1 공식 Host 경계와 갱신 시점

2026-08-12에 다시 확인한 공식 API 기준은 다음과 같다.

- RisuAI와 PocketRisu의 `getCurrentLorebookEntries()`는 character global, current-chat local,
  enabled-module 원본 항목을 합친 snapshot을 반환한다. native key 발동, decorator, 확률,
  재귀 검색, 우선순위와 token budget 적용 결과를 반환하는 API가 아니다.
- 로어북 edit/delete, character/chat 전환과 enabled-module 변경을 직접 알리는 공통 plugin
  event는 없다. RisuAI의 `output` listener는 모델 출력 완료 신호이며 로어북 변경 신호가
  아니고, PocketRisu 공통 계약으로 사용할 수도 없다.
- 합쳐진 snapshot만으로 항목별 character/chat/module 출처를 확정할 수 없으면 내용을 보고
  출처를 추측하지 않는다. 공식 관찰로 범위를 확정할 수 없는 항목은
  `current_host_aggregate`로 보존하며 범위별 항목인 것처럼 표시하지 않는다.

공식 근거:

- [RisuAI output listener 계약](https://github.com/kwaroran/RisuAI/blob/72ce721878d65b09baf4339638dfd221d1788261/src/ts/plugins/apiV3/risuai.d.ts#L1838-L1893)

Host 원본 snapshot을 다시 읽는 경우는 다음으로 제한한다.

1. 기능을 처음 켰거나 현재 범위의 DB snapshot이 없을 때;
2. 사용자가 `로어북 새로고침`을 명시적으로 실행했을 때;
3. 이미 관찰하는 current character/chat index의 조합이 바뀌었을 때;
4. 동의를 받아 읽은 `enabledModules` 집합이 이전 관찰값과 바뀌었을 때;
5. 사용자가 복구·재색인을 명시적으로 요청했을 때.

같은 character/chat 안의 edit/delete는 공식 변경 신호가 없으므로 수동 새로고침을 정본 갱신
경로로 둔다. 일반 턴마다 전체 로어북을 다시 읽거나 polling, DOM 감시, `output` listener로
변경을 추측하지 않는다. 평소 턴은 MariaDB의 현재 참조 snapshot만 검색한다. 완전 자동 갱신은
Host가 공식 change event 또는 revision을 제공한 뒤 별도 계약으로 추가한다.

### 7.2 모드와 별도 저장 영역

| 모드 | DB 검색·Explorer | 본문·출판사 전달 |
|---|---|---|
| `off` | 0 | 0 |
| `search_only` | exact/key/lexical과 선택적 semantic 후보, trace만 허용 | 0 |
| `reference_assist` | `search_only` 결과에서 Go가 선별 | 사용자가 명시적으로 켠 경우에만 별도 참조 lane으로 전달 |

로어북 항목은 `lorebook_reference_entry.v1` 논리 영역에 원문·key·관찰 범위·entry identity·
snapshot/revision·lifecycle을 보존한다. 기존 store가 이 의미를 표현할 수 없는 것이 재현된
경우에만 새 table/API를 추가한다. 다음 자료로 자동 병합하거나 승격하지 않는다.

- 직접 근거·정밀 기억·주관 기억;
- 관계·개체·인물 상태와 세계 규칙;
- 원작 canonical 자료와 session event.

내용 hash는 변경 관찰과 빠른 동일성 비교용이다. stable entry ID, 정사 근거, admission 조건,
업데이트 차단 조건으로 사용하지 않는다. 로어북 항목이 현재 출력에 등장했다는 이유만으로
평론가가 이를 세션에서 실제 발생한 사건으로 저장하지 않는다.

### 7.3 검색과 관련성

scope·lifecycle·consent는 다른 캐릭터·채팅의 자료가 섞이지 않도록 엄격하게 검증한다.
내용 관련성과 중복은 느슨하게 처리한다. 검색 순서는 다음과 같다.

1. 현재 입력의 declared key·entry ID·정확 문구;
2. comment·key·content의 일반 문자 검색;
3. 앞선 결과가 현재 요구를 충분히 지원하지 못할 때 선택적 semantic 후보 확장;
4. Go hydration 뒤 현재 snapshot·scope·lifecycle 재검증.

semantic 점수는 후보 폭만 넓힌다. native 발동, 정사, 인물 지식, 관계, 사실 권한과 최종
전달을 확정하지 않는다. 고정 개수나 고정 글자 수를 채우려고 관련 없는 항목을 넣지 않고,
하나의 고정 유사도 값으로 전체 후보를 일괄 탈락시키지 않는다. Vector 장애가 나도
exact/key/lexical 결과는 유지한다. 로어북 검색만을 위한 LLM 호출·요약·분류도 추가하지 않는다.

### 7.4 기억·native 로어북과의 중복 경계

로어북과 기억은 저장·검색·후보 단계에서 서로 제거하지 않는다. 기억 전달 계획을 먼저
확정한 뒤, 실제 최종 입력 조립 단계에서만 Archive 로어북 참조의 반복 표시를 판단한다.

확정 중복으로 인정할 수 있는 최소 범위는 다음뿐이다.

- CRLF/LF, 본문 앞뒤 공백과 연속 공백만 정규화한 뒤 전체 본문이 동일함;
- 같은 Host entry와 같은 관찰 revision이 두 수집 경로에서 반복됨;
- 로어북 전체 본문이 실제 요청 payload에 그대로 존재함.

Vector 유사도, 같은 이름, 일부 문장 겹침, 비슷한 요약, key 일치와 추정 발동만으로는
중복 처리하지 않는다. 시점·관계 방향·기억 소유자·공개 범위가 다르거나 판단이 모호하면
둘 다 유지한다. accepted current state와 현재 관계·위치·소유 상태가 로어북 기본 설정과
충돌하면 중복이 아니며 현재 기억을 반드시 남긴다. 주관 기억은 로어북의 객관 설정과
비슷하다는 이유로 생략하지 않는다.

최종 표시 규칙은 다음 순서를 따른다.

1. RisuAI actual payload에 같은 전체 본문이 확실히 있으면 Archive 로어북 참조만 생략한다.
2. 실제 전달될 Archive 기억과 로어북 참조가 확실히 같으면 기억을 남기고 로어북 참조만
   생략한다.
3. 같은 로어북이 여러 현재 범위에서 관찰되면 DB 행과 출처는 모두 보존하고, 최종 입력의
   동일 본문 한 번에 retained source refs를 연결한다.
4. 중복 판정 실패·관측 부족·부분 유사에서는 아무것도 생략하지 않는다.

중복 억제는 해당 요청의 표시만 줄이며 DB 행을 수정·삭제하지 않는다. **로어북 참조와 기억을
동시에 제거할 수 없고, 하나를 생략하려면 다른 하나가 실제 payload에 남는 것이 먼저
확정되어야 한다.** hash 불일치나 중복 판정 오류도 전달 거부 조건이 아니다.

### 7.5 예산·출판사·장애 경계

핵심 기억 선택과 최종 전달을 먼저 확정하고, 로어북 참조는 그 결과를 바꾸지 않는 별도 lane에서
남은 전체 보조 입력 문자 예산을 사용한다. 핵심 기억 K를 소비하거나 기억·직접 근거·현재 상태·
주관 기억을 밀어내지 않는다. 별도 lane도 전체 모델 입력 상한에서는 면제되지 않으며 고정 개수·
고정 quota를 채우지 않는다.

trace/HUD는 최소한 native payload 관찰 chars, Archive 기억 chars, 로어북 후보·선택·중복 생략·
예산 defer 수와 delivered chars를 분리한다. 현재 chars는 Archive Center 조립 영역의 문자 수이며
provider 실제 전체 token과 같다고 표시하지 않는다. provider usage가 있으면 별도 관측값으로 둔다.

출판사는 메인 모델에 실제 전달된 로어북 참조와 actual payload에 존재가 확정된 본문만 근거로
사용한다. 검색 후보·미전달·stale·범위 불명 자료를 사용하지 않고, 로어북 때문에 Publisher를
추가 호출하지 않는다. `search_only`에서는 Publisher 전달도 0이다.

로어북 DB·Vector·Host 관찰 장애는 **로어북 참조 lane만 중단**한다. RisuAI native 로어북,
Archive 기억, 원문 저장과 본문 응답은 계속한다. 장애를 이유로 후보를 확대하거나 stale 자료를
다른 scope에서 가져오는 우회 경로는 만들지 않는다.

### 7.6 넣지 않을 기능

- 전체 항목의 무조건적 Chroma 미러와 매 턴 재색인;

## 8. 수명주기·복구·실환경 완료 범위

### 8.1 Source·revision·표시 최종문

- edit는 새 source revision을 만들고 이전 revision의 파생 결과를 current에서 제외한다.
- reroll은 같은 logical user turn의 새 assistant generation을 active-final로 전환하고 이전
  generation 파생 결과를 supersede한다.
- delete는 대상 source와 의존 파생 결과를 invalidated/tombstoned로 만들며 부분 삭제 성공을
  허용하지 않는다.
- branch는 shared ancestor와 branch-local tail을 구분하고 다른 branch의 current projection을
  재사용하지 않는다.
- copy/move/connect는 raw message index가 아니라 backend가 계산한 source baseline과 stable
  identity mapping을 사용한다.
- complete-turn과 Critic은 실제 displayed final 하나만 admission한다. final을 관찰할 수 없으면
  사용자 응답은 보존하되 canonical write는 deferred/read-only로 둔다.

### 8.2 Transaction·outbox·동시성·재시작

- source commit 이전 파생 canonical write는 0이어야 한다.
- 같은 dependency batch의 일부 operation 실패 시 해당 batch의 partial commit을 허용하지 않는다.
- DB commit 뒤 Vector 실패는 durable outbox에서 재시도한다.
- stale worker는 compare-at-commit revision fence에서 거부한다.
- retry와 duplicate callback은 idempotent여야 한다.
- process kill·timeout·restart 뒤 committed source와 job 상태가 일치해야 한다.
- Publisher·recall 장애가 raw source 내구 저장을 취소하지 않는다.

### 8.3 Dependency invalidation·reindex·rebuild

source revision이 바뀌면 atomic memory/evidence, current state와 story clock, perspective,
relation·habit·profile, thread realization, search document/vector, recall/injection plan,
Publisher support/plan과 HUD·Explorer read model을 같은 dependency graph로 무효화·재계산한다.

- MariaDB canonical source에서 전체 Chroma generation을 재구축할 수 있어야 한다.
- 부분 reindex는 대상 source/revision/dependency를 명시하고 unrelated generation을 current로
  바꾸지 않는다.
- schema·embedding model·normalization 변경은 새 generation에서 검증한 뒤 current pointer를
  원자적으로 전환한다.
- 중단·재시작·retry 뒤 duplicate vector와 missing current vector가 없어야 한다.
- Vector가 없어도 exact·lexical recall과 메인 저장·응답은 유지된다.

#### 8.3.1 `perspective_scoped_typed_delivery` 오분류 피드백 수정

상태: **소스·자동 회귀 검증 완료, 실 PocketRisu·MariaDB·Chroma·Voyage 검증 대기**

한 턴에 관계·습관·인물 성격·말투·주관 기억 배열이 하나라도 존재한다는 이유만으로 그 턴의
전체 기억을 비공개 전용으로 분류하던 판정을 제거한다. 전체 Critic 결과와 typed 기억은
MariaDB의 canonical 자료로 보존하고, 일반 검색·Vector에는 항목별 공개 근거로 만든
`memory_public_projection.v1`만 사용한다.

- 객관 자료와 `committed + source_observed + public` 근거가 확인된 관계·습관·인물 성격·말투는
  일반 exact·lexical·Vector 검색 대상으로 유지한다.
- 기억 소유자·비공개 범위·보호 비밀·비공개 identity·review-required 자료는 일반 projection에서
  제외하되 기존 typed perspective/protected-memory 전달은 삭제하지 않는다.
- 공개 자료와 비공개 자료가 같은 Memory 행에 있으면 공개 projection은 일반 기억 칸으로,
  canonical 비공개 자료는 보호 기억 칸으로 각각 전달한다.
- `embedding_model`에는 실제 embedding이 생성된 경우의 실제 provider model만 기록한다.
  기존 `perspective_scoped_typed_delivery` 값은 과거 sentinel 식별과 UI 숨김에만 사용하며 새로
  저장하지 않는다.
- `/search`, Vector hydration, prepare-turn 일반 기억, integrity, 강제 재색인은 같은 공개 projection
  계약을 사용한다. 원문 chat log로 검색 결과를 채우거나 전체 private `SummaryJSON`을 다시
  전달하는 보충 경로는 사용하지 않는다.
- 강제 재색인은 활성 committed source의 저장된 `DerivedResultJSON`을 저장 당시 version/hash로
  확인한 뒤 현재 admission·durable outbox로 재생한다. Critic을 다시 호출하거나 별도 임시
  색인을 만들지 않으며, 공개 대상에서 제외된 과거 aggregate Vector는 cancel/delete operation으로
  정리한다.
- 세션 이전도 같은 공개 projection과 정밀 기억 eligibility를 사용한다. Voyage 입력에 원문 chat
  log를 다시 넣지 않으며, 이전으로 바뀐 source revision의 committed 결과 hash를 재계산해 이후
  강제 재색인에서도 같은 정본을 재생할 수 있게 한다.
- 강제 재색인의 integrity·orphan 판정은 이 경로가 실제로 생성·정리하는 memory·직접 근거·정밀
  기억·세계 규칙만 같은 canonical inventory로 비교한다. KG와 episode/chapter/arc/saga처럼 다른
  writer가 소유한 Vector를 이 작업의 누락·고아로 세지 않으며, 비공개 전용 자료나 정상 정밀 기억도
  잘못된 누락·초과 Vector로 세지 않는다.
- 기존 canonical 원문·committed extraction·typed 기억은 삭제하지 않는다. 손상된 hash/JSON,
  비활성 또는 누락 source는 추정 복구하지 않고 해당 재색인 항목의 명시적 실패로 남긴다.

자동 검증은 objective-only, 공개 관계·습관·인물 성격·말투, private-only, public+private 혼합,

### 8.4 Publisher·Critic lifecycle

`publisher_plan.v2`는 request-scoped proposal이며 canonical memory가 아니다.

- plan은 session/request/logical turn/branch/generation/revision/input digest와 source snapshot에
  결합한다.
- reroll·edit·delete·branch·새 generation에서 이전 plan·focus·carry를 재사용하지 않는다.
- explicit redirection은 current request에서 이전 focus를 해제한다.
- Publisher failure, draft, rejected plan과 failed output candidate를 memory evidence로 저장하지 않는다.
- 이후 4.9의 advanced Publisher도 이 fence를 그대로 사용하며 별도 last-known plan cache를
  만들지 않는다.

### 8.5 선택형 lorebook lifecycle

4.0-G를 활성화한 경우에만 entry edit/delete, scope·module enable 상태, consent 철회,
partial observation, branch/copy/restart와 index rebuild를 release gate에 포함한다.

- consent 철회, scope 변경, 명시적 삭제 또는 같은 범위의 완전 snapshot에서 검증된 부재는
  current 검색·전달을 중단하고 이전 자료는 감사 이력으로만 보존한다.
- timeout, 권한 일시 오류와 부분 관찰은 삭제·tombstone으로 해석하지 않는다. last-confirmed
  snapshot과 원본 DB 행을 보존한다.
- consent와 character/chat/module 범위가 그대로임을 현재 관찰로 확인할 수 있을 때에만
  last-confirmed snapshot을 계속 검색할 수 있다. 범위를 확인할 수 없으면 해당 로어북 참조
  lane만 이번 요청에서 생략하고 Archive 기억과 RisuAI native 로어북은 유지한다.
- 다른 scope의 stale snapshot을 현재 자료로 대신 쓰거나 read 실패를 이유로 후보를 확대하는
  fallback은 만들지 않는다.

### 8.6 OS·package·upgrade·rollback

지원 Windows·Linux·macOS·Termux에서 fresh install, 지원되는 이전 release의 update,
`.env`·MariaDB·Chroma data 보존, launcher health commit/rollback, 부분 다운로드·권한 오류·
포트 충돌·불완전 runtime과 backup/restore를 검증한다. source test와 package fixture를 실제
설치·loaded plugin·DB roundtrip 증거로 바꾸어 보고하지 않는다.

### 8.7 장기 session과 완료 증거

장기 session에서 latency·memory·DB/index 증가, 재처리·삭제·restart 성능과 정확도를 함께
측정한다. 각 요구사항은 source 변경, 회귀, package, loaded RisuAI, 실제 MariaDB/Chroma와
지원 provider/OS 증거를 구분해 연결한다. 문서·schema·fixture 존재만으로 4.0 완료를 선언하지
않는다.

### 10.3 분기 발견 계약

전용 branch event가 없다. 현재 bounded 구현은 RisuAI `output` callback에서 마지막 비활성
`branchedfrom` 표식 후보가 이미 존재할 때만 그 표식과 바로 앞 source message 좌표를
동기적으로 고정하고, 기존 session-routing 요청으로 보조 관찰한다. 표식이 없는 일반
output은 추가 요청을 만들지 않는다. UI open, 명시 sync, `beforeRequest` topology 재확인은
현재 계약이 아니며 fallback으로 추가하지 않는다.

JavaScript는 callback의 character/chat index, child chat ID, 마지막 표식과 바로 앞 message의
ID·role·disabled 상태만 Go에 전달한다. Go는 exact 표식을 파싱하고 부모 route를 read-only로
resolve한다. 바로 앞 message가 `user`이면 그 ID를 anchor로 쓰고, `char`이면 함께 관찰한 가장
가까운 이전 enabled user의 opaque ID를 anchor로 쓴다. parent Host chat ID와 이 user anchor로
기존 owner가 만든 durable logical-turn ID를 exact 대조해 부모의 유일한 active source revision과
canonical fork turn을 구한다. 내용이나 index로 추측하지 않는다. output callback 자체는 branch
event나 displayed-final 증거가 아니다. accepted active source가 없는 starter/greeting 분기는
`unresolved`이며 부모 import나 fork badge를 만들지 않는다.

다음은 자동 분기로 인정하지 않는다.

- 주기 polling, UI 문구·버튼·DOM 감시;
- `Branch`, `Copy` 같은 채팅 이름;
- 채팅 ID가 달라졌다는 사실만 있는 일반 복사·가져오기·구버전 자료;
- RisuAI output listener가 발화했다는 사실만 있는 경우;
- reroll/swipe, 부분 수정, 삭제 또는 같은 logical turn의 generation 교체;
- 부모·fork message를 확인할 수 없는 손상된 `branchedfrom` 표식.

같은 topology snapshot을 반복 확인해도 branch row와 membership이 늘어나지 않아야 한다.
메시지 내용 수정 탐지 digest와 topology snapshot digest를 분리해, 본문 수정이 새 branch로
등록되지 않게 한다. 표식이 없거나 부모를 확인할 수 없으면 `unlinked/ambiguous`로 표시하고
자동 부모를 추측하지 않는다.

### 10.4 고정 source revision membership

분기 상속은 부모를 실시간으로 계속 참조하는 방식이 아니다. 자식 채팅에서 실제로 복제되어
관찰된 각 메시지를 Archive Center immutable source revision과 대조해, **분기 생성 시점에
자식이 실제 가진 revision 집합**을 고정한다.

예를 들어 다음 topology에서 B가 활성 branch라면:

```text
R
└─ A
   ├─ B
   │  └─ E
   └─ C
      └─ D
```

B의 검색 가능 범위는 다음뿐이다.

- R에서 B의 자식 snapshot에 실제 포함된 source revision;
- A에서 B의 자식 snapshot에 실제 포함된 source revision;
- B에서 생성된 active source revision과 그 유효 derived revision.

다음은 제외한다.

- 형제 C와 자손 D;
- B의 자식 E;
- B 생성 후 부모 A에 새로 추가된 source;
- B 생성 후 부모 A에서 수정되어 B snapshot에 실제 반영되지 않은 새 revision;
- tombstone, superseded, rejected와 stale derived revision.

자식이 A의 더 오래된 메시지에서 다시 분기되면 `parent_scope_id + turn cutoff`만으로 상속을
계산하지 않는다. 자식 snapshot에 존재하는 stable message identity와 대응 source revision을
membership으로 고정한다. 부모의 이후 수정·삭제·재색인은 이 고정 membership을 자동으로
바꾸지 않는다. source 원문을 물리 복제할 필요는 없으며 membership이 같은 immutable source
revision을 참조한다.

### 10.5 branch별 현재 상태와 검색

공통 과거 사건과 현재 상태를 한 값으로 덮어쓰지 않는다.

- 과거 사건: immutable source와 그 근거에 묶인 기억;
- 현재 유효 상태: 활성 branch membership만으로 계산한 branch projection;
- 변경 이력: source/derived revision lifecycle;
- 단일값 관계: 같은 branch 안에서 새 active 값이 이전 값을 supersede;
- 다중값 관계: 기존 cardinality 계약에 따라 함께 존재 가능.

모든 검색은 LLM에게 전체 branch tree를 보내 판단시키지 않고 다음 순서로 제한한다.

```text
active Host chat
  -> verified branch scope
  -> fixed source revision membership
  -> active derived revision validation
  -> branch-local current-state projection
  -> exact/lexical/vector candidate
  -> 동일 branch predicate로 재검증
  -> recall/injection plan
```

SQL과 Vector는 서로 다른 branch 규칙을 쓰지 않는다. Chroma metadata만 믿지 않고 MariaDB의
정본 membership과 lifecycle로 hydration 단계에서 다시 검증한다. 현재 branch를 확정할 수
없으면 형제·자손 후보로 넓히지 않고 branch dimension을 `unavailable/degraded`로 보고한다.

### 10.6 reroll·수정·삭제·복사와 Canon/IF

- reroll/swipe는 같은 logical user turn의 generation 교체이며 새 branch가 아니다.
- 부분 수정은 같은 source의 새 revision이며 새 branch가 아니다.
- 명시적 Host 분기로 새 chat과 유효한 `branchedfrom` 표식이 함께 생긴 경우만 자동 branch다.
- Host 화면에서 chat이나 branch를 삭제해도 Archive 기억을 자동 삭제하지 않는다. Archive의
  명시적 기억 삭제·rollback만 기존 backend lifecycle을 따른다.
- 부모 chat이 Host에서 사라져도 자식의 고정 membership은 유지하고 UI에서 부모를
  `host_missing`으로 표시한다.
- chat 이름 변경은 stable topology ID와 membership을 바꾸지 않는다.
- 일반 chat 복사·가져오기·구버전 자료는 표식과 부모 근거가 없으면 자동 branch가 아니다.

RisuAI/PocketRisu는 정사와 IF를 공식 metadata로 제공하지 않으므로 Archive Center가 자동
판정하지 않는다. 사용자 분류는 `canon`, `if`, `unclassified`, `archived`이며 UI 강조와 검색
정책에만 반영한다. 현재 활성 Host chat과 사용자가 `canon`으로 표시한 branch는 서로 다른
개념이다.

### 10.7 분기 기능 완성 후 세계선 중심 UI 전면 개편

Go는 topology, 고정 membership, 현재 branch와 조상 경로, branch 상태, node 요약과 상세
자료를 조립해 versioned ViewModel로 반환한다. JavaScript는 이 ViewModel을 렌더링하고
drag·pan·zoom·click·resize 같은 화면 상호작용만 소유한다.

UI 전면 개편은 `4.0-BR-A~F`의 분기 기능과 ViewModel 검증이 끝난 뒤 시작한다. 기존 UI에
분기 조건과 임시 계산을 계속 덧붙이지 않는다. 세계선 canvas뿐 아니라 Archive Center의
탐색 구조, 현재 session·branch 표시, 기억·자료·상태 상세, 작업 진행과 오류 표시, 설정
화면을 같은 반응형 shell과 Go ViewModel 기준으로 다시 정리한다. UI를 바꾸더라도 기존
기억 검색·저장·수명주기 owner와 API를 우회하지 않는다.

세계선 화면은 다음을 제공한다.

- 2차원 무한 canvas에서 상하좌우 자유 이동;
- 휠 또는 pinch 확대·축소;
- 중앙의 시간·논리 순서 축과 부모→자식 가지;
- 중첩 branch가 다시 자식 가지로 확장되는 topology;
- 현재 활성 branch와 그 조상 경로 강조;
- canon/if/unclassified/archived의 서로 다른 비파괴 표시와 필터;
- 현재 위치 복귀, 활성 branch만 보기, 전체 topology 보기;
- 축소 시 사건·episode·chapter 단위 집약;
- 확대 시 입력 원문·응답 원문, 기억·근거·관계·상태·세계 규칙과 source/derived revision,
  유효 여부, 공통 구간/branch 고유 구간, fork message를 확인하는 상세 panel;
- branch·node 수가 많아도 전체 DOM을 한 번에 만들지 않는 viewport 기반 가상화;
- 데스크톱 mouse와 모바일 touch에서 같은 topology 의미 유지.

터치·포인터 조작 계약은 다음과 같다.

- 한 손가락 또는 한 포인터 drag는 node 이동이 아니라 canvas pan이다;
- 두 포인터의 거리를 이용해 pinch zoom-in·zoom-out하고, 두 포인터의 중간 지점을 확대
  중심으로 유지한다;
- 두 포인터에서 한 포인터로 바뀔 때 확대 동작을 끝내고 pan으로 자연스럽게 전환한다;
- mouse drag는 pan, wheel은 pointer 위치 중심 zoom이며 touch·pen·mouse가 같은 ViewModel을
  사용한다;
- 짧은 node tap/click은 선택과 상세 보기만 수행하고 topology나 canonical 자료를 변경하지
  않는다;
- 세계선 영역 밖의 일반 세로 스크롤과 버튼 조작을 막지 않으며, gesture capture는 canvas
  영역으로 한정한다;
- 확대·축소, 현재 branch로 복귀, 전체 topology 맞춤 기능은 gesture 외에 명시적 버튼과
  키보드 접근 경로도 제공한다;
- 최소·최대 zoom, node 밀도와 집약 단계는 고정 상수가 아니라 viewport, 접근성 설정,
  ViewModel의 semantic zoom 단계와 실제 성능 측정으로 정한다.

고정 node 수, zoom 배율, 보존 기간, polling 간격과 패널 비율은 설계 상수가 아니다. 실제
viewport, 데이터 밀도, 접근성 설정과 성능 측정에 따라 ViewModel/UI 계층에서 결정한다.

공개 navigation API가 없으므로 4.0의 보장 범위는 node 상세 보기와 현재 Host chat 강조까지다.
graph node 클릭으로 RisuAI/PocketRisu chat을 강제 전환하지 않는다. DOM 클릭이나 Host 내부
함수 import를 정식 기능으로 만들지 않는다.

### 10.8 Host 호환성 표

| 기능 | RisuAI | PocketRisu | Archive Center 4.0 처리 |
|---|---|---|---|
| 분기 생성 | 선택 메시지까지 복제 | 선택 메시지까지 복제 | snapshot에서 검증 |
| `branchedfrom` | 부모 ID·이름·fork message ID 포함 | 같은 표식 포함 | 직접 부모 topology 근거 |
| current character/chat index | 공개 API 있음 | 공개 API 있음 | thin adapter 관찰 |
| chat snapshot 읽기 | 공개 API 있음 | 공개 API 있음 | bounded RisuAI callback의 현재 marker/source 좌표만 관찰 |
| output listener | 공개 `output` listener 있음 | 공개 API에서 확인되지 않음 | 기존 표식 보조 관찰만 허용, branch event/displayed-final로 사용 금지 |
| branch listener | 없음 | 없음 | 즉시 branch event 완료 주장 금지 |
| 공개 chat navigation | 확인되지 않음 | 확인되지 않음 | 상세 보기까지만 보장 |
| 실기기 검증 | 별도 필요 | 별도 필요 | source 확인과 구분해 기록 |

현재 공개 API 차단 항목은 다음과 같다.

1. **분기 생성 직후 알림 없음**: 현재 bounded 구현은 RisuAI output callback 시점에 이미
   존재하는 표식만 보조 관찰한다. UI open·명시 sync·beforeRequest 재확인은 구현되지 않았고,
   PocketRisu 자동 관찰 경로도 UNKNOWN이다. 즉시 반영이 필수라면 Host upstream의 공개
   event가 필요하다.
2. **graph에서 Host chat으로 직접 이동 불가**: 공개 navigation API 전에는 구현 완료로
   표시하지 않는다.

향후 upstream 제안은 현재 구현 계약과 구분해 다음 형태로 기록한다.

```text
addRisuChatListener('branch', { parentChatId, childChatId, forkMessageChatId })
addRisuChatListener('chatChanged', { characterId, chatId })
navigateToChat({ characterId, chatId, messageId? })
```

    zoom 버튼, 현재 branch 복귀·전체 맞춤, canvas 밖 스크롤, 상세 panel과 viewport
    가상화가 RisuAI·PocketRisu의 실제 데스크톱·터치 환경에서 같은 topology를 유지함.

각 시나리오는 `source 회귀 → 빌드 산출물 → loaded plugin → RisuAI/PocketRisu 실기기 → 실제
MariaDB/Chroma` 증거를 구분한다. 자동 source test 통과를 실기기·release 완료로 바꾸어
보고하지 않는다.
