# Archive Center 4.X 모델 능력 적응형 RP 시뮬레이션 지원 로드맵

상태: 계획 초안
범위: 4.0 정밀 장기 기억 이후의 4.X 계열
작성 목적: 대규모 등장인물과 복잡한 세계관을 다루는 RP에서 생성 모델의 능력과 관계없이 설정 이행을 강화하고, 모델의 실제 능력에 따라 지원 강도를 조절하는 방법을 확정한다.

## 0. 압축 복구용 결정 스냅샷

- 4.X는 3.3~3.5와 4.0을 앞당기거나 대체하는 작업이 아니라 두 release gate를 소비하는 후속 계층이다.
- 3.3 source spine, 3.5 effective Host/output contract와 4.0 identity·time·state·knowledge·
  relation·profile·recall이 `release_gate_verified`이기 전에는 production payload에 4.X 결과를 적용하지 않는다.
- 전체 로어북 reader·DB/Chroma mirror·activation 재구현은 폐기된 경로이며 4.X에서도 되살리지 않는다.
- 모델명·작품·장르·인물 수·고정 점수·고정 후보 수로 정책을 분기하지 않는다.
- 4.X는 canonical memory를 쓰거나 truth·importance·관계·profile을 재판정하지 않고,
  검증된 상태를 현재 장면 실행 계약으로 투영한다.
- 기억의 이미지·도표 변환은 3.4 범위에서 제외된 후속 opt-in 연구다. 공식 RisuAI image request
  capability와 provider별 visual token·한글/고유명사 판독·source fidelity를 검증하기 전에는
  production memory delivery가 아니며, 이미지 결과만으로 canonical 기억·상태·관계·비밀
  판정을 만들지 않는다.
- 사용자 피드백 이전에 prerequisite·source fence·예산·장애 격리·실제 payload parity를
  packet별로 검증한다. 라이브 평가는 모델별 체감 품질과 첫 출력 채택을 확인하는 최종 단계다.

### 0.1 사용자 확정 목적과 창작 자유 경계

- 4.X의 목적은 저성능 모델도 다양한 인물과 복잡한 세계관을 최대한 이행하게 하고,
  고성능 모델에서도 긴 세션의 인물·관계·지식·시간·세계 상태 누락을 줄이는
  **모델 능력 적응형 RP 지원**이다. Archive Center가 장기 기억 백엔드라는 이유로 이 목적을
  삭제·축소·폐기하거나 3.6~4.0의 기억 작업으로 흡수하지 않는다.
- 캐릭터 단편화, 말투·성격 이탈, 전지적 지식, 근거 없는 친밀감, 직전 사건 복기와 해결된
  사건 부활을 줄이고, 피폐물·복수극·정치극 등에 이미 존재하는 갈등·대가·적대 세력·독립
  목표가 무난한 일상물로 중화되지 않게 돕는 것은 4.X의 정식 목적이다.
- 이 지원은 이야기를 대신 결정하지 않는다. 활성 인물·동기·갈등·다음 전개는 근거가 있는
  복수 후보와 경계로만 제공하며 특정 등장·행동·감정·관계 변화·사건·속도·결말을 정답으로
  강제하지 않는다. 사용자/player character의 선택과 본문 모델의 창작 자유가 최종 결정권을 가진다.
- 하나의 thread를 계속 전면화하거나 그 thread의 해결을 작품 전체 종결로 확대하지 않는다.
  조용한 장면을 허용하며, 반대로 현재 자료에 존재하지 않는 갈등·폭력·배신을 장르 유지를
  명분으로 새로 만들지 않는다.
- `must_preserve`와 `must_not_assert`는 사실·권한·비밀·연속성 경계다.
  `must_account`, `may_advance`, 전개 후보와 장면 카드는 비구속 지원이며 plot beat, 고정
  cadence, 필수 사건 수 또는 자동 재작성 명령이 아니다.
- “장면 실행 계약”의 실행은 RisuAI payload에 적용할 구조화된 지원 자료라는 뜻이다.
  감독관의 계획대로 이야기를 집행한다는 뜻이 아니며, 이 절과 충돌하는 명령형 해석은 허용하지 않는다.

### 0.2 공식 RisuAI 적합성 상속

4.X의 모든 구현은 `permanent-risu-host-backend-boundary.md`의
`Official RisuAI Conformance Baseline`과 3.3~3.5·4.0의 검증된 계약을 상속한다. 작업 시작 전에
지원할 공식 RisuAI 버전의 문서와 upstream source/type에서 실제 payload 적용 지점, 메시지·
streaming·최종 표시·리롤·삭제·분기 순서를 확인하고 commit 또는 tag·날짜·hook/type을
검증 기록에 남긴다.

- 4.X는 공식 RisuAI가 실제로 노출한 관찰값과 앞 단계가 승인한 source/memory projection만
  입력으로 사용한다. prompt 문구, 모델명, 작품명, 인물 수, DOM 모양이나 임의 ID로 host 상태를
  추정하지 않는다.
- 노출되지 않은 generation·revision·streaming·display·visibility 사실은
  `unobserved`/`not_exposed`이며, `false`나 추정값으로 바꾸어 simulation eligibility나 stale
  판정을 통과시키지 않는다.
- JavaScript는 Go가 만든 실행 계약을 공식 RisuAI payload에 적용하고 실제 표시 결과를 관찰한다.
  활성 인물 선택, 장면·세계·세력 simulation, 예산, 우선순위, fence와 실패 처리는 Go가 소유한다.
- 4.X release gate에는 공식 shape를 사용하는 production adapter 시험과 실제 RisuAI에서 guide
  OFF/ON, streaming, 리롤, 삭제, 분기, stale 결과 거부와 메인 응답 비차단을 확인한 증거가 필요하다.
  fixture·shadow·문법 검사만으로 production 호환이나 완료를 선언하지 않는다.

공식 RisuAI 변경에 대응할 때 기존 adapter와 versioned contract를 갱신하며, 별도 watcher,
parallel injector, JavaScript simulation 정책 또는 독립 저장 경로를 추가하지 않는다.

## 1. 결론

이 작업을 단순한 프롬프트 작성 가이드로 축소하지 않는다.

목표는 Archive Center가 보유한 장기 기억, 원작 자료, 현재 장면과 인물 상태를 근거로 다음 응답에 필요한 정보만 선별하고, 생성 모델이 능력에 맞게 사용할 수 있는 **장면 실행 계약**으로 제공하는 것이다. 낮은 능력의 모델에는 더 명시적이고 분해된 계약을, 높은 능력의 모델에는 불필요한 간섭을 줄인 압축 근거와 경계를 제공한다.

Archive Center가 더 큰 생성 모델을 흉내 내는 것이 아니라 다음 실패를 구조적으로 줄이는 것이 목표다.

- 여러 인물의 정체성, 지식 범위, 관계, 목적과 말투가 서로 섞이는 문제
- 복잡한 세계 규칙, 세력 관계, 시간과 공간 조건을 잊는 문제
- 캐릭터의 한 가지 특징만 과장해 평면적인 인물로 만드는 문제
- 예시 대사를 현재 문맥과 무관하게 그대로 재사용하는 문제
- 현재 장면에 없는 인물이나 자료를 과도하게 주입하는 문제
- 원인과 결과, 미해결 약속과 갈등, 장기 서사 흐름이 끊기는 문제
- 결과가 마음에 들지 않아 반복 리롤하면서 출력 비용이 증가하는 문제

이 계층은 어떤 모델의 추론 한계도 완전히 제거한다고 약속하지 않는다. 자료가 없거나 서로 충돌하는 경우에는 만들어내지 않고 부족함을 명시해야 한다. 목표는 동일한 모델을 사용할 때 설정 이행률과 첫 출력 채택률을 최대한 높이고, 고성능 모델에서도 긴 세션과 복잡한 세계관으로 인한 누락·혼동을 줄이는 것이다.

## 2. 기존 문서와의 경계

### 2.1 4.0 정밀 장기 기억

`4.0-precision-long-term-memory-roadmap.md`는 무엇을 기억하고, 어떤 근거와 시점·관점·생명주기로 저장하고 회상할지를 담당한다.

이 문서는 그 기억을 현재 장면에서 **누가 무엇을 알고 어떤 상태·동기·제약과 복수의 행동
가능성을 가지는지**로 변환하는 비구속 실행 지원 계층을 담당한다. 4.X 작업은 4.0 기억
계약을 대체하거나 약화하지 않으며, 하나의 행동이나 전개를 정답으로 선택하지 않는다.

### 2.2 3.1-3.2 원작 DB

`3.1-3.5-consolidated-release.md`의 3.1~3.2 범위는 작품, 판본, 원문, 승인된 사실,
출처와 충돌을 담당한다.

원작 DB는 선택 기능이며 Archive Center의 주 기능이 아니다. 4.X는 원작 DB가 꺼져 있거나 장애가 나도 메인 장기 기억, 시작, `/ready`, 저장, 삭제와 회상을 막아서는 안 된다. 원작이 활성화된 채팅에서는 원작 자료를 보조 근거로 사용할 수 있지만, 현재 사용자 입력과 명시적인 사용자발 분기가 우선한다.

### 2.3 2.5 출력 품질·다중 에이전트 자료

2.5 자료의 인물·연속성·세계관·스타일 검토 관점과 제한된 제안 계약은 구조적 참고 자료로만 사용한다.

과거 문서에 있는 JavaScript 정책 계산, JavaScript 점수화, 고정 역할 수와 전체 출력 자동 재작성 설계는 현재의 영구 Host/Backend 경계를 따르는 구현 근거로 사용하지 않는다. 새 정책, 조립, 라우팅, 예산과 판정은 Go 백엔드가 소유한다.

Risu Recomposer와 같은 외부 다중 에이전트 플러그인은 별도의 선택 계층이다. Archive Center 4.X의 기본 기능이 해당 플러그인이나 다중 모델 호출에 의존해서는 안 된다.

### 2.4 3.3-3.5 선행 마일스톤과의 경계

3.3~3.5는 더 이상 4.X에 흡수된 과거 번호가 아니다.
`3.1-3.5-consolidated-release.md`의 3.3~3.5 범위가 다음 선행 기능을 소유한다.

| 버전 | 선행 마일스톤 | 4.X가 상속하는 결과 |
|---|---|---|
| 3.3 | source envelope·bootstrap·acceptance lifecycle, RisuAI Host Context observation과 supervisor OFF/ON trace | 검증된 active source spine, `risu_host_context_snapshot.v1`, `guidance_application_trace.v1` |
| 3.4 | native-present Host Context의 권한·중복·constraint compile과 생성 전 `response_execution_contract.v1` | native Host source authority, 실제 payload 적용과 독립 narrative support lane |
| 3.5 | Host-grounded Output Fidelity와 출판사·평론가 플로팅 작업 HUD | 설정 충실성, guide efficacy, source→constraint→payload→final output evidence와 현재 요청의 비차단 작업 ViewModel |

4.X는 이 결과를 다시 저장하거나 별도 supervisor를 병렬 구현하지 않는다. 4.0의 정밀 기억과
3.5의 effective Host Context·출력 전처리를 읽어 캐릭터 해석, 활성 인물, 세계·세력과 thread simulation으로
확장한다. 3.5에서 만든 `response_execution_contract.v1`은 4.X에서
`narrative_execution_brief.v1`로 확장되며 두 계약이 같은 목적의 중복 block이 되어서는 안
된다.

3.5는 current input과 실제 전달된 Host Context·검증된 memory constraint의 기본 이행,
현재 출판사·평론가 요청의 작은 비차단 플로팅 HUD까지
완료 판정한다. stable identity·관계 이력·graph-neighborhood coverage와 장애·성능·live
closure는 4.0 gate가 소유하고, 명사 언급·개체·관계 주장·Direct Evidence 연결과 전체 관계
UI는 4.5가 소유한다. 캐릭터 단편화·단일 특성 환원·예시 대사 복사·
과도한 친밀감·장르 압력·활성 인물·세계 simulation의 의미 품질은 이 문서가 소유한다.
3.5 fixture가 이 실패를 관찰하더라도 4.X 구현 완료 증거로 쓰거나 3.5에 별도
profile/simulation critic을 만들지 않는다.

### 2.5 3.6~4.0 정밀 장기 기억과의 경계

3.6~4.0은 4.X 시뮬레이션의 일부가 아니라 `4.0-precision-long-term-memory-roadmap.md`의
메인 장기 기억 구현 구간이다.

| 구간 | 소유하는 것 | 소유하지 않는 것 |
|---|---|---|
| 3.3~3.5 | actual Host context 관찰·source evidence·constraint compile, 출력 guide와 적용 trace | 전체 raw lore 저장·검색·activation 재구현, 요청 단위 관계 graph·UI, stable identity·메인 기억 truth·관계 history·완성형 graph recall·profile·simulation |
| 3.6~4.0 | 3.3 active source 기반 atomic admission·identity·시간·상태·주관 지식·관계·profile·recall·delivery lifecycle | source/Host 재수집·재판정, guide strength, 활성 인물·세계 simulation |
| 4.X | 검증된 3.5 source와 4.0 기억을 현재 장면 실행 카드·simulation brief로 투영 | 앞선 두 구간의 canonical write·검색·예산 정책 재구현 |

4.X production enable은 3.5 A~C·E와 4.0의 필수 contract·release gate, 그리고
`4.0-precision-long-term-memory-roadmap.md`의 **3.5 이관 gate**가 모두 검증된 뒤에만 허용한다.
개발 중 명시적 shadow evaluation에서는 일부 prerequisite가 비활성·불완전한 상태를
`prerequisite_unmet/coverage_gap`으로 관찰할 수 있지만 그 결과를 실제 payload나 canonical
write에 적용하거나 4.X release evidence로 집계하지 않는다. 누락 prerequisite를 모델 추론,
3.5 재계산, 별도 storage나 JavaScript fallback으로 대신 만들지 않는다.

## 3. 제품 목표와 비목표

### 3.1 제품 목표

1. 모든 모델에 현재 장면에서 필요한 인물·세계·서사 조건을 전달하되 실제 능력에 맞춰 명시성과 압축 수준을 조절한다.
2. 장기 기억과 원작 자료를 그대로 쏟아 넣지 않고 실행 가능한 단위로 선별한다.
3. 인물마다 지식, 오해, 비밀, 감정 원인, 관계와 목표를 분리한다.
4. 성격과 말투를 단일 특징이나 예시 문장으로 환원하지 않는다.
5. 세계관을 백과사전 요약이 아니라 현재 행동에 영향을 주는 규칙과 인과관계로 제공한다.
6. 단순한 턴에는 거의 개입하지 않고 복잡한 턴에만 필요한 지원을 확대한다.
7. 모델 성능 보조가 장기 기억의 저장 정확성과 기존 Archive Center 기능을 침범하지 않게 한다.
8. 첫 출력 채택률을 높여 불필요한 리롤과 출력 토큰 비용을 줄인다.

### 3.2 비목표

- 특정 모델, 작품, 등장인물, 세력 또는 장르에 맞춘 하드코딩
- 모든 모델에서 동일한 품질을 보장하거나 낮은 능력의 모델을 모든 상황에서 상위 모델과 같게 만든다는 주장
- 자료가 없는 사실, 감정, 관계와 세계 규칙을 자동 생성해 정답으로 저장하는 기능
- 모든 등장인물을 매 턴 주입하거나 고정된 인물 수만 선택하는 정책
- 예시 대사를 그대로 재사용해 말투를 흉내 내는 방식
- 매 턴 모든 평론가·감독관·에이전트를 호출하는 방식
- 출력 실패를 무조건 성공으로 처리하거나 검증 실패를 숨기는 방식
- 원작 DB 또는 보조 LLM 장애가 메인 기능을 막는 구조
- 노드 그래프 UI를 선행 조건으로 삼는 것

### 3.3 Requirement ledger

각 구현 item은 사용자 요구, production owner, 부정 fixture와 실환경 증거까지 연결한다.

### 3.4 목표 축소·보수적 의미 왜곡 금지

4.X의 목표는 일부 캐릭터 카드나 경고 UI를 추가하는 것이 아니라, 3장의 Requirement ledger 전체가
실제 생성 요청과 결과에서 작동하게 하는 것이다. 단계·schema·DTO·prompt·trace·shadow·
진단 화면 또는 소수 fixture는 preparatory slice이며 4.X 전체 완료가 아니다.

이 문서의 용어는 다음 의미로만 사용한다.

- `optional`은 조건에 따라 **호출하지 않을 수 있음**을 뜻한다. requirement의 production
  구현·라우팅·실패 격리·검증 자체를 생략할 수 있다는 뜻이 아니다.
- `sparse`는 source에 없거나 현재 request에 적용되지 않는 필드를 발명하지 않는다는 뜻이다.
  source가 지지하는 인물의 복수 성격 축·관계·반례·지식 경계를 편의를 위해 삭제한다는
  뜻이 아니다.
- `compact`는 같은 의미를 더 짧은 wire representation으로 전달한다는 뜻이다. 필수 제약,
  source authority, 인물별 차이 또는 내적 모순을 제거하는 저품질 profile이 아니다.
- `safe`와 `isolated`는 unsupported 사실 승격과 메인 기능 장애 전파를 막는다는 뜻이다.
  갈등·욕망·비판·거절·관계 변화·서사 진행을 보수적으로 동결하거나 무색한 출력만 만드는
  정책이 아니다.
- `unknown`은 실제 source와 host observation으로 확정할 수 없다는 상태다. 구현이 어렵거나
  모델을 신뢰하지 않는다는 이유로 확인된 사실까지 공백 처리하는 기본값이 아니다.
- `degraded`는 일부 계약을 전달·검증하지 못했다는 실패 상태다. 원 payload를 보존할 수는
  있지만 정상 지원 성공이나 품질 완료로 집계할 수 없다.

안전한 판단은 무조건 적게 행동하는 판단이 아니라 **근거가 허용하는 전체 범위를 정확히
실행하는 판단**이다. 근거가 없을 때의 과잉 생성과 근거가 있는데도 필요한 관계 변화·인물
반응·세계 인과·입력 응답을 막는 과잉 억제는 대칭적인 fidelity 실패다. 예를 들어 사소한
접촉만으로 사랑을 만들면 안 되지만, source가 직접 지지하는 사랑·배신·결별·화해를
“안전하게” 제거해서도 안 된다.

요구 문구에 둘 이상의 해석이 있고 그 선택이 기능 범위·품질·비용·사용자 체감을 바꾸면
기존의 넓은 목표와 실제 실패 사례를 유지한 채 결정 항목으로 올린다. 구현자가 가장 작은
해석, 가장 쉬운 fixture 또는 가장 보수적인 동작을 임의 채택할 수 없다. 완화·제외·후속
이동은 15.5의 change control과 사용자 명시적 승인을 거쳐야 한다.

#### 3.4.1 최소 개선·안전 명목의 완료 위장 금지

회귀 위험을 줄이기 위해 bounded slice로 구현할 수는 있지만, “기본 기능을 건드리지 않는
가장 작은 보완”을 최종 목표로 삼을 수는 없다. 다음 방식은 4.X 구현 또는 품질 개선으로
인정하지 않는다.

- 카드·prompt·경고 UI 하나만 추가하고 실제 selection→payload→output 계약을 연결하지 않음;
- 오류를 만들지 않는다는 이유로 모든 장면을 단순·hold·skip·진단-only로 처리;
- 갈등·관계 변화·NPC의 독립 행동을 억제한 결과를 안정성 개선으로 보고;
- 특정 장르·인물·작품·문구·모델·점수·인물 수·thread 수·turn 수를 고정해 사례만 통과;
- 어려운 requirement를 선택 기능·낮은 우선순위·후속 버전으로 재분류하고 일부 성공을 전체 완료로 보고;
- 보조 기능 장애 격리를 보조 기능의 미구현·무호출·빈 결과 성공과 동일시.

최소 변경은 **원래 목표를 축소하지 않는 가장 작은 완결 단위**를 뜻한다. 각 단위는 실제
Go production owner, RisuAI payload 적용, 부정·반전 fixture와 failure/degraded 상태를 함께
가져야 한다. 나머지 requirement는 문서와 완료 gate에 계속 남으며, 사용자의 명시적 승인
없이 삭제·완화·후속 이동할 수 없다.

## 4. 영구 아키텍처 원칙

### 4.1 소유권

- JavaScript는 RisuAI의 실제 입력·출력·메시지·스트리밍 상태를 관찰하고, Go가 만든 최종 계획을 실제 payload에 적용하며 UI를 표시한다.
- 통합 Go `/prepare-turn` orchestration은 현재 장면 해석, 인물 선택, 세계 규칙 선택, 위험
  판단, 모델 능력 대응, 서사 예산, 프롬프트 조립, 검토 라우팅과 안정적인 오류 상태를
  소유한다. 메인 기억 검색·hard filter는 4.0 `memory_recall_plan.v2`, native Host Context의
  attribution·constraint compile은 3.5 `host_context_support_plan.v1`, 원작 검색은 원작 전용 owner가
  수행한다. 4.X는 store·Chroma를 다시 검색하거나 별도 ranking을 만들지 않는다. 추가 evidence가
  필요하면 stable entity/dimension/source need를 upstream planner에 요청하고 versioned 결과를
  소비한다.
- MariaDB는 canonical truth이고 ChromaDB는 재구축 가능한 검색 인덱스다.
- 보조 LLM은 후보, 요약 또는 검토 결과를 만들 수 있지만 canonical truth를 직접 기록하거나 Go admission을 우회할 수 없다.

### 4.2 기본 흐름

```text
RisuAI 관찰값
  -> Host Context ID·scope·revision·hash·actual payload span 확인
  -> Go 장면·요청 판정
  -> 장기 기억 회상 계획
  -> 선택적 원작 자료 회상
  -> 장면 시뮬레이션 상태 구성
  -> 모델 능력에 맞춘 실행 계약 조립
  -> RisuAI 실제 요청에 적용
  -> 메인 모델 출력
  -> 최종 표시 결과 관찰
  -> 선택적 품질 진단 및 다음 기억 후보
```

이 흐름에서 보조 계층이 실패하면 확인 가능한 경고와 실패 이유를 남기고 기존 메인 요청 경로로 내려가야 한다. 다만 일부만 만들어진 계획을 정상 계획처럼 섞어 적용해서는 안 된다.

단일 `/prepare-turn` 안에서도 base memory·Host Context plan은 optional 4.X child와 독립적으로 완성
가능해야 한다. simulation·supervisor·critic child는 bounded deadline, panic recovery와 lane별
stable status를 가지며 timeout/malformed/panic 시 last-known simulation plan을 재사용하지 않는다.
공통 composer는 완전한 base plan과 검증된 optional item만 합친다. canonical mutation·source
invalidation·migration은 fail-open 대상이 아니며 transaction 실패 시 이전 committed revision을
유지한다.

### 4.3 입력 우선순위

충돌 시 다음 원칙을 따른다.

1. 현재 사용자가 명시한 입력과 지시
2. 사용자가 명시적으로 만든 현재 세션의 분기와 변화
3. 근거가 확인된 현재 장면·장기 기억 상태
4. 현재 활성 RisuAI 캐릭터·시나리오·로어북·작가 노트 중 in-world로 허용된 범위
5. 사용자 Local Canon Overlay
6. 현재 continuity와 시점에 허용된 승인 Canon Pack 자료
7. 근거가 불충분한 추론 후보

낮은 순위의 자료가 높은 순위의 사실을 덮어서는 안 된다. 불확실한 추론은 사실형 문장으로 위장하지 않는다.

이 목록의 첫 항목은 **이번 응답의 response obligation 우선순위**다. 현재 user message의 모든
문장이 객관적 truth라는 뜻이 아니다. truth authority는 trusted host role/channel, source kind,
speaker, branch와 4.0 Go admission이 별도로 결정한다. user/player 행동·대사, 인물의 주장·거짓말·
추측, OOC 정정과 서술된 세계 사건을 분리하고, user 입력이나 접촉만으로 상대 인물의 감정·
상호성·동의·관계 transition을 만들지 않는다.

## 5. 독립 예산 계약

Archive Center의 메인 기억 주입이 최우선이다. 4.X 시뮬레이션 지원은 기억과 원작 자료를 다시 복사해 예산을 이중 소비하는 별도 백과사전 블록이 되어서는 안 된다.

논리적 예산은 다음처럼 분리한다.

| 논리 이름 | 역할 | 원칙 |
|---|---|---|
| `max_injection_chars` | 사건, 상태, 관계, 발언과 근거 회상 | 기존 동적 장기 기억 예산을 유지하며 최우선 보호 |
| `reference_injection_max_chars` | 보완·단독 공통 원작 정보 | 기존 참조형·단독형 계약을 유지하고 장애 격리 |
| `primary_canon_base_max_chars` | 단독 모드의 기반 원작 정보 | 원작 단독 모드에서만 사용하고 메인 기억 예산과 합치지 않음 |
| `narrative_support_max_chars` | 인물 해석·지식 경계·관계·장면 계획·세계 인과 실행 계약 | 별도 상한과 추적을 가지며 앞선 계층의 원문을 중복 주입하지 않음 |
| `orchestration_cost_profile` | 선택적 사전 감독관·사후 평론가의 입력·출력·호출 비용 | 본문 주입 예산과 분리하며 호출하지 않은 턴은 비용 0 |

앞의 이름 중 현재 runtime에 없는 것은 4.X의 제안 계약이며 구현 완료를 뜻하지 않는다.
사용자 UI에는 서사 지원 상한과 비용·속도·품질 실행 profile 정도만 노출하고, 내부 역할별
호출 제한은 Go가 versioned policy로 관리한다.

첫 네 행은 본문 모델에 들어가는 서로 독립적인 주입 예산 계층이며,
`orchestration_cost_profile`은 본문에 들어가는 다섯 번째 주입 블록이 아니라 내부 보조
호출 비용 계약이다.

`narrative_support_max_chars` 안의 활성 인물, 인물별 지식, 관계·감정, 말투·성격 경계,
장면 흐름과 세계 상태 몫은 현재 장면에 따라 동적으로 배분한다. 현재 모델의 컨텍스트
용량, 실제 요청 크기, 장면 복잡도와 활성 위험을 입력으로 Go가 계산하며 특정 모델명,
고정 비율, 고정 인물 수 또는 고정 문자 수로 분기하지 않는다.

이 예산 lane은 3.5가 `response_execution_contract.v1`용으로 만든 동일 lane을 4.X가 확장해
사용한다. 4.X가 두 번째 narrative budget이나 별도 최종 절단기를 만들지 않으며, 기존
`/prepare-turn`의 단일 Go allocator가 3.5 base item과 4.X extension item을 함께 조립한다.
4.X OFF이면 3.5 base item·예산·payload 결과가 변하지 않는다.

RisuAI가 이미 실제 요청에 넣은 로어북·캐릭터·시나리오 범위는 native observation으로
표시하고 의미가 같은 내용을 다시 주입하지 않는다. native overlap은 원자료 삭제나
canonical truth 변경 근거가 아니라 이번 delivery의 중복 억제 근거일 뿐이다.

예산 부족 시에는 다음 순서를 따른다.

1. source-backed current constraint, current response obligation, 이미 발동한 consequence와 사용자 입력
2. 실제 활성 인물의 지식·목표·관계·현재 상태
3. 현재 행동에 직접 영향을 주는 세계 규칙과 인과 조건
4. 미해결 약속·갈등·비밀과 직전 사건
5. 배경 설명과 낮은 관련성의 보조 정보

단순 잘라내기로 계약의 한쪽만 남기지 않는다. 축약 또는 제외된 항목과 이유를 backend trace에 남긴다.
전체 컨텍스트가 부족하면 `narrative_support_max_chars` 계층이 자체적으로 축약·유예되고,
기존 장기 기억이나 현재 사용자 입력을 밀어내기 위해 예산을 우회하지 않는다.
다만 예산 부족은 필수 인물·지식·관계·세계 인과 중 일부를 조용히 제거할 권한이 아니다.
같은 의미를 더 짧게 표현할 수 없고 정확한 실행 계약을 전달하지 못하면 누락 dimension과
source ID를 `simulation_degraded/coverage_gap`으로 보고하며 지원 성공으로 집계하지 않는다.
설정된 `narrative_support_max_chars`를 늘리거나 최대로 사용해도 `max_injection_chars`와 원작·
Host lane의 설정 상한을 줄이거나 잔여분을 자동 차용하지 않는다. provider 전체 상한 때문에
동시 수용이 불가능하면 공통 Go allocator가 각 lane 내부의 compaction/defer와 누락 source를
보고하되 사용자가 정한 lane 계약 자체를 다시 배분하지 않는다.

3.5 output guide와 4.X simulation support는 설정상 독립이지만 같은 narrative lane·Go allocator·
최종 block을 공유한다.

| 3.5 guide | 4.X support | 실제 결과 |
|---|---|---|
| OFF | OFF | RisuAI native Host Context payload는 그대로 유지하되 Archive Center output/simulation execution block 없음 |
| ON | OFF | 3.5 `response_execution_contract.v1` base만 적용 |
| OFF | ON | 3.5 guide item·supervisor proposal 없이 4.X simulation extension item만 단일 block에 적용 |
| ON | ON | base와 extension을 공통 Go composer가 중복 제거해 단일 block·budget·hash로 적용 |

4.X ON은 3.5 guide OFF를 몰래 다시 켠 상태가 아니다. base guide strength를 상속하거나
supervisor base proposal을 실행하지 않고 4.X의 별도 사용자 설정과 prerequisite gate를 따른다.
어느 조합에서도 Host Context, 메인 기억과 원작 예산을 함께 끄거나 JS가 두 block을 조립하지
않는다.

## 6. 핵심 논리 계약

아래 이름은 4.X 설계를 위한 논리 계약 이름이며 현재 구현 완료를 뜻하지 않는다.
기본적으로 request-scoped sparse read model 또는 audit/proposal DTO이며 4.0 canonical row와
Host observation을 source ID·revision/hash로 참조한다. 별도 truth store를 만들거나 모든
필드를 모델로 채우지 않는다. 알려지지 않거나 현재 장면에 불필요한 값은
`unknown`, `not_applicable` 또는 `deferred`로 남긴다. 영구 materialization은 재현된 성능·
replay 요구와 invalidation owner가 있을 때만 별도 승인한다.

상태 이름은 owner별 namespace를 가진다. 4.0 extraction queue의 `reprocess_deferred`, 최종
payload의 `delivery_deferred`, cast/thread 선택의 `attention_deferred`를 같은 `deferred` 성공
상태로 합치지 않는다. trace·UI·완료 집계는 각각의 reason, age, retryability와 coverage를
분리해 starvation을 숨기지 않는다.

### 6.0 request/apply revision fence

모든 4.X snapshot·card·brief·proposal·report는 3.5 `GUIDE-REQUEST-FENCE`의 session·branch·
request·generation·input/Host/guide revision과 4.0의 active source set, entity mapping,
story-clock, relation/profile/thread projection revision을 함께 가진다. Go는 계산 시작과 최종
compose 시 이를 비교하고, JavaScript는 payload 적용 직전에 host-observable fence를 다시
확인한다.

새 입력·reroll·delete·branch switch·Host 수정·entity split/merge·memory correction 또는
guide/4.X OFF 전환 뒤 도착한 결과는 `stale_rejected/cancelled/superseded`로 폐기한다. 이전
simulation result, supervisor proposal과 fidelity report를 다음 request의 cache·fallback·
canonical evidence로 사용하지 않는다. 동일 idempotency key의 중복 도착은 한 번만 적용한다.

### 6.1 상속 입력 `risu_host_context_snapshot.v1`

이 계약의 정의·수집·lifecycle owner는 3.3~3.5다. 아래 항목은 4.X가 새로 정의하거나
저장하기 위한 schema가 아니라, 검증된 snapshot에서 읽을 수 있어야 하는 소비 조건이다.

- actual payload의 message path·role·order와 selected source span/hash;
- request·generation·session·branch fence;
- Host가 직접 제공한 경우의 source kind·ID·scope·revision·visibility;
- 신뢰된 host role/channel metadata와 OOC/meta/in-world 경계;
- 제공되지 않은 source 종류·activation·stable ID의 `unknown/not_exposed` capability.

4.X는 snapshot의 actual payload span·hash와 Host가 노출한 metadata를 다시 관찰하거나 재판정하지
않는다. 3.5가 제공한 source reference·상태를 그대로 참조하며 source 종류가 unknown이면
캐릭터 설명·로어북·작가 노트라고 추측하거나 승인 원작 Canon·4.0 memory truth로 병합하지 않는다.

Host Context가 수정·비활성화·삭제된 뒤 오래된 hash가 현재 장면 카드에 남아서는 안 된다.
반대로 native payload에 이미 포함되었다는 이유로 historical source evidence를 삭제하거나
미래 회상 대상에서 영구 제외하지 않는다.

### 6.2 `simulation_snapshot.v1`

현재 턴이 시작되는 순간의 실행 가능한 세계 상태다.

- scene identity, 시간, 위치와 직전 변화
- 현재 장면에 실제로 참여하는 인물
- 장면 밖에 있지만 현재 행동에 직접 영향을 주는 인물·세력
- 인물별 위치, 가시성, 행동 가능 여부와 물리 상태
- 공개 사실, 비밀, 오해와 인물별 known/suspected/unknown/misinformed/hidden/revealed 경계
- 현재 작동 중인 세계 규칙과 위반 시 결과
- 세력별 목표, 자원, 제약과 현재 충돌
- 진행 중인 사건, 약속, 갈등, 위협과 미해결 질문
- 최근 accepted `turn_realization.v1`, current input semantic delta와 response obligation
- 이미 실현된 event/outcome IDs, 해결·유예된 thread와 아직 실현되지 않은 causal frontier
- recap·reflection·사용자 agency 대기처럼 진행 없이도 유효한 discourse mode와 source-linked reason
- 자료 출처, authority, 불확실성과 적용 가능한 branch·continuity

`simulation_snapshot.v1`은 4.0 `narrative_thread_lifecycle.v1`에서 파생한
`thread_execution_view`를 포함한다.

- 현재 branch에서 eligible한 thread ID와 lifecycle, 미해결 제약·대가·목표 충돌;
- 이번 요청의 attention role과 선택된 thread, 연관되지만 유예된 thread와 source-linked defer reason;
- parent·dependency·conflict·causal successor와 해결 시 남겨야 할 consequence;
- 허용된 closure scope, transition authority와 영향을 받을 수 있는 thread ID;
- 예산 때문에 일부를 전달하지 못한 경우의 coverage 상태와 누락된 source ID.

이 view는 read-only다. 4.X는 4.0 `turn_realization.v1`의 realized/mentioned/recollected 또는
thread lifecycle·closure authority를 재분류하거나 write-back하지 않는다. 4.X가 OFF여도 4.0
thread recall/delivery는 독립적으로 계속되며, 4.X attention 부재가 기본 defer·dormant·resolved
판정으로 사용되지 않는다.

여기서 서사 압력은 장르명이나 긴장 점수가 아니라, 근거가 있는 제약·대가·목표와 이미
발동한 인과가 현재 선택 가능성에 미치는 영향이다. `foreground`, `background`, `deferred`는
이번 요청의 attention일 뿐 lifecycle을 변경하지 않는다. `dormant`도 `resolved`가 아니며,
검색 결과나 선택된 thread가 비었다는 사실은 이야기 전체 종료의 근거가 아니다.

그래픽 노드 UI는 필수가 아니다. 내부적으로 관계 edge가 필요해지더라도 canonical 사실과 근거를 대체하는 별도 진실 저장소로 만들지 않는다.

### 6.3 `character_execution_card.v1`

매 턴 고정 캐릭터 카드를 전부 넣는 방식이 아니라 현재 장면에서 선택된 각 인물의 실행 단위다.

- identity와 현재 장면에서의 역할
- 원하는 것, 피하려는 것과 즉시 행동 동기
- 알고 있는 것, 모르는 것, 잘못 알고 있는 것과 숨기는 것
- 다른 활성 인물과의 현재 관계·권력·거리·부채, 신뢰·경계, 애착·의존, 경쟁·열등감,
  존중·불만과 과거 사건의 영향
- 겉으로 보이는 관계 태도와 실제 내적 태도의 차이 및 공개 범위
- 상대별 `relationship_view`: 4.0 admitted current/history·transition refs, 이번 context에서
  근거 있는 표현, counterevidence·예외와 `must_preserve` state
- `relationship_change_envelope`: 이번 장면에 인과적으로 허용되는 변화 후보, 아직
  확정하면 안 되는 변화와 direction·domain·reciprocity·magnitude·permanence·consent 경계
- 현재 감정과 그 감정이 생긴 원인
- 신체 상태, 통증, 피로, 치료·회복과 행동 제약
- 스스로 선택하고 행동할 수 있는 agency와 가능한 다음 행동
- 성격의 여러 축, 상황별 예외와 내적 모순
- 특성별 원래 의미 영역과 현재 장면에서 영향을 줄 수 있는 범위
- 4.0 profile의 `supported_expression`, 반례와 관계·상태별 변화
- 4.0 profile의 `unsupported_entailment`: 자료가 지지하지 않아 자동으로 따라오면 안 되는 해석
- 말투의 추상적 특징과 최근 문맥에서의 변화
- 해당 인물을 평면화하거나 희화화하기 쉬운 해석 위험
- 출처 기억과 설정 근거

예를 들어 과학이나 기계에 관심이 있다는 설정은 관심 분야와 사고 습관의 증거이지,
모든 대사를 수치·상태 보고 형식으로 만들라는 지시가 아니다. 강한 능력이나 높은 지위도
그 자체로 냉정함, 거만함, 사회성 부족, 감정 억제나 특정 말버릇을 뜻하지 않는다. 이
예시는 production 키워드 분기 목록이 아니라 서로 다른 특성 영역의 무근거 연결을
금지하는 설명이다.

장면 카드는 `안정적인 인격 -> 관계별 모습 -> 현재 상태 -> 관심·능력이 실제로 드러나는
조건 -> 말투 -> 과잉 해석 방지` 순으로 투영한다. 하나의 특징은 현재 목표, 관계, 감정
원인, 지식, 신체 상태, 반례와 문맥을 통과한 뒤에만 행동과 표현에 영향을 준다.

4.X는 4.0에서 admission된 `supported_expression`, relationship/state modulation,
counterevidence와 relation transition을 소비할 뿐 raw 설정을 다시 해석해 새로운 trait
edge나 관계 사실을 만들지 않는다. edge가 없다는 사실로 반대 성격을 확정하지 않고,
`unsupported_entailment`를 모델 생성 금지어·형용사 목록이나 고정 archetype table로
사용하지 않는다.

player character나 사용자 입력은 NPC의 기본 호감·신뢰·애정·친밀감·복종을 높이는 prior가
아니다. 친절·도움·접촉·명령 수행은 먼저 interaction event로 취급하고 4.0 관계 transition
근거가 있을 때만 `relationship_view`를 바꾼다. 단일 사건도 source가 큰 변화를 직접
지지하면 허용할 수 있으므로 고정 횟수나 점진적 단계 ladder를 요구하지 않는다.

### 6.4 `voice_behavior_projection.v1`

말투는 예시 대사 모음이 아니라 재생성 가능한 행동 특성으로 표현한다.
이 projection은 4.0 `PM-UTTERANCE`, character profile과 말투·호칭 evidence에서 파생하는
request-scoped 실행 단위이며 독립적인 원문 추출·저장 owner가 아니다.

- 문장 길이와 리듬의 경향
- 직접적·우회적 표현의 경향과 상대별 변화
- 어휘 수준, 존대·반말, 감정 노출 방식
- 농담, 침묵, 회피, 질문과 반응의 사용 양상
- 압박·친밀·갈등·공적 상황에서의 변화
- 자주 하지 않는 표현과 금지된 평면화 패턴
- 예시 대사에서 추출된 근거와 신뢰 수준

예시 대사는 분석 근거로만 사용할 수 있다. 현재 생성 모델에 그대로 복사할 문장으로 제공하지 않는다. 결과가 예시 문구를 기계적으로 반복했는지는 일반화된 중복 검사를 통해 진단하되 특정 대사를 코드에 넣지 않는다.
한두 발화만으로 안정된 말투를 확정하지 않고 speaker, addressee, 감정, 장면과 story time을
함께 보존한다. 새 근거가 기존 지문과 다르면 무조건 평균내지 않고 상황별 변화인지 실제
변화인지 review 대상으로 남긴다.

### 6.5 `world_execution_slice.v1`

세계관 전체 요약이 아니라 현재 장면에 영향을 주는 부분만 제공한다.

- 현재 장소와 이동·접근 제약
- 물리, 사회, 마법, 기술 또는 제도 규칙
- 규칙이 현재 인물의 선택에 주는 가능성과 제한
- 세력 간 관계, 각 세력의 목표와 현재 자원
- 인물·세력별 목표를 실행할 수단, 발동 조건, 방해 요인과 아직 남은 대가
- 시간 순서, 선행 조건과 발생 가능한 결과
- 알려진 사실과 인물별로 알려지지 않은 사실
- 원작, 세션 분기와 사용자 설정 사이의 우선순위
- 충돌하거나 불확실한 자료

세계 규칙은 설명 문단만 주입하지 않는다. 가능하면 `조건 -> 허용·금지 행동 -> 결과 -> 근거`의 실행 가능한 관계로 조립한다.
인물이나 세력의 목표·반대·위협은 user/player에게 우호적으로 보이도록 자동 완화하지 않는다.
반대로 발동 조건이 충족되지 않은 위협을 장면을 자극하기 위해 실행하거나, 정당한 대기·회복·
협상·일상 장면을 실패로 간주해 사건을 강제하지 않는다.

### 6.6 `narrative_execution_brief.v1`

메인 생성 모델에 전달하는 최종 지원 계약이다. 이것은 `response_execution_contract.v1`과
나란히 주입되는 두 번째 block이 아니라 같은 `/prepare-turn` owner가 만드는 versioned
확장 projection이다. 3.5 base의 source fidelity item을 그대로 보존하고 4.X 고유 simulation
item만 더해 단일 ordered block·budget·hash를 반환한다.

필드 소유권은 다음처럼 고정한다.

- 3.5 base: current input의 `must_respond`, effective Host Context·검증된 memory의 `must_preserve`, source
  fidelity `must_not_assert`, guide profile과 적용 trace;
- 4.X extension: 활성 인물 카드, 다층 character projection, 세계·세력 slice, thread attention,
  progression/resolution envelope와 model-adaptive 표현;
- 공통 Go composer: 중복 제거, 우선순위, 전체 `narrative_support_max_chars`, block order,
  compaction·defer, 최종 text/hash와 coverage gap.

확장 field가 없거나 4.X가 OFF/degraded이면 base 계약을 재계산·약화·삭제하지 않는다.

- 현재 장면을 한 문장으로 고정하는 anchor
- 이번 입력에 반드시 반응해야 하는 대상
- 활성 인물별 필수 유지 조건
- 현재 세계 규칙과 지식 경계
- 직전 사건에서 이어져야 할 인과관계
- 이번 턴에서 가능한 자연스러운 진행 범위
- 아직 해결하면 안 되는 복선과 제안 상태에 머물러야 하는 사건
- 해서는 안 되는 설정 위반, 지식 누출과 인물 혼합
- 사용자/player character의 행동·감정·결정을 대신 확정하지 않는 agency 경계
- 정보가 없어 모델이 임의로 확정해서는 안 되는 항목
- 사용된 기억·원작·세션 근거 ID

또한 `thread_execution_view`에서 파생한 `progression_change_envelope`를 포함한다.

- `must_preserve`: 현재도 유효한 제약·대가·목표·미해결 상태;
- `must_account`: 이미 발동해 이번 응답에서 무시하면 인과가 끊기는 영향;
- `may_advance`: 근거와 사용자 agency 안에서 진행할 수 있지만 강제할 수 없는 frontier;
- `hold_allowed`: 유예·회복·협상·관찰·recap처럼 진행하지 않아도 유효한 source-linked 이유;
- `must_not_assert`: user/player 결정, 근거 없는 공격·배신·폭로·화해·관계 변화·종료;
- `resolution_envelope`: 이번 출력이 변경할 수 있는 thread ID, closure scope, 남겨야 할
  consequence와 sibling·ancestor·session·work closure 금지 범위.

이 계약은 완성된 소설 문장을 대신 쓰지 않는다. 메인 모델이 창작할 여지는 남기되 설정 이행에 필요한 경계와 인과를 더 분명히 한다.

각 item은 다음 실행 역할을 구분한다.

- `constraint_only`: 유지해야 하지만 본문에서 다시 설명할 필요는 없는 현재 상태;
- `response_obligation`: current input의 새 행동·질문·선택·정정에 직접 반응할 항목;
- `already_realized`: 이미 발생했으므로 유지하되 재발생·복기하지 않을 event/outcome;
- `causal_frontier`: 아직 실현되지 않았고 근거 있는 다음 결과로 이어질 수 있는 항목;
- `reference_only`: 현재 행동에 필요할 때만 쓰는 배경;
- `intentional_hold`: recap·reflection·불확실성·pacing·사용자 agency 때문에 새 사건을
  강제하지 않는 source-linked 상태.

역할은 문장·키워드·유사도 점수로 정하지 않고 current input delta, final realization,
event/thread lifecycle과 source IDs에서 Go가 계산한다. 장면 anchor도 매번 다시 서술할
문장이 아니라 현재 state를 식별하는 참조다. 직전 턴의 요약·감정 재진술·기존 계획
반복만으로는 response obligation을 충족하거나 progression을 만들었다고 보지 않는다.
전면에 선택된 thread 하나가 해결되어도 sibling·parent·arc·saga·session·작품은 각각의
authority와 근거 없이 닫히지 않는다. 반대로 조용한 응답도 `must_preserve`와 `must_account`를
지우지 않고 현재 입력에 실질적으로 반응한다면 유효하다.

다음은 wire format을 고정하지 않는 비규범적 표현 예시다. 실제 label, 순서와 압축은
versioned backend contract와 모델 능력 profile이 결정한다.

```text
[현재 장면]
장소·시점·관점: <근거 있는 현재값>

[활성 인물: <entity_id>]
현재 위치·행동 가능성: <현재 상태>
이번 장면의 목표·회피: <근거 있는 동기>
안정적 인격 / 현재 감정: <분리된 값>
관계 태도: <상대와 공개 범위별 값>
알고 있음 / 의심 / 모름 / 잘못 믿음: <사실 ID별 경계>
말투 원리: <예문이 아닌 상대·상태별 특징>
근거 있는 표현: <현재 장면에서 드러날 수 있는 특성>
자동 해석 금지: <자료가 지지하지 않는 영역 간 파생>

[연속성과 세계 규칙]
반드시 유지: <위치·시간·부상·소지품·규칙·미해결 사건>
아직 확정·해결 금지: <proposal 또는 비공개 상태>

[이번 응답]
현재 사용자 입력에 반응한다.
사용자/player character의 행동과 감정을 대신 결정하지 않는다.
자료에 없는 사실을 확정하지 않는다.
```

작은 모델에는 이처럼 짧고 평평한 항목을 제공하고, 더 높은 능력의 모델에는 같은 의미를
덜 반복적인 형태로 압축한다. 두 경우 모두 source authority와 금지 경계는 동일하다.

### 6.7 `model_capability_profile.v1`

모델 이름이나 공급자를 하드코딩하지 않고 실제 관찰 가능한 능력으로 지원 강도를 정한다.

- 유효 컨텍스트 크기와 요청당 출력 제약
- 구조화 입력 준수 여부
- 다수 인물의 화자·지식 경계 유지 능력
- 긴 지시에서 핵심 조건을 잃는 경향
- 예시 문장 직접 복사 경향
- 세계 규칙과 인과관계 유지 능력
- 최근 실사용 턴에서의 실패 유형과 불확실성
- 사용자가 선택한 비용·속도·품질 정책

각 capability evidence는 model endpoint·model/config·유효 context·tool availability·사용자
policy revision, 관찰 source와 유효 기간을 가진다. endpoint·설정·도구·context 계약이 바뀌면
이전 evidence를 무효화하거나 재검증하며, `output_fidelity_report.v1` 문장을 직접 자기학습
신호로 사용하지 않고 Go가 source와 failure class를 검증한 집계만 반영한다.

관찰은 진단과 라우팅에만 사용한다. 특정 모델을 열등하다고 영구 낙인찍거나, 실제 사용자 개인정보 프로필로 확장하지 않는다.
능력 evidence가 없거나 충돌하면 높은 능력을 추정해 필수 경계를 생략하지 않는다. unknown
profile에서도 source authority, agency, 관계·지식·연속성의 `must_preserve` 의미는 유지하고
표현 형식과 선택적 호출 범위만 검증 가능한 수준으로 조절한다.

이 profile은 3.5/4.0/4.X protocol capability negotiation을 대신하지 않는다. required contract
version이나 source field가 없으면 표현 profile로 우회하지 않고 prerequisite/incompatible
상태를 반환한다. profile 변경은 표현·압축·선택적 호출만 바꾸며 authority·agency·visibility와
eligible source 의미를 바꾸지 않는다.

### 6.8 `scene_guidance_proposal.v1`

이 계약은 3.5 `supervisor_scene_proposal.v2`를 소비하는 4.X extension envelope다. 별도
supervisor owner, 병렬 LLM 호출 또는 독립 proposal writer가 아니다. 같은 Go orchestration
경로가 4.X ON 턴에서 **한 번의 supervisor LLM 요청**으로 3.5 base와 4.X extension field를
함께 반환받아 한 번에 검증한다. base 호출 뒤 extension을 위해 두 번째 LLM을 호출하거나 두
결과를 JS에서 합치지 않는다. 4.X가 필요하지 않은
턴에는 base만 사용한다. 선택적 사전 감독관은 소설 본문이나 새 사실이 아니라 짧은 장면
계획 후보만 반환한다.

- 현재 장면의 핵심 갈등과 아직 해결하면 안 되는 복선;
- Go가 제공한 근거 안에서의 인물별 즉시 동기;
- 자연스럽게 가능한 다음 전개 후보;
- 말투·감정 표현과 관계 태도에서 주의할 점;
- 사용한 source ID와 불확실성;
- 새 사실을 확정하지 않았다는 proposal 상태.

이 결과는 `simulation_snapshot.v1`이나 character state를 직접 변경할 수 없다. Go가
확정한 사실·인물 상태·지식 범위와 충돌하는 제안은 제외하며, 감독관이 없거나 실패하면
결정론적으로 조립한 장면 카드만으로 메인 요청을 계속한다.

감독관은 `relationship_change_envelope`의 방향·domain·상호성·크기·지속·consent 범위를
넓히거나 이미 실현된 event/outcome을 다음 beat로 다시 제안할 수 없다. 감독관의 문장,
confidence와 여러 감독관의 합의는 source evidence가 아니다.

감독관은 `progression_change_envelope`도 넓힐 수 없다. `may_advance` 후보 중 일부를
제안할 수는 있지만 `hold_allowed`를 무효화하거나, 새 압력·사건·반전을 만들거나,
`resolution_envelope` 밖의 sibling·ancestor·session·작품을 닫을 수 없다. 선택되지 않은
thread를 중요하지 않거나 해결된 것으로 재분류해서도 안 된다.

제안된 사건과 장면 밖 변화는 `proposal -> 실제 final displayed output의 발생 근거 ->
4.0 memory candidate -> backend admission`을 거쳐야만 canonical state가 될 수 있다.
다만 final output에 문장이 나타났다는 사실은 사건의 발생 span을 가리킬 뿐, 그 사건을
제안할 권한이나 관계·thread closure 권한까지 증명하지 않는다. 4.0 admission은 current
input, 기존 상태, actor/faction 목표, 인과 선행 조건, agency owner와 resolution scope를
다시 검증해 감독관 proposal이 출력 경유로 사실 세탁되는 것을 막는다.

### 6.9 `output_fidelity_report.v1`

선택적 사후 검토가 생성하는 진단 결과다.

- 인물 혼동 또는 잘못된 화자 귀속
- 인물별 지식 경계 누출
- 성격 평면화 또는 단일 특징 과장
- 특성의 의미 영역을 넘어선 근거 없는 행동·말투 파생
- 인물의 복수 근거를 장르 전형이나 단일 archetype으로 치환
- 관계·감정·상황이 달라도 같은 특성만 반복하는 context collapse
- 예시 대사·자료 문장의 부적절한 재사용
- 근거 없는 관계 태도 급변과 상대별 태도 혼합
- wrong-direction·자동 reciprocity, relation-domain 간 무근거 전파와 unsupported magnitude·permanence
- interaction·authority·의무·두려움을 신뢰·애정·친밀감·복종·동의로 잘못 승격
- 위치·시간·부상·행동 가능 상태 모순
- 미해결 사건의 근거 없는 소멸 또는 성급한 해결
- source-backed 제약·대가·갈등·인물·세력 목표를 무난함이나 안전 명목으로 중화한 경우
- 발동 근거 없이 갈등·위협·배신·폭로·파국을 확대해 조용한 장면을 부당하게 실패 처리한 경우
- 선택한 한 thread만 반복 전면화해 sibling·dependency·후속 consequence를 잃는 tunnel vision
- 한 thread의 해결을 parent·arc·saga·session·작품 종료로 확대하거나 dormant를 resolved로 취급한 경우
- 적대·경쟁·독립 목표가 있는 NPC와 세력을 user/player 우호·수동 대기 상태로 바꾼 경우
- 사용자/player character의 행동·감정 강제
- 직전 입력과 사건에서 이어지는 이야기 흐름 단절
- already-realized event/outcome 재연과 resolved thread 부활·해결 반복
- current input delta에 답하지 않고 recent output·summary·profile digest만 재서술
- 같은 root evidence의 raw·summary·profile echo와 intentional hold 근거 없는 scene stagnation
- 합법적인 recap·reflection·다른 POV 반응을 새 objective event나 오류로 잘못 판정
- 세계 규칙, 시간, 장소와 인과 위반
- 장면 목적과 사용자 입력의 누락
- 장기 기억·원작·세션 분기와의 충돌
- 근거 ID, 영향 범위, 확실성, 재검토 필요 여부

이 보고서는 canonical 기억을 직접 바꾸거나 출력을 무조건 재작성하지 않는다. report 문장과
agent 합의 자체도 source evidence가 아니다. 기억 후보가 필요하면 실제 user input, 승인
설정 또는 final displayed output의 exact span/hash를 가리켜 일반 4.0 admission에 전달하며
report 자신을 evidence로 가리킬 수 없다.

보고서는 `조용함`, `갈등`, `사건 발생` 자체를 오류로 판정하지 않는다. 현재 입력, actor의
독립 목표, thread lifecycle과 `progression_change_envelope`를 기준으로 unsupported
neutralization과 unsupported escalation을 대칭적으로 진단한다.

## 7. 장면별 동적 선택

### 7.1 의미 없는 입력 처리

입력이 장면 진행이나 정보 검색에 의미가 없다면 자료를 채우기 위해 아무 기억이나 강제로 주입하지 않는다. `no_relevant_support`와 같은 설명 가능한 상태로 통과시킨다.
`no_relevant_support`는 필수 upstream source lane의 조회·capability와 eligibility accounting이
정상 완료되고 eligible item이 실제로 없을 때만 사용한다. provider/contract 실패, budget
truncation, stale fence와 prerequisite 미충족의 alias가 아니다.
의미 없는 입력과 recap·reflection·기다림·사용자 agency 대기처럼 새 사건 진행을 요구하지
않는 입력은 구분한다. 후자는 `intentional_hold`로 response obligation을 충족할 수 있지만,
기계적인 직전 턴 복기나 임의 사건 생성 어느 쪽도 강제하지 않는다.

### 7.2 활성 인물 선택

인물 수는 고정하지 않는다. 전체 eligible set은 다음 근거로 먼저 확정하며 예산을 eligibility
조건으로 사용하지 않는다.

- 현재 입력에 직접 언급되거나 행동 대상이 됨
- 현재 장소에 존재하고 반응할 인과적 이유가 있음
- 직전 장면에서 행동·발화·상태 변화가 이어짐
- 직전 사건·약속·위협·비밀에 직접 연결됨
- 장면 밖에서도 현재 결과에 직접 영향을 줌
- 제외하면 화자, 관계, 지식 또는 세계 상태가 잘못될 위험이 큼

eligible set을 확정한 뒤 현재 `narrative_support_max_chars` 안에서 foreground, background와
deferred attention을 정한다. 선택되지 않은 인물이 삭제되거나 중요하지 않다고 판정되는 것은
아니다. 이번 실행 계약에서 유예된 것뿐이며 reason·누락 dimension·coverage gap을 남긴다.
장면 밖 인물과 세력은 현재 장면에 영향을 주는 변화만 집단·배경 상태로 압축한다.
제안된 offscreen 변화는 실제 본문에서 발생하거나 승인된 근거가 생기기 전까지 canonical
사건으로 저장하지 않는다.

### 7.3 복잡도 판정

고정 등장인물 수나 특정 단어로 복잡한 장면을 판정하지 않는다. 활성 관계 수, 상충하는 목표, 지식 경계, 동시 사건, 시간·공간 전이, 적용 규칙과 최근 실패 증거를 함께 본다.

단순 장면은 짧은 계약으로 통과시키고 복잡한 장면은 인물별 카드와 세계 실행 조각을 늘린다. 복잡도 상승이 곧 모든 자료 주입이나 모든 검토 모델 호출을 뜻하지 않는다.

### 7.4 thread 선택과 이야기 종료 경계

Go는 고정 thread 수나 순환 순서 없이 current input, 현재 장면, active character·faction의
목표, dependency, 이미 발동한 consequence와 예산으로 이번 요청의 thread attention을
선택한다. 모든 eligible thread는 다음 중 하나로 설명되어야 한다.

- 현재 응답에서 직접 다룰 `selected`;
- 선택된 thread와 함께 보존해야 할 `related`;
- 이번 응답에는 넣지 않되 lifecycle을 유지하고 source-linked 이유를 남기는 `deferred`.

선택은 저장 상태를 바꾸지 않는다. 한 thread의 foreground 유지, 유예, resolution은 다른
thread의 상태를 자동 변경하지 않으며, closure는 `resolution_envelope`에 명시된 ID와 scope에
만 적용한다. 이야기 전체 종료는 검색 결과, 긴장 완화, 장면 마무리 문구나 단일 목표 달성이
아니라 user/host의 명시적 종료 authority와 영향을 받는 thread 전체의 근거가 필요하다.

이는 모든 thread를 매 턴 진행시키라는 뜻도 아니다. 현재 입력이 휴식·대화·관찰·회복·
협상을 요구하면 조용한 장면을 유지할 수 있고, 관련 pressure는 삭제하지 않은 채 배경
제약으로 보존한다. 반대로 복수극·정치적 대립·생존 위협 등 어떤 source-backed pressure가
실제로 작동 중이면 장르명을 인식하지 않아도 그 제약·대가·목표 충돌이 인물 선택과 가능한
행동에 계속 영향을 줘야 한다.

## 8. 모델 능력 적응 전략

### 8.1 정보를 더 넣는 대신 실행 단위를 명확하게 만든다

- 긴 서술형 설정을 현재 행동에 필요한 조건으로 분해한다.
- 인물별 정보를 섞지 않고 반복 가능한 동일 구조로 제공한다.
- 사실, 추론, 금지, 불확실성을 구분한다.
- 중요한 인과관계를 선행 조건과 결과로 연결한다.
- 낮은 관련성의 역사와 배경 설명은 제외하거나 식별자만 남긴다.

### 8.2 캐릭터 평면화 방지

한 가지 특성을 말투 생성기로 사용하지 않는다. 인물 표현은 최소한 현재 목적, 관계, 감정 원인, 지식, 신체 상태와 성격의 복수 축을 함께 고려해야 한다.

모순되는 특징은 오류가 아니라 사람다운 상황 의존성일 수 있다. 예외와 변화가 근거로 존재한다면 한쪽을 제거해 단순화하지 않는다.

특성은 의미 영역을 가진다.

- 능력은 무엇을 할 수 있는지에 관한 근거이며 사회적 태도를 자동 결정하지 않는다.
- 관심은 무엇에 주의를 기울이는지에 관한 근거이며 모든 대사의 소재나 말버릇이 아니다.
- 직업과 지위는 권한·책임·제약에 관한 근거이며 감정 표현 방식의 증거가 아니다.
- 외형은 관찰 가능한 상태이며 가치관이나 지능·도덕성의 증거가 아니다.
- 현재 감정은 일시적 행동 조절 요인이며 stable personality를 즉시 덮어쓰지 않는다.

모델에 단일 성격 태그를 강조하는 대신 가치관, 장기 욕구, 두려움, 도덕적 경계, 내적
모순, 관계별 태도, 현재 목적과 회피 대상을 함께 제공한다. 카드가 길어질 때도 하나의
특성만 남기고 나머지 축과 반례를 잘라내는 압축은 허용하지 않는다.

검토기는 특정 형용사나 표현 목록으로 전형화를 찾지 않는다. 출력의 행동·말투가 어떤
source evidence와 장면 조건으로 정당화되는지 추적하고, 한 특성이 서로 다른 영역의
행동을 반복적으로 독점했는지를 진단한다.

관계도 하나의 호감도나 “친밀함” 태그로 평면화하지 않는다. 신뢰·애정·의존·존중·두려움·
의무·권력·동의 등 확장 가능한 domain은 방향과 공개 범위가 다르며 서로 자동 전파되지
않는다. NPC의 독립 목표·가치·경계와 player character를 대하는 근거는 다른 인물을
대하는 근거와 같은 절차로 선택한다. 입력을 제공한 주체라는 이유만으로 player를
특별히 사랑·신뢰·찬양하거나 비판·거절 능력을 잃게 만드는 것은 캐릭터 fidelity 실패다.

### 8.3 대사 예시 복사 방지

- 예시 대사를 최종 실행 계약의 직접 생성 재료로 넣지 않는다.
- 예시에서 말투 차원과 관계별 변화만 추출한다.
- 현재 장면과 일치하지 않는 내용어, 고유 사건과 문장을 재사용하지 않는다.
- 반복 검사는 특정 작품 문구가 아닌 입력 근거와 출력 사이의 일반화된 중복으로 판정한다.

### 8.4 모델 능력별 표현 변경

능력이 낮거나 최근 실패가 많은 모델에는 더 짧고 명시적인 실행 계약, 인물별 분리와 우선순위 표시를 제공한다. 능력이 충분한 모델에는 불필요한 반복과 과잉 지시를 줄이고 근거, 충돌, 불확실성과 반드시 지켜야 할 제한만 제공한다. 고성능 모델도 긴 세션에서 모든 장기 기억과 인물별 지식 경계를 스스로 복원할 수 있다고 가정하지 않는다.

모델별 지원 강도는 사용자 설정과 관찰 증거에 의해 결정하며 공급자명, 제품명 또는 버전 문자열에 고정하지 않는다.

사용자에게 보이는 실행 profile은 다음 의미를 가질 수 있다. 이름은 모델 등급이 아니라
가이드 표현과 비용 정책이다.

| profile | 장면 실행 계약 |
|---|---|
| `compact` | 핵심 활성 인물, 필수 상태, 금지 모순과 실행 순서를 강하게 압축 |
| `standard` | 인물별 상태·관계·지식·말투 경계와 장면 계획을 균형 있게 제공 |
| `deep` | 복수 세력, 장기 복선과 장면 밖 영향을 더 넓게 검토하되 관련성·예산 gate 유지 |

profile은 고정 인물 수, 고정 호출 수 또는 고정 문자 배분을 뜻하지 않는다. 동일 profile도
실제 컨텍스트 여유와 장면 위험에 따라 Go가 packet 크기와 호출 여부를 조절한다.

### 8.5 메인 작가는 하나로 유지한다

기본 경로에서는 RisuAI가 호출한 메인 모델이 최종 응답을 작성한다. 보조 모델 여러 개가 각각 완성 답변을 만든 뒤 다수결로 선택하는 방식을 기본값으로 삼지 않는다.

평론가나 감독관은 근거 기반 문제 후보와 제한된 수정 계획을 제안할 수 있지만, 그 모델의 성능이 전체 결과의 단일 실패 지점이 되지 않게 한다.

### 8.6 제품별 역할 분담

| 계층 | 책임 |
|---|---|
| Archive Center | 기억, source authority, 개체 상태, 인물별 지식, 활성 인물 선별, 장면 실행 계약과 정합성 진단 |
| RisuAI 본문 모델 | 제공된 사실·경계 안에서 실제 서술과 대사를 생성 |
| Risu Composer 등 선택적 외부 계층 | 사용자가 활성화한 중요 장면의 다중 에이전트 검토·제한된 재작성 |

Archive Center의 기본 완료 조건은 Composer가 없어도 충족되어야 한다. 반대로 Composer가
활성화되어도 Archive Center의 canonical 저장·인물 선택·예산과 source authority를
우회할 수 없다.

### 8.7 서사 압력과 사용자 agency의 공존

Archive Center는 이야기를 대신 집필하거나 예정된 plot beat를 강제하지 않는다. 대신
현재 상태에서 사라지면 안 되는 압력과 선택권을 동시에 전달한다.

- NPC와 세력은 user/player와 독립된 목표·수단·제약·중단 조건을 유지한다.
- `must_account`는 이미 발생한 인과를 무시하지 말라는 경계이지 특정 결과를 강제하는
  지시가 아니다.
- `may_advance`는 복수의 합법적 전개 가능성을 남기며, 감독관이 하나를 정답으로 만들지
  못한다.
- user/player의 결정·감정·행동은 명시적 입력 없이 확정하지 않는다.
- 조용한 장면은 압력의 삭제나 전 인물 화해가 아니며, 격렬한 장면도 곧 thread·arc·작품
  종료를 뜻하지 않는다.
- 장면이 바뀌거나 한 목표가 달성되어도 남은 대가·반대 세력·의존 thread와 후속
  consequence는 각각의 lifecycle로 계속 보존한다.

따라서 지원 계약은 “이번 턴에 사건을 일으켜라”가 아니라 “현재 입력에 반응하되, 사라지면
안 되는 제약과 actor의 독립 목표를 지우지 말고, 근거와 agency 안에서 가능한 변화만
선택하라”는 형태여야 한다.

## 9. 선택적 평론가·감독관 계층

### 9.1 기본 원칙

평론가·감독관의 성능은 중요하지만 절대적인 진실 판정자로 사용하지 않는다.

- 먼저 Go가 근거, 인물 경계, 세계 규칙과 허용된 변경 범위를 확정한다.
- 검토 모델은 해당 범위 안에서 위반 후보를 찾는다.
- 결과에는 근거 ID와 영향을 받은 범위가 있어야 한다.
- 근거가 없거나 모델끼리 합의했다는 이유만으로 canonical 상태를 바꾸지 않는다.
- 기억 후보의 evidence는 실제 input, 승인 설정 또는 final displayed output의 exact span/hash를
  가리켜야 하며 감독관·critic·verifier report 자체를 가리킬 수 없다.
- 검토 실패, timeout과 불완전 응답은 정상 성공으로 위장하지 않는다.
- 단순한 턴에는 호출하지 않을 수 있다.

마지막 항목은 per-turn 실행 선택이다. `SIM-PRE-SUPERVISOR`와 `SIM-POST-AUDIT`를 4.X
requirement로 유지하는 한 production route, 실행·skip 판정, timeout·malformed response와
기능 OFF 경로를 구현하고 실제로 검증해야 한다. 호출을 생략한 턴은 source-linked skip
reason을 남기며, 모든 턴을 “단순”로 분류해 기능을 사실상 미구현 상태로 두어서는 안 된다.

### 9.2 Go 계산과 사전 감독관의 분리

다음 작업은 LLM을 호출하지 않고 Go가 수행한다.

- 현재 장면과 활성 인물 선별;
- 이름·별명·개체 ID 확인;
- 위치, 부상, 관계와 인물별 지식 경계 계산;
- direction·domain별 `relationship_view`와 evidence-bound change envelope 계산;
- current input delta, already-realized outcomes, response obligation, unresolved frontier와
  intentional hold 판정;
- 전체 eligible thread의 lifecycle·dependency·남은 consequence를 읽고 request-scoped
  `thread_execution_view`와 `progression_change_envelope` 계산;
- selected·related·deferred의 coverage와 defer reason, thread별 resolution scope 및
  sibling·ancestor·session·작품 closure 금지 계산;
- 현재 적용되는 세계 규칙과 연속성 충돌 검사;
- native Host Context와 Archive Center 주입의 중복 억제;
- 주입 예산, 우선순위와 item별 포함·축약·유예 판정.

사전 감독관은 장면 복잡성 때문에 실제로 필요한 경우에만 짧게 호출한다. Go가 제공한
근거 안에서 핵심 갈등, 인물별 동기, 자연스러운 다음 전개 후보와 표현상 주의점을
`scene_guidance_proposal.v1`로 반환한다. 사실·위치·관계·지식 범위를 새로 만들거나
canonical 상태를 수정하지 않는다.
감독관은 Go가 준 relationship/progression envelope를 넓힐 수 없으며 already-realized
outcome을 다음 사건으로 다시 제안할 수 없다.

감독관 선택은 모델명에 연결하지 않는다. 실행 profile은 논리적으로 `감독 생략`,
`압축 감독`, `정밀 감독`과 `출력 후 진단`을 표현할 수 있지만, 실제 호출은 관계·목표
충돌, 비밀과 지식 범위, 중요한 관계 변화, 장기 복선, 불확실한 캐릭터 해석과 최근 실패
근거로 Go가 결정한다. 재귀적인 자동 리롤은 허용하지 않는다.

### 9.3 사전 지원 우선과 사후 검토

첫 구현은 출력 후 전체 재작성보다 입력 전 실행 계약 강화에 집중한다. 이는 출력 토큰이 더 비싼 환경에서 리롤을 줄이는 목적과 맞는다.

사후 검토는 다음 순서로 확장한다.

1. 관찰과 진단만 수행
2. 사용자에게 근거가 보이는 수정 후보 제공
3. Host가 안전하게 지원하고 보호 구간 검증이 끝난 경우에만 제한된 자동 보완 검토

전체 응답 자동 재작성은 별도 고위험 기능으로 남기며 4.X 기본 완료 조건에 포함하지 않는다.

비용 비교는 단순한 감독 호출 횟수가 아니라 `사전 감독 입력·짧은 출력 + 실제 본문 생성
+ 선택적 사후 진단`과 `지원 없는 본문 생성 × 실제 리롤 횟수`를 함께 측정한다. 입력 토큰이
늘었더라도 첫 출력 채택률이 올라 전체 출력 비용이 줄었는지를 별도로 보고한다.

## 10. 하드코딩 금지 계약

다음 항목을 Go, JavaScript, 프롬프트와 테스트의 정책 상수로 추가하지 않는다.

- 특정 작품명, 인물명, 세력명, 장르와 고유 대사
- 고정된 활성 인물 수, 후보 수, 에이전트 수와 호출 수
- 고정 점수, 유사도, 가중치, 위험 임계치와 우선순위 수치
- 특정 모델명에 연결된 품질 등급이나 전용 프롬프트 문구
- 성별, 직업, 관심사와 말투를 직접 연결하는 규칙
- 전역 호감도·친밀도 score, 고정 관계 단계·점진성 ladder, 접촉·친절·명령 keyword,
  player/user 우대 prior로 애정·신뢰·복종·동의·상호성을 결정하는 규칙
- n-gram·문장 유사도 cutoff, 고정 novelty score·반복 허용 횟수나 턴당 최소 사건 수로
  복기·진행·정체를 판정하는 규칙
- 특정 키워드만으로 장면 복잡도나 인물 상태를 확정하는 규칙
- 장르명·감정어·사건어로 서사 압력을 판정하는 detector와 고정 tension score·곡선·단계
- 턴당 최소 사건, 고정 전개 cadence, thread age, 고정 foreground 수, round-robin scheduler
- foreground·검색 결과·요약 문구를 lifecycle이나 전체 종료로 승격하는 규칙,
  `all_story_complete` flag와 ending phrase detector
- 별도 pressure DB·per-thread agent·JavaScript watcher처럼 기존 thread/event/evidence owner를
  우회하는 평행 정책 저장소
- 테스트를 통과시키기 위한 무조건 성공, 빈 결과 성공과 canned response

필요한 정책은 versioned backend contract, 사용자 설정, 관찰된 runtime 능력과 fixture에서 유도한다. 테스트용 구체적 인물이나 수치는 fixture 데이터일 수 있지만 production 정책으로 승격하지 않는다.

## 11. 추적과 UI

UI는 모델의 숨은 추론을 노출할 필요가 없다. 대신 다음 결과를 사용자가 확인할 수 있어야 한다.

- 이번 턴에 시뮬레이션 지원이 사용됐는지
- 선택된 인물·세계·기억·원작 자료의 출처와 제외 이유
- 각 예산의 사용량과 축약·유예 상태
- 모델 능력 대응이 적용된 이유
- 선택적 검토가 실행·건너뜀·실패한 이유
- 인물 혼동, 지식 누출, 세계 규칙 위반 등 발견된 문제
- 최종 요청에 실제 적용된 실행 계약

기존 `Assembled Auxiliary Context`와 원작 DB 표시 영역을 다시 합치지 않는다. 실제 본문
모델에 전달된 `narrative_support_max_chars` 범위는 `Simulation Support Context` 또는
동등하게 명확한 별도 진단 영역에서 표시한다. 감독관·평론가 내부 입력은 본문 주입으로
오인되지 않도록 orchestration trace에서 따로 표시한다.

버튼을 눌러 확인하는 진단이면 충분한 상태에 실시간 health check나 지속 polling을 추가하지 않는다.

## 12. 단계별 구현 순서

아래 버전 번호는 현재 작업 순서를 표현하는 임시 계획이며 각 단계의 완료 증거가 확보되기 전에는 완료 버전으로 표시하지 않는다.

### 4.1 기반 계약과 회귀 기준

- 현재 대형 RP 실패 사례를 neutral fixture로 고정
- 장기 기억, 원작 DB와 시뮬레이션 지원의 소유권·예산 경계 확정
- 3.5의 `risu_host_context_snapshot.v1`·`response_execution_contract.v1` 입력 호환성을
  고정하고, 4.X가 새로 소유하는 `simulation_snapshot.v1`과 `narrative_execution_brief.v1`만 정의
- 4.0 `turn_realization.v1`에서 current input delta, already-realized outcome, response
  obligation, unresolved frontier와 intentional hold를 읽는 `SIM-PROGRESSION` 계약 정의
- 4.0 `narrative_thread_lifecycle.v1`에서 lifecycle·dependency·closure authority와 전체 eligible
  set을 읽는 `SIM-THREAD-FIDELITY`·`thread_execution_view` 계약 정의
- 3.5가 관찰한 Host Context ID·scope·revision·hash·actual payload span과 unknown capability,
  삭제·비활성·분기 상태를
  재수집하지 않고 simulation 입력 lineage로 소비
- 현재 요청에 이미 포함된 Host Context의 중복 억제 결과를 상속하고 4.X가 같은 lore block을
  다시 조립하지 않음을 검증
- 4.X 기능 OFF 시 3.5 Host Context·출력 guide와 4.0 memory payload·저장 결과가 그대로임을 검증
- 메인 시작, `/ready`, 저장, 삭제, 리롤과 회상 회귀 기준 확정

### 4.2 인물 실행 카드

- `character_execution_card.v1`과 `voice_behavior_projection.v1` 구현
- 인물별 지식, 오해, 비밀, 관계, 목적, 감정 원인과 agency 분리
- 4.0 profile의 특성 의미 영역, 근거, 반례, 관계별 모습과 현재 상태를 장면 카드에 투영
- 4.0 `relationship_state.v1`에서 상대별 `relationship_view`와 evidence-bound change
  envelope를 투영하고 user/player 우대·자동 reciprocity·cross-domain·영속성 승격 차단
- 성격 평면화, 영역 간 무근거 행동 파생과 예시 대사 복사 진단
- 장면 기반 동적 활성 인물 선택과 제외 이유 trace

게이트: 4.0 `PM-RELATION-LIFECYCLE`의 direction·domain별 current/history/transition,
counterevidence·consent·rollback parity가 실제 경로에서 검증되기 전에는 4.2 관계 fidelity를
완료로 표시하지 않는다.

### 4.3 세계관·세력 시뮬레이션 조각

- `world_execution_slice.v1` 구현
- 규칙, 세력, 자원, 시간·공간과 인과관계 선택
- actor/faction의 독립 목표·수단·발동 조건·대가와 thread별 `progression_change_envelope` 조립
- 현재 장면에 필요한 evidence dimension을 4.0 recall·3.5 Host Context planner에 요청하고 반환된
  계층적 회상 결과만 소비
- 원작 사실, 세션 분기와 불확실한 추론의 충돌 보호

### 4.4 모델 능력 적응과 독립 예산

- `model_capability_profile.v1`의 관찰 가능한 신호 확정
- 모델명 비의존 압축·명시성·구조화 정책
- `narrative_support_max_chars`와 `orchestration_cost_profile` 분리, 기존 예산 보호와 중복 주입 방지
- `compact`, `standard`, `deep` 표현 profile이 고정 인물·호출·비율 정책이 아님을 검증
- 단순·복잡 장면의 동적 라우팅과 비용 trace

### 4.5 관계 graph·시각화와 선택적 충실도 검토

- current input·사건·기억·Direct Evidence에서 명사 언급을 빠짐없이 후보 lookup하되,
  언급·확인된 노드·확정 관계를 서로 다른 상태로 저장
- 인물·물건·장소·사건·개념을 canonical node로, 관계를 subject·predicate·object와
  source·시점·knower·privacy·confidence를 가진 relation assertion으로 표현
- 별칭·동명이인·일반 명사·관계 명사의 admission, tentative link, merge/split/retire와
  source 삭제·수정 뒤 rebuild 계약
- source·사건·기억·Direct Evidence를 관계 truth가 아니라 assertion을 지지하거나
  반박하는 provenance로 연결
- 요청별 bounded graph traversal과 예산 조립에서 selected/deferred/excluded 이유,
  privacy 차단과 coverage gap을 추적
- 전체 graph와 현재 장면 local graph, node/edge 상세, source 근거, 시점·branch·knower·
  공개 범위, 충돌·미확정 상태를 탐색하는 관계 UI
- UI의 수동 확인·분리·병합·관계 정정이 canonical admission·revision·audit 계약을
  우회하지 않도록 Go ViewModel과 명시적 mutation API로 제한
- 3.5에서 제거한 request link projection이나 같은 source turn 중심 규칙을 compatibility
  경로로 되살리지 않음

- `scene_guidance_proposal.v1`을 3.5 `supervisor_scene_proposal.v2`의 단일-owner extension으로
  구현하고, 사전 감독과 진단-only 사후 검토 경로 분리
- `output_fidelity_report.v1` 진단-only 경로
- 인물 혼동, 지식 누출, 단일 특성·전형화, 관계 급변·자동 상호성, already-realized
  replay·summary echo·scene stagnation, unsupported neutralization·escalation, thread tunnel
  vision·closure scope 누출, 문장 복사와 세계 규칙 위반 검출
- 검토 결과가 canonical 기억을 직접 변경하지 못하도록 admission 적용
- 감독관 proposal이 final output을 경유해 사건·관계·thread closure authority로 세탁되지 않도록
  causal precondition·agency owner·resolution scope 재검증
- timeout, 불완전 응답과 보조 모델 장애의 메인 기능 격리

### 4.6 라이브 품질 검증과 안정화

- 실제 사용자 동의 기반 장기 라이브 테스트
- 서로 다른 관찰 능력 profile에서 동일 시나리오 비교
- 각 능력 profile에서 지원 OFF와 지원 ON의 맹검 비교
- 첫 출력 채택률, 리롤, 비용, 지연과 설정 이행 실패를 함께 측정
- 관계 direction/domain transition과 realization→다음 brief→final output의 source ID E2E correlation
- eligible→selected/related/deferred→brief→output→thread transition의 coverage와 한 thread 해결 뒤
  sibling·ancestor·session 상태 보존 E2E correlation
- 배포 전 OS별 시작·저장·업데이트·삭제 회귀 검증

## 13. 평가 기준

단일 총점으로 완료를 결정하지 않는다. 적어도 다음 실패율과 비용을 분리해 본다.

- 잘못된 화자·인물 귀속
- 인물 간 말투와 성격의 붕괴
- 인물별 지식·비밀 경계 누출
- 캐릭터 단일 특성 과장과 agency 상실
- 능력·관심·직업·외형·지위에서 사회적 성격·감정·말투를 무근거 파생한 횟수
- 관계·상태가 달라져도 하나의 archetype 행동만 반복한 횟수
- player/user 입력을 NPC의 호감·신뢰·애정·친밀감·복종 근거로 사용한 횟수
- wrong-direction·자동 reciprocity, relation-domain 전파와 근거 없는 magnitude·permanence transition
- 예시 대사 또는 근거 문장의 직접 재사용
- 시간, 장소, 세계 규칙과 세력 관계 위반
- 원인 없는 사건 전개와 미해결 서사 누락
- source-backed 제약·대가·목표 충돌·적대 세력을 무근거로 중화한 횟수
- 조용한 장면이나 합법적 hold에 근거 없는 사건·위협·배신·폭로를 강제한 횟수
- eligible thread가 설명 없이 누락되거나 한 thread만 반복 foreground되어 다른 thread가 굶는 횟수
- thread-local resolution이 sibling·parent·arc·saga·session·작품 종료로 전파된 횟수
- dormant·deferred를 resolved로 오인하거나 검색 결과 없음으로 이야기 완료를 판정한 횟수
- NPC·세력의 독립 목표·반대·행동 가능성을 user/player 우호나 수동성으로 바꾼 횟수
- current input delta 미응답, already-realized outcome 재연, resolved thread 부활과 summary echo
- 새 state·knowledge·decision·reaction·thread·causal/discourse 결과도 intentional-hold 근거도 없는 scene stagnation
- 현재 입력과 무관한 기억·원작 자료의 과잉 주입
- 불확실한 자료를 사실로 확정한 횟수
- source가 지지하는 반응·관계 변화·갈등·인과 진행을 보수성 때문에 누락·동결한 횟수
- capability unknown·compact profile·예산 부족을 이유로 필수 dimension을 조용히 억제한 횟수
- 선택적 route가 필요한 장면인데도 실행되지 않았거나 모든 장면이 단순로 분류된 횟수
- 사용자 리롤과 첫 출력 채택 여부
- 입력·출력 토큰 비용과 응답 지연
- 기존 장기 기억 저장·회상 회귀

평가 임계치는 구현 코드의 고정 숫자가 아니라 versioned 평가 profile과 실사용 증거로 관리한다. 품질 개선과 비용 증가를 따로 제시해 사용자가 정책을 선택할 수 있게 한다.

## 14. 필수 검증 시나리오

- 여러 인물이 동시에 대화하며 서로 아는 정보가 다른 장면
- 한 인물이 거짓말하고 다른 인물은 그 사실을 모르는 장면
- 직전 턴의 위치·부상·소지품 변화가 현재 행동을 제한하는 장면
- 세력별 목표와 자원이 충돌하는 대형 세계관 장면
- 과학·기계·전투 같은 한 가지 관심사가 있는 인물을 평면화하기 쉬운 장면
- 강한 능력이나 높은 지위만 설정된 인물에게 자료에 없는 냉정함·거만함·사회성 부족 같은 별도 성격을 부여하기 쉬운 장면
- 동일 인물이 친한 상대, 낯선 상대와 적대 상대에게 근거 없이 완전히 같은 태도를 보이기 쉬운 장면
- player character가 사소한 친절·도움·접촉을 했지만 NPC의 지속적 신뢰·애정·복종·상호
  감정 transition을 지지하는 source는 없는 장면
- 한쪽 인물의 감정만 근거가 있거나 직무상 명령을 수행했는데 반대 방향 감정·충성·동의로
  승격하기 쉬운 장면
- 한 번의 친밀 행동에 대한 consent scope만 있고 사랑·독점 관계·미래 동의를 자동
  확정해서는 안 되는 장면
- 단일 사건이 승인 설정·세계 규칙과 final output에서 큰 관계 변화를 직접 지지하여 고정
  횟수 없이 정상 transition되어야 하는 장면
- 설정 예시 대사를 현재 문맥과 무관하게 복사하기 쉬운 장면
- 원작과 사용자 분기가 충돌하는 장면
- 자료가 없거나 서로 충돌해 abstention이 필요한 장면
- 의미 없는 입력이라 지원 자료를 주입하지 않아야 하는 장면
- current input에 새 행동·질문이 있는데 직전 final output과 summary만 복기해 응답하지 않는 장면
- 이미 실현된 사건을 다음 턴에 다시 발생시키거나 해결된 thread를 다시 해결하는 장면
- 사용자가 recap·reflection·기다림을 요구해 `intentional_hold`가 맞으며 새 사건을 강제하면 안 되는 장면
- 과거 사건에 대한 다른 인물의 새 POV 반응은 허용하되 objective event를 중복 생성하면 안 되는 장면
- 표현은 달라도 outcome이 같은 반복과 표현은 비슷하지만 새 결정·지식·반응이 있는 진행을 구분하는 장면
- raw event, summary와 profile digest가 같은 root evidence일 때 같은 목적의 중복 주입을 억제하는 장면
- 같은 source와 장면을 `compact`, `standard`, `deep`으로 표현해도 authority·agency·관계·지식·
  연속성의 필수 의미는 동일하고 상세도와 표현만 달라지는 장면
- 모델 능력 evidence가 unknown이지만 높은 능력을 임의 추정해 필수 인물 카드와 경계를
  생략해서는 안 되는 장면
- 일부 정보는 충돌하지만 나머지 인물 상태와 current input response obligation은 명확하여,
  불확실한 unit만 분리하고 확정 가능한 지원은 계속해야 하는 장면
- 예산이 부족해 필수 dimension을 완전하게 전달할 수 없으므로 빈 성공 대신 누락 source와
  `simulation_degraded/coverage_gap`을 보고해야 하는 장면
- 갈등·거절·배신·결별 또는 큰 관계 변화가 source에서 직접 지지되는데 “안전”을 이유로
  무난한 친화·관계 동결·무행동으로 바꾸면 안 되는 장면
- 복수·정치 대립·생존 위협의 source-backed pressure가 남아 있지만 사용자가 휴식·관찰·
  회복·대화를 택해, 압력을 삭제하지 않으면서도 새 충돌을 강제하지 않아야 하는 장면
- 적대 세력의 발동 조건이 충족되어 실제 제약과 대가를 반영해야 하지만 user/player에게
  우호적으로 만들거나 일상 대화만 반복해서는 안 되는 장면
- 여러 독립 thread 중 하나만 해결되어 sibling·parent·후속 consequence는 열려 있어야 하고,
  작품이 끝난 듯한 closure를 만들면 안 되는 장면
- 현재 선택되지 않은 thread가 source-linked defer reason과 lifecycle을 유지하고 다음 관련
  입력에서 다시 eligible해져야 하는 장면
- 현재 검색 결과가 없거나 모든 foreground item이 처리됐지만 dormant·background thread와
  session은 종료되지 않는 장면
- user/player가 제시된 갈등에 즉시 참여하지 않기로 했을 때 그 결정을 대신 뒤집지 않으면서
  NPC·세력의 독립 목표와 이미 발동한 consequence는 보존해야 하는 장면
- 감독관이 근거 없는 공격·배신·화해·thread closure를 제안하고 본문 모델이 이를 출력했어도,
  final span만으로 permission·authority가 생기지 않아 4.0 admission에서 거부되어야 하는 장면
- thread가 다른 consequence로 변형되거나 source-backed 근거로 다시 열릴 때 lineage를
  보존하되 단순 recap만으로 resolved thread를 부활시키지 않는 장면
- 감독관 또는 사후 진단이 필요한 복잡한 장면과 실제로 skip 가능한 단순 장면을 함께 넣어,
  route 실행·skip reason·실패 격리가 모두 관찰되어야 하는 장면
- 삭제, 리롤, 분기와 rollback 이후 이전 상태가 재등장하면 안 되는 장면
- 원작 DB, 보조 모델 또는 Chroma가 실패해도 메인 기능이 계속되는 장면
- 기능 OFF에서 현재 Archive Center 결과가 바뀌지 않는 장면

각 regression test는 해당 기능을 제거하거나 반대로 구현했을 때 실패해야 한다. mock과 문자열 검사는 실서비스 통합 증거로 보고하지 않는다.

## 15. 완료 조건

4.X 시뮬레이션 지원은 다음 조건을 모두 만족해야 완료로 볼 수 있다.

- 장기 기억이 여전히 최우선이며 기존 동적 예산과 저장 계약이 손상되지 않음
- 원작 DB가 선택 기능으로 격리되고 장애가 메인 기능을 막지 않음
- 장면 실행 계약이 Go에서 만들어지고 JavaScript가 별도 정책 엔진이 되지 않음
- 기능 OFF 시 기존 실제 payload, 저장, 삭제와 회상 결과가 보존됨
- 의미 없는 입력과 자료 부족 시 임의의 내용을 강제 주입하지 않음
- 활성 인물 수, 후보 수, 모델, 작품, 점수와 가중치 하드코딩이 없음
- 인물별 지식·관계·목적·감정·신체 상태와 말투가 서로 분리되어 전달됨
- 능력·관심·직업·외형·지위와 성격·감정·말투의 의미 영역이 분리되고 영역 간 영향에는 source evidence가 있음
- 관계별 태도, 현재 상태, 반례와 내적 모순이 단일 archetype 압축 과정에서 손실되지 않음
- 4.0 방향·domain별 관계 current/history와 transition 근거가 `relationship_view`·실제
  payload·output report에서 같은 source ID로 대조되고 user/player 우대·자동 상호성·
  cross-domain·영속 관계 승격이 없음
- 예시 대사를 그대로 재사용하지 않고 행동·말투 특징으로만 활용함
- 세계 규칙과 인과관계가 현재 장면에 필요한 범위로 전달됨
- current input delta, already-realized outcome, response obligation, causal frontier와
  intentional hold가 구분되고 직전 사건·summary의 재연 고리가 없음
- 모든 eligible thread가 selected·related·source-linked deferred 중 하나로 추적되며 attention과
  lifecycle이 섞이지 않음
- source-backed 압력·actor 목표·대가가 무근거 중화되지 않고, 합법적 조용한 장면에는 사건을
  강제하지 않아 unsupported neutralization과 escalation을 모두 방지함
- thread resolution이 명시된 ID·scope에만 적용되고 sibling·parent·arc·saga·session·작품
  종료로 자동 전파되지 않음
- supervisor proposal과 final output occurrence가 관계·사건·closure permission으로 세탁되지
  않고 causal precondition·agency owner·resolution scope admission을 통과함
- 합법적 recap·reflection·다른 POV 반응은 허용하며 턴당 사건을 강제로 만들지 않음
- 감독관·critic·verifier 문장이나 합의가 memory·관계·offscreen event의 source가 되지 않음
- 선택적 검토 실패가 정상 성공으로 위장되지 않고 메인 출력·저장을 막지 않음
- `SIM-PRE-SUPERVISOR`와 `SIM-POST-AUDIT`의 production route, 실행·skip·timeout·malformed·
  기능 OFF 경로가 실제로 검증되고 per-turn 선택성을 구현 생략으로 사용하지 않음
- 서로 다른 능력 profile에서 지원 OFF 대비 목표 실패 범주의 감소·비퇴행을 requirement별로
  재현하며, 설정 이행과 첫 출력 채택을 서로 대체하지 않고 각각 보고함
- 고성능 profile에서 과잉 지시로 인한 품질 저하가 없고 capability unknown이나 compact
  표현이 필수 의미 축소·silent suppression을 만들지 않음
- source가 지지하는 관계·감정·갈등·인과 진행이 안전 또는 보수성 명목으로 동결되지 않으며,
  unsupported 확장과 supported omission을 모두 검출함
- 개선 효과와 입력 비용·출력 비용·지연을 함께 공개함
- 실제 RisuAI, MariaDB와 Chroma 경로를 사용한 증거가 있음
- `SIM-INTENT-FIDELITY`를 포함한 모든 requirement가 `release_gate_verified`이고 open·blocked·
  `implemented_unverified` 항목이나 승인되지 않은 범위 변경이 없음
- 변경 작업마다 JavaScript 추가·삭제 줄과 남은 adapter-side 정책을 보고함

### 15.1 완료 상태

requirement와 phase 상태는 최소한 다음을 구분한다.

- `open`: 아직 production owner 또는 구현이 없음;
- `blocked`: 필수 결정·환경·근거가 없어 다음 gate에 진입할 수 없음;
- `preparatory`: 문서·schema·DTO·prompt·trace·fixture만 존재;
- `implemented_unverified`: production code는 연결됐지만 실제 host/payload/quality gate가 부족함;
- `integration_verified`: 실제 RisuAI observation에서 Go plan과 payload 적용까지 대조됨;
- `release_gate_verified`: 요구별 부정·변형·장기 라이브·장애 격리 증거까지 통과함.

모든 Requirement ledger 항목이 `release_gate_verified`이거나 사용자가 명시적으로 scope를 변경하기
전에는 4.X 전체를 완료·핵심 완료·사실상 완료라고 표현하지 않는다.

### 15.2 완료 증거로 인정하지 않는 방식

| 금지 방식 | 왜 불충분한가 | 필요한 대체 증거 |
|---|---|---|
| 논문·URL·자료 위치 발견 | 참고 근거를 찾은 것이 production 기능이나 자료 적용을 뜻하지 않음 | 실제 채택 항목, owner, payload와 output correlation |
| 문서·schema·DTO·prompt 문자열 존재 | 계약이 실제 요청에 적용됐는지 증명하지 못함 | production Go route와 실제 RisuAI payload hash 대조 |
| mock-only·복제 구현·shadow trace | 실제 host·DB·vector·payload 부작용과 선택 경로를 증명하지 못함 | 실제 runtime E2E와 guard 제거·반전 mutation test |
| 한 profile·한 장면의 happy path | 모델 적응·복잡도·관계·지식·실패 격리를 증명하지 못함 | 능력·장면·branch·budget·failure 변형 fixture |
| 단일 평균 점수 또는 `A 또는 B` 개선 | 한 실패의 악화를 다른 지표가 숨길 수 있음 | requirement별 실패·비퇴행·비용을 분리한 결과 |
| 선택적 route 전부 skip | 구현되지 않은 기능을 비용 절약으로 위장할 수 있음 | 실행 필요 장면과 정당한 skip 장면의 route evidence |
| `unknown`·빈 카드·no-op 성공 | 과잉 억제와 미구현을 안전으로 위장할 수 있음 | known positive의 실제 지원과 unknown boundary fixture |
| 진단 경고만 표시 | 본문 요청에 지원 계약이 적용됐는지 증명하지 못함 | plan item→payload span→출력 fidelity correlation |
| 테스트 package와 실제 loaded artifact 불일치 | 검증한 코드와 사용자가 실행한 코드가 다름 | source commit·build·package·loaded artifact hash chain |

### 15.3 Completion evidence manifest

각 phase와 최종 완료 보고는 다음을 제출한다.

- 원래 사용자 요구→requirement ID→production owner→fixture→실환경 evidence 추적표;
- commit/build ID, contract·policy version과 실제 loaded artifact hash;
- RisuAI Host Context ID·scope·revision·hash와 실제 payload 포함 observation;
- 4.0 memory/reference source ID에서 simulation snapshot·character card·scene brief로 이어지는 lineage;
- 4.0 thread lifecycle fingerprint와 eligible·selected·related·deferred coverage, 각 defer reason,
  `progression_change_envelope`와 출력 뒤 affected/sibling/ancestor state diff;
- backend plan/item hash, 실제 RisuAI payload span/hash와 final displayed output correlation;
- 모델 capability observation, unknown/conflict 상태와 선택한 표현·호출 profile의 이유;
- `compact/standard/deep` 간 must-preserve semantic parity와 축약·유예된 dimension;
- 선택적 supervisor/audit의 실행·skip·timeout·malformed 결과와 source-linked reason;
- 지원 OFF/ON의 requirement별 오류, 첫 출력 채택, 리롤, 입력·출력 비용과 지연;
- false positive뿐 아니라 false suppression·omission·관계 동결·current-input 미응답 결과;
- `simulation_degraded/coverage_gap`의 누락 source/dimension과 원 payload 보존 상태;
- 장애 주입, 기능 제거·조건 반전 시 실패하는 negative/mutation evidence;
- 실행한 정확한 명령, passed/failed/skipped 수와 사용한 실제 외부 runtime version;
- requirement별 상태와 open·blocked·미검증·승인된 범위 변경;
- JavaScript 추가·삭제 줄 수와 adapter에 남은 business logic.

증거가 없거나 required test가 skip됐거나 실제 loaded artifact를 확인하지 못하면 complete가
아니라 `blocked` 또는 `implemented_unverified`다.

### 15.4 의미·상태 위장 방지

다음 상태를 서로 바꿔 보고하지 않는다.

- `no_relevant_support`: 정상 판정 결과 현재 request에 적용할 지원이 없음;
- `intentional_hold`: current input이 recap·reflection·대기를 요구해 새 사건을 강제하지 않음;
- `simulation_degraded`: 필수 지원 일부를 만들거나 전달하지 못함;
- `supervisor_skipped`: route는 정상이지만 source-linked 정책상 이번 턴 호출하지 않음;
- `supervisor_failed` / `audit_failed`: 호출·계약·timeout 실패;
- `support_disabled`: 사용자가 기능을 끔;
- `blocked`: 필수 결정·환경·evidence가 없어 완료 gate에 진입할 수 없음.

`safe`, `compact`, `unknown`, `no_relevant_support`는 실패·미구현·예산 잘림을 숨기는 성공
alias가 아니다. 전체 서비스가 ready여도 해당 요청의 degraded·failed 상태는 그대로 노출한다.

### 15.5 Change control

- requirement를 완화·제외·후속 이동하려면 원래 요구, 제외되는 RP 사례, 품질·비용·호환성
  영향, 대안, 재포함 조건을 문서화하고 사용자 명시적 승인을 받아야 한다.
- bounded slice나 단계별 구현은 실행 순서만 나누며 남은 requirement를 전체 완료 범위에서
  제거하지 않는다.
- `optional`을 미구현으로, `compact`를 의미 삭제로, `safe`를 무행동으로, `unknown`을 편의상
  공백으로 재정의하는 것은 계약 변경이며 승인 없이 허용하지 않는다.
- 구현 난이도, 외부 모델 품질, 비용, OS 차이, schema 필요성 또는 기존 green test는 범위
  축소 근거가 아니다.
- 평가 대상 profile·언어·장면·관계·branch·provider를 줄이면 축소된 검증 범위를 먼저
  공개하고 전체 완료로 보고하지 않는다.
- 남은 결정은 owner, 결정 단계, 합격 evidence와 다음 단계 차단 조건을 가지며 무기한
  “안전 검토 중” 상태로 둘 수 없다.

## 16. 아직 확정하지 않은 결정과 4.0 선행조건

다음은 구현 전에 별도 재현과 계약 검토가 필요하다.

- RisuAI가 최종 표시 전 draft 검토를 안전하게 허용하는지
- RisuAI Host Context 종류별로 신뢰할 수 있는 stable ID·scope·actual payload observation을 어디까지 제공하는지와 activation이 unknown인 범위
- 시뮬레이션 지원 예산을 기존 컨텍스트 크기에서 정확히 어떻게 유도할지
- 모델 능력 profile을 수동 설정, 관찰 기반 또는 혼합으로 운영할지
- 사후 검토를 진단-only보다 확장할 필요가 실제로 있는지
- 사용자별 비용·속도·품질 preset을 어떤 최소 UI로 제공할지

다음 항목은 4.X가 별도로 재결정하거나 저장 owner를 만들지 않는다. 4.0 구현 단계에서
production mapping을 확정해야 하는 상속 prerequisite이며 4.X는 검증된 결과만 읽는다.

- `relationship_state.v1`을 기존 관계 state/event에서 투영할지, normalized relation key나
  request-scoped read model이 필요한지와 direction·domain·transition·counterevidence·consent·
  rupture/recovery 보장 방식
- 기존 raw/event/thread 구조에서 `turn_realization.v1`과 root-evidence coalescing을 보장하는 방식
- 기존 `pending_threads`·event·evidence·hierarchy projection에서 `narrative_thread_lifecycle.v1`의
  stable ID, branch, dependency, consequence carry와 closure scope를 보장하는 방식

이 결정이 끝나기 전에는 임시 JavaScript fallback, 모델명 분기, 고정 인물 수 또는 고정 품질 점수를 추가하지 않는다.

## 19. 독립 검토와 연구 근거

2026-07-19 재검토에서는 관리형 독립 agent 세 개가 관계·캐릭터 구조, turn progression과
hardcoding·source 세탁 위험을 각각 읽기 전용으로 검토했다. 요청한 `kimi_coder`,
`glm_subcoder`, `deepseek_validator` 역할은 현재 환경에서 모두 `agent type is currently not
available`로 거부되어 사용한 것처럼 표시하지 않았다. 연결된 architecture, structure와
risk validation agent 결과를 Codex가 통합했고 로컬 Ollama API의 `glm-5.2:cloud`로 추가
반대검증을 수행했다.

공통으로 채택한 개선은 다음과 같다.

- 4.0 direction·domain별 `relationship_state.v1`과 4.X `relationship_view`·change envelope;
- final output에서 이미 실현된 outcome과 mention/recall을 구분하는 `turn_realization.v1`;
- current input delta, response obligation, causal frontier와 intentional hold를 구분하는
  `SIM-PROGRESSION`;
- 4.X 계약을 새 truth table이 아니라 sparse read model/proposal DTO로 제한;
- 4.0 말투 evidence를 소비하는 `voice_behavior_projection.v1`으로 중복 owner 제거;
- 감독관·critic report 자체를 source evidence로 사용할 수 없는 경계.

다음 제안은 채택하지 않았다.

- 관계는 항상 여러 interaction 뒤 점진적으로만 변해야 한다는 고정 규칙: 단 하나의
  authoritative 사건이나 세계 규칙이 큰 변화를 직접 지지할 수 있으므로 횟수·속도보다
  direction·domain·causal source·scope를 검증한다.
- 복기된 과거 기억을 단순 `stale`로 만들어 회상에서 제거하는 방식: 사용자 요청에 따른
  recap, flashback과 다른 POV 반응은 합법적이므로 raw history는 보존하고 realization type과
  delivery purpose를 구분한다.
- 관계 domain별 별도 score/table, anti-repetition DB·packet과 전용 LLM reviewer: 기존
  evidence/state/event/thread, scene brief와 fidelity report를 확장한다.

2026-07-20에는 같은 세 관리형 agent가 이번 추가 요구를 다시 교차 검토했다. architecture
review는 새 pressure 저장소 대신 4.0의 논리적 `narrative_thread_lifecycle.v1`을 기준점으로
삼고 4.X에는 request-scoped `thread_execution_view`만 추가할 것을 제안했다. structure
review는 lifecycle과 attention을 분리하고 thread-local resolution이 sibling·parent·상위
scope에 전파되지 않는 closure 규칙을 요구했다. risk validation은 감독관 proposal이 final
output에 섞인 뒤 사실·관계·종료 권한으로 세탁되는 경로를 release blocker로 지적했다.

세 검토에서 공통으로 채택한 내용은 다음과 같다.

- 압력을 장르·긴장 점수가 아니라 source-backed 제약·대가·actor/faction 목표 충돌로 정의;
- `must_preserve`, `must_account`, `may_advance`, `hold_allowed`, `must_not_assert`와
  `resolution_envelope`를 가진 대칭적 진행 경계;
- 모든 eligible thread를 selected·related·source-linked deferred로 설명하는 coverage;
- 조용한 장면의 합법성과 source-backed 압력 보존을 함께 검증하고 unsupported
  neutralization과 escalation을 모두 오류로 취급;
- one-thread tunnel vision, dormant→resolved 오인, local→global closure와 false story ending 방지;
- final displayed occurrence와 causal permission·agency·closure authority의 분리.

새 pressure DB, 장르 detector, tension score·curve, 고정 전개 cadence·thread 수·round-robin,
per-thread agent, JavaScript watcher와 `all_story_complete` flag는 기존 owner를 중복시키거나
정책을 하드코딩하므로 채택하지 않았다. 4.X의 새 요구는 `SIM-THREAD-FIDELITY` 하나로 묶고
기존 snapshot·brief·proposal·report 계약을 확장한다.

연구 자료의 수치·prompt·schema를 production 정책으로 복사하지 않고 실패 범주와 평가
관점만 clean-room으로 사용한다.

- [Towards Understanding Sycophancy in Language Models](https://arxiv.org/abs/2310.13548):
  user preference에 맞추는 학습이 독립 판단보다 동조를 강화할 수 있음을 다룬다. 이
  로드맵에서는 user/player input을 NPC의 감정·관계 evidence로 사용하지 않는 경계로
  대응한다.
- [InCharacter](https://aclanthology.org/2024.acl-long.102/): character fidelity를 지식·
  말투만이 아니라 다차원 성격으로 평가한다. trait-domain, 반례와 관계별 투영 근거다.
- [EmoCharacter](https://aclanthology.org/2025.naacl-long.316/): 성격·지식 일관성과 구별되는
  emotional fidelity 평가 필요성을 제시한다. stable personality, current emotion과 관계
  transition을 분리하는 근거다.
- [SPASM](https://aclanthology.org/2026.findings-acl.412/): 장기 다중 턴에서 persona drift,
  role confusion과 echoing을 다루고 인물별 관점 projection을 검증한다. Archive Center의
  perspective-bound character card와 repetition fixture에 대응한다.
- [NGEP](https://aclanthology.org/2022.aacl-short.24/): 생성 문장 자체보다 event structure를
  먼저 계획해 장기 인과 일관성을 보조하는 방향을 다룬다. 이미 실현된 outcome과 causal
  frontier를 분리하는 설계 근거로만 사용한다.
- [LongStory](https://arxiv.org/abs/2311.15208): 장·단기 context와 구조적 위치를 이용해
  coherence·completeness·repetition을 함께 평가한다. 본 문서에서는 고정 novelty 점수가
  아니라 realization/thread/source 기반 fixture로 변환한다.

논문이나 agent 의견은 구현 완료 증거가 아니다. 완료는 production Go owner, 실제
MariaDB·Chroma·RisuAI 경로와 guard 제거·반전 시 실패하는 negative/mutation evidence로만
판정한다.
