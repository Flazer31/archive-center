# Archive Center 5.0

주제: Persona Capsule과 Original Work DB의 독립 DLC 모듈화

상태: 구현 전 권위 로드맵, `preparatory`

기준일: 2026-07-24

대상:

- Persona Capsule DLC
- Original Work DB DLC
- Archive Center 5.0 DLC 통합 adapter와 기존 내부 구현의 안전한 제거

## 0. 결정 스냅샷

- Archive Center 4.0은 정밀 장기 기억의 lifecycle·복구·라이브 release gate를 그대로 소유한다.
- Archive Center 4.X는 4.0 기억과 원작 자료를 읽는 모델 능력 적응형 RP simulation 계층을 그대로 소유한다.
- 5.0은 4.X의 목적을 취소·축소·흡수하지 않는다. 각 DLC는 4.X 없이도 독립 작동하고,
  Archive Center와 결합하면 4.0 기억과 선택적으로 활성화된 4.X에 versioned read-only 근거를
  제공할 수 있다. 5.0은 장면·전개·활성 인물·서사 압력이나 모델 적응 정책을 다시 구현하지 않는다.
- 페르소나 캡슐과 원작 DB의 실제 독립 제품화, 저장소·UI·패키지 분리, single-owner cutover와
  기존 Archive Center 내부 구현 제거는 **Archive Center 5.0**이 소유한다.
- 4.0과 4.X에서는 5.0을 위해 현재 기능을 미리 제거하거나 임시 외부 저장소·병렬 writer·두 번째
  주입 경로를 만들지 않는다.
- 현재 Archive Center 내부 구현은 5.0 cutover gate가 통과할 때까지 production 기준 동작으로
  유지한다.
- 각 DLC는 Archive Center 없이도 설치·시작·관리·기본 사용이 가능한 독립 제품이어야 한다.
- Archive Center가 명시적인 versioned capability 계약으로 DLC를 인식하면, DLC의 근거를
  read-only로 받아 현재 세션의 기억·상태·예산과 결합해 더 강한 기능을 제공한다.
- 결합 모드에서는 한 요청에 하나의 최종 주입 owner와 데이터 영역별 하나의 canonical writer만
  존재한다.
- shadow 비교를 위한 bounded dual-read는 허용할 수 있지만 silent dual-write, 공유 table 직접
  접근, 두 제품의 동시 주입과 last-known 결과 재사용은 허용하지 않는다.
- Persona Capsule DLC와 Original Work DB DLC는 Archive Center 버전과 독립된 자체 `1.x`
  제품 버전을 사용한다. Archive Center 5.0은 지원하는 DLC contract 범위와 최소 제품 버전만
  명시한다.

## 1. 5.0의 목표

Archive Center 5.0의 목표는 기능 수를 늘리는 것이 아니라 현재 한 제품 안에 함께 들어 있는
두 선택 기능을 독립 제품으로 분리하고 Archive Center를 얇은 통합 허브로 만드는 것이다.

```text
현재
Archive Center.js
  -> archive-center-go
  -> 메인 기억 + 페르소나 캡슐 + 원작 DB

5.0 목표
Persona Capsule DLC ─┐
                     ├─ versioned read-only integration ─> Archive Center 5.0
Original Work DB DLC ┘                                  -> Go 최종 계획
                                                         -> RisuAI payload 적용
```

독립화 이후에도 다음 결과는 약화하지 않는다.

- Persona Capsule의 support-only authority, owner visibility와 secret guard;
- 원작 자료의 작품·판본·continuity·branch·time·knower·review·provenance;
- 메인 장기 기억과 원작 사실의 canonical truth 분리;
- MariaDB authority와 재구축 가능한 Chroma index 원칙;
- Go가 소유하는 최종 선택·예산·조립;
- RisuAI Host 관찰과 실제 payload 적용만 담당하는 JavaScript 경계;
- DLC가 없거나 실패해도 Archive Center 메인 시작·ready·저장·삭제·회상이 유지되는 장애 격리.

### 1.1 5.0으로 배치하는 이유

이 작업은 단순 파일 이동이나 UI 탭 분리가 아니다. 다음을 동시에 변경한다.

- 제품과 배포 단위;
- canonical data owner;
- DB·index migration과 rollback;
- capability와 contract version 협상;
- 요청별 주입 owner;
- 독립 실행 상태와 결합 실행 상태;
- updater, backup, 복구와 지원 OS 검증;
- 기존 내부 코드와 schema 사용 중단.

따라서 정밀 장기 기억의 release closure인 4.0이나 simulation 소비 계층인 4.X에 섞지 않는다.
물리적 분리와 기존 경로 제거는 breaking lifecycle 작업으로 취급하고 5.0에서 독립적으로
검증한다.

## 2. 버전과 제품 소유권

| 구간 | 소유하는 범위 | 소유하지 않는 범위 |
|---|---|---|
| Archive Center 4.0 | 메인 정밀 장기 기억, capability·namespace·read-only export 기반, lifecycle·복구·release gate | DLC 독립 패키징, 외부 저장소 cutover, 기존 내부 기능 제거 |
| Archive Center 4.X | 검증된 기억·원작 자료를 소비하는 인물·세계·세력 simulation과 모델 능력 적응 | 페르소나·원작 canonical storage, DLC 배포와 migration |
| Persona Capsule DLC 1.x | 독립 capsule/entry, privacy, import/export, standalone UI·저장·기본 적용 | Archive Center 메인 기억과 session canonical truth |
| Original Work DB DLC 1.x | 작품·판본·continuity·원문·provenance·review·Canon Pack·Local Overlay·원작 검색 | Archive Center 세션 사건·관계·profile과 메인 기억 |
| Archive Center 5.0 | capability 협상, session binding, read-only adapter, 최종 Go 예산·조립, cutover와 내부 본체 제거 | DLC canonical row 직접 수정, DLC 내부 ranking·review 재구현 |

4.X의 4.1~4.6 단계 번호는 기존 simulation 로드맵을 유지한다. 5.0 준비를 이유로 이 번호를
재사용하거나 기존 완료 조건을 축소하지 않는다.

## 3. 현재 상태와 출발점

### 3.1 Persona Capsule

현재 페르소나 캡슐은 논리적으로 optional이지만 독립 제품은 아니다.

- `PersonaCapsuleStore`, `PersonaMemoryCapsule`, `PersonaMemoryEntry`,
  `PersonaCapsuleAttachment`가 공용 Go store와 MariaDB 구현에 있다.
- capsule과 entry는 숫자 DB ID, `source_chat_session_id`,
  `target_chat_session_id`와 내부 `source_memory_id`를 사용한다.
- complete-turn critic과 extraction이 주관 기억과 capsule candidate를 만든다.
- `/prepare-turn`이 target session에 attach된 entry를 읽고 `persona_recollection` lane을
  최종 기억 예산에 조립한다.
- candidate queue, 승인, 생성, attach와 관리 UI가 `Archive Center.js` 안에 있다.
- 현재 응답과 저장 형식에는 독립 제품용 contract/schema version, portable stable ID,
  revision과 content hash가 완전한 경계로 존재하지 않는다.

현재 `support_only_persona_recollection`, `canonical_write=false`,
`current_world_truth=false`, explicit target attachment 원칙은 5.0에서도 보존한다.

### 3.2 Original Work DB

원작 DB는 데이터와 검색 영역이 이미 메인 기억에서 비교적 강하게 분리돼 있다.

- `reference_works`, continuity, document, timeline, entity/alias, claim/knower,
  review, provenance와 session binding/runtime이 별도 영역을 가진다.
- `ReferenceLibraryStore`는 session canonical store와 구분된 optional extension이다.
- 원작 전용 Chroma collection과 별도 reference budget이 있다.
- Canon Pack manifest, Local Overlay, source observation과 package lifecycle 계약이 있다.
- supplement는 현재 장면의 빠진 자료를 보완하고 primary는 명시적으로 선택한 경우에만
  주요 설정원이 된다.

그러나 같은 `archive-center-go`, MariaDB store·설정·인증·UI를 사용하며 `/prepare-turn`이
reference recall, Canon Base와 injection formatting을 같은 프로세스의 함수로 직접 호출한다.
현재 UI의 primary “단독 모드”는 원작 DB를 주요 설정원으로 쓰는 모드이지 Archive Center 없이
실행되는 독립 제품을 뜻하지 않는다.

## 4. 영구 소유권 경계

### 4.1 데이터 owner

| 데이터 | canonical owner | Archive Center가 할 수 있는 일 |
|---|---|---|
| 세션 원문·사건·상태·관계·profile·주관 지식 | Archive Center | 저장·admission·recall·delivery |
| authored persona capsule과 portable recollection | Persona Capsule DLC | 명시적으로 활성화된 read-only item을 요청하고 session에 binding |
| 작품·판본·continuity·원문·Canon fact·provenance | Original Work DB DLC | 승인되고 현재 scope에 맞는 read-only reference item을 요청 |
| 현재 RisuAI session·branch·request 관찰 | Archive Center adapter | 공식 Host가 노출한 범위만 전달 |
| 최종 payload 예산·우선순위·block 조립 | Archive Center Go | DLC 결과와 메인 기억을 한 번만 조립 |
| 실제 RisuAI payload 적용 | Archive Center JavaScript | Go가 반환한 완전한 block을 적용 |

한 제품이 다른 제품의 table, Chroma collection, migration metadata나 private raw source를
직접 읽거나 쓰지 않는다. 같은 MariaDB 서버를 사용할 수 있는지는 구현 시 별도로 결정할 수
있지만 database/schema/credential과 migration owner는 논리적으로 격리해야 한다.

### 4.2 truth와 identity

- authored persona baseline은 Archive Center가 세션 근거에서 파생한 current profile과 같은
  truth blob으로 합치지 않는다.
- persona, Host setting entity, Archive Center session entity와 original-work reference entity는
  별도 namespace를 유지한다.
- 이름·별칭·설명 유사도나 모델 추측만으로 identity를 병합하지 않는다.
- cross-link는 stable ID, namespace, evidence와 mapping revision을 가진 explicit binding이다.
- 원작 사실은 세션에서 실제로 발생한 사건·관계·인물의 기억으로 자동 승격하지 않는다.
- capsule recollection은 현재 세계의 객관적 진실, 상대 인물의 지식이나 현재 관계를 자동
  변경하지 않는다.

## 5. 공통 DLC 통합 계약

이 장은 transport와 API endpoint를 확정하지 않는 논리 계약이다. 실제 RisuAI와 지원 OS에서
검증한 뒤 local HTTP, 공식 plugin communication 또는 다른 지원 transport 중 하나를 선택한다.
플러그인명, 파일명, process명, DOM 문구나 비공식 요청 ID 추측은 capability 확인 근거가 아니다.

### 5.1 Capability manifest

각 DLC는 최소 다음을 명시적으로 반환해야 한다.

- 제품 stable ID와 제품 version;
- 지원 contract와 schema version;
- 제공 가능한 read capability와 선택적 write capability;
- corpus/capsule generation과 revision;
- standalone 또는 integrated 동작 mode;
- health, retryability와 영향 lane;
- privacy·raw-source export 가능 범위;
- 최소 호환 Archive Center version;
- migration 중인지, read-only인지와 canonical writer 상태.

Archive Center는 required capability가 없거나 version이 맞지 않으면 `incompatible`을 명시하고
해당 DLC lane만 사용하지 않는다. JavaScript가 과거 내부 selection·budget·assembly를
silent fallback으로 되살리지 않는다.

### 5.2 요청과 결과

Archive Center의 요청은 최소 다음 경계를 가진다.

- request-scoped correlation과 deadline;
- session/branch와 관찰 가능한 generation·revision fence;
- 활성화된 capsule 또는 work/edition/continuity binding;
- 현재 장면에서 필요한 evidence dimension;
- visibility, spoiler, time, knower와 privacy ceiling;
- 요청 가능한 최대 item·문자 예산;
- 결과를 실제 payload에 사용할지 shadow 비교만 할지.

DLC 결과는 최소 다음을 반환한다.

- contract version, result revision과 계산에 사용한 corpus/capsule generation;
- `ok`, `empty`, `degraded`, `failed`, `incompatible`, `cancelled`,
  `stale_rejected` 중 안정적인 상태;
- source/provenance가 있는 immutable item;
- selected/deferred/excluded와 이유;
- visibility와 authority;
- 사용 문자 수, truncation과 coverage gap;
- retryability와 안전하게 표시 가능한 warning.

Archive Center는 요청 fence가 바뀌거나 deadline이 끝난 결과를 적용하지 않는다. 이전 요청의
결과, last-known selection 또는 부분 응답을 다음 payload에 재사용하지 않는다.

### 5.3 단일 주입 owner

- standalone mode에서 Archive Center가 없으면 각 DLC가 자신의 기본 RisuAI 적용 경로를
  소유할 수 있다.
- integrated mode에서 Archive Center가 현재 요청의 final composer가 되면 DLC의 직접 주입은
  중지되고 DLC는 read-only item만 반환한다.
- 같은 capsule이나 reference item을 DLC와 Archive Center가 각각 payload에 넣지 않는다.
- Archive Center Go가 메인 기억, persona와 reference의 우선순위·예산·중복 제거를 최종 결정한다.
- DLC는 메인 기억 예산을 차용하지 않고 Archive Center는 DLC 내부 ranking이나 review를
  다시 계산하지 않는다.

### 5.4 장애 격리

DLC가 미설치, OFF, 빈 상태, timeout, crashed, degraded 또는 incompatible여도 다음은 유지한다.

- Archive Center 시작과 `/ready`;
- raw conversation 저장;
- 메인 장기 기억 저장·검색·삭제·rollback;
- DLC가 없을 때의 기본 `/prepare-turn` 결과;
- 실제 RisuAI 요청과 표시 lifecycle.

일부만 만들어진 item을 정상 결과처럼 섞지 않는다. canonical mutation과 migration 실패는
fail-open 대상이 아니며 이전 committed generation을 유지한다.

## 6. Persona Capsule DLC 1.x

### 6.1 Standalone 완료 조건

Archive Center 없이 다음이 가능해야 한다.

- capsule과 entry의 생성·조회·수정·삭제;
- 수동 작성과 승인된 import;
- portable export와 round-trip import;
- persona 선택과 target context 활성화·비활성화;
- 명시적 privacy, visibility, reveal policy와 secret guard;
- 자체 저장소·UI·backup·upgrade·rollback;
- RisuAI에 support-only persona recollection을 적용하는 기본 경로;
- LLM 추출기 없이도 완전한 기본 동작.

portable contract는 Archive Center DB row와 무관한 stable capsule/entry ID, schema version,
revision, content hash, provenance, source kind, language, authority, visibility와 tombstone을
가진다. Archive Center 내부 `source_memory_id`는 선택적 외부 provenance일 수는 있어도
독립 identity가 될 수 없다.

### 6.2 Archive Center 결합 강화

사용자가 명시적으로 결합을 활성화하면 Archive Center는 다음을 추가할 수 있다.

- 현재 session과 stable persona/entity binding;
- source-backed candidate와 exact evidence pointer;
- 4.0의 stable/current/dynamic profile, 관계·반례와 current state를 읽은 relevance 판정;
- knower·owner visibility와 protected-secret hard filter;
- Go 최종 예산, 중복 억제와 실제 payload parity;
- final displayed lifecycle과 다음 턴 stale-result 차단.

Archive Center가 제공한 current profile이나 relation은 DLC의 authored baseline을 덮어쓰지
않는다. DLC entry가 사용됐다는 사실도 canonical memory admission 근거가 아니다.

### 6.3 분리 시 특별 위험

- 현재 숫자 ID와 chat session ID를 portable stable ID로 안전하게 매핑해야 한다.
- 현재 tag·문구 기반 보조 secret 추론은 명시 필드와 negative fixture로 교체해야 한다.
- complete-turn critic과 독립 DLC가 같은 candidate를 이중 생성하지 않아야 한다.
- 실제 사용자 OOC profile과 RP player/NPC persona를 명시적 namespace와 opt-in으로 분리한다.
- candidate queue와 UI state를 옮길 때 기존 pending item을 조용히 승인·삭제하지 않는다.

## 7. Original Work DB DLC 1.x

### 7.1 Standalone 완료 조건

Archive Center 없이 다음이 가능해야 한다.

- Canon Pack preview·validate·install·deactivate·remove·rollback;
- 작품·판본·continuity와 제목·별칭 검색;
- Private Full-Text Source Library의 로컬 보존;
- Local Canon Overlay와 pack provenance의 독립 보존;
- review/admission, conflict·uncertainty와 evidence inspection;
- exact·lexical 검색과 승인 자료 browse;
- embedding이 없을 때 semantic search만 degraded되는 동작;
- 원작 전용 vector index의 재구축과 generation 검증;
- 자체 UI·상태·backup·upgrade·rollback.

Source Discovery와 LLM extraction은 선택 기능이다. provider가 없어도 pack lifecycle, local
source 보존, provenance, review와 exact search는 작동해야 한다.

### 7.2 Archive Center 결합 강화

사용자가 작품과 continuity를 명시적으로 연결하면 Archive Center는 다음을 수행한다.

- 현재 세션의 branch·current node·reveal ceiling을 DLC 요청 scope로 전달;
- supplement 또는 primary mode와 session binding을 소유;
- 현재 장면의 missing evidence dimension 요청;
- 승인된 result의 source ID·revision·provenance를 보존;
- 메인 기억과 사용자 분기를 우선하고 원작 결과를 별도 예산으로 최종 조립;
- 원작 자료의 failure·coverage gap을 메인 기능과 분리해 표시.

원작 DB가 session memory row, character current state, relationship, profile이나 thread lifecycle을
직접 쓰지 않는다.

### 7.3 Canon Pack compatibility

현재 `compatibility.archive_center`는 Archive Center 내부 installer 기준이다. 독립 DLC로
이전할 때 기존 manifest를 조용히 재해석하지 않는다.

- 기존 pack version과 checksum·provenance를 보존한다.
- DLC engine compatibility와 Archive Center adapter compatibility를 구분한다.
- 필요한 manifest 변경은 새 contract version으로만 추가한다.
- 기존 pack을 자동 신뢰하거나 새로운 stable work/edition ID로 추측 병합하지 않는다.
- migration preview는 DB와 Chroma를 수정하지 않고 예상 mapping·충돌·누락을 먼저 반환한다.

## 8. Archive Center 5.0에 남는 얇은 adapter

5.0 cutover 뒤 Archive Center에 남는 책임은 다음뿐이다.

- DLC capability와 contract version 확인;
- 사용자 설정과 session binding;
- RisuAI의 실제 session·branch·request 관찰;
- DLC read request와 deadline·revision fence;
- 메인 기억·persona·reference의 최종 Go 예산·우선순위·중복 제거;
- 완전한 result block과 trace;
- JavaScript의 실제 payload 적용과 UI 상태 표시;
- DLC 장애 시 기본 Archive Center 경로 보존.

다음은 제거 대상이다.

- Archive Center 내부의 DLC canonical CRUD와 전용 저장 owner;
- 독립 제품으로 이동한 관리 UI와 candidate queue;
- 내부 전용 reference/capsule ranking·formatting의 중복 구현;
- 외부 DLC와 같은 데이터를 쓰는 병렬 writer;
- 호환 기간이 끝난 legacy adapter와 silent fallback.

MariaDB table이나 기존 사용자 데이터를 제거하는 것은 코드 제거와 별도 승인 작업이다.
5.0 release가 성공했다는 이유만으로 legacy data를 자동 삭제하지 않는다.

## 9. 구현 packet과 cutover 순서

### 5.0-A 현재 동작과 데이터 inventory

- Persona와 reference의 API, UI, store, schema, index, job, provider 설정과 `/prepare-turn`
  결합 지점을 고정한다.
- 기존 DB clone에서 row·hash·attachment·binding·vector generation을 읽기 전용으로 조사한다.
- standalone, integrated, OFF와 장애 시 현재 동작을 neutral fixture로 고정한다.

Exit gate:

- 모든 read/write/injection owner와 migration 대상이 누락 없이 ledger에 연결되고 실제 사용자
  데이터 mutation 없이 preview할 수 있다.

### 5.0-B Portable contract와 capability

- 공통 capability, request/result와 stable outcome을 확정한다.
- Persona stable ID·privacy·import/export contract를 확정한다.
- Original Work stable work/edition/continuity·provenance와 pack compatibility contract를 확정한다.
- transport는 공식 RisuAI와 지원 OS에서 재현한 뒤 선택한다.

Exit gate:

- contract mismatch, missing capability, stale revision과 privacy ceiling 위반이 stable negative
  result로 차단되고 제품명·파일·DOM 추측이 없다.

### 5.0-C 독립 제품 완성

- Persona Capsule DLC와 Original Work DB DLC가 Archive Center 없이 각각 standalone gate를
  통과한다.
- 자체 설치·UI·storage·upgrade·backup·rollback과 no-provider/degraded 상태를 검증한다.
- 기존 내부 데이터의 DB-write-free migration preview와 round-trip export/import를 검증한다.

Exit gate:

- Archive Center process, store, session API나 내부 row ID 없이 독립 기능이 완성된다.

### 5.0-D Read-only adapter와 shadow 비교

- Archive Center가 외부 DLC capability와 revision을 확인한다.
- 내부 현재 결과와 외부 DLC 결과를 bounded dual-read로 비교한다.
- shadow 결과는 payload, canonical write나 다음 요청 fallback에 사용하지 않는다.
- latency, selected/excluded, provenance, budget과 failure state를 비교한다.

Exit gate:

- 동일 fixture와 사용자 승인 DB clone에서 의미·ID·provenance·예산 차이가 설명되고 blocker가
  0개이며 DLC 장애 시 Archive Center base plan이 불변이다.

### 5.0-E Single-owner cutover

- 명시적 사용자·release 설정으로 external DLC를 canonical owner로 전환한다.
- 전환 transaction은 한 시점에 하나의 writer와 하나의 injection owner만 활성화한다.
- 내부 owner는 read-only compatibility 상태가 되며 새 write와 직접 주입을 중지한다.
- cutover generation, adapter version과 migration fingerprint를 기록한다.

Exit gate:

- restart·timeout·stale response·DLC crash·version mismatch·rollback rehearsal에서 dual-write,
  duplicate injection, stale resurrection과 data loss가 없다.

### 5.0-F 내부 본체 제거와 release closure

- 안정화 기간과 rollback rehearsal 뒤 Archive Center 내부 CRUD·UI·ranking·storage owner를
  제거한다.
- 얇은 adapter와 absence/degraded UI만 남긴다.
- legacy code와 compatibility read의 제거 조건을 evidence manifest에 연결한다.
- legacy table과 데이터 삭제는 별도 사용자 승인·backup·dry-run 없이는 수행하지 않는다.

Exit gate:

- source commit, test, loaded package hash, 실제 RisuAI와 지원 OS의 standalone/integrated/OFF
  결과가 연결되고 open/blocked requirement가 없다.

## 10. 필수 검증 matrix

### 10.1 Standalone

- Persona Capsule DLC만 설치한 상태에서 생성·import/export·활성화·privacy·기본 적용;
- Original Work DB DLC만 설치한 상태에서 pack lifecycle·browse·review·exact search;
- provider·embedding 없음, DB restart, index 없음과 partial failure;
- 독립 upgrade·rollback 뒤 stable ID·revision·provenance 보존.

### 10.2 Archive Center without DLC

- 두 DLC가 모두 없거나 OFF여도 시작·ready·prepare·complete·삭제·리롤·rollback·장기 기억이
  4.0/4.X 기준과 동일;
- DLC 설정·placeholder·empty block이 실제 payload에 들어가지 않음;
- JavaScript가 과거 내부 조립 경로를 silent fallback으로 되살리지 않음.

### 10.3 Integrated

- Persona entry와 original reference가 각각 한 번만 선택·주입됨;
- 현재 사용자 입력과 메인 기억이 원작·persona보다 우선함;
- 원작 사실, authored persona와 session canonical truth가 분리됨;
- wrong session·branch·continuity·time·knower·visibility 후보가 차단됨;
- supplement와 primary 예산, persona와 메인 기억 예산이 서로 차용되지 않음;
- 실제 Go item/hash/used chars와 RisuAI payload가 일치함.

### 10.4 Failure와 concurrency

- DLC timeout·crash·malformed·incompatible·stale revision에서 이후 DLC item 적용 0;
- 같은 요청의 중복 schedule과 중복 injection 0;
- active external call과 남은 background request 0;
- cutover·restart·rollback 중 canonical writer 1개;
- migration 실패 시 이전 committed owner와 generation 유지;
- last-known result의 다음 요청 재사용 0.

### 10.5 Security와 privacy

- API key, Authorization, cookie, private raw source와 DB credential 노출 0;
- 실제 사용자 OOC profile의 무동의 capsule export 0;
- owner-private recollection의 player/다른 인물 누출 0;
- Canon Pack에 배포 권한 없는 full text 포함 0;
- trace와 UI에는 안전한 stable status와 bounded provenance만 표시.

## 11. Migration과 rollback 원칙

- 기존 내부 구현은 5.0-E 전까지 canonical owner다.
- schema·data migration은 항상 preview, count, mapping, conflict와 checksum을 먼저 반환한다.
- migration은 idempotent하고 중단·재개 가능해야 한다.
- source text, review state, attachment, binding, provenance와 stable user choice를 보존한다.
- external owner로 전환한 뒤 stale internal snapshot을 자동 fallback으로 사용하지 않는다.
- rollback은 같은 revision을 가진 export/import와 명시적 owner cutover로 수행한다.
- application rollback과 사용자 데이터 삭제를 같은 작업으로 묶지 않는다.
- legacy DB/table/Chroma 삭제는 별도 승인, backup·recovery point와 dry-run이 있어야 한다.

## 12. Stop condition

다음 중 하나라도 발생하면 5.0 cutover 또는 내부 제거를 중단한다.

- DLC가 없을 때 Archive Center 기본 동작이 달라짐;
- shared table 직접 접근이나 양쪽 canonical dual-write가 필요함;
- plugin명·process명·파일·DOM·내용 hash만으로 상대 제품을 감지함;
- contract version, corpus/capsule revision 또는 request fence가 불명확함;
- 같은 item이 DLC와 Archive Center에서 중복 주입됨;
- 원작 사실이 session event로, authored persona가 current profile로 자동 승격됨;
- private raw source, secret, 사용자 OOC profile이나 인증 정보가 경계를 넘어 노출됨;
- migration fingerprint나 rollback rehearsal 없이 기존 내부 owner를 제거함;
- standalone gate가 실패한 상태에서 integrated mode만 통과시켜 완료를 주장함;
- 4.0 또는 4.X의 release blocker를 5.0 fallback으로 우회함.

## 13. 비목표

5.0 DLC 분리 작업은 다음을 자동으로 포함하지 않는다.

- 새로운 AI 역할이나 추가 LLM 호출;
- 원작 사실·persona candidate의 자동 승인;
- 두 번째 메인 기억 DB;
- 새 장면 simulation, Judge, Prover, Table Read 또는 출력 재작성;
- 원작 완전성의 고정 score·레코드 수 기준;
- plugin marketplace, 원격 Canon registry나 cloud sync;
- 사용자 승인 없는 실데이터 reindex·dedupe·orphan 삭제·session 병합;
- 기존 4.0/4.X requirement의 축소.

추가 기능은 독립 requirement, 비용·privacy·lifecycle 검토와 사용자 승인을 받아 별도 버전으로
배치한다.

## 14. 완료 판정

현재 문서 상태는 `preparatory`다. 문서, DTO, schema 초안, mock server, UI placeholder,
syntax test나 일부 in-memory test만으로 5.0을 구현 또는 완료로 표시하지 않는다.

최종 evidence manifest는 최소 다음을 연결한다.

- requirement와 owner;
- source commit과 변경 파일;
- contract/schema/product version;
- migration preview·apply·rollback fingerprint;
- standalone, Archive Center without DLC와 integrated test;
- failure·concurrency·privacy negative test;
- 실제 RisuAI, 지원 OS, MariaDB/Chroma 또는 DLC 자체 store 결과;
- loaded artifact/package hash;
- 내부 경로 제거와 legacy data 보존 확인;
- open, blocked, implemented_unverified와 release_gate_verified 상태.

5.0 완료는 두 DLC의 독립 실행, Archive Center 결합, absence/degraded parity, single-owner cutover,
rollback과 내부 본체 제거가 실제 release artifact에서 모두 검증된 경우에만 선언한다.
