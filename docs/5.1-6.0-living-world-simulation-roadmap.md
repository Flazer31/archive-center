# Archive Center 5.1-6.0 Living World 상태 전이·행동 시뮬레이션 로드맵

> 현재 지위: Living World의 상세 초안이지만 번호는 역사적이다. 새 통합 정본의
> 8.1~9.0이 이 범위를 소비한다. 4.1부터 이어지는 전체 제품 흐름과
> `AC Ensemble Agent` 6.1~7.0·8.3 경계는
> [`4.1-9.0-integrated-roadmap.md`](../../_archive/future-reference/4.1-9.0-integrated-roadmap.md)를 우선한다.
> 이 문서에 계획된 계약명은 현재 source 구현을 뜻하지 않는다.
> Standalone의 `main_draft/rewrite/final composer`와 Integrated의
> `scene_context/role turn/performance transcript/transcript assembler`를 혼용하지 않는다.

- 상태: 초안 / 구현 전 계획 / 버전 배정 제안 / 현재 구현 주장 없음
- 범위: Archive Center 5.0 release closure 이후의 5.1~6.0
- 작성 목적: 장기 RP에서 인물과 세계가 현재 입력에만 반응하는 현상을 줄이고, 시간·공간·지식·생존·관계·인과 제약 안에서 인물과 세력이 지속적으로 행동하는 효과를 만든다.

이 문서는 학습된 범용 예측 모델을 새로 만드는 계획이 아니다. Archive Center가 이미 보유한
기억·상태·관점·관계·thread·표시 최종본 계보 위에 **source-backed explicit state, typed
action, action-conditioned successor/outcome prediction, world clock, observation assimilation과
제한된 counterfactual rollout**을 추가하는 **world-model-inspired symbolic narrative simulation**
계획이다. 현재 연속성 검사는 이 계획의 안전 기초이지만, 그 자체나 이 플러그인 전체를 학습형
월드 모델이라고 부르지 않는다.

최종 목표는 world-model 연구를 최대한 충실하게 복제하는 것이 아니다. 그 구조 중 RP·chat에서
사용자가 실제로 체감할 수 있는 부분만 빌려 **인물이 자기 상태와 목표를 이어 가고, 떨어진 인물이
순간이동하지 않으며, 죽은 인물이 근거 없이 부활하지 않고, 지식·관계·장면 밖 인과가 다음 대사와
행동에 유의미하게 드러나게 하는 것**이 목표다. 학술적 유사성이 높아도 이 체감을 개선하지 않거나
비용·지연·privacy·창작 자유를 악화시키는 구성은 구현 우선순위가 아니다.

## 0. 결정 스냅샷

- 5.1~5.9는 `Living World` 세대의 구축·통합·검증 단계이고, 6.0은 검증된 release profile을
  안정 제품 경계로 승격하는 milestone이다.
- 6.0은 날짜나 기능 수만으로 자동 승격하지 않는다. 승격할 profile의 포함 requirement와 모든
  non-waivable gate가 실제 RisuAI 장기 세션에서 `release_gate_verified`가 아니면 그 profile은
  5.x/beta/disabled에 머문다. optional profile 미완료가 core 완료로 세탁되거나 core 승격을
  불필요하게 막지 않는다.
- 4.6~5.0은 검증된 기억과 세계 자료를 장면 실행 계약으로 투영하고 출력 위반을 진단한다.
  5.1의 continuity kernel은 불가능한 delta를 거르는 최소 안전층이다. 유의미한 world-model
  **흉내 효과**는 여기에 관찰 동화, clock, typed action, 행동 조건부 successor/outcome,
  prediction residual과 admission loop까지 연결됐을 때만 성립한다.
- 별도 `AC WorldModel.js` 또는 두 번째 세계 상태 저장소를 만들지 않는다. 핵심 상태 전이,
  actor scheduling, 인과 검증과 canonical admission은 Archive Center Go에 통합한다.
- 사용자에게는 DLC와 비슷한 선택 기능으로 보일 수 있지만, canonical state owner는 항상
  Archive Center다. 기능 OFF와 단계별 mode를 제공하여 기존 기억 기능과 장애를 격리한다.
- AC Ensemble Agent Integrated는 인물별 모델 호출, 순차 역할 연기와 공개 performance
  transcript의 lossless assembly를 담당할 수 있다.
  인물 선정, private context 배정, 발언 순서, 상태 전이 승인, 반복 종료와 canonical write는
  Archive Center Go가 소유한다.
- 보조 LLM, AC Ensemble Actor, OpenRouter Fusion과 다른 검토 모델은 모두 proposal 또는
  review producer다. 어느 모델도 합의·점수·문장만으로 canonical truth를 기록할 수 없다.
- 언급은 물리적 존재가 아니다. 현재 입력에 이름이 등장했다는 이유로 인물을 현재 장소에
  출현시키거나, 사망·구속·거리·이동 시간·지식 경계를 무시하지 않는다.
- 안전성은 세계와 인물을 정지시키는 정책이 아니다. 근거 없는 행동은 막고, 근거와 조건이
  충족된 독립 행동·갈등·관계 변화·장면 밖 진행은 실제로 허용해야 한다.
- world-model component는 이름이나 논문과의 유사성으로 채택하지 않는다. 사전 등록한 사용자
  가시 실패를 줄이거나 정당한 행동·상호작용을 늘리는 marginal contribution이 없으면 제거,
  축소 또는 research 상태로 남긴다.

### 0.2 명칭과 계약 이름의 지위

- 내부 기능명: `world_simulation`
- 사용자 노출 후보명: `Archive Center Living World`
- 피해야 할 완료 표현: `범용 월드 모델`, `학습된 물리 시뮬레이터`, `완전 자율 세계`,
  `AGI형 인물`
- 이 문서에서 `simulation`은 source-backed state와 규칙 안에서 후보 전이를 계산·검증하는
  bounded process를 뜻한다.
- 이 문서의 backtick 이름은 책임과 계보를 설명하기 위한 **논리적 계약 예시**다. 현재 파일,
  API, DTO, table 또는 migration의 존재를 뜻하지 않으며, 구현 전 owner mapping에서 기존
  계약 확장으로 표현 가능한지 먼저 확인한다.

## 1. 해결하려는 사용자 문제

### 1.1 현재 입력 중심 반응

인물이 자기 목표, 위치, 일정, 관계와 이전 행동보다 현재 사용자 입력에 과도하게 끌려가면
세계가 살아 있는 것이 아니라 매 턴 다시 생성되는 것처럼 보인다.

5.1~6.0은 다음을 분리한다.

- 사용자가 이번 응답에서 다뤄 달라고 한 `response_obligation`;
- 현재 장소에서 물리적으로 행동할 수 있는 `scene_presence`;
- 현재 사실을 알고 반응할 수 있는 `knowledge_eligibility`;
- 자기 목표와 조건에 따라 행동 후보를 가질 수 있는 `actor_eligibility`;
- 행동 결과를 실제 세계 상태로 기록할 수 있는 `transition_authority`.

사용자 입력은 첫 번째 항목을 높일 수 있지만 나머지를 자동으로 참으로 만들지 않는다.

### 1.2 방지해야 할 대표 실패

- 멀리 떨어진 인물이 이름이 언급되자 즉시 현재 장면에 등장함;
- 이동 시간이나 통로 없이 장소가 바뀜;
- 사망·의식 불명·구속·중상 상태인 인물이 정상적인 물리 행동을 수행함;
- 인물이 관찰하거나 전달받지 않은 사실을 알고 행동함;
- 한 장면의 호감 표현이 상호적이고 영속적인 관계로 즉시 승격됨;
- 한 관계 domain의 변화가 다른 모든 관계 domain으로 전파됨;
- 감독관·Actor·Judge의 제안이 실제 발생한 사건처럼 저장됨;
- 장면 밖 인물과 세력이 사용자가 다시 언급할 때까지 완전히 정지함;
- 반대로 모든 장면 밖 인물을 매 턴 호출하여 비용과 임의 사건을 폭증시킴;
- 한 thread의 해결이 다른 thread, arc, session 또는 작품 전체의 종료로 전파됨;
- 리롤·삭제·분기 뒤 폐기된 rollout이나 이전 최종본이 다시 canonical state를 오염함.

### 1.3 성공 체감

사용자는 내부 상태표보다 다음 결과로 성공을 판단한다.

- 부재 중인 인물은 이유 없이 나타나지 않지만, 연락·소문·대리인·도착 준비처럼 가능한
  방식으로 장면에 영향을 줄 수 있음;
- 장면 밖 인물이 자기 목표를 진행하고 나중에 흔적·보고·결과로 발견될 수 있음;
- 죽은 인물은 일반 물리 Actor로 행동하지 않지만 회상·기록·꿈·환영·유령·부활 규칙이
  있는 작품에서는 해당 mode와 조건에 맞게 등장할 수 있음;
- 관계는 사건의 크기, 당사자, domain, 반례와 누적 근거에 맞게 변화함;
- 인물이 모르는 사실에는 오해·추측·무지로 반응하고, 공개된 뒤에만 지식 상태가 변함;
- 여러 인물이 서로의 실제 공개 행동에 반응하며, 최종 장면이 그 결과와 모순되지 않음;
- 실패하거나 비용이 부족한 턴에는 기존 메인 생성과 기억 저장이 중단되지 않고 명시적인
  degraded trace가 남음.

#### Livingness scorecard — 세계가 얼마나 유동적이고 살아 움직이는가

`livingness`는 사건 수, 상태 변화량이나 agent 호출 수 하나로 계산하지 않는다. 많이 움직이기만
하면 무근거 plot 진행·관계 급변·사용자 agency 침해를 보상하게 된다. 다음 축을 따로 평가한다.

| 축 | 사용자가 느끼는 질문 | 관찰 가능한 지표 예시 |
|---|---|---|
| 목표 지속성 | 입력에 이름이 없어도 인물·세력이 하던 일을 이어 가는가 | source-backed goal 유지·재고·완료율, 입력 언급 의존도 |
| 상태 민감성 | 같은 입력도 위치·시간·생존·지식이 다르면 행동이 달라지는가 | paired-state action/outcome divergence와 설명 가능한 reason |
| 대안 유연성 | 한 행동이 막혔을 때 멈추지 않고 가능한 연락·우회·보류·준비를 찾는가 | hard violation 없이 채택된 causal alternative와 supported omission |
| 장면 밖 지속성 | 보이지 않는 동안의 변화가 나중에 흔적·소문·결과로 연결되는가 | trigger→hypothesis/admission→discovery lineage, arbitrary event rate |
| 상호 반응성 | 다른 인물이 실제 공개 행동의 결과에 맞춰 반응하는가 | accepted public outcome 후 행동 변화, blocked/private leakage rate |
| 장기 파급 | 부상·자원·믿음·관계가 한 턴 장식이 아니라 후속 선택에 남는가 | admitted state→후속 actor packet/action/displayed behavior correlation |
| 제약 속 생동성 | 세계 규칙과 user/player agency를 지키면서도 가능한 갈등·변화를 얼리지 않는가 | hard violation, policy freeze, 정당한 행동 누락을 분리한 비퇴행 |
| 비용 대비 체감 | 추가 호출이 실제 RP 차이를 만드는가 | matched-cost first-output adoption, reroll, p95 latency와 marginal gain |

종합 점수 하나로 safety와 생동성을 상쇄하지 않는다. 먼저 authority·privacy·agency·stale fence를
통과한 결과만 놓고 각 livingness 축과 비용을 비교한다. `움직임이 많음`, `극적임`, `관계 수치가
자주 변함`은 성공 지표가 아니며, 아무 변화도 없는 조용한 장면도 상태에 맞으면 정답일 수 있다.
반대로 모든 후보를 차단해 오류율만 낮추는 `frozen world`도 실패다.

### 1.4 이 문서가 말하는 world-model 참조 범위

| 분류 | 최소 의미 | 이 로드맵의 지위 |
|---|---|---|
| continuity validator | 현재 상태와 제안 delta의 모순·불가능성을 검사 | 5.1의 필수 안전 기초지만 이것만으로 world model 완료가 아님 |
| world-model-inspired symbolic narrative simulation | 명시 상태와 clock에서 typed action별 후속 상태·outcome을 제한적으로 계산하고 관찰·잔차로 다음 상태를 갱신 | 5.1~5.7의 실제 제품 목표; 학습형 world model과 다른 메커니즘 |
| learned latent world model | 데이터에서 잠재 상태와 dynamics를 학습해 미래를 예측 | 구현 계획 아님; 별도 연구 승인 없이는 추가하지 않음 |
| continuous physics/social simulator | 연속 물리·사회 전체를 정밀하게 계산 | 범위 밖이고 약속하지 않음 |
| orchestration controller | 어떤 규칙·Actor·reviewer 경로를 실행할지 선택 | 5.8의 책임이며 world dynamics 자체가 아님 |

따라서 “순간이동을 차단했다”, “상태표가 있다” 또는 “Actor를 여러 번 호출했다”만으로
world model을 구현했다고 표현하지 않는다. 다음 폐루프가 production owner와 실제 계보에서
연결될 때도 정확한 완료 표현은 `world-model-inspired simulation loop`다.

```text
canonical state S_t + source/Host observations O_t
  -> authority·diegetic-frame·time·branch 기준 observation assimilation
  -> Actor i가 볼 수 있는 O_i,t와 persistent goal/commitment
  -> typed action candidates A_i,t
  -> hard precondition + basic 또는 5.6 advanced conflict/reservation
  -> action-conditioned successor/outcome prediction과 resolved outcome
  -> Actor별 value vector와 필요 시 고위험 structured counterfactual 비교
  -> foreground/offscreen rollout state
  -> performance transcript renderer의 structured realization receipt + 실제 displayed lineage
  -> prediction residual와 ambiguity 판정
  -> admitted / admission_pending / rejected
  -> canonical state S_t+1과 다음 Actor별 관찰
```

`S_t+1`은 모델 문장, confidence, 다수결이나 rollout 존재만으로 생기지 않는다. 기존 Go
admission owner가 source/simulation authority, revision fence와 realization proof를 통과시킨
delta만 반영한다.

## 2. 선행 문서와 경계

### 2.1 4.6~5.0에서 상속하는 것

[`4.6-5.0-model-adaptive-rp-publishing-roadmap.md`](4.6-5.0-model-adaptive-rp-publishing-roadmap.md)는
다음을 소유한다.

- `simulation_snapshot.v1`, `character_execution_card.v1`, `world_execution_slice.v1`;
- 인물·관계·지식·세계·세력·thread의 현재 장면용 read model;
- actor/faction의 목표·수단·발동 조건·대가와 bounded progression envelope;
- `scene_guidance_proposal.v1`과 모델 능력 적응형 장면 실행 계약;
- `output_fidelity_report.v1`의 우선 진단-only 경로;
- offscreen 변화의 bounded hypothesis와 canonical write 금지선.

5.1은 이 데이터를 다시 검색하거나 두 번째 graph·관계·profile owner를 만들지 않는다.
4.6~5.0의 read model과 continuity envelope는 `현재 무엇이 유지되어야 하는가`를 제공한다.
5.1 이후의 새 책임은 **관찰을 현재 상태에 동화하고, typed action을 조건으로 가능한 successor와
outcome을 계산하며, 임시 rollout·realization·canonical admission을 분리하는 것**이다.
즉 4.8의 실행 조각은 world-model input이지 action-conditioned dynamics의 완료 증거가 아니다.

4.8의 offscreen 결과는 계속 bounded hypothesis로 시작한다. 5.5에서 정의하는 opt-in
offscreen admission은 4.8 결과를 몰래 정사로 승격하는 것이 아니라, 검증된 delta·parent
revision·rules version·tick receipt와 별도 source kind를 요구하는 새 권한 계약이다. 이 계약이
완료되기 전에는 5.4 결과를 canonical state에 기록하지 않는다.

### 2.2 5.0 완료와 5.1 진입

- 문서·schema·neutral fixture는 5.0 구현 중 미리 준비할 수 있다.
- production payload 적용과 canonical transition 구현은 5.0의 관련 source→payload→displayed-final
  lineage, rollback, branch와 output fidelity prerequisite가 검증된 뒤 시작한다.
- 5.0이 `implemented_unverified`인 상태에서 5.1 계약을 연결했다면 5.1도 자동으로 같은 상태
  이상을 주장할 수 없다.
- 5.1 작업이 5.0의 미완료 requirement를 후속 버전으로 이동시키거나 5.0 완료를 대신하지 않는다.

### 2.3 AC Ensemble Agent와 경계

[`AC Ensemble Agent DESIGN.md`](../../workbench/ac-ensemble-agent/DESIGN.md)의 단독형
`standalone_rewrite`는 여러 전문 작성자가 같은 `main_draft`를 병렬 재작성하는 문서 제작
파이프라인이다. 이것만으로 Actor가 세계 상태 안에서 살아 움직이는 것은 아니다.

4.4와 4.5, 5.3의 책임은 다음처럼 겹치지 않는다.

- 4.4는 연동 요청에서 별도 플러그인이 request/stage owner가 되고 Archive Center Publisher 호출을
  0회로 만드는 exactly-one cutover를 소유한다.
- 4.5는 나레이터와 선택된 Actor가 검증된 공개 장면을 순차적으로 이어받는 role-turn loop,
  lossless `performance_transcript` assembly와 실제 displayed final 하나만 complete-turn·Critic·
  memory admission으로 보내는 Host/finality spine을 소유한다. `main_draft`는 필수 선행이 아니다.
- 5.3은 그 연동 경로 안에서 Actor가 자유문 재작성 후보가 아니라 typed action proposal을
  내고, Go가 검증한 action-conditioned successor/outcome만 다음 역할의 공개 현실이 되게 한다.
  4.4/4.5의 request owner, final receipt, admission 또는 terminal fallback owner를 다시 만들지 않는다.

5.3은 문서에 계획된 `ensemble_performance`와 연결한다.

- Archive Center가 최초 `public_scene_state`와 Actor별 `private_actor_context`를 구성한다.
- 나레이터가 scene context와 공개 세계 상태에서 장면을 열거나 연결한다.
- Go가 장면에 관련된 다음 Actor를 고르고 Actor는 자기 관점에서 실제 대사·행동 proposal을
  만든다.
- Go가 proposal을 검증하고 허용된 전이만 rollout state에 적용한다.
- 다음 Actor는 검증 뒤 갱신된 공개 상태만 이어받는다.
- 공개 role turn은 performance transcript의 구성 요소가 되고 transcript assembler는 완료된
  rollout을 의미 변경 없이 한 번 렌더링한다.
- 실제 표시 확인 전에는 미완성 transcript, Actor 발언과 assembler 결과를 canonical assistant
  turn이나 세계 사건으로 승인하지 않는다.

현재 [`AC Ensemble Agent DESIGN.md`](../../workbench/ac-ensemble-agent/DESIGN.md)의 Standalone은
`standalone_source_implemented` / `standalone_regression_passed` / `live_pending`이다. 이는
Integrated performance의 완료 또는 차단 증거가 아니다. 5.3 production 진입은 4.4가 공유
plugin shell·provider transport·credential persistence·Host lifecycle을 별도 검증한
`integrated_runtime_ready`, 5.1의 최소 outcome/conflict 기초, 5.2 scheduler의
`dependency_ready`와 관련 Host lifecycle의 `integration_verified`를 모두 요구한다. 이 gate는
각 기능의 장기 RP release 완료를 미리 요구하지 않으며 두 mode를 같은 요청에서 실행하지 않는다.

### 2.4 독립 DLC와 경계

[`standalone-dlc-separation-roadmap.md`](standalone-dlc-separation-roadmap.md)의 원칙을 상속한다.

- 한 data domain에는 한 canonical writer만 둔다.
- integrated mode에는 한 final injection/orchestration owner만 둔다.
- 외부 기능은 immutable snapshot을 읽고 proposal을 반환할 수 있지만 Archive Center admission을
  우회할 수 없다.
- DLC 미설치·OFF·timeout·crash가 Archive Center 시작, 기억 저장·검색·삭제, 기본
  `/prepare-turn`과 RisuAI 표시 lifecycle을 막지 않는다.
- 별도 프로세스나 제품 분리가 나중에 필요해도 canonical world state는 Archive Center에 남긴다.

따라서 5.1~6.0의 기본 계획은 Archive Center 내부 Go module이다. 사용자가 보는 설정과 배포
경험만 선택형 DLC처럼 구성한다.

### 2.5 연구 아이디어와 외부 근거의 사용 범위

- MDASH에서 가져오는 것은 전문 agent가 후보를 찾고 별도 단계가 검증·증명하는 구조적 원칙이다.
  보안 스캐너의 규모, agent 수나 benchmark를 Archive Center 품질 증거로 사용하지 않는다.
- OpenRouter Fusion은 2026-08-13 공식 문서 기준 outer model이 선택적으로 1~8개 panel과
  analyst를 호출한 뒤 outer final을 쓰는 beta 기능이다. 5.8에서 고위험 전이의 반론·누락
  검토에 사용할 수 있지만 Actor simulation, 상태 저장소 또는 canonical judge로 사용하지
  않는다. 기본 3-panel 비용은 단일 completion보다 대략 4~5배이며 일부 panel/analyst 실패가
  전체 status 안에 남을 수 있으므로 실제 invocation, `failed_models`, analysis와 final lineage를
  별도로 확인한다.
- 모델 합의는 source가 아니다. 여러 모델이 같은 오류에 동의해도 Go hard constraint를 넘을 수 없다.

외부 사실, 제품 설계상 추론과 아직 확인하지 못한 사실을 섞지 않는다.

**VERIFIED — 외부 1차 자료가 직접 말하는 범위**

- Ha와 Schmidhuber의 `World Models`는 학습된 압축 시공간 표현과 그 안에서의 policy 학습을
  다룬다. MuZero는 행동을 반복 적용해 planning에 필요한 reward·policy·value를 예측하는
  학습 모델을 다룬다. 어느 연구도 Archive Center의 explicit symbolic state나 RP 품질을
  검증한 것은 아니다.
- PDDL2.1의 원 논문은 temporal action, duration과 numeric resource를 명시적으로 표현한다.
  이는 typed action의 구조적 참고일 뿐 PDDL runtime 도입 근거가 아니다.
- multi-objective RL의 1차 연구에는 scalar 하나가 아니라 reward vector와 Pareto-dominating
  policy set을 다루는 방법이 있다. 이 문서는 이를 학습 알고리즘으로 이식하지 않고,
  Actor별 상충 목적을 조기에 전역 scalar 하나로 평탄화하지 않는 설계 참고로만 사용한다.
- TruthfulQA와 sycophancy 실험은 평가한 LLM들이 거짓 답변이나 사용자 견해 동조를 만들 수
  있음을 실증했다. 특정 현재 provider의 오류율이나 Archive Center 완화 효과는 이 결과에서
  추론할 수 없다.

**INFERRED — 위 근거와 Archive Center 경계에서 도출한 설계 선택**

- 현재 제품에는 학습 dynamics보다 source-backed state, typed action과 deterministic hard
  validator가 더 좁고 감사 가능하다.
- Actor 목적은 actor-specific value vector로 보존하고 privacy·agency·hard constraint를
  어떤 총점과도 상쇄하지 않는다.
- LLM은 action/outcome/realization의 proposal producer로 제한하고, 구조화 receipt와 실제
  displayed lineage가 모호하면 `admission_pending`으로 남긴다.
- counterfactual rollout은 모든 장면의 기본 호출이 아니라 고위험 후보의 제한된 비교 도구로만
  사용한다.

**UNKNOWN — 현재 Host·통합·live 사실**

- 지원할 실제 RisuAI artifact가 stable request/generation identity, 안전한 bounded draft
  replacement, reroll·delete·branch와 최종 표시를 admission에 충분한 원자성으로 노출하는지;
- 현재 AC Ensemble 단독형 결과가 실제 RisuAI 저장·화면 본문이 되는지와 장기 RP 품질;
- 실제 production state에서 world time, authorial command와 structured realization sidecar를
  어느 기존 owner·field로 관찰할 수 있는지;
- 실제 MariaDB·Chroma·provider·OS·loaded package에서 이 로드맵의 비용·품질·복구 gate가
  통과하는지.

이 UNKNOWN을 문서·fixture·모의 회귀로 VERIFIED로 바꾸지 않는다. 해당 capability가 없으면
자동 admission·repair를 비활성화하고 지원 범위를 낮추며 JavaScript 추정 경로를 만들지 않는다.

## 4. 영구 소유권과 기본 아키텍처

### 4.1 Archive Center Go

Go가 소유한다.

- canonical world/session/branch state와 revision;
- 장면·Actor·세력 eligibility와 scheduling;
- 위치·이동·시간·생존·신체·지식·관계·자원·인과 transition policy;
- Actor별 private context와 public scene state의 ViewModel;
- proposal validation, conflict resolution과 rollout state;
- AC Ensemble 및 선택적 reviewer 호출 순서, deadline, 반복과 종료;
- final render plan, displayed-final lineage·receipt 해석과 canonical admission;
- offscreen tick의 trigger, budget, source type, admission과 future effect;
- rollback, reroll, delete, branch, idempotency와 stable error;
- 비용, trace, HUD와 설정 ViewModel.

### 4.2 RisuAI JavaScript

JavaScript가 소유할 수 있는 범위는 다음뿐이다.

- 공식 hook에서 입력, request, streaming, message index와 실제 표시 최종본 관찰;
- 최소 versioned observation packet 전송;
- Go가 만든 payload plan 또는 최종 응답을 실제 RisuAI 구조에 적용;
- 표시 일치 확인과 UI·localization;
- backend-unreachable transport에 필요한 최소 transient queue.

JavaScript는 Actor 선택, `can_*` 판정, relationship change, offscreen tick, conflict 해결,
prompt 조립, retry policy나 canonical write를 계산하지 않는다.

2026-08-13 현재 공개 [RisuAI Plugin V3 type](https://raw.githubusercontent.com/kwaroran/Risuai/main/src/ts/plugins/apiV3/risuai.d.ts)의
`output` listener는 streaming과 Host-side transformation 뒤 committed chat snapshot을 관찰하지만,
reroll·delete·branch 전용 listener나 원자적 canonical-admission transaction은 보이지 않는다.
지원 tag/commit별 capability matrix와 live E2E가 닫히지 않으면 해당 lifecycle admission은
`UNKNOWN`/disabled다. listener는 순차 await되므로 heavy world simulation을 그 안에서 기다리지
않고, background result는 captured message identity·generation·revision을 다시 확인해 stale 또는
`messageIndex=-1`이면 폐기한다.

### 4.3 AC Ensemble Agent

AC Ensemble은 연동 mode에서 다음 실행 표면을 제공한다.

- 선택적 감독관과 나레이터·Actor별 provider/model 호출, deterministic/lossless transcript
  assembler;
- Go가 준 role-specific input으로 대사·행동·사건 proposal 생성;
- 허용된 public rollout state를 다음 역할 호출에 전달;
- 완료된 rollout을 사용자에게 보일 하나의 RP 본문으로 렌더링;
- provider 응답·실패·latency·usage observation 반환.

AC Ensemble은 canonical DB, 기억 검색, 인물 지식 배정, actor eligibility, transition approval,
반복 종료와 admission을 소유하지 않는다.

### 4.4 저장 계층

- MariaDB는 canonical truth와 admitted transition ledger의 owner다.
- ChromaDB는 canonical source에서 재구축 가능한 검색 인덱스이며 rollout state나 proposal의
  canonical store가 아니다.
- request-scoped rollout은 메모리 또는 명시적 임시 저장 영역에 둘 수 있지만 restart 뒤
  canonical state로 자동 승격하지 않는다.
- audit 보존이 필요한 proposal은 canonical truth와 분리된 provenance/trace로 저장하며 recall
  source가 되지 않는다.
- 새로운 table이나 worker는 기존 state/lifecycle/admission owner로 표현할 수 없는 재현된 요구가
  있을 때만 추가한다.

### 4.5 기존 owner 확장 원칙

- 5.1의 observation assimilation과 transition decision은 기존 Go state/source/lifecycle owner의
  versioned read/decision projection을 확장한다. 별도 `WorldModel DB`, event store, graph store나
  JavaScript policy cache를 전제하지 않는다.
- 5.5는 4.0·4.5가 소유하는 displayed-final, complete-turn, Critic와 memory admission spine에
  realization receipt, simulation authority와 prediction residual 판정을 추가한다. 두 번째
  canonical admission service나 dual-write ledger를 만들지 않는다.
- 5.8은 4.9의 동일 Go Publisher/orchestration owner에 world-model risk·cost·residual 입력을
  확장한다. 4.9의 `directed/reviewed/deep` guidance depth와 5.8의 Living World execution route는
  다른 축이지만, 한 요청의 final guidance block·render owner·admission owner는 각각 하나다.
- 실제 source audit에서 기존 owner로 표현할 수 없는 재현 요구가 확인되기 전까지 이 문서의
  논리 이름을 새 파일·API·table 생성 지시로 해석하지 않는다.

## 5. 상태 계층과 전이 의미

### 5.1 필수 상태 계층

```text
canonical_state
  현재 session·branch에서 승인된 세계 상태

rollout_state
  한 요청 또는 offscreen tick 안에서만 사용하는 임시 상태

proposal
  Actor·규칙·감독관·모델이 제안한 행동 또는 사건

accepted_transition
  Go hard validation을 통과하여 rollout_state에만 적용된 전이

displayed_realization
  실제 RisuAI 최종 표시문에서 발생한 것으로 확인된 장면 변화

admitted_transition
  revision·source·authority·proof를 통과하여 canonical_state에 반영된 전이
```

`accepted_transition`은 이름과 무관하게 canonical acceptance가 아니다. 최종 장면이 해당
전이를 누락·반전·변형하면 canonical state에 기록하지 않는다.

### 5.2 전이 식별과 fence

모든 transition proposal과 decision은 최소 다음 lineage를 가진다.

- session ID, branch/worldline ID와 logical turn ID;
- request ID, generation ID와 parent canonical revision;
- actor/faction ID, proposal ID와 causal parent IDs;
- source refs, visibility, knower scope와 authority kind;
- rules/policy version과 mode;
- proposed delta, accepted delta와 excluded fields;
- status, reason code, created/validated/displayed/admitted timestamps;
- provider/model call이 있었다면 호출 lineage와 response hash;
- offscreen tick이면 tick ID, world-time range와 trigger.

stale parent revision, 다른 branch, cancelled generation 또는 superseded final에 연결된 결과는
현재 pointer를 바꾸지 않는다.

### 5.3 hard transition checks

최소 논리 판정은 다음을 포함한다. 이름은 설계용이며 실제 함수 수를 미리 고정하지 않는다.

| 판정 | 확인 범위 |
|---|---|
| `can_appear(actor, scene)` | 현재 위치, 존재 mode, 소환·통신·회상 같은 등장 방식, 장면 시간 |
| `can_move(actor, destination, time)` | 출발지, 경로, 이동 시간, 봉쇄, 능력과 비용 |
| `can_know(actor, fact)` | 관찰, 전달, 추론, 오정보, 비밀, 시점과 공개 범위 |
| `can_act(actor, action)` | 생존, 의식, 신체 상태, 구속, 능력, 자원과 금지 규칙 |
| `can_affect(actor, target)` | 거리, 매체, 접촉 가능성, 권한과 대상 상태 |
| `can_spend(actor, resource)` | 현재 보유량, reservation, 중복 소비와 대가 |
| `can_change_relationship(actor, target, domain)` | 당사자, 방향, domain, 사건 근거, 변화 envelope와 영속성 |
| `can_transfer_knowledge(source, target, fact)` | 전달 행위, 채널, 신뢰, 왜곡, 가로채기와 privacy |
| `can_resolve_thread(actor, thread, scope)` | causal prerequisite, agency owner, 해결 권한과 전파 범위 |
| `can_schedule_effect(transition, time)` | 지연 효과, 취소 조건, branch와 revision |

판정 결과는 단순 boolean이나 하나의 `blocked`로 축약하지 않는다. 특히 **현재 상태·세계 규칙상
불가능함**과 **가능할 수 있지만 정책·권한이 없음**을 분리한다.

- `allowed`: 현재 근거와 상태에서 허용;
- `conditional`: 명시된 비용·이동·선행 전이를 먼저 적용하면 허용;
- `hard_impossible_current_state`: 현재 위치·시간·생존·resource·world rule로 successor가 존재하지 않음;
- `authority_blocked`: 변화 자체는 가능할 수 있으나 해당 source/actor/simulation에 write 권한이 없음;
- `agency_blocked`: user/player 또는 다른 actor의 선택·동의를 대신 확정하려 함;
- `policy_blocked`: 활성 user mode·privacy/provider·risk policy가 실행을 허용하지 않음;
- `conflict_pending`: basic resolver로 결정할 수 없는 동시 action/resource/causal conflict;
- `unknown`: 필요한 host/source 사실이 노출되지 않음;
- `needs_evidence`: upstream recall/source dimension이 필요;
- `stale_rejected`: revision 또는 lifecycle fence 불일치.

`hard_impossible_current_state`는 “제품 정책상 하지 않음”의 alias가 아니며, authority/policy block을
세계 법칙으로 세탁하지 않는다. 반대로 모델이 그럴듯한 후속 상태를 썼다는 이유로 hard
impossibility를 policy warning으로 낮추지 않는다.

`unknown`은 자동 허용도 자동 사망·부재 판정도 아니다. 모델에게 사실을 발명하게 하지 않고
가능한 불확실성 표현 또는 보수적 비확정 proposal로 남긴다.

### 5.4 생존과 존재 mode

한 개의 `alive` boolean으로 모든 표현을 결정하지 않는다.

예시 mode:

- `physical_present`, `physical_remote`, `incapacitated`, `restrained`;
- `dead_confirmed`, `death_uncertain`, `missing`;
- `memory`, `recording`, `dream`, `hallucination`, `vision`;
- source가 허용하는 경우의 `ghost`, `summoned`, `resurrection_candidate`.

`dead_confirmed`는 일반적인 물리 행동을 막지만 인물의 모든 서사적 언급을 금지하지 않는다.
유령이나 부활은 작품 규칙, 행위자, 비용과 선행 조건을 가진 별도 transition이어야 하며 사용자
입력에 이름이 등장했다는 사실만으로 활성화하지 않는다.

### 5.5 관계 전이

장면의 감정과 장기 관계를 분리한다.

- 순간 감정: 놀람, 안도, 분노, 공포, 호감 표현;
- 관계 domain: 신뢰, 친밀감, 충성, 의존, 존경, 두려움, 적대, 빚, 권력;
- 관계 방향: A→B와 B→A;
- 현재 표현과 영속 상태;
- 변화 근거, 반례, consent, magnitude와 permanence.

큰 사건은 한 턴에도 큰 변화를 만들 수 있다. 이를 고정 턴 수로 막지 않는다. 대신 source와
실제 사건이 해당 방향·domain·크기·영속성을 지지하는지 검증한다. 한쪽의 고백, 도움이나
감정 표현을 상대방의 동일한 관계 변화로 자동 복제하지 않는다.

### 5.6 지식과 관점 전이

- canonical fact가 존재해도 모든 Actor가 아는 것은 아니다.
- `known`, `believed`, `suspected`, `unknown`, `misinformed`, `hidden`, `revealed`를 분리한다.
- Actor proposal은 자기 knowledge state를 기준으로 생성한다.
- 실제 대화, 관찰, 문서 열람 또는 신뢰 가능한 전달이 accepted/admitted된 뒤에만 지식 전이를
  적용한다.
- 나레이터와 transcript assembler가 Actor별 private context를 본문에 직접 누출하지 않도록
  public event와 private cause를 분리한다.

### 5.7 Observation/source assimilation

world model은 source를 새로 검색하는 두 번째 recall engine이 아니다. 기존 owner가 선택·승인한
source와 공식 Host observation을 다음 순서로 현재 상태에 동화한다.

1. observation의 source kind, authority, session·branch·request·generation과 exact revision을 보존;
2. 현재 장면, 회상, 꿈, 가정, 기록, offscreen 같은 diegetic frame과 event/observation time을 분리;
3. entity, actor별 knower/visibility와 주장자·관찰자·대상을 연결;
4. 현재 canonical state와 support·contradiction·ambiguity를 계산;
5. `assimilated_constraint`, `claim_only`, `simulation_candidate`, `admission_pending`, `rejected`처럼
   의미가 다른 결과를 구분;
6. 허용된 observation만 `S_t`의 constraint 또는 admission 후보로 전달.

현재 user message가 존재한다는 Host 관찰은 response obligation을 증명하지만 그 안의 모든
서술을 객관적 세계 사실로 만들지 않는다. 인물의 거짓말, OOC 저자 명령, player action과
서술자 사건을 prompt 문구로 추정하지 않는다. 이를 구분할 공식 role/channel/typed command가
없으면 해당 truth·authority는 `unknown` 또는 `admission_pending`이다.

새 observation이 기존 사실을 정정하면 current state를 조용히 덮어쓰지 않는다. 기존 correction·
revision owner를 통해 새 source revision과 supersession 범위를 만들고, 그 사실에 의존한 아직
미승인 prediction, counterfactual branch, scheduled effect와 causal descendant를 찾아
invalidate/revalidate한다. 이미 admitted descendant는 자동 삭제하지 않고 기존 correction·rollback
권한으로 영향 범위를 검토한다. correction 결과가 ambiguous하면 old/new 중 하나를 편의상 채택하지
않고 해당 successor·schedule을 pending/deferred한다.

### 5.8 World clock와 event ordering

최소 시간 표현은 다음을 분리한다. 이름은 논리 예시다.

- `canonical_world_time`: 현재 branch에서 admission된 세계 시간 또는 bounded interval;
- `scene_time`: 현재 foreground 장면의 시간·순서;
- `observation_time`: Host/source가 관찰된 시간이며 사건 발생 시간과 같다고 가정하지 않음;
- `simulation_horizon`: rollout이 읽을 수 있는 이미 승인된 시간 범위;
- `scheduled_effect_time`: admitted 원인에서 파생된 실행 예정 시각·조건.

clock은 wall clock, request 횟수, message index, turn 수나 LLM이 자연어로 추정한 경과로 전진하지
않는다. 기존 story-clock owner가 인정한 foreground time advance, 공식적으로 구분된 authorial
time command, admitted action의 duration 또는 admitted 원인의 scheduled effect만 candidate가
될 수 있고 최종 갱신은 기존 Go admission owner가 한다. flashback·dream·hypothetical frame은
현재 clock을 바꾸지 않는다.

정확한 시간이 source에 없으면 가짜 timestamp를 만들지 않고 interval·partial order·unknown을
유지한다. 같은 시각의 action은 최소 conflict/reservation 규칙으로 ordering하고, 결정 근거가
없으면 임의 total order 대신 `admission_pending`으로 남긴다. offscreen tick은 이미 admission된
world-time advance를 소비해 bounded catch-up을 계산할 뿐, Host wall time 경과를 세계 시간으로
승격하지 않는다. tick·scheduled effect는 branch/revision에 고정하고 restart·reroll·delete 뒤
exactly-once 또는 명시적 invalidation을 보장한다.

모든 clock advance candidate는 최소 `before`, `delta/duration`, `after`, authority/source ref,
diegetic frame, branch/revision과 uncertainty를 가진 structured clock receipt로 대조한다. 정확한
`before` 또는 source owner를 mapping할 수 없으면 delta를 현재 clock에 더하지 않는다. 이 문서
작성 시점에는 production world-clock field와 authorial time-command owner가 **UNKNOWN**이며,
해당 mapping이 닫히지 않으면 offscreen active mode와 time-based canonical admission은
`blocked/disabled`다. wall-clock fallback이나 JavaScript counter를 만들지 않는다.

### 5.9 Source/simulation authority matrix

정확한 field mapping은 5.1 packet에서 기존 owner를 조사해 확정한다. 최소 권한 경계는 다음과
같다.

| 입력/source kind | 직접 증명하는 것 | canonical delta 권한 |
|---|---|---|
| 기존 admitted state/event와 승인 source projection | 현재 baseline·rule·constraint | 새 사건을 스스로 만들지 않음; successor validation의 근거 |
| 원작·설정·로어의 승인 fact/rule | 세계 규칙과 가능한/금지된 결과 | 현재 session에서 사건이 발생했다는 증거는 아님 |
| 현재 user/Host utterance | 입력·주장이 관찰됐고 응답 의무가 있음 | typed author/player authority와 diegetic frame이 확인된 scope만 기존 admission으로 전달; 나머지는 claim/pending |
| 실제 displayed foreground + structured realization receipt | 특정 final lineage와 표현 span | receipt·span·authority·precondition이 일치한 realized delta만 기존 admission owner가 결정 |
| admitted 원인의 deterministic scheduled consequence | 원인·rule·시간 조건에서 파생된 결과 | 실행 시 precondition을 다시 통과한 허용 field만; 원인 취소·stale이면 0 |
| Actor·LLM·Publisher·Reviewer proposal | 가능한 행동·해석 후보 | 직접 권한 0; confidence·합의도 source가 아님 |
| offscreen simulation candidate | opt-in rules 안에서 계산된 가능한 사건 | 기본은 hypothesis; 별도 `simulation_generated` authority, receipt, 허용 field와 user policy가 모두 있을 때만 bounded admission 후보 |
| AC Ensemble role turn/transcript assembler sidecar | proposal 또는 realization 주장 | Go validation과 actual displayed lineage 전에는 직접 권한 0 |

일반 simulation authority는 player 행동·감정, 사망·부활, 영속 관계·동의, 대형 소유권 이전와
상위 thread/작품 closure를 자동 승인하지 않는다. 각 domain의 high-risk 목록은 장르·키워드가
아니라 기존 authority·agency·state contract로 정의한다. 허용 범위 밖 결과는 reviewer 수나
극적 품질과 무관하게 `admission_pending` 또는 `rejected`다.

### 5.10 Typed action과 action-conditioned successor/outcome

행동 proposal은 자유문 지시가 아니라 최소 다음 의미를 가진다.

- action/operator kind, actor/faction, target과 affected domain;
- start location·destination·channel, start/end 또는 duration;
- state·knowledge·authority precondition과 causal parents;
- resource read/write/reservation, cost와 취소 조건;
- intended effect와 Actor가 기대하는 outcome;
- deterministic delta, 허용 outcome envelope, unknown/unsupported field;
- 공개 사건, private intent와 observer/knower projection;
- source refs, policy/rules version, uncertainty와 lineage.

successor는 `T(S_t)`가 아니라 `T(S_t, action, clock, rule_profile)`로 계산한다. Actor가 원한
`intended_effect`와 실제로 가능한 `predicted_outcome`을 분리하고, 결과는 최소 `attempt`,
`success`, `partial`, `failed`, `interrupted`, `cancelled`, `unknown`을 구분한다. 근거 없는 정확한
확률은 만들지 않으며, deterministic effect·bounded alternative·unknown field를 별도로 남긴다.

5.3과 5.4 전에 5.1/5.2의 **basic outcome slice**가 먼저 production owner에 연결돼야 한다.
이 slice는 한 Actor의 중복 action, 같은 resource의 reservation, 상호 배타 delta, 필수 선행
action, 단순 time ordering과 outcome status를 처리한다. 해결할 수 없는 multi-Actor·장기 causal
competition은 모델 호출 순서로 결정하지 않고 5.6 대상임을 표시해 pending/defer한다.

### 5.11 Actor-specific value vector와 bounded counterfactual

각 Actor는 하나의 전역 `reward`가 아니라 source-backed 목적별 value vector를 가진다.

- active goal/commitment별 진행·후퇴와 포기 조건;
- 의무·가치·금지선과 belief consistency;
- 신체 안전·타인 위험과 물리 비용;
- 방향·domain별 관계 영향과 consent;
- 자원·시간·deadline·기회비용;
- secrecy·exposure·knowledge gain/loss;
- 불확실성과 reversible/irreversible risk.

hard constraint, privacy와 user/player agency는 vector 성분이 아니라 non-compensable gate다.
Actor A의 값과 Actor B의 값을 한 숫자로 더하거나 player 만족도를 모든 NPC의 공통 보상으로
사용하지 않는다. 같은 Actor 안에서도 source가 weight나 우선순위를 지지하지 않으면 임의
scalarization하지 않고 non-dominated 후보와 unresolved trade-off를 남긴다. conflict 결과는
value 합계가 아니라 authority, world rule, resource, time과 5.1/5.6 outcome resolver가 결정한다.

structured counterfactual rollout은 다음 high-risk category에만 선택적으로 사용한다: irreversible
vitality/location/resource 변화, 비밀 공개, 큰 관계·동의 변화, thread closure, multi-Actor conflict,
offscreen canonical admission 또는 prediction residual이 큰 후보. candidate action, 합법적 hold/no-op와
필요한 대안만 versioned depth·breadth·cost 상한 안에서 비교하며, 각 branch는 typed state delta와
unknown을 반환한다. 저위험 장면은 추가 rollout/provider call 0이어야 하고, rollout prose·선호·
다수결은 truth나 admission 근거가 아니다.

모든 counterfactual branch는 같은 immutable parent state/revision, clock receipt, rules/policy와
eligible candidate set에서 갈라지고 request scope 안에서만 존재한다. branch 실행 중 canonical
state, MariaDB, Chroma, RisuAI payload, memory/admission, scheduled effect와 외부 tool side effect의
write는 0이다. 다른 parent/revision의 branch 결과를 비교하거나 다음 request의 cache/fallback으로
재사용하지 않는다.

### 5.12 Structured realization receipt와 prediction residual

서로 다른 authority를 가진 receipt를 하나로 합치지 않는다.

- `displayed_realization_receipt` 예시: transcript renderer가 foreground 본문과 함께 제안한다.
  transition/event/action ID, predicted outcome ID, realized/omitted/reversed/expanded/frame_changed/
  ambiguous, diegetic frame, claimed displayed span/hash, actor·target·observer, realized delta,
  knowledge/visibility consequence, unsupported addition과 renderer lineage를 가진다.
- `simulation_outcome_receipt` 예시: Go basic/advanced resolver가 foreground 또는 offscreen typed
  action에 대해 만든다. parent state/revision, clock before/delta/after, action set, applied rule,
  reservation/conflict decision, resolved outcome/delta, uncertainty와 causal descendants를 가진다.

두 이름은 논리 예시이며 새 API·table을 뜻하지 않는다. displayed receipt는 renderer의 주장이지
proof 자체가 아니고, simulation receipt는 규칙 계산 결과이지 foreground 표시 증거가 아니다.
Go는 각각을 authority에 맞게 대조해 `prediction_residual`을 만든다. residual은 outcome mismatch,
누락·반전, 예상 밖 delta, frame/time/observer mismatch와 아직 판단할 수 없는 ambiguity를
분리한다. text hash는 lifecycle 일치를 증명하지만 자연어의 사건 의미 전체를 증명하지 않는다.

foreground auto-admission 후보는 원칙적으로
`accepted/resolved delta ∩ simulation_outcome_receipt ∩ displayed_realization_receipt의 exact span ∩
source/agency authority`의 교집합으로 제한한다. offscreen에는 displayed receipt를 요구하지 않지만
`validated delta ∩ simulation_outcome_receipt ∩ explicit simulation-generated authority/user policy`의
교집합만 후보가 되며 source kind를 foreground observation과 분리한다. 교집합 밖의 unsupported
addition은 기존 admission으로 재검증하고, 판단할 수 없는 차이는 pending이다.

- 기계적으로 대조 가능한 exact event/delta만 자동 admission 후보가 될 수 있다.
- 본문이 암시·부정·비유·시점 혼합으로 모호하거나 receipt와 span이 불일치하면
  `admission_pending`; 자동으로 `realized`나 `rejected`로 추정하지 않는다.
- transcript assembler가 입력 role turn에 없던 delta를 새로 만들면 lossless assembly 위반이며
  해당 delta는 기존 source/authority와 precondition을 다시 통과하기 전에는 저장하지 않는다.
- residual은 trace·평가·future review 입력일 뿐 canonical truth, global reward 또는 온라인
  self-learning label이 아니다.
- Host가 structured receipt와 final lineage를 안정적으로 연결하지 못하면 soft semantic delta의
  자동 admission을 비활성화하고 foreground response는 보존한다.

## 6. 기능 mode

| mode | 포함 범위 | 모델 호출 |
|---|---|---|
| `off` | 5.0까지의 기존 기억·Publisher·simulation support 유지 | Living World 추가 호출 0 |
| `continuity_only` | 5.1 hard transition, observation/clock과 기본 outcome 제약 | 규칙 기반 우선, 추가 호출 불필요 |
| `actor_intent` | 5.2 actor eligibility, value vector와 typed action 후보 | 필요 actor에 한해 선택적 |
| `ensemble_rollout` | 5.3 순차 Actor 상황극, action-conditioned successor와 final render | AC Ensemble 역할 호출 |
| `offscreen_hypothesis` | 5.4 장면 밖 sparse tick과 canonical write 없는 rollout | 조건이 발생한 actor/faction만 선택적 |
| `offscreen_admission` | 5.5가 허용한 simulation-generated authority 안의 opt-in admission | hypothesis route + 필요한 proof/review만 |

- mode는 누적 capability지만 한 요청에는 하나의 final orchestration path만 사용한다.
- `ensemble_rollout`과 standalone `standalone_rewrite`를 같은 요청에서 연속 실행하지 않는다.
- 비용 부족이나 provider 실패로 낮은 mode로 내려가면 실제 실행 mode와 빠진 requirement를
  `degraded`로 기록한다. 조용한 자동 downgrade를 정상 성공으로 집계하지 않는다.
- 6.0 기본값은 5.9 실사용 결과에서 결정한다. 제안 기본은 규칙 기반 `continuity_only`,
  Ensemble과 canonical offscreen admission은 명시적 opt-in이다.

mode는 한 요청의 실행 route이고 release profile은 배포·승격 증거 묶음이다. 둘을 같은 상태로
표시하지 않는다.

| release profile | 포함 가능한 범위 | 선행 profile |
|---|---|---|
| `core_continuity` | 5.1 explicit state/clock/typed action/basic outcome + 보수적 foreground admission spine | 5.0 |
| `actor_intent` | 5.2 scheduler와 actor-specific value vector | `core_continuity` |
| `ensemble_shadow` | 5.3 typed Actor performance, canonical world write 0 | `actor_intent`, AC Ensemble `integrated_runtime_ready` |
| `ensemble_opt_in` | 5.3 performance + 5.5 foreground realization/admission | `ensemble_shadow`, 5.5 foreground gate |
| `offscreen_hypothesis` | 5.4 canonical write 없는 sparse rollout | `actor_intent` |
| `offscreen_admission_opt_in` | 5.5 simulation-generated authority와 receipt 기반 admission | `offscreen_hypothesis` |
| `advanced_conflict` | 5.6 multi-Actor/resource/long-causal resolution | `core_continuity` |
| `long_horizon` | 5.7 goal·belief·relation·condition dynamics | 실제 사용하는 선행 profile |
| `adaptive_review_opt_in` | 5.8 risk/cost route와 선택적 reviewer | 실제 routing 대상 profile |

한 optional profile의 미완료가 검증된 `core_continuity` artifact의 release를 자동 차단하지 않는다.
반대로 version가 6.0이라는 이유로 미검증 optional profile을 GA로 표시하지 않는다. 각 profile은
별도 enablement, evidence manifest, known limitation과 kill switch를 가진다.

다음 gate는 profile별 scope change로 면제할 수 없다.

- 단일 Go owner, JavaScript 관찰·적용 경계와 새 parallel DB/graph/memory 부재;
- source/simulation authority, user/player agency와 Actor별 privacy/knower ceiling;
- session·branch·request·generation·revision fence, stale·rollback·idempotency;
- basic outcome/conflict 없이 Actor/Ensemble/offscreen 결과를 다음 현실로 전달하지 않음;
- proposal·합의·receipt만으로 canonical write하지 않고 ambiguity를 pending으로 보존;
- 기능 OFF와 optional dependency 실패에서 base memory·response·admitted state 비퇴행;
- 지원 Host capability, actual loaded artifact, payload/display/DB lineage와 failure evidence 정직성.

## 7. 단계별 구현 로드맵

### 5.1 World-State / Transition Kernel

#### 목적

LLM 호출 여부와 무관하게 source/observation을 현재 state에 동화하고, typed action을 조건으로
가능한 successor/outcome과 불가능한 delta를 Go가 일관되게 판정할 최소 kernel을 만든다.
continuity-only 안전층과 symbolic world-model loop의 기초를 같은 owner 안에서 구분한다.

#### 작업

- 기존 `simulation_snapshot.v1`과 state/lifecycle owner의 production field mapping 고정;
- 공식 Host/source observation의 authority·diegetic frame·time·branch·knower assimilation;
- 기존 story-clock owner mapping, world/scene/observation time과 simulation horizon 분리;
- source/simulation authority matrix와 authorial command가 미노출일 때의 pending 계약;
- canonical/rollout/proposal/accepted/displayed/admitted 상태 계층 계약;
- location, presence, world time, vitality, physical condition, knowledge, relationship, resource와
  thread authority의 최소 transition schema;
- typed action의 precondition·duration·resource·visibility·intended effect·outcome envelope;
- action-conditioned deterministic/bounded/unknown successor projection;
- `can_*` hard check와 stable reason code;
- conditional transition의 prerequisite chain;
- 단일 Actor/resource reservation·상호 배타 delta·time ordering과
  `attempt/success/partial/failed/interrupted/cancelled` basic outcome slice;
- 5.5가 확장할 최소 admission skeleton: actual final lineage 불확실·semantic ambiguity는
  canonical no-write와 `admission_pending`;
- session·branch·request·generation·canonical revision fence;
- 동일 proposal의 idempotent validation과 duplicate application 방지;
- `continuity_only` OFF/ON production route;
- 차단·허용·unknown·needs-evidence trace와 Go ViewModel;
- 순간이동, 죽은 인물 행동, 전지적 지식, 관계 급변의 부정·반전 fixture.

#### 하지 않는 것

- Actor별 LLM 호출;
- 장면 밖 canonical 진행;
- 다중 Actor conflict resolution;
- 자유문 미래 생성, learned dynamics와 전역 reward;
- 자동 final rewrite;
- JavaScript 정책과 두 번째 canonical store.

#### Exit gate

- 같은 state와 proposal은 provider/model과 무관하게 같은 hard decision을 만든다.
- 같은 state라도 action·clock·rule profile이 다르면 설명 가능한 successor/outcome 차이를 만들고,
  action 없는 continuity check와 행동 예측을 같은 성공으로 집계하지 않는다.
- 언급만으로 presence가 바뀌지 않고 conditional travel이 prerequisite 없이 적용되지 않는다.
- 사망·의식·구속·지식·관계·thread scope 위반이 production Go route에서 차단된다.
- 기능 OFF 시 5.0 payload, 저장, 삭제, rollback과 표시 결과가 불변이다.
- 실제 RisuAI request와 displayed-final lifecycle에서 `continuity_only` 적용·skip·stale rejection이
  대조되기 전에는 `release_gate_verified`가 아니다.
- owner mapping, logical contract, production negative tests와 basic outcome가 통과하면 5.2/5.4
  source 작업을 위한 `dependency_ready`일 수 있으나, 이는 Host integration이나
  `core_continuity` release 완료를 뜻하지 않는다.

### 5.2 Actor Intent, Value Vector & Scheduler

#### 목적

인물이 현재 입력에만 반응하지 않고 자기 목표, 지식, 위치, 자원, 관계와 기회에 따른 typed
action 후보를 갖게 한다. Actor별 목적을 전역 scalar reward로 평탄화하지 않는다.

#### 작업

- actor/faction eligibility를 location, knowledge, active goal, opportunity, urgency, causal reachability,
  cost와 scene relevance로 계산;
- 언급된 인물, 현재 등장 인물, 원격 영향 가능 인물과 장면 밖 후보를 분리;
- actor별 persistent goal state와 request-scoped intent proposal 분리;
- stable motive, active commitment, reconsider trigger와 이번 action intent 분리;
- goal progress, obligation, safety, 관계 domain, resource/time, secrecy와 uncertainty의
  actor-specific value vector;
- 행동, 침묵, 보류, 협상, 거절, 이동 준비와 간접 영향 proposal 허용;
- 고정 Actor 수 대신 전체 eligible set과 selected/deferred/excluded reason 추적;
- Actor가 볼 수 있는 private context 최소화와 privacy ceiling;
- proposal마다 typed precondition, resource reservation, cost, intended effect,
  predicted outcome envelope와 uncertainty 기록;
- hard gate 뒤에도 상충 후보가 남고 irreversible/high-risk category이면 action·합법적 hold·
  필요한 대안만 structured bounded counterfactual로 비교;
- low-risk candidate에는 counterfactual/provider 추가 호출 0;
- 우선 shadow/trace-only 비교 후 `actor_intent` mode에 bounded 적용;
- 사용자/player의 감정·선택·관계를 NPC scheduler가 대신 확정하지 못하도록 agency guard.

#### 하지 않는 것

- 모든 eligible Actor 호출;
- Actor proposal의 canonical write;
- 현재 장면과 무관한 사건 강제;
- 고정 장르·인물 수·모델명에 따른 scheduler 분기.
- Actor 간 value 합산, player 만족도 global reward와 근거 없는 scalarization.

#### Exit gate

- 이름이 언급된 원격 인물은 physical actor로 자동 선발되지 않는다.
- 현재 장면에 없더라도 통신·대리인·사전 준비처럼 인과적으로 가능한 영향 후보는 제외되지 않는다.
- 인물이 source-backed 목표를 지속·수정·포기할 수 있고, 단순한 `do nothing`만 안전 결과로
  선택되지 않는다.
- Actor selection 변화가 source, state, risk와 budget 차이로 설명된다.
- 같은 Actor의 value dimension과 trade-off가 source ref로 설명되고, 다른 Actor의 vector와 합산해
  conflict outcome을 결정하지 않는다.
- 고위험 counterfactual은 bounded structured delta만 만들고 저위험 route와 canonical state를
  불필요하게 확장하지 않는다.
- provider timeout·empty·malformed가 기본 생성과 기억 저장을 막지 않고 `degraded`로 남는다.

### 5.3 AC Ensemble `ensemble_performance` 연동

#### 진입 조건

- AC Ensemble Agent의 `integrated_runtime_ready`;
- 4.4 exactly-one stage-owner cutover와 4.5 finality/admission spine의 actual owner mapping;
- 5.1 basic outcome/conflict와 5.2 actor selection의 `dependency_ready`;
- 공식 RisuAI의 current request, postprocess/assembly result와 displayed-final 관찰 계약 확인.

이는 5.1·5.2의 전체 장기 RP `release_gate_verified`를 요구하지 않는다. source 통합을 시작하는
의존 gate와 active profile을 출시하는 live gate를 분리한다. Standalone 완료 여부는 별도
제품 gate이며 Integrated production은 자체 `integrated_runtime_ready`와 4.4·4.5 증거로 판정한다.

#### 목적

서로 독립적인 재작성 후보를 합치는 방식이 아니라, 역할별 Actor가 검증된 공개 장면 상태를
순차적으로 이어받아 반응하는 bounded performance를 구현한다.

#### 작업

- `archive_center.output_lineage.v1`과 `archive_center.ensemble_packet.v1`의 실제 Go contract;
- 4.4/4.5의 owner 선택, performance transcript/final lineage와 terminal fallback을 재사용하고
  두 번째 bridge·complete-turn·admission 경로를 만들지 않음;
- RisuAI recent context와 Archive memory에서 최초 scene context·`public_scene_state`와 Actor별
  `private_actor_context` 구성;
- 선택적 비공연 감독관 proposal, narrator와 Actor role turn의 서로 다른 authority와 output schema;
- 나레이터가 공개 scene context에서 첫 role turn을 만들고 Go가 dynamic next speaker를 선택;
- 각 role turn의 자유문을 직접 적용하지 않고 typed action/realization proposal로 변환한 뒤
  Go validation·basic outcome resolution을 거쳐 accepted transition 적용;
- action-conditioned successor와 공개 event만 다음 Actor의 `public_scene_state`로 전달;
- blocked proposal을 다음 Actor의 현실로 전달하지 않음;
- 역할별 공개 사건과 private reasoning/source의 분리;
- Go가 다음 발언자, 반복, stop reason과 final render readiness 결정;
- 공개 role turn은 `performance_transcript`에 누적하고 lossless transcript assembly는 완료된
  rollout 뒤 한 번만 실행;
- standalone과 integrated mode의 exactly-one 선택;
- 종단 실패 시 partial transcript·명시적 Host fallback의 처리와 lineage를 4.5 계약에 맞춰
  명시하고 성공으로 위장하거나 Standalone으로 자동 전환하지 않음.

#### Exit gate

- Actor는 다른 Actor의 비공개 기억 원문을 받지 않는다.
- 다음 역할은 검증된 누적 공개 상태와 transcript에 반응하며 고정 round-robin으로 호출되지
  않는다.
- 불가능한 Actor 행동은 rollout과 performance transcript에서 제외된다.
- transcript assembler가 private context나 차단된 proposal을 본문 사실로 세탁하거나 공개
  role turn의 의미를 다시 쓰지 않는다.
- 실제 표시 확인 전 role turn, 미완성 transcript와 assembled candidate에서 기억 추출·canonical admission이
  시작되지 않는다.
- 5.5 foreground realization receipt가 연결되기 전에는 5.3 결과를 integration shadow로만 쓰며
  world delta를 canonical state에 자동 기록하지 않는다.
- 플러그인 load, stage dispatch, transcript assembly, final display와 장기 RP 품질을 실제
  RisuAI에서 확인한다.

5.3의 source/contract exit, Host integration exit와 `ensemble_opt_in` release exit는 별도다.
5.3 source 구현이 5.5를 기다리지 않고 검증된 shadow를 만들 수 있고, 5.5는 그 typed receipt를
기존 admission owner에 연결할 수 있다. 실제 profile 승격은 두 증거를 모두 요구한다.

### 5.4 Offscreen Hypothesis Simulation

#### 목적

현재 장면에 없는 인물과 세력이 완전히 정지하지 않도록, admission된 world-time 범위와 중요한
조건이 있을 때만 제한된 장면 밖 **hypothesis** rollout을 계산한다. 이 phase의 독립 완료는
canonical offscreen write가 아니라 재실행 가능한 후보와 receipt다.

#### 작업

- 진입 gate: 5.1 world-clock/typed-action/basic outcome와 5.2 offscreen eligibility의
  `dependency_ready`; 5.5 전체 release는 요구하지 않음;
- offscreen trigger: admission된 world-time 경과, deadline, goal condition, 자원 임계치, 메시지 도착,
  admitted 사건과 scheduled effect;
- current scene actor와 offscreen actor/faction scheduler 분리;
- 매 사용자 턴이 아니라 조건 기반 sparse tick;
- tick별 최대 actor/faction, proposal, depth, token, latency와 world-time 범위 budget;
- offscreen `rollout_state`와 foreground rollout 분리;
- travel, resource, information, faction, dependency와 causal prerequisite 검증;
- 모든 proposal을 typed action으로 만들고 basic reservation/outcome을 먼저 적용하며, advanced
  conflict가 필요한 후보는 임의 순서로 실행하지 않고 pending/deferred;
- irreversible/high-risk admission 후보만 bounded structured counterfactual과 residual target 생성;
- `hypothesis`, `validated_candidate`, `admission_pending` 상태 분리;
- 미발견 사건의 knower/visibility와 later discovery path;
- 동일 world-time range 재실행, restart, branch와 rollback의 idempotency;
- 사용자 설정에서 hypothesis-only와 future canonical admission 허용 범위 분리. 5.5 전에는
  canonical admission 설정 자체를 활성화하지 않음.

#### 하지 않는 것

- 매 턴 세계 전체 스캔·호출;
- 중요하지 않은 일상 행동의 무제한 생성·저장;
- LLM 문장을 offscreen 사건의 source로 사용;
- 다른 branch의 offscreen tick 공유;
- 5.5 admission 계약 전에 hypothesis를 canonical state로 기록.

#### Exit gate

- 장면 밖 진행이 특정 이름·인물 수·턴 수가 아니라 실제 trigger와 state로 재현된다.
- 동시에 아무 조건도 없는 조용한 기간에는 추가 호출과 임의 사건이 0일 수 있다.
- 조건이 충족된 갈등·이동·세력 목표를 비용 절약 명목으로 영구 동결하지 않는다.
- offscreen 결과가 현재 Actor에게 자동 공개되지 않고 discovery 전 knowledge boundary를 유지한다.
- stale·중복·다른 branch tick이 foreground payload나 canonical state를 바꾸지 않는다.
- 이 gate를 통과하면 `offscreen_hypothesis` profile만 승격할 수 있다. canonical offscreen event는
  5.5 authority/receipt gate와, advanced conflict가 실제 필요한 경우 5.6 gate까지 통과해야 한다.

### 5.5 Structured Realization Receipt & Admission Extension

#### 목적

4.0·4.5의 기존 displayed-final/complete-turn/memory admission owner를 확장하여 foreground
realization과 opt-in offscreen candidate를 실제 세계 변화로 승인하거나 pending/reject할 수 있게
한다. 자연어 본문 의미 전체를 “증명”하는 새 verifier나 두 번째 admission ledger를 만들지 않는다.

#### 작업

- actual displayed final과 request/generation/revision의 일치 확인;
- renderer가 제안한 structured realization receipt의 action/event ID, diegetic frame, outcome,
  delta와 claimed span/hash 검증;
- accepted/predicted transition, structured receipt와 actual final span의
  realized/omitted/reversed/expanded/ambiguous 비교 및 prediction residual;
- 관계·지식·위치·생존·자원·thread delta별 lineage·receipt 교집합과 reason;
- transcript assembler가 role turn에 없던 unsupported transition을 만든 경우 lossless assembly
  실패로 분류하고 admission 거부;
- 실제 발생했지만 proposal에 없던 변화는 기존 source/admission policy로 재검증;
- offscreen canonical admission을 명시적 opt-in authority로 추가하되 LLM prose가 아니라
  validated delta, parent revision, rules version, tick/source receipt를 근거로 사용;
- source/simulation authority matrix로 auto-admit 가능한 field와 항상 pending/user-authority가
  필요한 high-risk field를 분리;
- offscreen admitted event와 observed/displayed event의 source kind 분리;
- 미발견 offscreen event는 canonical이더라도 Actor knowledge에 자동 투영하지 않음;
- scheduled effect, cancellation, supersession과 causal descendants 관리;
- reroll·delete·branch·copy/move에서 transition ledger와 active pointer parity;
- 기억 추출, relationship update와 thread lifecycle이 admitted final만 소비하도록 연결.
- ambiguous prose, missing/mismatched receipt, unsupported Host finality와 unresolved conflict는
  `admission_pending`; 임의 승인·거절·본문 hash 기반 의미 추정 금지;
- receipt/residual은 trace·평가 input이며 canonical source나 online learned reward가 아님.

#### Exit gate

- `selected`, `proposed`, `accepted` 또는 `rendered`만으로 canonical write가 일어나지 않는다.
- displayed final이 transition을 누락·반전하면 해당 delta가 저장되지 않는다.
- exact structured event/delta만 자동 admission 후보가 되고 암시·부정·비유·frame ambiguity는
  pending으로 남는다.
- opt-in offscreen admission은 재실행 가능한 receipt와 source kind를 가지며 direct evidence로
  위장되지 않는다.
- 리롤·삭제·분기 뒤 폐기된 transition과 scheduled effect가 다시 활성화되지 않는다.
- 실제 RisuAI 표시 본문, MariaDB row와 다음 턴 `simulation_snapshot`이 같은 admitted revision으로
  대조된다.

5.5는 5.6 결과를 미리 요구하지 않는다. 5.1 basic outcome slice가 **완전히 해결한 single-step,
non-conflicting delta**부터 admission을 연다. multi-Actor/resource/long-causal conflict, partial
reservation 또는 unresolved ordering은 반드시 pending으로 남기고, 5.6이 typed resolved outcome을
반환한 뒤 **같은 5.5 admission owner**에 재입장한다. 5.6은 canonical write를 직접 수행하지
않으므로 phase owner와 evidence가 순환하지 않는다.

필수 E2E는 두 경로를 모두 검증한다. (a) fully resolved basic delta가 receipt 교집합과 actual final
lineage를 통과해 한 번만 admitted됨, (b) advanced conflict가 5.5에서 pending→5.6 resolved
outcome→5.5 재검증으로만 admitted되며 5.6 직행 write와 unresolved partial admission은 0임.

### 5.6 Advanced Conflict & Causality Resolver

#### 목적

5.1의 basic outcome slice를 넘어 여러 Actor와 세력이 동시에 상충하는 typed action을 제안할
때 실행 순서, 자원, 위치와 장기 결과를 일관된 인과로 해결한다. 이 phase가 5.3/5.4의 첫
proposal을 가능하게 하는 최소 conflict owner는 아니다.

#### 작업

- read/write set 또는 동등한 state reservation으로 동시 전이 충돌 검출;
- 같은 자원 중복 소비, 같은 대상의 양립 불가능 상태, 교차 이동과 선행 조건 경쟁 해결;
- initiative를 고정 점수가 아니라 세계 규칙, 시간, 준비, 능력과 사건 조건으로 계산;
- `attempt`, `success`, `partial`, `failed`, `interrupted`, `cancelled` 결과 분리;
- Actor intent와 실제 outcome 분리;
- actor-specific value vector 총합이나 모델 응답 순서가 아니라 world rule·authority·time·
  reservation과 명시된 conflict policy로 typed resolved outcome 반환;
- 후속 scheduled effect와 causal parent/child chain;
- 관계·부상·사망·발견·thread resolution의 scope-limited 전파;
- renderer가 accepted outcome을 벗어났을 때 한 번의 bounded repair/re-proof를 허용할 공식
  Host 계약 검증;
- 안전한 draft replacement가 노출되지 않은 Host에서는 자동 repair를 활성화하지 않고
  admission 거부와 명시적 failure를 유지.
- resolved outcome과 causal lineage를 5.5 기존 admission extension에 반환하고 직접 canonical
  write하지 않음.

#### Exit gate

- 동시 행동의 결과가 호출 순서 우연이나 마지막 모델 문장으로 결정되지 않는다.
- 의도한 행동과 실제 성공한 결과가 기억·관계·세계 상태에서 구분된다.
- 자원·위치·생존·thread closure의 이중 적용과 범위 누출이 없다.
- 5.6 미지원 conflict가 pending인 동안 5.3/5.4의 다른 독립 transition과 base response를
  불필요하게 차단하지 않되 partial conflict를 성공으로 표시하지 않는다.
- repair를 사용하면 최초 출력, 수선 출력, 실제 표시와 admission lineage가 모두 남고 최대 1회
  제한이 실제로 검증된다.

deterministic advanced resolver의 exit와 optional automatic repair의 exit를 분리한다. 공식 Host가
안전한 replacement를 노출하지 않으면 resolver profile은 release할 수 있어도 repair는
`blocked/disabled`로 남으며, 이를 resolver 전체 실패나 조용한 repair 성공으로 바꾸지 않는다.

### 5.7 Long-horizon Character Dynamics

#### 목적

인물의 목표, 믿음, 감정, 관계와 신체 상태가 서로 다른 생명주기로 변하며 다음 장면과 장면 밖
행동에 지속적으로 영향을 주게 한다.

#### 작업

- stable motive, current goal, immediate intent와 action outcome 분리;
- actor-specific value vector의 dimension·source·reconsider trigger를 유지하고 전역 score로
  관계·안전·의무를 합치지 않음;
- 목표의 생성·활성·보류·충돌·포기·완료·대체 transition;
- Actor별 belief와 canonical fact의 차이, 오정보 수정과 신뢰도 변화;
- Actor별 recall strength, 확신, cue 기반 재활성화와 왜곡/교정 projection. canonical fact·world
  memory를 삭제하거나 전역 importance 하나로 모든 인물의 망각을 표현하지 않음;
- 순간 감정, 누적 태도와 장기 관계 domain의 서로 다른 변화 envelope;
- 부상, 피로, 자원 부족과 회복의 시간 기반 scheduled effect;
- 반복 성공·실패·배신·도움·부재가 목표와 관계에 미치는 source-linked 누적;
- 기억 회상 실패나 모델 omission이 canonical 목표·관계를 소거하지 않도록 projection 분리;
- 장기 상태가 actor selection, intent와 표현에 실제 전달되었는지 payload→displayed-final 추적;
- 한 인물을 한 trait·archetype으로 압축하지 않는 다축 character dynamics ViewModel.

#### Exit gate

- 한 턴의 감정이 자동으로 영속 관계가 되지 않고, 큰 사건의 정당한 큰 변화도 임의로 억제되지 않는다.
- A→B와 B→A의 믿음·관계·목표가 별도로 유지된다.
- 인물의 이전 목표가 현재 입력에 이름이 없다는 이유만으로 사라지지 않는다.
- 장기 상태가 DB에 존재하기만 하는 것이 아니라 actor packet, action과 displayed behavior에서
  source ID로 대조된다.
- 장기 세션에서 성격 평면화, 자동 친밀화와 목표 망각이 mode OFF 대비 감소한다.

앞의 source/state/delivery exit는 `dependency_ready/integration_verified` 증거이고 마지막 장기
품질 비교는 5.9의 profile release evidence다. 후자를 먼저 요구해 5.7 production route 구현을
막거나, 전자만으로 RP 개선 완료를 주장하지 않는다.

### 5.8 Adaptive Orchestration & Optional Multi-model Review

#### 목적

4.9의 동일 Go Publisher/orchestration owner를 world-model execution risk까지 확장한다. 모든
장면에 가장 비싼 경로를 사용하지 않고, 실제 transition 위험과 사용자 설정에 따라 필요한
검증 깊이를 선택하되 두 번째 Publisher·Reviewer·guidance/render 경로를 만들지 않는다.

#### 작업

- 장면 위험 신호: 사망·부활, 장거리 이동, 비밀 공개, 큰 관계 변화, 주요 자원 소비,
  thread closure, 다중 Actor 충돌, 큰 prediction residual과 offscreen canonical admission;
- `continuity_only`, `actor_intent`, `ensemble_rollout`, `offscreen_hypothesis`,
  `offscreen_admission`의 명시적 route;
- 4.9 `directed/reviewed/deep`은 narrative guidance depth, 5.8 route는 world-model compute path로
  분리하되 같은 request owner가 exactly one 조합을 고정하고 한 final block·render를 반환;
- low-risk는 규칙/단일 successor만 사용하고, high-risk에서만 bounded structured
  counterfactual 또는 optional review 실행;
- provider/model 이름이 아니라 관찰 가능한 capability, contract support, latency와 사용자가 정한
  budget으로 호출 형식 조절;
- 규칙만으로 판정 가능한 transition은 추가 모델 호출 없이 처리;
- AC Ensemble은 role-specific performance가 필요한 장면에 사용;
- Fusion 또는 다른 다중 모델 검토는 고위험 proposal의 반론, 모순, coverage gap을 찾는 선택적
  reviewer로만 사용;
- reviewer는 eligible evidence, privacy ceiling, transition schema와 fixed deadline 안에서만 동작;
- panel/judge 합의가 hard constraint, source authority와 Go admission을 덮어쓰지 못하게 함;
- reviewer가 Actor별 value vector를 global score로 합치거나 prediction residual을 truth/reward로
  사용하지 못하게 함;
- 여러 provider에 private context가 전송될 수 있으므로 명시적 provider allowlist, 지원되는
  요청의 ZDR 요구, secret redaction과 사용자 동의 정책;
- ZDR provider routing이 plugin·tool의 별도 보존 정책까지 자동 보장한다고 가정하지 않고
  Fusion 및 함께 활성화된 tool의 data policy를 별도 확인;
- 호출 수, token, 실제 provider usage, latency, 품질 변화와 첫 출력 채택률 공개.

#### Exit gate

- 단순 장면은 Living World OFF 대비 불필요한 다중 호출 없이 처리된다.
- 고위험 장면은 설정과 budget이 허용할 때 필요한 검토를 실제 실행하고, skip 이유를 남긴다.
- Fusion 미지원·timeout·malformed가 canonical decision이나 메인 출력을 막지 않는다.
- Fusion OFF/ON 비교에서 비용·지연과 requirement별 실패 변화가 별도로 보고된다.
- 외부 panel에 Actor별 비공개 기억 전체나 미발견 사건을 무조건 전송하지 않는다.
- ZDR 설정과 별개로 Fusion·tool의 실제 data policy와 전송 범위를 사용자가 확인할 수 있다.
- 4.9 Publisher OFF/`none`을 5.8이 우회해 guidance를 생성하지 않고, 5.8 OFF이면 검증된 이전
  direct route가 유지된다.

### 5.9 Living World Release Candidate

#### 목적

기능 추가를 멈추고 실제 사용자 환경에서 장기 일관성, 장애 격리, 비용과 RP 품질을 검증하여
6.0 artifact와 **각 release profile의 개별 승격 가능성**을 판단한다.

#### 작업

- 지원 공식 RisuAI 버전의 문서·upstream commit/tag·hook/type 재확인;
- actual plugin load, before/after request, streaming, final display, save, reroll, delete, branch와
  chat transition의 production E2E;
- 실제 MariaDB canonical write, Chroma rebuild/hydration과 restart/recovery;
- memory family별 persistence→selection→hydration→eligibility→rendered→payload→admission 계보,
  confirmed branch owned-range와 vector preview/trace 비누출;
- semantic scene boundary와 hierarchy child-source coverage·summary fidelity·open-tail 상태;
- Windows, 지원 POSIX/배포 환경과 실제 package hash chain;
- 서로 다른 provider family와 capability profile 비교;
- mode별 OFF/ON, no-provider, timeout, malformed, partial, crash와 backend unavailable;
- 장기 세션에서 actor count, world size, thread 수, offscreen duration과 branch 변형;
- latency p50/p95, token/cost, 호출 수, first-output acceptance와 reroll률;
- 기존 장기 기억·Publisher·원작 자료·삭제·rollback 성능과 의미 비퇴행;
- profile별 포함 requirement, non-waivable gate, enablement 기본값, 열린 requirement, known
  limitation과 사용자 승인 scope change ledger;
- finite live matrix에서 0건을 절대 오류율 0으로 표현하지 않고 category별 exposure·관찰 건수와
  검증 범위를 함께 보고;
- JavaScript lines added/removed와 남은 adapter-side policy 보고.

#### Exit gate

- 승격할 profile의 포함 requirement와 모든 non-waivable gate가 `release_gate_verified`다.
- 순간이동, 사망 상태 위반, 전지적 지식, 관계 급변, 무근거 thread closure와 stale resurrection의
  목표 회귀가 profile별 pre-registered live matrix에서 관찰되지 않고, exposure와 남은 한계를
  함께 공개한다. 이는 오류 가능성 0의 증명이 아니다.
- `core_continuity`는 optional profile이 disabled/beta인 채 독립 승격할 수 있다. optional profile은
  core 증거에 기대어 승격하거나 문서상 존재만으로 6.0 약속에 포함되지 않는다.
- `offscreen_hypothesis`는 canonical write 0을, `offscreen_admission_opt_in`은 별도 authority·receipt·
  rollback을 각각 증명한다. 둘을 하나의 성공으로 합치지 않는다.
- 장면 밖 activity/비용/privacy 평가는 해당 offscreen profile을 승격할 때만 필수지만, optional
  기능 실패가 base 기능을 막지 않는 non-waivable isolation은 모든 artifact에서 필수다.
- AC Ensemble과 Fusion이 없거나 실패해도 Archive Center 기본 기능이 유지된다.
- source/test/package/loaded/live/long-session evidence가 하나의 완료 표현으로 합쳐지지 않는다.

### 6.0 Archive Center Living World

6.0은 새 실험 기능을 넣는 단계가 아니라 5.1~5.9에서 **해당 profile에 대해 검증한 계약만**
정식 제품 경계로 고정한다. 하나의 6.0 artifact 안에서도 profile은 `GA`, `beta/opt-in`,
`disabled/unavailable`을 구분한다.

#### 포함 조건

- `core_continuity`의 안정된 versioned transition, clock, typed action/basic outcome, output lineage와
  보수적 admission contract;
- 기존 DB를 보존하는 migration, backup, rollback과 downgrade 정책;
- mode별 설정, 비용 한도, privacy/provider 선택과 설명 가능한 trace UI;
- 기본 `continuity_only`와 artifact에 포함된 profile별 opt-in/disabled 상태의 fresh install·update 동작;
- AC Ensemble capability negotiation과 absence/failure isolation. `ensemble_opt_in` 승격은 별도 manifest;
- canonical offscreen admission을 포함할 때만 명시적 사용자 정책과 audit/replay manifest;
- 실제 release artifact, 운영 문서, 문제 해결 runbook과 known limitation;
- 5.9 completion evidence manifest 승인.

#### 6.0이 약속하는 것

- 모든 artifact: Go owner, source/authority/fence, base memory·response 비퇴행과 profile 상태의 정직한 표시;
- `core_continuity` GA: 세계 상태와 허용 delta가 시간·공간·생존·지식·관계·인과 제약 안에서
  구조적으로 대조되고 ambiguity는 canonical write 대신 pending이 됨;
- `actor_intent` GA일 때만: 인물이 actor-specific goal/value vector로 typed action 후보를 가짐;
- `ensemble_opt_in` GA일 때만: 여러 Actor가 검증된 action-conditioned 공개 outcome에 순차 반응함;
- `offscreen_hypothesis` GA일 때만: 장면 밖 목표가 sparse bounded candidate로 진행됨;
- `offscreen_admission_opt_in` GA일 때만: 허용된 simulation-generated event가 별도 source kind,
  receipt와 rollback 경계로 canonical state에 반영될 수 있음;
- `advanced_conflict`, `long_horizon`, `adaptive_review_opt_in`은 각 manifest가 GA일 때만 그 이름의
  추가 결과를 약속함;
- 여러 모델을 사용할 수 있지만 모델 합의가 정사 권한이 되지 않음;
- 실제 표시·승인된 변화와 장면 밖 simulation event가 source kind와 관점 경계를 유지함;
- 고급 기능을 끄거나 외부 plugin이 없어도 Archive Center 장기 기억 기능이 정상 동작함.

#### 6.0이 약속하지 않는 것

- 현실 전체를 예측하는 범용 월드 모델;
- 작품 규칙이 없는 물리·사회 결과의 완전한 정확성;
- 모든 인물의 매 순간 연속 simulation;
- LLM hallucination의 완전 제거;
- 사용자를 대신하는 plot·player character·감정·관계 결정;
- 비용과 지연이 없는 무제한 multi-agent orchestration;
- disabled/beta optional profile의 독립 행동·Ensemble·offscreen canonical 진행·고급 conflict·
  multi-model 품질 향상;
- learned dynamics, online self-training, calibrated outcome probability와 전역 최적 plot;
- 외부 provider의 내부 보존·학습·routing을 Archive Center가 기술적으로 통제한다는 보장.

#### 현재 입력만으로 기계적으로 증명할 수 없는 것

- displayed text hash만으로 암시·부정·비유·시제·시점이 섞인 자연어의 모든 사건 delta를 완전
  증명하는 것;
- source/rule이 없는 물리·사회·심리 결과의 유일한 정답과 정확한 확률;
- stochastic LLM/provider가 같은 입력에서 항상 같은 proposal·본문을 반환함;
- outbound packet에 금지 source가 없다는 사실을 넘어 모델이 공개 단서에서 비밀을 추론하지
  않는다는 절대 보장;
- 외부 provider 내부의 실제 retention·학습·gateway fallback이 0임을 로컬 trace만으로 증명하는 것;
- finite fixture와 live session에서 오류 0건을 모든 미래 입력의 오류율 0으로 일반화하는 것.

이 한계는 구현 포기의 근거가 아니다. 기계적으로 증명 가능한 교집합만 auto-admit하고,
나머지는 `admission_pending`, 명시적 사용자 권한, disabled profile 또는 known limitation으로
남기는 제품 경계다.

#### LLM 고유 한계와 대응

- LLM은 사실이 아닌 그럴듯한 action/outcome/receipt를 만들 수 있으므로 proposal producer다.
- user 방향에 동조하거나 여러 모델이 같은 오류를 반복할 수 있으므로 confidence·합의·다수결은
  authority가 아니다.
- 긴 context window, retrieval hit 또는 DB row 존재는 장기 상태가 실제 payload에서 사용되거나
  시간·인과가 일관되게 갱신됐다는 증거가 아니다. long-context 모델도 정보 위치에 따라 성능이
  저하될 수 있으므로 payload→displayed-final→다음 turn 계보를 따로 검증한다.
- 자유 자연어 plan은 executable world action이 아니다. precondition, resource, ordering,
  branch/revision과 effect를 deterministic validator가 다시 확인한다.
- 외부 source·tool·deterministic validator가 새 정보를 주지 않는 동일 모델의 자기 비평·재작성은
  독립 검증이 아니며 정답을 훼손할 수 있다. 이를 모든 tool-assisted correction의 불가능으로
  일반화하지 않는다.
- LLM evaluator는 후보 순서·verbosity·self-preference bias를 가질 수 있다. candidate identity와
  순서를 가능한 범위에서 blind/randomize하고 structured/human check와 분리한다.
- agent 수, round 수와 합의율은 correctness evidence가 아니다. 공유 prompt·첫 답·model family의
  상관 오류와 순응을 별도 측정한다.
- 자연어 확률과 self-report는 calibration evidence가 아니므로 successor는 deterministic,
  bounded alternative와 unknown을 분리한다.
- prompt 준수·structured output은 provider/config에 따라 실패할 수 있으므로 malformed·partial·
  timeout은 degraded/pending이며 stale plan을 재사용하지 않는다.
- LLM의 내부 chain-of-thought, 숨은 belief와 provider 내부 상태는 world state나 debugging proof로
  저장·요구하지 않는다.

## 8. End-to-end 흐름

### 8.1 현재 장면

```text
RisuAI 공식 관찰값 + canonical_state
  -> Go request/revision fence
  -> source/authority/frame/time/knower observation assimilation
  -> 5.0 simulation snapshot + 5.1 world/scene clock
  -> Actor별 observation와 5.2 goal/value vector
  -> typed action candidates
  -> 5.1 hard constraints + basic reservation/outcome
  -> high-risk일 때만 bounded structured counterfactual
  -> 선택 시 5.3 AC Ensemble role turns
  -> 필요 시 5.6 advanced conflict/outcome resolution
  -> accepted resolved transition만 rollout_state 갱신
  -> simulation_outcome_receipt + final scene render/realization receipt
  -> RisuAI 실제 표시 확인
  -> 5.5 accepted/simulation/displayed/authority 교집합 + prediction residual
  -> admitted / admission_pending / rejected
  -> admitted transition만 canonical_state S_t+1 반영
  -> 기억·관계·지식·thread lifecycle 후속 처리
```

### 8.2 장면 밖 진행

```text
admitted world-time/state change
  -> 5.4 trigger evaluation
  -> bounded offscreen actor/faction selection
  -> 같은 parent revision에서 typed action proposal
  -> 5.1 basic outcome, 고위험이면 bounded counterfactual
  -> 필요 시 5.6 advanced conflict resolution
  -> simulation_outcome_receipt + offscreen rollout candidate
  -> 기본 hypothesis-only
  -> 5.5 explicit simulation authority/user policy 교집합 검증
  -> admitted offscreen event
  -> canonical_state 갱신, Actor knowledge는 불변
  -> 이후 관찰·전달·발견 transition이 있을 때 knowledge 갱신
```

## 9. 실패와 degraded 계약

| 실패 | 허용 결과 | 금지 결과 |
|---|---|---|
| state/source 부족 | `unknown` 또는 `needs_evidence`, 기본 장면 경로 유지 | 사실·위치·생존·관계를 임의 생성 |
| world-clock owner/before 불명 | time-based route `blocked/disabled`, 기존 clock 유지 | wall clock·turn 수·JS counter로 시간 전진 |
| Actor provider 실패 | 해당 proposal 제외, 명시적 degraded | stale proposal 또는 다른 Actor 기억 재사용 |
| AC Ensemble 종단 실패 | partial transcript 폐기/보존 여부와 explicit Host fallback 계보 기록, admission 보류 | 실패를 ensemble 성공으로 기록하거나 Standalone으로 자동 전환 |
| receipt/display ambiguity | foreground response 보존, 해당 delta `admission_pending` | text hash나 renderer self-report만으로 realized 추정 |
| unresolved advanced conflict | 5.5 pending 후 5.6 resolved outcome으로 재입장 | 부분 reservation·호출 순서 결과를 직접 admission |
| final render 명시적 반전 | 해당 transition admission 거부, 가능할 때만 bounded repair | 표시되지 않은 accepted delta 저장 |
| offscreen tick 실패 | 이전 committed canonical revision 유지 | partial candidate의 canonical write |
| Fusion 실패 | base Go decision 유지, reviewer 실패 기록 | panel 다수결을 truth로 대체 |
| stale/branch mismatch | 결과 폐기와 `stale_rejected` | 현재 branch pointer 변경 |
| backend unavailable | RisuAI 기본 생성·표시와 transport 상태 유지 | JavaScript가 로컬 simulation 정책 실행 |

last-known rollout, 이전 Actor 결과, 이전 final이나 축약 proposal을 다음 요청의 정상 결과로
자동 재사용하지 않는다.

## 10. 예산과 호출 정책

- 전체 eligible actor/faction set을 먼저 확정하고 budget은 호출·전달 attention만 조절한다.
- Actor 수, round 수, 후보 수와 offscreen tick 수를 특정 작품·장르·모델에 고정하지 않는다.
- 규칙 기반 판정, 단일 Actor proposal, Ensemble performance, optional review를 서로 다른 비용
  단계로 추적한다.
- bounded counterfactual은 high-risk category에서만 별도 호출·depth·breadth·latency를 추적하며
  저위험 route는 counterfactual 비용 0이다.
- world simulation budget이 core memory, Host Context, original work와 final response budget을
  잠식하지 않도록 기존 단일 Go allocator에 통합한다.
- budget 부족은 숨은 성공이 아니다. 실행하지 못한 Actor, transition과 proof requirement를
  reason과 함께 기록한다.
- cost 절약을 이유로 확정된 위험 transition 검증을 생략하지 않는다. 해당 mode를 실행할 수
  없으면 lower mode와 degraded status를 명시한다.

## 11. UI와 관찰 가능성

사용자 UI는 내부 chain-of-thought나 Actor private context를 노출하지 않고 다음을 설명한다.

- 현재 Living World mode와 실제 실행 route;
- canonical revision, clock receipt의 before/delta/after/source/uncertainty와 현재 scene presence;
- selected/deferred/excluded actor/faction과 이유;
- 허용·조건부·hard impossible·authority/agency/policy blocked·conflict pending transition과 stable reason;
- typed action, actor-specific value dimension, predicted/resolved outcome와 counterfactual 실행/skip 이유;
- offscreen hypothesis, admission pending, admitted event와 discovery 상태;
- simulation receipt, displayed realization receipt, prediction residual과 admission 교집합;
- provider call, timeout, degraded, token/cost와 latency;
- reroll·삭제·branch로 무효화된 rollout과 transition;
- 기능 OFF에서 기존 경로가 유지되었는지.

UI에서 proposal을 `발생한 사건`, hypothesis를 `정사`, selected Actor를 `등장 인물`, 모델 합의를
`검증 완료`로 표시하지 않는다.

## 12. 필수 검증 시나리오

### 12.1 위치와 이동

1. A는 서울, B는 부산에 있고 현재 장면 시간은 5분이다.
2. 사용자가 B의 이름을 언급한다.
3. B의 즉시 physical appearance는 차단된다.
4. 전화, 메시지, 대리인 또는 이동 시작은 조건에 맞을 때 후보가 될 수 있다.
5. 충분한 world time과 경로 transition이 승인된 뒤에만 B의 장소가 바뀐다.

### 12.2 사망과 비물리 등장

1. C의 사망이 confirmed canonical state다.
2. 일반 Actor 호출과 물리 행동은 차단된다.
3. 회상·녹음·꿈은 별도 mode로 허용될 수 있다.
4. 작품에 유령·부활 규칙이 없다면 사용자 언급만으로 해당 mode를 만들지 않는다.
5. 규칙이 있다면 행위자·비용·선행 조건과 결과를 transition chain으로 검증한다.

### 12.3 관계 급변

1. A→B 신뢰는 낮고 B→A 신뢰는 중립이다.
2. B가 A를 한 번 돕는다.
3. A의 순간 안도와 제한된 신뢰 변화는 가능하지만 연애·충성·상호 관계로 자동 전파되지 않는다.
4. 반대로 source-backed 생명 구조나 배신처럼 큰 사건은 근거에 맞는 큰 변화를 허용한다.

### 12.4 지식 누출

1. A만 비밀 X를 알고 B는 `unknown`이다.
2. 나레이터와 transcript assembler가 X의 source를 다루더라도 B Actor에게 private 원문을
   전달하지 않는다.
3. B는 공개 사건에서 추측할 수 있지만 곧바로 `known`이 되지 않는다.
4. 전달·관찰 transition이 admitted된 뒤에만 B knowledge state가 갱신된다.

### 12.5 장면 밖 독립 행동

1. 원격 세력 F는 3일 뒤 자원을 확보한다는 goal과 조건을 가진다.
2. 현재 장면이 F를 언급하지 않아도 world time과 조건이 충족되면 sparse tick 후보가 된다.
3. 자원·이동·충돌 검증 뒤 event가 hypothesis 또는 opt-in admitted event가 된다.
4. 현재 Actor는 발견하기 전까지 결과를 알지 못한다.
5. 나중에 현장, 보고, 소문을 통해 discovery transition이 발생한다.

### 12.6 Ensemble 상호작용

1. Actor A가 공개 행동을 제안하고 Go가 일부만 허용한다.
2. 다음 Actor B는 허용된 결과만 현재 현실로 받는다.
3. 차단된 A의 private intent나 행동은 B의 지식과 final scene에 나타나지 않는다.
4. transcript assembler가 입력 role turn에 없던 새 결과를 발명하면 lossless assembly 실패이며
   proof에서 admission이 거부된다.

### 12.7 리롤·삭제·분기

1. 첫 final에서 A가 장소 X로 이동한다.
2. 사용자가 리롤하여 이동하지 않은 final을 채택한다.
3. 첫 rollout, displayed realization, scheduled effect와 transition은 superseded된다.
4. 다른 branch에서의 상태는 독립적으로 유지된다.
5. restart 뒤에도 폐기된 이동이 다시 나타나지 않는다.

### 12.8 장애와 비용

1. Actor provider, transcript assembler, Fusion, backend와 offscreen tick을 각각 실패시킨다.
2. core memory, 기본 response와 canonical DB가 가능한 범위에서 유지된다.
3. 실행하지 않은 단계를 성공으로 집계하지 않는다.
4. OFF 대비 호출 수, token, latency와 RP 실패 범주 변화를 함께 측정한다.

### 12.9 Clock와 observation correction

1. 같은 state/action에서 admission된 clock delta가 5분인 경우와 5시간인 경우 successor가 달라진다.
2. 각 advance는 before/delta/after/source/uncertainty receipt를 가지며 unknown before에서는 적용 0이다.
3. 과거 위치 관찰이 정정되면 그 위치에 의존한 미승인 이동 prediction과 scheduled effect가
   invalidate/revalidate된다.
4. correction이 old state를 silent overwrite하거나 이미 admitted descendant를 임의 삭제하지 않는다.

### 12.10 Typed action, Actor value와 counterfactual

1. 같은 Actor가 안전·의무·관계·시간 측면에서 상충하는 두 typed action과 합법적 hold를 가진다.
2. hard/agency gate를 먼저 적용하고, 근거 없는 global scalar로 한 후보를 정답으로 만들지 않는다.
3. irreversible high-risk일 때만 같은 parent/revision의 structured counterfactual이 실행된다.
4. counterfactual branch의 DB·Chroma·payload·admission·scheduled-effect write는 0이고 저위험 장면의
   counterfactual 호출도 0이다.

### 12.11 Receipt와 ambiguity

1. simulation receipt는 물리 이동 성공을 예측하지만 displayed receipt/본문은 꿈 frame으로 렌더링한다.
2. actual display hash는 일치해도 physical location delta는 교집합 밖이므로 admit되지 않는다.
3. 명시적 반전은 rejected, 암시·시제 혼합으로 판단 불가능한 경우는 `admission_pending`이다.
4. transcript assembler가 새 delta를 추가하면 lossless assembly 실패로 기록하고 기존
   authority/precondition을 재통과하기 전에는 저장하지 않는다.

### 12.12 Basic/advanced conflict와 admission 재입장

1. fully resolved single-step/non-conflicting delta는 5.1 basic outcome→5.5 receipt 교집합으로 한 번만 admitted된다.
2. 같은 자원을 두 Actor가 동시에 소비하는 action은 5.5에서 `conflict_pending`이다.
3. 5.6 typed resolved outcome 뒤 같은 5.5 owner에 재입장해 admission을 다시 판정한다.
4. 5.6 direct canonical write, partial reservation admission과 호출 순서 기반 winner는 0이다.

### 12.13 Release profile 독립성

1. `core_continuity` GA artifact에서 Ensemble·offscreen admission·Fusion은 disabled여도 base 기능이 동작한다.
2. `offscreen_hypothesis`는 후보를 만들지만 canonical row delta는 0이다.
3. optional profile 하나의 live gate 실패가 다른 profile의 성공으로 합쳐지지 않는다.
4. UI, package와 manifest가 각 profile을 GA/beta/disabled로 동일하게 표시한다.

## 13. 완료 증거

각 phase 완료 보고는 최소 다음을 포함한다.

- requirement ID와 production owner;
- source commit/build ID와 contract/policy version;
- neutral, negative, inverted, stale, branch, failure와 long-session fixture;
- production Go route와 실제 RisuAI payload/display observation;
- actual MariaDB canonical revision과 필요 시 Chroma rebuild evidence;
- provider/model/OS/profile, mode와 설정;
- selected proposal, validation, rollout, displayed lineage와 admission correlation;
- observation assimilation, clock before/delta/after, typed action, predicted/resolved outcome,
  simulation/displayed receipt, residual과 admission 교집합 correlation;
- counterfactual이 실행된 high-risk reason, 동일 parent/revision과 durable/external write 0 증거;
- OFF/ON의 실패 범주, first-output adoption, reroll, latency, token/cost 비교;
- release profile별 GA/beta/disabled 상태, non-waivable gate와 독립 evidence manifest;
- package와 실제 loaded artifact hash;
- 열린 limitation, blocked requirement와 승인된 scope change;
- JavaScript lines added/removed 및 남은 adapter-side business logic.

다음은 단독 완료 증거가 아니다.

- 문서, schema, DTO, prompt 또는 UI가 존재함;
- mock-only, shadow trace 또는 source grep;
- Actor 수나 모델 수가 늘어남;
- Go test 또는 JavaScript syntax가 통과함;
- 한 개 happy path가 좋아 보임;
- Fusion panel이 합의함;
- proposal 또는 rollout이 만들어졌지만 final payload와 표시를 확인하지 않음;
- 실제 RisuAI 없이 복제 harness에서만 성공함;
- source package와 loaded plugin이 같은지 확인하지 않음.

## 14. 범위 밖

- 별도 graph DB 또는 두 번째 장기 기억 시스템;
- 범용 물리 엔진, 3D 공간이나 연속 시간 simulation;
- 모든 NPC의 매 순간 background process;
- 사용자가 요청하지 않은 player character 자동 조종;
- 고정 plot beat, 필수 사건 수와 결말;
- Actor의 숨은 chain-of-thought 저장·표시;
- 모델명·작품명·프롬프트 문구 기반 정책;
- 검증되지 않은 자동 재작성 반복;
- AC Ensemble이나 Fusion의 필수 의존성화;
- learned latent dynamics, online RL/self-training과 prediction residual을 reward로 쓰는 경로;
- 모든 Actor 목적을 하나의 global scalar reward로 합쳐 plot을 최적화하는 경로;
- counterfactual branch의 durable write, 외부 tool side effect와 다음 request 재사용;
- 6.0 이후의 별도 독립 제품 분리와 marketplace 계획.

## 15. 아직 확정하지 않은 결정

다음 항목은 각 단계의 contract 문서에서 실제 source와 Host capability를 확인한 뒤 확정한다.

1. 5.1이 기존 `simulation_snapshot.v1`을 확장할지 새 major contract가 필요한지;
2. rollout state의 메모리/임시 저장 범위와 crash recovery 정책;
3. offscreen canonical admission의 기본 OFF 여부와 사용자별 authority 범위;
4. world time advance의 기존 production owner와 host observation mapping;
5. conflict ordering에서 결정적 규칙과 모델 제안이 각각 맡을 범위;
6. official RisuAI가 안전한 bounded repair를 위한 draft replacement/protected span을 노출하는지;
7. AC Ensemble capability negotiation, narrator/Actor role-turn packet, dynamic next-speaker,
   performance transcript, timeout과 terminal fallback의 정확한 wire contract;
8. 6.0에서 `continuity_only`를 기존 사용자에게 자동 활성화할지;
9. offscreen event 보존 기간, audit visibility와 export/import 범위;
10. Fusion에 보낼 수 있는 최소 redacted packet과 provider privacy 조건;
11. authorial command, player action, in-world claim을 구분하는 공식 Host/source authority가 실제로
    노출되는지와 미노출 시 사용자 확인 UI 범위;
12. simulation outcome receipt와 displayed realization receipt를 어떤 기존 owner/field로 전달하고
    exact span/event ID를 대조할 수 있는지;
13. 6.0 artifact에서 각 release profile의 GA/beta/disabled 기본값과 독립 kill switch.

결정 전에는 JavaScript fallback, 임의 DB table, 고정 actor/round 수, model-name branch나
dual-write를 추가하지 않는다.

## 16. 바로 다음 문서 packet

구현 전 다음 순서로 bounded 문서를 만든다.

1. **LW-A 현재 production state owner mapping**
   위치, world/scene clock, vitality, knowledge, relationship, resource, thread, correction,
   scheduled effect와 displayed-final/admission의 실제 Go field/store/lifecycle owner를 표로 고정한다.
2. **LW-D RisuAI official capability record**
   지원 버전의 request, streaming, postprocess, displayed final, structured sidecar, reroll, delete,
   branch와 typed author/player authority hook/type을 upstream commit/tag와 함께 기록한다. 미노출
   capability는 `UNKNOWN`으로 두고 dependent active profile을 차단한다.
3. **LW-B neutral failure inventory**
   순간이동, 사망 인물 행동, 지식 누출, 관계 급변, offscreen 정지, stale resurrection의 재현
   fixture와 현재 출력·DB 결과를 기록한다.
4. **LW-C 5.1 logical contract**
   observation assimilation, state/clock, authority taxonomy, typed action, basic conflict/outcome,
   successor, receipts/residual, revision fence와 OFF parity를 확정한다.
5. **LW-E AC Ensemble capability contract**
   `integrated_runtime_ready` 증거가 없으면 blocked로 유지하고, 이후 `ensemble_packet`, typed role action,
   public successor, performance transcript, lossless assembly/final receipt와 terminal failure를
   고정한다.
6. **LW-F live evaluation plan**
   profile별 동일 시나리오, OFF/ON, provider/OS, exposure, 비용과 장기 세션 비교 방법을 확정한다.

이 여섯 packet은 구현 완료 증거가 아니다. 각 packet의 mapping과 fixture가 production owner,
실제 payload, displayed final과 canonical admission에 연결될 때만 다음 phase로 이동한다.
