# Archive Center 6.1-6.5 Fugu 참조형 World Conductor 로드맵

> 2026-09-08 안내: 아래는 작성 당시의 설계·버전 배정 기록이다.
> 현재 작업 순서와 버전 배정은 [4.1–9.0 통합 로드맵](../../_archive/future-reference/4.1-9.0-integrated-roadmap.md),
> 실제 4.3 반영 상태는 [현황 요약](archive-center-4.3-status-summary.md)을 따른다.
> 아래의 예정·완료 표기를 현재 소스나 실행 결과의 증거로 사용하지 않는다.

- 상태: 초안 / 구현 전 계획 / 6.0 이후 버전 배정 제안
- 범위: Archive Center Living World 6.0 안정판 이후의 6.1~6.5
- 조사 기준: 2026-08-13 / Sakana 공식 report·제품·API 문서
- 작성 목적: Sakana Fugu의 query-adaptive orchestration, 동적 agent topology, 선택적 정보 공유,
  agent 격리와 학습형 routing 원리를 참고하여 6.0의 좁은 symbolic narrative world model을
  실행하는 추론 품질·비용·정보 격리를 강화한다.

이 문서는 Sakana Fugu를 Archive Center의 필수 provider나 canonical owner로 채택하는 계획이
아니다. Fugu가 보여 준 **학습된 동적 오케스트레이션**을 세계 상태 기반 다중 행위자
시뮬레이션에 맞게 다시 해석하는 후속 로드맵이다.

5.1~6.0은 모순 없이 지속되는 세계 상태, 행동 가능성, 인과, 표시 최종본과 canonical
admission을 완성한다. 6.1~6.5는 그 안정된 세계 위에서 **이번 사건에 누가 참여하고, 어떤
정보를 보고, 어떤 순서와 통신 구조로 생각·행동·검증할지**를 동적으로 조직한다.

## 0. 결정 스냅샷

- 6.1~6.5의 사용자 노출 후보명은 `World Conductor`다. 내부 기능명 후보는
  `world_conductor`다.
- Fugu에서 가져오는 것은 제품명, prompt, 고정 agent 수나 내부 구현이 아니라 다음 원리다.
  - 요청·상태별 worker 선택;
  - 고정 pipeline이 아닌 동적 workflow topology;
  - 단계별 subtask와 의존성;
  - 필요한 이전 결과만 공유하는 access list;
  - 첫 agent가 전체 궤적을 고정하는 orchestration collapse 방지;
  - 단순 요청과 복잡 요청의 서로 다른 품질·지연 operating point;
  - 실사용 end-to-end 결과로 routing policy를 개선하는 방식.
- Fugu는 월드 모델이 아니다. Fugu식 Conductor는 세계의 사실·위치·생존·지식·관계·인과를
  결정하지 않고, 6.0이 허용한 범위 안에서 agent workflow만 제안한다.
- 6.0 canonical state, transition kernel, conflict resolver, displayed-final proof와 admission이
  모든 Conductor 결과보다 우선한다.
- Conductor, Actor, specialist, aggregator, AC Ensemble과 외부 Fugu API는 모두
  `truth_authority=false`, `canonical_write=false`인 proposal producer다.
- Go가 `allowed_actor_set`, `allowed_role_set`, `allowed_artifact_set`, privacy ceiling, budget와
  deadline을 먼저 고정한다. Conductor는 이 envelope를 넓힐 수 없다.
- JavaScript는 공식 RisuAI lifecycle 관찰, versioned observation 전송, Go 결과의 실제 적용과
  표시 확인만 담당한다. topology·access·routing·retry·admission 정책을 소유하지 않는다.
- 6.1은 결정적 baseline과 논리 계약부터 시작한다. 6.2는 정보 격리, 6.3은 topology,
  6.4는 모델·비용·privacy 적응, 6.5는 충분한 trace가 있을 때만 학습형 routing을 다룬다.
- 6.5에서도 학습형 Conductor가 권한·사실·상태 전이를 결정하지 않는다. 학습 대상은 허용된
  workflow 중 어떤 구성이 좋은지에 한정한다.
- 5.1~6.0 구현 중에는 Fugu식 workflow를 미리 실행하지 않는다. 대신 6.x가 필요한 stable
  lineage, actor eligibility, access evidence, route decision과 outcome trace를 잃지 않도록 한다.
- 6.1~6.5 기능 OFF, agent/provider 미설치, timeout, malformed와 policy rollback은 6.0 Living
  World와 기본 장기 기억 기능을 바꾸거나 막지 않는다.
- 6.5 stable release와 학습형 route 승격은 별도 gate다. 학습 evidence가 부족하면
  deterministic/adaptive Conductor만 안정판으로 내고 `learned_shadow`는 research 상태로 남긴다.

### 0.1 제안 버전 소유권

| 버전 | 주된 작업 | 사용자에게 보이는 변화 |
|---|---|---|
| 6.1 | Constrained World Conductor 계약과 결정적 baseline | 장면마다 필요한 최소 역할만 선택하되 결과를 재현·설명할 수 있음 |
| 6.2 | Dynamic Access Graph와 agent 격리 | 인물별 비밀·오해·관찰 범위를 지키며 독립적으로 판단하고 필요한 공개 사건만 공유 |
| 6.3 | Adaptive Topology와 specialist routing | 대화·충돌·추격·정치·장면 밖 사건에 맞춰 병렬·순차·트리형 검토 구조를 다르게 구성 |
| 6.4 | Model Pool·비용·지연·privacy 적응 | 단순 장면은 가볍게, 고위험 장면은 적합한 모델과 검증 깊이로 처리 |
| 6.5 | Trace-trained Routing과 World Conductor release closure | 실사용 결과를 바탕으로 route를 개선하되 Go hard authority와 즉시 rollback을 유지 |

### 0.2 6.0과 6.1의 경계

```text
6.0까지
  무엇이 사실인가
  누가 어디에 있고 무엇을 아는가
  어떤 행동이 가능한가
  충돌한 행동의 결과가 무엇인가
  실제 발생한 변화가 무엇인가

6.1부터
  이번 상태에서 누구에게 사고를 맡길 것인가
  어떤 역할과 specialist가 필요한가
  각 agent가 어떤 자료를 볼 수 있는가
  병렬·순차·트리 중 어떤 topology가 적합한가
  언제 충분하다고 판단하고 합성할 것인가
```

6.1이 6.0 state authority를 재판정하거나 두 번째 simulation engine을 만드는 경우에는 이
로드맵을 구현한 것이 아니다.

World Conductor의 제품 목표도 world model 연구를 더 닮게 만드는 것이 아니다. 6.0의 제한된
simulation loop가 RP·chat에서 **더 유동적이고 살아 움직이는 세계**로 체감되도록 필요한 계산만
배치하는 것이다. topology가 복잡하거나 agent가 많아도 독립 목표, 상태 민감한 행동, 가능한
대안, 장면 밖 인과, 공개 결과에 대한 상호 반응과 장기 파급이 좋아지지 않으면 실패다.

다음 livingness 축은 5.1~6.0의 동일 scorecard를 소비한다: 목표 지속성, 상태 민감성, 대안
유연성, 장면 밖 지속성, 상호 반응성, 장기 파급, 제약 속 생동성과 비용 대비 체감. Conductor는
이를 한 reward로 합쳐 privacy·agency·hard constraint와 상쇄하지 않는다. 사건 수·상태 변화량·
agent 수·합의율·극적 정도를 livingness의 proxy로 사용하지 않으며, 아무 일도 일어나지 않는 것이
상태에 맞는 장면과 모든 행동을 과잉 차단한 frozen world를 구분한다.

여기서 두 종류의 topology를 섞지 않는다.

- **world topology**는 canonical assertion, location·relation·thread lifecycle, causal link와
  actor eligibility에서 파생되는 세계 구조 및 read-only ViewModel이다. 6.0 owner가 결정한다.
- **execution topology**는 이미 허용된 Actor·thread·evidence에 대해 어떤 proposal producer와
  specialist를 어떤 순서·의존성·예산으로 실행할지 나타내는 request-scoped 임시 DAG다.
  World Conductor가 제안할 수 있는 것은 이것뿐이다.
- 기존 Go scheduler가 전체 eligible actor/faction set을 먼저 고정한다. Conductor는 그 집합 안의
  attention/call 배치와 selected/deferred/excluded accounting을 제안할 수 있지만, 언급·모델
  추천·예산을 이유로 새 Actor의 존재·도달 가능성·자격을 만들 수 없다.

### 0.4 월드 모델 관점과 버전별 현실성 판정

[World Models](https://arxiv.org/abs/1803.10122)와
[DreamerV3](https://arxiv.org/abs/2301.04104)의 공통 핵심은 observation/state representation,
action-conditioned dynamics, imagined rollout이며, 완전한 agent loop에는 policy/value와 실제
observation feedback도 필요하다. 6.1~6.5는 이 dynamics를 학습하거나 대체하지 않는다.

```text
5.1~6.0
  observation -> symbolic state -> typed action -> successor/outcome -> bounded rollout
  -> structured realization -> displayed/admitted feedback

6.1~6.5
  위 계산 중 어떤 proposal producer·specialist·provider를 어떤 access·budget으로 실행할지 선택
```

따라서 World Conductor는 **world model 자체가 아니라 그 바깥의 meta-controller**다. agent 수가
늘거나 Fugu/Fusion을 호출했다고 action-conditioned dynamics, world clock, actor value 또는
observation model이 좋아지는 것은 아니다.

| 버전 | 현실성 | 실제로 가능한 범위 | 현재 불가능하거나 연구로 남길 범위 |
|---|---|---|---|
| 6.1 | 조건부 가능 | Go가 허용 집합과 유한 DAG template를 결정적으로 만드는 local baseline | LLM이 자유형 plan을 냈다는 이유로 안전·정합성이 증명되는 것 |
| 6.2 | 자체 executor에서는 조건부 가능 | Archive Center가 직접 만드는 access graph, redacted packet과 write-free shadow | 외부 Fugu 내부 agent별 access·provider 전달을 공개 응답만으로 증명하거나 외부 호출의 zero side effect를 주장하는 것 |
| 6.3 | 제한된 template는 조건부 가능 | `single`, 독립 병렬, 공개 사건 뒤 순차 반응, build-verify의 유한 catalog | arbitrary recursive topology, 다수결을 truth로 사용, agent 수 증가를 품질 향상으로 간주하는 것 |
| 6.4 | static policy는 조건부 가능 | user allowlist, capability evidence, 예상 비용, hard call/deadline cap, provider drift abstain | 불투명한 nested orchestration의 총비용·retention·내부 payload visibility를 사전에 완전 증명하는 것 |
| 6.5 stable | 조건부 가능 | 비학습 deterministic/adaptive Conductor의 별도 안정판 | 아직 없는 6.1~6.4 production evidence를 전제로 현재 production-ready라고 표시하는 것 |
| 6.5 learned | 현재 연구 단계 | consented corpus의 offline/shadow 비교와 bounded canary | 적은 관찰 trace만으로 인과적 우월성을 증명하거나 route 학습을 world-dynamics 학습이라고 부르는 것 |

이 판정은 기능을 영구히 불가능하다고 선언하는 것이 아니다. 현재 공식 API와 검증 가능한
증거로 제품이 약속할 수 있는 범위를 구분한다. 공개 계약이 추가되면 `UNKNOWN` 항목을 다시
검증하되, 확인되지 않은 내부 동작을 `VERIFIED`로 승격하지 않는다.

## 1. 공식 Fugu에서 확인한 참고 원리

### 1.1 Fugu와 Fugu-Ultra

Sakana Fugu technical report는 두 operating point를 구분한다.

- Fugu는 latency를 중시하며 입력마다 한 worker를 선택한다. 보고서의 설명상 lightweight
  selection head가 worker를 고르고, 일반 Fugu는 역할 배정보다 빠른 model selection에
  집중한다.
- Fugu-Ultra는 품질을 중시하며 Conductor가 subtask, worker와 access list를 포함한 workflow를
  자연어로 구성한다. 독립 시도, chain, tree, debate와 specialist 투입처럼 문제별 topology를
  다르게 만들 수 있다.
- technical report의 학습 설정과 현재 상용 API의 agent 수·model pool은 같은 고정 계약으로
  보지 않는다. Archive Center는 보고서의 숫자를 제품 정책으로 복사하지 않는다.

### 1.2 Agent 격리와 선택적 공유

Fugu-Ultra는 같은 workflow에서 agent별 function-calling trajectory를 격리하고, Conductor가
정한 access list를 통해서만 다른 agent의 결과를 보게 한다. 목적은 첫 agent가 환경과 상호작용한
경로가 뒤의 모든 agent를 같은 방향으로 끌어가 중복 기여를 만드는 orchestration collapse를
줄이는 것이다.

반면 이전 workflow의 환경 상호작용은 persistent shared memory로 제공하여 같은 자료를 반복
탐색하지 않게 한다. 이 두 원리를 Living World에 그대로 적용하지 않고 다음처럼 변형한다.

- 같은 rollout에서 raw private trajectory는 격리한다.
- 다른 agent가 읽을 수 있는 것은 Go가 승인한 public event 또는 명시적인 artifact edge뿐이다.
- workflow 사이에 공유되는 것은 모든 agent의 raw tool history가 아니라 admitted canonical
  state와 actor별 perspective projection이다.
- 과거에 한 agent가 볼 수 있었던 private memory를 다음 workflow의 다른 agent에게 전역
  공유하지 않는다.

### 1.3 동적 aggregator와 specialist

Fugu 보고서는 지식 문제에서는 독립 시도와 task에 맞는 aggregator를 선택하고, coding에서는
builder와 debugger를 번갈아 투입하며, 특수 지식이 필요할 때 specialist를 부르는 사례를
설명한다.

Living World에서는 이 원리를 다음으로 번역한다.

- aggregator 모델을 고정하지 않을 수 있지만 최종 사실 권한은 항상 Go에 남긴다.
- 물리, 이동, 지식, 관계, 인과, thread closure와 privacy specialist는 필요 위험이 있을 때만
  proposal 또는 반론을 만든다.
- specialist가 동의해도 blocked transition이 허용되거나 새 source가 생기지 않는다.
- final composer는 accepted public transition만 렌더링하며 specialist의 private 분석을 정사
  문장으로 세탁하지 않는다.

### 1.4 학습과 최적화에서 가져올 것

Fugu는 single-step worker 성능, 실제 multi-turn agent trajectory와 terminal outcome을 사용해
routing을 학습·최적화한다. Fugu-Ultra의 Conductor는 workflow correctness reward를 사용한다.

Archive Center가 가져올 원리는 다음뿐이다.

- 개별 응답 점수보다 전체 workflow 결과를 본다.
- 모델의 일반 명성보다 실제 harness 안에서의 역할별 성공을 측정한다.
- route, topology, 비용과 최종 결과의 lineage를 연결한다.
- 충분한 실사용 데이터와 결정적 baseline이 생긴 뒤에만 학습형 routing을 검토한다.

Fugu의 training recipe, reward 수치, worker pool과 benchmark score를 Archive Center의 완료
증거나 그대로 사용할 training specification으로 취급하지 않는다.

### 1.6 LLM과 다중 agent에 대해 과장하지 않을 근거

이 로드맵은 LLM의 일반 능력을 부정하지 않지만, 다음 한계를 제품 계약으로 우회하려 한다.

- [Lost in the Middle](https://arxiv.org/abs/2307.03172)은 long-context model도 관련 정보의 위치에
  따라 성능이 달라지고 중간 정보 활용이 저하될 수 있음을 보였다. 긴 prompt나 전체 history
  전송은 canonical memory, retrieval delivery 또는 실제 사용의 증거가 아니다.
- [PlanBench](https://arxiv.org/abs/2206.10498)는 조사한 planning domain과 당시 모델에서 action,
  state change와 plan verification에 큰 실패를 보고했다. 이 결과를 모든 LLM의 영구 불가능
  증명으로 일반화하지는 않지만, 자유 자연어 계획을 transition proof로 쓰지 않을 충분한
  근거다.
- [Large Language Models Cannot Self-Correct Reasoning Yet](https://openreview.net/forum?id=IkmD3fKBPQ)은
  조사한 reasoning task에서 외부 feedback 없는 intrinsic self-correction이 자주 실패하거나
  성능을 악화시킬 수 있음을 보였다. critic·debate·재시도를 자동 correctness amplifier로
  간주하지 않는다.
- [LLM-as-a-Judge의 position bias 연구](https://arxiv.org/abs/2406.07791)는 judge의 선택이 후보
  순서에 체계적으로 영향을 받을 수 있음을 보였다. model vote, Fusion analyst와 Conductor의
  자기 평가는 보조 feature일 뿐 truth label이 아니다.

이 연구들은 특정 task, model과 평가 설정의 결과다. 따라서 `LLM은 절대 계획할 수 없다`거나
`multi-agent는 항상 나쁘다`고 주장하지 않는다. 대신 재현 가능한 Go validator, 독립 human
evaluation, matched-compute baseline과 실제 displayed/admitted outcome 없이는 개선을 완료로
표시하지 않는다.

### 1.7 OpenRouter Fusion과의 관계

[OpenRouter Fusion Router 공식 문서](https://openrouter.ai/docs/guides/routing/routers/fusion-router)는
outer model이 선택적으로 Fusion을 호출하고 1~8개 panel model을 병렬 실행한 뒤 analyst가 답을
비교하고 outer model이 최종 답을 쓰는 beta 구조, model 수·tool-call 제한과 비용 증가를
문서화한다. Fusion은 6.x에서 선택적 `coverage reviewer` 또는 비교 baseline이 될 수 있지만 World
Conductor의 대체물은 아니다.

- panel 합의나 analyst 답은 world source, transition proof 또는 admission 권한이 아니다.
- Fusion을 부르면 provider call, tool 사용, 비용과 data transfer가 생기므로 local
  `plan_shadow`가 아니다.
- model slug나 설정 존재만으로 실제 Fusion 실행을 증명하지 않는다. `tool_choice`, generation
  metadata, panel/analyst trace와 outer-final lineage를 대조한다.
- 기본 3-panel은 같은 prompt의 단일 completion보다 대략 4~5배 비용이며 panel 수에 선형
  증가한다. panel과 analyst의 web search/fetch는 추가 비용과 별도 data policy를 만든다.
- server-tool의 `status: ok`여도 일부 panel 실패나 analyst `analysis` 누락이 있을 수 있으므로
  `failed_models`, raw response, analysis와 outer final을 별도로 기록한다.
- panel 수 증가가 독립 증거를 보장하지 않는다. 같은 오류·자료·judge bias가 상관될 수 있다.
- Fusion OFF/timeout은 6.0 baseline과 non-Fusion Conductor를 막지 않는다.
- 실제 이득은 같은 비용·입력·평가 rubric의 single strong worker와 matched-compute로 비교한다.
- OpenRouter ZDR은 inference provider routing 범위이며 활성 plugin/tool의 보존까지 자동 보장하는
  것으로 해석하지 않는다.

관련 현재 계약은 [Fusion server tool](https://openrouter.ai/docs/guides/features/server-tools/fusion),
[OpenRouter ZDR](https://openrouter.ai/docs/guides/features/zdr)과
[Data Collection](https://openrouter.ai/docs/guides/privacy/data-collection)도 함께 재검증한다.

## 2. Fugu 용어를 World Conductor로 번역하는 방법

| Fugu 개념 | World Conductor 대응 | 그대로 복사하지 않는 이유 |
|---|---|---|
| user query | 현재 canonical snapshot, user input와 world trigger | RP는 한 질문의 정답이 아니라 지속 상태 변화임 |
| worker model | Actor, narrator, specialist, resolver proposal producer, renderer | Actor identity와 model identity는 서로 다름 |
| subtask | 행동 proposal, 독립 관찰, 반론, 결과 표현 task | subtask 문장이 사건 발생 권한을 갖지 않음 |
| access list | source·visibility가 있는 `access_graph` edge | 인물의 지식·privacy와 branch fence를 검증해야 함 |
| workflow state | request-scoped orchestration state와 rollout state | canonical world state와 분리해야 함 |
| agent trajectory | private agent trace | 다른 Actor의 지식이나 기억 source가 아님 |
| aggregator | accepted artifact를 합성하는 renderer/composer | 합성 모델이 truth authority가 되어서는 안 됨 |
| persistent shared memory | admitted state + actor별 perspective projection | raw 전역 agent history는 비밀과 오해를 누출함 |
| correctness reward | hard violation, continuity, agency, 채택, 비용의 다목적 outcome | RP에는 하나의 정답 문자열이 없음 |
| self-call·재귀 | bounded workflow expansion 후보 | 무제한 비용과 종료 불능 위험 때문에 기본 제외 |
| model pool | user-approved provider/capability pool | privacy, 비용, availability와 role별 실측이 필요함 |

핵심 공식은 다음과 같다.

```text
Fugu식 query-adaptive scaffold
  + 6.0 canonical world state
  + actor별 observation boundary
  + deterministic transition validation
  + displayed/admitted proof
  = Fugu 참조형 World Conductor
```

## 3. 6.1 진입 전제와 영구 소유권

### 3.1 6.0 필수 전제

6.1 production route는 자신이 실행할 6.0 release profile이 실제 경로에서 검증되기 전에는
활성화하지 않는다. 모든 profile에 필요한 non-waivable 전제는 다음과 같다.

- `canonical_state`, `rollout_state`, proposal, accepted, displayed와 admitted 상태 계층;
- `can_appear`, `can_move`, `can_know`, `can_act`, `can_affect`, relationship change와 thread
  closure의 동등한 production hard validation;
- actual displayed final proof와 canonical admission;
- reroll, delete, branch, stale request와 restart parity;
- 6.0 mode OFF/ON, package, loaded artifact와 long-session release evidence.

profile별 추가 전제를 분리한다.

- actor/ensemble/offscreen route는 actor/faction eligibility, persistent goal과 실제 사용하는
  Actor별 private/public projection이 검증된 경우에만 연다. `core_continuity`만 실행하는 route에
  5.2 optional profile을 억지로 요구하지 않는다.
- offscreen route는 offscreen trigger, hypothesis, simulation authority와 opt-in admission이
  검증된 경우에만 연다.
- multi-Actor conflict route는 conflict/causality resolution, reservation과 scheduled effect가
  검증된 경우에만 연다.
- AC Ensemble execution route는 `standalone_complete`, backend integration, 실제 loaded RisuAI의
  displayed-final lineage와 6.0 release evidence가 모두 검증된 경우에만 연다.
- 미검증 profile을 제외한 `continuity_only` Conductor는 그 좁은 범위로 출시할 수 있다. optional
  profile 하나가 미완료라는 이유로 unrelated baseline 전체를 영구 차단하지 않는다.

문서, schema, mock나 6.0 source implementation만으로 어떤 6.1 production entry도 열리지 않는다.

### 3.2 Archive Center Go

Go는 계속 다음을 소유한다.

- canonical world/session/branch state와 revision;
- eligible actor/faction/role/evidence의 전체 허용 집합;
- 각 Actor의 knowledge, privacy와 visibility ceiling;
- world time, location, vitality, physical state, relationship, resource와 thread authority;
- Conductor envelope, plan validation, access graph validation과 budget;
- workflow scheduling, cancellation, deadline와 stable failure state;
- proposal transition validation, conflict resolution과 rollout update;
- final render readiness, displayed proof와 canonical admission;
- route trace, evaluation ViewModel, route policy version과 rollback.

Conductor가 Go 안의 module인지 외부 model call인지와 관계없이 이 권한은 이동하지 않는다.

### 3.3 RisuAI JavaScript

JavaScript는 다음만 담당한다.

- 공식 RisuAI가 실제 노출한 request, streaming, output candidate와 committed output 관찰;
- reroll/delete/branch/replacement는 지원 tag의 공식 capability가 있을 때 관찰하고, 없으면
  capability를 `UNKNOWN`/unsupported로 기록하여 해당 admission profile을 비활성화;
- 최소 versioned observation packet 전송;
- Go가 선택한 exactly-one route의 실제 payload/result 적용;
- displayed value 확인과 UI·localization;
- backend-unreachable transport에 필요한 최소 transient state.

JavaScript는 prompt prose를 해석하여 lifecycle 종류를 추정하지 않으며 workflow step, access edge,
model/Actor 선택, specialist 호출, topology, fallback, training signal이나 route reward를 계산하지
않는다. 현재 공개 Plugin V3 type의 output listener는 committed chat snapshot을 제공하지만
reroll/delete/branch 전용 lifecycle과 최종 DOM 의미를 모두 보장하는 계약으로 간주하지 않는다.
[RisuAI Plugin V3 공식 type](https://raw.githubusercontent.com/kwaroran/Risuai/main/src/ts/plugins/apiV3/risuai.d.ts)

현재 `output` listener는 streaming과 Host-side output transformation 뒤의 snapshot을 관찰하지만
listener가 순차 await된다. 무거운 Conductor/worker 실행을 listener 안에서 기다려 Host 흐름을
지연시키지 않는다. background 결과는 captured chat/message identity, generation과 revision을
재검증하고 `messageIndex=-1`, 삭제, supersession 또는 mismatch이면 폐기한다.

### 3.4 AC Ensemble Agent

AC Ensemble은 6.x에서 provider-neutral workflow executor가 될 수 있다.

- Go가 승인한 step별 role/model 호출;
- step input view와 tool/function call 전달;
- worker response와 usage/latency/failure observation 반환;
- accepted public artifact를 다음 승인된 step에 전달;
- 완료된 public rollout을 최종 장면으로 렌더링.

AC Ensemble은 허용 Actor 집합, access graph, canonical state, transition approval, final admission과
route policy를 소유하지 않는다. standalone rewrite와 World Conductor integrated route를 같은
요청에서 연속 실행하지 않는다.

현재 `live_pending` 상태이므로 production integrated route의 선행 능력으로 간주하지 않는다.
`standalone_complete`, 5.1/5.2 gate와 공식 displayed-final 관찰 계약이 닫힌 뒤에만 실제
workflow executor 후보로 승격한다. terminal failure에서 다른 mode로 조용히 갈아타거나 실패한
`main_draft`를 성공한 displayed final로 기록하지 않는다.

### 3.5 Sakana Fugu API의 선택적 위치

Sakana Fugu API는 다음 중 하나로 실험할 수 있다.

- Conductor proposal을 만드는 외부 model;
- 특정 복잡 step의 worker;
- 고위험 workflow의 반론·coverage reviewer;
- final renderer 후보.

그러나 공개 API의 표준 output과 usage 정보만으로 내부 worker topology, access list와 provider별
실제 private context 전달이 Archive Center 계약대로 실행됐다고 입증할 수 있다고 가정하지
않는다. 내부 orchestration이 외부에서 충분히 검증되지 않으면 Fugu를 **내부가 불투명한 하나의
worker model**로 취급한다.

- Fugu 내부 agent 합의는 Archive Center transition proof가 아니다.
- Fugu persistent memory를 canonical world memory로 사용하지 않는다.
- Fugu에 Actor별 private context 전체를 한 번에 보내 내부 격리를 기대하지 않는다.
- provider pool opt-out은 사용자 privacy 통제에 유용하지만 Actor별 visibility 검증을 대신하지
  않는다.
- Fugu 미설치·계정 없음·provider 제한·timeout이 6.0과 World Conductor baseline을 막지 않는다.

2026-08-13 현재 공식 공개 문서에서 확인 가능한 API 표면과 이 로드맵의 해석은 다음과 같다.

- [Models 문서](https://console.sakana.ai/models)는 Responses, Chat Completions, Models와
  Anthropic-compatible Messages API를 문서화한다. `previous_response_id`는 받지 않고 전체
  history를 입력으로 보내도록 하므로 Archive Center가 conversation/world persistence를 계속
  소유한다.
- 같은 문서에서 `temperature`, `seed`, `top_p` 등 여러 sampling field는 accepted-but-ignored다.
  외부 Fugu response를 결정론적 transition kernel이나 replay proof로 사용할 수 없다.
- Fugu-Ultra의 output-token 상한은 final response에만 적용되고 orchestration token은 별도 usage로
  과금된다. token 상한 하나만으로 내부 총비용이 bounded되었다고 가정하지 않는다.
- [Get Started](https://console.sakana.ai/get-started)의 현재 Codex 설정은 Fugu를 stateless retry
  대상으로 설명하고, 일반 Fugu에는 provider pool opt-out을 제공한다. 이것은 durable memory,
  Actor별 privacy isolation 또는 deterministic replay 보장이 아니다.
- 표준 response/usage 문서는 내부 worker identity, step별 transcript, topology와 access list를
  Archive Center가 검증할 수 있는 계약으로 약속하지 않는다. 공식 계약과 live observation이
  추가되기 전에는 이 항목을 `UNKNOWN`으로 둔다.
- [Privacy Policy](https://console.sakana.ai/privacy-policy)는 prompt, upload, output, feedback와
  session data 처리 및 설정에 따른 training/fine-tuning opt-out을 설명한다. 외부 Fugu 실험은
  최소 redacted packet, 사용자 동의, provider allowlist, retention·삭제 정책을 먼저 충족한다.

### 3.6 DLC·외부 실행기 packaging 경계

World Conductor UI나 provider executor를 DLC처럼 분리할 수는 있지만, 분리 가능한 것은
request-scoped proposal/execution surface뿐이다.

- DLC는 immutable read-only item 또는 typed worker result만 반환한다.
- Archive Center Go가 eligibility, access, budget, validation, deduplication, exactly-one final
  composition/injection과 admission을 한 번만 수행한다.
- DLC 부재·비활성·crash는 6.0 route를 바꾸지 않는다.
- 별도 `World Conductor.js`, world-state DB, graph truth store, scheduler, supervisor, final injector나
  admission engine을 만들지 않는다.

## 4. 5.1~6.0에서 미리 보존할 Fugu-ready 기반

이 절은 6.x 기능을 5.x로 앞당기는 계획이 아니다. 5.1~6.0 owner가 자신의 결과를 안정된
contract와 trace로 남겨 6.1이 세계 상태를 다시 추정하거나 parallel owner를 만들지 않게 하는
연결 요구다.

| 기존 단계 | 6.x를 위해 보존할 결과 | 5.x에서 하지 않을 것 |
|---|---|---|
| 5.1 World-State / Transition Kernel | observation/clock/action, proposal/decision ID, basic outcome, reason와 revision fence | Conductor가 hard rule·clock·successor를 수정하게 하지 않음 |
| 5.2 Actor Intent / Value / Scheduler | 전체 eligible actor/faction set, selected/deferred/excluded reason, actor-specific value와 private context refs | 학습 model이 actor authority나 전역 reward를 결정하게 하지 않음 |
| 5.3 Ensemble | role turn lineage, public/private artifact 분리, next-speaker와 stop reason, exact mode | 자유 topology나 raw private trace 공유를 미리 활성화하지 않음 |
| 5.4 Offscreen Hypothesis | trigger, tick, eligible set, world-time range, noncanonical candidate와 discovery path | offscreen agent를 매 턴 모두 호출하거나 hypothesis를 정사화하지 않음 |
| 5.5 Structured Realization / Admission Extension | proposed→resolved/accepted→receipt→displayed→admitted correlation, residual과 rejected/pending reason | model consensus·본문 hash를 admission 근거로 사용하지 않음 |
| 5.6 Advanced Conflict / Causality | read/write conflict, typed resolved outcome, causal parents와 scheduled effect를 같은 5.5 admission owner로 반환 | 호출 순서를 결과 규칙으로 쓰거나 직접 canonical write하지 않음 |
| 5.7 Long Horizon | goal/belief/emotion/relation 상태와 실제 actor behavior correlation | omission을 state 삭제로 해석하지 않음 |
| 5.8 Adaptive Orchestration | Living World의 coarse simulation mode·검증 깊이, risk feature, skip/degraded와 cost/latency trace | 6.x execution DAG나 별도 planner를 미리 만들지 않음 |
| 5.9 Release Candidate | 동일 snapshot에서 OFF/ON 실패 범주, adoption, reroll, cost와 long-session 결과 | 단일 평균 점수로 route 품질을 축약하지 않음 |
| 6.0 Stable Release | freeze된 logical contract, migration, rollback, capability와 evidence manifest | 6.1이 6.0 contract를 무단 재정의하게 하지 않음 |

### 4.1 결정적 baseline의 중요성

6.0의 규칙 기반 `continuity_only`·actor selection·ensemble route는 6.x가 제거할 구식 경로가
아니다. 동적 Conductor의 개선과 회귀를 비교하고, learned policy를 즉시 rollback할 안전한
baseline이다.

- baseline은 같은 snapshot·settings·policy version·capability manifest·budget/deadline class에 같은
  normalized plan을 만들어야 한다. provider availability나 clock을 숨은 입력으로 두지 않는다.
- 4.9 Publisher는 narrative guidance subplan, 5.8은 coarse Living World mode/risk depth, 6.x는 그
  허용 route 안의 execution DAG·worker assignment만 소유한다. 동일 요청의 Go planner, final
  guidance block, render와 injection path는 각각 하나뿐이다.
- 동적 route 실패 때 baseline을 사용할 수 있지만 실제 outcome은 `degraded_baseline`으로
  기록하고 정상 adaptive 성공으로 집계하지 않는다.
- last-known adaptive plan이나 이전 workflow를 baseline 대신 재사용하지 않는다.

## 5. Requirement ledger

| ID | 요구사항 |
|---|---|
| `WC-OWNER` | Conductor는 workflow proposal만 만들고 world truth·hard transition·canonical admission은 Go가 소유 |
| `WC-ENVELOPE` | actor, role, artifact, provider, privacy, budget와 deadline 허용 집합을 plan 전에 고정 |
| `WC-PLAN` | step, dependency, access, output contract, parallel group와 stop condition이 versioned plan으로 추적됨 |
| `WC-ACCESS` | agent는 승인된 input view와 artifact edge만 읽고 raw canonical/private state 전체를 받지 않음 |
| `WC-ISOLATION` | 독립 agent trajectory가 첫 agent의 경로에 무조건 끌려가지 않으며 차단된 proposal이 공유되지 않음 |
| `WC-PERSISTENCE` | workflow 간 공유는 admitted state와 perspective projection만 사용하고 raw private trajectory를 world memory로 만들지 않음 |
| `WC-TOPOLOGY` | 상태·위험에 따라 single, parallel, sequential, tree와 bounded debate를 선택하되 무제한 recursion을 금지 |
| `WC-SPECIALIST` | 물리·지식·관계·인과·thread·privacy specialist는 필요 위험에서만 호출되고 truth authority를 갖지 않음 |
| `WC-AGGREGATOR` | aggregator/model은 동적으로 선택할 수 있지만 accepted public artifact 밖의 사실을 합성하지 않음 |
| `WC-MODEL-POOL` | model/provider 선택은 user allowlist, capability evidence, privacy, cost, latency와 availability를 지킴 |
| `WC-BUDGET` | step·round·parallelism·token·latency·cost의 상한과 stop reason이 실행 전에 존재 |
| `WC-OUTCOME` | route, calls, proposal, validation, final proof, admission, adoption, reroll과 cost가 같은 lineage로 연결됨 |
| `WC-LEARNING` | 학습 대상은 허용된 workflow 선택에 한정되고 권한·visibility·hard rule은 학습으로 변경하지 않음 |
| `WC-BASELINE` | 결정적 6.0 baseline과 OFF parity를 유지하고 adaptive 실패를 성공으로 위장하지 않음 |
| `WC-ROLLBACK` | policy version, canary, kill switch와 이전 baseline 복귀가 canonical data mutation 없이 가능 |
| `WC-PRIVACY` | 외부 worker마다 최소 redacted input만 보내고 내부 multi-agent provider를 Actor 격리의 증거로 간주하지 않음 |
| `WC-LIVE-EVIDENCE` | mock·prompt·model 수가 아니라 실제 payload, displayed final, DB state와 장기 RP 효과로 완료를 판단 |
| `WC-INTENT-FIDELITY` | 비용·안전을 이유로 모든 인물을 정지시키거나 불필요한 agent 호출을 지능으로 위장하지 않음 |

각 requirement는 최소 `open`, `blocked`, `preparatory`, `implemented_unverified`,
`integration_verified`, `release_gate_verified`를 구분한다.

## 6. 논리 계약

아래 이름은 설계용 logical contract다. 현재 구현된 API, 별도 file, table이나 endpoint를 뜻하지
않는다. 기존 owner와 DTO로 표현할 수 있으면 새 경로를 추가하지 않는다.

### 6.1 `world_conductor_envelope.v1`

Go가 Conductor 호출 전에 만드는 immutable permission envelope다.

최소 의미:

- session, branch/worldline, logical turn, request/generation과 canonical revision;
- world time, scene ID와 simulation mode;
- current user obligation과 player agency ceiling;
- `allowed_actor_set`과 Actor별 role 가능 범위;
- Go scheduler가 확정한 eligible actor/faction/thread/evidence set fingerprint와 각 항목의
  selected/deferred/excluded accounting 요구;
- `allowed_specialist_set`과 호출 이유가 될 risk dimensions;
- `allowed_artifact_set`과 각 artifact의 owner, visibility, knower, privacy, source revision;
- provider/model allowlist와 disallowed data class;
- 최대 step, depth, parallelism, round, token, latency와 cost;
- 허용 output contract와 tool set;
- hard stop, cancellation, stale와 fallback policy;
- policy/contract version.

Conductor는 이 envelope 밖의 Actor, source, tool, role, provider, 시간 또는 비용을 요구할 수는
있지만 plan validation 결과는 `scope_expansion_rejected`다. Go가 그 요구를 자동 승인하지 않는다.

### 6.2 `world_workflow_proposal.v1`

Conductor가 반환하는 request-scoped workflow proposal이다.

```text
workflow_id
base_envelope_hash
route_class
risk_dimensions
steps[]
  step_id
  task_kind
  actor_or_role_ref
  capability_need
  input_view_refs[]
  access_from_step_ids[]
  depends_on[]
  parallel_group
  output_contract
  tool_scope
  step_budget
stop_conditions[]
expected_final_artifacts[]
explanation_codes[]
truth_authority = false
canonical_write = false
```

- 자유 자연어 instruction은 구조화된 task kind와 authority를 넓히지 않는다.
- step graph는 6.1에서 bounded DAG로 시작한다. 반복이 필요하면 Go가 소유한 명시적 round와
  stop condition을 사용한다.
- self-call, 재귀와 새 Conductor 생성은 6.1~6.4 기본 금지다. 6.5 연구에서도 depth와 총비용이
  envelope에 고정되지 않으면 실행하지 않는다.

### 6.3 `world_access_graph.v1`

Agent가 서로 무엇을 볼 수 있는지를 artifact edge로 표현한다.

Node 후보:

- actor private view;
- public scene snapshot;
- accepted public event;
- narrator environment observation;
- specialist question과 bounded finding;
- transition decision summary;
- final render input.

Edge는 최소 다음을 가진다.

- from/to step 또는 artifact ID;
- visibility와 knower scope;
- public, private, redacted, aggregate 또는 decision-only projection;
- source revision과 expiry;
- allowed purpose;
- privacy/data class;
- reason과 policy version.

금지 edge:

- 다른 Actor의 raw private memory·belief·goal 원문;
- hidden offscreen event를 discovery 없이 현재 Actor에게 전달;
- blocked/stale proposal을 실제 public event로 전달;
- specialist private analysis를 Actor knowledge로 전달;
- previous branch/workflow raw trajectory를 current truth로 전달;
- chain-of-thought 또는 provider hidden reasoning 저장·공유.

### 6.4 `world_workflow_execution.v1`

승인된 plan의 실제 실행 계보(lineage)다.

- proposed plan, validated plan과 rejected/rewritten step;
- step status: selected, running, completed, empty, blocked, timeout, malformed, cancelled,
  stale_rejected와 skipped;
- actual model/provider/capability profile;
- input view/artifact hashes와 output hash;
- tool calls, public observation과 usage/latency;
- transition proposal와 Go validation result;
- rollout update와 public event publication;
- stop reason, degraded reason과 final render readiness.

Go가 plan을 안전한 subset으로 축소했다면 원 proposal과 validated plan을 모두 보존한다. 조용히
수정한 plan을 원래 Conductor 성공으로 표시하지 않는다.

### 6.5 `world_conductor_outcome.v1`

route 품질과 학습 가능성을 위한 결과 계약이다.

- baseline/adaptive/shadow/canary route;
- requirement별 hard violation과 supported omission;
- actor selection coverage와 불필요 호출;
- knowledge/privacy leak 여부;
- blocked proposal 세탁 여부;
- causal/relationship/thread fidelity;
- livingness 축별 outcome: 목표 지속성, 상태 민감성, 대안 유연성, offscreen→discovery,
  accepted-public 상호 반응, 장기 상태→행동 전달과 frozen-world omission;
- displayed-final realization과 canonical admission;
- user adoption, reroll, correction과 session continuation;
- step/model별 token, cost와 latency;
- provider failure와 degraded path;
- reward feature와 human evaluation은 별도 필드;
- outcome completeness와 missing observation.

사용자 reroll 하나를 자동으로 route 실패 또는 보상 0으로 해석하지 않는다. 문체 선호, 사용자
의도 변경, 모델 오류와 world continuity 오류를 가능한 범위에서 분리한다.

### 6.6 `world_route_policy.v1`

6.4~6.5의 versioned route policy다.

- policy ID, generation, training/evaluation corpus fingerprint;
- supported envelope/contract version;
- eligible feature set과 금지 feature;
- allowed route classes;
- model/provider capability observations;
- cost/latency constraints;
- canary percentage 또는 session opt-in;
- rollback target과 kill-switch condition;
- known limitation과 evidence status.

policy는 canonical state schema, privacy ceiling와 hard validation rule을 포함하거나 변경하지
않는다.

## 7. 기능 mode와 실행 상태

| mode | 의미 | 사용 단계 |
|---|---|---|
| `off` | 6.0 route 유지, volatile ID·timestamp를 제외한 model-bound payload와 canonical DB projection parity, Conductor worker/provider 추가 호출 0 | 전체 |
| `deterministic_baseline` | Go 규칙으로 재현 가능한 workflow 구성 | 6.1+ |
| `plan_shadow` | plan만 계산·검증하며 추가 worker/provider/tool 호출과 외부 비용이 없음 | 6.1~6.5 |
| `execution_shadow` | 명시적 동의·별도 budget으로 dark worker를 실행하되 결과를 payload·rollout·recall·admission에 사용하지 않음 | 6.2~6.5 |
| `access_isolated` | 승인된 access graph와 agent isolation을 실제 workflow에 적용 | 6.2+ |
| `adaptive_topology` | 상태·위험에 따라 승인된 topology와 specialist를 동적으로 선택 | 6.3+ |
| `adaptive_pool` | model/provider/cost/privacy profile까지 route에 반영 | 6.4+ |
| `learned_shadow` | trace-trained policy를 shadow 비교만 수행 | 6.5 |
| `learned_conductor` | 별도 learned promotion gate를 통과한 policy만 opt-in/canary로 적용 | 6.5+ |

- mode는 capability progression이지 성공 status가 아니다.
- 한 요청에는 하나의 final orchestration owner와 하나의 render path만 사용한다.
- OFF parity는 byte-for-byte 전체 process/trace 동일성을 뜻하지 않는다. request ID, timestamp와
  transport metadata를 제외한 normalized payload hash, canonical MariaDB revision, Chroma projection,
  표시 결과와 provider call count를 비교한다. core config 감사 기록은 Conductor 실행 trace가 아니다.
- `plan_shadow`는 추가 agent/provider/tool 호출을 하지 않는다. `execution_shadow`는 외부 비용과
  data transfer가 있으므로 별도 opt-in·privacy·retention·budget을 요구한다.
- 외부 Conductor model이 workflow proposal만 만들더라도 그것은 provider call이므로
  `plan_shadow`가 아니라 `execution_shadow`다.
- 어떤 shadow 결과도 production payload, rollout, recall, canonical write 또는 다음 route의
  fallback에 사용하지 않는다.
- `execution_shadow`의 tool은 read-only·side-effect-free allowlist로 제한한다. 파일·DB·RisuAI
  payload·외부 업무 시스템을 변경하거나 다른 agent를 spawn하는 tool은 shadow에서 호출하지
  않는다. 단, provider request 자체의 과금·logging·retention·data transfer는 외부 side effect이며
  `0`이라고 주장하지 않고 consented execution evidence로 기록한다.
- adaptive route 실패 후 baseline을 사용하면 `degraded_baseline`이며 adaptive 성공이 아니다.

## 8. 단계별 구현 로드맵

### 6.1 Constrained World Conductor 계약과 결정적 baseline

#### 목적

Fugu식 동적 orchestration을 허용하기 전에 6.0 세계 권한을 절대 넘지 않는 envelope, workflow
proposal, plan validation과 재현 가능한 baseline을 만든다.

#### 현실성 및 LLM 한계

- finite template와 Go validation으로 만드는 local deterministic planner는 기술적으로 가능하며
  Fugu나 별도 LLM이 필요하지 않다.
- LLM이 만든 workflow proposal은 malformed, 누락, scope expansion과 허구 dependency를 가질 수
  있다. explanation이 그 plan의 안전성이나 최적성을 증명하지 않는다.
- 따라서 모든 model proposal은 untrusted input이고, invalid plan을 Go가 worker call 전에 거부할
  때만 6.1의 production 범위가 된다.

#### 작업

- 6.0 state/transition/actor/ensemble production owner mapping 재확인;
- `world_conductor_envelope.v1`, `world_workflow_proposal.v1`과 execution outcome의 최소 contract;
- actor·role·artifact·tool·provider·budget 허용 집합 선고정;
- Go deterministic baseline planner;
- bounded DAG, dependency, parallel group와 stop condition validation;
- scope expansion, cycle, missing dependency, invalid access, excessive budget와 stale fence 차단;
- baseline과 Conductor `plan_shadow`의 동일 snapshot 비교;
- simple scene, dialogue, conflict, offscreen tick와 high-risk transition route class;
- plan/skip/failure/degraded와 reason ViewModel;
- 기능 OFF에서 normalized 6.0 payload, canonical state와 provider call count parity 확인;
- JavaScript에 topology 계산을 추가하지 않음.

#### Fugu 참조점

- 입력별 worker 선택;
- task별 workflow 생성;
- latency-oriented simple route와 quality-oriented deep route 구분;
- workflow correctness를 end-to-end 결과로 평가할 준비.

#### 하지 않는 것

- 자유로운 agent recursion;
- 학습형 route production 적용;
- raw private memory의 agent 간 공유;
- Conductor의 transition rule 변경;
- 모델 이름 기반 고정 route;
- 별도 canonical store나 second final composer path.

#### Exit gate

- 같은 snapshot·settings·policy version·capability manifest·budget/deadline class의 normalized
  baseline plan이 재현 가능하다.
- Conductor proposal이 envelope 밖의 Actor·정보·도구·비용을 확장하지 못한다.
- invalid topology와 stale plan이 worker call 전에 차단된다.
- local `plan_shadow`가 추가 외부 호출·비용을 만들지 않고 payload, tool, rollout, MariaDB와
  Chroma를 바꾸지 않는다. 외부 Conductor 호출을 plan shadow evidence에 섞지 않는다.
- `execution_shadow`를 6.1 완료로 몰래 포함하지 않으며, 이후 실행 시에도 explicit opt-in과 별도
  비용·privacy trace 없이는 시작하지 않는다.
- Conductor timeout·malformed·empty에서 6.0 route가 유지되고 failure가 숨겨지지 않는다.
- 실제 RisuAI request lineage와 Go route trace를 대조하기 전에는
  `implemented_unverified` 이상으로 표시하지 않는다.

### 6.2 Dynamic Access Graph와 agent 격리

#### 목적

Fugu의 intra-workflow isolation과 access list 원리를 인물별 지식·오해·privacy를 가진 세계
시뮬레이션에 맞게 구현한다.

#### 현실성 및 외부 API 한계

- Archive Center가 step별 packet을 직접 만들고 실제 outbound hash를 보존하는 executor에서는
  access graph 경계를 검증할 수 있다.
- 외부 Fugu 하나에 여러 Actor의 private packet을 넘긴 뒤 provider 내부 topology가 이를 올바르게
  격리했다고 공개 final response만으로 증명하는 것은 현재 공식 API 계약상 불가능하다.
- `privacy leak 0`은 provider 내부 보존·학습까지 포함한 절대 명제가 아니다. 검증 가능한 gate는
  forbidden source ID, canary와 data class의 outbound 노출 0, access-edge 위반 0이며 retention은
  계약·설정·사용자 동의 항목으로 별도 관리한다.

#### 작업

- `world_access_graph.v1`의 artifact node와 visibility edge;
- actor private view, public scene, accepted event와 specialist finding 분리;
- 독립 Actor/검토 step에는 공통 결과를 미리 주지 않는 clean-slate input;
- sequential reaction step에는 accepted public event만 전달;
- blocked, conditional 미충족, stale와 private proposal의 publication 금지;
- agent/tool trajectory의 step owner와 branch/revision 추적;
- workflow 간 memory는 admitted state와 perspective projection만 소비;
- final composer input에서 private reasoning·blocked proposal·hidden event 제거;
- external provider별 redacted input preview와 data-class trace;
- 6.4보다 먼저 필요한 최소 static provider allowlist, data-class deny, retention/training disclosure,
  hard request/deadline cap을 6.2 external execution 선행 gate로 고정;
- access edge 생성·거부 이유 ViewModel;
- orchestration collapse와 knowledge leak neutral fixture.
- 명시적 opt-in·별도 budget의 `execution_shadow`에서 provider payload와 access graph를 대조하되,
  dark result를 payload·rollout·recall·admission에 전달하지 않음;
- `execution_shadow`가 canonical MariaDB, Chroma projection, RisuAI message/payload, file/tool과
  외부 업무 시스템을 변경하지 않는 negative test. provider 과금·logging·retention은 별도
  허용 side effect로 계측;

#### Fugu 참조점

- 같은 workflow 안의 agent trajectory 격리;
- access list에 의한 선택적 결과 공유;
- workflow 사이의 필요한 memory 유지.

#### World Conductor 고유 변형

- Fugu식 shared memory 대신 canonical admitted state와 actor별 perspective를 사용한다.
- Actor가 본 사실과 모델이 내부적으로 읽은 context를 같은 knowledge transition으로 취급하지
  않는다.
- 독립 agent가 서로 다른 결론을 내리는 것은 허용하지만 세계 상태에는 Go가 승인한 결과만
  반영한다.

#### Exit gate

- Actor A의 private memory·belief·goal이 access edge 없이 Actor B에게 전달되지 않는다.
- 첫 Actor의 raw 행동 초안이 독립 Actor의 input을 고정하지 않는다.
- sequential Actor는 실제 accepted public change에는 반응하지만 blocked proposal에는 반응하지
  않는다.
- final composer가 private/blocked artifact를 본문 사실로 세탁하지 않는다.
- 이전 branch와 superseded workflow의 private trajectory가 current workflow에 섞이지 않는다.
- 실제 provider request payload와 access graph hash를 대조한 evidence가 있다.
- forbidden source/data-class canary의 outbound exposure와 access-edge 위반이 사전 등록 fixture에서
  0건이고, 외부 provider 처리·retention 한계가 UI와 evidence manifest에 표시된다.

### 6.3 Adaptive Topology와 specialist routing

#### 목적

현재 세계 상태, 인물 수가 아닌 eligible set, 사건 위험과 사용자 budget에 따라 필요한 협업
구조를 동적으로 구성한다.

6.3의 `adaptive`는 아직 학습형이 아니다. versioned rule/template와 deterministic multi-objective
score로 허용 topology를 고르며, 같은 snapshot·policy·capability manifest에는 같은 plan을 만든다.

#### 현실성 및 다중 agent 한계

- 최초 stable 범위는 `single`, `independent_parallel`, `sequential_public`, `build_verify`의 네
  template로 제한한다. tree, debate, specialist insertion과 mixed scene은 각 template의 추가
  비용·종료·access proof가 생긴 뒤 opt-in experimental profile로 연다.
- 여러 agent는 서로 다른 관점이나 coverage를 줄 수 있지만 같은 model family, evidence와 judge를
  쓰면 오류가 상관될 수 있다. 다수결과 답의 다양성은 correctness proof가 아니다.
- arbitrary natural-language topology와 recursive self-call을 안전·비용 한도 안에서 완전 검증하는
  것은 현실적인 6.3 범위가 아니다.

#### 지원 topology

- `single`: 한 worker가 proposal 또는 render;
- `independent_parallel`: 서로의 결과를 보지 않는 복수 Actor/해결안;
- `sequential_public`: accepted public event 뒤 다음 Actor가 반응;
- `tree_aggregate`: 독립 leaf 결과를 bounded aggregator가 비교;
- `build_verify`: 한 worker의 proposal을 다른 specialist가 반론·누락 검토;
- `bounded_debate`: 같은 evidence set에서 찬반을 만든 뒤 Go가 검증;
- `specialist_insertion`: 필요한 risk dimension에 한해 전문가 step 추가;
- `mixed_scene`: parallel intent 뒤 conflict resolution과 sequential reaction.

#### 작업

- scene/risk feature에서 route class 후보 생성;
- topology별 allowed data flow와 output contract;
- physics/movement, knowledge/privacy, relationship, causality/resource, thread/agency와
  render-fidelity specialist catalog;
- specialist를 일반 평론가가 아니라 bounded question에 답하는 proposal producer로 제한;
- fixed aggregator 제거 가능성 검토와 capability-based aggregator candidate;
- aggregator가 accepted artifact 밖의 사실을 추가하지 못하는 proof;
- topology depth, parallelism, step/round와 stop reason enforcement;
- route가 불필요한 단순 장면에는 추가 worker 0 또는 최소 호출;
- supported action을 과잉 검토로 중화하지 않는 omission evaluation;
- deterministic baseline과 adaptive topology의 requirement별 비교.
- 동일 장면을 matched-compute로 비교하여 더 비싼 model 효과와 routing 효과를 분리.

#### Fugu 참조점

- question별 tree/debate/aggregation;
- builder와 debugger의 순차 교대;
- 특수 지식이 필요할 때 specialist 투입;
- task에 맞는 aggregator 선택.

#### 하지 않는 것

- agent 수나 topology 복잡도를 품질 지표로 사용;
- 모든 장면에 debate·critic 추가;
- specialist 문장을 새로운 memory/source로 저장;
- model vote로 hard rule을 뒤집음;
- user/player 선택을 다수 Actor가 대신 결정;
- 종료 조건 없는 대화와 자기호출.

#### Exit gate

- 단순 장면은 추가 provider call 0의 `single` route를 유지하고 Go planning p95 overhead가 사전
  등록한 budget 이내다. 절대 latency 증가 0을 약속하지 않는다.
- 복잡 장면은 risk에 맞는 topology가 실제 실행되고 선택 이유가 설명된다.
- 독립·순차 step의 data flow 차이가 access graph와 provider payload에서 확인된다.
- specialist가 필요한 위반을 줄이면서 정당한 갈등·관계 변화·사건 진행을 동결하지 않는다.
- aggregator 변경이 truth authority, privacy ceiling와 final admission을 바꾸지 않는다.
- route failure가 정상 adaptive 성공 또는 더 단순한 topology 성공으로 숨겨지지 않는다.

### 6.4 Model Pool·비용·지연·privacy 적응

#### 목적

Fugu의 model routing 방향을 참고하여 역할별 실측 능력과 사용자 제약에 맞는 worker를 선택하되,
provider 이름이나 benchmark 명성에 세계 권한을 부여하지 않는다.

#### 현실성 및 provider 한계

- pinned capability manifest, user allowlist와 static privacy/cost policy는 구현 가능하다. 자동
  capability 추론과 provider 간 품질 순위는 drift가 큰 관찰값이며 canonical rule이 아니다.
- Fugu-Ultra처럼 내부 orchestration이 불투명한 API는 final output cap만으로 총 token·비용을
  정확히 선계산할 수 없다. 예상 ceiling과 hard request/step/deadline cap을 두고, 제공자가 필요한
  cap이나 usage를 노출하지 않으면 production route에서 abstain한다.
- provider가 prompt를 전혀 보존·학습하지 않는다는 사실을 Archive Center가 기술적으로 증명할
  수 없다. 최신 계약 snapshot, opt-out, 최소 packet과 사용자 동의로 관리하며 `zero retention`을
  제품 보장으로 쓰지 않는다.

#### 작업

- role/task-kind별 `model_capability_observation`과 실제 outcome 연결;
- direct generation, Actor embodiment, structured proposal, tool use, critic, aggregation과 render
  capability를 분리;
- user provider/model allowlist·denylist와 explicit override;
- secret/private/offscreen data class별 허용 provider와 redaction;
- provider retention/training/privacy policy를 사용자가 확인할 수 있는 설정·trace;
- simple route는 Fugu식 single-worker operating point 우선;
- high-risk route는 budget이 허용할 때만 Ultra식 deeper topology 후보;
- latency p50/p95, timeout, token, cache와 실제 billed usage 추적;
- model/provider unavailable, rate limit, partial과 capability mismatch의 stable outcome;
- route 전에 관찰 가능한 expected/worst-case 비용 범위와 deadline 계산, hard request/step cap,
  실행 중 budget exhaustion stop. opaque nested usage는 exact preflight proof가 아님을 표시;
- model 교체가 Actor identity·knowledge·goal을 바꾸지 않도록 role packet 고정;
- optional Sakana Fugu API를 black-box worker/conductor candidate로 A/B 시험;
- AC Ensemble와 external Fugu의 중첩 orchestration 비용·visibility를 별도 표시.

#### Fugu 참조점

- worker별 세부 전문성에 따른 routing;
- 새 model을 pool에 추가할 수 있는 behavioral composition;
- 품질·latency가 다른 operating point;
- provider opt-out과 configurable pool.

#### 하지 않는 것

- `모델 X는 항상 관계`, `모델 Y는 항상 물리` 같은 영구 hard-code;
- provider 자체 평가만으로 capability 확정;
- 외부 Fugu 내부 agent를 독립 Actor로 집계;
- max output token만 제한하고 orchestration 비용을 무제한 허용;
- privacy 미확인 provider에 전체 canonical snapshot 전송;
- cheapest route를 fidelity 성공으로 간주.

#### Exit gate

- 같은 role packet을 서로 다른 provider family에서 비교하고 requirement별 강점·실패가 추적된다.
- user allowlist·privacy·cost ceiling 밖의 model/provider가 선택되지 않는다.
- model 변경이 Actor perspective, state authority와 admission 결과를 자동 변경하지 않는다.
- 단순/복잡 route의 비용·지연·첫 출력 채택과 실패 범주가 함께 보고된다.
- Fugu API가 없거나 내부 topology가 불투명해도 provider-neutral baseline과 adaptive pool이
  작동한다.
- nested orchestration의 실제 billed usage와 payload visibility를 확인하지 못하면 production
  default로 승격하지 않는다.
- Fugu/worker capability drift나 model 제거를 감지하지 못하면 frozen route를 강행하지 않고
  deterministic compatible route로 abstain한다.

### 6.5 Trace-trained Routing과 World Conductor release closure

#### 목적

6.1~6.4에서 축적한 source-linked workflow outcome으로 허용된 route 선택을 개선하고, 학습형
policy가 hard authority를 건드리지 않는 상태에서 World Conductor의 실사용 release gate를
닫는다.

#### 현실성 및 학습 한계

- non-learned World Conductor stable은 learned evidence와 분리하면 조건부로 가능하다.
- learned route는 현재 consented production corpus, label policy, 최소 sample과 confidence가 없으므로
  `PLANNED/RESEARCH`다. 이 조건이 생기기 전에는 일정만으로 6.5 learned를 승격할 수 없다.
- 관찰 trace에서 선택된 route와 좋은 결과가 함께 나타났다는 사실만으로 route의 인과적 개선을
  증명할 수 없다. scene 난도, provider 품질, 사용자 취향과 선택 편향이 confounder다.
- 학습하는 것은 route-template·worker assignment·budget/stop policy이지 world representation,
  transition dynamics, Actor utility나 canonical truth가 아니다. 이를 `world model learning`으로
  보고하지 않는다.

#### 진입 조건

- 6.1~6.4 requirement의 production trace와 결정적 baseline;
- route→provider payload→proposal→transition decision→displayed final→admission lineage;
- 충분히 다양한 scene, actor, world, provider, mode, failure와 long-session sample;
- privacy/consent가 확인된 training/evaluation corpus;
- route 결과와 문체 선호·사용자 의도 변경을 구분할 최소 label policy;
- offline replay와 holdout 평가 환경;
- randomized 또는 matched shadow assignment, route propensity와 eligibility logging, 독립 human
  rubric, 사전 등록한 최소 표본·confidence·non-inferiority 기준;
- policy rollback과 kill switch.

#### 학습 대상

- baseline/adaptive route class 선택;
- 필요한 specialist kind;
- independent/sequential/tree/build-verify topology 후보;
- allowed model capability profile;
- stop/continue와 추가 검토의 기대 가치;
- quality·cost·latency operating point.

학습형 policy의 action space는 versioned route-template ID, 이미 eligible인 specialist/worker의
ranking·assignment, budget tier와 aggregator 후보로 제한한다. 자연어 arbitrary DAG나 access edge를
직접 생성하지 않으며, 선택된 template의 access graph는 Go가 결정적으로 compile한다. 여러 worker가
비슷하게 좋은 경우 한 개 hard winner만 정답으로 만들지 않고 uncertainty/soft target을 보존한다.

#### 학습 금지 대상

- canonical fact와 world rule;
- Actor knowledge, privacy와 visibility ceiling;
- `can_*` hard validation;
- relationship change와 thread closure authority;
- branch/revision fence;
- canonical admission과 rollback 범위;
- provider allowlist와 사용자 금지 설정;
- player agency.
- prompt prose, 임시 role/provider 생성과 arbitrary self-recursion;
- production traffic에서 즉시 갱신되는 per-user online RL/bandit.

#### outcome과 reward 원칙

한 개 aggregate 점수만 최적화하지 않는다. 최소 다음을 분리한다.

- hard constraint violation: 순간이동, vitality, knowledge, privacy, resource, thread scope;
- supported omission: 가능한 독립 행동·갈등·관계 변화·장면 밖 진행 누락;
- unsupported escalation과 안전 명목의 neutralization;
- Actor 선택 coverage와 불필요 호출;
- orchestration collapse와 후보 다양성;
- blocked/private proposal의 final 세탁;
- displayed-final fidelity와 admission consistency;
- 사용자 채택, 리롤, 수정과 장기 session 지속;
- cost, latency, timeout과 provider failure;
- 단순 장면 non-regression.

모델 judge나 Conductor의 자기 평가는 보조 feature일 수 있지만 ground truth가 아니다. 실제
transition proof, user correction, admission 결과와 분리하여 기록한다.

observational trace만으로 learned route 승격을 결정하지 않는다. 가능한 경우 consented shadow에서
route를 무작위 또는 propensity-aware로 배정하고, 불가능한 경우 matched scene/provider/cost와
doubly robust 등 사전 지정한 분석으로 선택 편향을 보고한다. 어느 방법도 충분한 표본과 독립
평가 없이 인과 증명을 보장하지 않는다.

학습·평가 split은 turn 단위 무작위 분할을 금지하고 story/session/character 단위로 격리한다.
provider/model-version holdout, unseen world와 long-session OOD pack을 유지한다. uncertainty나 OOD가
기준을 넘으면 policy가 abstain하고 6.3 deterministic route를 사용한다.

#### rollout 순서

```text
offline replay
  -> holdout world/provider evaluation
  -> learned_shadow
  -> opt-in session canary
  -> bounded user cohort
  -> requirement별 release review
  -> learned_conductor opt-in
```

- shadow policy는 production route의 입력이나 다음 training label을 자기 결과로 오염시키지
  않는다.
- canary에서 hard violation, privacy leak, 비용 폭증, stale result 또는 baseline 대비 중요
  regression이 발생하면 즉시 policy generation을 비활성화한다.
- learned kill·policy 교체 시 이미 실행 중인 해당 generation의 graph와 worker result는
  `cancelled` 또는 `stale_rejected`로 폐기하며 baseline이나 다음 요청에 재사용하지 않는다.
- rollback은 canonical state와 DB migration을 되돌리지 않고 route pointer만 안정 baseline으로
  복귀한다.

#### Fugu 참조점

- worker performance 기반 supervised routing;
- 실제 multi-turn harness의 terminal outcome 최적화;
- query-adaptive topology를 학습하는 Conductor;
- 새 worker model을 behavioral pool에 추가하는 확장성.

#### Exit gate

- learned policy가 envelope와 Go validation을 우회할 수 없다는 부정·변형 test가 있다.
- offline, shadow, canary와 live 결과를 서로 다른 evidence 단계로 보고한다.
- deterministic baseline 대비 requirement별 개선과 regression, 비용·지연을 함께 공개한다.
- 사전 등록한 randomized/matched 평가에서 품질 우월성 또는 quality non-inferiority 상태의
  비용·지연 개선이 확인되고, route propensity·missing outcome과 confidence interval을 함께
  공개한다.
- unseen world/character/provider와 long-session holdout에서 route가 안정적이다.
- user opt-out, policy pin, kill switch와 baseline rollback이 실제 loaded artifact에서 동작한다.
- learned route가 없는 환경에서도 6.0과 6.1 baseline이 정상 동작한다.

6.5의 완료 표시는 둘로 나눈다.

- **World Conductor stable**: 활성 deterministic/adaptive profile에 포함된 `WC-*` 중
  `WC-LEARNING`을 제외한 requirement, OFF parity와 실제 장기 RP release matrix가
  `release_gate_verified`다. learned evidence가 부족하면
  `learned_shadow`를 beta/research/disabled로 남긴 채 이 범위만 release할 수 있다.
- **Learned Conductor promoted**: offline/holdout/shadow/canary와 privacy·cost·rollback gate까지
  별도로 통과한 경우에만 `learned_conductor`를 완료로 표시한다.

어느 범위든 포함된 필수 requirement가 `release_gate_verified`이기 전에는 해당 6.5 완료라고
표현하지 않는다. 사용자는 optional 기능을 release scope에서 제외할 수는 있지만 `WC-OWNER`,
`WC-ENVELOPE`, `WC-ACCESS`, `WC-PRIVACY`, `WC-BASELINE`, branch/stale fence, player agency와
displayed-final/admission 같은 non-waivable safety gate를 면제할 수 없다.

## 9. End-to-end 흐름

### 9.1 Foreground scene

```text
RisuAI 공식 관찰 + 6.0 canonical_state
  -> Go가 scene/risk/actor eligibility 확정
  -> world_conductor_envelope 고정
  -> baseline 또는 Conductor workflow proposal
  -> Go plan/access/budget validation
  -> 승인된 topology 실행
       independent Actor proposals
       sequential public reactions
       필요한 specialist findings
  -> 각 step 결과를 6.0 transition kernel이 검증
  -> accepted public event만 rollout_state와 access graph에 게시
  -> final renderer가 accepted artifacts를 장면으로 표현
  -> 실제 RisuAI displayed final 확인
  -> realized transition proof
  -> admitted transition만 canonical_state 반영
  -> conductor outcome과 route evidence 기록
```

### 9.2 Offscreen simulation

```text
admitted world-time/state trigger
  -> 6.0 offscreen eligible actor/faction set
  -> Conductor envelope에 allowed set 고정
  -> 독립 또는 conflict-aware topology 제안
  -> Actor/faction intent와 specialist proposal
  -> transition/conflict validation
  -> hypothesis 또는 opt-in admitted event
  -> Actor knowledge는 discovery 전까지 불변
  -> route outcome은 world source가 아니라 orchestration evidence로 저장
```

### 9.3 독립성과 상호작용의 균형

```text
독립 사고가 필요한 단계
  private view + common public baseline
  다른 agent raw output 비공개

상호 반응이 필요한 단계
  accepted public event만 게시
  다음 Actor가 그 결과에 반응

최종 합성 단계
  accepted public artifacts + final rollout state
  private reasoning과 blocked proposal 제외
```

## 10. Orchestration collapse 방지 계약

World Conductor가 여러 agent를 호출해도 모두가 첫 출력의 표현과 결론을 반복하면 월드 모델
흉내 효과가 없다. 다음을 별도 실패 범주로 추적한다.

- 첫 Actor proposal을 독립 Actor input에 그대로 포함;
- 이전 agent의 reasoning 문장을 다음 agent의 사실 전제로 제공;
- aggregator가 첫 candidate를 기준 답으로 취급;
- 모든 specialist가 같은 broad prompt와 전체 context를 받아 중복 응답;
- 같은 model·prompt·seed 성격의 복제 호출을 독립 증거로 집계;
- public event가 되지 않은 intent를 모두가 관찰한 것처럼 사용;
- agent 수는 늘었지만 행동 후보·관점·검증 coverage가 늘지 않음.

방지 수단:

- step 목적과 output contract 분리;
- clean-slate independent input;
- access edge 최소화;
- 동일 evidence에서 찬반 또는 다른 role question 부여;
- public event publication을 Go accepted transition 뒤로 제한;
- 후보 유사도·공통 오류와 unique contribution trace;
- 불필요한 중복 agent를 다음 route에서 줄이는 cost signal.

다양성 자체도 정답은 아니다. 서로 다른 hallucination을 많이 만드는 것을 collective
intelligence로 평가하지 않는다.

## 11. 평가와 학습 데이터

### 11.1 수집 단위

한 record는 최소 다음을 같은 lineage로 연결한다.

- canonical snapshot hash와 source revisions;
- scene/user obligation과 risk features;
- eligible actor/faction/role/artifact set;
- baseline plan과 adaptive/shadow plan;
- access graph;
- actual worker/provider calls;
- action/event proposals;
- hard validation, conflict result와 rollout deltas;
- final render와 displayed realization;
- admitted/rejected transitions;
- user adoption, reroll, correction와 다음 session behavior;
- cost, token, latency와 failure;
- evaluator 종류와 uncertainty.

### 11.2 데이터 오염 방지

- Conductor prompt나 specialist finding을 world source로 저장하지 않는다.
- learned policy가 선택한 route만 다시 정답 label로 강화하지 않는다.
- retrieval·selection·call만으로 기억 또는 route 성공을 주장하지 않는다.
- user reroll을 모두 불만족 label로 단순화하지 않는다.
- 공개되지 않은 chain-of-thought를 수집·학습 요구사항으로 만들지 않는다.
- private memory가 training export에 들어갈 때 user consent, redaction과 retention policy를 적용한다.
- deleted/rolled-back/branch-private data의 training eligibility를 canonical lifecycle과 분리해
  재검증한다.

### 11.3 평가 split

- seen world / unseen scene;
- unseen world·character set;
- story/session/character 단위 train/validation/holdout 격리와 turn-random split 금지;
- small/large eligible actor set;
- foreground/offscreen/mixed;
- simple/high-risk transition;
- one/multiple provider families;
- normal/timeout/malformed/unavailable;
- short/long session;
- reroll/delete/branch/restart;
- privacy-restricted model pool;
- capability drift와 새 model 추가.

### 11.4 성공 기준

다음 지표를 하나로 합쳐 숨기지 않는다.

- hard world violation rate;
- supported action omission rate;
- livingness 축별 paired-state/matched-cost 개선과 frozen-world rate;
- knowledge/privacy leak rate;
- relationship direction/domain/magnitude error;
- thread closure scope error;
- orchestration collapse와 duplicate contribution;
- Actor coverage와 irrelevant call;
- final realization/admission mismatch;
- first-output adoption과 reroll;
- p50/p95 latency, token/cost와 provider failure;
- baseline 대비 non-regression.

finite fixture나 live sample에서 오류가 0건 관찰되었다는 사실을 무오류 보장으로 표현하지 않는다.
critical suite는 사전 등록하고 0건을 요구할 수 있지만, live 결과에는 노출량, 최소 session/turn 수,
오류율 상한 또는 confidence interval과 알려진 미지원 Host/provider 범위를 함께 보고한다.

## 12. 실패와 degraded 계약

| 실패 | 허용 결과 | 금지 결과 |
|---|---|---|
| Conductor `off` | normalized 6.0 payload·canonical projection parity, 추가 Conductor worker/provider call 0 | deterministic/adaptive route 또는 JavaScript 임시 topology |
| active mode에서 optional Conductor component absent | 해당 mode의 fresh deterministic baseline과 `degraded_component_absent` | OFF로 성공 위장 또는 last-known topology 재사용 |
| plan timeout/malformed | configured mode에 따른 fresh `degraded_baseline` 또는 normalized 6.0 route, 명시적 trace | stale/last-known plan 재사용 |
| scope expansion | 해당 step/plan 차단 | Actor·정보·도구를 자동 추가 |
| access violation | edge·step 차단, privacy warning | redaction 없는 payload 전송 |
| worker failure | 해당 proposal 제외 또는 계획된 bounded alternate | 다른 Actor의 private output으로 대체 |
| specialist failure | 검증되지 않은 finding 제외 | review 생략을 approval로 해석 |
| aggregator failure | 기존 lineage 계약에 따른 base final 보존 또는 terminal failure | 후보를 임의 canonical final로 승격 |
| budget exhaustion | stop reason과 completed subset 표시 | 무제한 추가 호출 |
| Fugu API failure | 호출 전 실패는 fresh provider-neutral baseline, 호출 시작 뒤 실패는 명시적 terminal/partial outcome과 기존 lineage 보존 | Fugu 내부 결과 추정 또는 실행 도중 다른 mode/model로 조용히 갈아타기 |
| learned policy regression | policy kill switch와 baseline rollback | canonical data rollback과 혼합 |
| stale/branch mismatch | workflow 전체 또는 해당 step 폐기 | current pointer 변경 |
| displayed-final mismatch | transition admission 거부 | workflow completion을 사건 proof로 사용 |

fallback은 미리 versioned policy에 있는 경로만 사용한다. 편의를 위해 이전 성공 plan, 다른
session/branch의 topology, last-good worker output이나 숨은 default prompt를 사용하지 않는다.

## 13. 필수 검증 시나리오

### 13.1 단순 장면의 최소 route

1. 현재 장면에는 한 Actor와 낮은 위험의 일상 대화만 있다.
2. baseline과 adaptive route가 불필요한 specialist·debate를 호출하지 않는다.
3. Living World continuity와 Actor private view는 유지된다.
4. OFF 대비 비용·지연 증가와 출력 품질을 측정한다.

### 13.2 원격 인물 언급

1. 사용자 입력이 멀리 있는 B를 언급한다.
2. 6.0 eligibility가 physical presence를 허용하지 않는다.
3. Conductor가 B를 Actor로 요청해도 scope/transition validation이 즉시 출현을 막는다.
4. 통신·대리인·이동 준비가 허용되면 해당 task만 조건부 topology에 포함한다.

### 13.3 비밀과 오해가 다른 세 인물

1. A는 비밀 X를 알고, B는 오정보를 믿고, C는 모른다.
2. 세 Actor가 clean-slate private view로 독립 intent를 만든다.
3. access graph 없이 X가 B/C 또는 external specialist에게 전달되지 않는다.
4. 공개 발언이 accepted된 뒤에만 다음 Actor가 그 public event에 반응한다.

### 13.4 Orchestration collapse

1. Actor A가 잘못된 첫 proposal을 만든다.
2. 독립 Actor B와 specialist는 A의 raw output을 받지 않는다.
3. A의 오류에 모두가 동조하는 topology와 격리 topology를 비교한다.
4. unique contribution, 공통 오류, 비용과 final violation을 기록한다.

### 13.5 동시 충돌과 specialist 삽입

1. 복수 Actor가 같은 자원이나 장소에 양립 불가능한 행동을 제안한다.
2. Conductor가 mixed topology와 필요한 causality/resource specialist를 선택한다.
3. specialist는 반론을 만들지만 outcome은 6.0 conflict resolver가 결정한다.
4. accepted outcome만 다음 Actor와 final renderer에 전달한다.

### 13.6 관계 고위험 장면

1. 한쪽의 고백·구조·배신이 큰 관계 변화를 제안한다.
2. relation specialist는 방향·domain·magnitude·permanence와 source coverage를 검토한다.
3. 모델 합의가 자동 reciprocity나 영속 관계 승격을 만들지 않는다.
4. 정당한 큰 변화도 안전 명목으로 제거하지 않는다.

### 13.7 장면 밖 세력 topology

1. 여러 세력에 독립 goal과 같은 world-time trigger가 있다.
2. Conductor는 eligible set 안에서 독립 intent와 conflict topology를 구성한다.
3. 미발견 event는 current Actor access graph에 들어가지 않는다.
4. hypothesis/admission/discovery와 route outcome을 분리한다.

### 13.8 동적 aggregator

1. 동일 accepted artifacts를 서로 다른 renderer/aggregator profile에 제공한다.
2. capability에 맞는 aggregator 선택이 표현 fidelity를 높이는지 비교한다.
3. 어느 aggregator도 accepted artifact 밖의 사건을 추가하지 못한다.

### 13.9 Provider와 privacy 제한

1. 일부 provider를 제외하고 secret data 전송을 금지한다.
2. route가 허용 pool 안에서만 구성되는지 확인한다.
3. external Fugu를 쓰면 하나의 black-box worker로 추적하고 내부 agent 수를 독립 검증으로
   집계하지 않는다.
4. privacy-compatible route가 없으면 명시적으로 skip/degraded 처리한다.

### 13.10 Learned policy rollback

1. learned policy가 비용 폭증 또는 hard violation route를 선택하게 만든다.
2. canary guard가 policy를 비활성화한다.
3. 다음 요청은 deterministic baseline으로 돌아간다.
4. canonical state, DB schema, user setting과 branch가 손상되지 않는다.

### 13.11 리롤·삭제·분기

1. 첫 workflow와 final이 transition A를 만든다.
2. 리롤 또는 branch에서 다른 topology와 transition B가 채택된다.
3. 첫 workflow의 private trajectory, access edge, scheduled effect와 learning eligibility가 current
   branch로 부활하지 않는다.
4. policy training/export가 삭제·branch privacy contract를 우회하지 않는다.

## 14. 완료 증거

각 version 완료 보고는 최소 다음을 포함한다.

- `WC-*` requirement와 production owner;
- source commit/build, contract와 route policy version;
- deterministic stable 범위와 learned promotion 범위를 구분한 release manifest;
- 6.0 prerequisite의 실제 release evidence reference;
- baseline, shadow, adaptive, learned와 fallback route 구분;
- plan, validated plan, access graph와 actual provider payload hash;
- worker proposal, Go validation, public event, final render, displayed final과 admission correlation;
- actual RisuAI load·streaming·committed output evidence와 지원 tag별 reroll·delete·branch capability
  matrix. 공식 관찰이 없는 lifecycle은 `UNKNOWN`/feature-disabled 또는 별도 수동 evidence;
- actual MariaDB canonical revision과 restart/recovery;
- shadow OFF/ON에서 canonical MariaDB와 Chroma projection 무변경 증거;
- provider family, model pool, privacy setting, OS와 package hash;
- requirement별 OFF/ON failure, adoption, reroll, latency와 cost;
- long-session, negative, inverted, stale, malformed와 policy rollback 결과;
- open/blocked limitation, 사용자가 제외한 optional scope와 non-waivable safety gate 유지;
- JavaScript lines added/removed와 남은 adapter-side business logic.

다음은 단독 완료 증거가 아니다.

- Fugu 논문이나 API를 읽음;
- Fugu를 provider 목록에 추가함;
- Conductor prompt·role catalog·workflow JSON이 존재함;
- agent/model 호출 수가 늘어남;
- 여러 모델이 합의함;
- access graph가 trace에는 있지만 실제 provider payload와 다름;
- mock, shadow, fixture 또는 syntax/test만 통과;
- route score 평균 하나가 개선됨;
- proposal은 좋아졌지만 displayed final과 canonical state에 효과가 없음;
- source artifact와 실제 loaded plugin/package가 같은지 확인하지 않음;
- 비용·privacy·supported omission을 제외하고 hard violation만 줄임.

## 15. 범위 밖과 금지선

- Sakana Fugu의 prompt, weights, training data나 비공개 orchestration 구현 복제;
- Sakana Fugu API의 필수 의존성화;
- 별도 `AC Fugu.js`가 canonical world state 또는 routing policy를 소유하는 구조;
- 별도 `World Conductor.js`, actor scheduler, supervisor, final injector 또는 admission engine;
- 두 번째 world DB, graph DB 또는 memory system;
- Conductor에게 canonical write, knowledge reveal, relationship와 thread closure 권한 부여;
- 모든 Actor의 매 순간 연속 simulation;
- agent 수, round, topology depth, 작품, 장르와 모델명을 고정한 route;
- raw chain-of-thought 저장·공유·학습;
- user/player character의 선택·감정·관계를 agent 다수결로 결정;
- 무제한 self-call, recursion, debate와 repair loop;
- 사용자 동의 없는 private RP data의 외부 training export;
- learned policy를 이유로 deterministic baseline 제거;
- 6.0 미완료 항목을 Conductor가 보완했다는 명목으로 6.0 완료 처리.

## 16. 아직 확정하지 않은 결정

1. 6.0 production DTO 중 어느 contract를 확장하고 어떤 logical contract만 새 이름으로 둘지;
2. World Conductor가 기본 Go rule planner, 별도 provider call 또는 두 방식을 언제 사용할지;
3. 6.1 bounded DAG의 최대 표현 범위와 반복 workflow의 최초 허용 시점;
4. AC Ensemble integrated mode의 실제 workflow execution API;
5. official RisuAI가 여러 후처리 step과 안전한 final replacement를 어디까지 노출하는지;
6. external Fugu API가 내부 topology, agent identity, provider routing과 data visibility를 어느
   수준까지 공식 response로 제공하는지;
7. provider privacy/retention metadata의 canonical source와 갱신 주기;
8. route outcome의 human label과 user reroll reason 수집 UI;
9. training corpus opt-in, deletion, branch privacy와 retention policy;
10. learned policy의 학습 방식: supervised router, contextual bandit, evolutionary search, RL 또는
    비학습 adaptive rule;
11. learned promotion을 위한 최소 story/session 수, confidence, non-inferiority와 hard-stop 기준;
12. `World Conductor`의 사용자 기본값과 6.0 기존 사용자 migration;
13. dynamic aggregator를 model selection으로만 허용할지 role/task instruction까지 적응시킬지;
14. offscreen workflow의 cost quota와 foreground 응답 latency 격리 방법.

이 결정 전에는 JavaScript fallback, dual owner, 새 canonical table, 무제한 worker loop, hidden
provider routing이나 model-name policy를 추가하지 않는다.
