# Archive Center 4.3.0-test.12 — 추가 검색 병렬화와 시간 표시

날짜: 2026-09-07. 상태: `implemented_unverified`.
test.11의 서사 가이드 강도 작업을 포함한다.

## 변경 이유와 동작

기존 1차 분석은 병렬이지만, 그 뒤 담당들이 요청한 추가 검색은 하나씩 기다렸다.
각 검색에는 서버 확인, 질문 임베딩, 기존 세션 범위의 검색과 정본 확인, 원문 연결,
후보 조립이 포함된다. 조립 직후 후보를 다시 계산하는 중복도 있었다.

이번 변경은 다음 순서로 작동한다.

1. 활성 담당들의 1차 분석을 기존대로 병렬 실행한다.
2. 각 담당이 요청한 기존 한도 내의 추가 검색을 동시에 실행한다.
3. 같은 요청 입력을 이용하는 원문 연결·후보 조립은 요청 내부에서 순서대로 수행한다.
4. 검색 완료 순서와 무관하게 기존 담당 순서대로 결과를 합친다.
5. 합쳐진 후보를 필요한 담당의 기존 2차 분석에 제공한다.
6. 받은 기억 추천과 기존 Go 기본 선정 동작을 유지하여 출판사와 최종 주입문으로 전달한다.

검색 질문·범위·필터·횟수와 AI 호출 수를 늘리지 않는다. 5개 담당이 모두 켜졌다면
분석은 기존처럼 5회에 필요한 보충 0~5회가 더해진다. 담당별 추가 질문은 최대 1개다.
검색당 내부 벡터 호출은 기존 이력 세션과 broad/memory/precise 범위에 따라 여러 번이다.
기존 출판사 호출은 이 분석 횟수와 별개다.

정본 후보는 처음 조립할 때 렌더링/선정으로 변경되기 전의 사본을 보관한다.
그 요청에서 후보가 필요하면 사본을 복사하며, 원문과 순서 및 비공개 관점을 유지한다.
사본은 JSON으로 노출되지 않는 요청 내부 필드다. 영구 캐시·새 저장소는 추가하지 않는다.

## HUD와 진단

추가 검색이 있을 때만 **추가 기억 검색**과 `완료 수/전체 수`, 진행 상태,
실제 경과 시간이 나타난다. 검색별 세부 시간은 접힌 목록으로 표시한다.

| 항목 | 측정하는 작업 |
| --- | --- |
| 검색 서버 확인 | 기존 Chroma 상태 확인 |
| 질문 임베딩 | 기존 제공자를 통한 검색 질문 임베딩 |
| 기억 검색 | 기존 이력 세션·필터의 벡터 검색 호출 |
| 기억 유효성 확인 | 검색 결과의 활성 원본 리비전 확인 |
| 원문 연결 | 검색 결과와 기존 정본 기억의 연결 |
| 조립 순서 대기 | 같은 요청의 다른 후보 조립이 끝날 때까지 대기 |
| 후보 조립 | 기존 입력으로 후보/주입문 조립 및 후보 사본 전달 |

전체 검색 시간은 모든 검색과 병합이 끝날 때까지의 실제 경과 시간이다.
검색별 소요 시간은 서로 겹치므로 합산하지 않는다. 기존 `backend_timing`의
`preprocessing_search`도 이 경과 시간을 사용한다. 이 단계는 `injection_assembly`
안에 포함되므로 상위 단계와 다시 합산하지 않는다. 세부 항목 합계에는 표시 정밀도와
일반 함수 처리 시간이 모두 포함되는 것은 아니므로 전체 경과 시간과 정확히 같지 않을 수 있다.

부분/실패 상태는 검색 진단이다. 받은 추천이나 출력·저장을 새로 거부하는 조건이 아니다.
기존 HUD 스트림과 타이머를 사용하며 질문·원문·프롬프트·키는 시간 화면에 넣지 않는다.
백엔드 정책은 Go가 소유하고 JavaScript는 이 값을 표시한다.

## 검증

- 후보 사본을 실제 조립 결과와 비교하는 회귀: 최초/추가 검색 후보, 사적 기억,
  원문·순서, 렌더링 메타데이터 분리, 중첩 슬라이스 복사, OFF와 AI 전달을 검사했다.
  수정 전의 후보 재계산 함수를 Go overlay로 대입하면 최초/추가 조립 회귀 둘 다
  `candidate pool recomputed the already assembled request sources`로 실패했다.
- 채널로 세 검색을 동시에 멈추고 역순으로 완료시켜, 실제 동시 실행·안정적인 병합·
  별칭·2차 대기·부분 실패·첫 추천 보존·호출 수와 시간 화면의 요청 격리를 검사했다.
- 등록된 `/prepare-turn` 경로에서 임베딩 HTTP와 벡터 검색 경계의 실제 중첩을
  확인했다. 검색한 정본이 2차 입력과 최종 Go payload 계획에 전달되며, 기존 검색
  필터/횟수와 7개 세부 시간이 유지된다. 제공자·저장소는 시험용 경계다.
- 생산 JavaScript 함수를 실행해 진행/완료/부분 상태, 실제 전체 시간과 겹치는
  개별 시간, 문자 이스케이프, 기존 타이머 연결·완료·다음 요청 정리를 검사했다.
- JavaScript는 이번 시작점 대비 추가 70줄/삭제 4줄이다. 세 언어 라벨, 검색 시간
  화면과 기존 타이머 연결 및 test.12 식별자다. Go의 검색/선정 정책을 복제하지 않는다.
- Go 1.26.6 HTTP 영역 전체 회귀 통과(18.113초), JavaScript 실행형 회귀 통과
  (12.874초), `go vet ./internal/httpapi`, JavaScript 문법과 변경 공백 검사 통과.

단일 후보 전달 단계의 시험 데이터 벤치마크(3회): 기존 재계산 54.2~60.9µs,
약 40,408바이트/301회 할당; 후보 사본 전달 2.31~3.02µs, 3,920바이트/6회 할당.
이는 작은 시험 데이터의 해당 함수만 비교한 결과다. 전체 RP 요청의 시간 감소나
40M 이력 성능을 뜻하지 않는다. 주된 대기 시간 개선은 독립 외부 검색의 중첩에서
기대되며 실제 개선 폭은 제공자·네트워크·검색 서버의 동시 처리 능력에 따라 달라진다.

## 비교와 남은 실제 확인

[예제 비교](archive-center-4.3-preprocessing-comparison.md)는 전처리만 다룬다.
Coco의 도구 반복 탐색, 여러 예제의 순차 초안 작성과 AC의 정본 기억 준비는
처리하는 일이 다르다. 동일 조건의 실제 시간·출력 비교 없이 우열을 확정하지 않는다.

실제 화면에서 본 기록은 HUD test.8, 실행 중 백엔드는 test.11이었다. 당시 세계·사물
담당은 1차 12.7초 실패, 2차 19.1초 성공이었다. 첫 실패의 실제 `calls[].error`는
확인되지 않았다. 이번 검색 시간 수정이 그 모델 호출 실패까지 해결했다고 보지 않는다.

실제 MariaDB/Chroma/제공자·RisuAI에서 test.12를 사용한 지연과 최종 출력은 미확인이다.
Race 검사는 이 환경의 CGO 비활성화 및 gcc 부재로 실행되지 않았다. 코드 검토와
동시 실행 시험은 통과했지만 race 검사 결과를 대신하지 않는다.
사용자 백엔드·저장 설정·설치 플러그인은 시작하거나 교체하지 않는다.
