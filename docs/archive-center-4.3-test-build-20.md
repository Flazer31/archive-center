# Archive Center 4.3.0-test.20 — 전처리 입력과 근거 연결 보완

날짜: 2026-09-08. 상태: `implemented_unverified`.

## 변경 내용

test.19의 제공된 자료를 고정하고, 모델이 읽는 입력과 선택 근거가 최종 요청에 이어지는
기존 Go 경로를 수정했다. 새 역할·추가 호출·사후 출력 편집은 추가하지 않았다.

- **입력 순서:** 현재 입력과 최근 대화, 담당·예산, 이전 결과·보완 근거를 후보 목록 앞에 둔다.
  기존 JSON 맵 직렬화에서는 긴 후보 목록이 현재 입력보다 먼저 나왔다.
- **반복 출처:** 완전히 같은 출처·턴·공개 범위·지식 소유자·열람자 정보만 `source_catalog`로
  한 번 묶는다. 서로 다른 인물의 지식 범위와 모든 후보 원문·ID·순서는 그대로다.
  한 번만 등장하는 출처는 원래 항목 안에 둔다.
- **정확한 연결:** AI가 선택한 사실과 완성 턴 요약에 각각 요청 내 `F`·`S` 참조를 표시한다.
  담당 설명에도 같은 참조를 붙여, 한 출처에 속한 서로 다른 사실을 구별한다. 설명의 반복
  출처는 별도 `P` 목록으로 묶으며, 출판사가 실제로 받는 자료에도 참조와 목록을 전달한다.
  로어북의 `L` 참조는 설명의 출처 목록에 연결하며 기존 로어북 본문 형식은 유지한다.
- **기존 2차 검토:** 이전 결과에도 동일한 짧은 참조를 사용한다. 공통 기본 지침은 해당 참조의
  실제 원문과 최근 진행을 보고 선택·이유를 검토하도록 보완했다. 저장된 사용자 지침은
  계속 우선하며 설정 파일을 덮어쓰지 않았다.
- **확인 자료:** `calls[].input`은 기존 정본 후보 자료다. `model_input`은 실제 모델에 전송하는
  직렬화된 사용자 메시지이고 `model_input_chars`·`system_prompt_chars`를 함께 기록한다.
  후보 원문 한도와 전체 요청 글자 수를 혼동하지 않도록 구분한다.

원문, AI 추천 순서, 자료별 K, 기존 공개·비밀 범위, 추천 없음 시 해당 영역 Go 선정과
보완 실패 시 1차 결과 유지 규칙은 보존했다. AI의 틀린 이유를 Go가 새 사실로 바꾸거나
추천을 사후 잘라내는 기능은 없다. 사용자의 창작 방향을 제한하는 규칙도 추가하지 않았다.

## 확인한 결과

1. 입력 순서·출처 반복과 개별 사실 연결을 확인하는 새 회귀 두 개가 수정 전 코드에서
   실패했다. 수정 후 실제 전처리 HTTP 경계와 최종 기억·출판사 입력까지 통과했다.
2. 같은 출처의 다른 사실, 다른 인물의 비공개 지식, 완성 요약 출처, 두 차례 참조,
   출판사 OFF·성공·실패, 추천 없음 및 부분 실패 경로를 검사했다.
3. 전체 Go **35개 패키지·일반 3,851개·하위 783개** 통과. 첫 실행에서 빌드 번호 시험 하나가
   test.19를 기대해 실패했으며, test.20으로 갱신하고 해당 패키지 전체를 다시 통과했다.
   MariaDB 8개·Chroma 2개·실제 제공자 1개·POSIX 실행 비트 1개는 환경상 생략했다.
   별도 두 도구 패키지에는 시험 파일이 없다. JS 원본·패키지 구문 검사도 통과했다.
4. 제공된 test.19의 **10개 호출 입력**을 새 표현으로 만들고 되돌려 대조했다. 후보 원문·개수·
   순서·출처·지식 범위·현재 입력·최근 대화·예산이 유지됐다. 이 검사는 외부 호출 없이
   실제 입력 조립 함수를 사용한다.
5. 같은 선택 결과를 재조립한 담당 설명은 약 **3.9만 자 → 2.0만 자**다. 실제 모델 입력
   글자 수도 10개 모두 감소했지만, 가장 큰 1차 입력은 여전히 약 17.2만 자다.
   이를 토큰 감소율·응답 속도·정확도 향상으로 환산하지 않는다.

이 결과는 전달 구조의 수정과 데이터 보존을 입증한다. AI가 test.19의 잘못 연결한 이유나
과다 선택을 실제로 고쳤다는 증거는 아니다. 원래 잘못된 이유를 넣은 회귀도 그대로
전달되는지 검사해, Go가 해석을 대신 고쳤다는 오판을 피했다.

## 남은 검증

수정 전후 실제 모델 비교는 **대기 중**이다. 최초 네트워크 시도는 샌드박스에서 차단됐고
응답을 받지 못했다. 이후 자동 승인 심사가 비공개 기억을 포함한 test.19 자료를 현재
설정된 Ollama Cloud·LLM Gateway에 전송하는 데 명시적인 승인을 요구하며 거절했다.
전송 대상·자료·총 10회 호출에 대한 질문을 사용자에게 전달했고, 승인 없이 재시도하지 않았다.
네트워크가 차단된 초기 진단의 PASS 표시는 제공자 성공 증거가 아니며 실패 로그로 보존한다.

승인 후 비교하더라도 고정된 2차 입력에 대한 역할별 수정 전·후 1회 비교다. 전체 1차→검색→
2차 파이프라인이나 실제 RisuAI의 최종 RP 출력을 검증하는 것은 아니다. 설치된 test.20의
실제 호출·최종 입력·출력 확인이 남아 있으며, 한 번의 성공으로 일반 품질을 보증하지 않는다.
오래된 자산과 현재 현금의 시점 혼재, 약속 상태와 그래프 연결은 기존 후속 계획 범위다.
