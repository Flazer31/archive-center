## 후속 구현과 새 DB 연결 로그

[test.17 요청 준비 최적화](archive-center-request-preparation-20260914.md)가 후속 구현이다.
아래 1~4절의 코드 설명과 `Go +0/-0`는 변경 전 조사 시점의 기록이다. 현재 보완 검색은
초기 요청의 준비 결과를 재사용한다. 내부 계산 개선을 실제 50분 문제의 해결로 취급하지 않는다.

50분 제보자가 추가로 제공한 로그:

```text
[mysql] 2026/09/14 05:09:58 connection.go:801 closing bad idle connection: connection reset by peer
[mysql] 2026/09/14 05:09:58 packets.go:155 write tcp 127.0.0.1:58502->127.0.0.1:3307: write: broken pipe
```

확인된 내용은 유휴 연결의 재사용 검사에서 단절을 발견한 것과 로컬 MariaDB(3307)로
보내던 쓰기가 실패한 것이다. 두 줄의 시각만으로 같은 연결·쿼리인지, 오류 전후 어느 구간에서
얼마나 기다렸는지는 알 수 없다. 긴 AI 대기 후 유휴 연결 단절을 발견했을 가능성과 DB 지연이
준비를 늘렸을 가능성을 모두 구분한다.

정식 `v4.3.1` 태그와 현재 소스 모두 드라이버 v1.10.0을 사용한다.
양쪽의 `internal/store/mariadb.go:OpenMariaDB`는 최대 open 10 / idle 5개만 설정하고
연결 최대 수명·유휴 수명을 설정하지 않는다. 관리 실행기의 기본 DSN에는 `parseTime=true`만
있고 연결·읽기·쓰기 timeout은 명시되지 않는다. 사용자가 별도로 설정한 DSN과 서버 설정은
미확인이다. 드라이버 v1.10.0의 `ResetSession`은 해당 첫 로그와 함께 `driver.ErrBadConn`을
반환한다. Go `database/sql.retry`는 최대 두 번 시도 후 새 연결을 강제 사용하며, 이 경로
자체에는 수십 분 sleep 또는 무한 재시도 루프가 없다. 새 연결/쿼리의 대기 시간은 별개다.
[드라이버 공식 설정 문서](https://github.com/go-sql-driver/mysql#important-settings)도
서버가 닫기 전에 연결을 교체하도록 수명 설정을 권장한다.

따라서 **DB 연결 단절은 확인, 50분 지연의 원인 여부는 미확정**이다. 이미 남은 로그의
05:09:58 전후 시각, 해당 prepare 요청 시작/종료와 단계 기록, MariaDB 오류·재시작 기록을
대조하는 것이 다음 확인이다. 요청 ID·DB 쿼리 시간을 확인하지 않고 사용자에게 새 유료 턴을
요구하거나 특정 DB 설정을 원인으로 단정하지 않는다. 이번 조립 작업에서 DB 정책은 변경하지 않았다.

## 3. 소스에서 확인한 위치와 버전 차이

### 후보 조립

정식 `v4.3.1:go-service/internal/httpapi/group_turn_prepare.go`는 각 보완 검색 후
`searchAssemblyMu` 안에서 **전체 `buildPrepareTurnInjectionAssemblyWithBudget`**을 실행하고
그 결과에서 후보만 꺼낸다. 검색은 겹치지만 조립은 요청 안에서 직렬이다. 전역 mutex는 아니다.

현재 활성 4.4는 아래를 개선했다.

- `group_turn_prepare.go:1052`, `prepare_turn_assembly.go:92`: 공통 공개 자료와 회수용 어휘를
  요청 안에서 한 번 준비해 재사용한다. 전역 장기 캐시를 추가한 것이 아니다.
- `prepare_turn_assembly.go:142`: 보완 검색은 `buildPrepareTurnSupplementCandidates`에서
  `buildPrepareTurnAssembly(input, false)`를 호출해 불필요한 최종 전달 조립을 생략한다.
- 그러나 `group_turn_prepare.go:1080`의 조립 mutex는 유지되고, 같은 기본 자료를 사용한
  질문별 후보 구성은 반복된다. 후보 전용 함수도 lane 선정·상태/관계 구성 등 공통 조립 본체를
  지나며 `prepare_turn_assembly.go:1158`에서 최종 전달 전 반환한다.

이번 113턴은 이전 최적화 후에도 15~19초 후보 조립이 네 번 이어진다는 실사용 증거다.
mutex만 없애면 자동으로 15~19초가 된다고 단정하지 않는다. 공유 입력과 CPU/할당 비용을
확인해야 한다. 질문과 무관하게 반복하는 후보 준비 작업의 비용을 먼저 측정하고 재사용 범위를
검토하되, 검색 질문·후보·점수·공개 범위·최종 내용은 보존한다. 정확히 어느 하위 함수가
각 15~19초를 소비하는지는 아직 CPU/할당 프로파일 없이 확정할 수 없다.

### 시간 표시의 범위

- `turn_timing.go:14` / `group_turn_prepare.go:254`: backend 타이머는 handler 호출마다 새로 시작.
- `turn_workflow_hud.go:375`, `:643`: 같은 request ID의 begin은 기존 기록을 반환하고 이미
  시작한 단계의 시각을 다시 설정하지 않는다.
- 같은 파일 `:1255`, `:1311`: 담당별 같은 round와 보완 검색 표는 새 값으로 교체한다.
- `Archive Center.js:14731`: backend_timing이 이미 있는 HUD에는 새 값을 덮어쓰지 않는다.
- 정상적으로 인식된 retry는 `Archive Center.js:34078` 이후 준비된 payload를 재사용하며,
  이 경로는 `v4.3.1`에도 있다. 정상 retry가 항상 prepare 재호출을 만든다는 주장은 틀리다.

[격리 HUD 결과](../../_diagnostics/20260914-long-prepare-report/results.json): 실제 ledger에 합성
30분 경과 시각을 넣고 같은 ID로 begin/start/record/finish를 반복하면 단계에는 30분,
담당 표에는 마지막 10초, 검색에는 마지막 50초만 남았다. 새 ID 대조는 새 시작 시각을 사용했다.
이는 **서로 다른 측정 범위가 표시될 가능 조건**이며, 해당 사용자에게 prepare 재진입이
있었다는 증거가 아니다. HUD는 UTC timestamp 차이, backend는 `time.Since`를 사용하므로
시스템 시각 변동 등의 영향도 원본 시각 없이 배제하지 않는다. 요청/턴 판정은 변경하지 않는다.

## 4. 남은 확인과 범위

50분 제보는 이미 끝난 요청의 추가 검색을 펼친 두 질문별 breakdown, 전처리 최근 결과,
Effective Input 및 request ID/시각을 가진 기존 요청 로그로 먼저 추적한다. 새 유료 턴을
기본 요구하지 않는다. test.16의 CPU/할당 위치는 같은 후보를 사용하는 격리 프로파일로 확인할 수 있다.
RAM 증가·GC·swap·CPU 포화는 지연을 증폭할 수 있으나 이번 화면은 누수 확정 증거가 아니다.
기존 진단 보고서에 CPU/heap 프로파일과 모든 물리 요청 이력이 자동 포함된다고 가정하지 않는다.

실행 코드·설정·프롬프트·DB·서비스·패키지는 변경하지 않았다. JS +0/-0, Go +0/-0.
문서와 격리 관측 검사만 추가했으며 업로드하지 않았다. 해결 상태나 배포 완료로 표시하지 않는다.
