## 4.3.1 기억 동작 기준선 — 2026-09-10 확정

사용자 결정에 따라 **현재 4.3.1을 이후 기억 작업의 고정 비교 기준**으로 삼는다.
구현 식별은 [4.3.1-test.4 소스·패키지 기록](archive-center-4.3.1-test-build-4.md)을 따른다.
공개 배포·설치·업데이트의 기준은 아직 `v4.3.0`이다. 이번 결정은 기억 개발의 기준 확정이며,
4.3.1 정식 공개·새 빌드·전체 실사용 검증 완료를 뜻하지 않는다.

목표는 저장된 기억 중 현재 장면에 필요한 핵심과 주변 세부사항을 충분히 전달하는 것이다.
덜 중요한 기억이 매번 주입되지 않아도 원본은 남으며, 관련 단서가 생기면 다시 후보가 될 수 있어야 한다.
이 방향을 유지하고 후속 버전에서 간접 단서·관계 회수를 넓힌다. 기본 기억의 누락을 사람다운
망각으로 취급하지 않으며, 계획된 선택형 인물 기억 표현은 기본 회수와 별도로 다룬다.

### 유지할 동작

| 구간 | 4.3.1에서 이어갈 기준 |
|---|---|
| 검색·합치기 | 현재 입력과 최근 대화의 검색 근거를 각각 보존한다. 같은 출처의 중복을 합친 뒤 검색당 개수 제한으로 다시 자르지 않는다. |
| 후보·전달 폭 | 유효한 출처·공개 범위의 검색 결과에서 표시용 요약 선정 전에 사실 후보를 만든다. 분류별 핵심 우선 수를 확보하고 남은 문자 예산에 관련 세부사항을 담는다. 후보 확보량과 최종 전달량을 구분한다. |
| 단서·순위 | 현재 입력과 최근 맥락의 일치 근거, 한국어 조사 형태를 살린다. 의미 관련성·중요도·최근성을 구분하며, 오래됐다는 이유만으로 중요한 기억의 의미까지 잃지 않게 한다. |
| 저장 중요도 | 자유문 정리 힌트나 메타데이터 일치만으로 요약 행 전체의 중요도를 낮추지 않는다. 개별 사건의 종료와 같은 요약에 든 습관·약속을 구분한다. |
| 출처·관점 | 공개 사건·직접 근거와 일반 주관 기억을 각 선정 경로로 전달하고 보유자·출처·시점을 유지한다. 비밀의 공개 범위와 세션·분기 범위를 지킨다. |
| 선택형 AI | 전처리·출판사를 모두 꺼도 개선된 Go 기본 기억이 작동한다. 편집자는 같은 공통 회수 개선을 사용하며 정상 추천의 원문·순서를 유지한다. 추천이 없는 분류는 Go 선정, 보완 호출 실패는 1차 결과 유지라는 기존 동작을 이어간다. |
| 조립 비용 | 단어 확장 결과의 최초 등장 순서·의미를 유지하면서 중복 확인 비용을 줄인다. 성능 개선을 위해 후보 폭을 줄인 결과를 같은 동작으로 취급하지 않는다. |

고정하는 것은 위 동작과 검증 사례다. 특정 파일 배치, 검색 후보 계산의 `512`·`4` 계수,
모델의 창작 문장까지 영구 고정하는 것은 아니다. 후속 개선은 같은 자료에서 필요한 사실의
회수·전달, 혼동·반복, 비용을 함께 비교한다. 새로운 런타임 거부 조건·자동 호출을 추가하는 결정도 아니다.

### 비교 자료와 남은 과제

- 1.0·3.9.9·4.1·4.2·4.3은 장점과 퇴행의 역사적 비교 자료로 보존한다. 이후 버전은
  **4.3.1과 직전 검증 버전 모두**에 비교한다. 이전 버전 전체로 회귀하는 것을 기본 해결책으로 삼지 않는다.
- [구버전 공통 재검사](archive-center-4.3.1-memory-revalidation.md), 아래 세 회수 회귀 파일,
  test.4의 단어 순서·긴 질의 조립 검사를 인계한다. 기본 기억만/출판사만/편집자만/둘 다를
  같은 저장 자료·입력·예산으로 비교하고, 추천 없음·일부 실패·보완 실패를 함께 확인한다.
- 사용자 후속 제출 자료에서는 여러 턴 진행 뒤 다섯 담당의 1·2차 호출 성공과 선택 원문의
  백엔드 최종 조립 반영, 오래된 기록의 전달을 확인했다. 이는 해당 사례의 관측이다.
  `effective_user_text_not_observed`가 있는 자료로 최종 제공자 요청 전체의 반영이나 모든 사용자 회상률을 확정하지 않는다.
- 현재값·과거값의 다른 필드 간 혼재, 완료·부분 완료와 남은 목표의 구분, 담당별 입력 차이와
  계획을 완료로 해석하는 문제는 남은 개선 대상이다. 이를 보존할 정답으로 고정하지 않는다.
- 별도 공개 근거가 없는 오래된 혼합 요약, 이미 잘못 낮아진 저장 중요도, 조회 범위 밖 자료는
  이번 수정으로 자동 복구되지 않았다. 넓은 후보 회수와 상태·해석의 정확성을 구분해 평가한다.

4.4는 이 기준을 보존하는 리팩터링과 별도 의미 통합, 4.5는 맥락 묶음, 4.6은 항목별
시점·상태·이행, 4.7은 단서·검색·예산, 4.8~4.9는 근거 관계와 실제 회수를 맡는다.
이후 버전의 작업 순서는 [통합 로드맵](../../_archive/future-reference/4.1-9.0-integrated-roadmap.md#memory-baseline-431)을 유지한다.

## 목표와 확인된 범위

저장된 유효한 기억이 검색·합치기·후보 구성 과정에서 일찍 사라지는 문제를 다섯 항목의
한 묶음으로 수정한다. 관련 기억을 충분히 비교한 뒤 기존 중요도·시간·문자 예산으로
전달하며, 전처리를 사용하지 않는 기본 Go 기억 주입도 같은 개선을 받는다.

[버전 비교 재검증](../../_diagnostics/20260910-memory-version-audit/revalidation.md)에서
3.9.9·4.1·4.2·4.3과 활성 소스를 비교했다. 현재 입력에서 찾은 기억이 최근 대화 검색과
경쟁해 앞단 한도에서 빠지는 현상은 4.2 이후 조건에서 재현됐다. 최종 사실 후보 구성 전에
빠지므로 4.3의 최종 점수와 전달 폭 개선만으로는 회복되지 않았다.
어휘 구제와 요약 전체 감점은 이전 버전에도 존재했다. 공개 사건·직접 근거의 분리 전달은
4.1 이후 실제로 개선된 경로이며 보존한다.

검사는 통제된 외부 검색 결과와 Go 요청 처리로 수행됐다. 특정 사용자 DB의 원인,
실제 임베딩의 검색 성능, RisuAI에 적용된 최종 요청과 본문 회상 성공은 아직 별도 확인 대상이다.
1.0은 남은 참고 소스 비교이며 동일 환경의 실행 성능 비교로 취급하지 않는다.

## Top K를 대신하는 Go 후보 조회량

본문 기억의 사용자 Top K 입력을 제거하고 Go가 기억 문자 예산으로 각 검색의 후보 수를 정한다.
`prepareTurnMemoryCandidateLimit`의 시험 정책은 `4 × ceil(문자 예산 / 512)`다.
512자는 계산 단위이고 4는 비교 여유분이다. 실제 요약 평균 길이나 검증된 최적 배수라는 뜻이 아니다.
2,048자/9,000자/18,000자 예산에서 각각 16/72/144개를 각 질문·상속 범위 검색에서 요청한다.
실제 반환 수는 저장 자료 수 등에 따라 적다. 같은 출처를 합친 뒤 이 수로 다시 자르지 않는다.

| 제어 항목 | 현재 역할 | 확인할 문제 |
|---|---|---|
| Go 검색 후보 수 | 문자 예산으로 계산하는 비교 범위 | 요청 수·반환 수·후보 도달을 분리해 확인 |
| 합친 검색 결과 | 질문별 근거를 보존하고 같은 출처 ID를 중복 제거 | 검색별 K를 합친 결과에 재적용해 현재 입력의 기억을 버리는가 |
| 분류별 핵심 기억 우선 수 | 최종 선정에서 분류별 핵심을 먼저 확보 | 이를 최종 전달 최대 개수로 오해하는가 |
| 기억 문자 예산 | 실제 전달 분량 제어 | 후보 확보량과 혼용되어 너무 일찍 잘리는가 |

- 기존 `topK` 저장값과 `top_k` API 필드는 보존한다. 본문 일반 기억 조회에는 사용하지 않는다.
  별도 참조 검색과 직접 조회의 기존 설정은 유지한다. 분류별 핵심 우선 수도 유지한다.
- 검색 후보 수와 최종 주입 개수를 같은 숫자로 묶지 않는다. 더 넓게 조회해도 모두 주입하지는 않는다.
- 예를 들어 두 검색에서 각각 5개를 얻었다면 합친 결과를 다시 5개로 자르지 않는다.
  하지만 필요한 기억이 각 검색의 6번째 밖에 있다면 이 수정만으로 해결되지 않는다.
- 현재 시험 정책은 아래 고정 순위 자료에서 후보 확보와 최종 예산을 검증했다.
  실제 Chroma 검색 지연·정답 순위 분포로 최적화한 정책은 아니다. 조회 수가 늘어 조립 비용이
  증가할 수 있다. 자동 반복 검색과 추가 AI 호출은 도입하지 않았다.
- `topK`를 공유하는 직접 근거 등 다른 호출자도 확인한다. 일반 기억 수정을 이유로
  다른 검색의 설정 의미를 조용히 바꾸지 않는다. 의미가 바뀌면 UI 이름·설명도 함께 맞춘다.
- 조회 범위 밖의 기억을 모두 찾는다는 보장은 없다. 시험 정책의 범위와 한계를 함께 기록하며,
  장기 세션의 실제 분포를 확인하기 전 완전한 회수나 최적 조회량으로 확정하지 않는다.

## 2026-09-10 구현과 검증 기록

- `group_turn_prepare.go`: 일반 기억 초기/보완 검색의 예산 기반 조회량, 보완 질문의 어휘 맥락 전달.
  `prepare_turn_recall.go`: 검색별 근거 합치기, 합친 K 재절단 제거, 한국어 조사 형태와 원래 입력의 독립 비교.
  관측은 `vector_shadow.candidate_policy`, `candidate_budget_chars`, `candidate_limit` 및 검색 항목의
  `recall_queries`에 남는다. 마지막 값은 사실 후보의 `score_lineage.recall_queries`까지 전달된다.
- `prepare_turn_assembly.go` / `prepare_turn_priority_memory.go`: 기존 출처·공개·인물 범위를 통과한
  후보에서 표시 요약 렌더링 전에 사실을 만든다. 똑같은 대표 요약을 가진 서로 다른 세부 사실도 유지한다.
  요약의 벡터 점수를 관련 없는 하위 사실에 일괄 복제하지 않는다.
- `memory_search_text.go`: 혼합 기억에 공개 직접 근거가 있으면 그 근거로 공개 검색문을 구성한다.
  새 저장/재색인과 기존 자료의 Go 공개 투영이 공유한다. 운영 Chroma의 오래된 벡터를 자동 재색인하지 않았다.
- `turn_extraction_persist.go`: 자유문 `prune_targets`는 정리 힌트/audit로 보존한다. 메타데이터 포함 JSON 검색과
  요약 행 전체의 중요도 감소·`stale_demote` 기록은 제거했다. 기존 상태/개별 사실 처리와 저장 확정은 유지한다.
- `Archive Center.js`: Top K 입력/저장 DOM 참조/본문 요청 필드 제거, 진단 이름을 검색 후보 수로 변경.
  본문 후보 계산은 Go 소유다. JS 변경 **+1/-9**, 사용자 프롬프트·키·기억 데이터 변경 없음.

검증 파일:

- `memory_recall_restoration_test.go`: 이전 소스에서 실패한 검색 경쟁·요약 전체 오감점 자료,
  조사 차이, 공개/혼합 기억의 저장→검색→주입과 비공개 범위.
- `memory_recall_restoration_matrix_test.go`: 전처리 끔/정상/추천 없음/일부 역할 실패/보완 실패 ×
  출판사 끔/켬 **10조합**. 외부 검색·LLM만 고정 응답으로 바꾸고 실제 `/prepare-turn`을 호출한다.
  기존 K=1보다 뒤인 40번째 기록이 AI 후보·최종 기억·주입문·payload plan에 도달한다.
  출판사의 실제 로컬 HTTP 호출과 가이드 적용, 보완 실패 후 1차 결과 보존도 검사했다.
- `memory_recall_restoration_coverage_test.go`: 초기 입력/최근 검색의 중복 근거와 중간 임베딩 실패 시
  질문 식별 유지, 표시용 동일 요약에 가려진 서로 다른 사실, 조회량·문자 예산 비교.

고정 순위 비교는 기억 180개, 요약 약 120/700자, 목표 순위 10/40/80/160, 예산 2,048/9,000/18,000자의
24가지 자료에서 기존 검색 5개와 새 조회량을 비교했다. 후보를 5개만 받으면 24개 모두 목표가 범위 밖이었다.
새 정책에서는 범위 안 12개가 후보와 최종 기억에 도달하고, 범위 밖 12개는 그대로 누락으로 관측됐다.
모든 최종 기억은 문자 예산 안에 있었다. **이 숫자는 검색 모델 정확도나 실사용 성공률이 아니다.**
독립적인 단서가 없는 검색 순위 밖의 자료까지 자동 회복되었다고 해석하지 않는다.

원본 검사 로그는 `_diagnostics/20260910-memory-recall-restoration`에 보존한다.
전체 검사 및 패키지 식별은 [test.2 기록](archive-center-4.3.1-test-build-2.md)에 연결한다.
실제 사용자 DB·Chroma·제공자·RisuAI 로드/최종 출력은 이 오프라인 시험의 증명이 아니다.
이미 오감점된 중요도와 공개 사실을 별도 추출하지 않은 과거 혼합 요약은 추정 복구하지 않았다.

## 승인된 다섯 작업

### 1. 검색 결과 합치기와 검색 근거 보존

현재 입력과 최근 완료 대화의 검색 결과를 질문별로 구분한다. 같은 기억의 중복은 합치되
어떤 질문에서 어떤 관련성으로 검색됐는지 남긴다. 합친 일반 기억 후보에 같은 K를
재적용하는 절단을 제거한다. 서로 다른 질문의 점수 중 최댓값만으로 현재 입력의 근거가
사라지지 않도록 최종 선정까지 전달한다. 위의 검색당 후보 확보량 검사도 이 항목에 포함한다.

주요 소유자: [prepare_turn_recall.go](../go-service/internal/httpapi/prepare_turn_recall.go)의
`prepareTurnRetrievalQueries`, `searchAcrossSessions`, `selectPrepareTurnMemoryLanesWithVector`.
Chroma의 세션 범위 및 일반 기억 전용 검색은 보존한다.

### 2. 최종 사실 후보를 만드는 순서 수정

이미 조회했고 기존 공개 범위·출처 규칙에 따라 사용할 수 있는 기억에서 사실 후보를 만든다.
앞단에서 표시용 요약으로 선정됐는지를 사실 후보 생성의 전제로 삼는 순서를 바꾼다.
그 뒤 관련성·중요도·시간·분류별 핵심 우선 수·문자 예산을 적용한다.

주요 소유자: [prepare_turn_assembly.go](../go-service/internal/httpapi/prepare_turn_assembly.go)의
`buildPrepareTurnInjectionAssemblyWithBudget`와
[prepare_turn_priority_memory.go](../go-service/internal/httpapi/prepare_turn_priority_memory.go)의
`appendPrepareTurnPriorityMemoryFactSeeds` 및 최종 선정 경로.
후보 확보와 최종 전달은 별도 관측으로 남긴다.

### 3. 현재 입력의 키워드로 다시 찾는 경로 보완

`스트레칭`과 `스트레칭을` 같은 조사 차이를 처리하고, 원래 입력과 최근 대화의 일치 근거를
구분한다. 짧은 입력에 최근 사건 요약을 붙인 결과로 원래 단서가 약해지는 경로를 고친다.
명확한 단서로 찾은 기억은 후보로 비교하며 무조건 최상위에 고정하지 않는다.

주요 소유자: `prepare_turn_recall.go`의 `prepareTurnMemoryRecallEvidence`와
[memory_search_text.go](../go-service/internal/httpapi/memory_search_text.go)의 검색 텍스트 구성.
특정 RP·모델·제보 문장만 처리하는 분기 대신 기존 어휘 처리 경로를 수정한다.

### 4. 정리 힌트에 따른 요약 전체 중요도 오감점 수정

`prune_targets`를 포함한 JSON 전체 문자열을 정리 대상과 비교하는 동작을 제거한다.
새 기억에 정리 힌트가 들어 있다는 이유로 그 새 기억까지 감점하지 않도록 한다.
사건 하나의 완료를 같은 요약에 있는 습관·약속 전체의 중요도 하락으로 적용하지 않는다.
대상이 특정되지 않은 힌트는 기록으로 남기며 저장 중요도 전체를 덮어쓰는 근거로 사용하지 않는다.

주요 소유자: [turn_extraction_persist.go](../go-service/internal/httpapi/turn_extraction_persist.go)의
`applyCriticSoftPrune`와 실제 저장 호출자. 기존 개별 사실·상태 처리를 먼저 확인한다.
이미 감점된 운영 데이터의 원래 값을 추측해 일괄 복원하지 않는다. 과거 데이터 복구는
근거와 범위를 별도로 확인할 문제다.

### 5. 공개 기억과 전처리 후보의 기준 통일

공개 사건·습관·직접 근거가 검색과 최종 주입에 도달하도록 공통 후보 경로를 연결한다.
`memory_search_text.go`의 `buildPublicMemoryProjection`과 저장된 공개 근거를 함께 확인한다.
혼합 요약의 대표문이 없어도 공개 직접 근거로 전달되면 성공으로 센다.
자유문에만 남은 공개 사실과 별도로 추출된 공개 사실을 구분하며, 비공개 내용을 함께
노출하는 방식으로 누락을 해결하지 않는다. 필요한 공개 사실 자체가 추출되지 않은 옛 자료는
조회 수 수정으로 복원된다고 주장하지 않는다.

전처리 1차와 보완 검색도 개선된 공통 후보를 사용한다. 정상 AI 추천 내용과 순서는 유지한다.
추천이 없는 분류와 호출 실패 분류에는 개선된 Go 기본 선정을 사용한다. 보완 호출 실패 시
1차 추천을 유지하는 기존 동작도 보존한다. 이 수정에 추가 유료 AI 호출을 요구하지 않는다.

## 진행 순서와 검증 기준

1. 현재 설정과 요청·검색·후보·주입 결과를 고정하고 기존 결함이 드러나는 회귀 자료를 확보한다.
2. 1·2번으로 후보 유실을 함께 수정하고, 검색당 후보 확보량이 충분한지 비교한다.
3. 3·4번의 어휘 회수와 중요도 오감점을 수정한다.
4. 5번으로 공개 기억·전처리 1차·보완 검색을 연결한다.
5. 아래 공통 검사를 통과한 하나의 변경 묶음으로 검토한다. 작은 수정마다 별도 배포하지 않는다.

| 검사 | 통과 기준 |
|---|---|
| 검색당 후보 수 | 관련 기억이 K 밖에 있는 자료에서도 조회량 변화의 효과와 잔여 누락 위치를 확인한다. 합친 결과만 넓힌 것으로 완료 처리하지 않는다. |
| 검색 합치기 | 최근 검색 점수가 더 높아도 현재 질문의 검색 근거가 유지되고, 중복 기억은 출처별 한 후보로 합쳐진다. |
| 후보 → 전달 | 공간이 충분한 자료에서 목표 세부 사실이 후보 및 최종 주입에 도달한다. 표시용 요약 개수만으로 먼저 제외되지 않는다. |
| 어휘 회수 | 조사 유무·짧은 입력·최근 맥락 추가·벡터 결과 부재 대조군에서 원래 단서의 회수 경로를 확인한다. |
| 중요도 정리 | 메타데이터에만 목표 단어가 있는 새 행, 습관과 종료 사건이 섞인 행, 무관한 행의 저장 중요도를 잘못 낮추지 않는다. |
| 공개/주관 기억 | 공개 요약·공개 사건·직접 근거·혼합 자료를 구분하고, 공개 사실 도달과 비공개 범위 보존을 함께 확인한다. |
| 전처리 | 정상 추천·추천 없음·일부 실패·보완 실패를 같은 자료와 예산으로 비교한다. AI 추천 순서와 기존 실패 시 동작을 보존한다. |
| 옵션 조합 | 전처리 끔/켬 × 출판사 끔/켬 네 조합에서 기본 기억 도달을 확인한다. |
| 기존 동작 | 세션·분기·리롤·출처 삭제 범위, 핵심 우선 선정과 문자 예산을 유지한다. |
| 전달 관측 | `memory_delivery_plan.final_text` → `injection_pack.injection_text` → `payload_application_plan`을 구분해 확인한다. |

기존 저장 자료와 기록된 AI 응답을 재사용하여 Go 회귀 검사를 먼저 수행한다. 최종 선정이나
본문 문체를 정답 문자열로 고정하는 대신 필요한 사실의 도달·출처·공개 범위와 예산을 검사한다.
실제 RisuAI 적용 및 제공자 요청·표시 출력 검사는 별도 단계다. 소스 검사 통과를 실사용
품질 보장으로 표시하지 않으며, 빌드·실행 검증 상태도 각각 기록한다.

## 후속 계획과 경계

이 묶음은 현재 확인된 기억 회수 결함의 수정이다. 노드 그래프·일반 연상 검색·시간 모델 등
미래 기능으로 넘겨야만 해결되는 문제로 묶지 않는다. 동시에 그 기능 전체를 이번 범위에 넣지 않는다.
[4.4 계획](archive-center-4.4-refactoring-plan.md)의 동작 보존 리팩터링과는 별도의 의도된 수정이다.
구현·검증된 후 그 결과를 4.4-A 기준 사례로 인계하고, 재현된 결함을 보존해야 할 동작으로 고정하지 않는다.
소스와 로컬 시험 패키지는 함께 갱신한다. 사용자 DB를 수정하거나 공개 GitHub에 배포하는 작업은 포함하지 않는다.
