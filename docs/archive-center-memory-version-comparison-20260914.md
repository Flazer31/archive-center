[추가 검사와 원본 결과](../../_diagnostics/20260914-direct-evidence-budget/README.md), 이후 승인받은 [test.16 배분 수정과 검증](archive-center-auto-memory-budget-20260914.md)을 구분해 참고한다.

**결론: 이번 공통 시험에서 test.15의 Go 기본 기억 전달은 4.3.1 수준을 유지했다. 4.2·4.3에서 재현되는 검색 결과 합산 단계의 누락은 재현되지 않았다. 추가 검색을 요청한 담당에게 다른 분류의 완료 근거가 빠지는 문제는 test.15에서 개선됐다. 다만 완료 상태의 저장까지 자동으로 해결된 것은 아니다.**

검사 중 런타임 소스, 검색 정책, 중요도, 저장 자료, 프롬프트는 수정하지 않았다. 런타임 JS **+0 / -0**. 구현 상태는 내부 검증 완료이며, 이번 test.15를 실제 로드한 사용자 세션의 검증은 별도다(`implemented_unverified`).

### 검색 합산·후보·전달 폭

현재 입력 단독, 더 강한 최근 맥락, 더 약한 최근 맥락, 검색 개수 증가, 조사 차이, 정밀 기억 보완의 일곱 조건을 같은 값으로 실행했다. 4.2·4.3은 강한 최근 검색이 경쟁할 때 옛 습관을 최종 주입에서 놓쳤다. 약한 최근 맥락·개수 증가·정밀 기억 보완을 대조 조건으로 함께 확인했으므로 ‘어느 버전이 항상 기억하지 못한다’는 시험이 아니다.

4.3은 세부사항의 전달 폭과 최종 의미 점수 반영을 이미 회복했지만, 앞선 검색 결과 합산에서 빠지는 자료에는 그 개선을 적용할 수 없었다. 4.3.1과 test.15는 이 공통 자료에서 검색된 기억을 최종 단계까지 전달했다. 이번 test.15의 변경으로 4.3.1의 기억 보존이 후퇴한 결과는 없었다.

### 중요도와 공개 범위

종료된 도적 사건과 일상 습관이 같은 요약에 있는 시험에서, 구형 경로는 `prune_targets`를 통해 요약 전체의 중요도를 낮췄다. 새 요약의 메타데이터까지 걸려 0.3→0.1로 낮아지는 결과도 재현됐다. 4.3.1과 test.15는 이 저장 중요도를 덮어쓰지 않았다.

반면 **공개 경험이 비공개 요약 내부에만 섞여 있고 별도 공개 사건·근거가 없는 경우**에는 모든 Go 비교 버전에서 일반 기억 전달로 나오지 않았다. 원본은 저장돼 있지만 공개 부분만 분리할 근거가 부족한 경로다. 공개 사건/인용 근거가 명시된 경우에는 4.0 이후 개선된 결과를 보였다. 이 시험에서 비공개 내용의 일반 전달 누출은 없었다.

## 3. 1.0에서 확인한 장점과 한계

1.0은 다른 구조이므로 위 HTTP 표와 같은 수치로 합치지 않았다. 원본 소스의 함수를 AST로 불러오되 점수·필터·요약 해석·문자 자르기 로직은 바꾸지 않았다. 저장소 질의와 Chroma 후보 ID, 임베딩 벡터, 시계만 시험 경계로 교체했다.

- 검색 후보에 포함된 오래된 습관은 최근 기억들과 경쟁해도 전달됐다. 후보에서 빠지면 전달되지 않았고, 후보 범위를 늘리거나 Chroma 후보 없음에 따른 기존 SQL 경로를 사용할 때 다시 전달됐다.
- 중요도 10인 오래된 기억과 최신 기억은 모두 정규화 중요도 1을 유지했다. 시간은 별도 최신성 점수에 영향을 줬다. 현재 기본값은 의미 유사도 0.60 / 중요도 0.25 / 최신성 0.15, 시간 반감기 168시간, 최신성 하한 0.20이다. 이는 잔존 수정본의 기본값이다.
- 실제 조립 함수는 요약 하나를 200자로, Storyteller 포맷은 220자로 잘랐다. 긴 요약 뒤에 있는 ‘겨울에 보증 만료’ 조건은 검색 성공 후에도 전달되지 않았다.
- 조사 차이 세 경우는 **이미 Chroma 후보로 주어진 기억의 점수·전달**을 실행한 것이다. 이것을 Go 표의 ‘벡터 없는 키워드 자체 검색 성공’과 같은 검증으로 취급하지 않는다.

따라서 1.0의 중요도 유지와 단순한 전달 경로는 장점이지만, 기억 누락이 없는 버전은 아니었다.

### 비용 관찰

작은 동일 시험 자료의 시스템 프롬프트+사용자 패킷을 물리 요청별로 합산한 **문자 수**다. 실제 제공자의 토큰 수·과금·추론 시간은 측정하지 않았다.

| 구성 | 4.3 | 4.3.1 | test.15 |
|---|---:|---:|---:|
| 두 담당을 다른 모델로 개별 호출 | 44,586자 | 44,586자 | 54,787자 |
| 두 담당의 연결·모델 설정 동일 | 44,586자 | 44,586자 | 37,371자 |

현재 버전이 **항상 입력량이 적다는 결론은 아니다.** 이 자료에서는 개별 호출이 구형보다 약 23% 많았고, 묶음 호출은 구형보다 약 16% 적었다. 프롬프트 변경과 근거 복원을 모두 포함한 버전 간 차이이며, 차이 전체를 test.15의 한 변경 탓으로 돌리지 않는다. 전체 검사 실행 시간에는 컴파일·시험 준비가 포함되므로 서비스의 준비 시간 비교값으로 사용하지 않는다.

## 5. 완료된 약속이 다시 미완료처럼 보이는 문제의 남은 범위

생산 `saveCharacterAndStateArtifacts`를 같은 입력으로 실행한 결과:

1. **요약문에만 ‘약속을 이행했다’가 있으면:** 모든 Go 비교 버전에서 pending 완료 저장 요청이 발생하지 않았다.
2. **같은 `lifecycle_key`의 `resolved_threads`가 있으면:** 4.2 이후는 해당 약속을 47턴 완료 상태로 쓰고, 무관한 약속은 그대로 뒀다. 3.9.9–4.1은 이 구조화된 종료 입력을 처리하지 않았다. 이는 해당 계약의 도입 전후 차이이며 과거 버전의 모든 관리·상태 변경 기능이 없다는 뜻은 아니다.
3. **완료 후 단순 회상:** 새 pending 저장 요청이 발생하지 않았다.
4. **별개의 새 약속:** 기존 완료 약속과 구분해서 저장했다.

이것은 저장 함수가 올바른 쓰기를 요청하는지에 대한 내부 검증이다. 실제 사용자 DB의 41·46·47턴 평론가 추출값은 없으므로 첫 완료 추출이 누락됐는지, 이후 다른 추출이 다시 open 항목을 만들었는지까지 확정하지 않는다. 이번 수정은 DB의 과거 pending 상태를 소급 수정하지 않는다.

**남은 실패 가능성:** 완료 근거가 검색되지 않거나, 평론가가 종료 항목을 만들지 않거나, 전처리/본문 AI가 받은 근거를 잘못 해석하면 미완료 취급이 다시 나올 수 있다. 이 가능성을 막으려고 과거 약속·주관 기억·세부 기억을 일괄 제외하는 변경은 하지 않았다.

## 6. 현재 내부 회귀의 범위와 한계

- 전처리 꺼짐 / 정상 추천 / 추천 없음 / 일부 담당 실패 / 추가 검색 후 2차 실패와 출판사 켜짐·꺼짐의 10개 HTTP 조합에서 기존 습관이 최종 주입까지 도달했다.
- 180개 후보, 원문 약 120·700자, 문자 예산 2,048·9,000·18,000자, 검색 순위 10·40·80·160의 기존 회귀를 실행했다. 범위 안에 들어온 중요 기억은 전달했고 문자 예산도 지켰다. **검색 범위 밖의 기억까지 무조건 찾는 시험은 아니다.**
- 5개 담당의 추가 검색, 1차 선택 유지, 주관 기억 176개, 서로 다른 질문·동시 조립에서 원본 자료 보존을 검사했다. 현재 전체 Go 실행에는 삭제·리롤·HUD·보호 범위·출처 검사 등 기존 회귀도 포함된다.
- 같은 비밀 ID 없이 다른 표현으로 공개 사실을 기록한 경우에는 **옛 비밀 안내와 새 공개 사건이 함께 전달되는 한계가 남았다.** 과거 사건이 삭제된 것은 아니지만 최신 공개 범위 해석이 흔들릴 수 있다.
- 14개 건너뜀에는 실제 MariaDB/Chroma 통합, 설치/배포 환경, 구성된 실제 제공자, 별도 첨부 파일이 필요한 입력 패킹 검사가 포함된다. 새 내부 비교가 이 외부 검증까지 대신한 것은 아니다.
- 실제 100만/200만 토큰 세션의 회상률, 본문 AI의 말투·원작 지식·서사 판단, 실사용 시간/RAM, 실제 RisuAI 최종 표시 품질은 이번 시험으로 수치화하지 않았다.
