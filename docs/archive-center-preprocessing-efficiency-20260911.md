## 2026-09-12 — 승인된 두 범위의 구현 및 로컬 검증

사용자의 “문서에 따라서 작업, 다른 것은 건드리지 않기” 요청에 따라 다음 두 범위만 수정했다.
원문 추가 축소, 선행 담당/여섯 번째 요약 AI, 새로운 재시도·워처·큐, DB 스키마 변경,
기억 검색/순위/공개 범위 정책 변경, 출판사·평론가 병합은 적용하지 않았다.

### 1. 같은 설정의 전처리 담당 묶음

- `prepare_turn_multi_agent.go`의 기존 설정 적용과 결과 처리를 각각
  `multiAgentProxyRequest`, `finishMultiAgentCall`로 분리해 단일/묶음 경로가 함께 사용한다.
  `prepare_turn_multi_agent_group.go::callMultiAgentRound`는 한 prepare 요청의 같은 회차에서
  실제 연결·모델·온도·출력 한도·시간 한도·추론·서비스 옵션이 같은 담당을 묶는다.
  출판사 상속/담당 덮어쓰기를 적용한 결과와 기존 제공자 정규화를 기준으로 비교한다.
  서로 다른 API 키, endpoint, 추론/생성 설정은 같은 모델이어도 별도 요청이다.
- `memory_preprocessing.group.v1`의 `shared_input`에는 직렬화 결과가 동일한 필드만 한 번
  둔다. 각 `roles[].input`과 합치면 원래 담당의 모델 입력을 그대로 복원할 수 있다.
  담당 프롬프트, F/S/L/C 참조, 후보 원문, 출처/시점/공개 범위, 기존 최근 대화 선택은 보존한다.
- 응답은 `roles` 객체의 담당별 추천으로 나누어 기존 파서/보정/최종 선정에 넘긴다.
  읽힌 담당 결과를 유지하며, 누락된 담당은 기존 실패 처리, 2차 실패는 기존 1차 결과 유지,
  정상 빈 최종 추천은 기존 Go 선정으로 처리한다. 추가 재호출이나 세 번째 회차는 없다.
- 2차 참여 여부와 보완 검색 수는 기존 판단을 사용한다. 1차가 모두 같은 설정이면 1회,
  2차 참여 담당도 같은 설정이면 그 회차에 1회 추가된다. 설정이 전부 다르면 기존 5회다.
- **한도 결정:** 묶음 출력 상한은 참여 담당의 기존 출력 한도 합계다. 담당별 값은 요청의
  작업별 출력 배분으로 표시되며, 제공자가 각 담당을 독립적으로 강제하는 한도는 아니다.
  추론과 timeout은 동일한 기존 설정을 요청당 한 번 적용한다. 합산 한도를 모델이 지원하지
  않거나 시간 초과가 나면 기존 제공자 오류로 기록한다. 자동 한도 변경/개별 재호출은 없다.
- **공개 범위 결정:** 묶인 모델은 참여 담당의 자료를 같은 문맥에서 본다. 독립 모델의 문맥
  격리와 동일하다고 주장하지 않는다. Go의 원문별 소유자/공개 범위와 공개 참조 요청 규칙,
  최종 주입 권한 판정은 유지한다. 서로 다른 설정의 모델에 비공개 교차 요청을 추가하지 않는다.
- 진단의 `shared_request_id`, `shared_roles`가 같은 실제 요청의 담당들을 연결한다.
  실제 `model_input`, `system_prompt`, `request_raw_result`, provider `usage`는 묶음의 첫
  담당 기록에만 보관한다. 다른 담당의 canonical `input`, 해석 결과와 오류는 각각 남긴다.
  `analysis_calls`/`analysis_attempts`는 묶음을 한 번 집계한다. 역할 시간은 같은 요청의
  경과 시간이며 역할 간 합계로 전체 대기 시간을 계산하지 않는다. 사용량 없는 응답은 0으로
  만들지 않고 역할별 실제 토큰을 임의 배분하지 않는다. 기존 제공자 내부 재시도 정책은 그대로다.

## 2026-09-12 — 후속 방향: 담당은 유지하고 같은 설정의 호출을 묶기 (구현 전 계획 기록)

사용자는 토큰 절감 방법을 먼저 정리하라고 요청한 뒤, 같은 제공자·모델·호출 설정을 사용하는
담당을 한 요청에 묶는 방향을 선택했다. 원문 축소만 반복하는 접근의 한계를 인정하고,
**공통 자료의 반복 전송**을 우선 줄인다. 공통 장면을 새 AI로 요약하는 단계, 독립 압축기,
제공자 캐시나 세션 기억에 의존하는 방식을 이번 기본안에 추가하지 않는다.

### 현재 구현과 변경할 경계

현재 `prepare_turn_multi_agent.go::runMultiAgent`는 활성 담당마다 1차 호출을 만들고, 기존
보완 필요 판정에 따라 담당별 2차 호출을 만든다. `callMultiAgent`가 실제 연결/추론 옵션,
프롬프트, HTTP 요청, 파싱과 사용량을 담당한다. `multiAgentInput`의 후보는 분야별로 이미
구분되지만 현재 입력·최근 대화는 각 담당에 반복된다. `multiAgentModelInput`의 C 선택과
설명 재사용은 일부 2차 반복을 줄일 뿐, 첫 5개 요청의 공통 자료 반복을 없애지는 않는다.

후속 변경은 이 기존 Go 소유자 안에서 정리한다. JS에 모델 묶음 정책을 만들거나 전처리와
무관한 출판사/평론가 호출까지 합치지 않는다. 턴 인식 수정은
[별도 진단 범위](../../_diagnostics/20260912-turn-lifecycle-audit/turn-lifecycle-audit.md)로 유지한다.
두 작업의 검증 준비는 함께 하되, 한쪽 수정을 다른 쪽의 해결 증거로 삼지 않는다.

### 선택한 기본안

1. **역할 5개와 편집 가능한 프롬프트는 유지한다.** 하나의 준비 요청과 같은 분석 회차 안에서
   실제 호출에 적용되는 연결·모델·설정이
   같은 담당들의 작업을 한 요청에 넣는다. 출판사 상속과 담당별 덮어쓰기를 적용한 결과를
   기준으로 하며, 제공자/모델 표시 이름만 같다는 이유로 연결 계정이나 추론 설정을 바꾸지
   않는다. 설정이 다른 담당은 독립 요청을 유지한다. API 키나 비밀 설정을 묶음 식별 로그에
   기록하지 않는다. 역할 프롬프트가 다르다는 것은 정상이며 각 담당의 지시를 그대로 포함한다.
2. **같은 자료는 요청 안에서 한 번 전달한다.** 공통 지시·현재 입력·공통 최근 대화를 한 번
   두고, 분야별 지시·후보·예산·출처 참조를 연결한다. 동일한 텍스트라도 출처/턴/보유자/공개
   범위가 다르면 서로 다른 근거로 남는다. 각 역할의 원래 읽기 자료를 정확히 재구성할 수
   있게 하며, 절감을 위해 N·후보 범위·최종 전달 예산을 자동으로 낮추지 않는다.
3. **결과는 담당별로 받는다.** 묶음 응답 안에서 역할별 완전한 선정 목록·순서·설명·검색 질문을
   분리해 기존 처리로 돌려준다. 공통 결론 하나로 다섯 역할을 덮어쓰지 않는다. 정상 추천의
   순서, 추천 없음의 Go 선정, 성공한 빈 최종 선정, 실패한 2차의 1차 유지 등은 기존 소유자의
   동작을 보존한다. 일부 역할의 형식 문제 때문에 다른 역할의 읽을 수 있는 결과를 버리는
   새 조건을 만들지 않는다. 기존 항목별 보정/부분 활용을 재사용한다.
4. **2차는 기존에 필요한 담당만 묶는다.** 검색 횟수·보완 판정·최대 2차 정책은 그대로 둔다.
   참여 담당의 1차 결과, 필요한 기존 근거와 추가 근거를 그 요청에 넣는다. 1차가 끝났다고
   다음 API 요청이 그 문맥을 기억한다고 가정하지 않는다. 기존 C 구간 선택과 명시적 설명
   재사용은 담당별 의미를 유지한다. 첫 5개 담당이 모두 같은 설정이면 1차는 1회이고, 2차까지
   필요하면 해당 회차의 묶음 호출이 추가된다. 전체 턴이 무조건 1회라는 뜻은 아니다.
5. **사용량은 실제 요청마다 한 번 집계한다.** 역할별 결과와 실제 전송 요청을 구분하고,
   같은 묶음의 provider usage·경과 시간을 각 역할에 복사해 합산하지 않는다. 역할별 토큰을
   제공자가 주지 않으면 임의 배분한 값을 실제 사용량으로 표시하지 않는다. 실제 전송 시도와
   기존 제공자 재시도도 구분한다. usage 누락은 0이 아니며 문자 수와 과금 토큰은 별개다.

1차의 단순 예시는 동일 설정 5개면 1회, 3개/2개의 두 설정이면 2회, 모두 다르면 5회다.
묶인 모델은 여러 담당의 자료를 한 문맥에서 보므로 독립적인 5개 분석 호출과 같지 않다.
역할별 출처·공개 범위와 최종 주입 구분은 보존해야 하지만, 모델 문맥까지 격리된다고
설명해서는 안 된다. 역할 사이의 비공개 자료 노출 범위도 구현 전에 명시할 설계 항목이다.

### 구현 전에 남은 세부 결정

- **출력/추론 예산과 시간 한도:** 기존 역할별 한도를 한 요청의 한도로 그대로 쓰면 다섯
  결과를 담기 부족할 수 있다. 반대로 무조건 합산하면 제공자 지원 범위를 넘을 수 있다.
  단일 요청에서는 역할마다 독립적인 시간/생성 상한을 그대로 집행할 수 없으므로, 묶음의
  실제 한도와 기존 역할 설정의 의미를 함께 정해야 한다. 설정을 조용히 덮어쓰거나 지원
  범위를 추정해 자동 재호출하는 구현으로 넘기지 않는다. 구체적 계산 규칙은 아직 미정이다.
- **긴 설명의 출력 비용:** 묶음만으로 설명·추론 토큰이 자동 감소하지 않는다. 현재 짧은
  설명 지시와 2차 명시적 재사용의 실제 효과를 먼저 비교한다. 선정 ID나 근거를 줄여 출력
  비용을 맞추거나, 새 요약/검수 AI 호출을 추가하는 방안은 이번 결정에 포함되지 않았다.
- **실패 영향 범위:** 한 요청의 시간 초과가 묶인 담당 모두에 영향을 줄 수 있다. 읽힌 역할별

  정리한다. 묶음 실패 후 자동으로 다섯 호출을 다시 보내는 새 재시도 정책은 추가하지 않는다.
