기준일: 2026-09-11

최초 진단 뒤 사용자가 불필요한 항목의 생성을 수정하도록 승인했다. 아래 적용 기록을 우선한다.
사용자 DB·설정·실행 중인 백엔드·배포 파일은 변경하지 않았다.

계획 권위는 [통합 로드맵](../../_archive/future-reference/4.1-9.0-integrated-roadmap.md)이다.
이번 기록으로 4.4의 기존 작업 순서나 이후 버전 배정을 바꾸지 않는다. 상세 구현 버전은 미배정이다.
[4.3.1 기억 기준](archive-center-memory-recall-restoration-plan.md#memory-baseline-431)을 유지한다.

## 2026-09-11 적용 기록 — 수집 품질 수정

원문 RAG·질문 생성의 구현에 앞서, 사용자가 지적한 원작 자료 수집 경로를 수정했다.

- `runSourceCandidateExtraction`: 링크 글자를 자동으로 개체로 승격하던 구조적 후보 생성과
  관련 전용 함수들을 제거했다. 본문·목록·표는 기존 추출 AI가 문맥을 해석할 자료로 전달한다.
  추출 연결이 없으면 원문/section을 유지하고 추출 미완료로 표시하며 개체는 생성하지 않는다.
  `structural_roster_candidates` 진단 필드는 0으로 유지한다. 과거 항목의 수동 repair API는 유지한다.
- 검색 추출·문서 추출·자동 검토 프롬프트에서 링크 조각과 실제 이름, 웹페이지 광고·가입 안내·
  메뉴·독자 댓글·편집 메모와 작품 정보를 구분하도록 명시했다. 검색 추출은 기존
  `external_metadata` 분류 처리를 사용한다. 새 거부 조건이나 이름 차단 목록, 추가 검증 호출은 없다.
- 각주를 일괄 제외하던 지시를 수정했다. 설정 조건·예외가 있는 각주, 작품 속 공고·대사와
  실제 짧은 이름은 문맥에 따라 보존한다. 본문처럼 섞인 광고의 의미 판정에는 기존 추출 AI가 관여한다.
- `referenceDocumentExtractionText`: HTML에서 본문이 모두 제외된 경우 원문을 다시 넘기던
  재유입 경로를 제거했다. 그런 문서의 추출 작업은 생성 항목 0개로 완료되고 추출/자동 검토 AI를 호출하지 않는다.
  `discoveryHTMLSections`에서 문단 태그 없이 div/main/인라인 요소에 적힌 정상 본문도 기존
  광고·주석 영역 제외를 적용한 상태로 수집한다. 따라서 단순한 HTML의 유효 본문까지 잃지 않는다.
  일반 평문 입력, 비어 있지 않은 문서의 추출 오류 처리, 기존 원문 보관·승인·색인 계약은 유지한다.

검증은 생산 함수와 저장 호출을 기록하는 테스트 경계, 로컬 HTTP 제공자 응답으로 수행했다.
새 회귀 5개는 수정 전 소스 overlay에서 모두 실패하고 수정 후 통과했다. 기호·조사·광고 링크의
자동 개체화 제거, 정상 `L`·`렌`과 설정 각주 저장, 웹페이지 정보의 기존 분류 반영, 광고만 있는
HTML의 무호출 완료, 태그 없는 정상 본문 보존과 두 추출/검토 프롬프트 전달을 확인했다. 원작 관련 테스트 128개도 통과했다.
로컬 제공자의 분류 응답은 기록된 시험 응답이므로 실제 AI의 광고 판정 성공률을 입증하지 않는다.

증거: [수정 전 회귀](../../_diagnostics/20260911-reference-ingestion-fix/targeted-before-final.txt),
[원작 관련 전체 검사](../../_diagnostics/20260911-reference-ingestion-fix/reference-suite-final.jsonl).
[최종 전체 Go 검사](../../_diagnostics/20260911-reference-ingestion-fix/go-suite-final.jsonl)는
5,832건 통과, 13건 환경 의존 검사 제외, 실패 0건이다. 제외 항목은 실제 MariaDB/Chroma/제공자,
배포 업그레이드와 POSIX 실행 권한 등이며 해당 실환경의 성공을 의미하지 않는다.
활성 JS 변경 +0/-0. 기존 DB의 잘못된 항목을 일괄 삭제하지 않았다.
실행 중인 사용자의 백엔드 교체와 실제 웹 수집/모델 확인은 아직 진행하지 않았다.

## 1. 목적과 사용자 결정

사용자는 원문·웹사이트에서 자료를 가져와 개체와 사실로 재정리하는 과정의 품질을 문제로 지적했다.
원작 자료를 먼저 보존하고, 현재 장면에 필요한 질문을 만들어 해당 자료에서 근거를 찾아 읽는
방식을 검토하기로 했다. 사용자가 RP 입력을 원작 질문이나 OOC로 바꿀 필요가 없어야 한다.

- 원문을 일차 자료로 유지하고, 요약·정리 결과 때문에 원래 세부사항을 찾을 수 없게 되는 일을 줄인다.
- 현재 입력, 설정된 최근 대화 참고 범위, 세션 기억을 바탕으로 필요한 원작 질문을 내부에서 만든다.
- 검색 결과를 읽고 근거와 출처를 전달한다. 본문 전개와 사용자 캐릭터의 설정은 사용자가 결정한다.
- 광고 문구, 사이트 메뉴, 본문에 무관한 주석·댓글·편집 잔여물이 작품 항목으로 생성되는 문제를 다룬다.
- 원작 자료의 검색·질문 처리는 Go 소유다. JS에 별도의 자료 선정 정책을 만들지 않는다.

## 3. 원작견 v2.11에서 참고할 점

검토 대상은 로컬 [📕원작견 v2.11.js](<../../reference/external-examples/example/📕원작견 v2.11.js>)다.
소스 비교이며 실제 외부 검색 성공률이나 비용을 측정한 결과가 아니다.

`buildFirstPrompt`는 최근 대화와 작품 정보를 이용해 인물·말투 또는 장면에 필요한 설정을 조사하게 한다.
`loreqa_callLLM`의 도구 경로는 검색과 읽기를 나눈다. Ollama 경로의 `lore_search`로 페이지를 찾고,
`lore_fetch`로 특정 단어 주변이나 지정한 위치부터 읽는다. 읽기 결과에는 현재 범위·전체 길이·남은
내용이 있어 후속 질문이나 추가 읽기의 단서가 된다. 도구 결과를 받은 모델이 다음 도구를 결정한다.

AC에 참고할 핵심은 **질문 → 검색 → 해당 부분과 주변 문맥 읽기 → 근거 전달**이다.
처음부터 모든 자료를 하나의 요약으로 바꾸는 것보다 필요한 근거를 원문에서 확인하기에 적합한 구성이다.

그대로 이전할 설계는 아니다. 원작견에는 다음 차이가 있다.

- 선택한 모드에 따라 인물·설정 분석, 추가 검증, 여러 차례의 도구 호출이 이어진다. 항상 한두 번 호출하는 구조가 아니다.
- 기본 분석이 곧 외부 검색을 뜻하지 않는다. 웹 검색/MCP는 별도 설정이며, 일부 도구는 다른 모델의 답변을 이용한다.
- 도구 설명에 있는 “검증된 공식 DB”라는 문구는 자료의 공식성이나 실제 검색 수행을 보증하지 않는다.
- 다음 장면 예측, 상황별 대사 작성, 사용자 캐릭터를 조사에서 제외하는 지시는 AC 편집자의 기억 준비 역할과 다르다.
- 반복 호출 상한 30회와 추가 검증 흐름을 그대로 가져오면 현재의 준비 시간 문제를 키울 수 있다.

## 4. 제안 흐름 — PLANNED

### 원문 저장과 검색

MariaDB는 원문·작품/판본·출처·수집 시점·문서 위치의 기준 저장소로 둔다.
ChromaDB에는 원문 구간에 대응하는 파생 색인을 두는 방향을 검토한다. 구간에는 제목 경로와
필요한 인접 문맥을 연결하고, 표는 속성명·값·단위의 대응이 유지되도록 읽기 단위를 설계한다.
기존 승인 항목도 검색 단서로 활용하며 기존 자료를 일괄 삭제하거나 강제로 다시 요약하지 않는다.

검색용으로 정리한 본문과 보관 원문은 구분한다. 광고·메뉴가 검색 본문에서 빠져도 원래 위치를
확인할 수 있어야 한다. 이 구상은 기존 검색 개수·기억 문자 예산을 일괄 확대하거나 폐기하는 결정이 아니다.

### 자동 질문과 읽기

1. Go가 현재 입력, UI의 최근 대화 참고 설정에 따른 대화, 세션 기억과 원작 자료의 간단한 목록을 전달한다.
2. 편집자가 장면에 필요한 사실과 아직 확인할 근거를 질문으로 작성한다. 이미 알고 있는 중요한 조건도 확인 대상이다.
3. 현재 입력에서 얻은 검색 단서와 AI 질문의 단서를 함께 유지해 자료를 찾는다. 질문으로 원래 입력을 대체하지 않는다.
4. 검색된 원문 구간과 제목·표·주변 문장·관련 각주를 읽는다. 검색되지 않은 사실은 확인되지 않은 상태로 표현한다.
5. 근거 위치·원문 발췌와 그에 대한 해석을 구분해 기억 조립에 전달한다. 출판사가 켜져 있으면 같은 근거를 받는다.

질문 예시는 “나베랄이 이번에 어떤 반응을 해야 하는가?”보다는 “나베랄의 인간에 대한 태도와
아인즈의 지시에 따를 때의 조건은 무엇인가?”에 가깝다. 장면을 대신 정하는 대신 참고할 사실을 찾는다.
민우가 이번 세션에서 아인즈의 오랜 동료로 존중받는다는 설정은 세션 기록에서 읽는다.
원작 DB는 원작 인물의 기본 정보를 제공하며, 사용자 캐릭터의 지위나 이번 세션의 관계를 원작 설정으로 덮어쓰지 않는다.
이 예시는 시험 사례이며 특정 작품·인물 전용 런타임 규칙을 추가하는 뜻이 아니다.

처음에는 기존 1차 분석·보완 검색·2차 분석을 활용하는 범위를 검토한다. 원문을 더 읽어야 할 때
반복 탐색을 지원할지는 비용·도달률 비교 후 별도로 결정한다. 새 담당이나 검증 AI를 자동으로 추가하지 않는다.
AI 추천 원문과 순서, 추천이 없는 분류의 Go 선정, 보완 호출 실패 시 기존 1차 결과 유지 계약은 보존한다.
전처리를 사용하지 않는 기본 기억 경로도 유지하며, AI 자동 질문을 모든 사용자에게 필수 호출로 만들지 않는다.

## 5. 수정 전 기호·조사가 항목이 되는 경로 — REPRODUCED

재현 범위는 현행 Go의 HTML 파서 → 구조적 후보 → 중복 조정 → staging → 저장 함수 호출이다.
실제 DB 대신 호출을 기록하는 기존 저장소 테스트 경계를 사용했다. 외부 사이트와 유료 AI는 호출하지 않았다.

`sourceDiscoveryStructuralRosterCandidates`는 같은 묶음에 내부 문서 링크가 있는 목록 항목이
여러 개 있으면 각 링크의 표시 글자를 개체 이름 후보로 만든다. `structuralRosterName`은 링크
글자가 실제 개체 이름인지 해석하지 않는다. 따라서 문장 중간의 기호·조사 링크도 이 경로에 들어온다.

| 합성 HTML 사례 | 관찰한 결과 |
| --- | --- |
| 주변 문장이 있는 목록에서 `[`, `{`, `(`, `의`, `는`, `에`, `L`, `렌`을 각각 내부 링크로 표시 | 구조적 개체 후보 8개 생성. 중복 조정 뒤 `[`, `의`, `는`, `에`, `L`, `렌` 6개를 검토 대기 개체로 저장하도록 호출. |
| `{` 또는 `(`를 첫 기호로 두고 정상 이름 `L`과 함께 배치 | 각각 `{` 또는 `(`도 검토 대기 개체 저장 호출까지 도달. |
| 같은 글자를 링크 없이 평문으로 배치 | 해당 구조적 개체 후보 0개. |
| 기호만 있는 목록, 주변에 의미 있는 문장 없음 | 현행 section 정규화에서 제외되어 해당 section 0개. |

기호 3개가 처음 사례에서 1개로 합쳐지는 이유도 확인했다. `normalizeSourceCandidateValue`가
기호를 제거하므로 이들의 논리 식별 키가 같아진다. 이것은 기호가 원래 이름으로 오인되는 문제와
별개의 중복 처리 관찰이며, 모든 기호가 각각 동시에 저장된다는 주장은 하지 않는다.

staging은 `persistSourceDiscoveryCandidates(..., approve=false)`를 통해 개체를 `pending`으로 저장한다.
추출 AI를 사용하지 않은 재현에서도 발생했으므로 AI의 JSON 오류만으로 설명할 수 없다.
다만 **검토 대기 항목이 생성되는 것과 승인되어 Chroma 검색·최종 입력에 들어가는 것은 다르다.**
이번 재현의 승인 호출은 0회다. 사용자에게 보인 실제 항목의 출처는 아직 확인하지 않았다.
모델 추출 경로에서 비슷한 항목이 생겼는지도 이 재현으로 전부 확정할 수 없다.

실제 항목을 추적할 때는 `origin_kind`, `structural_provenance`, `job_id`, `evidence_set`과
그 원문을 비교한다. 기존 `repair-structural-roster/v1`는 수동 경로이며 정상 수집마다 자동 실행되지 않는다.
해당 provenance 전체를 처리하므로 이번 진단에서 사용자 DB에 실행하지 않았다.

수정 방향은 링크 글자를 개체로 바로 바꾸는 현재 해석을 고치는 것이다. 링크는 원문의 참조 위치로
유지하고, 해당 절의 맥락을 읽는 기존 추출 경로가 실제 이름과 설명을 구성하게 하는 범위를 검토한다.
한 글자 이름 `L`·`렌`도 유효할 수 있으므로 글자 수나 특정 문자만으로 이름을 없애는 방식으로 해결하지 않는다.
구조적 목록 처리가 확보하던 실제 인물·사물 목록의 누락 여부도 함께 비교해야 한다.

## 6. 수정 전 광고·주석 점검과 정리 방향

사용자의 추가 요구: 광고문 같은 의미 없는 문구와 본문에 무관한 주석도 작품 항목에서 제외해야 한다.

현행 `discoveryHTMLSections`는 `script`, `style`, `nav`, `footer`, `aside` 등의 영역을 건너뛴다.
`discoveryHTMLBoilerplateContainer`는 일부 class/id/role의 광고·댓글·메뉴 표시를 인식한다.
HTML의 `<!-- ... -->` 주석은 본문 텍스트로 취급하지 않는다.

합성 HTML에서 확인한 범위:

- HTML 주석, `nav`, `div class="advertisement"`, `div class="comments"` 내용은 section에서 제외된다.
- 평범한 `div/p`에 들어 있는 “지금 가입하고 할인 혜택을 받으세요”는 section으로 남는다.
- 별도 광고 표시가 없는 연결 목록의 “무료 가입”, “특별 할인”은 구조적 개체 후보가 된다.
- 능력의 발동 조건을 설명하는 일반 각주 문단은 파서에 남는다. 그러나 기존 문서 추출·자동 검토
  프롬프트에는 `footnotes`를 일괄 제외/거부 대상으로 적은 부분이 있다. 필요한 각주까지 빠질 위험은
  `SOURCE_VERIFIED`이며 실제 모델이 얼마나 제외했는지는 이번에 측정하지 않았다.

정리 방향은 **웹페이지를 운영하는 문구와 작품 내용을 설명하는 문구를 구분해서 검색 본문을 만드는 것**이다.
광고·가입 안내·메뉴·독자 댓글·편집 작업 메모는 원작의 인물이나 사실로 승격하지 않는다.
작품 속 광고나 게시판이 이야기의 일부인 경우, 인용 대사, 설정의 조건·예외가 적힌 각주에는 작품 정보가 있다.
그런 문구는 원래 문맥과 연결해 읽는다. 각주 번호 자체를 별도 개체로 만들지 않는다.

원작 RAG 색인을 추가하는 것만으로 수집 때 생긴 잘못된 항목이 자동으로 사라지지는 않는다.
현재 HTML 해석과 기존 추출·검토 프롬프트의 범위를 함께 점검하고, 이미 만들어진 자료의 처리는
원문·작업 기록으로 영향 범위를 확인한 후 별도 작업으로 결정한다. 이번에는 정리·삭제를 실행하지 않았다.

## 7. 원문 RAG 진행 순서와 검증 기준

1. **수집 품질:** 위 적용 기록의 수정과 오프라인 검증을 진행했다. 실제 웹 수집/모델에서는
   정상 인물 목록, 한 글자 이름, 표, 설정 각주, 광고와 무관한 본문이 함께 보존되는지 추가 확인한다.
2. **원문 검색·읽기:** 보존 문서로 위치가 확인되는 작은 시험 자료를 만들고 원문 구간 검색과 인접 문맥 읽기를 검증한다.
3. **질문 연결:** 기존 편집자가 질문을 생성하고 실제 원작 근거를 받는 경로를 붙인다.
   출판사 사용 여부와 무관하게 검색된 근거가 최종 입력까지 도달하는지 확인한다.
4. **비용과 범위:** 기준 검색, 질문 기반 검색, 추가 읽기의 도달률·문자량·호출 수·실제 시간을 비교한다.
   추가 반복 탐색은 그 결과를 보고 검토한다. 출시 버전·기존 자료 이전 범위는 이 기록에서 확정하지 않는다.

검증 자료에는 숫자·레벨·단위가 있는 표, 별명, 오래된 사건, 앞뒤 문장에 나뉜 조건, 각주 속 예외,
원문에 없는 사실, 원작과 다른 사용자 세션 관계, 본문처럼 섞인 광고, 정상적인 짧은 이름을 포함한다.
기본 기억만/출판사만/편집자만/둘 다와 추천 없음·일부 실패를 같은 자료로 비교한다.
선정됨, 읽힌 근거, 백엔드 조립, 요청 직전 반영, 실제 본문 사용 여부는 별도 증거로 기록한다.
본문 AI가 근거를 따르는 정도와 AC가 근거를 전달했는지를 한 수치로 섞지 않는다.
